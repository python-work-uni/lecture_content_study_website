Hashes, MACs and Signatures: Proving Data Has Not Changed

This week is about the three tools that answer the question “is this exactly what was sent, and who sent it?”. A cryptographic hash gives a short, tamper-evident fingerprint of data. A message authentication code (MAC) adds a shared secret so only the two parties can produce that fingerprint. A digital signature adds a private key, so anyone can verify who signed and the signer cannot later deny it.

Read this first: hold one mental model for the whole week — a hash is a fingerprint, a MAC is a fingerprint stamped with a shared secret, and a signature is a fingerprint stamped with a private key. Everything else is details: how hard fingerprints are to forge (the resistance properties), how the fingerprint is computed (SHA), and how we combine it with encryption (AEAD).

The Integrity Idea: A Fingerprint for Data

Before we can trust a message, we need a cheap way to tell whether even one bit changed in transit. That is the job of a hash.

The goal of a hash function is integrity — we want to ascertain that a received message is the same as the one that was sent. Think of a fingerprint: it is tiny compared with the person, but it is a stand-in that changes completely if the identity changes.

The core idea is to define a function that creates a checksum, called a hash function. The classic exchange works like this:

  1. The sender applies the hash function to the message and obtains a checksum, called the hash value or simply the hash.
  2. The sender encrypts the message (to protect confidentiality) and sends the ciphertext together with the hash value of the plaintext.
  3. The receiver decrypts the message, applies the same hash function, and compares the result with the transmitted hash value.
  4. If the two hash values match, the plaintext must be correct.
Message M→ Hash H(M)→ Send M (encrypted) + hash→ Receiver recomputes and compares

What we are trying to prevent

For secure communication we normally want both confidentiality and integrity. With hash functions we want to prevent two specific attacks:

  • Recovering the plaintext from the hash alone. This does not defeat integrity directly, but it defeats the encryption we are relying on for confidentiality.
  • Finding another bit sequence with the same hash value. If an attacker can do this, they can swap the plaintext for a different one and the hash will not change — so the tampering goes undetected.
💡
Why “plausibility” is not security: you might think you could just look at the decrypted text and judge whether it looks sensible. That fails badly — plausibility is not a reliable way to determine integrity. We need a mathematical check, not a judgement call.
🤔
Pause & predict: If a hash value is only a few dozen bytes but the message is a gigabyte, how many different messages must share that same few-dozen-byte hash? (Hold that thought — it becomes the collision problem in a few sections.)

What a Hash Function Actually Is

A hash function squeezes any-length input into a fixed-length output — and the good ones look random while doing it.

Hash function (H) — a function that takes an input of variable length and produces a fixed-length output h = H(M). It is a one-way function: you can compute the output from the input, but you cannot practically run it backwards.

The output goes by several names depending on context: digest, hash, hash value, checksum and CRC are all terms you will see. They all point at the same idea — a short stand-in value for a longer piece of data.

The crucial contrast: CRC is not designed for cryptography at all, while MD5 and SHA-1 were designed for cryptography but were found to be insufficient. That distinction matters later when we decide what is safe to use.

What makes a hash “good”

  • Given a large set of inputs, the outputs should be evenly distributed.
  • The outputs should emulate randomness — with no obvious pattern linking inputs to outputs.
  • Because the input space is far larger than the output space, collisions are inevitable — two different inputs map to the same output. A good design merely makes them hard to find.
🧠
Memory hook: a hash is a blender. Any fruit goes in, always the same size of smoothie comes out, and you cannot un-blend it back into the original fruit.

What Cryptographic Hashes Are Used For

Message authentication is the headline use; digital signatures and a cluster of everyday tasks follow.

Message authentication (integrity)

Message authentication validates the integrity of a message, and often we also want to confirm the sender’s claimed identity. When a hash function is used for this, the resulting value is commonly called a message digest.

  1. The sender sends the message m and its hash h(m).
  2. The receiver uses the same hash function to compute h(m′) on the received message m′.
  3. The receiver checks whether h(m) = h(m′). A mismatch means either the message or the hash was altered.

The problem: a person-in-the-middle

Hashing alone is vulnerable to a person-in-the-middle attack (also called a man-in-the-middle). An attacker who intercepts the message can replace the message and recompute the hash to match, because the hash function is public and keyless. The receiver sees the altered message with a matching hash and detects nothing.

This is the problem of origin authentication — proving not just that the message is intact, but that it came from the claimed sender. It is closely related to integrity. The standard fix is a Message Authentication Code (MAC), also called a keyed hash function.

Digital signatures

  • The hash value of the message is signed (encrypted) with the sender’s Private Key (PR).
  • Anyone who knows the sender’s Public Key (PK) can verify the message.
  • An attacker would need the sender’s private key to alter the message without detection.

Other applications

🔑 One-way password files

Store the hash of a password rather than the password itself, so a stolen file does not reveal the passwords.

🕵️ Intrusion detection

Hash critical files and watch for any change that would signal an intruder.

🦠 Virus detection

Known malware hashes identify infected or altered files.

🎲 PRF / PRNG

Build a pseudorandom function (PRF) or Pseudorandom Number Generator (PRNG) from the hash.

ℹ️
Key takeaway: a plain hash proves the message was not corrupted, but it cannot prove who sent it. MACs and digital signatures exist to close exactly that gap.

Preimage, Second Preimage and Collision Resistance

Three formal guarantees turn an ordinary hash into a cryptographic hash function.

First, two vocabulary words:

Preimage — a specific input value (or set of values) that produces a particular output. If h = H(x), then x is the preimage of h.
Collision — two different inputs that give the same hash: H(a) = H(b) with a ≠ b.

Every hash function has collisions, because it maps a huge input space into a fixed-size output space. The question is only how hard they are to find. A hash is called a cryptographic hash function when it satisfies all three of the following:

1️⃣ Preimage resistance

Given a randomly chosen output y, it is computationally infeasible to find any x with H(x) = y.

2️⃣ Second preimage resistance

Given a randomly chosen input x, it is computationally infeasible to find a different x′ with H(x) = H(x′).

3️⃣ Collision resistance

It is computationally infeasible to find any pair (x, x′) with x ≠ x′ and H(x) = H(x′).

Notice the phrase “computationally infeasible”, not “impossible”. Brute force is always possible in principle — hash every candidate input until one matches — but a good hash makes that take far too long to be practical.

PropertyWhat the attacker is givenWhat they must findProtected against
PreimageA hash value yAny input x with H(x) = yRecovering the original message from its hash
Second preimageA specific input xA different x′ colliding with xSwapping a message for a forged one with the same hash
CollisionNothing (free choice)Any two inputs that collideBlocking a cheating sender from pre-crafting a pair
🧠
Memory hook: Preimage = “find a key for this lock”. Second preimage = “find another key for this lock”. Collision = “find any two keys that open the same lock”.
🤔
Pause & predict: Which is easier for an attacker — breaking second preimage resistance (find a twin for a given message) or collision resistance (find any colliding pair)? The next section tells you why the answer surprises people.

How the Properties Relate — and Pseudo-randomness

Collision resistance is the strongest of the linked properties; preimage resistance stands off on its own.

  • Collision resistance implies second preimage resistance. Any function that is hard to find any collision in is also hard to find a second input matching a given hash. The reverse is not always true.
  • Preimage resistance stands apart. A function can be preimage resistant without being collision or second-preimage resistant, and vice versa. No strict implication runs between preimage and the other two.
  • Collision resistance is the strongest of the two related properties. If an attacker can break second-preimage resistance, they have also broken collision resistance. So collision resistance is the hardest to satisfy — and (confusingly) the easiest to attack, as the birthday section shows.

In short: a successful second-preimage attack implies a successful collision attack, but not the other way around. And a successful collision can sometimes be all the attacker needs.

Pseudo-randomness

Pseudo-randomness is the property of a sequence that appears random but is produced by a deterministic process. It is not traditionally listed as a requirement of cryptographic hash functions, but it is implied, and the three resistance properties depend on the randomness of the output.

  • Cryptographic hashes are used for key derivation and pseudorandom number generation.
  • In integrity applications, effectiveness relies on the output behaving randomly.
  • So it is worth checking that a given hash really produces output that looks pseudo-random.
Checking pseudo-randomness on the command line
echo "CYBERSECURITY ENGINEERING" | sha256sum

echo "CYBERSECURITY ENGINEERING" | md5sum

Same input, two very different-looking outputs — no visible structure, no way to guess the next hash from the last. That apparent randomness is exactly what we want.

💡
Why this matters: a function that fulfilled only the three formal properties but produced patterned, predictable output would be dangerous — patterns leak information and make collisions findable. Pseudo-randomness is the quiet fourth requirement.

The Birthday Attack and Output Length

Collisions are far easier to find than intuition suggests — roughly the square root of the number of possibilities.

The birthday problem

If there are 365 days in a year, how many people must be in a room before there is a 50% chance that two of them share a birthday? The surprising answer is just 23 people — far fewer than most people expect.

Why? We are not asking whether someone matches a specific birthday. We are simply asking whether any two people match each other. That gives the attacker vastly more opportunities to find a match.

The proof sketch

Add people one by one and track the probability P(no match) that all birthdays remain unique:

  • 1st person: no conflict possible, so probability = 365/365 = 1.
  • 2nd person: must avoid one date, so probability = 364/365 ≈ 0.99.
  • …and so on, so after k people P(no match) = 1 · (364/365) · … · ((365−k+1)/365).

From birthdays to hashes

Birthday attack — if random variables are chosen from a uniform distribution over the range 0 to N−1, the probability of encountering a repeated element exceeds 50% after about √N choices.

Applied to hashes: a hash with an n-bit output has 2ⁿ possible values, so an attacker needs only about 2^(n/2) attempts for a 50% chance of a collision. The 50% threshold is the standard benchmark in cryptanalysis — better-than-coin-flip odds mean the function is considered practically broken.

This is why output length is a hard security requirement. The currently accepted minimum output length of a cryptographic hash function is n ≥ 160 bits.

"Halve the bits, not the work"
For an n-bit output, collisions arrive after about 2^(n/2) tries — so every extra bit of output only doubles the collision effort, not the search space.
⚠️
Common trap: collision resistance is the hardest property to design but the easiest to attack. The attacker needs any two colliding inputs — maximum freedom, no target to hit. That is fundamentally easier than matching one specific given input.

The SHA Family

One family, three generations: SHA-1 (dead), SHA-2 (workhorse) and SHA-3 (sponge-based backup).

The Secure Hash Algorithm (SHA) is the most prevalent hash function today. It was developed by the National Institute of Standards and Technology (NIST) and introduced as a federal information processing standard, FIPS 180, in 1993.

  1. SHA-0 and SHA-1 produce a 160-bit hash value. They are no longer considered secure because they are susceptible to collisions.
  2. SHA-2 family: NIST introduced SHA-224, SHA-256, SHA-384 and SHA-512 in 2001 (with the revised standard appearing in 2002). This is the family in wide use today.
  3. SHA-3 family: the latest member, released by NIST in 2015, with SHA3-224, SHA3-256, SHA3-384 and SHA3-512. It uses a completely different internal design.

Inside SHA-2: Padding and the Compression Function

SHA-512 pads the message, splits it into blocks, then churns each block through 80 rounds of mixing.

Take SHA-512 as the worked example. It accepts a message of maximum length less than 2¹²⁸ bits, processes it in 1024-bit blocks, and outputs a 512-bit message digest.

Padding and length encoding

  1. The original message of L bits is padded with a single 1 bit followed by enough 0 bits so the total length is congruent to 896 mod 1024 — that leaves room at the end.
  2. A 128-bit encoding of the original length L is appended, bringing the padded message to an exact multiple of 1024 bits.
  3. The padded message is split into N blocks of 1024 bits each: M₁, M₂, …, M_t. These are the “plaintext blocks” feeding the compression chain.
  4. H₀ (the initialisation vector, IV) is a fixed, publicly specified 512-bit constant defined in the standard. It is not secret and not random.
The compression chain
H_i = F(H_(i−1), M_i)    for i = 1 … N   →   digest = H_N

F is the compression function. It takes the previous chaining value and one message block, and produces the next chaining value. Its job is to compress 1024 bits of block plus 512 bits of state down to a new 512-bit state.

What happens inside F?

  • F unpacks H_(i−1) into eight 64-bit working registers a–h, which are transformed across 80 rounds.
  • A message schedule expands the 1024-bit block M_i into 80 round words W₀–W₇₉ — analogous to how the AES key schedule turns one key into many round keys.
  • Each round mixes in one W_t and one public constant K_t. Six of the eight registers simply shift along, so only two new values are computed per round.
  • Davies–Meyer feedforward: after round 79, the final a–h are added mod 2⁶⁴ back to the original H_(i−1) (the long bypass lines in the standard diagram).
  • The result of those eight additions is H_i, which is passed to the next block.
Pad + length→ Split into 1024-bit blocks→ F: 80 rounds of a–h→ Davies–Meyer add mod 2⁶⁴→ H_i

Where SHA-2 is used

  • Widely implemented in security protocols: TLS/SSL, SSH, IPSec and more.
  • Validates and signs digital certificates and documents.
  • Verifies transactions in cryptocurrencies — Bitcoin uses SHA-256.
🧠
Memory hook: SHA-512 is an assembly line: pad the block, run it through 80 identical stations, then bolt the finished part back onto the original state (Davies–Meyer) before the next block arrives.
🤔
Pause & predict: Why include the original message length in the padding? (Because without it, an attacker could craft a different-length message with an identical padded bit sequence — the length field blocks that trick.)

SHA-3 and the Sponge Construction

SHA-3 replaces SHA-2’s eight registers with one big state that is absorbed, permuted, then squeezed.

SHA-3 uses a single unified state of r + c bits passed repeatedly through a permutation f. Instead of SHA-2’s eight working registers, there is one large state that gets permuted again and again. This design is called a sponge.

Absorbing phase

  • Each message block is XORed into the top r bits of the state.
  • Then f scrambles the entire state.
  • The bottom c bits are never directly touched by the message input, which protects the security margin.

Squeezing phase

  • Output is read from the top r bits; f is applied between each read.
  • You can squeeze out as many bits as needed, making SHA-3 naturally an extendable output function.

SHA-2

  • Eight 64-bit working registers a–h.
  • Merkle–Damgård chaining over blocks.
  • Vulnerable to length-extension attacks.

SHA-3

  • One large state of r + c bits.
  • Sponge: absorb, permute, squeeze.
  • No length-extension vulnerability.

Rate vs capacity

Rate r versus capacity c is a tunable trade-off. A larger r means faster hashing (more bits absorbed per round), but a smaller c means lower security. The different SHA-3 variants simply change this split.

No length-extension vulnerability

In SHA-2, an attacker who knows H(m) can compute H(m ∥ extra) without knowing m — the length-extension attack. The sponge structure eliminates this, because the hidden c bits make the full internal state unrecoverable from the output.

💡
Why SHA-3 exists: it is a safety net. Even if SHA-2 were broken, a structurally different design means the same attack would not automatically carry over. Having two unrelated strong designs is good engineering.

Why MACs? Keyless Hashes vs Keyed Authentication

Hashes are keyless, so anyone can forge a matching hash. A MAC incorporates a secret key and closes that door.

The problem with plain hashes

Hashes are keyless. Anyone, including an attacker, can compute a valid hash for a forged message. So a plain hash proves the message was not corrupted but cannot prove who sent it. A MAC fixes this by incorporating a secret key into the computation — think of it as a keyed hash.

Two levels of any authentication mechanism

Any mechanism for message authentication or digital signatures has two levels of functionality:

  • Lower level: a function that generates an authenticator — a value used to authenticate a message.
  • Higher level: an authentication protocol that uses that function as a primitive, letting a recipient verify a message.

The functions used to generate an authenticator fall into three classes:

  1. Hash function — used alone it may not provide authentication, because unprotected hash values are exposed to person-in-the-middle attacks.
  2. Message encryption — symmetric, public-key, or both (see below).
  3. Message authentication code (MAC) — the focus of this week.

The four uses of message encryption

The MAC itself

Message Authentication Code (MAC) — a special tag of fixed size, generated using a secret key shared between the communicating parties, that is appended to the original message. Also known as a cryptographic checksum.
MAC definition
MAC = C(K, M)

Here M is the input message, C is the MAC function, K is the shared key and MAC is the resulting code. The message plus its MAC is transmitted; the receiver recomputes the MAC with the shared key and compares. If the MACs match, and the key is known only to sender and receiver, three things follow:

  • The receiver is assured the message has not been altered — any change without a matching MAC causes a mismatch, and the attacker cannot produce a valid MAC without the key.
  • The receiver is assured of the message’s origin — no other party has the key needed to generate the valid MAC.
  • If the message includes a sequence number (as in HDLC, X.25 and TCP), the receiver can verify the sequence integrity — an attacker cannot silently change the order.

Note: the basic MAC process does not provide confidentiality. That can be added by encrypting either before or after the MAC — the next sections show how.

🤔
Pause & predict: Alice sends Bob a message and MAC, both computed with a shared key. Can Alice later deny sending it, with Bob as the only witness? (No — Bob could have computed the same MAC himself, so a third party cannot tell. That limitation is why digital signatures exist.)

MAC Requirements and the HMAC Construction

A MAC must be a strong hash plus a secret — HMAC mixes that secret in twice with two padding constants.

Requirements

The intuition: given the MAC t for a message m, an attacker should not be able to generate a valid MAC for a different message. Formally, a function used as a MAC must satisfy:

  1. It must have all the resistance properties of a cryptographic hash function.
  2. It must be computationally infeasible to predict a correct MAC t′ for a message m′ ≠ m, even when the attacker is allowed to know any other combinations of (m, t).

A cryptographic hash function takes care of the first requirement. Mixing in a secret s addresses the second, provided the resistance properties hold.

ℹ️
Scope note: MACs can also be built from a symmetric block cipher, but in this course we focus only on MACs derived from a cryptographic hash function.

HMAC (Hash-based Message Authentication Code)

Several methods exist for folding a secret key into a hash algorithm, but the most widely used is HMAC. It was published as RFC 2104, is the obligatory MAC for IP security (IPSec), is used in internet protocols such as SSL, and is ratified as the NIST standard FIPS 198.

HMAC
HMAC(K, M) = H[(K ⊕ opad) ∥ H[(K ⊕ ipad) ∥ M]]
  • H can be any cryptographic hash function (e.g. SHA-2, SHA-3, MD5, SHA-1).
  • K is the shared secret key; M is the input message.
  • opad and ipad are publicly known constant bit strings. They are required for HMAC’s security proof to hold, though their precise values matter little.
  • ipad = 00110110 (hex 36) repeated b/8 times; opad = 01011100 (hex 5C) repeated b/8 times, where b is the block size in bits.

The HMAC algorithm, step by step

  1. Pad the key. Append zeros to the left of K to create a b-bit string K⁺. (If K is 160 bits and b = 512, append 44 zeroes.)
  2. Inner pad. XOR K⁺ with ipad to produce the b-bit block S_i.
  3. Append the message. Append M to S_i.
  4. Hash once. Apply H to the stream from step 3.
  5. Outer pad. XOR K⁺ with opad to produce the b-bit block S_o.
  6. Append the inner hash. Append the hash result from step 4 to S_o.
  7. Hash again and output the result. That double hashing is the “nested” structure you see in the formula.
ipad → H → opad → H
"Inner first, outer last"
The message is hashed with the key ⊕ ipad (inner), then that result is hashed again with the key ⊕ opad (outer). Two different key-derived masks stop an attacker from extending or splicing the hash.
🧠
Memory hook: HMAC is a double lock. The inner hash proves the message, the outer hash protects that proof with the key.

HMAC Security, the MD5 Question, and Applications

HMAC’s strength is provably tied to its underlying hash — and because the key is secret, even a weak hash becomes hard to attack online.

The security of any MAC based on an embedded hash function depends in some way on the cryptographic strength of that hash function and the key size. The appeal of HMAC is that its designers proved an exact relationship between the strength of the embedded hash function and the strength of HMAC.

Can we use MD5 for HMAC?

According to the birthday paradox, 2⁶⁴ attempts give at least a 50% chance of a collision in MD5 (128-bit output), which looks feasible with today’s technology. So can we use MD5 inside HMAC? The answer is yes — and the reason teaches an important lesson.

  • To attack MD5 directly, the attacker can choose any set of messages and work offline on a dedicated machine to find a collision, because the algorithm and the default IV are public.
  • But when attacking HMAC, the attacker cannot generate (message, code) pairs offline because they do not know the secret key K.
  • They must instead observe sequences of messages generated by HMAC under the same key and attack those known messages.
  • This requires about 2⁶⁴ observed blocks generated with the same key. On a 1-Gbps link, the attacker would need a continuous stream of messages with no key change for about 150,000 years to succeed.

So attacking HMAC-with-MD5 is infeasible in practice. If speed is a concern, HMAC-MD5 can be preferred over HMAC-SHA-1. (That does not mean MD5 is safe for plain hashing — it is not.)

Applications of HMAC

HMAC is widely used wherever two parties share a secret key and need to verify both the authenticity and integrity of a message — not just that it arrived uncorrupted, but that it came from a trusted sender.

☁️ API request signing (e.g. AWS Signature V4)

The client signs the full request (URL, headers, body, timestamp) with HMAC using a shared secret. The server recomputes the signature independently; a mismatch means the request was tampered with or replayed. This provides integrity and replay protection on top of authentication.

🎫 JWT and one-time passwords

HMAC is used to sign JSON Web Tokens (JWT) and to generate One-Time Passwords (HOTP/TOTP).

⚠️
Common trap: HMAC alone does not guarantee confidentiality — the message is still readable. In practice this happens over an encrypted TLS connection, which handles confidentiality separately.
🤔
Pause & predict: Why does a secret key turn a “broken” hash into a safe MAC? (Because the attacker can no longer compute hashes offline — they need real traffic under the secret key, which may take longer than the universe provides.)

Authenticated Encryption and the Four Orderings

Combining encryption and authentication by hand is error-prone — AE bundles them into one operation, but the order still matters.

So far we have treated confidentiality (encryption) and authenticity (MAC) as separate. Combining them correctly is tricky and error-prone, and mistakes such as misordering or misusing the two primitives create vulnerabilities.

Authenticated Encryption (AE) — provides confidentiality and integrity/authentication in a single primitive. Its security depends on how tightly the two are coupled — ideally, no plaintext is released until integrity is verified.
Authenticated Encryption with Associated Data (AEAD) — extends AE by allowing additional data (the associated data) that is authenticated but not encrypted. It is sent in plaintext but included in the integrity check.

AE matters because a MAC alone gives integrity and authenticity but not confidentiality, leaving data exposed; and using encryption and MAC separately invites developer mistakes. Integrating them reduces those errors — important for secure messaging and financial transactions.

The lesson: all four can be made secure, but only if the construction is carefully specified. The safest general instinct is Encrypt-then-MAC, because integrity is checked on the ciphertext before anything is trusted.

🧠
Memory hook: say the protocol order as “TLS authenticates first, IPSec encrypts first, SSH does both independently”.

AEAD in Practice: GCM and CCM

Two standard AEAD modes: GCM (fast and parallel, but brittle) and CCM (sequential, but ideal for constrained devices).

AEAD extends AE by also authenticating data that must stay readable (headers, metadata) but still needs tamper protection. Its MAC tag computation and encryption can be performed in parallel, making AEAD schemes efficient. It is defined for both block ciphers and stream ciphers. Two constructions dominate:

GCM (Galois/Counter Mode)

  • Currently the strongest and most widely used block-cipher AEAD mode, and highly efficient because it is parallelisable.
  • Follows the Encrypt-then-MAC paradigm: the message is encrypted in a variant of CTR mode, and the resulting ciphertext is multiplied with key material and message-length information over GF(2¹²⁸) to generate the authenticator tag.
  • The standard also specifies a mode that supplies the MAC only, called Galois MAC.
  • Uses two functions: GHASH, a keyed hash function, and GCTR, CTR mode with counters incremented by one.
  • Very brittle in implementation. Nonce reuse, for example, can completely break security. Always use a well-vetted library rather than implementing it yourself.

CCM (Counter with CBC-MAC)

  • Standardised by NIST to support the security requirements of IEEE 802.11 WiFi networks.
  • A carefully engineered variation of MAC-and-Encrypt: it computes CBC-MAC over the message to generate a tag, then encrypts both the message and the tag using CTR mode — so it is a MAC-then-Encrypt construction.
  • Sequential (the MAC must complete before encryption begins), making it less efficient than GCM, but widely used in constrained environments such as IoT and WiFi.
  • A single key K is used for both encryption and MAC. This is safe here for the same reason as GCM: the two uses are carefully separated by the design and accounted for in the security proof.

GCM

  • Encrypt-then-MAC, parallel.
  • Fast; best throughput and latency.
  • Brittle: nonce reuse is catastrophic.

CCM

  • MAC-then-Encrypt, sequential.
  • Slower, but simple and safe.
  • Ideal for IoT and 802.11 WiFi.
⚠️
Common trap: never hand-roll GCM. A single repeated nonce can reveal the key material and destroy all guarantees. Use a standard library.

Digital Signatures: The Need and Basic Operation

Signatures replace the shared secret with a private key, so anyone can verify and the signer cannot deny.

Why MACs are not enough

Hashes give us integrity but no notion of who sent the message. MACs give integrity and authenticity, but rely on a shared secret key — both Alice and Bob must already have agreed on a key. That creates three fundamental limitations:

  • Cannot prove to a third party that Alice sent the message. Bob could have computed the same MAC himself, so a judge or external verifier cannot distinguish who created it.
  • Does not scale. If Alice wants to communicate securely with 1000 people, she needs 1000 different keys.
  • No non-repudiation. Alice can later deny sending the message, and there is no way to prove otherwise.

Digital signatures solve this using asymmetric (public-key) cryptography: Alice signs with her private key and anyone can verify with her public key.

  • No shared secret is needed.
  • A third party can verify the signature independently.
  • Alice cannot deny signing — this is non-repudiation.

The basic operation

Consider Bob sending a message to Alice. Bob does not care about confidentiality, but he wants Alice to be sure the message is from him:

  1. Bob computes a hash of the message with a secure hash function such as SHA-512.
  2. He feeds that hash, along with his private key, into the signature generation algorithm, producing a short block — the digital signature.
  3. He sends the message with the signature attached.
  4. Alice recomputes the hash of the message and provides it, plus Bob’s public key, to the verification algorithm.
  5. If the algorithm says the signature is valid, Alice is assured of two things.

✍️ It was signed by Bob

No one other than Bob has access to his private key, which is required to create a signature verifiable with his public key.

🔒 The message is intact

Without access to Bob’s private key, no one can alter the message to produce a hash value that verifies with Bob’s public key.

⚠️
Critical caveat: this only works if the verifier can be certain that the public key they hold actually belongs to Bob. A forged or substituted public key breaks every guarantee. This is the problem of public key authentication, solved by PKI (Public Key Infrastructure) and digital certificates — covered later in the course.
🤔
Pause & predict: MACs require a shared key, signatures require a key pair. Which property does the key pair unlock that no shared key ever can? (Non-repudiation — proof to a third party.)

Two Approaches: RSA and DSA

Both hash the message with SHA, but RSA is a general-purpose scheme while DSA is signature-only.

There are two main approaches for constructing digital signatures. Both use SHA for hashing the message.

(a) The RSA approach

RSA is a general-purpose public-key scheme — it can also be used for encryption and key exchange. In 2013 an expanded version of the standard, FIPS-186-4, incorporated RSA-based signature algorithms.

  1. The message is passed through a hash function to produce a secure, fixed-length hash code.
  2. That hash code is encrypted using the sender’s private key to form the signature.
  3. The message and the signature are transmitted together.
  4. The recipient hashes the message, and decrypts the signature using the sender’s public key.
  5. If the calculated hash matches the decrypted signature, the signature is accepted as valid.

Because only the sender knows the private key, only the sender could have produced a valid signature.

RSA signature (informally)
signature = E(PRa, h(m))   ·   verify: h(m) =? D(PUa, signature)

(b) The DSA approach

The Digital Signature Algorithm (DSA) was proposed in 1991 and published by NIST via FIPS 186. It uses SHA and provides only the digital signature function. Unlike RSA, it cannot be used for encryption or key exchange. It is derived from the ElGamal signature scheme, and NIST intentionally standardised it as signature-only, excluding the encryption capability ElGamal supports.

  • The message is hashed using SHA, producing h(m).
  • The hash is provided to a signature function, along with a random number k generated for this particular signature.
  • The signature function also depends on the sender’s private key PRa and a set of parameters shared across a group of users — the global public key PUG.
  • The resulting signature consists of two components, s and r.
  • At the receiver, the hash of the incoming message is generated and fed, with the signature, into a verification function that depends on PUG and the sender’s public key PUa. The output equals the component r if the signature is valid.
DSA domain parameters — let p be prime, q a prime divisor of (p − 1), and g an element of order q in ℤp. The global public key PUG = (p, q, g) is shared by all users. The user’s private key is a random number x with 0 < x < q, and the public key is derived from it.

In the underlying modular-exponentiation setting, parties compute values such as X = g^a mod p and a shared secret k = Y^a mod p = X^b mod p. This is the same discrete-logarithm mathematics that underpins Diffie–Hellman key exchange, and it is where DSA’s global parameters come from.

Key Takeaways

If you remember nothing else, remember this.

1

A hash function maps variable-length input to a fixed-length output h = H(M), is one-way, and is used for integrity. Its output is also called a digest, hash value or checksum.

2

A plain hash cannot prove origin. Because it is keyless, an attacker can replace the message and recompute the hash — a person-in-the-middle attack.

3

Three resistance properties: preimage resistance, second preimage resistance and collision resistance. Collision resistance implies second preimage resistance, but not preimage resistance.

4

The birthday attack finds collisions in about 2^(n/2) attempts for an n-bit hash, so output length must be at least 160 bits (2⁸⁰ attempts).

5

SHA is the standard family: SHA-1 (160-bit, insecure), SHA-2 (SHA-224 to SHA-512, 2001) and SHA-3 (sponge, 2015). Use SHA-2 today, with SHA-3 as a structurally different alternative.

6

SHA-512 pads with a 1 bit and the original length, splits the message into 1024-bit blocks, and runs each through 80 rounds of compression with a Davies–Meyer feedforward.

7

SHA-3 uses a sponge with a state of r + c bits: absorb, permute, squeeze. The hidden capacity bits remove the length-extension vulnerability.

8

A MAC is a keyed hash that adds a shared secret, giving integrity and origin authentication. It does not give confidentiality.

9

HMAC(K, M) = H[(K ⊕ opad) ∥ H[(K ⊕ ipad) ∥ M]]. It is RFC 2104 and FIPS 198, and even HMAC-MD5 is practically safe because the attacker cannot work offline.

10

Authenticated encryption combines confidentiality and integrity. The four orderings are H→E, A→E (TLS), E→A (IPSec, strongest) and E+A (SSH); AEAD adds authenticated associated data, with GCM and CCM as the main modes.

11

Digital signatures use public-key cryptography — sign with the private key, verify with the public key — adding third-party verifiability and non-repudiation that MACs cannot provide.

12

RSA is general-purpose; DSA is signature-only. DSA uses global parameters PUG = (p, q, g), a per-message random k, and produces a signature (s, r). Signatures depend on trustworthy public keys (PKI).

Glossary

Every term you need to speak this week’s language.

Hash function (H)
A one-way function that takes an input of variable length and produces a fixed-length output h = H(M). Used for integrity.
Digest (hash value)
The fixed-size output of a hash function. Also called a hash, checksum or message digest depending on context.
Collision
Two different inputs that produce the same hash value, H(a) = H(b) with a ≠ b. Always possible; a good hash makes them hard to find.
Preimage
An input value that produces a given output: if h = H(x), then x is the preimage of h.
Preimage resistance
Given a randomly chosen hash value y, it is computationally infeasible to find any x with H(x) = y. Protects confidentiality of the original message.
Second preimage resistance
Given a randomly chosen input x, it is computationally infeasible to find a different x′ with H(x) = H(x′). Prevents substituting a forged message.
Collision resistance
It is computationally infeasible to find any pair (x, x′) with x ≠ x′ and H(x) = H(x′). Implies second preimage resistance; the strongest of the linked properties.
Birthday attack
If values are chosen uniformly from 0 to N−1, a repeat appears with more than 50% probability after about √N choices. For an n-bit hash, about 2^(n/2) attempts suffice.
Pseudo-randomness
The property of appearing random while being produced deterministically. Not formally required of hashes, but implied and relied upon by the resistance properties.
Length field
A security measure: the original message length is encoded into the padding, making it harder for an attacker to produce a different message with the same hash.
SHA-2
NIST’s 2001 family: SHA-224, SHA-256, SHA-384 and SHA-512 (plus SHA-512/224, SHA-512/256). The current workhorse hash family.
SHA-3
NIST’s 2015 family (SHA3-224 to SHA3-512) based on a sponge construction — a structurally different alternative to SHA-2.
Sponge construction
SHA-3’s design: a state of r + c bits that absorbs message blocks, permutes with f, then squeezes output. Rate r trades speed against security capacity c.
Length-extension vulnerability
A SHA-2 weakness: knowing H(m), an attacker can compute H(m ∥ extra) without knowing m. SHA-3’s hidden capacity bits prevent it.
Salt & rainbow table
A rainbow table is a precomputed lookup of common inputs to hashes. A salt — a random string concatenated with the plaintext before hashing — defeats such lookups.
Message Authentication Code (MAC)
A fixed-size tag generated from a message and a shared secret key, appended to the message. Gives integrity and origin authentication. MAC = C(K, M).
Keyed hash function
Another name for a MAC — a hash computation that incorporates a secret key.
HMAC
Hash-based MAC: HMAC(K, M) = H[(K ⊕ opad) ∥ H[(K ⊕ ipad) ∥ M]]. RFC 2104; FIPS 198; obligatory for IPSec. The most common form of MAC.
ipad and opad
Publicly known constant bit strings (36 and 5C) XORed with the padded key in HMAC. Required for its security proof.
Origin authentication
Proving that a message came from the claimed sender, not just that it was uncorrupted. A plain hash cannot do this; a MAC can.
Authenticated Encryption (AE)
A single primitive providing confidentiality and integrity/authentication together, so plaintext is ideally not released until integrity is verified.
AEAD
Authenticated Encryption with Associated Data: extends AE to authenticate additional data (such as headers) that is sent in plaintext but included in the integrity check.
GCM (Galois/Counter Mode)
A fast, parallelisable AEAD block-cipher mode following Encrypt-then-MAC. Uses GHASH and GCTR over GF(2¹²⁸). Brittle: nonce reuse breaks security.
CCM (Counter with CBC-MAC)
A NIST AEAD mode for WiFi (802.11) and IoT. Computes CBC-MAC over the message, then encrypts message and tag in CTR mode — a MAC-then-Encrypt construction.
GHASH and GCTR
GCM’s two building blocks: GHASH is a keyed hash producing the authenticator tag; GCTR is CTR mode with counters incremented by one.
Digital signature
A short block produced by signing a message hash with the sender’s private key. Anyone with the public key can verify it, proving origin and integrity.
RSA signature approach
Hash the message, encrypt the hash with the sender’s private key, and verify by decrypting with the public key and comparing. RSA is general-purpose (also encryption and key exchange).
DSA (Digital Signature Algorithm)
A signature-only scheme proposed in 1991 (FIPS 186), derived from ElGamal. Uses a per-message random k and produces a two-part signature (s, r).
Global public key (PUG)
The DSA system-wide parameters PUG = (p, q, g), where p is prime, q divides (p−1), and g has order q in ℤp. Shared by all users.
Non-repudiation
The guarantee that a signer cannot later deny having signed. Digital signatures provide it; MACs do not, because both parties share the key.

No terms in this category.

Practice Questions

Look away from the page first — retrieval is what builds memory.

Answer, reveal, then tick “Mastered”. Your progress is saved.
Q1

Define a hash function and explain what “one-way” means. What is its output called?

Answer: A hash function H takes an input of variable length and produces a fixed-length output h = H(M). “One-way” means you can compute the output from the input, but you cannot practically reverse the process to recover the input. The output is called a hash value, hash, digest, checksum or message digest depending on context. Its principle objective in cryptography is data integrity.
Q2

Why are collisions mathematically guaranteed for any hash function, and what does it mean for a hash to be “good”?

Answer: The input space is effectively infinite while the output space is finite, so many inputs must map to each output — collisions exist by counting alone. The question is only how hard they are to find. A “good” hash distributes outputs evenly and makes them emulate randomness, and it makes collisions computationally infeasible to find.
Q3

Describe hash-based message authentication, then explain the person-in-the-middle attack that defeats it.

Answer: The sender sends the message m with its hash h(m); the receiver recomputes h(m′) on the received message and compares. If they match, the message is unchanged. But because the hash function is keyless, an attacker who intercepts the message can replace it and recompute a matching hash. The receiver cannot detect the substitution. This is the problem of origin authentication, and it is why MACs are needed.
Q4

State the three resistance properties of a cryptographic hash function, and distinguish second preimage from collision resistance.

Answer: (1) Preimage resistance: given a random output y, it is infeasible to find any x with H(x) = y. (2) Second preimage resistance: given a random input x, it is infeasible to find a different x′ with H(x) = H(x′). (3) Collision resistance: it is infeasible to find any pair (x, x′), x ≠ x′, with H(x) = H(x′). Second preimage fixes the first input for the attacker; collision gives the attacker free choice of both inputs, which is why collisions are easier to find.
Q5

Explain the relationships among the three properties. Which implies which, and which stands apart?

Answer: Collision resistance implies second preimage resistance, but not the reverse. Preimage resistance stands apart — no strict implication links it to the other two, so a function can have it without the others and vice versa. Collision resistance is the strongest of the two linked properties. Equivalently, a successful second-preimage attack implies a successful collision attack.
Q6

Explain the birthday attack and use it to justify the 160-bit minimum output length.

Answer: If values are drawn uniformly from 0 to N−1, a repeat appears with more than 50% chance after about √N choices — the birthday problem (just 23 people give a 50% shared-birthday chance). For an n-bit hash there are 2ⁿ outputs, so only about 2^(n/2) attempts are needed. A 64-bit output falls to 2³², trivial on modern hardware. At n ≥ 160, the attacker needs 2⁸⁰ attempts, which remains infeasible. Fifty per cent is the standard benchmark: better-than-coin-flip odds mean the hash is practically broken.
Q7

What is pseudo-randomness, and why does it matter even though it is not formally listed as a hash requirement?

Answer: Pseudo-randomness is the property of a sequence that looks random but is produced by a deterministic process. It is implied rather than stipulated: cryptographic hashes are used for key derivation and pseudorandom number generation, and the three resistance properties depend on the output being random. In integrity applications the security relies on outputs behaving randomly, so it is worth verifying that a given hash really does produce apparently random output.
Q8

You are given the hex string 5baa61e4c9b93f3f0682250b6cf8331b7ee68fd8. Which hashing algorithm most likely produced it, and how would rainbow tables recover the plaintext?

Answer: There are 40 hex characters, and two hex characters represent a byte, so the output is 20 bytes = 160 bits. Only SHA-1 among the common algorithms produces a 160-bit digest, so it is SHA-1. Rainbow tables precompute hashes of common words into lookup tables; an online lookup returns the plaintext “password”. Defences include salt — a random string concatenated with the plaintext before hashing — and using modern hashes rather than MD5 or SHA-1.
Q9

Describe how SHA-512 handles a message from start to finish, including padding and the compression function.

Answer: SHA-512 accepts a message shorter than 2¹²⁸ bits and outputs a 512-bit digest in 1024-bit blocks. The message of L bits is padded with a single 1 bit and enough 0 bits so the length is congruent to 896 mod 1024, then a 128-bit encoding of L is appended, making the total a multiple of 1024. The padded message is split into blocks M₁ … M_t. The fixed, public 512-bit IV H₀ seeds the chain. Inside the compression function F, H_(i−1) is unpacked into eight 64-bit registers a–h; a message schedule expands each block into 80 words W₀–W₇₉; 80 rounds each mix in one W_t and one constant K_t; finally a Davies–Meyer feedforward adds the registers mod 2⁶⁴ back to H_(i−1) to give H_i.
Q10

Explain SHA-3’s sponge construction and why it resists length-extension attacks.

Answer: SHA-3 keeps a single state of r + c bits and repeatedly applies a permutation f. In the absorbing phase, each message block is XORed into the top r (rate) bits and f scrambles the whole state; the bottom c (capacity) bits are never directly touched by the message. In the squeezing phase, output is read from the top r bits, applying f between reads, so it is naturally an extendable output function. Rate versus capacity is a trade-off: larger r is faster, smaller c is less secure. Because H(m) does not reveal the hidden capacity bits, an attacker cannot reconstruct the full state to compute H(m ∥ extra) — so the SHA-2 length-extension weakness is gone.
Q11

Why do we need MACs when we already have hashes? State the two requirements a MAC function must satisfy and the three assurances a matching MAC gives.

Answer: Hashes are keyless, so an attacker can compute a valid hash for a forged message — they prove the message was not corrupted but not who sent it. A MAC mixes in a secret key, so it is a keyed hash. Requirements: (1) it must have all the resistance properties of a cryptographic hash function, and (2) it must be computationally infeasible to predict a correct MAC t′ for a different message m′ ≠ m, even knowing other (m, t) pairs. A matching recomputed MAC assures the receiver that (a) the message was not altered, (b) the message came from the claimed origin, and (c) any sequence number is intact. MACs alone do not provide confidentiality.
Q12

Write the HMAC formula, explain its parts, and answer: can we use MD5 for HMAC?

Answer: HMAC(K, M) = H[(K ⊕ opad) ∥ H[(K ⊕ ipad) ∥ M]]. H is any cryptographic hash; K is the shared secret; M is the message; ipad (36) and opad (5C) are public constants required for the security proof. The message is hashed with the key XOR ipad, then that result is hashed with the key XOR opad. Yes, MD5 can be used inside HMAC. A direct MD5 attacker can find collisions offline, but against HMAC they do not know the key, so they cannot generate (message, code) pairs offline. They would need to observe about 2⁶⁴ blocks under the same key — roughly 150,000 years on a 1-Gbps link. HMAC-MD5 may be chosen over HMAC-SHA-1 if speed matters.
Q13

Name the four approaches to authenticated encryption, say which protocol uses each, and describe GCM and CCM.

Answer: Four approaches: (1) Hashing then encryption (H→E): send E(K, (M ∥ H(M))). (2) Authentication then encryption (A→E, MAC-then-Encrypt): E(K2, [M ∥ MAC(K1, M)]) — used by SSL/TLS. (3) Encryption then authentication (E→A, Encrypt-then-MAC): send (E(K2, M), MAC(K1, C)) — used by IPSec and considered strongest. (4) MAC-and-Encrypt (E+A): (E(K2, M), MAC(K1, M)) — used by SSH. GCM is an Encrypt-then-MAC AEAD mode: it encrypts in a CTR variant, then authenticates over GF(2¹²⁸) using GHASH and GCTR; it is fast and parallel but brittle, so nonce reuse is catastrophic and libraries must be used. CCM is a MAC-then-Encrypt mode: it computes a CBC-MAC tag, then encrypts message and tag in CTR mode; it is sequential and slower but ideal for WiFi (802.11) and IoT. AEAD additionally authenticates associated data that stays in plaintext.
Q14

What do digital signatures add over MACs, and how do the RSA and DSA approaches differ?

Answer: MACs need a shared secret, so they cannot prove to a third party who sent a message, do not scale (n keys for n people) and give no non-repudiation. Signatures use asymmetric cryptography — sign with the private key, verify with the public key — so anyone can verify, no shared secret is needed, and the signer cannot deny signing. A forged or substituted public key would break this, which is why PKI and digital certificates matter. Both approaches hash the message with SHA. RSA (FIPS-186-4, 2013) is general-purpose: the hash is encrypted with the sender’s private key to form the signature, and verified by decrypting with the public key and comparing. DSA (FIPS 186, 1991, derived from ElGamal) is signature-only — no encryption or key exchange. It uses global public parameters PUG = (p, q, g) shared by all users, the sender’s private key, and a per-message random k, producing a two-part signature (s, r) verified with PUG and PUa.
