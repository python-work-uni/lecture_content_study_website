INFO3616 · Week 6 · Hashes, MACs, and Signatures

Fingerprints, Seals, and Signatures

How do you know a message is exactly the one that was sent, and that it came from who it claims? A cryptographic hash gives a message a tamper-evident fingerprint. A Message Authentication Code (MAC) adds a shared secret so the fingerprint also proves origin. A digital signature replaces the shared secret with public-key cryptography so anyone can verify and the signer cannot deny it. Along the way: the birthday attack, length extension, HMAC, SHA-2, SHA-3 and authenticated encryption.

Read this first: a hash is a fingerprint (integrity only), a MAC is a sealed fingerprint (integrity + origin, but symmetric, so no non-repudiation), and a signature is a notarised fingerprint (integrity + origin + non-repudiation, asymmetric).

Hash Functions and the Integrity Goal

A hash squashes any input into a fixed-size fingerprint whose first security job is to prove a message arrived unchanged.

A hash function is a one-way function: it takes a variable-length block of data M and produces a fixed-size output h = H(M). The forward computation is easy; recovering the input from the output is infeasible. The output is called a digest, hash value, checksum or CRC depending on context, and a message digest when used for authentication.

Hash function — a function mapping an input of arbitrary length to a fixed-length output h = H(M), easy to compute forward and infeasible to invert.

Since the input space is vastly larger than the finite output space, two different inputs must map to the same output. A collision is exactly that: H(a) = H(b) with a ≠ b. So the design question is never "how do we remove collisions?" but "how do we make finding them hard?" A good hash produces outputs that are evenly distributed and emulate randomness.

Collisions are certain, not a bug; cryptographic strength is about the difficulty of finding one, not its existence.

Commonly used hash functions

CRC (CRC-16, CRC-32, …), MD5 (Message Digest), SHA-1 / SHA-2 / SHA-3 (Secure Hash Algorithm) and RIPEMD160. Two caveats: CRC was never designed for cryptography, and MD5 and SHA-1 were designed for it but found insufficient. MD5 is no longer used; SHA-1 is in phase-out.

The integrity workflow

The principal objective of hash functions in cryptography is data integrity: ascertaining that a received message matches the one sent.

Message M→ Hash H(M)→ Encrypt + send (M, h)→ Receiver decrypts→ Recompute & compare
  1. Sender hashes the message to obtain a checksum, the hash value.
  2. Sender encrypts and sends the message together with the hash value of the plaintext.
  3. Receiver decrypts and re-hashes, then compares with the transmitted value.
  4. Match means correct: if the hashes agree, the plaintext is intact.

Two conditions for this to work

ConditionWhy
(a) The message cannot be deduced from the hashOtherwise confidentiality is compromised, defeating the encryption (not integrity itself).
(b) No substitute plaintext with the same hashOtherwise an attacker replaces the plaintext without changing the hash, making the alteration undetectable.

A hash satisfying these criteria is a cryptographic hash function.

From Hash to Cryptographic Hash: Padding and the Length Field

A cryptographic hash adds structure to the input before hashing, and that structure is itself a security feature.

A cryptographic hash function is a hash suitable for security applications that satisfies the two conditions above; it acts like one-way encryption. Before hashing, the variable-length input is padded to an integer multiple of a predetermined fixed length, the block size. Padding is not just zeros: it incorporates the length of the original message in bits. This length field is a deliberate security measure that makes it harder to produce H(a) = H(b) with a ≠ b.

The hashing pipeline
M (variable length) → pad to multiple of block size (+ length field) → hash → h (fixed length)

The input of variable length is padded to a multiple of the block size and the padding includes the true input length, so length extension becomes worth understanding once we know the Merkle–Damgård chain.

What we are trying to prevent

We want both confidentiality and integrity; with hashes we aim to prevent two things. First, recovering the plaintext from the hash value alone, which defeats our encryption though not integrity itself. Second, finding a bit sequence with the same hash value; decryption of substituted bits may look implausible, but plausibility is not a reliable way to determine integrity.

Hashing gives integrity, never confidentiality: hashing a message does not hide it, so if you need privacy you still encrypt.

Applications of Cryptographic Hash Functions

Hashing alone proves a message was not corrupted but cannot prove who sent it, and that gap opens the door to MACs and signatures.

Message authentication and its weakness

Message authentication verifies a message's integrity, often with the added requirement of confirming the sender's claimed identity. The sender hashes the message and sends message plus hash; on receipt the receiver re-hashes and compares, and any disparity implies the message or hash was altered.

Alice: m→ h = H(m)→ Send (m, h)→ Bob: H(m′) =? h

This is vulnerable to a person-in-the-middle attack: an attacker (Darth) intercepts the message, replaces it, and also alters the digest to match. Bob detects nothing. The problem is called origin authentication, closely related to integrity, and the fix is to protect the digest.

A keyless hash proves "this data was not corrupted in transit" but says nothing about who supplied it, since anyone can hash a forged message.

The two fixes

A MAC (also called a keyed hash function) mixes a shared secret key into the hash, so only key-holders can produce it. A digital signature instead encrypts the hash with the sender's private key, so anyone with the sender's public key can verify it. Both are covered in full later.

Other applications include one-way password files (store H(password), not the password), intrusion detection (hash known-good files and flag changes), virus detection (fingerprint malicious code), and building a pseudorandom function (PRF) or pseudorandom number generator (PRNG). Hashing is also widely used for key derivation.

Hashes do integrity; MACs add origin; signatures add non-repudiation.

Preimage, Second Preimage and Collision Resistance

Three formal properties turn "hard to break" into something precise, differing only in what the attacker starts from.

Since collisions cannot be eliminated, we ask for three resistance properties instead. First, two definitions.

Preimage — an input value that produces a particular output. For h = H(x), x is the preimage of h.
Collision — two different inputs with identical hash values: H(a) = H(b), a ≠ b.

1. Preimage resistance

Goal: if the attacker knows an output hash value, they cannot find an input that produces it.

Preimage resistance
Given a randomly chosen y from H's range, it is computationally infeasible to find x such that H(x) = y.

It is not impossible, since brute force exists, but it must be computationally infeasible. This matters when confidentiality is required: violate it and an attacker can infer the message from the hash.

2. Second preimage resistance

Goal: given an input value, the attacker cannot find another input with the same output hash.

Second preimage resistance
Given a randomly chosen x, it is computationally infeasible to find x′ ≠ x such that H(x) = H(x′).

If compromised, an attacker could substitute a forged message with the same hash. Here the attacker starts from a specific input, which constrains them.

3. Collision resistance

Goal: the attacker cannot find any two inputs with the same output hash.

Collision resistance
It is computationally infeasible to find a pair (x, x′), x ≠ x′, such that H(x) = H(x′).

Note: collision resistance implies second preimage resistance, but not preimage resistance. A successful second-preimage attack implies a successful collision attack, and a collision can sometimes be all the attacker needs.

P · 2 · C
"Pick a target, Patch a fixed input, Pair anything"
Preimage = recover an input from a given output · 2nd preimage = find another input for a given input · Collision = find any two that match.

Relationships and what applications need

Collision resistance implies second preimage resistance: any function hard to find collisions in is also hard to find a second input matching a given hash, but not conversely. Preimage resistance stands apart: a function can be preimage resistant without being collision or second-preimage resistant, and vice versa. Collision resistance is the strongest of the two related properties; breaking second preimage also breaks collision. Yet collisions are the easiest to attack, because the attacker has maximum freedom, needing only any two colliding inputs with no target.

⚠️
Common trap: do not say "collision resistance means no collisions exist". It means finding one is computationally infeasible. Collisions always exist.

The Birthday Paradox and the Birthday Attack

Because we ask whether any two hashes match rather than one matching a target, collisions arrive at roughly the square root of the output space.

Birthday problem: "If there are 365 days in a year, how many people must be in a room before there is a 50% chance that two share the same birthday?" The answer is just 23, far fewer than intuition suggests. The surprise comes from asking whether any two people match each other, not whether someone matches a specific date, which gives the attacker vastly more opportunities.

Sketchy proof. Add people one by one, tracking the probability that all birthdays stay unique. After k people, P(no match) = 1 · (364/365) · … · ((365 − k + 1)/365).

k (people)P(no match)Interpretation
2058.9%Still more likely all birthdays differ.
2252.4%Approaching the tipping point.
2349.3%Below 50%, so a shared birthday is more likely than not.
2543.1%Chance of a match climbs quickly.
Generalised birthday attack — if random variables are chosen uniformly from the range 0 through N − 1, the probability of a repeated element exceeds 50% after about √N choices.

An n-bit hash has 2n possible values, so an attacker needs only about 2n/2 attempts for a better-than-50% chance of collision.

The birthday bound
collision expected after ≈ √(2ⁿ) = 2^(n/2) attempts

For a 64-bit output that is just 232, trivially achievable on modern hardware. For 160 bits the attacker needs 280, which remains computationally infeasible today, so the accepted minimum output length is n ≥ 160 bits.

💡
Why it matters: the 50% threshold is the standard cryptanalytic benchmark. Better-than-coin-flip odds means the function is practically broken, so output length is a hard security requirement.
⚠️
Common trap: do not confuse 2n (brute-force cost for a preimage) with 2n/2 (birthday cost of a collision). Doubling the digest squares the collision effort.

Pseudorandomness and Why Output Must Look Random

Pseudorandomness is not traditionally listed as a requirement, but every resistance property secretly depends on it.

Pseudo-randomness is the property of a sequence that appears random but is generated deterministically. A hash always returns the same output for the same input, yet that output should look as if it came from a random source. It is not traditionally listed as a requirement but is implied: hashes are used for key derivation and pseudorandom number generation, and the three resistance properties depend on the randomness of the output, since predictable or clustered output would make collisions and preimages easy.

To verify a hash really looks pseudorandom, hash a fixed string and check the hex digest for obvious structure (there should be none).

sha256sum
echo "CYBERSECURITY ENGINEERING" | sha256sum 605d08ba60312b5e8b79105bc4f31ee8c269b956cada4821c9e22876bab917e5
md5sum
echo "CYBERSECURITY ENGINEERING" | md5sum ca00a2f980e354eb1ff97c4305aaed2e

The SHA-256 digest is 64 hex characters (256 bits); MD5 is 32 hex characters (128 bits). Neither shows an exploitable pattern. A function that fulfils preimage, second-preimage and collision resistance is a cryptographic hash function, giving a feasibility-conditioned guarantee that attackers cannot obtain plaintexts and cannot easily find bogus inputs with the same hash. A few problems remain, and length extension is one.

Iterated Hashing, Merkle–Damgård and Length Extension

MD5, SHA-1 and SHA-2 hash long messages by chaining a compression function block by block, and that design has a known weakness.

How does a fixed block size consume a message of arbitrary length? Via an iterated construction, best known as the Merkle–Damgård construction, used by MD5, SHA-1 and SHA-2.

  1. Pad the message to an exact multiple of the block size, always including a length field recording the original bit-length.
  2. Split into blocks M₁, M₂, …, M_t, the "plaintext blocks" feeding the chain.
  3. Initialise a chaining value H₀, the fixed, publicly specified initialisation vector (IV). It is not secret and not random.
  4. Compress each block with a compression function F: H_i = F(H_(i−1), M_i).
  5. Output the final chaining value H_t as the digest.
The chaining recurrence
H_i = F(H_(i−1), M_i), digest = H_t

The digest is the final state of a chain, not a one-shot computation over the whole message, so anyone who knows that state can continue the chain.

Length-extension attacks

In SHA-2 (also MD5 and SHA-1), an attacker who knows H(m) can compute H(m ‖ extra) without knowing m. The published hash is the chaining value after the final padded block. If the attacker also knows the length of m, they can reconstruct the appended padding, set the given hash as the new chaining value, and feed in their own extra block. The result is a valid hash of "original message, its padding, and the attacker's data". They never learn m, but they can forge a hash for a related, longer message.

⚠️
Common trap: a naive MAC built as H(K ‖ M) is vulnerable. An attacker who knows H(K ‖ M) can extend it to a valid tag for K ‖ M ‖ padding ‖ extra without knowing K. This is why HMAC uses a nested, padded-key construction.

The Secure Hash Algorithm (SHA) Family

SHA is the most prevalent hash family, developed by NIST and evolved across three generations to keep pace with attacks.

The Secure Hash Algorithm (SHA) was developed by the National Institute of Standards and Technology (NIST) and introduced as FIPS 180 in 1993. The initial iterations, SHA-0 and SHA-1 (160-bit output), fell out of favour due to susceptibility to collisions.

FIPS 180 (1993): SHA-0 / SHA-1→ 2001/2002: SHA-2→ 2015: SHA-3

SHA-2 (NIST, 2001/2002) has variants SHA-224, SHA-256, SHA-384, SHA-512, plus the truncated SHA-512/224 and SHA-512/256. SHA-3 (NIST, 2015) has variants SHA3-224, SHA3-256, SHA3-384, SHA3-512, and is a different construction rather than a tweak of SHA-2.

Inside SHA-2: Padding, Compression and Feedforward

SHA-512 is the worked example: pad, split into 1024-bit blocks, and push each through 80 rounds of a register-based compression function.

SHA-512 takes a message of maximum length less than 2128 bits and produces a 512-bit digest, processing input in 1024-bit blocks.

The padding procedure

  1. Append a 1 and zeros: pad the message of L bits with a single 1 bit followed by enough 0 bits so the total length is congruent to 896 mod 1024, leaving room at the end.
  2. Append the length: a 128-bit encoding of L brings the padded message to an exact multiple of 1024 bits.
  3. Split into blocks M₁, M₂, …, M_t, the plaintext blocks feeding the chain.
  4. Initialise H₀ (the IV), a fixed, publicly specified 512-bit constant. It is not secret and not random.
SHA-512 padding
M ‖ 1 ‖ 0…0 ‖ L(128 bits) → length ≡ 0 mod 1024
🧠
Remember: the 896 mod 1024 rule exists because the last 128 bits are reserved for the length. 1024 − 128 = 896, so the message plus the 1 and zeros stops there.

Inside the compression function F

  • F unpacks H_(i−1) into eight 64-bit registers a–h, transformed across 80 rounds.
  • The message schedule expands the 1024-bit block M_i into 80 round words W₀–W₇₉, analogous to the AES key schedule turning one key into many round keys.
  • Each round mixes one W_t and one public constant K_t. Six of the eight registers just shift along, so only two new values are computed per round.
  • Davies–Meyer feedforward: after round 79, the final a–h are added mod 264 back to the original H_(i−1). Those eight additions produce H_i, passed to the next block.
Davies–Meyer feedforward
H_i = F(H_(i−1), M_i) + H_(i−1) (mod 2⁶⁴, per register)
💡
Why it matters: adding the input chaining value back to the output makes the compression function hard to invert, the one-way ingredient at the heart of the chain.

Applications: SHA-2 is implemented in security protocols (TLS/SSL, SSH, IPSec), validates and signs digital certificates and documents, and verifies cryptocurrency transactions, for example Bitcoin's use of SHA-256.

SHA-3 and the Sponge Construction

SHA-3 abandons the register chain for a single permuted state, and its hidden capacity bits give it immunity to length extension.

SHA-3 uses a sponge construction rather than SHA-2's register-based compression. Four ideas define it.

  • Single unified state of r + c bits is passed through a permutation f. Unlike SHA-2's eight registers, there is one big state repeatedly permuted.
  • Absorbing phase: each message block is XORed into the top r bits of the state, then f scrambles the entire state. The bottom c bits are never directly touched by the message input, protecting the security margin.
  • Squeezing phase: output is read from the top r bits, with f applied between each read. As many bits as needed can be squeezed out, making SHA-3 naturally an extendable output function.
  • Rate r versus capacity c is a tunable tradeoff: larger r means faster hashing but smaller c means lower security. Different SHA-3 variants just change this split.
Sponge state
state = r (rate, absorbed/squeezed) + c (capacity, hidden security margin)
Absorb block 1→ Permute f→ Absorb block 2→ Permute f→ Squeeze r bits→ Permute f …

Why SHA-3 has no length-extension vulnerability

Recall the SHA-2 problem: knowing H(m) lets an attacker compute H(m ‖ extra). The sponge eliminates this because the hidden capacity c bits make the full internal state unrecoverable from the output. The attacker only sees the top r bits and cannot reconstruct the rest of the state needed to continue absorbing.

SHA-3 was not created because SHA-2 broke; it gives a structurally different alternative so the ecosystem does not rest on one design.

Message Authentication Codes: Keyed Hashes

A MAC is a small tag computed with a shared secret key, proving both integrity and origin to anyone who holds that key.

Message authentication verifies that a received message comes from the said source and has not been altered. Every authentication or signature mechanism has two levels: a lower-level function generating an authenticator (a value used to authenticate a message), and a higher-level protocol using that primitive.

Three classes of authenticator-generating functions

  • Hash function: a keyless digest. Alone it may not provide authentication, because unprotected hashes are susceptible to person-in-the-middle attacks.
  • Symmetric encryption: encrypting with the shared key gives confidentiality and lets B confirm the message came from A, since the key is known only to A and B. But an attacker can modify the ciphertext bit pattern without the key; if the original message was a bit sequence, the receiver cannot detect it, because the modified ciphertext still decrypts to a valid bit sequence.
  • Public-key encryption: straightforward encryption with B's public key gives confidentiality but not authentication, since anyone can encrypt a forged message under B's public key. Encrypting with A's private key gives authentication but not confidentiality (anyone can decrypt with A's public key), and still permits undetected modification if the altered ciphertext maps to a legitimate message.
ℹ️
Context: to get both confidentiality and authentication with public-key encryption, A encrypts M first with their private key (a signature), then with B's public key. The drawback is cost: the complex public-key algorithm runs four times instead of two.

Why MACs when we already have hashes?

Hashes are keyless. Anyone, including an attacker, can compute a valid hash for a forged message, so they prove the message was not corrupted but cannot prove who sent it. A MAC incorporates a secret key, acting as a keyed hash. A MAC is a fixed-size tag generated with a secret key shared between the parties and appended to the message; MACs are also known as cryptographic checksums.

MAC definition
MAC = C(K, M) M = input message · C = MAC function · K = shared key

The message and MAC are transmitted together as (m, t). The recipient recomputes the MAC with the shared key and compares. If they match, and assuming the key is known only to sender and receiver, three things follow:

  1. Integrity: the message has not been altered. Any alteration without changing the MAC causes a mismatch, and without the key the attacker cannot produce a valid MAC.
  2. Origin: no other party has the secret key required to generate the valid MAC.
  3. Sequence integrity: if the message includes a sequence number (as in HDLC, X.25, TCP), the recipient can verify it, because an attacker cannot alter it undetected.
⚠️
Common trap: the MAC process does not provide confidentiality; add it by encrypting before or after the MAC. Also, like hashes, MACs must be irreversible, so do not expect to reverse one.

Requirements for a MAC

  1. Hash-grade resistance: the MAC function must have the resistance properties of a cryptographic hash function.
  2. Unforgeability: it must be computationally infeasible to predict a correct MAC t′ for m′ ≠ m, even given other (m, t) pairs.

A cryptographic hash satisfies the first; mixing in a secret s addresses the second, provided the resistance properties hold.

ℹ️
Context: block-cipher MACs such as CBC-MAC, and its NIST standardised refinement CMAC (used inside CCM), chain ciphertext blocks and use the last block as the tag. This course focuses on hash-derived MACs.

HMAC: The Hash-Based Message Authentication Code

HMAC folds a secret key into any hash function using two padded constants, and it is the most widely used MAC on the Internet.

The most widely used way to integrate a secret key into a hash is HMAC. Published as RFC 2104, it is the obligatory MAC for IP security, is used in Internet protocols including SSL, and is ratified as NIST standard FIPS 198.

The HMAC formula
HMAC(K, M) = H[ (K ⊕ opad) ‖ H[ (K ⊕ ipad) ‖ M ] ]

Read it inside out. The inner hash runs over the key XORed with ipad, concatenated with the message, producing a fixed-length hash. The outer hash runs over the key XORed with opad, concatenated with that inner hash. Here H can be any cryptographic hash function (SHA-3, SHA-2, SHA-1, MD5), K is the shared secret key, M is the message, and ipad and opad are publicly known constant bit strings required for the security proof. Their precise values matter little: ipad is 00110110 (3616) and opad is 01011100 (5C16), each repeated b/8 times (b is the block size in bits).

The HMAC algorithm

  1. Pad the key: append zeros to the left of K to create a b-bit string K⁺. If K is 160 bits and b = 512, append 44 zeroes.
  2. Inner key block: XOR K⁺ with ipad to produce the b-bit block S_i.
  3. Append the message M to S_i.
  4. Hash the stream from step 3 with H.
  5. Outer key block: XOR K⁺ with opad to produce the b-bit block S₀.
  6. Append the inner hash from step 4 to S₀.
  7. Hash and output: apply H to step 6 and output the result.
K⁺ ⊕ ipad→ ‖ M→ Inner hash→ K⁺ ⊕ opad ‖ inner→ Outer hash = MAC

ipad goes in first (inner), opad goes out last; this nesting defeats the length-extension attack that a naive H(K ‖ M) would suffer.

Security of HMAC and Its Applications

HMAC's strength is provably tied to the embedded hash, and the keyed setting turns MD5's offline collision weakness into an infeasible online attack.

The security of any MAC based on an embedded hash depends on the cryptographic strength of that hash and on the key size. The appeal of HMAC is that its designers proved an exact relationship between the strength of the embedded hash function and the strength of HMAC.

Can we use MD5 for HMAC?

Question: the birthday paradox says 264 attempts give at least a 50% chance of a collision in MD5 (128-bit output), which looks feasible today. Can we use MD5 for HMAC? Answer: Yes.

Attacking plain MD5

  • The attacker chooses any set of messages.
  • They work offline on a dedicated facility to find a collision.
  • They know the algorithm and default IV, so they can hash any message they choose.
  • The birthday attack is realistic.

Attacking HMAC-MD5

  • The attacker cannot generate (message, code) pairs offline, because they do not know K.
  • They must observe HMAC-generated messages under the same key.
  • This requires 264 observed blocks (272 bits) under one key.
  • On a 1-Gbps link with no key change, about 150,000 years, so infeasible today.
💡
Why it matters: the secret key removes the attacker's ability to prepare collisions offline. They must wait for the real system to produce colliding data under one key, pushing the cost out of reach. If speed matters, HMAC-MD5 can be used over HMAC-SHA-1.
⚠️
Common trap: "MD5 is broken, so HMAC-MD5 is broken" is a tempting but wrong leap. The break applies to plain MD5's collision resistance; inside HMAC the keyed, online setting changes the attack model.

Applications of HMAC

  • API request signing (AWS Signature V4): the client signs the full request (URL, headers, body, timestamp) with HMAC using a shared secret. The server recomputes it independently; a mismatch means the request was tampered with or replayed, giving integrity and replay protection on top of standard authentication.
  • Tokens and one-time passwords: HMAC signs JSON Web Tokens (JWT) and generates One-Time Passwords (HOTP/TOTP).
⚠️
Common trap: HMAC alone does not guarantee confidentiality; the message is still readable. In practice it runs over an encrypted TLS connection, which handles confidentiality separately.

Authenticated Encryption and AEAD (GCM and CCM)

Instead of bolting encryption and a MAC together, which is error-prone, authenticated encryption combines them into one primitive.

Confidentiality (encryption) and authenticity (a MAC) have been separate so far, and combining them correctly is tricky and error-prone. Authenticated encryption (AE) simultaneously provides both confidentiality and authenticity (integrity) in a single operation, ensuring data stays private while protected from tampering. A MAC alone does not provide confidentiality, and manual combination risks mistakes such as incorrect ordering or improper implementation. By integrating the two, AE reduces these errors.

AEAD — Authenticated Encryption with Associated Data extends AE by allowing additional data that is authenticated but not encrypted, sent in plaintext but included in the integrity check, for example headers or metadata. The tag computation and encryption can run in parallel, making AEAD efficient. It is defined for block and stream ciphers, and its security depends on how tightly the two are coupled; ideally no plaintext is released until integrity is verified.

The four approaches

ApproachWhat you sendUsed by
Hash then encrypt (H→E): h = H(M), then E(K, (M ‖ h))Enc_k(m, H(m))—
MAC-then-Encrypt (A→E): T = MAC(K₁, M), then E(K₂, [M ‖ T]); two keysEnc_k1(m, MAC_k2(m))SSL/TLS
Encrypt-then-MAC (E→A): C = E(K₂, M), then T = MAC(K₁, C); two keysEnc_k1(m), MAC_k2(Enc_k1(m))IPSec; strongest
MAC-and-Encrypt (E + A): C = E(K₂, M) and T = MAC(K₁, M); either order; two keysEnc_k1(m), MAC_k2(m)SSH

Encrypt-then-MAC (E→A) is regarded as the strongest because the tag protects the ciphertext itself, so modification is caught before decryption. GCM implements this paradigm.

GCM and CCM

Galois/Counter Mode (GCM) is parallelizable for high throughput and low latency, following Encrypt-then-MAC: the message is encrypted in a variant of CTR mode, and the ciphertext is multiplied with key material and message-length information over GF(2128) to generate the tag (the standard also defines a MAC-only mode, Galois MAC). It uses GHASH (a keyed hash) and GCTR (CTR with increment-by-one counters). It is the strongest and most widely used block-cipher AEAD mode, but very brittle: nonce reuse can completely break security, so use a well-vetted library.

Counter with CBC-MAC (CCM), standardized by NIST for IEEE 802.11 WiFi, is a tightly specified MAC-and-Encrypt: it computes CMAC over the message for a tag, then CTR-encrypts message and tag. It is sequential (the MAC completes first), so less efficient than GCM, and uses a single key for both uses (safe by design). It is common in constrained environments such as IoT and WiFi.

Digital Signatures: Need, Operation, RSA and DSA

A signature signs the hash with a private key, so anyone with the public key can verify and the signer cannot deny it, with no shared secret.

The need for digital signatures

Hashes give integrity but no notion of who sent the message. MACs give integrity plus authenticity but rely on a shared secret key, so both parties must already have agreed on a key. That creates a fundamental limitation:

Three limitations follow. A MAC cannot prove to a third party that Alice sent the message, because Bob could have computed the same MAC himself. It does not scale: communicating with 1000 people needs 1000 keys. And it gives no non-repudiation, since Alice can deny sending it with no way to prove otherwise.

Digital signatures solve this with asymmetric (public-key) cryptography: Alice signs with her private key and anyone verifies with her public key. This gives no shared secret needed, independent third-party verification, and non-repudiation, since Alice cannot deny signing.

Non-repudiation is what separates signatures from MACs. With a MAC either party could have produced the tag; with a signature only the private-key holder could have, and that is provable to anyone.

Basic operation

Bob wants to assure Alice the message is from him (he does not prioritise confidentiality). He hashes the message with a secure hash function such as SHA-512. The hash value and Bob's private key are input to a digital signature generation algorithm, producing a short block, the signature. He sends the message with the attached signature.

Message M→ Hash H(M)→ Sign with private key→ Send (M, signature)

Alice hashes the message and inputs the hash value and Bob's public key to a digital signature verification algorithm. If it returns valid:

  • Alice is assured the message was signed by Bob, since no one else has his private key, which is needed to create a signature verifiable with his public key.
  • Alice is assured of the message's integrity, since without Bob's private key no one can alter the message to produce a hash verifiable with Bob's public key.
⚠️
Common trap: this only works if the verifier can be certain the public key actually belongs to Bob. A forged or substituted public key breaks all guarantees. This is public-key authentication, solved by PKI and covered later under digital certificates.
✅
Key idea: signatures are computed over the hash, not the raw message (hash-then-sign). Hashing first makes signing efficient and ties the signature to collision resistance, so a weak hash weakens the signature scheme.

The DSA approach

There are two main approaches, both using SHA for hashing. DSA was proposed in 1991 and published by NIST via FIPS 186. It uses SHA and provides only the signature function: unlike RSA it cannot be used for encryption or key exchange. It is a dedicated signature-only scheme derived from ElGamal signatures, standardised with the encryption capability intentionally excluded.

  1. Hash the message M to generate a hash code.
  2. Add a random value: the hash code enters a signature function with a random number k generated for this particular signature.
  3. Add the keys: the function also depends on the sender's private key (PR_a) and a set of parameters known to a group of principals, the global public key (PU_G).
  4. Produce two components: the signature is the pair s and r.
  5. Verify: the receiver hashes the message and inputs it to a verification function depending on PU_G and the sender's public key (PU_a). Its output equals the signature component r if valid.

Only the sender, knowing the private key, could have produced a valid signature. In DSA a user computes r and s as functions of the public key components (p, q, g), the private key x, the hash H(M), and the random integer k.

DSA domain parameters
p prime · q a prime divisor of (p − 1) · g an element of order q in ℤp PU_G = (p, q, g) shared by all users · private key x with 0 < x < q
ℹ️
Context: the exam expectation is only the high-level ideas of DSA; refer to the textbook (Stallings, Chapter 13) for full detail.

The RSA approach

In 2013, FIPS-186-4 was proposed to incorporate signature algorithms based on RSA. The message is hashed to a secure fixed-length hash code; that hash code is encrypted using the sender's private key to form the signature; message and signature are transmitted. The recipient hashes the message and decrypts the signature using the sender's public key. If the calculated hash matches the decrypted signature, the signature is valid. Because only the sender knows the private key, only the sender could have produced it. RSA is a general-purpose public-key scheme that can also encrypt and exchange keys, whereas DSA is signature-only.

Deterministic versus probabilistic signatures

Note the per-message random number k in DSA. It must be generated randomly or pseudorandomly and be unique for each signing, which makes DSA a probabilistic scheme: signing the same message twice with the same key yields different (s, r) pairs. The textbook RSA signing procedure is deterministic for the same hash and key. Either way, k must never repeat: reusing a DSA k across signatures leaks the private key.

MAC versus digital signature

A MAC is symmetric: it gives integrity and origin but no third-party proof and no non-repudiation, and it needs a separate key per correspondent. A signature is asymmetric: it gives integrity, origin and non-repudiation, can be verified independently by any third party, and scales by publishing one public key, at the cost of being slower and more expensive.

Key Takeaways

If you remember nothing else from Week 6, remember these twelve points.

1

A hash is a fixed-size fingerprint. It maps variable-length M to fixed-size h = H(M), is one-way, and its security goal is integrity, not confidentiality.

2

Collisions are inevitable because the input space exceeds the output space. Cryptographic hashes make finding them computationally infeasible, not impossible.

3

Three resistance properties. Preimage (given y, find x), second preimage (given x, find another x′ with the same hash), collision (find any two colliding). Collision resistance implies second preimage resistance, not preimage resistance.

4

The birthday attack halves the exponent. An n-bit hash needs only about 2n/2 attempts for a 50% collision chance, hence the minimum n ≥ 160 bits.

5

SHA-2 uses Merkle–Damgård chaining: pad (with a length field), split into blocks, compress each into the next chaining value, with Davies–Meyer feedforward.

6

Length extension exploits that chain. Given H(m) you can compute H(m ‖ extra) without knowing m. Never build a MAC as H(K ‖ m).

7

SHA-3 uses a sponge: absorb blocks into the top r bits, permute with f, then squeeze output. The hidden capacity c gives immunity to length extension.

8

A MAC is a keyed hash. MAC = C(K, M) gives integrity plus origin authentication via a shared secret, and never provides confidentiality on its own.

9

HMAC = H[(K ⊕ opad) ‖ H[(K ⊕ ipad) ‖ M]]. RFC 2104, FIPS 198, the obligatory MAC for IP security, whose nested structure defeats length extension.

10

HMAC-MD5 is still usable. The attacker cannot mount the offline birthday attack without K; the online equivalent needs about 150,000 years on a 1-Gbps link.

11

Authenticated encryption combines the two. Encrypt-then-MAC (IPSec, GCM) is considered strongest; CCM is MAC-then-Encrypt and sequential. Always use vetted libraries.

12

Digital signatures add non-repudiation. Sign the hash with a private key, verify with the public key. RSA is general-purpose; DSA is signature-only and uses a per-message random k. Public-key authenticity depends on PKI.

Glossary

Thirty terms from Week 6, filterable by category.

Hash function
A one-way function mapping a variable-length input M to a fixed-size value h = H(M). Also called a digest or checksum.
Cryptographic hash function
A hash satisfying preimage, second preimage and collision resistance, suitable for security use. Acts like one-way encryption.
Message digest
The hash value produced when a hash function is used for message authentication.
Preimage
An input value producing a particular output. For h = H(x), x is the preimage of h.
Collision
Two different inputs producing identical hash values: H(a) = H(b) with a ≠ b. Mathematically inevitable.
Preimage resistance
Given a randomly chosen output y, it is infeasible to find x with H(x) = y.
Second preimage resistance
Given x, it is infeasible to find x′ ≠ x with H(x) = H(x′).
Collision resistance
Infeasible to find any pair (x, x′), x ≠ x′, with H(x) = H(x′). Implies second preimage resistance.
Pseudorandomness
A sequence that appears random but is generated deterministically. Implied, though not traditionally listed, as a hash requirement.
MAC (message authentication code)
A fixed-size tag computed with a shared secret key and appended to a message; also called a cryptographic checksum or keyed hash. MAC = C(K, M).
Authenticated encryption (AE)
Encryption that simultaneously provides confidentiality and authenticity in a single operation, avoiding the error-prone manual combination of encryption and MAC.
Digital signature
A value formed by encrypting a message hash with the sender's private key, verifiable by anyone with the sender's public key. Provides integrity, origin and non-repudiation.
Non-repudiation
The property that a signer cannot later deny signing. MACs do not provide it; digital signatures do.
SHA-2
NIST family from 2001/2002 with variants SHA-224, SHA-256, SHA-384, SHA-512 (plus SHA-512/224, SHA-512/256). Built on Merkle–Damgård chaining.
SHA-3
NIST family announced in 2015 with variants SHA3-224/256/384/512. Uses a sponge construction and resists length extension.
Sponge construction
SHA-3's design: a state of r + c bits permuted by f, with an absorbing phase (message XORed into the top r bits) and a squeezing phase (output read from the top r bits).
HMAC
Hash-based MAC: HMAC(K, M) = H[(K ⊕ opad) ‖ H[(K ⊕ ipad) ‖ M]]. RFC 2104 and FIPS 198; the obligatory MAC for IP security.
ipad / opad
Publicly known constants (3616 and 5C16, repeated b/8 times) XORed with the padded key in HMAC. Required for its security proof.
CBC-MAC / CMAC
Block-cipher-based MACs. CBC-MAC chains ciphertext blocks and uses the last block as the tag; CMAC is the NIST refinement used inside CCM.
GCM (Galois/Counter Mode)
An AEAD mode following Encrypt-then-MAC: CTR-mode encryption plus a GHASH-based tag over GF(2128). Parallelizable but brittle; nonce reuse breaks it.
CCM (Counter with CBC-MAC)
A NIST AEAD mode for IEEE 802.11: computes CMAC over the message, then CTR-encrypts message and tag. Sequential, single key, common in IoT/WiFi.
DSA (Digital Signature Algorithm)
A signature-only scheme proposed in 1991 (FIPS 186), derived from ElGamal and using SHA. Produces a two-part signature (s, r) using a global public key and a per-message random k.
RSA signature
A signature formed by encrypting a message hash with the sender's private key; verified by hashing the message and decrypting the signature with the public key. RSA is general-purpose.
Birthday attack
Exploiting the birthday bound: for an n-bit output, only about 2n/2 attempts give a 50% chance of a collision.
Length-extension attack
Given H(m), compute H(m ‖ extra) without knowing m. Possible in SHA-2/MD5/SHA-1 Merkle–Damgård designs; impossible in SHA-3.
Person-in-the-middle attack
An attacker intercepts a message, replaces it, and alters the keyless digest to match, so the receiver detects nothing. Motivates MACs and signatures.
Rainbow table & salt
Precomputed hash lookup tables for common plaintexts, used to reverse weak password hashes. Defeated by salting: concatenating a random string before hashing.
Merkle–Damgård construction
Iterated hashing used by MD5, SHA-1 and SHA-2: pad, split into blocks, and chain H_i = F(H_(i−1), M_i) from a fixed IV. Vulnerable to length extension.
Encrypt-then-MAC (E→A)
Encrypt the message, then MAC the ciphertext: Enc_k1(m), MAC_k2(Enc_k1(m)). Used by IPSec and GCM; considered the strongest ordering.
AEAD
Authenticated Encryption with Associated Data: AE that also authenticates (but does not encrypt) associated data such as headers. Defined for block and stream ciphers.

No terms in this category.

Practice Questions

Fourteen open-ended questions. Answer aloud from memory, then reveal the model answer.

Answer, reveal, then tick "Mastered". Your progress is saved.
Q1

Define a cryptographic hash function and explain why collisions are mathematically inevitable.

Answer: A one-way function mapping a variable-length input M to a fixed-size h = H(M), satisfying preimage, second preimage and collision resistance. Collisions are inevitable because the input space is vastly larger than the output space, so by the pigeonhole principle two inputs must share an output. The goal is to make collisions computationally infeasible to find.
Q2

Distinguish preimage, second preimage and collision resistance, stating what the attacker is given.

Answer: Preimage: given a random output y, infeasible to find any x with H(x) = y. Second preimage: given a specific input x, infeasible to find a different x′ with H(x) = H(x′). Collision: infeasible to find any pair (x, x′), x ≠ x′, with equal hashes. Collision resistance implies second preimage resistance but not preimage resistance.
Q3

Why can a keyless hash not provide origin authentication, and which mechanisms do?

Answer: A keyless hash can be computed by anyone. In a person-in-the-middle attack the attacker replaces the message and recomputes the digest so it matches, and the receiver detects nothing. A hash proves only that data was not corrupted, not who sent it. Origin authentication needs a secret only the legitimate parties control: a MAC (shared secret key) or a digital signature (sender's private key).
Q4

Explain the birthday attack and why 160 bits is the accepted minimum output length.

Answer: It derives from the birthday problem: about 23 people give a better-than-50% chance that two share a birthday, because we ask whether any two match, not whether one matches a specific date. Generalised, draws from a range of size N repeat with >50% probability after about √N draws. An n-bit hash has 2n values, so about 2n/2 attempts suffice. For 64 bits that is 232, trivial; at 160 bits the attacker needs 280, still infeasible.
Q5

State the relationships among the three resistance properties and say which is hardest to satisfy yet easiest to attack.

Answer: Collision resistance implies second preimage resistance (breaking second preimage also breaks collision), but not conversely. Preimage resistance stands apart: a function may be preimage resistant but not collision resistant, and vice versa. Collision resistance is the strongest related property and hardest to satisfy, but easiest to attack, because the attacker needs only any two colliding inputs, with no target constraint, which is what the birthday attack exploits.
Q6

Describe SHA-512's padding procedure and explain the purpose of the length field.

Answer: The message of L bits is padded with a single 1 bit followed by enough 0 bits so the total length is congruent to 896 mod 1024, then a 128-bit encoding of L is appended, bringing it to a multiple of 1024 bits. It is split into 1024-bit blocks feeding the compression chain from the fixed, public 512-bit IV. The length field binds the true input length into the padded string, raising the difficulty of producing two inputs with the same hash.
Q7

Compare SHA-2's compression function with the SHA-3 sponge, and explain why SHA-3 avoids length extension.

Answer: SHA-2 unpacks the previous chaining value into eight 64-bit registers, runs 80 rounds mixing message-schedule words and constants, then applies Davies–Meyer feedforward back to the input chaining value. SHA-3 keeps a single r + c state permuted by f, absorbing message blocks into the top r bits and squeezing output from there. Because the bottom capacity c bits are never revealed, an attacker who knows H(m) cannot reconstruct the full state and so cannot compute H(m ‖ extra). SHA-2, whose digest is the final chaining value, can be extended.
Q8

Define a MAC, state its two security requirements, and say what it does not provide.

Answer: A MAC is a fixed-size tag generated with a shared secret key and appended to the message, MAC = C(K, M). Requirements: (1) it must have the resistance properties of a cryptographic hash function; (2) it must be infeasible to predict a correct MAC t′ for m′ ≠ m, even given other (m, t) pairs. It gives integrity, origin and (with a sequence number) sequence integrity, but not confidentiality, and it cannot serve as a signature because both parties share the key.
Q9

Write the HMAC formula and explain the roles of ipad and opad.

Answer: HMAC(K, M) = H[(K ⊕ opad) ‖ H[(K ⊕ ipad) ‖ M]]. The key is zero-padded to the block size to give K⁺, XORed with ipad (00110110 repeated b/8 times) for the inner hash, and with opad (01011100 repeated b/8 times) for the outer hash. Both are public constants whose exact values matter little, but they are required for the security proof; the nesting prevents length extension.
Q10

MD5 is vulnerable to collisions. Why is it still acceptable inside HMAC?

Answer: Against plain MD5 the attacker chooses messages and works offline because they know the algorithm and default IV, so the 264 birthday attack is realistic. Against HMAC-MD5 they do not know K, so they cannot generate (message, code) pairs offline and must observe messages under the same key, requiring 264 observed blocks (272 bits). On a 1-Gbps link with no key change that is about 150,000 years. If speed matters, HMAC-MD5 can be used over HMAC-SHA-1.
Q11

Contrast MACs and digital signatures across keys, verification and non-repudiation.

Answer: Keys: a MAC uses one shared symmetric key; a signature uses a private key to sign and a public key to verify. Verification: a MAC can only be checked by a key-holder, so it cannot be proven to a third party (Bob could have computed the same MAC); a signature can be checked by anyone with the public key, including a judge. Non-repudiation: a MAC gives none, since both parties could produce the tag; a signature gives it, since only the private-key holder could sign. MACs also need a key per correspondent, while signatures scale by publishing one public key.
Q12

Describe how an RSA digital signature is generated and verified.

Answer: Generation: hash the message to a fixed-length hash code, then encrypt that hash code with the sender's private key to form the signature, and transmit message plus signature. Verification: the recipient hashes the received message and decrypts the signature with the sender's public key; if the calculated hash matches the decrypted signature, it is valid. Only the sender knows the private key, so only the sender could have produced it. RSA is general-purpose and can also encrypt and exchange keys; FIPS-186-4 added RSA signatures.
Q13

Explain the DSA approach at a high level, including the roles of the global public key, the private key x, and the per-message value k.

Answer: DSA hashes the message and passes the hash code to a signature function with a random number k generated for that signature. The function also depends on the sender's private key PR_a and a global public key PU_G, the domain parameters (p, q, g) shared by all users. The signature is the pair (s, r). Verification uses the hash, PU_G and the sender's public key PU_a, and its output equals r when valid. The private key is x with 0 < x < q; k is the fresh per-message secret. DSA is signature-only, derived from ElGamal; only high-level ideas are examinable.
Q14

List the four authenticated-encryption approaches, state which is strongest, and compare GCM with CCM.

Answer: Hash-then-Encrypt (H→E): Enc_k(m, H(m)). MAC-then-Encrypt (A→E): Enc_k1(m, MAC_k2(m)), used in SSL/TLS. Encrypt-then-MAC (E→A): Enc_k1(m), MAC_k2(Enc_k1(m)), used in IPSec and considered strongest. MAC-and-Encrypt (E + A): Enc_k1(m), MAC_k2(m), used in SSH. GCM is Encrypt-then-MAC, parallelizable and fast (GHASH and GCTR over GF(2128)) but brittle: nonce reuse breaks it. CCM is a tightly specified MAC-then-Encrypt using CMAC then CTR mode; it is sequential and uses a single key, common in WiFi and IoT.
