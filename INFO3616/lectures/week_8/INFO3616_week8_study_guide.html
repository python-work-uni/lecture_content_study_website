Network Security: Protocols — From Packets to TLS and IPSec

This week builds the networking foundation you need before you can secure anything, then teaches the cryptographic protocols that protect traffic at each layer of the Internet. You will meet TCP/IP, IP addressing and subnetting, the many ways networks are attacked, and the three big security protocols you are most likely to meet in a job: OAuth/OpenID, TLS and IPSec.

Read this first: Hold one mental model for the whole week — the Internet is a four-layer stack, and security is added one layer at a time. Every packet is built up as it travels down the layers and unwrapped as it travels up. Because each layer looks after a different part of that packet, each layer needs its own security protocol: WPA at the link layer, IPSec at the network layer, TLS at the transport layer, and OAuth/OpenID at the application layer. Learn the stack and the protocols slot neatly into place.

Why Network Security Matters

We run our whole lives over networks, so the network is where the attacks now arrive — and attackers start with an advantage.

Our technological infrastructure, applications and services are deeply woven into networked environments. Business, government and private life all depend on networks. That dependence grew sharply after the COVID-19 pandemic accelerated remote work and digital services. Today networks run critical operations from power grids to remote business, and organisations build private networks and use VPNs (virtual private networks) to connect remote staff securely.

Network security is the field that deals with attacks and defences in the context of networked systems. It is enormous — it is worth its own unit of study — so this week gives you the foundational building blocks.

Most attacks now target networked environments, including remote exploits such as SQL injection against web applications. The crucial difference from "simple" software security is this: the input to our programs comes from remote parties, and there is no a priori control over who can send us input. Anyone on the Internet can send us any kind or amount of traffic. And once an attacker gets inside a network, they have plenty of room to explore, breach and exploit.

💡
Why defenders are at a disadvantage: the asymmetry is structural. A defender must protect every device — a browser, a CCTV camera, an IoT sensor — while an attacker only needs one weak point. Any of those devices can quietly become part of a botnet (a network of compromised machines used to attack others).
ℹ️
How this week is organised: Part I covers networking fundamentals and attacks on networks. Part II covers security protocols, working top-down from the application layer (OAuth/OpenID), through the transport layer (TLS), down to the network layer (IPSec).

The Internet: Building Blocks

The Internet is a network of networks, made from four simple ingredients: devices, switches, links and organisations.

The Internet interconnects hundreds of millions of computing devices worldwide. It is easiest to understand through its four building blocks.

🖥️ Hosts / end systems

The billions of connected computing devices at the edge of the network, where applications actually run: smartphones, laptops, servers and IoT devices. They are called hosts or end systems.

🔀 Packet switches

The traffic controllers of the digital world. They take incoming packets (small chunks of data) and forward them towards their destination. The main examples are routers and link-layer switches.

🔌 Communication links

The physical or over-the-air paths connecting devices and switches: fibre-optic cable, copper wire, radio waves and satellite signals. Each link is characterised by its transmission rate, known as bandwidth.

🏢 Networks

A network is more than hardware: it is a collection of devices, routers and links managed by a single organisation such as an ISP, a university or a corporation. The Internet is a "network of networks".

Access to the Internet is provided through Internet Service Providers (ISPs), ranging from residential and corporate to university ISPs, plus public WiFi in airports and cafés. Historically, about 850 million devices were connected as of July 2011 (excluding intermittently connected devices such as smartphones), bringing the number of users to around 2 billion.

🤔
Pause & predict: Your phone browsing a web page and a router forwarding that page's packets are both "part of the Internet". Which building block is each one? (Answer: your phone is a host/end system; the router is a packet switch.)

Protocols and the TCP/IP Model

A protocol is an agreed set of rules for exchanging messages; the TCP/IP model is the four-layer blueprint every Internet device follows.

What is a protocol?

All communication on the Internet happens using protocols. A protocol controls the sending and receiving of messages. Examples include HTTP (the Web), TCP, IP, DNS, SSH, WiFi, 4G and Ethernet.

A protocol defines three things: the format of messages, the order in which messages are sent and received between entities, and the actions taken when a message is transmitted or received.

The easiest way to understand this is with a human protocol. If you want the time of day, you first say "Hi" to start the conversation. The typical response is a returned "Hi". Taking that reply as a signal to proceed, you then ask "What's the time?". A computer network protocol works the same way, except the entities are hardware or software, not people. For example, a PC sends a TCP connection request to a server; the server replies with a TCP connection response; then the PC requests a URL and the server returns the requested files.

Human protocol

  • "Hi"
  • "Hi" (reply)
  • "What's the time?"

Network protocol

  • TCP connection request
  • TCP connection response
  • HTTP request for a URL → server returns files
🧠
Memory hook: a protocol is a grammar plus etiquette — it says what a message looks like (format), who speaks when (order), and what each side does in response (actions).

The four layers of the TCP/IP model

The TCP/IP model is the practical framework that governs today's Internet traffic. It has four layers:

  1. Application layer — where network applications and their protocols live.
  2. Transport layer — moves messages between application processes.
  3. Network layer — moves packets from host to host across the Internet.
  4. Network interface layer — the local delivery layer; it can be separated into the data link layer and the physical layer, and includes the Media Access Control (MAC) layer.

The older OSI (Open Systems Interconnection) model was historically important for standardising network architecture, but today it is largely theoretical. The TCP/IP model is what the real Internet runs on.

Application↓ Transport↓ Network↓ Network interface (Link + MAC)

The Application Layer and Sockets

Applications live at the top layer, and they reach the network through a software doorway called a socket.

The application layer is where network applications (social networking, the Web, email, voice over IP, and so on) and their application-layer protocols reside. The main protocols are:

ProtocolFull nameWhat it does
HTTPHypertext Transfer ProtocolRequests and transfers Web documents.
SMTPSimple Mail Transfer ProtocolTransfers email messages.
FTPFile Transfer ProtocolTransfers files between two end systems.
DNSDomain Name SystemResolves human-friendly names (like www.ietf.org) into 32-bit network addresses.

An application-layer protocol is distributed over multiple end systems: the application on one end system uses it to exchange packets of information with the application on another. We call this packet of information at the application layer a message.

Sockets: the interface between application and network

A process is a program running within a host. Processes send and receive messages through a software interface called a socket. The classic analogy: a process is like a house, and its socket is like its door. To send a message, the process shoves it out of the door. It trusts that a transport infrastructure on the other side will carry the message to the destination process's door. When the message arrives, it passes through the receiving process's socket and the process acts on it. Two sockets are involved — one on each side.

A socket is the interface between the application layer and the transport layer within a host, and it is also called the Application Programming Interface (API) between the application and the network, because it is the programming interface used to build network applications.

💡
The key distinction: socket and above is controlled by the application developer (the application layer). Below the socket is controlled by the operating system (the transport layer and below). This boundary matters for security later: TLS sits just below the socket, while IPSec sits even deeper in the kernel.
🤔
Pause & predict: If you write a chat app, which part is your job and which part does the OS handle? (Answer: you write the application code and use the socket API; the OS handles transport and everything below the socket.)

The Transport Layer: TCP versus UDP

The transport layer gives applications logical, end-to-end communication — and offers two very different personalities: careful TCP and lightweight UDP.

The transport layer transports application-layer messages between application endpoints. It provides logical communication between application processes running on different hosts — logical, because the processes feel directly connected even though they are many hops apart. A transport-layer packet is called a segment. The sender breaks application messages into segments and passes them to the network layer; the receiver reassembles segments into messages and passes them up to the application layer.

There are two transport protocols available to Internet applications: TCP and UDP.

TCP — Transmission Control Protocol

  • Connection-oriented and reliable. A three-way handshake establishes the connection before data flows.
  • Point-to-point: one sender, one receiver.
  • Reliable, in-order byte-stream delivery — data arrives complete and in the right order.
  • Cumulative ACKs with retransmission: an ACK acknowledges all data up to the first missing byte, and lost data is resent.
  • Bi-directional full-duplex data flow — both directions at once.
  • Flow control (the sender will not overwhelm the receiver), congestion control (it adapts to network conditions), and pipelining with dynamic window sizing.
  • MSS (Maximum Segment Size) limits how much data fits in one segment.

Use cases: file transfer, email, web pages, and any application that needs guaranteed delivery.

UDP — User Datagram Protocol

  • Connectionless and lightweight. No handshake, so no round-trip-time (RTT) overhead.
  • "No frills" best-effort delivery.
  • Unreliable and unordered: segments may be lost or arrive out of order — "send and hope for the best".
  • A checksum provides basic error detection.
  • The application layer can add its own reliability on top if needed.

Use cases: streaming media (loss-tolerant and rate-sensitive), DNS, SNMP, HTTP/3, and other real-time apps. UDP is fast (no connection setup), works even when network service is degraded, and is simple (minimal overhead).

ℹ️
HTTP/3 is special: it is the first HTTP protocol that does not rely on TCP. It runs over UDP and builds extra reliability and security at the application layer to get lower latency.

The TCP three-way handshake

  1. The client sends a SYN packet to the server, asking whether the server is open for new connections.
  2. If the server has open ports that accept new connections, it replies with a SYN/ACK (an acknowledgement).
  3. The client receives the SYN/ACK and replies with an ACK. The connection is now established.

The first two segments carry no payload; the third may begin carrying data. Only after all three steps can the two hosts exchange data segments.

TCP

  • Connection-oriented, three-way handshake
  • Reliable, in-order
  • Flow and congestion control
  • Guaranteed delivery use cases

UDP

  • Connectionless, no handshake
  • Unreliable, unordered
  • No flow or congestion control
  • Loss-tolerant, rate-sensitive use cases
🧠
Memory hook: TCP = Trusted, Careful, Patient (checks everything). UDP = Unchecked, Direct, Prompt (just fires and forgets).

The Network Layer

The network layer is the Internet's delivery service: it moves datagrams from any host to any host, and IP is the one protocol every device must speak.

The network layer (also called the Internet layer) is responsible for moving network-layer packets, known as datagrams, from one host to another. The transport layer passes it a segment plus a destination address — just as you would hand the postal service a letter with a destination address — and the network layer delivers it to the transport layer in the destination host.

The sender encapsulates segments into datagrams and passes them to the link layer; the receiver delivers segments up to the transport layer. Network-layer protocols run in every Internet device: hosts and routers.

What a router does

  • Examines header fields in all IP datagrams passing through it.
  • Moves datagrams from input ports to output ports to transfer them along the end-to-end path.

Three components of the network layer

📦 IP protocol

Defines the fields in the datagram and how hosts and routers act on them. There is only one IP protocol, and every device with a network layer must run it.

🗺️ Routing component

Determines the path a datagram follows from source to destination, using routing protocols such as RIP, OSPF and BGP, or software-defined networking (SDN) controllers. Routing protocols compute the forwarding tables used to forward packets.

📨 Error reporting

ICMP (Internet Control Message Protocol) reports errors in datagrams and responds to requests for network-layer information.

IP datagram format

An IP datagram is the basic unit of data transmitted over the Internet. It has two parts: a header and the data (payload). The header carries fields such as the source IP address, destination IP address, protocol, time to live (TTL) and checksum, which are used for addressing and error detection. The version field says whether it is IPv4 or IPv6.

The maximum size of a datagram is set by the Maximum Transmission Unit (MTU) of the underlying network — often 1500 bytes for Ethernet. If a datagram is larger than the MTU, it can be fragmented into smaller pieces.

✅
Keep this in mind for IPSec: the IP header (source, destination, version, length) is exactly what IPSec will later learn to authenticate. Remember that fields like TTL change as a packet is forwarded, which is why only the "normally immutable" parts get protected.

IP Addressing, NAT and IPv6

Every interface needs a unique address; IPv4 ran out, so we invented NAT and then IPv6.

IPv4 addresses and interfaces

An IPv4 address is a 32-bit identifier associated with each host or router interface. An interface is the connection between a host or router and a physical link. Routers typically have multiple interfaces (one per link); a host typically has one or two (for example wired Ethernet and wireless 802.11). Crucially, an IP address is associated with an interface, not with the whole host or router.

Because an address is 32 bits, there are 232 possible addresses — about 4 billion. Addresses are written in dotted-decimal notation, where each of the four bytes is written in decimal separated by dots. For example, 223.1.1.1 is four bytes; 223 is the decimal value of the first 8 bits, and so on. In binary:

223.1.1.1 in binary
11011111 . 00000001 . 00000001 . 00000001

Each interface on every host and router in the global Internet must have a globally unique IP address (except for interfaces hidden behind NAT). Part of an interface's address is determined by the subnet it connects to.

IPv4 address classes

Classically, addresses were grouped into classes by their leading bits. The table summarises the ranges, first octet, default subnet mask and typical use.

In practice, CIDR (Classless Inter-Domain Routing) replaced the strict class system, allowing more flexible and efficient allocation of address space. A CIDR prefix such as /26 simply says how many leading bits are the network portion.

NAT: Network Address Translation

Imagine 15 PCs, a smartphone and two tablets all needing to work online at once. Ideally each would get its own Internet-accessible address, but IPv4 address space is scarce. NAT, proposed in 1994, became the necessary answer to IPv4 exhaustion.

The idea of NAT is simple: all devices in a local network share just one IPv4 address as far as the outside world is concerned. A NAT-enabled router rewrites addresses. Inside, all four interfaces might share the subnet 10.0.0/24. Datagrams leaving the network all use the same public source NAT address (say 138.76.29.7) but with different source port numbers. A NAT translation table maps private addresses and ports to public addresses and ports — for example, public 138.76.29.7:5007 maps to private 10.0.0.1:3345.

NAT also adds safety: outside attackers cannot directly reach internal devices, and internal information cannot casually reach the outside world.

💡
Why NAT matters for security: it hides the internal network behind one public face. It is not a true security mechanism, but it does block unsolicited inbound connections, which is why it is so widely used at home and in offices.

IPv6: a bigger address space

The prime motivation for IPv6 was that the 32-bit IPv4 address space was running out as new subnets and devices joined the Internet at a breathtaking rate. IPv6 expands addresses from 32-bit to 128-bit, providing trillions of IPs for every person on Earth and eliminating the need for NAT, since every device can have a unique public IP.

IPv6 also streamlines and modernises the header:

  • A 40-byte fixed header simplifies and speeds up router processing.
  • It removes the header checksum and hop-by-hop fragmentation, pushing error-checking and packet-sizing to the network's "edges".
  • A 20-bit field lets routers identify and prioritise specific traffic streams.
  • Native security: IPv6 was designed with IPSec support as a core requirement, giving a standard framework for encryption and authentication.

So why is IPv6 not finished? The migration gap: compatibility with existing systems, financial return on investment, and the many NAT-based versions already in use.

The IP hourglass

The Internet is often drawn as an hourglass with a "thin waist": one network-layer protocol, IP, sits at the narrow point. Everything above (transport, application) and below (link, physical) can vary, but IP must be implemented by every one of the billions of Internet-connected devices. That is why IPSec — which works at the IP layer — can protect essentially all traffic.

🤔
Pause & predict: Why did IPv6 make NAT unnecessary, yet NAT is still everywhere? (Answer: IPv6 gives every device a unique public address, but slow migration means IPv4 plus NAT remains dominant.)

Subnets and Subnetting

A subnet is an isolated island of interfaces that can reach each other without a router; subnetting borrows host bits to create more of them.

What is a subnet?

A subnet (short for "subnetwork") is a logical subdivision of an IP network. The defining test: a subnet is a group of device interfaces that can physically reach each other without passing through an intervening router.

IP addresses have structure:

  • The subnet part: devices in the same subnet share common high-order bits.
  • The host part: the remaining low-order bits, unique to each interface.

The recipe for defining subnets: detach each interface from its host or router, creating "islands" of isolated networks. Each isolated network is a subnet. Subnets improve performance and security by dividing large networks into smaller, manageable segments, reducing broadcast domains and giving better control over access.

How subnetting works

In IPv4, subnetting works by extending the default subnet mask, "borrowing" bits from the host portion to create more network addresses. Each subnet supports a certain number of hosts, set by how many bits remain for the host portion.

The two key formulas
number of subnets = 2^(bits borrowed)   |   usable hosts per subnet = 2^(host bits) − 2

We subtract 2 because the first address in each subnet is the network address and the last is the broadcast address; neither can be assigned to a host.

Worked example: 192.168.10.0 with a /26 mask

Given IP address 192.168.10.0 and subnet mask 255.255.255.192 (which is /26 in CIDR notation):

  1. Convert the mask to binary. 255 = 11111111, 255 = 11111111, 255 = 11111111, 192 = 11000000. So the mask is 11111111.11111111.11111111.11000000.
  2. Count the bits. /26 means 26 bits for the network, leaving 6 bits for hosts. Borrowed bits = 26 − 24 = 2 (for a Class C base), so number of subnets = 22 = 4. Hosts per subnet = 26 − 2 = 64 − 2 = 62.
  3. Find the block size. 256 − 192 = 64, so subnets step in blocks of 64.

Practice: 172.16.13.5 with mask 255.255.255.128

The address 172.x lies in Class B (128–191). The mask 255.255.255.128 is /25, splitting the /24 into two subnets of 128: 172.16.13.0–172.16.13.127 and 172.16.13.128–172.16.13.255. The host 172.16.13.5 is in the first subnet, so the subnet address is 172.16.13.0 and the broadcast address is 172.16.13.127.

Practice: 172.16.45.14/30

/30 means 30 network bits and 2 host bits (blocks of 4). Converting 172.16.45.14 to binary:

172.16.45.14 in binary
10101100.00010000.00101101.00001110

Masking off the last 2 bits gives the network address 10101100.00010000.00101101.00001100, which is 172.16.45.12. So the host belongs to the subnet 172.16.45.12/30.

The Link Layer and MAC Addresses

The link layer delivers a frame between two physically adjacent nodes, using MAC addresses found with ARP.

Terminology

  • Nodes — hosts and routers.
  • Links — the communication channels connecting adjacent nodes along a path: wired, wireless or LANs.
  • Frame — the layer-1 (or layer-2) packet; it encapsulates the datagram.

The link layer's job is to transfer a datagram from one node to the physically adjacent node over a single link.

Link-layer services

🧩 Framing and link access

Encapsulate the datagram into a frame. The MAC address in the frame header identifies the source and destination — note this is not the same as the IP address.

🔁 Reliable delivery between adjacent nodes

Includes flow control, error detection, error correction, and support for half-duplex and full-duplex operation.

MAC addresses and ARP

A MAC address is used locally to get a frame from one interface to another physically connected interface. Each interface on a Local Area Network (LAN):

  • Has a unique 48-bit MAC address, and
  • Has a locally unique 32-bit IP address.

The Address Resolution Protocol (ARP) is used to find a MAC address given an IP address. In other words: IP addresses route across the whole Internet, while MAC addresses identify a device on the local link.

ℹ️
IP versus MAC: think of IP as your postal address (used end-to-end across the world) and MAC as the name of the person at the front desk of a building (used only within that local building). ARP is the directory that tells you which front-desk name matches a given postal address.

Attacks on Networks

An attack is anything that could violate a security goal; passive attacks watch, active attacks change things.

An attack on a network is an event or sequence of actions that might lead to a violation of one or more security goals. For example, a DDoS attack on a server compromises the goal of availability.

The decisive difference from "simple" software security is that the input to our programs (web server, mail server) comes from remote parties, and there is no a priori control over who can send us input. Further attacks become possible simply because a remote party can choose any kind or amount of traffic to send us. A successful intrusion then gives an attacker plenty of opportunity to explore, breach and exploit the network.

Passive attacks

Passive attacks are acts of eavesdropping on, or monitoring of, transmissions. The goal is to obtain information that is being transmitted. The two types are:

  • Release of message contents — reading the data itself.
  • Traffic analysis — learning from the pattern of traffic even if contents are hidden.

Passive attacks are very difficult to detect because they do not alter the data at all.

Active attacks

Active attacks involve some modification of the data stream or the creation of a false stream. They fall into four categories:

🔁 Replay

Capture a valid transmission and send it again later. For example, replay a captured authentication sequence to gain access.

🎭 Masquerade

One entity pretends to be a different entity. A low-privilege entity can impersonate a high-privilege one and obtain extra privileges.

✏️ Modification of messages

Alter a legitimate message in transit — for example, changing the data and forwarding it to the server.

🚫 Denial of service

Reduce or destroy availability or correct functioning — for example, a DDoS attack on a remote server.

Ways to compromise security goals

Common trap: passive attacks cannot be detected by looking for changes, because there are none. That is why the defence is prevention (encryption) rather than detection.

Cryptographic Protocols by Layer

Security protocols are stacked to match the layer they protect; this week focuses on the three you will actually meet at work.

Cryptographic protocols are employed across the layers to protect data. Here is the map:

LayerProtocolsNotes
Link layerWPA3, WPA2Secure WiFi. Older WPA and WEP are broken.
Network layerIPSec, IKEv2Protect IP packets; provide integrity and confidentiality.
Transport layerTLS (for TCP), DTLS (for UDP)Robust security for transmitted data.
Application layerOpenID, OAuth, DNSSECAuthentication and authorisation; DNSSEC secures the Domain Name System.

As of today, the protocols you are most likely to encounter in a professional role, in order, are TLS, WPA2/WPA3, OpenID, OAuth and IPSec. This lecture focuses on the standards above Layer 2, working top-down: OAuth/OpenID, then TLS, then IPSec.

🧠
Memory hook: W-T-I-O bottom to top — WPA (link), TLS (transport), IPSec (network), OAuth/OpenID (application). (The order of the letters is not the stack order; remember each letter by its layer.)

Application Layer: OAuth and OpenID

OAuth is about authorisation (what a service may do), OpenID is about authentication (who you are).

OAuth is a standard for authorisation. It lets a user of one Internet service grant another service access to parts of their account. Some ideas resemble Kerberos: an authorisation server creates a "ticket" (a token) that allows access. OAuth is designed for use with HTTP, so websites can use its defined flows — which results in highly complex protocol flows, and several possible flows have been standardised.

OpenID is an authentication protocol that uses OAuth flows but is complementary to it. Authentication answers "who are you?"; authorisation answers "what are you allowed to do?".

💡
Why OAuth matters in practice: it removes the need to repeatedly enter usernames and passwords. You register with one provider (Google, Microsoft Azure, Facebook, Twitter) and use authorisation tokens to access other services. For example, if you have authenticated your Google account, you can grant a third-party app access specifically to your email information without sharing anything else. These protocols are complex, but for cloud services they have become the standard.

The actors in an OAuth flow

👤 Resource Owner

The entity that owns the data in the resource server — for example, you are the Resource Owner of your Facebook profile.

🗄️ Resource Server

The API that stores the data the application wants to access.

📱 Client

The application that wants to access your data.

🔐 Authorization Server

The main engine of OAuth — it issues the tokens that grant access.

✅
Exam-ready one-liner: "OAuth authorises; OpenID authenticates; OpenID is built on OAuth flows."
🤔
Pause & predict: You click "Sign in with Google" on a new website. Which protocol establishes who you are, and which one controls what the website can access? (Answer: OpenID authenticates you; OAuth authorises the website's access to specific data.)

Transport Layer Security: Foundations

TLS is a generic security layer that slips between TCP and the application, giving encryption, integrity and origin authentication transparently.

From SSL to TLS

  • TLS was originally developed as the Secure Socket Layer (SSL) by Netscape (the company that later became Mozilla).
  • SSLv1 proved very flawed and was never really deployed.
  • SSLv2 was deployed but was also flawed.
  • SSLv3 was finally robust and was standardised by the IETF as Transport Layer Security (TLS).
  • Out of habit, TLS is still sometimes called SSL. But SSLv3 has been phased out (marginal usage) and is disabled by most corporations offering TLS software.
  • The latest version is TLS 1.3, standardised in 2018. We study TLS 1.2 first, then TLS 1.3.

Design rationale

The original purpose of SSL/TLS was to protect HTTP at the application layer, where messages were previously unencrypted. The design goals were:

  • A generic security layer (a "layer 4.5") sitting between TCP and the application layer.
  • TLS makes use of TCP underneath.
  • Reuse of the socket abstraction: applications read and write to TLS sockets just like TCP sockets.
  • Use of encryption, integrity and origin authentication made as transparent to the application as possible.

Why not place TLS at the application layer? Because every application-layer protocol would have to be extended to use it, and those protocols are often text-based and already complex — inefficient. Placing TLS at the transport layer, which deals in bytes, was far more straightforward and efficient.

ℹ️
Transparent means: the application does not have to be rewritten to gain security. It just uses a TLS socket instead of a TCP socket. Tools like Ettercap can perform man-in-the-middle attacks within the same network, capturing images and videos viewed by users — a vivid demonstration of why unprotected HTTP is dangerous.

Socket recap (a little more detail)

  • An application asks the kernel for network communication by defining its requirements, such as reliable, stream-based communication.
  • A socket is an object the application can write to and read from — very much like a file descriptor.
  • It is an abstraction over source IP, destination IP, source port, destination port and the protocol used.
  • Kernel-level communication comes in two flavours: streaming communication (TCP — reliable, connection-oriented) and datagram communication (UDP — unreliable, message-oriented).
  • A raw socket is a socket with no layer-specific formatting done by the kernel — all of it is left to the application.

TLS sockets

Sockets are created with system calls using a standardised API. TLS sockets are implemented in libraries:

  • The library implements the ciphers, MACs and so on.
  • The library creates the socket with help from the kernel.
  • The library then provides a TLS socket to the application, which behaves similarly to a normal TCP socket.

In Python, you first open a TCP socket and then wrap it into a TLS socket:

Python (client initiating the connection)
s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.connect((HOST, PORT))
t = ssl.wrap_socket(s, ...)

The ... is where the security parameters are defined, potentially including settings such as Diffie-Hellman for key exchange. Because security and cryptography are complex, safe defaults matter: wrapping has many parameters, and using the library's secure defaults is vital.

⚠️
Common trap: the common design is that a TLS socket wraps a normal socket, and the many wrapping parameters are easy to get wrong. Never invent your own cryptographic parameters — use the safe defaults provided by the library.

Conceptual view of TLS

  • TLS assumes the existence of an X.509 PKI (Public Key Infrastructure): the authenticating party must have an X.509 certificate identifying it. Other variants (such as pre-shared key) exist but are rare.
  • TLS authentication can be mutual, but commonly only the server authenticates to the client. The client application then often authenticates to the server application, for example with a password.
  • TLS 1.3 always uses Authenticated Diffie-Hellman (and therefore has forward security). TLS 1.2 only strongly suggested it and also allowed classic hybrid cryptography, where the key is created jointly by client and server through a complex key-creation process.
🧠
Forward secrecy in one line: even if the server's long-term private key is later stolen, past session keys stay secret — because each session's key came from fresh Diffie-Hellman values, not from the long-term key alone.

The TLS Handshake and Subprotocols

Two messages negotiate the cryptography, then two messages authenticate and establish the key.

The conceptual protocol flow

We show the idea of TLS for server-only authentication, using Diffie-Hellman. Let the actors be client C and server S, with secret Diffie-Hellman values c and s respectively:

The four-message shape
C → S : N_C
S → C : N_S, Cert_S, g^s, Sig_S(N_C, N_S, g^s)
C → S : g^c, MAC_{K_C,S}(X)
  where X = N_C, N_S, Cert_S, g^s, g^c, Sig_S(N_C, N_S, g^s)
S → C : MAC_{K_C,S}(Y)
  where Y = (X, MAC_{K_C,S}(X))

Rationale of the flow

First half — negotiation and freshness. The client sends a nonce (a random number used once) to identify the new session. The server picks its own nonce to refer to the session, sends its certificate, picks a Diffie-Hellman value, and signs everything. This half is mainly negotiating the cryptography and declaring the nonces that will guarantee freshness.

Second half — authentication and key establishment. The client can now authenticate the server, thanks to the certificate and the signed nonce. It derives the symmetric key and can use MACs (message authentication codes, which check integrity and authenticity) from this point on. The client sends its own Diffie-Hellman value. The correctness of Diffie-Hellman can be checked via MAC. The server now has the symmetric key too and creates the final MAC over everything. When the client receives that final MAC, it knows no parameters have been tampered with.

🧠
Memory hook: "two messages for negotiation, two for AKE" — this pattern is very common in cryptographic protocols. AKE means Authentication and Key Establishment.

Negotiation in TLS

TLS negotiates the concrete ciphers, hash functions and MACs to use between the principals — a practice common to many cryptographic protocols. The TLS standard contains codepoints for supported mechanisms. The client proposes a suite of mechanisms; the server either picks its choice or rejects the connection if none are suitable.

TLS also supports extensions:

  • Server Name Indication (SNI) — the domain name the connection is meant for.
  • Identification of the protocol being protected (so the right application protocol is used).
  • Certificate Transparency and other useful mechanisms, such as indications of unusual cryptography.

TLS subprotocols

TLS is message-based: its subprotocols define message exchanges. It is not a single protocol but two layers of protocols. The Record Protocol provides basic security services to higher-layer protocols and embeds messages, mapping them onto TCP. On top of it sit the handshaking protocols and the application data:

📼 Record Protocol

The base protocol: it embeds messages and maps them onto TCP, providing the reliable end-to-end secure service.

🤝 Handshake Protocol

Negotiates session details such as cryptographic algorithms and session keys. (This is the protocol's name, not a category.)

🔄 Change Cipher Spec

Signals transitions in the use of cryptography — that the next messages use different encryption.

🚨 Alert

Signals errors or issues during the TLS process to the peer entity.

Additionally, TLS Application Data refers to the secured payloads carried over the network.

Handshake Protocol messages

Our conceptual flow is the Handshake Protocol. Its messages map to the abstract notation. The most important are:

MessageContents / purpose
ClientHelloVersion number, nonce, cipher suites.
ServerHelloVersion number, nonce, cipher suites, session ID.
ServerCertificateThe server's certificate.
ServerKeyExchangeThe server's Diffie-Hellman parameter.
ClientKeyExchangeThe client's Diffie-Hellman value.
FinishedThe MACs that confirm nothing was tampered with.

Messages of the Change Cipher Spec protocol may appear before or after Handshake Protocol messages; they signal that the next messages use different encryption.

The TLS 1.2 flow in words

  1. The client establishes its security capabilities: protocol version, session ID, cipher suite, compression method and initial random numbers.
  2. The server may send its certificate, key exchange and a request for the client's certificate, then signals the end of the hello phase.
  3. The client sends its certificate if requested, sends its key exchange, and may send certificate verification.
  4. The server changes the cipher suite and finishes the handshake.
  5. The client can then send the application payload.
🤔
Pause & predict: Which message carries the Diffie-Hellman value that lets the client compute the shared key? (Answer: the server's value arrives in ServerKeyExchange; the client's own value goes out in ClientKeyExchange.)

TLS 1.3 and 0-RTT

TLS 1.3 strips away old crypto, forces modern AEAD ciphers, and cuts the handshake to one round trip — with a fast but risky 0-RTT option.

TLS 1.2 was already the result of many improvements to TLS 1.0 and TLS 1.1. But it still contained weaknesses: relatively old cryptography, MAC-then-encrypt instead of Encrypt-then-MAC, and the use of compression. From about 2008 there was serious pressure on the protocol, and a redesign was needed.

Major differences in TLS 1.3

  • TLS 1.2 allowed a null cipher (authenticate-only, no encryption); this is now disallowed.
  • TLS 1.3 allows only AEAD ciphers (Authenticated Encryption with Associated Data), such as AES-GCM and ChaCha20-Poly1305, which provide confidentiality and integrity together.
  • Diffie-Hellman is now the default, except for one pre-shared-key mode.
  • Encryption starts immediately after ServerHello.
  • Certificates are encrypted and integrity-protected, and so are the Diffie-Hellman values shared during the KeyShare process.
  • 1-RTT: the client can send application payload data after just one round-trip time.

The TLS 1.3 handshake in three steps: the client sends a TLS hello proposing a key-agreement protocol, parameters and the cipher suites it supports; the server replies with its chosen key-agreement protocol, parameters, cipher suite and its signed certificate; finally the client checks the server's certificate, generates the key, and can now make an application request (for example, an HTTPS GET).

💡
Why 1-RTT is a big deal: reducing the handshake from two round trips to one roughly halves the time to establish a secure connection. Encryption begins sooner and certificates are hidden from eavesdroppers.

Session resumption and 0-RTT

TLS 1.2 had two session resumption features that allowed a connection to be re-established in just one RTT:

  • Session identifier — the server can look up a previous key by a unique session ID.
  • Session ticket — the client holds a token it can send to the server to resume the connection.

TLS 1.3 deprecates these and replaces them with a pre-shared key (PSK) mode, conceptually similar to a session ticket. It uses the Early Data extension to signal that 0-RTT will be used. This is an intentional design choice that acknowledges the weaknesses involved.

The problems with 0-RTT are real:

🔓 Not forward-secure

The session key is not forward-secure. If it is compromised, all encrypted data becomes known to the attacker.

🔁 No replay protection

An attacker could resend data. So 0-RTT must only be used for idempotent messages at the application layer — for example, an HTTP GET.

⚙️ Operator risk

It is unknown whether operators will implement 0-RTT correctly — a configuration mistake could reopen the replay risk.

Internet Layer: IPSec

IPSec is a suite that protects the actual IP packet, deep in the kernel — giving authentication, confidentiality and key management for all traffic.

What IPSec is

IPSec (IP security) is a set of protocols that, like TLS, provides authentication and key establishment, confidentiality and integrity. IP-level security encompasses three functional areas:

  • Authentication — assures that a received packet really was sent by the party named as the source, and was not altered in transit.
  • Confidentiality — lets communicating nodes encrypt messages to prevent eavesdropping.
  • Key management — handles the secure exchange of keys.

IPSec embeds its protective mechanisms as IP payloads. Recall that TLS does this as TCP payloads.

TLS

  • Protects TCP payloads.
  • Does not protect any TCP packet information — no integrity for port number, segment number, etc.
  • Can work in user space.

IPSec

  • Authenticates and integrity-protects the actual IP packet.
  • Protects IP header information (the immutable parts).
  • Must run in kernel space — can only be configured by admins.

Why IPSec exists: the IPv4 packet problem

When an entity receives an IP packet, it has no assurance of:

  • Data origin — anyone can spoof a source IP address.
  • Data integrity — no way to confirm the data was not altered in transit.
  • Confidentiality — IP packets are not encrypted.

The idea of IPSec is to configure the protection for IP packets between two IP addresses or address ranges — done with a policy.

Applications of IPSec

IPSec can secure communications across a LAN, across private and public WANs, and across the Internet:

🏢 Secure branch office connectivity

Build a secure VPN over the Internet or a public WAN, reducing the need for private networks and cutting costs.

🏠 Secure remote access

A remote user with IP security protocols can dial an ISP and gain secure access to the company network, saving toll charges for travellers.

🤝 Extranet and intranet connectivity

Securely connect with partner organisations, ensuring authentication and confidentiality plus a key-exchange mechanism.

🛒 Electronic commerce security

Adds an extra layer of encryption and authentication on top of whatever the application already provides.

The principal feature is that IPSec can encrypt and/or authenticate all traffic at the IP level, so all distributed applications (remote logon, client/server, email, file transfer, Web access) can be secured. The advantage is that it is transparent to end users and applications, and it includes a filtering capability so only selected traffic incurs the overhead — for example, an enterprise can disallow links to untrusted sites, encrypt packets leaving the premises, and authenticate packets entering.

IPSec services (RFC 4301)

IPSec provides security services at the IP layer by letting a system select the required security protocols, determine the algorithms to use, and put in place the necessary cryptographic keys. RFC 4301 lists:

  • Access control
  • Connectionless integrity
  • Data origin authentication
  • Rejection of replayed packets (a form of partial sequence integrity)
  • Confidentiality (encryption)
  • Limited traffic flow confidentiality

Two protocols provide security: the Authentication Header (AH), an authentication protocol, and the Encapsulating Security Payload (ESP), a combined encryption/authentication protocol.

Components of IPSec

  1. Security Association Database (SAD)
  2. Security Policy Database (SPD)
  3. ESP — authentication, integrity and confidentiality.
  4. AH — authentication and integrity for the IP header (not the payload).
  5. IKEv2 — Internet Key Exchange, an AKE protocol.
  6. Two modes — tunnel and transport.

IPSec is highly complex, and some functionality is even duplicated.

Security Associations (SA)

A Security Association describes the concrete way incoming and outgoing packets are going to be protected. An SA is a negotiated outcome, with negotiation based on the Security Policy. Key facts:

  • An SA describes a simplex (one-way) connection — one direction.
  • You need two SAs to describe bi-directional communication.
  • In total there can be four SAs: two per party, and two per mode (ESP and AH).
  • SAs are stored in the Security Association Database.

Security Policy Database (SPD) and SAD entries

The SPD relates IP traffic to specific SAs (or to no SA, for traffic allowed to bypass IPSec). Each SPD entry defines a subset of IP traffic and points to an SA. Each entry is defined by a set of IP and upper-layer protocol field values called selectors — the selectors define the IP flow and are used to filter outgoing traffic and map it to a particular SA.

Outbound processing follows this sequence for each packet:

  1. Compare the selector fields in the packet against the SPD to find a matching entry, which points to zero or more SAs.
  2. Determine the SA, if any, for this packet and its associated SPI.
  3. Do the required IPSec processing (AH or ESP).

A Security Association is normally defined by these parameters in an SAD entry:

ESP versus AH

🛡️ ESP — Encapsulating Security Payload

Provides confidentiality, data origin authentication, connectionless integrity, anti-replay and limited traffic-flow confidentiality. It can work with many algorithms, including authenticated encryption such as GCM. It can be used stand-alone or combined with AH. It adds a header (after the IP header and possibly AH) and a trailer after the protected data.

✍️ AH — Authentication Header

Authenticates parts of the IP header and the payload — but does not encrypt. The authenticated parts are the "normally immutable" ones: source and destination IP, version, length, and so on. It excludes parts that change as the packet is forwarded, such as Time-to-live.

The ESP header fields include: the SPI (identifies the SA); the Sequence Number (32 bits, a monotonically increasing counter giving anti-replay); an initialisation value (IV) or nonce if the algorithm requires one; the Payload/Protected Data (a transport-level segment in transport mode, or an IP packet in tunnel mode); Pad Length (8 bits); Next Header (8 bits, identifying the first header in the payload, e.g. TCP); and the Integrity Check Value (ICV) or authentication data, computed over the ESP packet minus the Authentication Data field.

IKEv2

IKEv2 provides mutual authentication and key establishment between two parties. It negotiates cryptographic parameters such as ciphers and hash functions. It results in a total of four Security Associations — one SA per party and direction. The SAs created with IKEv2 are then used by AH and/or ESP, and are stored in the Security Association Database.

Tunnel mode versus transport mode

Tunnel mode

  • Used when gateways (network routers) add the protection for their hosts.
  • The entire IP packet is encrypted and authenticated, then placed inside a new IP packet plus an IPSec header.
  • Routers along the way cannot inspect the inner IP header; the new packet may have totally different addresses.
  • Used when one or both ends of the SA is a security gateway such as a firewall or secure router.

Transport mode

  • Used when the endpoint is the same principal that adds the protection.
  • Adds a header (and trailer for ESP) that protects the normal, non-encapsulated payload.
  • Authenticates and encrypts only the payload; the IP header is only authenticated, not encrypted.
  • Typically end-to-end host-to-host; a drawback is that traffic analysis is possible.

VPNs

Tunnel mode can implement a virtual private network (VPN): a private network configured within a public network (a carrier's network or the Internet) to take advantage of the economies of scale and management of large networks. Gateways tunnel (encapsulate) the traffic. VPNs are widely used by enterprises to create wide-area networks spanning large regions, to provide site-to-site connections to branch offices, and to let mobile users dial into the company LAN. In a typical scenario, an organisation has LANs at dispersed sites; traffic leaving a site through a WAN is encrypted by an IPSec device (router or firewall) at the boundary, and decrypted on the way in — transparently to the workstations and servers on the LAN.

🧠
Memory hook: Tunnel = whole packet wrapped in a new envelope (gateway to gateway). Transport = only the letter is sealed (host to host), and the envelope's address stays readable.
🤔
Pause & predict: A company connects two branch offices over the public Internet with a router-to-router IPSec link. Which mode is this, and why? (Answer: tunnel mode — the gateways at each end wrap the whole original packet.)

Key Takeaways

If you remember nothing else, remember this.

1

Networks carry everything we do, and attackers have a structural advantage: input arrives from anyone, and one weak device is enough to join a botnet.

2

The Internet is a network of networks built from hosts/end systems, packet switches, communication links (with bandwidth) and ISPs.

3

A protocol defines format, order and actions; the TCP/IP model has four layers — application, transport, network and network interface.

4

Sockets are the API between application and transport. Socket and above is the app developer's job; below the socket belongs to the OS.

5

TCP is reliable and connection-oriented (three-way handshake, ACKs, flow and congestion control); UDP is lightweight and best-effort (no handshake, loss-tolerant use cases).

6

The network layer moves datagrams with IP, plus routing protocols (RIP, OSPF, BGP) and ICMP; routers forward datagrams from input to output ports.

7

IPv4 addresses are 32-bit and tied to interfaces, written in dotted-decimal; classes A–E gave way to CIDR, and NAT lets a whole network share one public address.

8

Subnetting borrows host bits: subnets = 2^(borrowed), usable hosts = 2^(host bits) − 2. A /26 gives 4 subnets of 62 hosts each.

9

IPv6 uses 128-bit addresses, a 40-byte fixed header, no header checksum, and native IPSec support; migration is slow because of compatibility and cost.

10

The link layer delivers frames between adjacent nodes using 48-bit MAC addresses found via ARP — distinct from IP addresses.

11

Attacks violate security goals: passive attacks eavesdrop (hard to detect), while active attacks replay, masquerade, modify messages or deny service.

12

OAuth authorises and OpenID authenticates at the application layer; TLS secures TCP; IPSec secures the IP packet. TLS 1.3 uses AEAD-only ciphers, mandatory forward secrecy and 1-RTT (with risky 0-RTT).

Glossary

Every term you need to speak this week's language.

Protocol
An agreed set of rules for communication: it defines the format of messages, the order in which they are exchanged, and the actions taken on sending or receiving them.
Host / end system
A computing device at the edge of the network where applications run — a smartphone, laptop, server or IoT device.
Packet switch
A device that takes incoming packets and forwards them towards their destination; mainly routers and link-layer switches.
Communication link / bandwidth
A physical or over-the-air path connecting devices and switches (fibre, copper, radio, satellite). Its transmission rate is called bandwidth.
TCP/IP model
The four-layer practical blueprint of the Internet: application, transport, network, and network interface (link + MAC).
Socket
The software interface (API) between an application and the transport layer. A process sends and receives messages through its socket, like a door on a house.
Frame
A link-layer packet that encapsulates a datagram for delivery between two physically adjacent nodes.
MAC address
A unique 48-bit address used locally to get a frame from one interface to another physically connected interface on a LAN.
ARP
Address Resolution Protocol — finds a MAC address given an IP address on the local link.
IPv4 address
A 32-bit identifier associated with a host or router interface, usually written in dotted-decimal notation (e.g. 223.1.1.1).
Interface
The connection between a host or router and a physical link. Routers usually have several; hosts usually have one or two. IP addresses belong to interfaces.
Subnet
A logical subdivision of an IP network: device interfaces that can reach each other without passing through an intervening router.
Subnet mask / CIDR
A mask that splits an address into a network part and a host part. CIDR notation (e.g. /26) states how many leading bits are the network portion.
NAT
Network Address Translation — all devices in a local network share one public IPv4 address as far as the outside world is concerned, using a translation table.
IPv6
The successor to IPv4, using 128-bit addresses, a 40-byte fixed header, no header checksum, and native IPSec support.
Attack on a network
An event or sequence of actions that might violate one or more security goals, such as availability, integrity or confidentiality.
Passive attack
Eavesdropping on or monitoring transmissions (release of message contents, traffic analysis). Very hard to detect because data is not altered.
Active attack
Modification of the data stream or creation of a false stream; the four categories are replay, masquerade, modification of messages and denial of service.
Masquerade
Impersonation: one entity pretends to be a different entity, often to gain extra privileges.
Denial of service (DoS/DDoS)
Any action that reduces the availability or correct functioning of a service or system, such as flooding a remote server.
OAuth
A standard for authorisation that lets a user grant another service access to parts of their account, using tokens (like a Kerberos ticket) over HTTP.
OpenID
An authentication protocol that uses OAuth flows. It establishes who you are, complementing OAuth's job of deciding what you may access.
TLS
Transport Layer Security — a generic security layer ("layer 4.5") between TCP and the application, providing encryption, integrity and origin authentication.
AEAD cipher
Authenticated Encryption with Associated Data — a cipher that gives confidentiality and integrity together. TLS 1.3 allows only these (e.g. AES-GCM, ChaCha20-Poly1305).
IPSec
A set of protocols providing authentication, key establishment, confidentiality and integrity for IP packets; it runs in kernel space and is configured by admins.
Security Association (SA)
A negotiated description of how packets will be protected. It is a one-way (simplex) connection; two SAs are needed for two-way traffic.
IKEv2
Internet Key Exchange v2 — provides mutual authentication and key establishment, negotiates cryptographic parameters, and creates four SAs used by AH and/or ESP.
ESP
Encapsulating Security Payload — provides confidentiality, data origin authentication, connectionless integrity and anti-replay. Can be used alone or with AH.
AH
Authentication Header — authenticates parts of the IP header and the payload (the normally immutable fields), but does not encrypt.
VPN
Virtual Private Network — a private network built within a public one; IPSec tunnel mode, with gateways tunnelling traffic, is a common way to build one.

Q1

Define a protocol and explain the human-conversation analogy. What three things does a protocol define?

Answer: A protocol is an agreed set of rules governing communication between two or more entities. It defines the format of messages, the order in which messages are sent and received, and the actions taken on transmission or receipt of a message. In the human analogy, you say "Hi" to start, receive "Hi" back as a signal to proceed, then ask "What's the time?" — in the network version a PC sends a TCP connection request, the server responds, then the PC requests a URL and the server returns files.
Q2

Name the four TCP/IP layers and give one protocol or idea belonging to each. How does the OSI model relate?

Answer: (1) Application — HTTP, SMTP, FTP, DNS; carries messages. (2) Transport — TCP and UDP; carries segments and provides logical end-to-end communication. (3) Network — IP, routing protocols (RIP, OSPF, BGP), ICMP; carries datagrams. (4) Network interface — link and MAC layers; carries frames. The OSI model was historically important for standardisation but is largely theoretical today; TCP/IP is the practical framework of the Internet.
Q3

Explain what a socket is, using the house-and-door analogy, and state where the boundary between application and OS lies.

Answer: A process is like a house and its socket is like its door. To send a message, the process shoves it out the door; the transport infrastructure on the other side delivers it to the destination process's door. Two sockets are involved, one on each side. A socket is the API between the application and the transport layer. Socket and above is controlled by the application developer; below the socket is controlled by the OS.
Q4

Contrast TCP and UDP, describe the TCP three-way handshake, and explain flow control and MSS.

Answer: TCP is connection-oriented and reliable: a three-way handshake establishes the connection, it is point-to-point, delivers a reliable in-order byte stream, uses cumulative ACKs with retransmission, is full-duplex, and applies flow and congestion control with pipelining and dynamic window sizing. UDP is connectionless and lightweight: no handshake, best-effort, unreliable and unordered, with a checksum for basic error detection. The handshake: (1) client sends SYN; (2) server replies SYN/ACK; (3) client sends ACK. Flow control stops the sender overwhelming the receiver; MSS (Maximum Segment Size) limits how much data a segment carries.
Q5

What is the network layer's job, what are its three components, and what does a router do? Mention the datagram format and MTU.

Answer: The network layer moves datagrams from one host to another, encapsulating transport segments and delivering them at the destination. Its three components are the IP protocol (defines datagram fields and how devices act on them — the only protocol every network-layer device must run), the routing component (RIP, OSPF, BGP, or SDN controllers compute forwarding tables), and ICMP for error reporting and network-layer information. A router examines header fields in passing datagrams and moves them from input ports to output ports. A datagram has a header (source/destination IP, protocol, TTL, checksum, version) and data; its maximum size is the MTU (often 1500 bytes for Ethernet), and larger datagrams are fragmented.
Q6

Explain IPv4 addressing (size, interfaces, dotted-decimal), convert 223.1.1.1 to binary, list the address classes, and say what CIDR is.

Answer: An IPv4 address is a 32-bit identifier tied to an interface (the connection to a physical link), so routers usually have several and hosts one or two. There are 232 addresses, written in dotted-decimal. 223.1.1.1 = 11011111.00000001.00000001.00000001. Classes: A 0–127 (mask 255.0.0.0, large networks), B 128–191 (255.255.0.0), C 192–223 (255.255.255.0, small networks), D 224–239 (multicast), E 240–255 (experimental). CIDR (Classless Inter-Domain Routing) replaced the strict class system, allowing flexible allocation; a prefix such as /26 says how many leading bits are the network portion.
Q7

Work the subnetting example: for 192.168.10.0 with mask 255.255.255.192 (/26), how many subnets and hosts, and what are the four subnet ranges? Then solve 172.16.13.5 with mask 255.255.255.128.

Answer: The mask 255.255.255.192 is 11111111.11111111.11111111.11000000. /26 uses 26 network bits, leaving 6 host bits. Borrowed bits = 26 − 24 = 2, so subnets = 22 = 4. Hosts = 26 − 2 = 62. Block size = 256 − 192 = 64. Subnets: 192.168.10.0/26 (hosts .1–.62, broadcast .63); 192.168.10.64/26 (hosts .65–.126, broadcast .127); 192.168.10.128/26 (hosts .129–.190, broadcast .191); 192.168.10.192/26 (hosts .193–.254, broadcast .255). For 172.16.13.5/255.255.255.128: 172 is Class B; the mask /25 splits the /24 into two, and .5 falls in the first, so subnet address = 172.16.13.0 and broadcast = 172.16.13.127.
Q8

If a host has address 172.16.45.14/30, what is its subnetwork? Explain NAT and the key features of IPv6, and describe the IP hourglass.

Answer: /30 means 30 network bits and 2 host bits (blocks of 4). 172.16.45.14 = 10101100.00010000.00101101.00001110; masking the last 2 bits gives ...00001100 = 172.16.45.12, so the subnet is 172.16.45.12/30. NAT lets all devices in a local network share one public IPv4 address, using a translation table to map private address/port pairs to public ones (e.g. public 138.76.29.7:5007 ↔ private 10.0.0.1:3345); it also hides the internal network. IPv6 uses 128-bit addresses (removing the need for NAT), a 40-byte fixed header, no header checksum, no hop-by-hop fragmentation, a 20-bit field for prioritising traffic streams, and native IPSec support; migration is slow (compatibility, ROI, NAT versions). The IP hourglass is the Internet's thin waist: one network-layer protocol (IP) that every connected device must implement.
Q9

Describe the link layer's job and services, and explain MAC addresses and ARP versus IP addresses.

Answer: Nodes are hosts and routers; links connect adjacent nodes (wired, wireless, LANs); a frame is the link-layer packet that encapsulates the datagram. The link layer transfers a datagram from one node to the physically adjacent node over a link. Services include framing and link access (with MAC addresses in the frame header identifying source and destination), reliable delivery between adjacent nodes, flow control, error detection and correction, and half- and full-duplex operation. Each LAN interface has a unique 48-bit MAC address and a locally unique 32-bit IP address. ARP finds a MAC address given an IP address. IP is used end-to-end across the Internet; MAC is used only locally on the link.
Q10

Define an attack on a network, distinguish passive from active attacks, list the four categories of active attack, and give several ways security goals can be compromised.

Answer: An attack is an event or sequence of actions that might violate one or more security goals. The difference from simple software security is that input arrives from remote parties with no a priori control over who can send it. Passive attacks eavesdrop or monitor (release of message contents, traffic analysis) and are very hard to detect because they do not alter data. Active attacks modify the data stream or create a false one, in four categories: replay, masquerade, modification of messages, and denial of service. Ways to compromise goals: masquerade (impersonation), eavesdropping, loss or modification of information, forgery of information, denial of accountability, sabotage/DoS, and authorization violation.
Q11

Map the common cryptographic protocols to their layers. Then explain the difference between OAuth and OpenID and name the four OAuth actors.

Answer: Link layer: WPA3/WPA2 (WPA and WEP are broken). Network layer: IPSec and IKEv2. Transport layer: TLS (for TCP) and DTLS (for UDP). Application layer: OpenID, OAuth, DNSSEC. In a professional role you are most likely to meet TLS, WPA2/WPA3, OpenID, OAuth and IPSec, in that order. OAuth is a standard for authorisation — it lets a user grant another service access to parts of their account using tokens (like a Kerberos ticket), and is designed for HTTP. OpenID is an authentication protocol that uses OAuth flows and is complementary. The four OAuth actors: Resource Owner (owns the data), Resource Server (the API storing the data), Client (the app wanting access) and Authorization Server (the main engine issuing tokens).
Q12

Trace TLS from SSL to TLS 1.3, explain its design rationale and conceptual view, then describe its subprotocols and the key Handshake Protocol messages.

Answer: TLS began as Netscape's SSL: SSLv1 was very flawed and never deployed, SSLv2 was deployed but flawed, and SSLv3 was robust and standardised by the IETF as TLS. SSLv3 is now phased out; TLS 1.3 (2018) is latest. Design rationale: protect HTTP via a generic "layer 4.5" between TCP and the application, reusing the socket abstraction, making encryption, integrity and origin authentication transparent. It is not at the application layer because every app protocol would need extending and they are often text-based and inefficient. Conceptual view: TLS assumes an X.509 PKI (the authenticating party has an X.509 certificate); authentication can be mutual but is commonly server-only, with the client authenticating by password. TLS 1.3 always uses authenticated Diffie-Hellman (forward security); TLS 1.2 also allowed hybrid key creation. Subprotocols: Record Protocol (maps messages onto TCP), Handshake Protocol, Change Cipher Spec, Alert, plus TLS Application Data. Key handshake messages: ClientHello (version, nonce, cipher suites), ServerHello (version, nonce, cipher suites, session ID), ServerCertificate, ServerKeyExchange (DH parameter), ClientKeyExchange (DH value), Finished (MACs).
Q13

List the major differences in TLS 1.3, explain 1-RTT, and describe 0-RTT with its three problems.

Answer: TLS 1.2's weaknesses included old cryptography, MAC-then-encrypt instead of Encrypt-then-MAC, and compression, leading to a redesign from about 2008. TLS 1.3 differences: the null cipher (authenticate-only) is disallowed; only AEAD ciphers are allowed (AES-GCM, ChaCha20-Poly1305); Diffie-Hellman is the default except for one pre-shared-key mode; encryption starts immediately after ServerHello; certificates and Diffie-Hellman values (KeyShare) are encrypted and integrity-protected; and 1-RTT lets the client send application payload after just one round trip. 0-RTT replaces TLS 1.2's session identifier and session ticket with a pre-shared-key mode, signalled by the Early Data extension. Problems: the session key is not forward-secure (if compromised, all encrypted data is exposed); there is no replay protection, so it must only be used for idempotent messages such as HTTP GET; and it is unknown whether operators will implement it correctly.
Q14

Explain IPSec: how it differs from TLS, its services, its components, the Security Association and SPD/SAD, ESP versus AH, IKEv2, and tunnel versus transport mode.

Answer: IPSec is a set of protocols providing authentication and key establishment, confidentiality and integrity, embedding its protections as IP payloads (TLS uses TCP payloads). Unlike TLS, IPSec authenticates and integrity-protects the actual IP packet, and it must run in kernel space (configured by admins), whereas TLS can run in user space. RFC 4301 services: access control, connectionless integrity, data origin authentication, rejection of replayed packets, confidentiality, and limited traffic flow confidentiality. Components: SAD, SPD, ESP, AH, IKEv2, and two modes. An SA describes how packets are protected; it is a negotiated, simplex (one-way) connection, so two are needed for two-way traffic (up to four in total, two per party and two per mode). The SPD maps IP traffic to SAs via selectors; the SAD stores SA parameters such as the SPI, sequence number counter, anti-replay window, AH/ESP information, lifetime, mode and path MTU. ESP gives confidentiality, authentication, integrity and anti-replay; AH authenticates parts of the IP header and payload but does not encrypt, covering the normally immutable fields (source/destination IP, version, length) and excluding changing fields such as TTL. IKEv2 provides mutual authentication and key establishment, negotiating ciphers and hashes and creating four SAs used by AH/ESP. Tunnel mode (gateways) encrypts and authenticates the whole original packet inside a new IP packet plus IPSec header, and can build a VPN; transport mode (end-to-end hosts) protects only the payload, authenticating but not encrypting the IP header, and allows traffic analysis.
