INFO3616 · Week 8 · Network Security: Protocols

Building Trust, Layer by Layer

Every time you load a page, check email, or join campus Wi-Fi, protocols negotiate keys, prove identities, and protect bytes. This week we walk that stack from the link layer to the application, meet the attacks that target each layer, and study the protocols you are most likely to meet at work: TLS, IPsec, and OAuth/OpenID.

Read this first: security is a negotiation, not a wall. A protocol cannot assume the network is trustworthy, so its first messages prove who is on the other end and agree on a shared secret. Every secure connection begins with a handshake trading freshness (nonces), identity (certificates), and keys (Diffie-Hellman).

The Networked World We Have to Defend

Networks carry everything we care about, which is exactly why attackers aim at them first.

Our infrastructure, applications, and services are deeply integrated into networked environments, and reliance grew sharply after COVID-19 accelerated remote work. Networks run critical operations, from power grids to remote business, and organisations often build private networks and use VPNs for remote connections.

Network security protects these systems because most attacks target networked environments, including remote exploits such as SQL injection. The field differs from ordinary software security because of asymmetry: an attacker can recruit almost any device, so a browser, CCTV camera, or IoT sensor can all join a botnet, leaving defenders structurally disadvantaged.

The Internet in one picture

The Internet interconnects hundreds of millions of devices. Roughly 850 million hosts were connected as of July 2011, excluding phones and laptops, bringing the estimate to about 2 billion users.

Hosts (edge)→ Communication links→ Packet switches→ ISPs→ Network of networks

A host or end system is a device at the edge where applications run. A communication link is the physical or over-the-air path connecting devices, from coaxial and fibre to radio and satellite, and its transmission rate is bandwidth. A packet switch takes incoming packets and forwards them toward their destination; routers and link-layer switches are the main kinds. An ISP provides access: residential, corporate, university, or public Wi-Fi.

⚠️
Common trap: treating the Internet as one managed system. A network is a collection of devices, routers, and links managed by one organisation such as an ISP, university, or corporation; the Internet is a "network of networks", so trust never extends globally by default.

Protocols and the TCP/IP Model

A protocol is a contract about message format, message order, and the actions each side takes.

The OSI (Open Systems Interconnection) model standardised network architecture historically but is largely theoretical today. The practical framework is the TCP/IP model with four layers, and almost every security decision this week sits in one of them.

🧱 Application

Where applications and their protocols live: HTTP, SMTP, FTP, DNS.

🚚 Transport

Moves application messages between processes on different hosts. TCP and UDP.

🗺️ Network

Moves datagrams host-to-host across the Internet. Home of IP.

🔌 Network interface

The link layer plus the physical / Media Access Control layer. Moves frames between adjacent nodes.

What exactly is a protocol?

Communication happens using protocols, which control the sending and receiving of messages. Examples are HTTP, TCP, IP, DNS, and SSH. A protocol defines the format and order of messages exchanged between two or more entities, plus the actions taken on transmission or receipt of a message or event.

Humans run protocols constantly, so the analogy works. To ask the time you first greet someone; a "Hi" comes back; you take that cordial reply as permission to proceed. The network version has the same shape: the PC sends a TCP connection request, the server returns a response, then the PC requests a URL and the server returns files.

The application layer and the socket

The application layer holds the Web, email, voice over IP, and social networking. HTTP handles Web document request and transfer, SMTP transfers email, FTP moves files, and DNS translates names such as www.ietf.org into addresses. The packet exchanged here is a message.

Applications send and receive through a socket. A process is a program running in a host; a socket is the interface between the application and transport layers and the API between application and network. Analogy: a process is a house and its socket is the door, through which messages pass to the transport infrastructure beyond.

ℹ️
Key distinction: the socket and everything above it are controlled by the application developer; everything below is controlled by the operating system. That boundary explains why TLS and IPsec feel so different to deploy.

The Transport Layer: TCP, UDP, and Handshakes

Transport offers two flavours: TCP for reliable streams you can build on, UDP for fast datagrams you cannot.

The transport layer provides logical communication between application processes on different hosts. The sender breaks application messages into segments and passes them down; the receiver reassembles them into messages. The Internet has exactly two transport protocols: TCP and UDP.

TCP: Transmission Control Protocol

TCP is connection-oriented and reliable. It requires a preliminary handshake establishing the transfer parameters, and a connection is always point-to-point: one sender, one receiver. It supports full-duplex bidirectional flow, uses pipelining so several unacknowledged segments can be outstanding, and manages a maximum segment size (MSS). Acknowledgements are cumulative, covering all data up to the first missing byte. Flow control stops the sender overwhelming the receiver's buffer, and congestion control throttles the source when the network is congested, both via window sizing.

  1. Client sends SYN asking whether the server is open for new connections.
  2. Server replies SYN/ACK, confirming receipt; it must have an open port able to accept the connection.
  3. Client answers ACK. The first two segments carry no payload; the third may contain data.

UDP: User Datagram Protocol

UDP is connectionless and lightweight: no handshake, so no round-trip setup cost. It is a "no frills" best-effort service with no reliability, ordering, flow control, or congestion control, so segments may be lost or arrive out of order. It includes a checksum for basic error detection, and applications can add reliability. UDP suits streaming multimedia (loss-tolerant, rate-sensitive), DNS, SNMP, HTTP/3, and real-time apps. Notably, HTTP/3 is the first HTTP protocol that does not rely on TCP.

The Network Layer and the IP Protocol

The network layer moves datagrams across the whole Internet, and IP is the one protocol every device must speak.

The network layer (also called the Internet layer) moves packets called datagrams from one host to another. The transport protocol passes a segment and a destination address down, like handing the postal service a letter with an address. The sender encapsulates segments into datagrams for the link layer; the receiver delivers segments back up. Network-layer protocols exist in every Internet device, hosts and routers alike.

📦 IP protocol

Defines the datagram's fields and how hosts and routers act on them. There is only one IP protocol, and all devices with a network layer must run it.

🧭 Routing

Determines the path via routing protocols such as RIP, OSPF, and BGP, or software-defined networking controllers, and computes forwarding tables.

🛎️ ICMP

Reports errors in datagrams and answers requests for network-layer information.

The IPv4 datagram format

A datagram has a header and a data (payload) section. The header carries the source and destination IP addresses, protocol, time to live (TTL), and a checksum, plus a version field saying IPv4 or IPv6. The maximum size is bounded by the Maximum Transmission Unit (MTU) of the underlying network, often 1500 bytes for Ethernet; larger datagrams may be fragmented.

💡
Why it matters: the original IPv4 packet gives no confidentiality and no integrity, and cannot prove origin, because source addresses can be spoofed. That gap is exactly what IPsec fills.

IPv4 addressing

Every host and router interface needs its own address; an address belongs to an interface, not a whole device. Routers usually have several interfaces; a host typically has one or two, such as wired Ethernet and wireless 802.11. An IPv4 address is 32 bits, giving 232 addresses, about 4 billion, written in dotted-decimal notation. For example, 223.1.1.1 is 11011111 00000001 00000001 00000001. Each interface is globally unique except behind NAT, and part of the address is set by its subnet.

🧠
The IP hourglass: the Internet is a thin waist. Every application and transport protocol sits above IP, every link technology below it, but the waist is a single protocol every one of billions of devices must implement. Protect IP and you protect almost everything.

Subnets, NAT, and IPv6

Subnets carve a network into manageable, more secure pieces, while NAT and IPv6 answer the shortage of addresses.

An IP subnet is a logical subdivision of a network. Devices in the same subnet can physically reach each other without passing through an intervening router. The subnet part of an address is the common high-order bits and the host part the low-order bits. To find subnets, detach each interface from its device, creating "islands" of isolated networks. Subnetting extends the default mask, borrowing bits from the host portion to create more network addresses, which uses space efficiently, shrinks broadcast domains, and improves access control.

A worked subnetting example

Take 192.168.10.0 with mask 255.255.255.192, or /26. The mask is 11111111.11111111.11111111.11000000: 26 network bits, leaving 6 host bits. Subtracting the original 24 Class C bits leaves 2 borrowed bits, so 22 = 4 subnets. Hosts per subnet are 26 − 2 = 62, subtracting the network and broadcast addresses. The block size is 256 − 192 = 64, giving the four ranges below.

NAT: Network Address Translation

Picture 15 PCs, a phone, and two tablets all needing access at once. Each would need a routable address, but IPv4 space is too small. Proposed in 1994, NAT became a necessary tool against IPv4 exhaustion: all devices in a local network share just one IPv4 address as far as the outside world is concerned. Inside, interfaces sit on a subnet such as 10.0.0.0/24, and every datagram leaving carries the same source NAT address, say 138.76.29.7, but a different source port. A NAT translation table maps private addresses and ports to public ones, so public 138.76.29.7:5007 might map to private 10.0.0.1:3345. NAT also adds safety: outsiders cannot directly attack internal devices, and internal information does not casually reach outside.

IPv6

IPv6 was motivated by watching the 32-bit space fill up. It uses 128-bit addresses, providing trillions of addresses and eliminating the need for NAT. It streamlines processing with a 40-byte fixed header, removes the header checksum and hop-by-hop fragmentation (pushing error checking and packet sizing to the edges), and adds a 20-bit field so routers can identify and prioritise flows. IPv6 was designed with IPsec support as a core requirement. Its rollout is incomplete because of compatibility concerns, financial return on investment, and the many NAT-based versions already deployed.

The Link Layer and Link-Layer Security

The link layer only moves a frame to the next physically adjacent node, and that local scope is where Wi-Fi security lives.

Hosts and routers are nodes; the channels connecting adjacent nodes are links (wired, wireless, or within a LAN). The layer-1 or layer-2 packet is a frame, encapsulating a datagram, and the layer's job is to transfer a datagram from one node to the physically adjacent node over a link. Its services include framing and link access (encapsulating the datagram in a frame with source and destination MAC addresses) and reliable delivery between adjacent nodes, with flow control, error detection, error correction, and half- or full-duplex operation.

MAC address — a unique 48-bit identifier used locally to get a frame from one interface to another physically connected interface. Every LAN interface has a unique MAC address and a locally unique 32-bit IP address. MAC addresses are local; IP addresses are routable, so they are not the same thing. To find a MAC address from a known IP address, a device uses the Address Resolution Protocol (ARP).
⚠️
Common trap: confusing MAC and IP addresses. A frame's MAC addresses are rewritten at each hop, while the datagram's addresses stay put across the whole path.
ℹ️
Link-layer crypto: this is where Wi-Fi security sits. WPA3 and WPA2 are current, while WPA and WEP are considered compromised and insecure. We focus above Layer 2, working top-down, so Wi-Fi gets no dedicated section, but you should place it on the layer map.

Attacks on Networks and the Goals They Break

An attack is any event or sequence of actions that may violate a security goal, and knowing the goal tells you the defence.

We define attacks on networks as events or sequences of actions that potentially violate one or more security goals. A DDoS attack on a server, for example, compromises availability. This differs critically from simpler software security: input to a web or mail server comes from remote, with no initial control over who can send it. Remote accessibility lets attackers send any kind or amount of traffic, and once inside a network an attacker has ample opportunity to explore, breach, and exploit it.

Passive versus active attacks

Passive attacks

  • Eavesdropping on, or monitoring of, transmissions
  • Goal: obtain information being transmitted
  • Two types: release of message contents and traffic analysis
  • Very difficult to detect, because no data is altered

Active attacks

  • Modify the data stream or create a false stream
  • Four categories: replay, masquerade, modification of messages, denial of service
  • Masquerade = one entity pretends to be another
  • Authentication sequences can be replayed to gain extra privileges

Seven ways to compromise security goals in networks

🎭 Masquerade / impersonation

An entity claims to be another entity.

👂 Eavesdropping

Reading information you were not meant to read. A man-in-the-middle can capture packets, sometimes including logins if the connection is not secure (HTTPS).

✂️ Loss or modification of information

Data is altered or destroyed. The attacker intercepts a packet, changes it, and forwards it on; for a password change they swap in their own password.

✍️ Forgery of information

Creating new information in another entity's name. After stealing credentials, the attacker changes your address to theirs.

🙈 Denial of accountability

Falsely denying participation. Because the attacker used your credentials, they can deny it and you may have to prove you did not act.

💥 Sabotage / denial of service

Reducing availability or correct functioning; a DDoS attack on a remote server is the classic example.

The seventh is authorisation violation: using a service or resource you were not meant to use. The moment an attacker takes over your account and accesses it, that is an authorisation violation.

🧠
Memory hook: eavesdropping attacks confidentiality, masquerade and forgery attack authenticity, modification attacks integrity, denial of service attacks availability.

Application Layer: OAuth and OpenID

OAuth delegates authorisation with tokens, and OpenID rides those flows to provide authentication.

OAuth is a standard for authorisation. It lets users of one service grant another service controlled access to parts of their account, reminiscent of Kerberos, which uses tickets to authorise access: an authorisation server creates a ticket (token) that allows access. If you have authenticated your Google account, OAuth lets you grant access specifically to email information without sharing anything else. The benefit is removing repeated credential entry: you register with one provider and use authorisation tokens for the others. OAuth is designed for HTTP and HTTPS and supports several standardised flows, which makes those flows genuinely complex.

OpenID focuses on authentication. With the Google example, you authenticate on another website using your Google ID, leveraging OAuth flows underneath; it is complementary, not competing. Many accounts are now linked across services, so one Facebook or Google account unlocks many others. Despite the complexity, OpenID has become the cloud standard on efficiency and security grounds, used by Google, Microsoft Azure, Facebook, and Twitter.

The four actors in an OAuth flow

👤 Resource owner

Owns the data on the resource server. On your Facebook profile, you are the resource owner.

🗄️ Resource / API server

The API storing the data the application wants to access.

📱 Client

The application that wants to access your data.

🔑 Authorization server

The main engine of OAuth; it issues the tokens clients present.

⚠️
Common trap: saying OAuth "logs you in". OAuth is authorisation: it grants access to resources. OpenID is the authentication layer that says who you are. "Sign in with Google" uses both.

TLS: A General-Purpose Layer at 4.5

TLS slides between TCP and the application so every application gets encryption, integrity, and origin authentication for free.

Transport Layer Security (TLS) is one of the most widely used security services; its latest version is 1.3. It evolved from Secure Sockets Layer (SSL), developed by Netscape, which later became Mozilla. SSLv1 was very flawed and never deployed. SSLv2 was deployed but also flawed. Only SSLv3 was robust, and the IETF later standardised it as TLS. People still say "SSL" out of habit, but SSL3 has been phased out and is disabled by most organisations.

The design goals

The original purpose was to secure HTTP, previously sent unencrypted at the application layer. Rather than alter the application layer, the designers created a generic security layer between TCP and the application layer, sometimes called "layer 4.5". The goals: be a generic security layer between TCP and the application; make use of TCP underneath; reuse the socket abstraction, so applications use TLS sockets like TCP sockets; and deliver encryption, integrity, and origin authentication as transparently as possible.

💡
Why not the application layer? Every application protocol would need extending to use it, and those protocols were often text-based and already complex. The transport layer deals in bytes, which is simpler and more efficient. Tools like Entercap show the problem: on an unsecured network they can run man-in-the-middle attacks and capture the images and videos a user views.

TLS sockets

An application requests network communication from the kernel by stating requirements such as "reliable, stream-based". A socket is an object the application writes into and reads from, much like a file descriptor, abstracting over source IP, destination IP, source port, destination port, and protocol. A raw socket skips kernel formatting and leaves everything to the application. TCP gives reliable, connection-oriented streaming communication; UDP gives unreliable, message-oriented datagram communication.

TLS sockets are implemented in libraries. The library handles ciphers, MACs, and other setup, works with the kernel to create the socket, and gives the application something that behaves like a normal TCP socket. In Python you open TCP and then wrap it:

Python: TCP then TLS
s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.connect((HOST, PORT))
t = ssl.wrap_socket(s, ...)

The ... defines security parameters, potentially including Diffie-Hellman. Because cryptography is easy to get wrong, use the safe defaults the library provides; the TLS socket wraps the normal socket, and safe defaults are vital.

Certificates and who authenticates whom

TLS relies on an X.509 Public Key Infrastructure (PKI): each party needing authentication must have an X.509 certificate. Other variants such as pre-shared keys exist but are rare. Authentication can be mutual, but commonly only the server authenticates to the client; the client then authenticates at the application layer, often with a password. TLS 1.3 always uses authenticated Diffie-Hellman, giving forward security, while TLS 1.2 strongly recommended it but also supported traditional hybrid cryptography, where the key is jointly created by client and server.

🧠
Remember the triple: encryption (confidentiality), integrity, and origin authentication. If you recall one thing about TLS, recall that.

Inside the TLS Handshake: Nonces, Diffie-Hellman, MACs

The handshake spends two messages negotiating and two more authenticating and agreeing on a key.

Consider TLS for server-only authentication with Diffie-Hellman. The actors are client C and server S, with secret Diffie-Hellman values c and s. Nonces NC and NS provide freshness.

C → S : NC→ S → C : NS, CertS, gs, SigS→ C → S : gc, MAC(X)→ S → C : MAC(Y)
  1. C → S : NC. The client sends a nonce to identify the new session, starting the negotiation.
  2. S → C : NS, CertS, gs, SigS(NC, NS, gs). The server picks its own nonce, sends its certificate, picks a Diffie-Hellman value, and signs everything. Signing the client's nonce ties the reply to this session and blocks replay.
  3. C → S : gc, MACK(X). The client authenticates the server via the certificate and signed nonce, derives the symmetric key, and can now use MACs. It sends its own Diffie-Hellman value, where X := NC, NS, CertS, gs, gc, SigS(NC, NS, gs).
  4. S → C : MACK(Y). The server now has the key too. It creates a final MAC over everything, where Y := (X, MAC(X)). This checks correctness of the Diffie-Hellman exchange; receiving it, the client is assured no parameters were tampered with.

First half: negotiation

  • Negotiate the cryptography
  • Declare nonces for freshness
  • Client nonce, then server nonce + certificate
  • Nothing secret yet

Second half: AKE

  • Authentication and key establishment
  • Client verifies server, sends its Diffie-Hellman value
  • Both derive the symmetric key
  • MACs confirm no tampering
🧠
Remember the rhythm: "two messages for negotiation, two for AKE". This pattern is common across cryptographic protocols, so recognising it helps you read new ones.

TLS Building Blocks: Subprotocols, Messages, Extensions

TLS is not one protocol but two layers of protocols, and each subprotocol carries a different kind of message.

TLS is message-based, and its subprotocols define the message exchanges. It uses TCP to provide a reliable end-to-end secure service. Crucially, TLS is two layers of protocols. The Record Protocol provides basic security services to higher-layer protocols, embeds their messages, and maps them onto TCP; HTTP or any application data can run on top.

🤝 Handshake Protocol

Negotiates session details such as cryptographic algorithms and session keys. Its name is the protocol's name, not a category. It lets server and client authenticate each other and negotiate an encryption and MAC algorithm and the keys used to protect data in an SSL record.

🔁 Change Cipher Spec Protocol

Signals transitions in the cryptography in use. It tells the other party the session key has been generated and the connection is switching to encrypted communication. Its messages may appear before or after handshake messages.

🚨 Alert Protocol

Conveys TLS-related alerts, signalling errors or issues during the TLS process to the peer entity.

📨 Application Data

The secured payloads carried over the network.

ℹ️
Structure note: the Change Cipher Spec Protocol is one of the protocols that use the Record Protocol, alongside the Handshake and Alert protocols. The Record Protocol is the base on which the others operate.

Negotiation and extensions

TLS negotiates concrete ciphers, hash functions, and MACs between the parties, as many cryptographic protocols do. The standard contains codepoints for supported mechanisms: the client proposes a suite, and the server selects its preference or rejects the connection if none is suitable. Extensions include Server Name Indication (SNI), which specifies the domain name the connection is intended for and helps identify the protocol being protected, plus Certificate Transparency, which ensures certificates are publicly logged, and indications of the application-layer protocol or unusually strong cryptography.

In the TLS 1.2 flow, the client first establishes security capabilities, including protocol version, session ID, cipher suite, compression method, and initial random numbers. The server may send its certificate and key exchange material, and may request a client certificate, then signals the end of the hello phase. The client sends a certificate if requested, sends its key exchange, and may send certificate verification. The server changes the cipher suite and finishes the handshake, after which the client sends the application payload.

TLS 1.3: Faster, Stronger, With Trade-offs

TLS 1.3 removes every weak option and encrypts sooner, but its optional 0-RTT mode buys speed by giving up replay protection.

TLS 1.2 was already the result of many improvements to TLS 1.0 and 1.1, but it still had weaknesses: relatively old cryptography, MAC-then-encrypt rather than Encrypt-then-MAC, and compression. From about 2008, serious pressure built and a redesign was needed, producing TLS 1.3, standardised in 2018.

The version history matters. TLS 1.0 (1999) and TLS 1.1 (2006) relied on MD5 and SHA-1, were vulnerable to downgrade attacks, and supported weak ciphers such as DES and RC4. TLS 1.2 (2008) added SHA-1/256/384, HMAC-based authentication, flexible cipher suites and RSA, DH, DHE, and ECDHE key exchange, supported secure renegotiation, and offered optional forward secrecy, but is now moving toward deprecation. TLS 1.3 (2018) is actively recommended: it eliminates renegotiation, mandates forward secrecy via ECDHE, permits only ECDHE and PSK key exchange, and completes in one round trip. Session resumption evolved from session IDs in 1.0 and 1.1, to IDs and session tickets in 1.2, to 0-RTT with tickets in 1.3.

The major differences in TLS 1.3

  • TLS 1.2 permitted a null cipher (authentication without encryption); this is no longer allowed.
  • TLS 1.3 mandates AEAD (Authenticated Encryption with Associated Data) ciphers only, such as AES-GCM and ChaCha20-Poly1305, guaranteeing confidentiality and integrity together.
  • Diffie-Hellman is the default key exchange, except for one pre-shared key mode.
  • Encryption begins immediately after ServerHello, so certificates and the Diffie-Hellman values shared in KeyShare are encrypted and integrity-protected.
  • 1-RTT: the client can send application payload after one round-trip, drastically cutting setup time.
  1. ClientHello. Indicates supported cipher suites and guesses the key agreement protocol and parameters.
  2. ServerHello. Chooses the key agreement protocol, parameters, and cipher suite, and returns a signed certificate.
  3. Client finishes and requests. The client checks the certificate, generates the key, and can now make an application request such as an HTTPS GET.

Session resumption and 0-RTT

TLS 1.2 had two session resumption features for one-RTT reconnects: the session identifier, letting the server look up a previous key, and the session ticket, a token the client holds and sends to resume. TLS 1.3 deprecates both in favour of a pre-shared key mode, conceptually similar to a ticket, and signals 0-RTT with the Early Data extension. This is intentional and openly acknowledges the weaknesses.

⚠️
Common trap: 0-RTT is not free speed. The session key is not forward-secure, so if it is compromised an attacker reads all encrypted data, and there is no replay protection, so data can be resent. Use 0-RTT only for idempotent application-layer messages such as HTTP GET, and note it is unknown whether operators implement this correctly.

IPsec: Security at the Network Layer

IPsec protects the IP packet itself, so it can secure traffic that has no security of its own.

IPsec provides security at the network layer across three functional areas: authentication, confidentiality, and key management. Authentication assures that a received packet really came from the party named as source and was not altered in transit. Confidentiality lets nodes encrypt messages to prevent eavesdropping. Key management handles secure key exchange. IPsec embeds its mechanisms as IP payloads, where TLS does the same as TCP payloads, is transparent to end users and applications, and includes a filtering capability so only selected traffic pays the overhead.

The three uncertainties of a plain IP packet

The base packet gives no assurance of data origin, because attackers can perform IP spoofing; no way to verify integrity, so you cannot confirm data was unaltered; and no confidentiality, because IP packets are not encrypted. IPsec's idea is to configure protection for packets between two IP addresses or ranges, and that configuration is done with a policy.

Where IPsec is used

IPsec secures communications across a LAN, across private and public WANs, and across the Internet. It supports secure branch office connectivity over the Internet, secure remote access for users dialling an ISP, extranet and intranet connectivity with partners, and enhanced e-commerce security. The principal feature enabling this is that IPsec can encrypt and/or authenticate all traffic at the IP level, so remote logon, client/server, email, file transfer, and Web access can all be secured.

Services listed by RFC 4301

  • Access control and connectionless integrity
  • Data origin authentication
  • Rejection of replayed packets (partial sequence integrity)
  • Confidentiality (encryption)
  • Limited traffic flow confidentiality
🧠
Memory hook: "Access, Integrity, Origin, Replay, Confidentiality, Flow". Note the two TLS does not give at the IP layer: replay rejection and traffic flow confidentiality.

IPsec Machinery: SAs, Databases, and IKEv2

A security association is the negotiated contract for one direction of traffic, and two databases track those contracts.

IPsec is complex, and some functionality is even duplicated. Its components are the Security Association Database (SAD), the Security Policy Database (SPD), ESP, AH, IKEv2, and two modes (tunnel and transport).

i) Security Association (SA)

A Security Association describes the concrete way incoming and outgoing packets are protected. It is a negotiated outcome based on the Security Policy, and it is a one-way relationship affording security services to the traffic carried on it.

Because an SA is simplex, you need two SAs for bi-directional communication. Since IPsec supports both ESP and AH, a typical configuration needs four SAs: two per party and two per mode. SAs combine in various ways and are stored in the Security Association Database.

Counting SAs
1 direction = 1 SA  ·  bidirectional = 2 SAs  ·  one per party per mode = 4 SAs

ii) Security Policy Database (SPD)

The SPD relates IP traffic to specific SAs, or to no SA when traffic may bypass IPsec. Each entry defines a subset of traffic and points to an SA; in complex environments multiple entries may relate to one SA, or multiple SAs to one entry. Entries are defined by IP and upper-layer protocol field values called selectors, and selectors define the IP flow, filtering outgoing traffic into a particular SA. Outbound processing: compare the packet's selector fields against the SPD to find an entry pointing to zero or more SAs; determine the SA and its Security Parameter Index; then apply AH or ESP as the SA requires.

What an SAD entry stores

Each entry normally holds a Security Parameter Index (SPI), a 32-bit value chosen by the receiver to uniquely identify the SA; a 32-bit sequence number counter generating AH/ESP sequence numbers; a sequence counter overflow flag deciding whether overflow audits and blocks transmission; an anti-replay window; AH information (algorithm, keys, lifetimes); ESP information (encryption and authentication algorithm, keys, initialisation values, lifetimes); the lifetime after which the SA is replaced or terminated; the IPsec protocol mode (tunnel, transport, or wildcard); and the observed path MTU with aging variables. The key management mechanism is coupled to the authentication and privacy mechanisms only by way of the SPI.

v) IKEv2: Internet Key Exchange

IKEv2 provides mutual authentication and key establishment between two parties and negotiates cryptographic parameters such as ciphers and hash functions. It results in four Security Associations, one per party and direction. These are used by AH and/or ESP and stored in the Security Association Database, so the agreed protocols and keys remain available for ongoing and future communication.

ℹ️
Context: IKEv2 is itself an AKE protocol (authentication and key exchange). If that sounds familiar, it is because the second half of the TLS handshake is also authentication and key establishment — the same job at a different layer.

AH, ESP, Tunnel Mode, and VPNs

AH authenticates, ESP encrypts and authenticates, and tunnel mode wraps the whole packet so gateways can build VPNs.

Two protocols provide IPsec's security. The Authentication Header (AH) is an authentication protocol designated by its header, and the Encapsulating Security Payload (ESP) is a combined encryption and authentication protocol designated by its packet format.

iii) Authentication Header (AH)

AH authenticates parts of the IP header and the payload. Only parts, because some header fields change as the packet is forwarded, such as Time-to-Live. The authenticated portions are the "normally immutable" ones: source and destination IP, version, length, and so on.

iv) Encapsulating Security Payload (ESP)

ESP provides confidentiality, data origin authentication, connectionless integrity, an anti-replay service (partial sequence integrity), and limited traffic flow confidentiality. Which services you get depends on the SA options and the implementation's place in the topology. ESP supports many algorithms, including authenticated encryption such as GCM, and can be used stand-alone or with AH. It adds a header after the IP header (and possibly AH header) plus a trailer after the protected data. Its fields are the SPI identifying the SA; the 32-bit monotonically increasing sequence number giving anti-replay; an initialisation value / nonce if the algorithm requires it; the payload / protected data (a transport segment in transport mode, an IP packet in tunnel mode); the 8-bit pad length; the 8-bit next header identifying the payload type; and the variable-length Integrity Check Value computed over the ESP packet minus the authentication data field.

vi) a. Tunnel mode

Tunnel mode is used when gateways (the routers of a network) add IPsec protection for the packets their hosts send. It protects the entire IP packet: after the AH or ESP fields are added, the whole packet plus security fields becomes the payload of a new outer IP packet. The original inner packet travels through a tunnel, and no router along the way can examine the inner IP header. Because the original is encapsulated, the new larger packet may have totally different source and destination addresses, adding security. It is used when one or both ends of an SA are a security gateway such as a firewall or router, and hosts behind firewalls can then communicate securely without implementing IPsec.

vii) b. Transport mode

Transport mode is used when the endpoint of the IP communication is the same principal that adds protection. It protects the normal, non-encapsulated payload, so protection extends to a TCP or UDP segment or an ICMP packet, and it is typically used for end-to-end host-to-host communication. ESP in transport mode encrypts and optionally authenticates the IP payload but not the IP header. AH in transport mode authenticates the payload and selected header portions. Transport mode gives confidentiality to any application that uses it, avoiding per-application encryption, but traffic analysis on the packets remains possible.

DimensionTunnel modeTransport mode
Who adds protectionGateways (routers/firewalls)The endpoint that is also the communication principal
What is protectedThe entire IP packet, inside a new outer IP packetOnly the payload; the IP header is authenticated, not encrypted
Header visibilityRouters cannot examine the inner IP headerThe original IP header is visible

Building a VPN from tunnel mode

Tunnel mode can implement a secure virtual private network: a private network configured within a public network, such as a carrier's network or the Internet, to gain the economies of scale and management facilities of large networks. Gateways are responsible for tunnelling (encapsulating) the traffic. In a typical IPsec VPN scenario, an organisation keeps LANs at dispersed locations; offsite traffic across a private or public WAN uses IPsec protocols in the router or firewall connecting each LAN to the outside world. That device encrypts traffic going into the WAN and decrypts traffic coming back, transparent to the workstations and servers on the LAN. Individual users dialling in can also get secure transmission, but their workstations must implement IPsec themselves.

LAN (plain)→ Gateway encrypts→ Untrusted WAN / Internet→ Gateway decrypts→ Remote LAN (plain)
✅
Do this: to choose a mode, ask where the IPsec endpoints sit. If routers bordering each site add protection, it is tunnel mode and you have a VPN. If the hosts add it end-to-end, it is transport mode.

Key Takeaways

If you remember nothing else, remember these twelve points.

1

Protocols are contracts. A protocol defines the format and order of messages and the actions taken on transmission and receipt. All Internet communication is governed by protocols.

2

The TCP/IP model has four layers: application, transport, network, and network interface. Almost every security decision can be located at one of them.

3

TCP is reliable and connection-oriented with a three-way handshake (SYN, SYN/ACK, ACK); UDP is connectionless and best-effort. Choose by loss tolerance and delay sensitivity.

4

IP is the thin waist. Every Internet device runs it, and the base IPv4 packet gives no origin assurance, no integrity, and no confidentiality.

5

Passive attacks (eavesdropping, traffic analysis) only read; active attacks (replay, masquerade, modification, denial of service) change or fabricate traffic.

6

Security protocols live at every layer: WPA2/WPA3 at the link, IPsec/IKEv2 at the network, TLS/DTLS at the transport, and OAuth/OpenID/DNSSEC at the application layer.

7

OAuth is authorisation by delegated tokens; OpenID is authentication and uses OAuth flows. "Sign in with Google" uses both.

8

TLS is a generic layer 4.5 between TCP and the application, delivering encryption, integrity, and origin authentication while reusing the socket abstraction.

9

The TLS handshake is two messages of negotiation and two for authentication and key establishment, using nonces for freshness, certificates for identity, Diffie-Hellman for keys, and MACs for integrity.

10

TLS 1.3 mandates AEAD ciphers, defaults to ECDHE for forward secrecy, encrypts from ServerHello onward, and completes in 1-RTT. Its optional 0-RTT mode is fast but not forward-secure and has no replay protection.

11

IPsec protects the IP packet, including the TCP header TLS leaves alone, and runs in kernel space. A Security Association is one-way; two are needed for two-way traffic.

12

AH authenticates selected header fields plus payload; ESP adds confidentiality. Tunnel mode wraps the whole packet at gateways and builds VPNs; transport mode protects only the payload end-to-end.

Glossary

Twenty load-bearing terms, filterable by the kind of idea they are.

Protocol
The format and order of messages exchanged between communicating entities, plus the actions taken on transmission or receipt of a message or event.
Nonce
A fresh value sent in a protocol to identify a new session and provide freshness, so old messages cannot be replayed. TLS uses a client and a server nonce.
Forward secrecy
The property that compromising a long-term key does not compromise past session keys. TLS 1.3 makes it mandatory via ECDHE; 0-RTT session keys lack it.
X.509 certificate / PKI
A certificate identifying a party, issued within a Public Key Infrastructure. TLS assumes an X.509 PKI for authenticating parties.
VPN
A private network configured within a public network to gain the scale and management of large networks. Gateways tunnel the traffic, typically with IPsec tunnel mode.
Host / end system
A computing device at the edge of the network where applications run: phones, laptops, servers, IoT devices.
Subnet
A logical subdivision of an IP network. Interfaces in one subnet can physically reach each other without passing through an intervening router.
TCP
Transmission Control Protocol. Connection-oriented and reliable, with a three-way handshake, point-to-point full-duplex service, cumulative ACKs, pipelining, flow control, and congestion control.
UDP
User Datagram Protocol. Connectionless and lightweight, with no handshake, reliability, ordering, or flow and congestion control. Used for streaming, DNS, SNMP, and HTTP/3.
IP
The single network-layer protocol every Internet device must run, defining datagram fields and how hosts and routers act on them. Its components are the IP protocol, routing, and ICMP.
NAT
Network Address Translation. All devices in a local network share one public IPv4 address, with a translation table mapping private addresses and ports to public ones.
IPv6
The successor to IPv4 using 128-bit addresses, a 40-byte fixed header, no header checksum or hop-by-hop fragmentation, a 20-bit flow field, and IPsec as a core requirement.
TLS
Transport Layer Security. A generic security layer (4.5) between TCP and the application providing encryption, integrity, and origin authentication. Current version 1.3.
AEAD cipher
Authenticated Encryption with Associated Data. TLS 1.3 allows only AEAD ciphers such as AES-GCM and ChaCha20-Poly1305, providing confidentiality and integrity together.
IPsec / IKEv2
A set of protocols providing authentication, confidentiality, and key management at the network layer using AH and ESP. IKEv2 is the AKE protocol that establishes security associations.
AH / ESP
Authentication Header authenticates parts of the IP header and payload. Encapsulating Security Payload adds confidentiality and authentication, alone or with AH.
Passive attack
Eavesdropping on or monitoring transmissions to obtain information, either message contents or traffic patterns. Hard to detect because nothing is altered.
Active attack
Modification of the data stream or creation of a false stream, subdivided into replay, masquerade, modification of messages, and denial of service.
Masquerade (impersonation)
When one entity pretends to be another. A captured authentication sequence can be replayed to gain privileges the entity does not own.
Denial of service (DDoS)
Any action reducing the availability or correct functioning of a service. A DDoS attack on a remote server compromises the availability goal.

No terms in this category.

Practice Questions

Answer out loud first, then reveal and check the model answer.

Answer, reveal, then tick "Mastered". Your progress is saved.
Q1

Define a network protocol, and use the human "what's the time?" example to explain format, order, and actions.

Answer: A protocol defines the format and order of messages exchanged between communicating entities, plus the actions taken on transmission or receipt. In the analogy, the format and order are the greeting, the returned greeting, then the request; the action is treating a cordial reply as permission to proceed. The network version is a TCP connection request and response, then the URL request and returned files.
Q2

Contrast passive and active attacks on a network. Why are passive attacks so hard to detect?

Answer: Passive attacks eavesdrop on or monitor transmissions to obtain information: release of message contents and traffic analysis. They are very hard to detect because they never alter data. Active attacks modify the data stream or create a false stream: replay, masquerade, modification of messages, and denial of service.
Q3

List the ways security goals can be compromised in a network, and give one concrete example.

Answer: Masquerade; eavesdropping (a man-in-the-middle capturing packets, including logins over non-HTTPS); loss or modification of information (changing a password request in flight); forgery of information; denial of accountability; sabotage/denial of service (a DDoS attack); and authorisation violation (using a service after account takeover).
Q4

Explain the TCP three-way handshake, then give two differences from UDP and one reason UDP could be the better choice.

Answer: The client sends SYN asking whether the server is open; the server replies SYN/ACK; the client answers ACK, and the first two carry no payload. TCP is reliable and connection-oriented with cumulative ACKs, in-order delivery, and flow and congestion control; UDP is connectionless, best-effort, unordered, and has neither. UDP suits streaming or real-time traffic, which are loss-tolerant and rate-sensitive. HTTP/3 is the first HTTP protocol not to rely on TCP.
Q5

You have 172.16.13.5 with a 255.255.255.128 subnet mask. What class is it, and what are the subnet and broadcast addresses?

Answer: Class B (128–191). The mask splits the class into 172.16.13.0–172.16.13.127 and 172.16.13.128–172.16.13.255. The address is in the first, so the subnet address is 172.16.13.0 and the broadcast is 172.16.13.127.
Q6

A host has address 172.16.45.14/30. Which subnetwork does it belong to, and why?

Answer: 172.16.45.12. It is a class B address; in binary it is 10101100.00010000.00101101.00001110. With 30 network bits the network address becomes 10101100.00010000.00101101.00001100.
Q7

Which cryptographic protocols belong to each of the four layers? Name at least one per layer.

Answer: Link: WPA3 and WPA2 (WPA and WEP are broken). Network: IPsec and IKEv2. Transport: TLS for TCP and DTLS for UDP. Application: OpenID and OAuth, plus DNSSEC for the Domain Name System.
Q8

Distinguish OAuth and OpenID, and name the four actors in an OAuth flow.

Answer: OAuth is a standard for authorisation: users grant another service controlled access to parts of their account, replacing repeated credential entry with tokens, reminiscent of Kerberos tickets. OpenID is a complementary authentication protocol using OAuth flows. The actors are the resource owner, the resource/API server, the client, and the authorisation server.
Q9

State the TLS design goals, and explain why TLS sits at "layer 4.5" rather than in the application layer.

Answer: A generic security layer between TCP and the application, using TCP underneath, reusing the socket abstraction so applications use TLS sockets like TCP sockets, and delivering encryption, integrity, and origin authentication transparently. At the application layer every protocol would need extending, and those protocols were often text-based and already complex; the transport layer deals in bytes, which is simpler.
Q10

Walk through the conceptual TLS handshake for server-only authentication with Diffie-Hellman, naming the role of each message.

Answer: The client sends nonce NC to identify the session. The server sends nonce NS, its certificate, Diffie-Hellman value gs, and a signature over all three. The client authenticates the server via the certificate and signed nonce, derives the symmetric key, and sends gc with a MAC over X. The server returns a final MAC over Y = (X, MAC(X)). The first half negotiates cryptography and declares nonces for freshness; the second half is authentication and key establishment, checked by MACs.
Q11

Name the TLS subprotocols and their jobs, and list the most important Handshake Protocol messages.

Answer: The Record Protocol embeds messages and maps them onto TCP. The Handshake Protocol negotiates algorithms and keys and authenticates the parties. The Change Cipher Spec Protocol signals transitions in the cryptography. The Alert Protocol conveys errors. Application Data is the secured payload. Key messages: ClientHello, ServerHello, ServerCertificate, ServerKeyExchange, ClientKeyExchange, and Finished.
Q12

What were the weaknesses of TLS 1.2, and what are the major differences introduced in TLS 1.3?

Answer: TLS 1.2 used relatively old cryptography, MAC-then-encrypt rather than Encrypt-then-MAC, and compression. TLS 1.3 disallows the null cipher, mandates AEAD ciphers only (AES-GCM, ChaCha20-Poly1305), makes Diffie-Hellman the default except one pre-shared key mode, encrypts immediately after ServerHello so certificates and KeyShare values are protected, and achieves 1-RTT. Renegotiation is eliminated and forward secrecy is mandatory via ECDHE.
