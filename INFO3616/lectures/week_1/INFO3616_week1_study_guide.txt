INFO3616 Week 1 – Study Guide
Introduction to Security Engineering
================================================

OVERVIEW
--------
This week's lecture introduces the foundational concepts of security engineering, distinguishing it from safety and reliability engineering. It presents a framework for analyzing security through policy, mechanisms, assurance, and incentives. The lecture covers core security goals, fundamental design principles, and common attack types, using real-world examples like the Target data breach to illustrate concepts.

------------------------------------------------
SECTION 1: What is Security Engineering?
------------------------------------------------

Security engineering focuses on building systems that produce only expected outputs even when faced with malice (intentional attacks), error, or mischance. Unlike safety engineering (which prevents accidents) or reliability engineering (which prevents failures), security engineering specifically addresses threats from intelligent adversaries who actively try to subvert the system.

Key concept: Security engineering means conceiving, designing, and implementing hardware and software that produces only the expected answers, even when confronted with malice, error, or mischance.

Example: Consider a bank's ATM system. Safety engineering would ensure it doesn't physically harm users. Reliability engineering would ensure it dispenses cash correctly most of the time. Security engineering ensures that even if someone tries to hack it, steal money, or trick it into giving extra cash, it still behaves correctly.

💡 Why it matters: Understanding this distinction helps focus security efforts on defending against intelligent attackers rather than just random failures.

------------------------------------------------
SECTION 2: The Security Engineering Framework
------------------------------------------------

The framework consists of four interconnected components:
- Policy: What we want to achieve (e.g., "Customer data must be stored only within our data centres")
- Mechanisms: The tools we use to enforce policy (e.g., encryption, access controls)
- Assurance: Our confidence in how well mechanisms work (e.g., time to break encryption)
- Incentives: Motivations of both defenders (to maintain security) and attackers (to break it)

Key concept: Policy defines goals; mechanisms implement them; assurance measures effectiveness; incentives explain why attacks happen and what defenses are needed.

Example: For online banking, policy might be "only authorized users can access accounts." Mechanisms include passwords and encryption. Assurance involves estimating how long it would take to crack passwords. Incentives explain why attackers want to steal money and why bank employees might be tempted to misuse access.

💡 Why it matters: This framework helps systematically analyze security problems and solutions rather than applying ad-hoc fixes.

------------------------------------------------
SECTION 3: Core Security Goals
------------------------------------------------

Security goals define what we want to protect and form the basis for security policies:

• Confidentiality: Keeping information secret from unauthorized parties (e.g., encryption)
• Integrity: Ensuring data isn't altered improperly (e.g., cryptographic hashes)
• Authenticity: Verifying the origin of messages/data (often includes integrity and freshness)
• Authorization: Determining what actions a user is allowed to perform
• Accountability: Tracking who did what for audit and non-repudiation
• Non-repudiation: Preventing denial of actions (supported by accountability)
• Deniability: Ability to deny involvement in certain actions (useful for confidential comms)
• Availability: Ensuring systems are accessible when needed (defending against DoS)
• Privacy: Controlling what personal information is shared

Example: When you use an ATM, confidentiality protects your PIN, integrity ensures your withdrawal amount isn't changed, authenticity verifies it's really you, authorization lets you withdraw but not change account settings, accountability logs your transaction, and availability ensures the ATM works when you need it.

💡 Why it matters: These goals help translate business needs into specific security requirements.

------------------------------------------------
SECTION 4: Fundamental Security Design Principles
------------------------------------------------

These principles guide the design of secure systems:

1. Economy of mechanism: Keep designs simple and small (e.g., UNIX's modular design)
2. Fail-safe defaults: Default to no access; require explicit permission
3. Complete mediation: Check every access against access controls
4. Open design: Security should rely on secret keys, not secret algorithms
5. Separation of privilege: Require multiple conditions for access (e.g., password + smart card)
6. Least privilege: Give users only the permissions they need
7. Least common mechanism: Minimize shared functions between users
8. Psychological acceptability: Security shouldn't hinder usability excessively
9. Isolation: Separate public access from critical resources
10. Encapsulation: Restrict data access through controlled interfaces (e.g., stored procedures)
11. Modularity: Develop security functions as reusable modules
12. Layering: Use multiple overlapping defenses (defense in depth)
13. Least astonishment: Systems should behave intuitively

Example: A layered defense for a corporate network might include: user authentication (MFA), role-based access control, regular patching, antivirus software, firewalls, encryption, and security training.

💡 Why it matters: Following these principles helps create systems that are both secure and usable.

------------------------------------------------
SECTION 5: Understanding Attacks
------------------------------------------------

Attacks can be classified as:
- Passive: Eavesdropping to learn information (e.g., traffic analysis, message interception)
- Active: Modifying data or creating false streams (e.g., replay, masquerade, message modification, denial of service)

Key concepts:
- Attack vector: Specific method to gain access (e.g., phishing, malware, person-in-the-middle)
- Attack surface: All vulnerabilities that could be exploited (network, software, human)
- Attack tree: Hierarchical diagram showing how attackers could achieve a goal

Example attack tree for internet banking:
Goal: Compromise user account
├── User credential compromise
│   ├── User surveillance
│   ├── Theft of token and notes
│   └── Malware installation
└── ... (other branches)

Who is the opponent? Includes criminals (financial gain), insiders, state actors, hacktivists, and increasingly AI-powered attackers.

💡 Why it matters: Understanding attacks helps design effective defenses by thinking like an attacker.

------------------------------------------------
SECTION 6: Applying the Framework - Bank Security Example
------------------------------------------------

Policy: Maintain correct account balances; protect ATM and online banking integrity/confidentiality/availability.

Mechanisms: Strong bookkeeping, access control, anomaly detection, four-eyes principle for large transfers, strong cryptography for ATMs.

Assurance: Confidence in mechanisms; biggest threat often insiders; anomaly detection difficult because unusual activity can be legitimate.

Incentives: Attackers want money without detection; employees might misuse access for personal gain.

Case Study - 2013 Target Breach:
- Policy failure: Allowed HVAC vendor network access without proper security checks
- Mechanism failure: Detection tools worked but response was inadequate
- Assurance issues: Over-reliance on single sign-on without least privilege
- Incentives: Target was lucrative during holiday season; poor response to alerts

💡 Why it matters: Shows how all framework components must work together; technical controls fail without proper processes and incentives.

------------------------------------------------
SECTION 7: Security as a Process
------------------------------------------------

Security is not a product you buy and forget; it's an ongoing process because:
- All products have flaws
- Human factors (users, admins, insiders) introduce variability
- Environments change (new technologies, business values)
- Attacker incentives evolve with circumstances
- Systems are complex and interconnected

Example: A firewall is useless if not properly configured, monitored, and updated as threats change.

💡 Why it matters: Effective security requires continuous effort, not just one-time solutions.

================================================
KEY TAKEAWAYS
================================================

• Security engineering defends against intelligent attackers, not just random failures
• The security framework has four components: policy, mechanisms, assurance, incentives
• Security goals include confidentiality, integrity, authenticity, authorization, accountability, and availability
• Fundamental design principles like least privilege and defense in depth create secure systems
• Attacks can be passive (eavesdropping) or active (modifying data)
• Real-world breaches like Target show failures across all framework components
• Security requires ongoing process thinking, not just one-time product implementation
• Understanding attacker motivations is crucial for effective defense prioritization
• Simplicity and usability are key to effective security through principles like psychological acceptability
• Defense in depth uses multiple layers so failure of one doesn't compromise the whole system
