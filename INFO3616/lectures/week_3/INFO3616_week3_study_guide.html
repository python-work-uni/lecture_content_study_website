Access Control

This lecture covers the foundational concepts of access control in cybersecurity — how systems decide who (or what) can access which…

Lecture Overview: This lecture covers the foundational concepts of access control in cybersecurity — how systems decide who (or what) can access which resources. You'll learn the difference between authentication, authorization, and access control; the two main paradigms (DAC vs MAC); how operating systems (Linux, Windows, macOS, iOS, Android) implement permissions; middleware and database access control; sandboxing and virtualization; hardware-level protections (memory, CPU rings, TPM); and the two classic security policy models: Bell-LaPadula (confidentiality) and Biba (integrity). This is core material for understanding how real systems enforce security boundaries.
01

Core Concepts & Terminology

Access Control vs Authentication vs Authorization

  • Access Control: The overall mechanism that determines which principals (users, processes, groups) can access which resources (files, programs, data). It's the policy enforcement layer.
  • Authentication: Proving identity — "Who are you?" (passwords, fingerprints, certificates).
  • Authorization: Granting privileges — "What are you allowed to do?" (permissions, roles).
💡
Why it matters: These three terms are often confused. In exams, you'll be asked to distinguish them or identify which layer a given mechanism operates at. Access Control Matrix (Naive Model) A table where rows = subjects (users), columns = objects (files), cells = permissions (r/w/x/-). Example from notes:
  • Sam (admin): rwx on OS, rwx on Accounts, rw on Data, r on Audit Trail
  • Alice (manager): x on OS, x on Accounts, rw on Data, - on Audit Trail
  • Bob (auditor): rx on OS, r on Accounts, r on Data, r on Audit Trail

Key insight: The matrix is conceptually simple but doesn't scale — too many entries to manage manually.

DAC vs MAC — The Two Paradigms

Discretionary Access Control (DAC)

  • Resource owners decide who gets access.
  • Flexible, user-controlled.
  • Example: OneDrive personal — you share a file with specific people or create a public link.
  • Risk: Users can accidentally (or maliciously) over-share. No central enforcement.

Mandatory Access Control (MAC)

  • Central authority (security admin) defines policy based on security labels (classifications).
  • Users CANNOT change permissions — even the file owner.
  • Example: OneDrive enterprise — admins restrict sharing to @company.com domains; DLP blocks sensitive data.
  • High rigour, used in military/government (Top Secret, Secret, Confidential).
💡
Memory aid: DAC = "Discretion = Your Decision" — owner decides. MAC = "Mandatory = Admin Commands" — central policy decides. OneDrive Comparison (from notes)

Operating System Access Control

3.1 Access Control Lists (ACLs)

  • Each object has a list: (subject, permissions).
  • Used in UNIX (POSIX — Portable Operating System Interface), Windows, social networks, CMS (Content Management System), ERP (Enterprise Resource Planning) systems.
  • Can be coarse (r/w/x) or fine-grained (specific operations).

3.2 Unix/Linux Permissions — The Core Model Every file/directory has:

  • Owner UID (User Identifier) — user who owns it
  • Group GID (Group Identifier) — group associated with it
  • Permission bits (3 sets × 3 bits = 9 bits):
    • Owner: r/w/x
    • Group: r/w/x
    • Others: r/w/x

Symbolic notation: -rw-r--r-- = owner rw, group r, others r Octal notation: 755 = rwx (7) + r-x (5) + r-x (5) Special bits (beyond the basic 9):

  • SUID (Set User ID): Program runs with file owner's privileges, not runner's. Example: mount command.
  • SGID (Set Group ID): On file = runs with file's group; on directory = new files inherit directory's group.
  • Sticky bit: On directory = only file owner (or root) can delete files inside. Example: /tmp.

Process Identity (3 UIDs/GIDs):

  • Real UID/GID: Who launched the process.
  • Effective UID/GID (eUID/eGID — effective User/Group Identifier): What permissions the process currently has (changed by SUID/SGID).
  • Saved UID/GID: Stored original UID/GID so process can drop privileges temporarily and regain them.

Root (UID 0): All-powerful. sudo lets permitted users run commands as root (requires sudo group membership + password).

💡
Worked Example: File -rwsr-xr-x 1 root root 40K /usr/bin/passwd
  • Owner root, SUID bit set (s in owner execute position).
  • When Alice runs passwd, it executes with root's privileges so it can modify /etc/shadow (which only root can write).
💡
Memory aid for permission bits: R-W-X = Read-Write-eXecute. Octal: r=4, w=2, x=1. So rwx=7, rw=6, rx=5, r=4. 3.3 macOS
  • Based on FreeBSD (Unix) — similar permission model.
  • Adds: File attributes, ACLs, Keychain (passwords + some ACLs), Kerberos network auth.
  • Since 10.5 (Leopard): TrustedBSD = MAC mechanisms protecting core system from malware.
  • Root disabled by default; admin users in "wheel" group can su to root.

3.4 Windows

  • More complex than Unix: ~15-16 permission types (not just RWX).

Examples: Traverse Folder/Execute File, List Folder/Read Data, Read Attributes, Write Attributes, etc.

  • Enforced by Security Reference Monitor (SRM) — trusted kernel component.
  • Complexity risk: Hard to configure correctly; secure defaults can still be misconfigured.

3.5 iOS

  • Unix-based, heavy sandboxing.
  • Apps run in separate sandboxes — cannot access other apps' files.
  • Permissions = capabilities requested at runtime (camera, SMS (Short Message Service), location, etc.).
  • Sensor values read-only (Biba model — integrity protection).
  • Hardware support: signed software, encryption, OS (Operating System) read-only to apps.

3.6 Android

  • Linux-based; each app runs under different UID.
  • Permissions = capabilities (SMS, camera, contacts).
  • Storage issue: "Public storage" world-readable/writable — developers misuse it.
  • Apps in signed .apk packages (self-signed certs = developer identity).
  • Android 6+ moved to "trust on first use" (like iOS) — dangerous permissions requested at runtime.
  • Google Play screens for malware but less strict than Apple App Store.
💡
Key comparison: iOS = stricter sandbox, OS read-only, mandatory code signing by Apple. Android = more permissive, self-signed certs, public storage risk.

Middleware Access Control

Middleware = message brokers (AMQP — Advanced Message Queuing Protocol), RPCs (Java RMI — Remote Method Invocation, CORBA — Common Object Request Broker Architecture, XML-RPC), often distributed. Challenges:

  • Exposed to external probing.
  • High complexity: define granularity, track/enforce permissions, easy to misconfigure.
  • Policy languages exist but are hard to use.
  • Mitigation: Protect from external access (firewall), but internal malware can still exploit.

4.1 Database Access Control

  • DBMS (Database Management System) has own access control (users, roles, GRANT/REVOKE).
  • Data still lives on disk/RAM → OS protections still needed.
  • Map OS users → DB roles (role-based access control).
  • SQL (Structured Query Language) standard: fine-grained control on any object → can become over-complex.
  • Integrity controls exist but computationally heavy to verify.

4.2 Browsers

  • Main rule: Same-Origin Policy — JS (JavaScript) can only talk to its originating IP/domain.
  • Code runs in sandbox (prevents host system alteration).
  • Chrome: each tab = separate OS process (isolation).

Confused Deputy Problem (important!)

  • A privileged component (deputy) is tricked by less-privileged attacker into misusing its authority.
  • Browser example: XSS (Cross-Site Scripting) — malicious script injected into trusted site runs with that site's permissions, can send authenticated requests, access cookies.
  • CSRF (Cross-Site Request Forgery) = classic confused deputy.
💡
Memory aid: Deputy = privileged component. Confused = tricked into acting for attacker. "Deputy does the dirty work."
05

Other Access Control Mechanisms

5.1 Sandboxing

  • Shielded environment with limited API.
  • Examples: Java applets (historical), JavaScript in browser, Chrome tabs as separate processes.
  • Challenge: Sandboxes can be "broken out of" — isolation not guaranteed.

5.2 Virtualization

  • VMs (Virtual Machines) emulate full computer systems (since 1960s IBM VM/370).
  • Types:
    • Full virtualization: Complete hardware emulation (even cross-architecture).
    • Para-virtualization: Guest OS modified to cooperate with hypervisor.
    • Containers/Jails: Lightweight — share host kernel, isolate userspace.
  • Hypervisor manages VMs (Ring -1 hardware support). Examples: VirtualBox, VMware, Xen, QEMU.
  • Not designed for access control, but breaking out is hard → raises attacker bar.
  • Caveats: VM detectable (malware behaves differently), hypervisor vulnerabilities exist.

5.3 Docker (Container Example)

  • Originally for CI/CD (Continuous Integration/Continuous Deployment).
  • Images = app + libraries; fast spin-up; Kubernetes (container orchestration platform) for orchestration.
  • Sandboxes apps: no direct inter-container communication.
  • Risk: Docker daemon runs as root — any user who can start/stop containers talks to daemon → attack surface.
  • Still provides extra separation layer.
💡
Worked Example: Docker daemon root issue. If user "alice" is in docker group, she can run docker run -v /:/host ubuntu chroot /host → full host root access.
06

Hardware Access Control

6.1 Memory Protection

  • CPUs use segment addressing: segment register + offset register.
  • Process accesses outside its segment → Segmentation Fault (SIGSEGV).
  • Protects both read and write.

6.2 Privileged Execution / CPU Rings

  • CPUs have hierarchical privilege rings.
  • Principle of Least Privilege: Code runs with minimum required privilege.
  • Kernel communication paths minimized and controlled.

Intel x86 Rings (Modern):

  • Ring 3: Applications (least privilege)
  • Ring 0: OS Kernel
  • Ring 0 (VMX root): Hypervisor/VMM (Virtual Machine Monitor)
  • SMM (System Management Mode): BIOS/firmware (highest)
  • Total: 9 rings (0-3 normal, 0-3 VMM root, SMM)

ARM Processors:

  • Dominant in phones, tablets, IoT (Internet of Things).
  • Licensable cores → customizable hardware protection.
  • MMU (Memory Management Unit) for virtual memory.
  • MPU (Memory Protection Unit) for simpler embedded.
  • CHERI (Capability Hardware Enhanced RISC Instructions): Fine-grained memory capabilities — can give sub-thread specific memory ranges. Potential to stop most zero-day exploits if adopted widely.

6.3 Isolated Cryptographic Components

  • Keys stored in hardware, accessed via dedicated interface.
  • Example: Intel TPM (Trusted Platform Module) — originally for DRM (Digital Rights Management), now general secure crypto storage.
💡
Memory aid: Rings = Russian dolls. Ring 3 inside Ring 0 inside VMM root inside SMM. Higher number = less privilege.
07

Security Policy Models

These are formal models specifying protection properties. Used to drive engineering. 7.1 Bell-LaPadula Model (1973) — Confidentiality Focus Goal: Prevent information flowing DOWN (from high classification to low). Two mandatory properties:

  1. Simple Security Property (No Read Up): Subject cannot read object at higher classification.
  2. **\*-Property / Star Property (No Write Down)**: Subject cannot write to object at lower classification.
  3. Discretionary Access Control: External entity defines access matrix (DAC component).

Implicit allowances:

  • Can read at own level OR DOWN.
  • Can write at own level OR UP.
💡
Why \*-property matters: Prevents "Trojan horse" where low user writes malicious program, waits for high user to run it, program exfiltrates secrets by writing down. Criticisms:
  • Single omnipotent "Trusted Principal" admin — who watches the watcher?
  • Confidentiality only — no integrity protection.
  • Ignores covert channels (e.g., CPU load signaling bits).
  • Composition fails: Two BLP (Bell-LaPadula) secure systems combined ≠ BLP-secure.

7.2 Biba Model — Integrity Focus Goal: Prevent malicious modification (corruption) of data. Reverse of BLP. Three properties:

  1. Simple Integrity (No Read Down): Subject may only read at own level or HIGHER.
  2. **\*-Integrity (No Write Up)**: Subject may only write at own level or LOWER.
  3. Invocation Property: Process cannot invoke higher-integrity process.

Examples:

  • In-flight entertainment reads avionics (airspeed) but CANNOT alter flight controls.
  • Odometer displays mileage but CANNOT change it.

7.3 Practical Example (from notes) Users: Bart (None), Homer (Low), Lisa (Medium), Marge (Ultimate) Objects: fridgecodes.txt (Ultimate), tvlockcodes.txt (Medium), playstationcodes.txt (Low)

QuestionBLP AnswerBiba Answer
Can Homer read TV codes?No (No read up)Yes (Read up allowed)
Can Marge help Homer get TV codes?No (No write down)Yes (Write down allowed)
Can Bart change all codes?Yes (Write up allowed!)No (No write up)
💡
Key insight: BLP allows low-integrity users to corrupt high-integrity data (Bart writes up). Biba prevents this but allows low-confidentiality reads. 7.4 Real-World Usage
  • Pure BLP/Biba rare — too rigid.
  • Biba variants common: Windows Vista, SELinux (Security-Enhanced Linux), some Red Hat, FreeBSD module.
  • Concepts used to discuss/design real access control in mobile, desktop, server OS.
💡
Memory aid: BLP = "Better Lock Papers" (Confidentiality — lock secrets UP). Biba = "Bad Integrity Blocks Alteration" (Integrity — block writes UP). Or: BLP = No Read Up, No Write Down. Biba = No Read Down, No Write Up. (Opposites!)

Practice Quiz Insights (Exam Prep)

The notes include 10 practice questions. Key patterns:

  1. Bell-LaPadula property identification: "No read up" = simple security; "No write down" = \*-property.
  2. Covert vs Side channels: Covert = using non-communication method (steganography). Side = inferring from artifacts (timing, heat, power).
  3. Model focus: BLP = confidentiality; Biba = integrity. They don't overlap.
  4. Linux permissions: r/w/x only. -rwxrwxrwx = everyone can do everything (dangerous!).
  5. BLP scenario questions: Given clearances/classifications, apply "no read up, no write down".
  6. DAC identification: If creator defines per-user access, it's DAC.
  7. Mobile sandboxing features: Each app = separate UID; controlled API comms; OS read-only; NOT full storage access.
  8. Docker for access control: TRUE — containers sandbox apps, raise attack bar.
  9. Confused Deputy in browsers: TRUE — scripting, add-ons, cookies vulnerable; CSRF is example.

QUANTITATIVE DETAILS & SPECIFICS

  • Unix permission bits: 9 basic + 3 special = 12 bits per file.
  • Windows permissions: ~15-16 distinct types (vs Unix's 3).
  • Intel modern CPUs: 9 rings total (0-3 normal, 0-3 VMM root, SMM).
  • BLP/Biba clearance levels in example: 4 levels (Top Secret, Secret, Confidential, Unclassified).
  • Practice quiz: 10 questions covering all major topics.
  • OneDrive DAC sharing options: Private, Specific People, Anyone with Link, Public.
  • OneDrive MAC controls: Domain restrictions, DLP (Data Loss Prevention) policies.
  • Android storage types: App-internal (private) vs Public (world-readable/writable).
  • Android permission model change: Pre-6.0 = install-time all-or-nothing; 6.0+ = runtime "trust on first use".

Terms to Know (Glossary)

Access Control Pipeline
Mechanism controlling which principals can access which resources.
Authentication Pipeline
Process of verifying identity (proving who you are).
Authorization Pipeline
Process of granting privileges (deciding what you can do).
Principal Pipeline
Active entity requesting access (user, process, group).
Object Pipeline
Passive resource being protected (file, program, data, port).
DAC (Discretionary Access Control) Pipeline
Owner-controlled access; users can delegate.
MAC (Mandatory Access Control) Pipeline
Central policy-controlled access; users cannot change.
ACL (Access Control List) Pipeline
Per-object list of (subject, permissions) entries.
UID/GID Pipeline
User ID / Group ID — numeric identifiers in Unix/Linux.
SUID (Set User ID) Pipeline
Bit allowing program to run with file owner's privileges.
SGID (Set Group ID) Pipeline
Bit for group-based privilege escalation or directory group inheritance.
Sticky Bit Pipeline
Directory bit restricting deletion to file owner (e.g., /tmp).
eUID/eGID Pipeline
Effective UID/GID — current runtime privileges of a process.
Same-Origin Policy Pipeline
Browser rule — scripts only talk to their originating domain.
Confused Deputy Problem Pipeline
Privileged component tricked into misusing authority for attacker.
Sandboxing Pipeline
Isolated execution environment with limited API.
Virtualization Pipeline
Emulating hardware to run guest OS; hypervisor manages VMs.
Container Pipeline
Lightweight virtualization sharing host kernel (Docker).
CPU Rings Pipeline
Hierarchical privilege levels (Ring 3=apps, Ring 0=kernel, etc.).
TPM (Trusted Platform Module) Pipeline
Hardware secure cryptographic key storage.
Bell-LaPadula Model Model
Confidentiality model — no read up, no write down.
Biba Model Model
Integrity model — no read down, no write up.
\*-Property (Star Property) Pipeline
BLP rule — no write down; prevents Trojan horse exfiltration.
Simple Security Property Pipeline
BLP rule — no read up.
Invocation Property Pipeline
Biba rule — process cannot invoke higher-integrity process.
Covert Channel Pipeline
Information flow via non-communication method (e.g., steganography).
Side Channel Trap
Information leakage via physical artifacts (timing, power, heat).
CHERI Pipeline
ARM capability hardware for fine-grained memory safety.
