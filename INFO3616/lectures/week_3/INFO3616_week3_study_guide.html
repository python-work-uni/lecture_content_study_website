Access Control: Who Gets In, and Why the System Says No

Every computer system has to answer one blunt question over and over: is this principal allowed to do this thing to this resource? This week shows you how that decision is made — from the tiny permission bits on a Unix file, through databases, browsers, sandboxes and virtual machines, all the way down to the privilege rings built into the CPU — and finishes with the formal policy models (Bell-LaPadula and Biba) that security architects use to reason about it.

Read this first: hold onto one mental model — access control is a layered gatekeeper. Authentication proves who you are, authorisation decides what you may do, and mechanisms (passwords, ACLs, permission bits, rings) enforce that decision at every layer of the stack. The same idea wears different clothes at each layer, but it is always the same idea.
~32 min read 16 teaching sections 12 practice questions 30 key terms

By the end you will be able to

  • Define access control, authentication and authorisation, and explain how they differ.
  • Place access control inside the policy → incentives → mechanisms → assurances framework, and read a simple access control matrix.
  • Contrast Discretionary Access Control (DAC) with Mandatory Access Control (MAC) and give a real example of each.
  • Read a Unix permission string such as -rwxr-xr-x, and explain UID, GID, root, sudo and the special SUID, SGID and sticky bits.
  • Describe how macOS, Windows, iOS and Android each implement access control, and how they differ.
  • Explain middleware, database and browser access control, including the same-origin policy and the confused deputy problem.
  • Explain sandboxing, virtualisation and containers, and why they raise the bar for attackers.
  • Describe hardware protections: memory segmentation, privilege rings, the principle of least privilege, TPMs, Intel rings and ARM's CHERI.
  • State the rules of the Bell-LaPadula and Biba models, apply them to a clearance table, and list their strengths and weaknesses.

Access Control, Authentication and Authorization

Three words that are constantly confused. Get them straight now and the rest of the week falls into place.

Access control is an important element of a security policy. Its aim is to control access to resources and assets: which principals (users, user groups, processes, machines and so on) may reach which resources, which files they can read, which programs they can execute, and how they share data with one another.

Concrete questions that access control answers:

  • Can a customer of a bank access the bank vault?
  • Can a program access the passwords of other users?

Notice how broad that is. Access control is not only about people; it is equally about programs acting on behalf of people. That is why the neutral word principal is used — a principal is any entity that can be granted or denied access.

Authentication vs authorisation

Authentication

The process of acquiring evidence of the identity of another party. It answers: who are you? Passwords, fingerprints and security protocols are authentication mechanisms.

Authorization

The process of verifying whether an entity is allowed an action — or, in the notes' wording, the allocation of a privilege to a party. It answers: what may you do?

ℹ️
Order matters: authentication normally comes first. You cannot sensibly decide what someone is allowed to do until you know who they are. This is why an operating system authenticates a principal with a password or fingerprint before it authorises access to files and ports.
A · A
"Authentication asks who; Authorisation asks what"
Authentication = identity (evidence). Authorisation = permission (privilege). Access control is the whole system that enforces the answer.
🤔
Pause & predict: You type your password to log in to a laptop. Is that authentication, authorisation, or both? (Answer: typing the password is authentication; the rules that then let you open some files and not others are authorisation.)

The Reference Framework and the Access Control Matrix

Access control is not a standalone gadget — it sits in a cycle of policy, incentives, mechanisms and assurance.

The course uses a small reference framework to place every security topic. Access control fits into it like this:

  • Access control is specified in the policy — the policy says who may do what.
  • It counters the incentives of the attacker, who wants to access a resource or asset.
  • It is implemented by one or more mechanisms — for example, passwords.
  • Those mechanisms give us a certain level of assurance — how much we can trust that the control actually holds.
Policy→ Incentives (attacker)→ Mechanisms→ Assurance

A password is the textbook example: the password is the mechanism, and the strength of the password relates directly to the assurance it provides. A four-character password gives weak assurance; a long passphrase with a second factor gives strong assurance.

Modelling access as a matrix

Access controls are often modelled as a matrix of access permissions: columns are objects (such as files), rows are users, and each cell says what that user may do to that object. The convention is r for read, w for write, x for execute, and - for no access at all.

UserOperating SystemAccounts ProgramAccounting DataAudit Trail
Sam (system administrator)rwxrwxrwr
Alice (manager)xxrw-
Bob (auditor)rxrrr

Read the story the matrix tells:

  • Sam is the administrator and has universal access — except the audit trail, which even he should only be able to read, never alter.
  • Alice needs to execute the operating system and applications, but only through the approved interfaces — she must not be able to tamper with them, so she has x but no w. She does need to read and write the data.
  • Bob the auditor can read everything (read plus execute on the OS, read on the rest).
💡
Why the matrix matters: it is the simplest mental picture of access control and it reappears all week. An ACL is essentially one column of the matrix; a capability is essentially one row. When you meet a new mechanism, ask: is this storing columns (objects) or rows (subjects)?
🤔
Pause & predict: Why should even the all-powerful Sam only read the audit trail? (Answer: if administrators could rewrite the audit trail, they could erase evidence of their own misuse — so the trail is deliberately read-only for everyone.)

Discretionary vs Mandatory Access Control

The single most examinable contrast of the week: who gets to decide access — the owner, or a central authority?

Access control always involves two kinds of thing:

  • Objects — the things being protected: files, processes, records and so on.
  • Subjects — the things that act on objects: people, groups, processes and so on. (Objects are owned by subjects.)

The spectrum of access control runs from complete owner freedom to complete central control.

Discretionary Access Control (DAC)

  • Access is controlled by the resource owner.
  • Access to an object is based on the identity of the owning subject.
  • Users can grant or revoke permissions to others at their discretion, and can pass on a privilege over their object — unless constraints exist (such as those imposed by MAC).
  • Gives a high level of flexibility and control to subjects.

Mandatory Access Control (MAC)

  • Access is enforced by a central authority based on security labels (such as classification levels).
  • An external entity (a security policy administrator) defines access.
  • A security kernel checks, via security attributes, whether a subject is allowed to interact with an object.
  • Users cannot change permissions themselves; gives a high level of rigour.

Where DAC and MAC came from

In the early days of computing, anyone with physical access to a computer controlled all of it: you could load any software, inspect everything in memory or on disk, and change anything. This is the model behind DAC — you start the machine in supervisor mode and, as administrator, you create less-privileged accounts for less-trusted tasks, such as running apps from companies you do not fully trust or giving others remote logon access.

DAC, however, is hard to manage at scale. In the 1970s the US military launched a large computer-security research program to protect classified information: a file marked Top Secret must never become available to a user with only Secret clearance — regardless of what any ordinary user, or even the supervisor, does. In such a multilevel secure (MLS) system, the sysadmin is no longer the boss: ultimate control rests with a remote government authority that sets the policy. The supervisor, or root access, is under remote control. Mechanisms of this kind became known as Mandatory Access Control.

ℹ️
Microsoft OneDrive — a familiar example. In personal use, OneDrive is DAC: the creator of a file or folder is the owner, ownership can be transferred, and the owner shares with Specific People, via Anyone with the Link, or Public, at permission levels View or Edit. In an enterprise, OneDrive adds MAC elements: Microsoft 365 admins set sharing and access policies (for example restricting sharing to specific domains), and Data Loss Prevention (DLP) automatically protects sensitive information by restricting access according to central policy. So OneDrive is primarily DAC for personal use, with MAC elements in enterprise settings.
D · M
"DAC = Do As you Choose; MAC = Mandated by Authority"
Discretionary: the owner decides. Mandatory: a central authority decides, enforced by the security kernel via labels.
🤔
Pause & predict: Your company's IT team blocks you from emailing a spreadsheet outside the organisation, and you cannot override it. Is that DAC or MAC? (Answer: MAC — a central policy, not your discretion, decides.)

Access Control Lists (ACLs)

One column of the access matrix, attached directly to the object it protects.

ACLs define the access of subjects to objects. Each object is associated with an access control list. An ACL entry consists of a user ID plus a mapping to allowed operations. Key properties:

  • An ACL can be defined globally (one list for many objects) or be much more fine-grained (a list per object).
  • Operations can be coarse — the familiar read/write/execute — or very fine-grained.
  • ACLs are a widespread mechanism: common in all UNIX systems (per the POSIX standards) and also present in Windows.
  • They are found beyond operating systems too: on social networking sites, in content management and enterprise resource management systems, and elsewhere.

Here is a tiny ACL for a single object, the accounting data:

UserAccounting Data
Samrw
Alicerw
Bobr

Compare this with the full matrix from earlier: the ACL is just the Accounting Data column lifted out and stored with the object. That is the essential idea — the permissions live with the thing being protected, not in a central table.

✅
Coarse or fine? Coarse operations (read/write/execute) are simple and fast to check. Fine-grained operations give precise control but are harder to manage. Choosing the right granularity is a recurring theme: too coarse and you cannot express the policy; too fine and the system becomes impossible to administer.

Unix/Linux: Users, Groups and Root

Before you can read permissions, you need to know who the players are.

Each Unix/Linux user has a User ID (UID) and a Group ID (GID). A user can also belong to additional groups — for example the sudo group, which carries the right to run commands as the superuser.

Where users and groups are stored

The file /etc/passwd holds user accounts. A sample entry is:

A /etc/passwd entry
sam:x:1000:1000:Sam Jones,,,:/home/sam:/usr/bin/zsh

Reading left to right: the username, a placeholder for the password, the UID (1000), the GID (1000), the full name, the home directory, and the login shell (/usr/bin/zsh).

The file /etc/group holds groups. A sample entry is:

A /etc/group entry
sudo:x:27:sam,pnappa

That is: the group name (sudo), a password placeholder, the GID (27), and the list of users in the group.

Root: the all-powerful user

Root has UID and GID of 0. Root can do what it likes — access any file, become any user — and certain actions only root can perform, such as starting particular communication processes. Root is normally the account made available to the system administrator on a system with discretionary access control.

  • The sudo command lets you run a command as root.
  • It works only if the invoking user is part of the sudo group, and it usually requires a password.
  • Non-sudo users can still run some commands with sudo if this is explicitly permitted in the sudoers file.
⚠️
Common trap: root is not a normal user with extra rights — it is effectively unrestricted. That is exactly why the principle of least privilege (coming later) says code should run with only the minimum privilege it needs, never as root unless unavoidable.

Unix/Linux: File Permissions

Nine bits, three audiences. Once you can read them, you can read any Unix system at a glance.

The Linux/Unix permission model is hierarchical and gives each file and directory three permission types — read (r), write (w) and execute (x) — assigned to three categories of user:

  1. Owner R/W/X — three bits saying what the file's owner can do. Bit R set means read, W means write, X means execute.
  2. Group R/W/X — three bits saying what members of the file's group can do.
  3. Other R/W/X — three bits saying what everyone else can do.

Each file records an Owner ID (the user that owns the file) and a Group ID (the group that 'relates to' the file).

ℹ️
Execute on a directory means traverse. Directories that have the X bit set can be traversed — you can pass through them to reach files inside. This is why a directory often shows x where you might not expect it.

Reading the permission string

Permissions are shown in a symbolic notation, for example rwxr-xr-x, or an octal notation, for example 755. They can be changed with commands such as chmod, chown and chgrp.

Take a real listing:

Example listing
-rw-r--r-- 1 sam sam 24K Jun 12 10:20 email.png

The leading - means this is a regular file. The next nine characters are the permissions in three blocks of three:

BlockValueMeaning
Ownerrw-Can read and write, cannot execute.
Groupr--Can read only.
Otherr--Can read only.

So in this example the owner, group and others can all read the file, but only the owner (sam) can write to it.

🤔
Pause & predict: A file shows rwxrwxrwx. Can the owner, the group and everyone else all read, write and execute it? (Answer: yes — all nine bits are set. This is normally far too permissive and dangerous.)

Unix/Linux: Special Bits and Process Identity

Three extra bits that change who a program runs as — and the three IDs that let the kernel track it.

The three special bits

🔑 Set-user-ID (SUID)

The owner of a program can mark the file as suid, enabling it to run with the privilege of its owner rather than the privilege of the user who invoked it. Useful for running specific programs with extra permissions without being a privileged user. The mount command is an example.

👥 Set-group-ID (SGID)

On a file, it behaves like SUID but with the group: the file executes with the privilege of the group that owns it. On a directory, any files created inside inherit the group ownership of the directory.

📌 Sticky bit

Does not affect individual files. At the directory level it restricts deletion: only the owner (and root) of a file can remove that file from the directory. The classic example is /tmp.

Processes inherit permissions

A process in Unix/Linux inherits permissions from the user who runs it, tracked through three pairs of IDs:

ID pairWhat it means
Real UID / GIDThe actual user and group that initiated the process — who owns it.
Effective UID / GID (eUID / eGID)Determines the permissions the process actually runs with. SUID and SGID affect this: the process may run with the file owner's or group's privileges rather than the launcher's.
Saved UID / GIDUsed by the kernel so the process can revert to its original identity after temporarily assuming different privileges.
💡
Why three IDs? Real identity, effective identity and a saved copy give a program a safe way to borrow extra privilege for a moment (say, to open a protected file), then drop back to normal. Without the saved ID, the kernel would have no record of what to switch back to.
⚠️
Common trap: SUID programs are a classic attack surface. If an SUID program can be tricked into doing the wrong thing, it does that wrong thing as its privileged owner. This links directly to the confused deputy problem later this week.

Other Operating Systems: macOS, Windows, iOS and Android

Same idea, four very different implementations — and the mobile ones show where access control is heading.

macOS

  • macOS is a fork of BSD (Unix), so it has similar permissions.
  • The BSD layer provides memory protection: applications cannot access system memory, or each other's memory, unless running with advanced permissions. This is why you can 'Force Quit' a wedged application without rebooting the whole system.
  • At the file-system level it is almost standard Unix: files have attributes and ACLs.
  • It also has the Keychain, which stores extra passwords and some ACLs, and built-in network authentication such as Kerberos.
  • The default install has the root account disabled, but admin users are in a group called wheel that allows them to su to root. Installing programs asks for the root password.
  • Since version 10.5 (Leopard), macOS has been based on TrustedBSD, a BSD variant that incorporates mandatory access control, used to protect core system components against tampering by malware.

Windows

  • Very powerful and complex. It shares similarities with Unix, but instead of RWX it features a much larger set of permissions — the notes say 13 kinds, the slides quote 15–16 attributes. Examples include Traverse Folder / Execute File, List Folder / Read Data and Read Attributes.
  • That intricacy can lead to errors despite secure default settings.
  • Enforcement is via the Security Reference Monitor (SRM), a trusted component that provides fine-grained security.

Apple iOS

  • Based on Unix. Apps have many user permissions, often for privacy: they request a capability to access device services such as the mobile network, phone, SMSes and camera the first time they attempt to use them, and this is granted only if the user consents.
  • Those many device services open up possible side-channel attacks — for example, an app denied access to the keyboard could still deduce keypresses using the accelerometer and gyro.
  • Sensor values are read-only, reflecting principles similar to the Biba model (you will meet Biba later this week).
  • Extensive access control: hardware support, signed software and encryption.
  • Sandboxing: apps cannot access files of other apps; apps get specific capabilities via APIs; they execute in a non-privileged mode; and the OS itself is read-only to the app.

Android

  • Based on Linux. Apps from different vendors run under different user IDs, and the Linux mechanisms control access at the file level — preventing one app from reading another's data or exhausting shared resources such as memory and CPU.
  • As in iOS, apps hold permissions that are effectively capabilities, granting access to device services such as SMSes, the camera and the address book.
  • Android supports a wide range of hardware platforms, but a concession follows: developers cannot assume uniform features across all devices.
  • Apps ship as signed packages (.apk files). Where iOS apps are signed by Apple, Android's verification keys come in self-signed certificates that function as the developer's name — supporting integrity of updates while keeping an open ecosystem.
  • Each package has a manifest demanding a set of permissions, and users must approve the dangerous ones (those that can spend money or compromise personal data). In early Android the user had to approve everything at install or not run the app; experience showed most users would click anything, and even flashlight apps demanded address-book access to sell. So Android 6 moved to the Apple model of 'trust on first use' — though apps compiled for earlier versions still demand capabilities at installation.
⚠️
Android's well-known storage problem. There are two forms: app-internal storage and 'public storage'. Evidence suggests developers often misuse public storage because it is easier — everyone can write to it. Unfortunately, that also means everyone can read from it. Add a more permissive API (apps can send SMS messages on your behalf), and you can see why the Google Play Store is less tightly controlled than Apple's App Store — although apps are still screened for malware.
🤔
Pause & predict: A flashlight app asks for access to your contacts and SMS. On modern Android, when is that permission granted? (Answer: on first use, when the app tries the service and you consent — not automatically at install.)

Middleware Access Control

The messy middle layer — often overlooked, frequently misconfigured, and regularly left open to probing.

Middleware is the glue software that sits between applications and the operating system, whether on a single host or distributed across several. Examples include message brokering (such as AMQP) and various forms of Remote Procedure Calls (RPCs) — Java RMI, CORBA, XML-RPC and others.

Middleware access control is genuinely hard, for three reasons:

  • Huge complexity: you must define the granularity of access well, keep track of permissions, and enforce them consistently.
  • It is easily misconfigured, and these components are often left open to probing by outsiders.
  • Policy languages exist to define access control, but they are themselves hard to use.

Where possible, protect middleware from external access. That at least guards against random, remote exploitation. But note the limit: malware that starts inside one participating system can still try to exploit the middleware, so perimeter protection alone is not enough.

Database access control

Database Management Systems (DBMSes) that support multiple users and processes have their own access control — but the actual data still often sits on disk or in RAM, so operating-system protections remain necessary. Key points:

  • Connecting to a database requires a username and password.
  • There is internal privilege management: users on the OS are mapped to roles inside the database. This is role-based access control (RBAC) — a user's permissions come from the role they hold (for example, a Database Administrator has more privileges than a Database Manager).
  • The SQL standard defines fine-grained methods for access control, and in theory any kind of object can be access-controlled.
  • That flexibility can lead to overkill in complexity, making the system cumbersome to manage and understand.
  • DBMSes also allow specific integrity controls, but these are computationally heavy to check.
💡
Why DBMS access control is not enough on its own: the database's rules only govern queries through the DBMS. Someone who reads the raw files on disk, or the memory pages, bypasses them entirely — which is exactly why the OS layer still matters.

Browsers and the Confused Deputy Problem

A browser is an access-control device that runs untrusted code all day — and its main rule has a famous loophole.

The web browser is another middleware platform on which we rely for access control, and whose complexity often lets us down. Its main rule is the same-origin policy: JavaScript or other active content on a web page is only allowed to communicate with the IP address it originally came from. Code is run in a sandbox so it cannot alter the host system.

By now there is a realisation that we should probably have treated browsers as access-control devices all along: the browser is where you run code written by people you do not trust, who will occasionally be malicious. That is why Google Chrome runs each tab in its own separate operating-system process — so a hanging script in one tab does not take down the whole browser.

Even so, the modern web environment is extremely hard to control:

  • Bugs in browsers are exploited in drive-by download attacks, where simply visiting a malicious page can infect your machine.
  • Many pages are full of trackers supplied by multiple ad networks and data brokers, which make a mockery of the intent behind the same-origin policy.
  • Attackers can launder origin: they make a mash-up of the target site plus their own evil scripts, then get the victim to view it through a proxy such as Google Translate.
  • A prudent person types their bank's URL directly or uses a bookmark — but marketing trains everyone to click links in emails.

The confused deputy problem

Confused deputy problem — when a privileged program (the 'deputy') is tricked by a less-privileged entity into misusing its authority on the attacker's behalf. The browser is 'confused' about who the real requester is, mistakenly attributing the malicious site's request to a trusted one, which can lead to unauthorised actions and data breaches.

In browsers, this typically appears through Cross-Site Scripting (XSS), where a malicious script is injected into a trusted website. The attack runs in three steps:

  1. Malicious script injection: a user visits a trusted website that has an XSS vulnerability, and the attacker injects malicious JavaScript into it.
  2. Executing malicious actions: when the user interacts with the site, the injected script runs in the browser with the website's permissions.
  3. Exploiting trust: the script can now act on the user's behalf — sending authenticated requests or accessing sensitive data — because the browser believes these actions came from the trusted site.
ℹ️
Coming up later: the confused deputy problem and XSS are covered in more depth in the web security lecture. Cross-Site Request Forgery (CSRF) is another classic example of a confused deputy.
🤔
Pause & predict: A script on a shopping site submits a request to the bank using the victim's logged-in session. Who is the 'deputy', and who is the attacker? (Answer: the browser is the deputy; the malicious script — injected into a trusted site — is the attacker, abusing the trust the browser places in that site.)

Sandboxing

Put untrusted code in a box with only the doors it truly needs — then hope the box holds.

Sandboxing creates a shielded environment where malicious applications cannot interfere with the surrounding system. The sandbox typically provides a limited API for interaction, striking a balance between functionality and security.

A sandbox provides a restricted environment in which code has no access to the local hard disk (or at most only temporary access to a restricted directory), and is only allowed to communicate with the host it came from — the same-origin policy again.

Examples

☕ Java applets

Running inside the browser. A historical example — almost obsolete today.

🟨 JavaScript in the browser

Active content confined to the sandbox and limited by the same-origin policy.

🧭 Google Chrome tabs

Each tab runs in its own separate process, isolating a crash or a compromise.

⚠️
The catch: the sandbox is hard to secure. There are methods by which it can be 'broken out of', compromising the intended isolation. Treat a sandbox as one layer of defence, not a guarantee.

Virtualisation and Containers

Not designed for access control, yet the effort needed to escape a virtual machine raises the bar for every attacker.

Virtual machines

The primary use case of virtualisation is Virtual Machines (VMs) that emulate a computer system. It is old technology — invented around the 1960s, when IBM's VM/370 let a single machine be partitioned into multiple virtual machines. A VM allows software to run even when the real environment it was written for is not available, and the operating system inside the VM sees only its 'own' hardware. At the client end, virtualisation lets you run a guest operating system on top of a host — for example, Windows on top of macOS.

Virtualisation comes in varying degrees:

DegreeWhat it means
Full virtualisationComplete emulation of hardware — even across different hardware architectures.
Para-virtualisationThe guest OS must be modified to support being virtualised.
Containers and jailsA form of light-weight virtualisation — an isolated environment for running applications.

A hypervisor manages and runs the VMs, with hardware support at the ring -1 level (rings are explained in the hardware section). Examples include VirtualBox, VMware, Xen and QEMU.

Virtualisation is not designed for access control, but the typically high effort required to 'break out' of a VM raises the bar for attackers. Keep three cautions in mind:

  • VM execution is detectable: a VM does not perfectly imitate a real environment, so malware can detect that it is inside one and act differently.
  • Hypervisors have vulnerabilities that can be exploited.
  • Therefore: always keep hypervisor software up to date, and never use virtualisation as a single defence.

Example: Docker

Docker started as a tool for continuous integration and delivery (CI/CD). It offers an abstraction over containers, supporting several operating systems through their native jail implementations. It builds images out of applications and their supporting libraries, is fast to spin up and delete, and is easy on resources. Management systems such as Kubernetes are available to orchestrate many containers.

  • Docker sandboxes the app in the container: an app cannot communicate with an app in another container.
  • However, the Docker daemon acts as broker and runs as root. That means any user who can start or stop containers can interact with the daemon — an expanded attack surface.
  • While not designed for access control, containers provide an extra degree of separation and raise the bar for attacks.
💡
The pattern to notice: sandboxes, VMs and containers are all isolation technologies. None was built as an access-control mechanism, but each makes an attacker's life harder by adding a boundary that must be crossed — which is exactly what access control is for.

Hardware Access Control

The bottom of the stack: how the CPU itself keeps processes apart and enforces privilege.

Hardware protections enhance system security through several mechanisms: memory protection, privileged execution and isolated cryptographic components.

Memory protection

CPUs support the operating system in keeping processes' memory allocations apart. This is primarily achieved through segment addressing: memory is addressed using two registers — a segment register pointing to a segment of memory, and an address register pointing to a location within that segment. If a process tries to access memory outside its address space, a segmentation fault (SIGSEGV) is raised. This protects against both unauthorised read and write operations.

Privileged execution

CPUs have layered modes called rings, organised into different privilege classes. ARM goes further, with separate registers for different privilege classes. This ensures critical operations are safeguarded by restricting access according to privilege level.

In the interaction between kernel and hardware:

  • Code runs in one of the available CPU modes, the rings.
  • CPUs enforce access control from higher-privileged rings to lower ones. A process running in a higher ring cannot directly interact with a process in a lower ring.
  • The principle of least privilege states that all code should run only with the minimal required privilege, never more.
  • The number of pathways for communication with the kernel should be limited to the required minimum and well controlled.
Principle of least privilege
run every piece of code with the minimum privilege it needs — and no more

Isolated cryptographic components

Keys can be stored in hardware, with functionality that uses them exposed through a dedicated interface. This restricts access to the keys so only authorised functionality can use them. The classic example is the Intel TPM (Trusted Platform Module), which was originally conceived for Digital Rights Management (DRM). The TPM provides a secure environment for cryptographic operations, minimising exposure to malicious software.

Intel processors

  • The Intel 80286 introduced segment addressing and rings.
  • The Intel 80386 added built-in virtual memory and a memory segment of 4 GB.
  • Rings of protection are supported by several mechanisms. The current privilege level can only be changed by a process in ring 0 (the kernel). Procedures cannot access objects in lower-level rings directly, but gates allow execution of code at a different privilege level and manage supporting infrastructure such as multiple stack segments.
  • Modern Intel CPUs have nine rings: rings 0–3 for normal code, below which is a further set of rings 0–3 in VMM root mode for the hypervisor, and at the bottom System Management Mode (SMM) for the BIOS. In practice the four levels actually used are SMM, ring 0 of VMX root mode, the normal ring 0 for the OS, and ring 3 for applications.

ARM processors

  • ARM is the processor core most commonly used in phones, tablets and IoT devices. Unlike Intel, ARM licenses a range of processor cores that chip designers include in their products.
  • The core initially contained no memory management, so ARM-based designs could be extensively customised. There are now variants with memory protection units (MPUs) and others with memory management units (MMUs) that also handle virtual memory.
  • ARM's latest offering is CHERI (Capability Hardware Enhanced RISC Instructions), which adds fine-grained capability support to ARM CPUs. CHERI lets a process spawning a subthread allocate it read and write access to specific ranges of memory, so multiple sandboxes can run in the same process.
  • The long-term promise: if used thoroughly in operating systems such as Windows, Android or iOS, CHERI has the potential to prevent most of the zero-day exploits of recent years by providing fine-grained spatial memory safety at the hardware level.
ℹ️
Ring numbering, explained. Lower number = more privilege. Ring 0 is the kernel; ring 3 is ordinary applications. The hypervisor's ring -1 sits below ring 0 (more privileged than the kernel), and SMM is lower still. That is why a VM can be managed without the guest OS being able to tamper with the hypervisor.
🤔
Pause & predict: Why does the principle of least privilege also tell us to limit the number of ways a program can talk to the kernel? (Answer: every communication pathway is a potential attack vector; fewer, well-controlled pathways mean a smaller surface for an attacker to exploit.)

Security Policy Models and Multilevel Security

Before you build mechanisms, you write down precisely what 'secure' means — that is a policy model.

Multilevel security (MLS) is a foundational form of access control. The idea is that information must be handled at different levels of classification — Top Secret, Secret, Confidential and so on. MLS has enormous importance in military and government, where access must be strictly controlled by classification.

Yet MLS is surprisingly difficult to implement while maintaining high utility. Consider the example: how can a system provide an automated means to reduce a document's classification from Top Secret to Secret, so that other dependent principals at the lower level can read it? Getting that declassification right, safely and automatically, is genuinely hard.

How to analyse a system's security

When analysing security, the usual order is:

  1. Analyse incentives and create a threat model — a model describing the attacker's motivations and capabilities.
  2. Analyse the security policy — the policy describes the goals to be achieved. It is relatively verbose.
  3. Analyse the security mechanisms that implement the policy.

A Security Policy Model is a highly precise and succinct statement about the protection properties of the system. It can be highly formal, and it drives engineering — it is the specification that mechanisms must satisfy.

💡
Why models matter even though pure implementations are rare: you will almost never meet a system that implements a policy model exactly. But the models give you the vocabulary to discuss real-world access control — and, as you will see, variants of one of them (Biba) are surprisingly common in real operating systems.

The Bell-LaPadula Model

The classic confidentiality model: information may not flow downwards.

The Bell-LaPadula (BLP) model is the classic security policy model for MLS, proposed in 1973. In the 1970s there was a growing realisation that operating systems would always contain vulnerabilities that users could work around. That underscored the need to implement MAC that could not be bypassed. BLP's basic property is that information cannot flow downwards.

It enforces two mandatory properties and includes one discretionary form of access control:

1. No read up simple security

No subject may read data at a higher security level. Equivalently, a subject can read their own level or down.

2. No write down star property

No subject may write data to a lower security level. Equivalently, a subject can write to their own level or up.

Why 'no write down' is crucial

The star-property (the no-write-down rule) is the subtle and crucial one. Picture the attack it blocks:

  1. A user at a low security level writes a program designed to exfiltrate data.
  2. The user waits for an administrator or user at a high security level to accidentally execute it.
  3. If the high-level user could then write the secret data down to the low level, the secret would leak.

'No write down' prevents higher-level entities from writing to lower-level objects, closing this indirect exfiltration path. Enforcing it effectively requires MAC.

The discretionary part

BLP also has one discretionary form of access control: an external entity defines the access of subjects to objects in a matrix. For example:

Subjecto1o2o3o4
Samreadappend—read
Bert—read-writeappendexecute

Innovations and criticisms

Innovations

  • Blends well with formal analysis.
  • Combines DAC and MAC in a single model.

Criticisms

  • Administration is via one omnipotent Trusted Principal — how do you secure that?
  • Defined with confidentiality in mind, not integrity.
  • Does not consider covert channels.
  • Two BLP-secure systems combined are not necessarily BLP-secure.
⚠️
Covert channel example: a program can encode a 1 as high CPU load and a 0 as low load. A program at a lower level can estimate the CPU load and thereby infer the secret — a channel BLP simply does not address.
🤔
Pause & predict: Under BLP, can a user with Secret clearance write a file that is Top Secret? (Answer: yes — writing up is allowed. 'No write down' only forbids writing to lower levels.)

The Biba Model and Using the Models

Bell-LaPadula reversed: now the goal is integrity — stopping malicious change, not stopping leaks.

The Biba model addresses integrity, not confidentiality: it aims to prevent malicious change. It can be seen as a reverse of Bell-LaPadula, and it has three core principles:

1. Read up simple integrity

A subject may only read data at its own level or higher (no read down).

2. Write down star integrity

A subject may only write data at its own level or lower (no write up).

3. Invocation property

A process from below cannot request higher access — it can only invoke subjects at an equal or lower level.

The first two rules control direct read and write access to data. The invocation property controls the ability of processes to call or execute other processes. It prevents a low-integrity process from invoking a high-integrity process to do its work for it, which could lead to an integrity breach.

Examples that make it click

  • An aircraft's in-flight entertainment system can read data from the avionics (such as airspeed) but cannot alter any avionics data — so entertainment-system vulnerabilities cannot compromise flight controls.
  • An odometer can display mileage but cannot change it, preserving the integrity of the vehicle's mileage data.

Worked example: applying both models

Suppose users have clearances and three files each require a clearance, and no other rules exist:

UserClearanceRequired clearanceObject
BartNoneUltimatefridgecodes.txt
HomerLowMediumtvlockcodes.txt
LisaMediumLowplaystationcodes.txt
MargeUltimate——

In a Bell-LaPadula model:

  • Can Homer obtain the TV lock codes? No — a 'Low' clearance cannot read a 'Medium' object (no read up).
  • Can Homer enlist Marge to get them? No — Marge cannot write down, so she cannot pass the codes down.
  • Can Bart change all codes as he wishes? Yes — with 'None' clearance he can write up, changing any document above him. This is an extreme example, but it highlights that BLP focuses only on confidentiality, not integrity.

In a Biba model:

  • Can Homer obtain the TV lock codes? Yes — read up is allowed.
  • Can Marge change all codes as she wishes? Yes — write down is allowed.

Which models are actually used?

Pure Bell-LaPadula implementations — or pure implementations of any single model — are rare. Variants of Biba, however, are much more common:

  • Windows Vista.
  • UNIX: SELinux, some Red Hat versions, and a FreeBSD module.

Even when pure models are absent, the concepts are useful for discussing real-world access control. That is why the lecture then shifts focus to real-world concepts in mobile, desktop and server operating systems and hardware.

BLP · BIBA
"BLP: no read up, no write down. Biba: no read down, no write up."
Bell-LaPadula protects confidentiality (stop secrets leaking down). Biba protects integrity (stop bad data flowing up). Biba is BLP flipped.
🤔
Pause & predict: Which model would you choose for a system where an untrusted sensor must never corrupt trusted control data? (Answer: Biba — its no-write-up rule stops low-integrity input from flowing into high-integrity systems.)

Key Takeaways

If you remember nothing else, remember this.

1

Access control controls which principals reach which resources. Authentication proves identity; authorisation allocates privileges. Authentication comes first.

2

Access can be modelled as a matrix of subjects against objects; cells hold r, w, x or no access. An ACL is one column; a capability is one row.

3

DAC = the owner decides (flexible, e.g. personal OneDrive). MAC = a central authority decides via security labels, checked by the security kernel (rigorous, e.g. enterprise DLP).

4

ACLs attach to objects and map user IDs to allowed operations. They are widespread: POSIX/UNIX, Windows, social networks and enterprise systems.

5

Unix uses nine permission bits — rwx for owner, group and others. Read -rw-r--r-- as owner read/write, group read, others read. X on a directory means traverse.

6

SUID runs a program as its owner; SGID as its group (or sets directory group inheritance); the sticky bit restricts deletion (used on /tmp). Processes carry real, effective and saved UID/GID.

7

Root has UID/GID 0 and is all-powerful; sudo (with the sudo group, usually a password, and the sudoers file) grants controlled root access.

8

Other OSes differ: macOS (BSD, Keychain, Kerberos, TrustedBSD MAC), Windows (13–16 permissions, enforced by the Security Reference Monitor), iOS (read-only sensors, signed software, sandboxing) and Android (apps as separate users, .apk signing, the public-storage problem).

9

Middleware and databases add their own controls — role-based access control maps OS users to database roles — but the OS layer is still needed because data lives on disk and in RAM.

10

Browsers enforce the same-origin policy and run code in a sandbox, yet suffer the confused deputy problem — a privileged program tricked into misusing its authority, classically via XSS.

11

Hardware enforces the bottom layer: memory segmentation (SIGSEGV on violation), privilege rings, the principle of least privilege, isolated cryptographic components such as TPMs, Intel's nine rings, and ARM's CHERI for fine-grained memory safety.

12

Bell-LaPadula protects confidentiality: no read up, no write down. Biba protects integrity and reverses it: no read down, no write up, plus the invocation property. Biba variants are common in real systems (SELinux, FreeBSD, Windows Vista).

Glossary

Every term you need to speak this week's language.

Access control
The element of a security policy that controls which principals may access which resources and assets — which files they can read, which programs they can execute, and how they share data.
Authentication
The process of acquiring evidence of the identity of another party. It answers 'who are you?' and normally precedes authorisation.
Authorization
The process of verifying whether an entity is allowed an action, or the allocation of a privilege to a party. It answers 'what may you do?'.
Discretionary Access Control (DAC)
Access controlled by the resource owner, based on the identity of the owning subject. Owners may grant or revoke permissions and pass privileges on, giving high flexibility.
Mandatory Access Control (MAC)
Access enforced by a central authority based on security labels. A security kernel checks security attributes; users cannot change permissions themselves. Gives high rigour.
Access Control List (ACL)
A list attached to an object that defines which subjects may perform which operations. Entries map a user ID to allowed operations, coarse or fine-grained.
User ID (UID) and Group ID (GID)
The numeric identifiers of a Unix/Linux user and group, recorded in /etc/passwd and /etc/group. Root has UID and GID 0.
Root
The all-powerful Unix/Linux user with UID and GID 0, able to access any file and become any user. Reached via su or sudo.
sudo and sudoers
The command that runs a command as root. It requires membership of the sudo group and usually a password; the sudoers file can permit specific commands for non-sudo users.
Set-user-ID (SUID)
A bit that lets a program run with the privilege of its owner rather than the invoking user — useful for granting narrow extra permissions (for example, mount).
Set-group-ID (SGID)
Like SUID but for the group. On a directory, files created inside inherit the directory's group ownership.
Sticky bit
A directory-level bit restricting deletion so only a file's owner (and root) can remove it. Used on /tmp.
Effective UID/GID
The identity a process actually runs with, which SUID/SGID can change. Real IDs identify the launcher; saved IDs let the kernel switch back.
Role-based access control (RBAC)
Granting permissions through roles — for example mapping OS users to database roles such as Database Administrator or Database Manager.
Ring
A CPU privilege level. Lower number means more privilege: ring 0 is the kernel, ring 3 ordinary applications, ring -1 the hypervisor, and SMM sits at the bottom.
Principle of least privilege
All code should run only with the minimal required privilege, never more, and kernel communication pathways should be minimised and controlled.
Trusted Platform Module (TPM)
An isolated hardware component storing cryptographic keys and exposing them through an interface. Intel's TPM was originally conceived for DRM.
CHERI
Capability Hardware Enhanced RISC Instructions — ARM's fine-grained capability support, letting subthreads be granted access to specific memory ranges and offering hardware-level memory safety.
Sandboxing
A shielded environment that stops malicious applications interfering with the surrounding system, typically exposing only a limited API. Hard to secure; can be broken out of.
Same-origin policy
The browser rule that JavaScript or other active content may only communicate with the IP address it originally came from.
Confused deputy problem
When a privileged program is tricked by a less-privileged entity into misusing its authority on the attacker's behalf, because it is confused about who the real requester is.
Cross-Site Scripting (XSS)
An attack that injects malicious script into a trusted website; the script then runs with the site's permissions, a classic confused deputy scenario.
Virtualisation
Emulating computer systems as virtual machines. Degrees range from full virtualisation through para-virtualisation to light-weight containers and jails.
Docker
A container abstraction that packages apps with their libraries, supports native jails, and sandboxes apps from one another. Its daemon runs as root, expanding the attack surface.
Multilevel security (MLS)
A foundational access-control model handling information at different classification levels (Top Secret, Secret, Confidential), of great importance in military and government.
Security policy model
A highly precise, succinct statement about the protection properties of a system. It can be highly formal and it drives engineering.
Bell-LaPadula (BLP)
The classic confidentiality model for MLS: no read up (simple security) and no write down (the star property), plus one discretionary matrix. Information cannot flow downwards.
Biba model
An integrity model that reverses Bell-LaPadula: read up (no read down), write down (no write up), and the invocation property. Variants are common in real systems.
Invocation property
The Biba rule that a process from below cannot request higher access — preventing a low-integrity process from invoking a high-integrity one to act on its behalf.
Covert channel
A method of passing information that is not normally used for communication — for example, encoding a bit as high or low CPU load. Bell-LaPadula does not address these.

No terms in this category.

Q1

Define access control, authentication and authorisation, and explain the relationship between them.

Answer: Access control is an element of a security policy that controls access to resources and assets — which principals may reach which resources, read which files, execute which programs, and share data how. Authentication is the process of acquiring evidence of the identity of another party ('who are you?'). Authorisation is verifying whether an entity is allowed an action, or allocating a privilege to a party ('what may you do?'). Authentication normally comes first, because you cannot sensibly decide permissions before you know the identity.
Q2

Place access control in the reference framework and explain the password example.

Answer: Access control is specified in the policy; it counters the incentives of the attacker who wants to access a resource or asset; it is implemented by one or more mechanisms; and those mechanisms give a certain level of assurance. A password is the mechanism, and the strength of the password relates directly to the assurance provided — a weak password gives weak assurance.
Q3

Read the naive access control matrix: why does Sam have universal access except read-only on the audit trail, and why does Alice have execute but not write on the operating system?

Answer: Sam is the system administrator, so he needs broad access to run the system — but even he should only be able to read the audit trail, never rewrite it, so evidence of misuse cannot be erased. Alice the manager needs to execute the operating system and applications, but only through the approved interfaces: she must not be able to tamper with them, so she has x but no w. She does need to read and write the data.
Q4

Contrast DAC and MAC, and use Microsoft OneDrive to illustrate both.

Answer: DAC is controlled by the resource owner: access is based on the identity of the owning subject, and owners can grant, revoke and pass on privileges unless constrained (for example by MAC). It is highly flexible. MAC is enforced by a central authority based on security labels; an external security policy administrator defines access, and a security kernel checks security attributes. It is highly rigorous. In OneDrive, personal use is DAC — the creator owns the file, can transfer ownership, and shares with specific people, anyone with the link, or publicly, at View or Edit levels. In enterprises, MAC elements appear: Microsoft 365 admins set sharing and access policies (for example restricting sharing to specific domains), and DLP automatically restricts access to sensitive information.
Q5

What is an ACL, what does an entry contain, and where are ACLs used?

Answer: ACLs define the access of subjects to objects. An object is associated with an ACL, which can be global or fine-grained. An ACL entry consists of a user ID plus a mapping to allowed operations, which may be coarse (read/write/execute) or very fine-grained. ACLs are common in all UNIX systems (POSIX standards), exist in Windows, and are also found on social networking sites and in content management and enterprise resource management systems.
Q6

A file is listed as -rw-r--r--. Who can do what? Then explain what the X bit means for a directory.

Answer: The nine bits split into three blocks: owner rw- (read and write, no execute), group r-- (read only) and others r-- (read only). So the owner, group and others can all read, but only the owner can write. For a directory, the X bit means the directory can be traversed — you can pass through it to reach files inside.
Q7

Explain SUID, SGID and the sticky bit, and give an example of each.

Answer: SUID lets an owner mark a program so it runs with the privilege of its owner rather than the invoking user — useful for granting narrow extra permissions without being a privileged user; mount is an example. SGID on a file is like SUID but with the group (the file executes with the owning group's privilege); on a directory, new files inherit the directory's group ownership. The sticky bit does not affect individual files; at the directory level it restricts deletion so only the owner (and root) can remove a file — used in /tmp.
Q8

What is the confused deputy problem, and how does XSS demonstrate it in a browser?

Answer: The confused deputy problem occurs when a privileged program (the deputy) is tricked by a less-privileged entity into misusing its authority on the attacker's behalf. The browser is confused about who the real requester is, wrongly attributing the malicious site's authority. Via XSS: an attacker injects malicious JavaScript into a trusted site that has an XSS vulnerability; when the user interacts, the script runs in the browser with the website's permissions; and because the browser believes the actions originate from the trusted site, the script can send authenticated requests or access sensitive data. CSRF is another example.
Q9

Why are virtualisation and containers relevant to access control even though they were not designed for it? Include their limitations.

Answer: They add an isolation boundary that an attacker must cross, so the typically high effort to 'break out' raises the bar. But limitations matter: VM execution is detectable because a VM does not perfectly imitate a real environment, so malware can detect it and act differently; hypervisors have vulnerabilities that can be exploited; and the Docker daemon runs as root, so any user who can start or stop containers can interact with the daemon, expanding the attack surface. Keep hypervisors up to date and never rely on virtualisation as a single defence.
Q10

State the Bell-LaPadula properties and explain why the star property is crucial, using the exfiltration example.

Answer: Bell-LaPadula enforces no read up (simple security) — no subject may read data at a higher level — and no write down (the star property) — no subject may write data to a lower level. The star property is crucial because a user at a low level could write a program to exfiltrate data and wait for an admin at a high level to accidentally execute it; if the high-level user could write down, the secret would leak. No write down closes this path and requires MAC to enforce effectively. BLP also has one discretionary form of access control: an external entity defines access in a matrix.
Q11

State the Biba properties and explain the invocation property. Then apply Biba and Bell-LaPadula to Homer and Marge.

Answer: Biba protects integrity: read up (simple integrity, no read down), write down (star integrity, no write up), and the invocation property — a process from below cannot request higher access, preventing a low-integrity process from invoking a high-integrity one to act for it. In the clearance example: under Bell-LaPadula, Homer (Low) cannot read the Medium TV codes, and cannot use Marge to get them because Marge cannot write down; under Biba, Homer can read up and get the TV codes, and Marge can write down and change the codes.
Q12

List the criticisms of Bell-LaPadula, and say which model is more commonly seen in real operating systems.

Answer: Criticisms: it relies on administration by one omnipotent Trusted Principal (how is that secured?); it is defined with confidentiality in mind, not integrity; it does not consider covert channels (for example encoding a bit as high or low CPU load); and a system composed of two Bell-LaPadula-secure systems is not necessarily Bell-LaPadula-secure. Its innovations are that it blends well with formal analysis and combines DAC and MAC. Pure BLP implementations are rare; variants of Biba are more common — for example Windows Vista, SELinux, some Red Hat versions and a FreeBSD module.
