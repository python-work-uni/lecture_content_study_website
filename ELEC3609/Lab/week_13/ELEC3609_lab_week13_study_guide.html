Lecture overview

Week 13 is a technical interview conducted by the tutors, focused on your deployment setup and security configurations for Assignment 3 (A3). Unlike the A2 interview, this one is built around a live instance: you must be able to demonstrate your deployed website and explain your configuration files. Interviews and deployment checks run in parallel, so the whole lab stays on schedule.

01

A3 Technical Interview Overview

Each group will participate in a technical interview conducted by the tutors, focusing on your deployment setup and security configurations for Assignment 3.

This lab session is a technical interview to assess your group's understanding of your deployment and security setup in A3.

💡

Why It Matters:

A2 tested whether you understood your own code. A3 tests whether you understand the system as it runs in production — the servers, the configuration and the security controls that keep it safe.
02

What Tutors Will Ask About

Tutors will ask questions about:

  • Your AWS deployment environment and configuration decisions.
  • Web server and backend setup (e.g. Nginx, uWSGI, HTTPS).
  • Your implementation of key security requirements (authentication, permissions, firewall, HTTPS, etc.).
  • Technical challenges or decisions encountered during deployment and hardening.

Be prepared to explain, justify and demonstrate your deployment and security setup using a live instance and related configuration files.

🧠

Memory Hook:

Four question areas — D-W-S-C — "Deployment environment, Web server/backend, Security requirements, Challenges."
⚠️

Common Trap:

Being able to run the site but not explain how requests travel through it. The interview asks why the setup is configured the way it is, not just whether the page loads.
03

Interview Flow

To efficiently manage lab time, interviews and deployment checks run in parallel.

Interview flow:

  • Groups are interviewed in ascending group number order (for example Group 1 → Group 2 → Group 3…).
  • When your group number is called, bring your laptop to the tutor's desk.
  • Each group has 10 minutes total, answering questions on deployment and security.
📝

Tip:

Have your laptop ready and your deployed website accessible before your turn, so no time is lost to setup.
ℹ️

Info:

If your group requires an earlier interview because of urgent circumstances, inform the tutors before the lab begins.
04

Parallel Deployment Check

  • One tutor conducts interviews at the tutor desk in ascending group order.
  • At the same time, the second tutor moves around the room to test deployments.
  • The second tutor verifies that your website is successfully deployed and functioning by interacting with it on your machine.
💡

Why It Matters:

This is why a live, working deployment is mandatory. While you answer questions at the desk, another tutor may be clicking through your site to confirm it really works.
⚠️

Common Trap:

Depending on a single instance that crashes before the check. The lab advises deploying on more than one member's environment as a backup.
05

What to Have Ready

Ensure your group has:

  • A deployed website running in one group member's AWS Learner Lab EC2 instance.
  • Access to your EC2 instance via terminal (SSH).
  • Access to key configuration files such as nginx.conf, uwsgi.ini, and your Django settings.
  • Be prepared to demonstrate live the deployment setup and security measures.
  • Be respectful and quiet while other groups are being interviewed.
  • All group members must attend and be prepared to answer.
🧠

Memory Hook:

Three essentials — the running site, SSH access, and your config files.
06

Preparation Checklist

This interview is part of your final project mark and focuses on your technical understanding of deployment and security. To prepare:

  • Practice accessing your EC2 instance via the command line.
  • Make sure you can locate and explain configuration files quickly — many groups waste time here.
  • If possible, deploy your website on more than one member's AWS Learner Lab environment as a backup, in case your primary instance is down.
💡

Why It Matters:

The interview is time-boxed to 10 minutes. Time spent hunting for nginx.conf is time not spent demonstrating what you know. Rehearse the navigation.
07

Security Topics to Master

Be familiar with how you implemented:

  • HTTPS, reverse proxy and uWSGI.
  • SSH configuration and file permissions.
  • Django production settings.
  • Security hardening (e.g. limited DB permissions, disabled debug mode, cookie/JWT protection).
⚠️

Common Trap:

Disabling debug mode but leaving other defaults untouched, or restricting the database to a powerful user. The list above is exactly what tutors probe — understand each control and why it exists.

Glossary

A3

Assignment 3 — the deployment-focused deliverable assessed in this interview.

Technical interview

A tutor-led, question-and-answer assessment, here about deployment and security.

Live instance

A running AWS EC2 instance hosting your deployed site.

AWS Learner Lab

The AWS environment where each student's EC2 instance runs.

Deployment check

The parallel verification that your website is deployed and functioning.

AWS deployment environment

The cloud setup (instance, networking, services) your site runs on.

nginx

The web server / reverse proxy in front of your application.

uWSGI

The application server that runs the Django WSGI application.

Reverse proxy

A server that forwards client requests to a backend — nginx forwarding to uWSGI.

HTTPS

Encrypted HTTP; a core A3 security requirement.

SSH

Secure Shell — how you access the EC2 instance from a terminal.

File permissions

The Linux controls governing who can read, write or execute files.

Django production settings

The deployment-time configuration of settings.py (e.g. debug mode off, allowed hosts set).

Debug mode

Django's verbose development mode, which must be disabled in production.

Security hardening

Tightening a system's configuration to reduce attack surface.

Limited DB permissions

Restricting the database user to only what the application needs.

Cookie/JWT protection

Securing authentication tokens against theft or misuse.

Firewall

The rules (e.g. security groups) controlling network access to the instance.

Authentication

Verifying who a user is.

Permissions

Controlling what an authenticated user (or process) may do.

nginx.conf

The nginx configuration file you must locate and explain.

uwsgi.ini

The uWSGI configuration file you must locate and explain.

Ascending group number order

The interview sequence, from lowest group number upward.

Final project mark

The overall project grade that this interview contributes to.

Worked Examples & Scenarios

Example 1

Locating configuration files fast

A group rehearses the exact paths before the interview. On their laptop they have an SSH session open to the EC2 instance, and they can immediately open nginx.conf, uwsgi.ini and their Django settings.py. When the tutor asks, "Show me how nginx forwards to the app," they point straight at the location / { include uwsgi_params; uwsgi_pass 127.0.0.1:8000; } block instead of hunting through directories.

Example 2

Demonstrating HTTPS and the reverse proxy

A tutor asks how HTTPS reaches the application. The group explains the flow: client → HTTPS → nginx (the reverse proxy) → uWSGI → Django, and shows the relevant configuration. Being able to walk through the request path demonstrates real understanding rather than a working page alone.

Example 3

Setting up a backup deployment

Because a second tutor roams the room testing deployments, a group deploys the same site on two members' AWS Learner Lab environments. If the primary instance is down when the tester arrives, the backup instance still proves the deployment works.

Example 4

Explaining a security hardening decision

A tutor asks why debug mode is off. A strong answer explains that debug mode is a development convenience, and that leaving it on in production can expose detailed traces and internal settings to the public. The group also mentions other hardening they applied, such as limiting database permissions and protecting cookie/JWT credentials.
