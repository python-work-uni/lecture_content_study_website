Building in the Cloud: AWS Services, Amazon RDS and GraphQL APIs

This lab introduces how real web applications are deployed and served in the cloud. It covers the core AWS building blocks (compute, networking, storage, security and monitoring), explains why a managed remote database like Amazon RDS beats a local file database for team development, and then introduces GraphQL — a query language for APIs that fixes the over-fetching, under-fetching and rigid-endpoint problems of REST.

Read this first: Two big ideas run through this lab. First, in the cloud you rent building blocks (a virtual server, a network, a managed database, a CDN) instead of owning them, and you wire them together securely. Second, an API is a contract for how clients ask for data — REST forces the server to decide the shape of every response, while GraphQL lets the client ask for exactly the fields it needs in a single request. Keep those two mental models in mind and everything else clicks into place.

The Big Picture: From Local Code to a Cloud Deployment

A modern web app is not one program on one machine — it is a set of rented, managed services wired together, and this lab teaches you both the infrastructure and the API layer.

💡
Why it matters: You have been building apps on your own laptop with a local database and a development server. That works for one person. Real systems must be reachable by users, survive crashes, stay secure, and let a whole team share one source of truth. Cloud services and a well-designed API layer are how that happens.

The two halves of this lab

This lab has two distinct halves that fit together:

  1. The infrastructure half (AWS Cloud). How you host an application: virtual servers, networks, managed databases, storage, content delivery and monitoring.
  2. The API half (GraphQL). How clients talk to that application: a query language that gives clients control over exactly what data they get back.

  • Explain the advantages of using Amazon RDS for collaborative, production-like development.

AWS Cloud Architecture Overview

AWS is a flexible, scalable platform, and its architecture is easiest to learn by grouping services into five categories: compute, storage, networking, security and management.

AWS provides a flexible and scalable cloud platform with various services to build secure, reliable and highly available applications. Rather than memorising a long list of product names, group them by the job they do.

The five categories of AWS services

CategoryWhat it providesExample services
ComputeMachines that run your codeEC2
StoragePlaces to keep objects and dataS3, RDS
NetworkingIsolated networks and traffic routingVPC, Internet/NAT Gateway, ELB
SecurityIdentity, permissions and secretsIAM, Parameter Store
ManagementMonitoring, metrics and alertsCloudWatch
🧠
Memory hook: Think C-S-N-S-M — Compute, Storage, Networking, Security, Management. Every AWS service you meet can be filed under one of these five headings.

Key components

  1. Amazon EC2 (Elastic Compute Cloud) — Scalable virtual servers to run applications. Supports various instance types, Auto Scaling and Load Balancing.
  2. Amazon RDS (Relational Database Service) — Managed relational database service supporting MySQL, PostgreSQL, Oracle and others. Offers automated backups, scaling and multi-AZ deployments.
  3. Amazon VPC (Virtual Private Cloud) — Isolated network environment for AWS resources with customisable IP ranges, subnets, route tables and gateways.
  4. Amazon AMI (Amazon Machine Image) — Pre-configured templates for EC2 instances, including operating system, software and configurations.
  5. AWS IAM (Identity and Access Management) — Manages user access and permissions for AWS resources using roles, policies and multifactor authentication.
💡
Why it matters: EC2 is the machine, the AMI is the blueprint used to create that machine, the VPC is the private network it lives in, RDS is the database it talks to, and IAM is the guard deciding who may do what. Almost every AWS deployment is some arrangement of these five.
🤔

Security Measures in a Cloud Architecture

Cloud security is layered: separate gateways control inbound and outbound internet traffic, IAM Roles remove hard-coded credentials, Parameter Store protects secrets, and a load balancer distributes traffic.

Having servers in the cloud is not enough — you must control who can reach them and how they reach out. AWS gives you a set of security building blocks.

The five security measures

  1. Internet Gateway — Enables internet access for VPC resources.
  2. NAT Gateway — Allows private subnets to access the internet securely (outbound only, without exposing them to inbound traffic).
  3. IAM Roles — Provide secure access to AWS services for applications without hard-coded credentials.
  4. Parameter Store — Secure storage for configuration data and secrets, with encryption using AWS KMS.
  5. Elastic Load Balancer (ELB) — Distributes incoming traffic for high availability and integrates with WAF for security.

Internet Gateway

  • Attaches to a VPC to give resources internet access.
  • Handles traffic for public subnets.
  • Inbound and outbound connectivity.

NAT Gateway

  • Lets private subnets reach the internet securely.
  • Shields those resources from inbound connections.
  • Used for outbound-only access (e.g. software updates).
⚠️
Common trap: Don't confuse the two gateways. The Internet Gateway is the front door that lets the public reach your resources; the NAT Gateway is a one-way exit that lets private resources go out to the internet without the internet getting in.
🧠
Memory hook: IAM Roles = no passwords in code. Instead of embedding AWS keys in your source, the application assumes a role and receives temporary credentials.

Additional AWS Services: Storage, Delivery and Monitoring

Beyond compute and networking, three services round out most deployments: S3 for object storage, CloudFront as a CDN for low-latency delivery, and CloudWatch for monitoring and alerts.

These services are not strictly required for a minimal deployment, but they solve three recurring problems: where to store files, how to deliver content quickly to users worldwide, and how to know what your system is doing.

The three additional services

  1. Amazon S3 — Scalable object storage with high durability, versioning and lifecycle management. Use it for user uploads, static assets and backups.
  2. AWS CloudFront — A Content Delivery Network (CDN) for low-latency content delivery, caching content at edge locations close to users.
  3. AWS CloudWatch — Monitoring and observability service for metrics, logs and alerts.
ServiceJobOne-line purpose
Amazon S3Object storageDurable, versioned storage for files and assets
AWS CloudFrontCDNServe content with low latency from edge locations
AWS CloudWatchObservabilityCollect metrics and logs, raise alerts
CDN — A Content Delivery Network caches content at servers around the world (edge locations) so users download it from somewhere geographically close, cutting latency.

The Deployment Blueprint for the Final Assignment

For the final assignment you do not build a full AWS architecture — you run one EC2 instance hosting both the application and the web server, and add RDS or S3 only if you need them.

This is the single most practically important fact in the cloud half of the lab, because it tells you exactly what you are expected to build.

What you actually need to deploy

  • You do not need to build a full AWS cloud architecture. The elaborate diagram of gateways, load balancers and multi-AZ databases is context, not a requirement.
  • Generally, use a single EC2 instance to host both the application and the web server.
  • The stack is EC2 + Nginx + uWSGI.
  • You may also consider using Amazon RDS and Amazon S3 as needed.
EC2 instance→Nginx (web server)→uWSGI (app server)→your application

Unpacking the stack

  • EC2 provides the virtual server.
  • Nginx is the web server that receives HTTP requests from users and forwards them.
  • uWSGI is the application server that runs your Python web application and speaks to Nginx.
  • RDS (optional) provides a managed remote database instead of a local file.
  • S3 (optional) provides object storage for files and assets.
✅
Exam tip: If asked "what does a typical ELEC3609 final deployment look like?", the expected answer is a single EC2 instance running Nginx and uWSGI, with RDS and S3 added only as needed — not a multi-service, load-balanced architecture.

Amazon RDS: Why Use a Remote Database Service

A managed cloud database gives your whole team one central, always-current, production-like database instead of many fragile local copies.

Amazon Relational Database Service (Amazon RDS) is an easy-to-manage relational database service optimised for total cost of ownership. In development it replaces the local database file (for example db.sqlite3) that you have been using so far.

The six reasons to use a remote database service

  1. Centralised and consistent database management — All team members work with one centralised, shared database. This eliminates manually updating local databases when changes are made, reducing errors and ensuring consistency across the team.
  2. Avoiding database files in version control — Database files like db.sqlite3 are unsuitable for version control due to their size, frequent changes and potential security risks. RDS manages the database remotely, keeping the repository clean and focused on code and migrations rather than raw data.
  3. Remote access and collaboration — Multiple developers can access the same database remotely, facilitating collaboration in distributed teams. Changes made by one developer are instantly available to others, eliminating the need for sharing database dumps or repeatedly setting up local databases.
  4. Simplified database migrations — Migrations are applied to a central instance, giving all developers immediate access to updated schemas. This streamlines the process compared to running scripts on individual local environments, ensuring everyone is on the same page.
  5. Development environment parity — Using RDS in development ensures the environment closely mirrors production, reducing environment-specific issues during deployment. This consistency helps catch potential issues early and facilitates smoother production rollouts.
  6. Backup, recovery and security — RDS offers built-in features for backup, recovery, encryption and scaling that are difficult to manage locally. This keeps the development database secure and reduces the risk of data loss or unauthorised access.
💡
Why it matters: A local db.sqlite3 file is a single point of truth that nobody shares. If two teammates edit their own copies, they diverge immediately. RDS makes the database a shared, managed service, exactly as it will be in production.
⚠️
Common trap: "It works on my machine" usually means your database and your teammate's have drifted apart. Environment parity (reason 5) is what prevents this class of bug.
🧠
Memory hook: C-A-R-S-D-B — Centralised, Avoid VCS, Remote collaboration, Simplified migrations, Development parity, Backup/security.

GraphQL: A Query Language for APIs

GraphQL is both a query language for APIs and a runtime for executing those queries against your data — a more efficient, powerful and flexible alternative to REST.

GraphQL was developed by Facebook in 2012 and released to the public in 2015. It provides a more efficient, powerful and flexible alternative to REST for interacting with APIs. Many popular public APIs adopted GraphQL as the default way to access them, including GitHub, Yelp and Shopify.

GraphQL — A query language for APIs and a runtime for executing those queries against your data. Clients describe exactly the data they want, and the server returns precisely that.

The core promise

In REST the server decides the shape of every response. In GraphQL the client sends a query describing exactly which fields it needs, and the server returns exactly those fields — no more, no less, and often in a single request.

🧠
Memory hook: GraphQL's tagline is essentially "ask for exactly what you want." REST gives you a fixed menu; GraphQL lets you build your own plate.
ℹ️
Note: A recommended ByteByteGo video is provided in the lab to build a basic understanding of GraphQL — worth watching before the assessment.

The Limitations of (Poorly Designed and Managed) REST

REST's fixed endpoints and server-defined responses cause four recurring problems: over-fetching and under-fetching, endpoint sprawl, lack of flexibility, and versioning bloat.

To understand why GraphQL exists, you first need to see what goes wrong with REST. Note the careful framing: these are the limitations of poorly designed and managed REST — REST itself is not inherently broken.

The four limitations

  1. Over-fetching and under-fetching — REST APIs often return more data than needed (over-fetching) or too little data (under-fetching), requiring multiple requests to different endpoints.
  2. Multiple endpoints — REST typically uses multiple endpoints for different resources (/users, /posts, /comments, etc.). Managing and maintaining these endpoints can be cumbersome as the API evolves or scales.
  3. Lack of flexibility — REST responses are often fixed by the server, meaning clients have little control over what data is returned. Changing data needs may require additional endpoints or modifications to the API.
  4. Versioning issues — REST APIs commonly use versioning (e.g. /v1/users, /v2/users) to manage changes, which can lead to bloated and complex API management.
Over-fetching — The API returns more data than the client needs, wasting bandwidth and processing.
Under-fetching — The API returns too little data, forcing the client to make several extra requests to different endpoints to assemble one screen.

REST (poorly designed)

  • Many endpoints, one per resource
  • Server decides the response shape
  • Prone to over- and under-fetching
  • Versioning via /v1, /v2 paths

GraphQL

  • One endpoint, client-shaped responses
  • Client asks for exact fields
  • Fetches related data in one request
  • Schema evolution instead of URL versioning
⚠️
Common trap: Over-fetching and under-fetching are opposite problems that appear in the same API. Over-fetching wastes bandwidth returning fields you ignore; under-fetching forces extra round-trips. GraphQL addresses both at once.
🤔
Pause & predict: A mobile screen needs a user's name and the titles of their three latest posts. With REST endpoints /users and /posts, how many requests might that take, and how much of each response would you throw away?

How GraphQL Works: Schema, Types, Queries, Mutations, Resolvers and Subscriptions

A GraphQL server is built around a schema that defines types, queries and mutations; resolvers provide the logic behind each field, and subscriptions add real-time updates.

These are the moving parts you must be able to name and explain.

The building blocks

  • GraphQL Schema — The schema is the core of any GraphQL server. It defines the types, queries and mutations that clients can use to interact with the API.
  • Defining types in GraphQL — Types are the building blocks of a schema. They define the shape of the data that can be queried.
  • Queries — Used to fetch data from a GraphQL server. They define what data the client can request (the read operations in CRUD).
  • Mutations — Used to modify data on the server (create, update and delete operations).
  • Resolvers — Functions that provide the logic for fetching or modifying data for each field in a type.
  • Subscriptions — Enable real-time capabilities in a GraphQL server, allowing clients to subscribe to certain events.
  • Running a GraphQL server — Can be done using libraries such as Apollo Server, Graphene (Python), and others.

What a type and query look like

type Post {
  id: ID!
  title: String!
  body: String
  author: User
}
query {
  post(id: "42") {
    title
    author {
      name
    }
  }
}

The query above asks for only two things — the post's title and its author's name. The server returns exactly that, and nothing else.

🧠
Memory hook: Map the parts to CRUD — Queries = Read, Mutations = Create, Update, Delete, Subscriptions = live updates. Resolvers are the engine underneath every field.
💡
Why it matters: The schema is the contract between client and server. It is typed, so clients know exactly what they can ask for, and the server knows exactly what it must be able to resolve. This is what makes GraphQL self-documenting compared with REST.

GraphQL vs REST: Similarities and Drawbacks

GraphQL and REST share the same architectural principles, transport and data formats — but GraphQL brings its own costs, including a learning curve, the N+1 problem, caching complexity and security risks.

GraphQL is not a free upgrade. You must be able to state both what it shares with REST and where it hurts.

Similarities

AspectShared featureNotes
Architectural principlesStateless, client-server architecture, CRUD operationsBoth follow the same high-level principles
Transport protocolUse HTTP as the transport layerStandard communication method for both
Data transfer formatsJSON (common); REST also supports XMLJSON is the default, but REST allows additional formats

Drawbacks of GraphQL

DrawbackExplanation
Learning curve & implementation complexityRequires schemas, types and resolvers, making setup more complex than REST
Over-fetching / N+1 problemDeeply nested queries can cause N+1 issues if not optimised properly
Performance with large queriesLarge, dynamic queries can degrade server performance
Caching complexityLacks standard HTTP caching; requires custom strategies or tools like Apollo
Security / malicious queriesFlexible queries can be abused (e.g. DoS); requires rate limiting and complexity analysis
Lack of built-in file upload supportNo native file upload support; needs workarounds such as multipart/form-data or graphql-upload
N+1 problem — A performance issue where resolving a list of N items triggers one extra query per item (N+1 total), usually from deeply nested queries that were not optimised.
⚠️
Common trap: Don't claim GraphQL "has no downsides" or "is always faster." It trades REST's rigid endpoints for flexibility, but pays for it with complexity, caching difficulty and new attack surfaces such as malicious deep queries.
✅
Exam tip: When comparing the two, structure your answer in three moves — (1) what they share (stateless client-server over HTTP, JSON, CRUD), (2) what GraphQL fixes (over/under-fetching, endpoint sprawl, flexibility, versioning), (3) what GraphQL costs (learning curve, N+1, caching, security, file uploads).

Choosing Between AWS Services and API Styles

Pick AWS services by the job they do and API style by the trade-off you can accept — managed services remove operational burden, and GraphQL buys flexibility at the cost of complexity.

This final synthesis turns the two halves of the lab into decisions you can defend.

Choosing AWS services

If you need to...Reach for...
Run application code on a virtual serverAmazon EC2 (built from an AMI)
Give resources an isolated networkAmazon VPC
Store relational data without managing serversAmazon RDS
Store files and objects durablyAmazon S3
Deliver content with low latency worldwideAWS CloudFront
Monitor metrics, logs and alertsAWS CloudWatch
Control who can access whatAWS IAM (roles, policies, MFA)
Keep secrets and config encryptedParameter Store (with AWS KMS)
Spread traffic across instancesElastic Load Balancer (with WAF)
Let private resources reach the internet safelyNAT Gateway

Choosing an API style

  • Choose REST when you want simple, cacheable, well-understood endpoints and native file uploads.
  • Choose GraphQL when clients have varied and changing data needs, when over- and under-fetching are hurting performance (especially on mobile), or when you want a single self-documenting endpoint driven by a typed schema.
🧠
Memory hook: Managed beats manual. Every "managed" AWS service (RDS, ELB, CloudFront) exists to remove operational work you would otherwise do yourself — backups, scaling, distribution, health checks.
💡
Why it matters: Architecture is a set of trade-offs. The final-assignment blueprint (one EC2 instance with Nginx + uWSGI, RDS/S3 optional) is the right-sized choice for a student project: enough to be production-like, without the cost and complexity of a full multi-service cloud.

Q1

Name the five key AWS components covered in this lab and give one line on what each does.

What is the difference between an Internet Gateway and a NAT Gateway?

Q3

Why do IAM Roles matter compared with putting AWS credentials in your code?

What does Parameter Store do, and how is its content protected?

Q6

Why is a local db.sqlite3 file unsuitable for version control, and what does RDS do instead?

Q7

List all six reasons to use a remote database service such as Amazon RDS.

Who created GraphQL, when, and name three well-known public APIs that adopted it.

Answer: GraphQL was developed by Facebook in 2012 and released to the public in 2015. Public APIs that adopted it include GitHub, Yelp and Shopify.
Q10

State and explain the four limitations of poorly designed REST APIs.

Answer: (1) Over-fetching and under-fetching — responses return too much or too little data, forcing multiple requests; (2) multiple endpoints — one endpoint per resource such as /users, /posts, /comments, which becomes cumbersome to maintain as the API evolves; (3) lack of flexibility — responses are fixed by the server, so clients have little control and changes may require new endpoints or API modifications; (4) versioning issues — paths like /v1/users and /v2/users lead to bloated and complex API management.
Q11

What are the parts of a GraphQL server, what does each do, and name two libraries used to run one.

Answer: The parts are the schema (defines the types, queries and mutations), types (define the shape of queryable data), queries (read operations), mutations (create, update and delete operations), resolvers (functions providing the logic to fetch or modify data for each field in a type) and subscriptions (real-time event updates). Q12

In what three ways are GraphQL and REST similar?

Answer: They share the same architectural principles (stateless, client-server architecture with CRUD operations), the same transport protocol (HTTP), and the same data transfer format by default (JSON — though REST also supports XML).
Q13

Answer: Learning curve and implementation complexity (schemas, types, resolvers); the N+1 problem with deeply nested queries if not optimised; performance degradation with large dynamic queries; caching complexity because it lacks standard HTTP caching; security risks from malicious queries (e.g. DoS) requiring rate limiting and complexity analysis; and no built-in file upload support, needing workarounds like multipart/form-data or graphql-upload.

When would you choose REST over GraphQL?

Answer: Choose REST when you want simple, well-understood, cacheable endpoints with standard HTTP caching and native file upload support. Choose GraphQL when clients have varied or changing data needs, when over- and under-fetching are hurting performance, or when you want one self-documenting endpoint driven by a typed schema.
