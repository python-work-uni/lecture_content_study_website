Structured Planning and System Design for Web Applications

How to turn a vague web-app idea into a real plan: writing well-formed functional requirements, sketching wireframes, and modelling your database as an entity-relationship diagram using Crow's Foot notation.

Read this first: Almost every failed student project fails at planning, not at coding. This lab gives you three artefacts that remove ambiguity before anyone writes a line of code — a requirements list that states exactly what the system must do, a wireframe that agrees on what it looks like, and an ER diagram that fixes how the data is shaped. Get these right and the implementation almost builds itself.

By the end you will be able to

  • Distinguish a System Requirements Specification (SyRS) from a Software Requirements Specification (SRS) and say which one your project needs.
  • Write a well-formed requirement using the capability–condition–constraint structure.
  • List and apply the IEEE 830 categories of functional requirements to a web application.

  • Read and draw ER diagrams in Crow's Foot notation, including correct cardinality at both ends.
  • Explain multiplicity and optionality and convert a many-to-many relationship into a junction table.
  • Apply the four normal forms (1NF–BCNF) as a checklist for your schema.
  • Set up a project repository with the folder, Git, testing, style and documentation conventions expected this semester.

Why Structured Planning Comes First

A web application is a communication problem before it is a coding problem, and these documents exist to remove ambiguity between the people who build it.

For a new system, you write formal documents before implementation starts. Two are named in industry standards: the System Requirements Specification (SyRS) and the Software Requirements Specification (SRS). Both answer "what should this do?", but at different scopes.

The trap for beginners is assuming you can skip straight to code because the idea "seems obvious". It is not obvious. Different team members picture different products, and that mismatch surfaces only after weeks of work. Planning tools convert private mental models into shared, checkable artefacts.

💡
Why it matters: The cost of a design change grows the longer it is discovered. A misunderstanding caught in a wireframe costs a five-minute conversation; the same misunderstanding caught after implementation costs a rewrite.

Learning objectives for this lab

By the end you should be able to:

  • Identify and write well-formed functional requirements.
  • Create effective wireframes and early design prototypes.
  • Model entity relationships using Crow's Foot notation in ER diagrams.

SyRS vs SRS: Two Scopes of Specification

The SyRS describes the whole system including hardware and processes; the SRS zooms in on the software alone.

These are not competing documents — they sit at different levels. The SyRS outlines the broader system context and objectives. The SRS focuses more narrowly on the software's expected behaviour and features.

This course does not require full SyRS or SRS documents. What it does require is a clear understanding of functional requirements, because that is the skill underlying both.

AspectSRS (IEEE 830)SyRS (IEEE 1233)
ScopeSoftware systemEntire system (software + hardware + process)
AudienceDevelopers, testers, project managersStakeholders, engineers, end-users
PurposeBlueprint for coding, testing, maintenanceDefines full system architecture and interactions
RelationMore detailed, component-levelHigh-level, integrative
✅
There is no single "best" documentation method. What matters is whether you cover the necessary information to make your design valid, complete and ready for implementation. Choose a style, then make sure nothing important is missing.
🧠
Memory hook: SyRS = System-wide (big picture, stakeholders). SRS = Software-only (detailed, developers).

Well-Formed Requirements: Capability, Condition, Constraint

A requirement is only usable if it names what the system does, when it does it, and within what limits.

Defined in IEEE 1233-1998 (SyRS), a well-formed requirement contains three parts:

  • Capability — the core functionality the system must perform.
  • Condition — the preconditions or input required to trigger that capability.
  • Constraint — the boundaries or non-functional requirements the system must follow.

Worked example: user authentication

  • Capability: The system shall authenticate users securely before granting access to sensitive information.
  • Condition: Users must provide valid credentials (username and password).
  • Constraint: Passwords must be stored using industry-standard hashing algorithms with a salt.

Notice how much sharper this is than "the app should have secure login". Each part is independently checkable: you can test whether authentication happens, whether credentials are required, and whether hashing with a salt is used.

⚠️
Common trap: Writing only what you "think is important" is not enough. Good requirements are verifiable, complete, and aligned with a structured approach, no matter which documentation you use. If you cannot write a test that passes or fails against a requirement, it is not finished.
🤔
Pause & predict: Take "The system shall let admins manage users." Which of capability, condition and constraint are present, and which are missing? Rewrite it so all three appear.

Functional Requirements (IEEE 830-1998, §5.3.2)

Functional requirements say what the software must do — its required behaviours in response to inputs and events — and are written as "shall" statements.

In Assignment 1 you extract and write functional requirements for your team's web application. Functional requirements define what the software must do: the required behaviours in response to inputs and events.

The official definition, adapted from IEEE 830-1998, Section 5.3.2:

> Functional requirements should define the fundamental actions that must take place in the software in accepting and processing the inputs and in processing and generating the outputs. These are generally listed as "shall" statements starting with "The system shall…"

The categories to cover

  • a) Validity checks on the inputs
  • b) Exact sequence of operations
  • c) Responses to abnormal situations, including:
  • i. Overflow
  • ii. Communication facilities
  • iii. Error handling and recovery
  • d) Effect of parameters
  • e) Relationship of outputs to inputs, including:
  • i. Input/output sequences
  • ii. Formulas for input to output conversion

It may be appropriate to partition the functional requirements into subfunctions or subprocesses. This does not imply that the software design will also be partitioned that way — grouping requirements for readability is not a commitment about architecture.

ℹ️
How to use this structure: Treat the list above as a template for your team's requirements section. Focus on what the system must do, not how it will be implemented.
✅
Exam tip: The phrase "The system shall…" plus one of the five category letters is a fast way to check completeness. If your requirements list has nothing under (c) error handling, your system is under-specified.

Wireframes and Design Prototyping

A wireframe is a cheap, early visual mockup whose job is to agree on layout, interaction and data flow — not to look pretty.

Wireframes are early-stage visual mockups that illustrate layout, user interaction, and data flow within a website or application. They are not final designs. They are tools that help your team:

  • Align on layout and structure
  • Plan component interactions
  • Guide front-end development
  • Avoid major design changes later

What makes a wireframe good

A good wireframe is not about artistic quality or detailed styling. What matters is that it is:

  • Consistent — layout, navigation and structure follow a logical pattern.
  • Interactive — pages and components reflect how users will actually interact with the system.
  • Developer-friendly — understandable even to team members who did not design it.

Even low-fidelity sketches can be highly effective. An effective example uses clearly labelled sections, repeating layout patterns, and a user flow that connects across pages. Bright colours are not necessary, but committing to a defined colour scheme early helps enforce consistency and guide future design decisions.

Choosing a prototyping tool

You may use any tool that helps your team collaborate and iterate quickly. Recommended options include Figma, Miro and Lucidchart.

There is no need for a fancy or complex tool. Select one that:

  • Enables rapid prototyping
  • Allows easy changes and flexibility
  • Supports multiple design ideas
  • Can be used without requiring advanced design skills

Later in the project you will revisit the prototype to evaluate UI consistency, component relationships, and how well the wireframe maps to your final implementation.

🧠
Memory hook — the three wireframe tests: C.I.D. — Consistent, Interactive, Developer-friendly.

Use Case-Based Requirements

Use cases describe system behaviour from the user's point of view, connecting user intent to system features.

Use cases describe system behaviour from a user's point of view. They are:

  • Focused on goal-oriented interaction
  • Written as textual scenarios or illustrated via use case diagrams
  • A way to connect user intent to system features

This approach suits teams that want to go beyond static functional lists and explore how users interact with the system in context. A worked reference in the source material is a full use case documentation and description for a Monopoly game.

ℹ️
Note: This is presented as optional reading. It is a complement to functional requirements, not a replacement — functional lists say what the system does, use cases show why a user cares.

ERD Fundamentals: The Four Components

An ERD is the blueprint of your database: it names the things you store, the fields on them, how they connect, and how many of each can connect.

An Entity Relationship Diagram (ERD) models the structure of your database by defining the entities in your system, the relationships between them, and the data associated with each. It is the bridge between your requirements and your actual tables.

ComponentDescription
EntityCore concepts or objects in your system, e.g. User, Product, Booking.
AttributeProperties or fields of an entity. A User might have user_id, email, created_at. Listed inside the entity box.
RelationshipHow entities are connected or interact. E.g. a User books a Product. Shown as lines between entities.
CardinalityHow many instances of one entity relate to another: one-to-one, one-to-many, many-to-many. Marked at the ends of relationship lines.
💡
Why it matters: ERDs communicate both the data structure and the business rules clearly, especially during early system design. A reader can see not just what you store but what your system forbids.
🤔
Pause & predict: For a booking app, name at least three entities, the primary key attribute for each, and one relationship verb phrase connecting two of them.

Crow's Foot Notation: Entities, Attributes, Relationships

Crow's Foot notation shows cardinality and optionality visually at each end of a line, keeping the diagram readable.

This course uses Crow's Foot Notation to draw ER diagrams. Its advantage is that it visually distinguishes the cardinality and optionality of relationships while preserving a clear structure.

Entity and attribute rules

  • An entity is drawn as a rectangle with the entity name as a label.
  • Attributes are listed inside the rectangle.
  • Primary keys are indicated with an asterisk * (primary keys are often prefixed with an asterisk).
  • Ensure attributes are atomic and meaningful.

Relationship rules

  • Represented by a line connecting two entities.
  • A verb phrase should describe the interaction — e.g. places, belongs to, includes.
  • Relationships may be bidirectional or recursive when needed. A recursive relationship is one where an entity relates to itself (for example, an employee managing other employees).
✅
Exam tip: A relationship line without a verb phrase is incomplete. "User — Product" tells a reader nothing; "User books Product" tells them the business rule.

Cardinality: Multiplicity and Optionality

Cardinality answers two separate questions at each end of a line — how many, and is it required?

Cardinality defines how many instances of one entity can relate to another and whether that relationship is required. It is shown at both ends of the connecting line. Cardinality consists of two independent dimensions.

Multiplicity — "how many"

  • Multiplicity of One — exactly one instance is allowed.
  • Multiplicity of Many — multiple instances are allowed.

Optionality — "is it required"

  • Mandatory — the relationship is required (minimum = 1).
  • Optional — the relationship is not required (minimum = 0).

Crow's Foot combines these into four common patterns:

Relationship TypeMeaning
Zero or ManyOptional, any number
One or ManyAt least one
One and Only OneExactly one (mandatory)
Zero or OneOptional, at most one
⚠️
Common trap: Be careful with optionality when designing your project. Incorrect use of optional vs. mandatory relationships is a common mistake. It changes what your system will allow a user to do — or fail to do — at runtime.
🧠
Memory hook: Read a crow's foot end as a sentence with a number pair. The circle means 0 (optional), the bar means exactly 1, and the three-pronged "foot" means many. So circle + foot = "zero or many".

Common Relationship Types in Practice

One-to-one, one-to-many and many-to-many differ not just in counts but in whether either side may be empty.

One-to-One

Each student is assigned exactly one seat, and each seat is assigned to exactly one student. Both ends are mandatory: every student must have a seat, and every seat must be assigned.

One-to-Many

One lecturer can teach many courses, but each course is taught by only one lecturer. A lecturer may teach zero courses, so the relationship from lecturer to course is optional.

Many-to-Many

Each student can enrol in many courses, and each course can have many students. However, a student may enrol in zero courses and a course may have no students, so both sides are optional.

TypeExampleOptionality in the example
One-to-OneStudent ↔ SeatBoth ends mandatory
One-to-ManyLecturer → CourseLecturer side optional (may teach zero)
Many-to-ManyStudent ↔ CourseBoth sides optional

Pause & predict: In a library system, a Book and a Loan — is that one-to-one, one-to-many or many-to-many? Is either end optional? Justify your answer before checking with a teammate.

From Many-to-Many to Junction Tables

A normalised design never leaves a many-to-many relationship as a direct line — it replaces it with a junction table carrying a composite primary key.

A well-normalised ERD can still involve many-to-many relationships conceptually, but they are resolved into an intermediate table. The worked example contains two many-to-many relationships:

  • A student can enrol in many courses, and each course can have many students.
  • An instructor can be assigned to multiple courses, and a course can have multiple instructors.

To achieve a normalised structure, instead of using many-to-many relationships directly, introduce two junction tables:

  • Enrollment connects students to courses.
  • CourseAssignment connects instructors to courses.

Both junction tables include additional attributes (e.g. enrolled_on, assigned_on) and use composite primary keys, allowing flexibility and ensuring data integrity. The extra attributes are the payoff: enrolled_on is a fact about the relationship, not about the student or the course, so it has nowhere else to live.

You may also see attribute data types and constraints (e.g. INT, VARCHAR, NOT NULL, UNIQUE) written into an ERD. These are not strictly required for ER diagrams, but including them improves clarity and communicates your design decisions — especially helpful when preparing the database for implementation.

ℹ️
Note: Many-to-many is a conceptual relationship; the junction table is its physical representation. You still describe the relationship as many-to-many when talking to stakeholders.

Database Design Pitfalls and Quick Checks

A well-designed schema is normalised, easy to extend, and aligned with real-world logic — most student marks are lost on three predictable mistakes.

A well-designed schema should be normalised, easy to extend, and aligned with real-world logic. Watch three areas.

1. Tables and entity structure

  • Make sure each table/entity represents a single real-world concept (e.g. User, Event, Booking).
  • Avoid merging unrelated concepts into one table.
  • Don't forget essential entities — think through your app's domain before you design.

Example mistake: combining users and admins into one table with a role flag, then hardcoding access logic. The offending pattern looks like this:

CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  username VARCHAR(50) NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,
  email VARCHAR(100) NOT NULL,
  role VARCHAR(10) CHECK (role IN ('user', 'admin')) NOT NULL
);
if user.role == 'admin':
    show_admin_panel()
else:
    show_user_dashboard()

This works for small apps but quickly leads to tightly coupled roles and permissions, hard-to-maintain branching logic, and poor separation of concerns. It also makes supporting more complex role-based behaviour difficult later.

2. Keys and relationships

  • Every table should have a primary key (PK).
  • Use foreign keys (FKs) to establish relationships — don't rely on implicit naming.
  • Use junction tables for many-to-many relationships. Each junction table should have two FKs and a composite primary key.

3. Fields, types and constraints

  • Use appropriate data types (e.g. varchar(255) for email, not one type for everything).
  • Define NOT NULL, UNIQUE and other constraints clearly.
  • Avoid vague or incomplete attribute lists — every table should store enough information to support your features.

Quick design check

Before moving on, make sure your database:

  • Has no duplicated or redundant data.
  • Has all important entities and relationships represented.
  • Uses keys and constraints appropriately.
  • Can be explained to others (e.g. via an ERD) clearly and confidently.
✅
Exam tip: You will revisit the design again before implementation, but getting the core structure right early saves trouble later. The quick design check is a fast way to self-assess before submission.

Normalisation from 1NF to BCNF

Normalisation is a sequence of tests, each removing a specific kind of redundancy, culminating in the strict rule that every determinant must be a candidate key.

Relational database design should follow normalisation principles to reduce redundancy and improve data integrity. Apply these progressively.

Normal FormDescription
1NF (First Normal Form)All fields should contain atomic values. No repeating groups or multi-valued attributes.
2NF (Second Normal Form)All non-key attributes must be fully dependent on the entire primary key. Especially important for composite keys.
3NF (Third Normal Form)There should be no transitive dependencies — non-key attributes must not depend on other non-key attributes.
BCNF (Boyce-Codd Normal Form)A stricter version of 3NF. Every determinant must be a candidate key.
⚠️
Common trap: Many-to-many relationships stored directly in one table (e.g. lists or repeated fields) are not in 1NF. Use proper junction tables with composite primary keys to resolve them. This is why the junction-table pattern from the previous section is not merely stylistic — it is a normalisation requirement.
🧠
Memory hook: "Atomic, Full key, Transitive, Candidate" — 1NF checks atomic values, 2NF checks full-key dependency, 3NF checks transitive dependency, BCNF checks candidate-key determinants.

Project Setup and Structure Guidelines

Agree the technical conventions once, early, so onboarding and collaboration do not depend on any single team member's memory.

To prepare for scalable and maintainable development, your team should define and follow a clear set of technical conventions across five areas.

Organise your project

  • Structure folders clearly (e.g. backend/, frontend/, docs/)
  • Use virtual environments and .env files
  • Track dependencies:
  • requirements.txt (Python/Django)
  • package.json (JavaScript/React)

Use Git properly

  • Set up Git with clear commit messages
  • Protect main branches (via GitHub settings) and define rulesets
  • Require pull requests and code reviews

Testing and code quality

  • Include integration testing and unit testing
  • Use test runners (pytest, npm test)
  • Track passing status and coverage

Style guides and standards

  • Follow PEP 8 and Django conventions
  • Use Prettier or ESLint for the frontend
  • Maintain clean import structure and consistent formatting

Documentation

  • Maintain a README.md with setup, team details, and contribution workflow
  • Document API endpoints using Postman, Swagger, or plain Markdown
  • Add in-code comments and developer notes when necessary

Consistent setup and documentation improves onboarding, collaboration, and long-term maintainability.

💡
Why it matters: These conventions are the difference between a project a new teammate can join in an hour and one only its author can run. Assessors on team projects read the repo structure, commit history and README as evidence of process quality.

Glossary

Every term you need to speak this week's language.

System Requirements Specification (SyRS)
A document (IEEE 1233) describing the entire system — software, hardware and process — its architecture and interactions. Its audience is stakeholders, engineers and end-users.
Software Requirements Specification (SRS)
A document (IEEE 830) describing the software system's expected behaviour and features at component level. Its audience is developers, testers and project managers.
Well-formed requirement
A requirement containing capability, condition and constraint, as defined in IEEE 1233-1998.
Capability, condition, constraint
The three parts of a well-formed requirement: capability is the core functionality, condition is the precondition or input that triggers it, and constraint is the boundary or non-functional rule the system must obey.
Functional requirement
A statement of what the software must do — the required behaviours in response to inputs and events — usually written as a "shall" statement beginning "The system shall…".
Wireframe
An early-stage visual mockup illustrating layout, user interaction and data flow; judged on consistency, interactivity and developer-friendliness rather than styling.
Use case
A description of system behaviour from a user's point of view, focused on goal-oriented interaction, written as a textual scenario or drawn as a use case diagram.
Entity Relationship Diagram (ERD)
A model of a database's structure showing entities, their attributes, the relationships between them and the cardinality of those relationships.
Entity
A core concept or object in the system, such as User, Product or Booking, drawn as a labelled rectangle.
Attribute
A property or field of an entity, listed inside the entity rectangle, e.g. user_id, email, created_at; attributes must be atomic and meaningful.
Relationship
A connection between two entities shown as a line and labelled with a verb phrase such as places, belongs to or includes.
Cardinality
How many instances of one entity can relate to another and whether that relationship is required; shown at both ends of a relationship line.
Multiplicity
The "how many" half of cardinality: multiplicity of one (exactly one) or multiplicity of many (multiple).
Optionality
The "required or not" half of cardinality: mandatory means minimum 1, optional means minimum 0.
Crow's Foot Notation
An ER diagram notation that visually distinguishes cardinality and optionality at both ends of a relationship line.
Primary key (PK)
A field that uniquely identifies each row of a table; marked in an ERD with an asterisk and required on every table.
Foreign key (FK)
A field that references the primary key of another table to establish a relationship explicitly, rather than relying on implicit naming.
Junction table
An intermediate table that resolves a many-to-many relationship, containing two foreign keys and a composite primary key plus any relationship-specific attributes.
Normalisation
The process of structuring relational tables to reduce redundancy and improve data integrity, progressing through 1NF, 2NF, 3NF and BCNF.
1NF
First Normal Form: all fields contain atomic values, with no repeating groups or multi-valued attributes.
2NF
Second Normal Form: all non-key attributes are fully dependent on the entire primary key — especially important with composite keys.
3NF
Third Normal Form: no transitive dependencies, meaning non-key attributes must not depend on other non-key attributes.
BCNF
Boyce-Codd Normal Form: a stricter version of 3NF in which every determinant must be a candidate key.

Practice Questions

Q1

What is the difference in scope, audience and purpose between an SyRS and an SRS?

Answer: The SRS (IEEE 830) covers the software system only; its audience is developers, testers and project managers, and its purpose is to be a blueprint for coding, testing and maintenance at component level. The SyRS (IEEE 1233) covers the entire system including hardware and process; its audience is stakeholders, engineers and end-users, and its purpose is to define the full system architecture and interactions at a high, integrative level.
Q2

Name the three parts of a well-formed requirement and define each.

Answer: Capability — the core functionality the system must perform. Condition — the preconditions or input required to trigger that capability. Constraint — the boundaries or non-functional requirements the system must follow. This structure comes from IEEE 1233-1998.
Q3

Rewrite this as a well-formed requirement: "The app should have secure login."

Answer: Capability: The system shall authenticate users securely before granting access to sensitive information. Condition: Users must provide valid credentials (username and password). Constraint: Passwords must be stored using industry-standard hashing algorithms with a salt. The original fails because it is not verifiable — you cannot test "secure" without defining what secure means.
Q4

List the five categories of functional requirements from IEEE 830-1998 §5.3.2.

Answer: (a) Validity checks on the inputs; (b) exact sequence of operations; (c) responses to abnormal situations, including overflow, communication facilities, and error handling and recovery; (d) effect of parameters; (e) relationship of outputs to inputs, including input/output sequences and formulas for input to output conversion. They are generally written as "shall" statements starting "The system shall…".
Q5

True or false: if you partition your functional requirements into subfunctions, your software design must be partitioned the same way. Explain.

Answer: False. Functional requirements may be partitioned into subfunctions or subprocesses for clarity, but this does not imply that the software design will also be partitioned that way. Requirements grouping is about readability, not architecture.
Q6

What three criteria make a wireframe good, and what does NOT matter?

Answer: A good wireframe is consistent (layout, navigation and structure follow a logical pattern), interactive (pages and components reflect how users will interact), and developer-friendly (understandable even to someone who did not design it). Artistic quality and detailed styling do not matter — low-fidelity sketches can be highly effective. A defined colour scheme is useful for enforcing consistency, but bright colours are not necessary.
Q7

What are the four components of an ERD, and how is each drawn or marked?

Answer: Entity — a core concept, drawn as a labelled rectangle. Attribute — a property listed inside the entity box, with primary keys marked by an asterisk. Relationship — a line between entities labelled with a verb phrase such as places or belongs to. Cardinality — marked at both ends of the relationship line, showing multiplicity and optionality.
Q8

Distinguish multiplicity from optionality, and give the minimum value associated with each optionality state.

Answer: Multiplicity is the "how many" dimension — multiplicity of one means exactly one instance is allowed, multiplicity of many means multiple are allowed. Optionality is the "required or not" dimension — mandatory means the relationship is required (minimum = 1), optional means it is not required (minimum = 0). Both are shown at both ends of the connecting line.
Q9

Name the four combined cardinality patterns in Crow's Foot notation and state what each means.

Answer: Zero or Many — optional, any number. One or Many — at least one. One and Only One — exactly one (mandatory). Zero or One — optional, at most one.
Q10

A lecturer can teach many courses and each course is taught by only one lecturer, but a lecturer may teach zero courses. Describe this relationship type and its optionality.

Answer: It is one-to-many. The relationship from lecturer to course is optional because a lecturer may teach zero courses; each course, however, is taught by exactly one lecturer.
Q11

How do you resolve a many-to-many relationship in a normalised design, and what must the resolving table contain?

Answer: Introduce a junction table. It must contain two foreign keys (one to each entity) and a composite primary key made from them. It may also carry attributes that describe the relationship itself, such as enrolled_on or assigned_on. In the worked example, Enrollment connects students to courses and CourseAssignment connects instructors to courses.
Q12

Why is storing a many-to-many relationship as a list or repeated field in a single table a problem?

Answer: Such a table is not in First Normal Form, because 1NF requires all fields to contain atomic values with no repeating groups or multi-valued attributes. The correct fix is a junction table with a composite primary key, which also makes the data easier to query and enforces integrity.
Q13

State the rule for each of 1NF, 2NF, 3NF and BCNF.

Answer: 1NF — all fields contain atomic values, with no repeating groups or multi-valued attributes. 2NF — all non-key attributes are fully dependent on the entire primary key (especially important for composite keys). 3NF — no transitive dependencies; non-key attributes must not depend on other non-key attributes. BCNF — a stricter version of 3NF in which every determinant must be a candidate key.
Q14

What is wrong with combining users and admins into one table with a role flag and branching on that flag in application code?

Answer: It works for small apps but produces tightly coupled roles and permissions, hard-to-maintain branching logic, and poor separation of concerns. It also makes supporting more complex role-based behaviour difficult later. The cleaner approach is to represent roles and permissions as their own concepts rather than hardcoding access logic.
Q15

List the five project setup areas this lab expects your team to define conventions for, with one concrete example from each.

Answer: Organise your project — e.g. backend/, frontend/ and docs/ folders plus .env files and requirements.txt or package.json. Use Git properly — clear commit messages, protected main branch, required pull requests and code reviews. Testing and code quality — integration and unit tests run with pytest or npm test, tracking pass status and coverage. Style guides — PEP 8 and Django conventions, Prettier or ESLint on the frontend. Documentation — a README.md with setup and contribution workflow, API endpoints documented with Postman, Swagger or Markdown.
