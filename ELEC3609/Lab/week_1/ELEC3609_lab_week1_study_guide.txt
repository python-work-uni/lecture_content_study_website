SECTION 2: SyRS vs SRS: The Difference
------------------------------------------------
In software engineering, formal documents such as the **System Requirements Specification (SyRS)** and the **Software Requirements Specification (SRS)** are used to define what a system should do *before* implementation begins.

- **SyRS (IEEE 1233)** — outlines the broader system context and objectives. It covers the entire system (software + hardware + process), is aimed at stakeholders, engineers and end-users, and defines the full system architecture and interactions.
- **SRS (IEEE 830)** — focuses more narrowly on the software's expected behaviour and features. It is the blueprint for coding, testing and maintenance, aimed at developers, testers and project managers, and is more detailed and component-level.

| Aspect | SRS (IEEE 830) | SyRS (IEEE 1233) |
| --- | --- | --- |
| Scope | Software system | Entire system (software + hardware + process) |
| Audience | Developers, testers, project managers | Stakeholders, engineers, end-users |
| Purpose | Blueprint for coding, testing, maintenance | Defines full system architecture and interactions |
| Relation | More detailed, component-level | High-level, integrative |

This course does **not** require you to produce full SyRS or SRS documents. What matters is a clear understanding of **functional requirements** — the specific tasks or services the system must perform — because writing them well supports effective system design and project planning.

✅ **Exam Tip:** There is no single "best" documentation method. What matters is whether you cover the necessary information to make your system design valid, complete and ready for implementation.

SECTION 3: Well-Formed Requirements: C-C-C
------------------------------------------------
Defined in **IEEE 1233-1998 (SyRS)**, a well-formed requirement has three parts:

- **Capability** — the core functionality the system must perform.
- **Condition** — the preconditions or input required to trigger that capability.
- **Constraint** — the boundaries or non-functional requirements the system must follow.

### Worked Example: User Authentication
- **Capability:** The system shall authenticate users securely before granting access to sensitive information.
- **Condition:** Users must provide valid credentials (username and password).
- **Constraint:** Passwords must be stored using industry-standard hashing algorithms with a salt.

⚠️ **Common Trap:** Writing *only* what "you think is important" is not enough. Good requirements are **verifiable, complete and aligned** with a structured approach, no matter which documentation format you use.
🧠 **Memory Hook:** **C-C-C** = Capability (what), Condition (when/input), Constraint (limits). Say "what, when, limits".

SECTION 4: Writing Functional Requirements
------------------------------------------------
In Assignment 1 you are expected to extract and write **functional requirements** for your team's web application. These define what the software must do — the required behaviours in response to inputs and events.

The official definition (adapted from **IEEE 830-1998, Section 5.3.2**) states that functional requirements should define the fundamental actions that must take place in the software in accepting and processing inputs, and in processing and generating outputs. They are generally listed as "shall" statements starting with **"The system shall…"**.

Functional requirements include:
- a) **Validity checks** on the inputs.
- b) **Exact sequence of operations.**
- c) **Responses to abnormal situations**, including:
  - i. Overflow.
  - ii. Communication facilities.
  - iii. Error handling and recovery.
- d) **Effect of parameters.**
- e) **Relationship of outputs to inputs**, including:
  - i. Input/output sequences.
  - ii. Formulas for input-to-output conversion.

It may be appropriate to partition the functional requirements into subfunctions or subprocesses. This does **not** imply that the software design will also be partitioned that way.

ℹ️ **Background:** Use this structure to guide your team's requirements section. Your focus should be on **what** the system must do, not **how** it will be implemented.
✅ **Exam Tip:** If a requirement cannot be tested ("the system shall be fast"), it is not well-formed. Rewrite it as something checkable, e.g. a "shall" statement with a measurable behaviour.

SECTION 5: Wireframes & Design Prototyping
------------------------------------------------
**Wireframes** are early-stage visual mockups that illustrate layout, user interaction, and data flow within a website or application. They are not final designs. They are tools to help your team:
- Align on layout and structure.
- Plan component interactions.
- Guide front-end development.
- Avoid major design changes later.

### What Makes a Good Wireframe
A good wireframe is **not** about artistic quality or detailed styling. What matters most is that it is:
- **Consistent** — layout, navigation and structure follow a logical pattern.
- **Interactive** — pages/components reflect how users will actually interact with the system.
- **Developer-friendly** — understandable even to team members who did not design it.

Even low-fidelity sketches can be highly effective. A **defined colour scheme** early on helps enforce consistency and guide future design decisions, though bright colours are not necessary.

### Choosing a Prototyping Tool
Recommended options include **Figma**, **Miro** and **Lucidchart**. There is no need to choose a fancy or complex tool — pick one that:
- Enables rapid prototyping.
- Allows easy changes and flexibility.
- Supports multiple design ideas.
- Can be used without advanced design skills.

Later in the project you will revisit your prototype to evaluate **UI consistency**, **component relationships**, and how well the wireframe maps to your final implementation.

💡 **Why It Matters:** A wireframe is cheap to change and a coded UI is expensive to change. Sketching first prevents expensive rework and gives the whole team one shared picture of the intended product.

SECTION 7: ERD Basics & Components
------------------------------------------------
An **Entity Relationship Diagram (ERD)** models the structure of your database by defining the entities in your system, the relationships between them, and the data associated with each. The four key components are:

| Component | Description |
| --- | --- |
| **Entity** | The core concepts or objects in your system, e.g. User, Product, Booking. |
| **Attribute** | Properties or fields of an entity, e.g. a User might have user_id, email and created_at. Attributes are listed inside the entity box. |
| **Relationship** | How entities are connected or interact, e.g. a User *books* a Product. Shown as lines between entities. |
| **Cardinality** | How many instances of one entity relate to another — one-to-one, one-to-many or many-to-many. Marked at the ends of relationship lines. |

ℹ️ **Background:** ERDs help communicate both **data structure** and **business rules** clearly, especially during early system design.

SECTION 8: Crow's Foot Notation
------------------------------------------------
In this unit you draw ER diagrams using **Crow's Foot Notation**. It visually distinguishes the **cardinality** and **optionality** of relationships while preserving a clear structure.

### Entity and Attribute
- An **entity** is drawn as a **rectangle** with the entity name as a label.
- **Attributes** are listed as fields inside the entity box.
- **Primary keys** are often prefixed with an **asterisk `*`**.
- Attributes should be **atomic** and meaningful.

### Relationship
- Represented by a **line** connecting two entities.
- A **verb phrase** (e.g. *places*, *belongs to*, *includes*) describes the interaction.
- Relationships may be **bidirectional or recursive** when needed.

### Cardinality
**Cardinality** defines how many instances of one entity can relate to another, and whether the relationship is required. It is shown at **both ends** of the connecting line. Cardinality is made of two ideas: **multiplicity** and **optionality**.

💡 **Why It Matters:** Crow's Foot is a compact notation: the shape at each end of a line encodes *how many* and *whether required*. Reading it correctly is the difference between a database that matches reality and one that allows invalid data.
------------------------------------------------
SECTION 9: Cardinality: Multiplicity & Optionality
------------------------------------------------
### Multiplicity
- **Multiplicity of One** — exactly one instance is allowed.
- **Multiplicity of Many** — multiple instances are allowed.

### Optionality
- **Mandatory** — the relationship is required (minimum = 1).
- **Optional** — the relationship is not required (minimum = 0).

### Combined Cardinalities
Crow's Foot combines multiplicity and optionality into four common patterns:

| Relationship Type | Meaning |
| --- | --- |
| **Zero or Many** | Optional, any number |
| **One or Many** | At least one |
| **One and Only One** | Exactly one (mandatory) |
| **Zero or One** | Optional, at most one |

### Common Relationship Types
| Type | Example |
| --- | --- |
| **One-to-One** | Each student is assigned exactly one seat, and each seat is assigned to exactly one student. Both ends are mandatory. |
| **One-to-Many** | One lecturer can teach many courses, but each course is taught by only one lecturer. A lecturer may teach zero courses, so that side is optional. |
| **Many-to-Many** | Each student can enroll in many courses, and each course can have many students. A student may enroll in zero courses and a course may have no students, so both sides are optional. |

⚠️ **Common Trap:** Be careful with optionality when designing your project. Incorrect use of optional vs mandatory relationships is a common mistake — and it is exactly the kind of error that lets bad data into your database.
🧠 **Memory Hook:** Every end of a relationship answers two questions — *How many?* (one/many) and *Must it exist?* (mandatory/optional).

SECTION 10: Worked ERD Example
------------------------------------------------
A well-normalised Crow's Foot ERD for a student/course system includes two **many-to-many** relationships:
- A student can enroll in many courses, and each course can have many students.
- An instructor can be assigned to multiple courses, and a course can have multiple instructors.

To achieve a **normalised** structure, instead of using many-to-many relationships directly, the design introduces two **junction tables**:
- **Enrollment** connects students to courses.
- **CourseAssignment** connects instructors to courses.

Both junction tables include additional attributes (e.g. `enrolled_on`, `assigned_on`) and use **composite primary keys**, which allow flexibility and ensure data integrity.

✅ **Exam Tip:** While Crow's Foot primarily focuses on entity relationships, the example ERD also includes attribute data types and constraints (e.g. `INT`, `VARCHAR`, `NOT NULL`, `UNIQUE`). These are not strictly required for ER diagrams, but including them improves clarity and communicates design decisions — very helpful when preparing the database for implementation.

SECTION 11: Database Design Quality Checks
------------------------------------------------
This lab revisits relational database design not to teach theory, but to help you avoid common design mistakes seen in past projects. A well-designed schema should be **normalised**, **easy to extend**, and **aligned with real-world logic**.

### Tables and Entity Structure
- Each table/entity should represent a **single real-world concept** (e.g. User, Event, Booking).
- Avoid merging unrelated concepts into one table.
- Don't forget essential entities — think through your app's domain before you design.

ℹ️ **Background — Example mistake:** Combining users and admins into one table with a role flag, then hardcoding access logic instead of separating concerns. For example:

```
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  username VARCHAR(50) NOT NULL UNIQUE,
  password_hash TEXT NOT NULL,
  email VARCHAR(100) NOT NULL,
  role VARCHAR(10) CHECK (role IN ('user', 'admin')) NOT NULL
);
```

And in the app logic:

```
if user.role == 'admin':
    show_admin_panel()
else:
    show_user_dashboard()
```

This works for small apps but quickly leads to tightly coupled roles and permissions, hard-to-maintain branching logic, and poor separation of concerns. It also makes supporting more complex role-based behaviour later much harder.

### Keys and Relationships
- Every table should have a **primary key (PK)**.
- Use **foreign keys (FKs)** to establish relationships — don't rely on implicit naming.
- Use **junction tables** for many-to-many relationships. Each junction table should have two FKs and a **composite primary key**.

### Fields, Types and Constraints
- Use **appropriate data types** (e.g. `varchar(255)` for email — not "everything").
- Define **NOT NULL**, **UNIQUE** and other constraints clearly.
- Avoid vague or incomplete attribute lists — every table should store enough information to support your features.

### Quick Design Check
Before moving on, make sure your database:
- Has no duplicated or redundant data.
- Has all important entities and relationships represented.
- Uses keys and constraints appropriately.
- Can be explained to others (e.g. via an ERD) clearly and confidently.

✅ **Exam Tip:** You will revisit your design before implementation, but getting the core structure right early saves trouble later.

SECTION 12: Normalisation: 1NF to BCNF
------------------------------------------------
Relational database design should follow **normalisation principles** to reduce redundancy and improve data integrity. The key normal forms you are expected to apply:

| Normal Form | Description |
| --- | --- |
| **1NF (First Normal Form)** | All fields should contain **atomic values**. No repeating groups or multi-valued attributes. |
| **2NF (Second Normal Form)** | All non-key attributes must be **fully dependent on the entire primary key** — especially important for composite keys. |
| **3NF (Third Normal Form)** | There should be **no transitive dependencies** — non-key attributes must not depend on other non-key attributes. |
| **BCNF (Boyce-Codd Normal Form)** | A stricter version of 3NF. Every determinant must be a candidate key. |

⚠️ **Common Trap:** Many-to-many relationships stored directly in one table (e.g. lists or repeated fields) are **not in 1NF**. Resolve them with proper **junction tables** and composite primary keys.
🧠 **Memory Hook:** **1** atomic, **2** full key, **3** no transitives, **B** every determinant is a candidate key.

SECTION 13: Project Setup & Structure
------------------------------------------------
To prepare for scalable and maintainable development, your team should define and follow a clear set of technical conventions.

### Organise Your Project
- Structure folders clearly (e.g. `backend/`, `frontend/`, `docs/`).
- Use **virtual environments** and `.env` files.
- Track dependencies: `requirements.txt` (Python/Django) and `package.json` (JavaScript/React).

### Use Git Properly
- Set up Git with clear commit messages.
- Protect main branches (via GitHub settings) and define **rulesets**.
- Require **pull requests** and **code reviews**.

### Testing and Code Quality
- Include **integration testing** and **unit testing**.
- Use test runners (`pytest`, `npm test`).
- Track passing status and coverage.

### Style Guides and Standards
- Follow **PEP 8** and Django conventions.
- Use **Prettier** or **ESLint** for the frontend.
- Maintain clean import structure and consistent formatting.

### Documentation
- Maintain a `README.md` with setup, team details and contribution workflow.
- Document API endpoints using **Postman**, **Swagger** or plain Markdown.
- Add in-code comments and developer notes when necessary.

💡 **Why It Matters:** Consistent setup and documentation improves onboarding, collaboration and long-term maintainability. These same conventions reappear in the Week 2 GitHub collaboration lab.

TERMS TO KNOW
================================================
**SRS**: Software Requirements Specification (IEEE 830) — the detailed software-level requirements blueprint.
**SyRS**: System Requirements Specification (IEEE 1233) — the high-level, whole-system requirements document.
**Functional requirement**: A "shall" statement defining what the software must do in response to inputs and events.
**Capability**: The core functionality a requirement says the system must perform.
**Condition**: The precondition or input needed to trigger a capability.
**Constraint**: A boundary or non-functional requirement the system must obey.
**IEEE 830**: The standard describing recommended practice for Software Requirements Specifications.
**IEEE 1233**: The standard describing how to develop a System Requirements Specification.
**Wireframe**: An early-stage, low-fidelity visual mockup of layout, interaction and data flow.
**Prototype**: An early design artefact used to test and communicate design ideas before development.
**Use case**: A goal-oriented description of system behaviour from a user's point of view, textual or diagrammatic.
**ERD**: Entity Relationship Diagram — a model of database entities, relationships and their data.
**Entity**: A core concept or object in the system, drawn as a rectangle (e.g. User, Product, Booking).
**Attribute**: A property or field of an entity, listed inside its box.
**Relationship**: How two entities are connected, shown as a line with a verb phrase.
**Cardinality**: How many instances of one entity relate to another, shown at both ends of a line.
**Multiplicity**: Whether an end of a relationship is one or many.
**Optionality**: Whether an end of a relationship is mandatory (min 1) or optional (min 0).
**Mandatory**: A relationship end that must exist (minimum = 1).
**Optional**: A relationship end that need not exist (minimum = 0).
**Crow's Foot Notation**: An ERD notation that shows cardinality and optionality with fork-like symbols at line ends.
**Primary key (PK)**: The attribute(s) that uniquely identify each row; often marked with an asterisk `*` in an ERD.
**Foreign key (FK)**: An attribute that references the primary key of another table to establish a relationship.
**Junction table**: A table that resolves a many-to-many relationship using two foreign keys.
**Composite primary key**: A primary key made from two or more columns, often the two FKs in a junction table.
**Normalisation**: Organising tables to reduce redundancy and improve data integrity.
**1NF**: First Normal Form — all fields hold atomic values; no repeating groups.
**2NF**: Second Normal Form — all non-key attributes depend on the entire primary key.
**3NF**: Third Normal Form — no transitive dependencies between non-key attributes.
**BCNF**: Boyce-Codd Normal Form — a stricter 3NF where every determinant is a candidate key.
**Transitive dependency**: A non-key attribute depending on another non-key attribute (violates 3NF).
**Candidate key**: Any minimal set of attributes that can uniquely identify a row.
**PEP 8**: The official Python style guide, required for clean Python/Django code.
**requirements.txt**: The file listing Python package dependencies (Python/Django projects).
**package.json**: The file listing JavaScript/React dependencies.
**README.md**: The repository front page documenting setup, team details and contribution workflow.
**Ruleset**: A GitHub setting controlling what can be pushed and merged into a protected branch.
**Integration test**: A test verifying multiple components work together.
**Unit test**: A test verifying a single unit of code in isolation.
**Code review**: Peer checking of a pull request before it is merged.

WORKED EXAMPLES
================================================
### Example 1: Rewriting a vague requirement
Vague: "The login page should be secure." Rewrite using C-C-C:
- **Capability:** The system shall authenticate users securely before granting access to sensitive information.
- **Condition:** Users must provide valid credentials (username and password).
- **Constraint:** Passwords must be stored using industry-standard hashing algorithms with a salt. The rewritten version is testable and complete, which is exactly what IEEE 1233 asks for.

### Example 2: Choosing the right cardinality
- **Student ↔ Seat:** each student has exactly one seat and each seat one student → **One and Only One** at both ends (one-to-one, mandatory).
- **Lecturer ↔ Course:** one lecturer teaches many courses, each course has one lecturer, and a lecturer may teach zero courses → **One-to-Many** with an optional lecturer end.
- **Student ↔ Course:** a student takes many courses and a course has many students, both optional → **Many-to-Many**.

### Example 3: Turning many-to-many into junction tables
Instead of drawing a direct Student↔Course many-to-many line, create a junction table:
- **Enrollment** holds the student FK and the course FK as a **composite primary key**, plus extra attributes such as `enrolled_on`.
- **CourseAssignment** does the same for Instructor↔Course with `assigned_on`. This makes the schema normalised and lets you attach data to the relationship itself.

### Example 4: Spotting the users-and-admins anti-pattern
A single `users` table with a `role` column (`CHECK (role IN ('user','admin'))`) and app logic branching on `user.role` looks fine for a small app, but it tightly couples roles and permissions, creates hard-to-maintain branching logic, and breaks separation of concerns. Separate the concerns instead of overloading one table.

### Example 5: The quick design check
Before you finish your ERD, run through the checklist: no duplicated/redundant data; all important entities and relationships represented; keys and constraints used appropriately; and you can explain the whole design to a teammate using the ERD alone.
