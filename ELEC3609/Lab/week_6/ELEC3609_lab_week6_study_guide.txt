SECTION 1: HTTP Recap: Stateless by Design
------------------------------------------------
**HTTP (HyperText Transfer Protocol)** governs communication between a client and a server. It is
**stateless**, meaning **each request is independent** and the server **does not retain memory of previous interactions**.

**Client–server model:** the client (a browser or app) initiates a request, and the server processes and responds. Each HTTP interaction is isolated; the server keeps no knowledge of earlier requests **unless external mechanisms such as cookies or sessions are used**.

**OSI model:** the OSI model describes **seven layers** of network communication. HTTP runs at the **application layer** — the topmost level — while actual data transmission is handled by the
**transport layer** (usually **TCP**). The layers are independent: HTTP focuses on content logic, while TCP ensures reliable delivery. Protocols like HTTP, FTP and DNS operate at the application layer, which handles **what** is communicated (web pages, data formats), not **how** it is sent.

**HTTP methods and status codes:**

| HTTP Method | Description | Status Code | Meaning |
| --- | --- | --- | --- |
| GET | Retrieve data | 200 | OK (Success) |
| POST | Submit new data | 404 | Not Found |
| PUT | Replace existing data | 500 | Internal Server Error |
| DELETE | Remove data | 403 | Forbidden |
| PATCH | Partially update data | 301 | Moved Permanently |

**Headers** are metadata sent with requests and responses. Common examples:

- **Content-Type: application/json** — defines the format of the request or response body.
- **Set-Cookie** — manages state across stateless HTTP.
- **Authorization** — carries access credentials or tokens.

💡 **Why It Matters:** Everything that follows in this lab exists *because* HTTP forgets you between requests. Cookies and sessions are the workaround.

SECTION 2: Cookies & Sessions: Holding State
------------------------------------------------
All client–server communication goes through HTTP, a **stateless** protocol: one state is not
related to another, so the client must **establish a TCP connection** to the server **every time**
it makes a request. Because the TCP connection is usually **short-lived**, neither endpoint can
rely on it to hold session state.

**What "holding a state" means:** imagine page A requires login. You log in and reach page A. When you move to page B on the same site, **without state-holding you would be prompted to log in again** — every time you visit a different page. Informing the site **who is currently logged in** and storing that information is the basis of a **session** (a semi-permanent exchange of information). Since HTTP cannot hold state by itself, **cookies and sessions** are the techniques used to fix this.

**How sessions + cookies work:**

1. When a user logs in, the server creates a **session ID** — a random token identifying that user.
2. This session ID is stored:
   - as a **cookie** in the user's browser, and
   - on the **server**, linked to the user's actual data (for example, username).
3. On each request, the browser **automatically sends the cookie** (with the session ID).
4. The server **reads the session ID** and retrieves the corresponding data from its storage (memory or database).
5. The server therefore "remembers" who you are **without storing personal data in the browser**.

**Why this is safer:**

- Cookies have a **4KB size limit**.
- Storing sensitive data in cookies is risky — it can be stolen.
- Sessions keep user data on the server, which is **more secure and scalable**.

💡 **Why It Matters:** A cookie is stored **client-side**; the **session data stays on the server**. Only the **session ID** is stored in the cookie, not the actual user data. That separation is what keeps the system secure and efficient.

⚠️ **Common Trap:** Putting real user data (roles, balances, personal details) in a cookie. Only the opaque session ID belongs there.

SECTION 3: Django Session Framework
------------------------------------------------
Django provides full support for **anonymous sessions** and lets you store and retrieve arbitrary
data on a **per-site-visitor** basis. Session data is saved **server-side** and associated with a
**session ID** stored in a cookie on the client side. Unlike cookies, session data is stored securely on the server and can hold more complex data than simple key-value pairs.

- **Session creation:** when an authenticated user accesses the site, Django assigns a unique session ID stored in a cookie called **sessionid**. This cookie is sent with every request.
- **Data storage:** Django stores session data server-side, and you access it via
  **request.session**.
- **Session expiry:** Django automatically manages session expiry based on your configuration.

**Enabling sessions:** sessions are implemented via middleware. They are enabled if
**django.contrib.sessions.middleware.SessionMiddleware** is in your **MIDDLEWARE** setting. The default settings.py created by `django-admin startproject` already has SessionMiddleware activated.

**Configuring sessions:** by default Django stores sessions **in your database** (using the model django.contrib.sessions.models.Session). For some setups it is faster to store them elsewhere:

```python
# settings.py
SESSION_ENGINE = 'django.contrib.sessions.backends.db'     # database-backed sessions (default)
SESSION_ENGINE = 'django.contrib.sessions.backends.cache'  # cached sessions
SESSION_ENGINE = 'django.contrib.sessions.backends.file'   # file-based sessions
```

Few settings control session behaviour:

```python
# settings.py
SESSION_COOKIE_AGE = 1800                  # Set session lifetime to 1800 seconds
SESSION_EXPIRE_AT_BROWSER_CLOSE = True     # Expire the session when the browser closes
```

**Using sessions + context processors:** the lab demonstrates a **context processor** that tracks remaining session time and last login time. A context processor is a function that **returns a dictionary**, and that dictionary is **merged into the context of every template rendering** — letting you add common data available globally to all templates without repeating code in every view.

```python
# til_app/context_processors.py
from django.utils import timezone

def remaining_session_time(request):
    # Check if user is authenticated
    if request.user.is_authenticated and request.session:
        # Get remaining session time
        remaining_time = request.session.get_expiry_age()
        # Store and access last login time
        last_login = request.session.get('last_login', None)
        if not last_login:
            last_login = timezone.localtime(timezone.now()).strftime('%m/%d/%Y - %I:%M%p')
            print(last_login)
            request.session['last_login'] = last_login
        return {'remaining_time': remaining_time, 'last_login': last_login}
    else:
        return {'remaining_time': None, 'last_login': None}
```

💡 **Why It Matters:** Context processors give every template global data (like a session countdown) in one place, so views stay clean and consistent.

SECTION 5: Custom User Model: Settings & Manager
------------------------------------------------
Substituting the default user model is necessary when you need to use **email instead of username**
for login, store **additional fields** such as profile pictures or roles, or customise user
behaviour. It provides flexibility without creating additional models or tables.

**Step 1 — Update settings:** point the **AUTH_USER_MODEL** variable at your custom model:

```python
# settings.py
AUTH_USER_MODEL = 'til_app.CustomUser'
```

This tells Django to use your custom user model instead of the default User model.

⚠️ **Common Trap:** Changing **AUTH_USER_MODEL** *after* you have created database tables is possible but complex. It cannot be done automatically and requires manually fixing the schema, moving data from the old user table, and possibly reapplying migrations. The safe approach is to
**start with a custom user model from the beginning**.

**Step 2 — Create a custom user manager:** a custom manager is needed to properly create user instances, handling both regular users and superusers. Override **create_user** and
**create_superuser** so users are created correctly:

```python
# til_app/models.py
class CustomAccountManager(BaseUserManager):
    def create_user(self, email, password=None):
        if not email:
            raise ValueError(_('You must provide an email address'))
        email = self.normalize_email(email)
        user = self.model(email=email)
        user.set_password(password)
        user.save(using=self._db)
        return user

    def create_superuser(self, email, password=None):
        user = self.create_user(email, password)
        user.is_admin = True
        user.is_superuser = True
        user.save(using=self._db)
        return user
```

ℹ️ **Background:** Django provides **PermissionsMixin**, an abstract model you can include in your user model's class hierarchy. It provides the methods and database fields needed to support Django's permission model.

SECTION 6: Custom User Model: Model & Admin
------------------------------------------------
**Step 3 — Create the custom user model** by inheriting from Django's **AbstractUser** and
**PermissionsMixin**:

```python
# models.py
class CustomUser(AbstractUser, PermissionsMixin):
    username = models.CharField(max_length=30, unique=False)  # Username is not unique
    email = models.EmailField(
        _("email address"),
        max_length=255,
        unique=True,
        error_messages={
            "unique": _("A user with that email address already exists."),
        },
    )
    image_location = models.CharField(
        max_length=255,
        default="/til_app/media/default_user_logo.jpg",
        unique=False, null=True, blank=True
    )
    is_admin = models.BooleanField(
        _("admin status"), default=False,
        help_text=_("Designates whether the user can log into this admin site.")
    )
    is_active = models.BooleanField(
        _("active"), default=True,
        help_text=_("Designates whether this user should be treated as active. "
                    "Unselect this instead of deleting accounts.")
    )
    date_joined = models.DateTimeField(_("date joined"), default=timezone.now)

    objects = CustomAccountManager()

    EMAIL_FIELD = "email"
    USERNAME_FIELD = "email"          # Set the email as the unique identifier
    REQUIRED_FIELDS = []              # Email and password are required by default

    def clean(self):
        super().clean()
        self.email = self.__class__.objects.normalize_email(self.email)

    def __str__(self):
        return self.email             # Display the email instead of the username

    @property
    def is_staff(self):
        return self.is_admin
```

**Step 4 — Update the admin interface** so the Django admin can manage your model. Create a custom admin class that overrides the base UserAdmin's fields:

```python
# admin.py
class UserAdmin(BaseUserAdmin):
    form = UserChangeForm
    add_form = UserCreationForm
    search_fields = ('email', 'username')
    list_filter = ('email', 'username', 'is_active', 'is_admin')
    list_display = ('email', 'username', 'is_active', 'is_admin')
    fieldsets = (
        (None, {'fields': ('email', 'username', 'image_location',)}),
        ('Permissions', {'fields': ('is_admin', 'is_active')}),
    )
    add_fieldsets = (
        (None, {
            'classes': ('wide',),
            'fields': ('email', 'username', 'image_location',
                       'password1', 'password2', 'is_active', 'is_admin')}
        ),
    )
    ordering = ('date_joined',)

admin.site.register(CustomUser, UserAdmin)
```

**Step 5 — Migrate the database.** Every time you update the model schema, run migrations to apply the changes:

```bash
python manage.py makemigrations
python manage.py migrate
```

⚠️ **Common Trap:** If you already have migrations using the default User model, switching to a custom user model can cause **migration conflicts**. Start with the custom model from the beginning, or remove the database file (`rm db.sqlite3`) and reapply migrations.

ℹ️ **Background:** If you only need to *extend* the existing User model rather than substitute it, you can create a **proxy model** based on User, or use a **OneToOneField** to a model holding the extra fields. To authenticate by email that way, you would need a custom authentication backend.

SECTION 7: Registration Form & Validation
------------------------------------------------
Django's **forms framework** simplifies creating, validating and processing forms without
repetitive boilerplate. Its key advantages:

- **Built-in validation** for different form field types, enforcing expected format and constraints.
- **Automatic HTML generation**, including appropriate input types and attributes.
- **Security features** — protection against Cross-Site Scripting (XSS) and Cross-Site Request Forgery (CSRF) by default.
- **Customisable and extendable** — your own validation logic, widgets and error messages.

**Step 1 — Define RegisterForm.** It extends **django.contrib.auth.forms.UserCreationForm** and adds custom validation:

```python
# til_app/forms.py
class RegisterForm(UserCreationForm):
    email = forms.EmailField(max_length=255, help_text="Required add a valid email address.")

    class Meta:
        model = CustomUser
        fields = ("email", "password1", "password2")

    def save(self, commit=True):
        user = super(RegisterForm, self).save(commit=False)
        user.email = self.cleaned_data['email']
        user.username = "user#" + user.email
        if commit:
            user.save()
        return user

    def clean_email(self):
        email = self.cleaned_data["email"].lower()
        # simple uni email validation
        try:
            pattern = r"^[a-z]{4}[0-9]{4}@uni\.sydney\.edu\.au$"
            if not re.fullmatch(pattern, email):
                raise forms.ValidationError(_("Please provide a valid uni email"))
        except Exception:
            raise forms.ValidationError(_("Please provide a valid uni email"))
        # email uniqueness verification
        try:
            CustomUser.objects.get(email=email)
        except CustomUser.DoesNotExist:
            return email
        raise forms.ValidationError(_("A user with that email already exists."))

    def clean_password2(self):
        password1 = self.cleaned_data.get("password1", "")
        password2 = self.cleaned_data["password2"]
        if password1 != password2:
            raise forms.ValidationError(_("The two password fields didn't match."))
        return password2
```

💡 **Why It Matters:** Field-level `clean_<field>` methods validate one field; the pattern of lowercasing the email, checking a regex, then checking uniqueness is a reusable recipe. Note the model-level exception: **CustomUser.DoesNotExist** tells you the email is free.

SECTION 8: Registration View, Template & URLs
------------------------------------------------
**Step 2 — Define the register() view.** It handles **GET** (display the form) and **POST** (process the submission):

```python
# views.py
def register(request):
    form = RegisterForm()
    if request.method == 'POST':
        form = RegisterForm(request.POST)
        if form.is_valid():                     # Check if the form is valid
            user = form.save()                  # Save the user to the database
            # Authenticate the user
            email = form.cleaned_data.get('email')
            password = form.cleaned_data.get('password1')
            user = authenticate(request, email=email, password=password)
            if user is not None:                # Check if authentication was successful
                login(request, user)            # Log the user in
                messages.success(request,
                    'Your account has been successfully created and you are now logged in!')
                return redirect('index')
    return render(request, 'registration/register.html', {'form': form})
```

ℹ️ **Background:** **authenticate()** checks the user's credentials against the authentication backends in Django's settings and returns a User object if valid. **login()** then saves the user's ID in the session using Django's session framework. When a user logs in, the user's ID and the backend used are saved in the session, so the same backend can fetch the user's details on a future request. Typically you use both together.

**Step 3 — Create the registration template** (`til_app/templates/registration/register.html`), which renders the form and handles errors:

```html
<form class="register-form" action="{% url 'register' %}" method="post">
  {% csrf_token %}
  <input type="email" name="email" id="email" placeholder="Email" required autofocus>
  <input type="password" name="password1" class="input_section" id="password" placeholder="Password" required>
  <input type="password" name="password2" class="input_section" id="password" placeholder="Confirm Password" required>
  <button type="submit">Create</button>
  {% for field in form %}
    <p>
      {% for error in field.errors %}
        <p style="color:red">{{ error }}</p>
      {% endfor %}
    </p>
  {% endfor %}
  {% if form.non_field_errors %}
    <div style="color:red"><p>{{ form.non_field_errors }}</p></div>
  {% endif %}
  <p class="message">Already registered? <a href="{% url 'login' %}">Sign In</a></p>
</form>
```

**Step 4 — Update URLs:**

```python

    path('register/', views.register, name='register'),
    # ...,
]
```

Django provides **built-in views** for authentication: **LoginView** for logging in and

SECTION 10: Restricting Access to Views
------------------------------------------------
Django offers several ways to restrict access so only authorised users reach certain parts of
the application. The most common is the **@login_required** decorator:

```python
from django.contrib.auth.decorators import login_required

@login_required
def my_view(request):
    ...
```

**login_required() does the following:**

- If the user is **not** logged in, redirect to **settings.LOGIN_URL**, passing the current absolute path in the query string. Example: `/til_app/login/?next=/til_app/posts/`.
- If the user **is** logged in, execute the view normally — the view code can assume the user is logged in.

💡 **Why It Matters:** The `?next=` parameter preserves where the user wanted to go, so after logging in they land on the right page instead of the homepage.

SECTION 13: Media Config & Overwriting Files
------------------------------------------------
**MEDIA_URL and MEDIA_ROOT** are the two key settings for handling uploads:

- **MEDIA_URL** — the public URL at which uploaded media files can be accessed.
- **MEDIA_ROOT** — the absolute filesystem path to the directory that holds the uploaded files.

```python
# settings.py
# https://docs.djangoproject.com/en/stable/ref/settings/#media-root
MEDIA_URL = '/til_app/media/'
MEDIA_ROOT = os.path.join(BASE_DIR, 'til_app/media')
```

In development, Django serves files directly from the local filesystem. Add this to the project
urls.py:

```python
# til_project/urls.py
urlpatterns = [
    # URL patterns
] + static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT)
```

This tells Django to serve files from MEDIA_ROOT when accessed via MEDIA_URL.

⚠️ **Common Trap:** This is **NOT suitable for production**. Django's development server is not optimised for serving static and media files and can cause security problems and performance/concurrency bottlenecks. In production, serve media and static files through a dedicated web server such as **Nginx or Apache**, or via a **CDN**.

**Default FileSystemStorage behaviour:** Django's default **FileSystemStorage does not overwrite** files with the same name. It **appends a suffix** (such as `_1`, `_2`) to avoid overwriting an existing file, so previously uploaded files are not lost.

If you need to **overwrite** a file with the same name, there are two approaches:

**Method 1 — Manually delete then save:**

```python
# views.py
from django.core.files.storage import FileSystemStorage

storage = FileSystemStorage()

def save_avatar(instance, file):
    file_name = "profile.jpg"
    if storage.exists(file_name):
        storage.delete(file_name)   # Delete existing file
    storage.save(file_name, file)   # Save new file
```

**Method 2 — Create a custom storage class** that overrides **get_available_name()** to prevent the suffix and overwrite instead:

```python
# storage.py
from django.core.files.storage import FileSystemStorage

class OverwriteStorage(FileSystemStorage):
    def get_available_name(self, name, max_length=None):
        # If the filename already exists, remove it as if it was a true file system
        if self.exists(name):
            self.delete(name)
        return name
```

Then use the custom storage class in your models (as a callable, to modify the storage at
runtime) when defining file or image fields:

```python
# models.py
from .storage import OverwriteStorage

class Thing(models.Model):
    image = models.ImageField(
        max_length=SOME_CONST,
        storage=OverwriteStorage(),
        upload_to=image_path
    )
```

SECTION 14: Signals & Method Overrides
------------------------------------------------
Django includes a **signal dispatcher** that helps **decoupled applications get notified when
actions occur elsewhere in the framework**. Signals allow certain **senders** to notify a set of
**receivers** that some action has taken place. They are especially useful when many pieces of code may be interested in the same events. Register signals by importing signals.py in the
**ready** method:

```python
# apps.py
class TilAppConfig(AppConfig):
    default_auto_field = 'django.db.models.BigAutoField'
    name = 'til_app'

    def ready(self):
        import til_app.signals
```

⚠️ **Common Trap:** Signals are **controversial**. Some developers argue they increase complexity and make code harder to trace and maintain; alternatives such as **custom model managers** or
**overriding model methods** are often recommended for more explicit logic. Still, understanding signals gives insight into Django's internal event system.

**Removing an image file when a post is deleted.** The stored file and the database record are
**separate entities** (ImageField stores a varchar path). When a model instance is deleted, Django deletes **only the database record**, not the associated file. There are two fixes.

**Option 1 — Use the post_delete signal:**

```python
# til_app/signals.py
from django.db.models.signals import post_delete
from django.dispatch import receiver

@receiver(post_delete, sender=Post)
def delete_post_image(sender, instance, **kwargs):
    if instance.image:
        instance.image.delete(False)  # Deletes the file without updating/saving the model
```

**Option 2 — Override the delete method in the Post model:**

```python
class Post(models.Model):
    # ... other fields
    def delete(self, *args, **kwargs):
        self.image.delete(save=False)     # Deletes the file via the storage backend
        super().delete(*args, **kwargs)   # Deletes the instance from the database
```

**Enforcing tag rules.** A Post can be associated with **zero, one or many** Tags, and a Tag can apply to **one or many** Posts. By default **ManyToManyField does not support an "at least one" constraint**, so Django will let you create a Tag with no posts. **Tag.clean()** is a validation hook checking for at least one associated Post:

```python
# models.py
from django.core.exceptions import ValidationError

class Tag(models.Model):
    name = models.CharField(max_length=10, unique=True)
    creation_date = models.DateTimeField(auto_now_add=True)

    def clean(self):
        if not self.posts.exists():  # Check if the tag has no associated posts
            raise ValidationError("A tag must be associated with at least one post.")
```

⚠️ **Common Trap:** In the built-in admin/form workflow, **clean() is called before the object is saved**. At that stage the Tag has **no primary key**, so accessing `self.posts` raises a
**ValueError** (not a ValidationError). To enforce the rule at creation time through a form, use a **ModelForm.clean()** method where the posts field is available from cleaned_data.

**Creating a tag in your own workflow:** use **get_or_create()** to fetch or create the Tag and attach it:

```python
# views.py
new_tags = request.POST.get('new_tags', '').split(',')
for tag in new_tags:
    if tag.strip():  # Avoid empty tag inputs
        tag_obj, created = Tag.objects.get_or_create(name=tag.strip())
        post.tags.add(tag_obj)
```

ℹ️ **Background:** get_or_create() calls create(), which does **not** trigger clean() automatically. To enforce Tag.clean() in your own workflow, call it after the object exists (so it already has a primary key), for example `tag_obj.full_clean()` (or `tag_obj.clean()`).

**Deleting unused tags — pre_delete signal.** Trigger a function whenever a Post is deleted, and delete each tag that had only that post:

```python
# signals.py
@receiver(pre_delete, sender=Post)
def delete_unused_tags(sender, instance, **kwargs):
    associated_tags = instance.tags.all()   # Tags associated with the deleted post
    for tag in associated_tags:
        if tag.posts.count() == 1:          # Only current post is linked
            tag.delete()
```

**Deleting unused tags — m2m_changed signal.** Fires when tags are removed from a Post (or posts removed from a Tag), deleting a Tag no longer linked to any Post:

```python
# signals.py
@receiver(m2m_changed, sender=Post.tags.through)
def delete_unused_tags_on_m2m(sender, instance, action, reverse, model, pk_set, **kwargs):
    if not reverse:  # instance = Post, model = Tag, pk_set are Tag IDs
        if action == "pre_clear":
            instance._old_tag_ids = list(instance.tags.values_list("pk", flat=True))
        elif action == "post_remove":
            if pk_set:
                for tag in model.objects.filter(pk__in=pk_set):
                    if tag.posts.count() == 0:
                        tag.delete()
        elif action == "post_clear":
            tag_ids = getattr(instance, "_old_tag_ids", [])
            if tag_ids:
                for tag in model.objects.filter(pk__in=tag_ids):
                    if tag.posts.count() == 0:
                        tag.delete()
            if hasattr(instance, "_old_tag_ids"):
                delattr(instance, "_old_tag_ids")
    else:  # reverse=True: instance = Tag, model = Post, pk_set are Post IDs
        if action in ("post_remove", "post_clear"):
            if instance.posts.count() == 0:
                instance.delete()
```

💡 **Why It Matters:** Signals keep related cleanup logic decoupled from the code that triggers it, but the same logic can live in an overridden model method. Know both, and prefer whichever your team finds easier to trace.

================================================
KEY TAKEAWAYS
================================================
1. **HTTP is stateless** — each request is independent and the server remembers nothing without cookies or sessions.
2. **Sessions + cookies hold state** — the server stores data under a session ID; only the ID lives in the browser cookie.
3. **Cookies are limited to 4KB and are risky** — never store sensitive data in them; keep user data server-side.
4. **Django sessions are enabled by SessionMiddleware** — data is accessed via request.session and stored by default in the database.
5. **Context processors inject global template data** — one function returns a dictionary merged into every template context.
6. **Substitute a custom user model for email login** — set AUTH_USER_MODEL and create a custom manager with create_user/create_superuser.
7. **Custom user model order matters** — start with it from the beginning; changing AUTH_USER_MODEL later requires manual migration work.
8. **RegisterForm adds validation** — clean_email checks format and uniqueness; clean_password2 checks the passwords match.
9. **authenticate() + login()** — authenticate checks credentials; login saves the user ID in the session.
10. **Use built-in LoginView and LogoutView** — the login field must still be named "username"; logout must be a POST form with a CSRF token.
11. **@login_required protects views** — it redirects anonymous users to LOGIN_URL with a `?next=` path.
12. **File uploads need ImageField/FileField and request.FILES** — the form template must use enctype="multipart/form-data".
13. **FileSystemStorage never overwrites** — it appends `_1`, `_2`; override with manual delete or a custom OverwriteStorage class.
14. **Signals react to events** — post_delete cleans up files; pre_delete and m2m_changed clean up unused tags, though overrides are a valid alternative.
15. **Cleanup is not automatic** — deleting a model instance deletes the DB record but not the stored file unless you act.

WORKED EXAMPLES
================================================
### Example 1: Tracing a Login Session End to End
1. The user submits the login form to the built-in LoginView (POST with `{% csrf_token %}`).
2. Django authenticates the credentials and calls login(), saving the user's ID and backend in the session.
3. Django creates a **session ID**, stores the session data server-side, and sends a **sessionid** cookie.
4. On the next request the browser automatically sends the cookie; the server reads the ID and retrieves the data.
5. A **context processor** merges global data such as `remaining_time` and `last_login` into every template.
6. A **@login_required** view now runs normally, because the user is recognised.

### Example 2: Custom User Model Migration Conflict
A project already has migrations for the default User model. The team sets
`AUTH_USER_MODEL = 'til_app.CustomUser'` and runs makemigrations, then hits migration conflicts.
The brief's guidance: it is recommended to **start with a custom user model from the beginning**;
otherwise you may need to **remove the database file (`rm db.sqlite3`) and apply migrations** again.

### Example 3: The Orphaned Image File
A Post is deleted, but its image file remains on disk. Why? The stored file and the database record
are **separate entities** (ImageField is stored as a varchar path), and deleting the model deletes
only the database row. Two fixes from the lab:

- Register a **post_delete** receiver that calls `instance.image.delete(False)`.
- **Override delete()** on Post to call `self.image.delete(save=False)` before `super().delete(...)`.

### Example 4: Overwriting an Uploaded Avatar
Uploading a second "profile.jpg" via default FileSystemStorage yields "profile_1.jpg" — the file is
**not** overwritten. To force an overwrite you can either call `storage.delete(file_name)` before `storage.save(...)`, or use a custom **OverwriteStorage** whose `get_available_name()` deletes the existing file and returns the same name.

### Example 5: Enforcing "At Least One Post" per Tag
Tag.clean() raises a ValidationError when `self.posts.exists()` is false. In the admin/form
workflow, however, clean() runs **before** the Tag is saved, so there is no primary key and
`self.posts` raises a **ValueError**. Correct approach: use a **ModelForm.clean()** where the posts
field is available from cleaned_data, or call `tag_obj.full_clean()`/`tag_obj.clean()` after the
tag has been created via get_or_create().

================================================
EXAM FOCUS
================================================
1. Why is HTTP described as stateless, and why does that matter for login? → Answer: Each request is independent and the server retains no memory of earlier requests, so cookies and sessions are needed to remember who is logged in.
2. What exactly is stored in the cookie and what stays on the server? → Answer: Only the random session ID is stored in the browser cookie; the actual user data stays server-side, linked to that ID.
3. Why are sessions considered safer and more scalable than storing data in cookies? → Answer: Cookies are limited to 4KB and can be stolen; server-side session data is more secure and scalable, and no personal data is kept in the browser.
4. How are Django sessions enabled and where is session data accessed? → Answer: Via django.contrib.sessions.middleware.SessionMiddleware in MIDDLEWARE; data is accessed through request.session.
5. What is a context processor and what does the TIL example return? → Answer: A function returning a dictionary merged into every template context; the example returns remaining_time and last_login.
6. When must you substitute a custom user model rather than extend the default? → Answer: When you need email (instead of username) for login, extra fields such as profile pictures or roles, or customised user behaviour.
7. What does AUTH_USER_MODEL do and what migration risk follows changing it? → Answer: It points Django at the custom user model; changing it after database tables exist can cause migration conflicts and requires manual schema/data fixes, so start with it from the beginning.
8. What do create_user and create_superuser do in the custom manager? → Answer: They correctly create regular users and superusers, normalising the email, setting the password, and flagging admin/superuser status.
9. Why must the login template still use name="username" when login is by email? → Answer: Django's authentication system expects the field name "username"; it maps to the email value while staying compatible with the default LoginView.
10. What does @login_required do for an anonymous user, and what is the `?next=` part? → Answer: It redirects to settings.LOGIN_URL and passes the current absolute path in the query string (e.g. /til_app/login/?next=/til_app/posts/) so the user returns after logging in.
11. Which settings map uploaded files, and how is media served in development? → Answer: MEDIA_URL is the public URL and MEDIA_ROOT the filesystem directory; in development you add static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT) to urls.py.
12. Why is serving media from the development server not suitable for production? → Answer: The development server is not optimised for static/media files and can cause security and performance/concurrency issues; use Nginx, Apache or a CDN.
13. What does FileSystemStorage do when a file with the same name exists? → Answer: It does not overwrite; it appends a suffix such as _1 or _2 to avoid losing the existing file.
14. Why does deleting a Post leave its image on disk, and how do you fix it? → Answer: The file and the DB record are separate entities; Django deletes only the record. Fix with a post_delete signal calling instance.image.delete(False), or override Post.delete() to call self.image.delete(save=False).
15. Why can Tag.clean() raise a ValueError in the admin, and what is the alternative? → Answer: clean() runs before saving, so the Tag has no primary key and self.posts raises ValueError; use a ModelForm.clean() instead or call full_clean()/clean() after creation.
16. What is the difference between get_user_model() and importing CustomUser directly? → Answer: get_user_model() returns the active user model and stays correct if the model is swapped, giving better flexibility and maintainability.
