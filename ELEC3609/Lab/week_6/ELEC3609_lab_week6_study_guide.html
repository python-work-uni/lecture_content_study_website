Django Authentication, Sessions and File Storage

A practical tour of how a Django app remembers who you are. It starts from HTTP's stateless nature, shows how cookies and server-side sessions fake a persistent connection, builds a custom email-based user model with registration, login and logout, adds secure image uploads through the media storage system, and finishes with signals that clean up files and tags when records disappear.

Read this first: HTTP forgets you after every request, so Django uses a two-part trick — a tiny sessionid cookie on the browser and the real user data on the server. Everything in this lab is a variation on that idea: authenticate a user, remember them across requests, attach files to records, and clean up the leftovers when records are deleted.

HTTP Recap

HTTP is stateless — each request is a fresh conversation, so the server has no memory of who you are unless you add one.

HTTP (HyperText Transfer Protocol) governs communication between a client and a server. Its defining property for this lab is that it is stateless: each request is independent, and the server does not retain memory of previous interactions.

Client–Server Model

The client (for example a browser or a mobile app) initiates a request, and the server processes it and responds. They are separate programs, possibly on separate machines, that only ever exchange messages.

Stateless Nature

Each HTTP interaction is isolated. The server does not retain knowledge of earlier requests unless external mechanisms (cookies, sessions) are used to carry that knowledge forward. Without those mechanisms, every request arrives as a stranger.

OSI Model and Layers

The OSI model describes seven layers of network communication. HTTP runs at the application layer — the topmost level — while the actual transmission of bytes is handled by the transport layer, usually TCP. The layers are independent: HTTP focuses on content logic while TCP ensures reliable delivery.

  • The application layer handles what is being communicated (web pages, data formats). Web protocols like HTTP, FTP and DNS live here.
  • The transport layer (for example TCP) handles how it is sent — the reliable delivery of data.
💡
Why it matters: Separating what from how is what lets the same HTTP request travel over Wi-Fi, fibre or 5G unchanged. It also explains why HTTP cannot hold state by itself — state-holding is simply not the application layer's job.

HTTP Methods and Status Codes

Requests carry a method that says what you want to do, and responses carry a status code that says what happened.

HTTP MethodDescriptionStatus CodeMeaning
GETRetrieve data200OK (Success)
POSTSubmit new data404Not Found
PUTReplace existing data500Internal Server Error
DELETERemove data403Forbidden
PATCHPartially update data301Moved Permanently
🧠
Memory hook: Methods are verbs, codes are verdicts. GET reads, POST creates, PUT replaces wholesale, PATCH patches part, DELETE removes. 2xx = fine, 3xx = look elsewhere, 4xx = your fault, 5xx = server's fault.

Headers

Headers are metadata sent alongside requests and responses. Three matter most here:

  • Content-Type: application/json — defines the format of the request or response body.
  • Set-Cookie — the mechanism that manages state across stateless HTTP.
  • Authorization — carries access credentials or tokens.
🤔
Pause & predict: You log in on page A, then click a link to page B on the same site. If HTTP is genuinely stateless, what must travel with that second request for the server to know it is still you?

Cookies and Sessions

A cookie is a small note the browser carries; a session is the server's filing cabinet that the note points to.

All client–server communication runs over HTTP, which is stateless — one interaction is not related to another. Practically, the client must establish a fresh TCP connection to the server for every request. Because that connection is short-lived, neither endpoint can rely on it to hold state.

What "holding a state" means

Imagine a website where page A requires login. You log in and successfully reach page A. You then navigate to page B on the same site. With no state-holding process, you would be prompted to log in again — and again on every subsequent page.

The process of telling the server who is currently logged in, and storing that information, is the basis of a session (a semi-permanent exchange of information). Because HTTP cannot hold state on its own, two techniques solve the problem: cookies and sessions.

How state is held

Web servers combine sessions with cookies:

  1. When a user logs in, the server creates a session ID — a random token identifying that user.
  2. That session ID is stored in two places:
  • as a cookie in the user's browser, and
  • on the server, linked to the user's actual data (for example, their username).
  1. On each subsequent request, the browser automatically sends the cookie containing the session ID.
  2. The server reads the session ID and retrieves the corresponding data from its storage (memory or database).
  3. The server therefore "remembers" who you are without storing any personal data in the browser.
ℹ️
Note: The cookie lives on the client; the session data stays on the server. Only the session ID crosses the wire — never the user's real data.

Why this design is safer

  • Cookies have a 4KB size limit, so they cannot hold rich user data anyway.
  • Storing sensitive data directly in cookies is risky, because cookies can be stolen.
  • Sessions keep user data on the server, which is more secure and more scalable.

Cookie (client-side)

  • Small key–value note stored in the browser
  • 4KB size limit
  • Automatically sent with every request
  • Holds only the session ID, not user data
  • Can be stolen if not protected

Session (server-side)

  • Arbitrary data stored per visitor on the server
  • No practical size limit; can hold complex objects
  • Keyed by the session ID from the cookie
  • Never exposes personal data to the browser
  • More secure and more scalable
🧠
Memory hook: The cookie is the claim ticket; the session is the coat check room. The ticket is worthless without the room, and the room never leaves the building.

Django Sessions in Practice

Django ships sessions as middleware — you enable it, choose where the data lives, then read and write request.session like a dictionary.

Django provides full support for anonymous sessions: it stores and retrieves arbitrary data on a per-site-visitor basis. It saves session data server-side and associates it with a session ID stored in a client-side cookie. Unlike cookies, session data is stored securely on the server and can hold more complex data than simple key–value pairs.

Three behaviours define Django sessions:

  • Session creation: when an authenticated user accesses the site, Django assigns a unique session ID stored in a cookie named sessionid. This cookie is sent with every request.
  • Data storage: Django stores session data server-side; you access it through request.session.
  • Session expiry: Django automatically manages expiry based on your configuration.

Enabling sessions

Sessions are implemented via a piece of middleware. They are enabled when django.contrib.sessions.middleware.SessionMiddleware appears in your MIDDLEWARE setting.

ℹ️
Note: The default settings.py produced by django-admin startproject already has SessionMiddleware activated.

Configuring where session data lives

By default Django stores sessions in your database using the model django.contrib.sessions.models.Session. In some setups it is faster to store session data on the filesystem or in your cache:

# settings.py
SESSION_ENGINE = 'django.contrib.sessions.backends.db'     # database-backed sessions (default)
SESSION_ENGINE = 'django.contrib.sessions.backends.cache'  # cached sessions
SESSION_ENGINE = 'django.contrib.sessions.backends.file'   # file-based sessions

Controlling session behaviour

A few settings give you control over lifetime and persistence:

# settings.py
# https://docs.djangoproject.com/en/stable/ref/settings/#sessions
SESSION_COOKIE_AGE = 1800            # Set session lifetime to 1800 seconds
SESSION_EXPIRE_AT_BROWSER_CLOSE = True  # Expire the session when the browser closes
🧠
Memory hook: 1800 seconds is exactly 30 minutes — the default-style session lifetime used here.

Using sessions: remaining time and last login

The TIL app uses a context processor to expose session data to every template. The function below tracks and displays the remaining session time and the last login time for authenticated users.

# til_app/context_processors.py
from django.utils import timezone

def remaining_session_time(request):
    # Check if user is authenticated
    if request.user.is_authenticated and request.session:
        # Get remaining session time
        remaining_time = request.session.get_expiry_age()

        # Store and access last login time
        last_login = request.session.get('last_login', None)
        if not last_login:
            last_login = timezone.localtime(timezone.now()).strftime('%m/%d/%Y - %I:%M%p')
            print(last_login)
            request.session['last_login'] = last_login

        return {'remaining_time': remaining_time, 'last_login': last_login}
    else:
        return {'remaining_time': None, 'last_login': None}
  • request.session.get_expiry_age() returns how many seconds remain before the session expires.
  • request.session.get('last_login', None) reads a stored value, defaulting to None if absent.
  • Writing request.session['last_login'] = ... persists a value into the server-side session store.
  • The function returns a dictionary, which Django merges into the context of every template render.
💡
Why it matters: A context processor lets you add common data to all templates without repeating the same code in every view. That is exactly what "global data" means in Django templates.
🤔

Django Authentication System Overview

Django separates proving who you are (authentication) from deciding what you may do (authorisation), and both are built into the framework.

Django provides a robust, customisable user authentication system built into its core. It has evolved to serve the most common project needs, handling a wide range of tasks with a careful implementation of passwords and permissions.

ℹ️
Note: Django's authentication system handles both authentication (verifying user identity) and authorisation (determining user permissions).

In the TIL project we create a customised user model so that email is used for authentication and registration instead of a username.

Authentication

  • Answers "who are you?"
  • Verifies identity, usually by checking credentials
  • Performed by authenticate()
  • Example: email + password match a stored user

Authorisation

  • Answers "what may you do?"
  • Determines permissions and access rights
  • Enforced by @login_required, permissions, admin flags
  • Example: only staff may open the admin site

Why substitute the default user model

Substituting the default user model is necessary when you need to:

  • use email instead of username for login,
  • store additional fields such as profile pictures or roles,
  • customise user behaviour more broadly.

It provides flexibility for specific authentication and user-management needs without creating additional models or tables.

⚠️
Common trap: Changing AUTH_USER_MODEL after database tables exist is possible but complex. It cannot be done automatically — it requires manually fixing your schema, moving data out of the old user table, and possibly reapplying migrations. Start with a custom user model from the beginning.

Building a Custom User Model

Five steps: point settings at the model, write a manager, define the model, register it in admin, then migrate.

Step 1: Update settings

In the project's settings.py, define the custom user model by setting AUTH_USER_MODEL to point at it:

# settings.py
AUTH_USER_MODEL = 'til_app.CustomUser'

This tells Django to use CustomUser instead of the default User model.

Step 2: Create a custom user manager

A custom user manager is needed to create user instances correctly. It handles creating both regular users and superusers, and you override create_user and create_superuser to guarantee correct creation.

# til_app/models.py
class CustomAccountManager(BaseUserManager):
    def create_user(self, email, password=None):
        if not email:
            raise ValueError(_('You must provide an email address'))
        email = self.normalize_email(email)
        user = self.model(email=email)
        user.set_password(password)
        user.save(using=self._db)
        return user

    def create_superuser(self, email, password=None):
        user = self.create_user(email, password)
        user.is_admin = True
        user.is_superuser = True
        user.save(using=self._db)
        return user

Note how create_superuser reuses create_user and then sets the admin flags.

Step 3: Create the custom user model

Define the model by inheriting from Django's AbstractUser and PermissionsMixin.

ℹ️
Note: Django provides PermissionsMixin, an abstract model you can include in your user model's class hierarchy. It supplies the methods and database fields needed to support Django's permission model.
# models.py
class CustomUser(AbstractUser, PermissionsMixin):
    username = models.CharField(max_length=30, unique=False)  # Username is not unique
    email = models.EmailField(
        _("email address"),
        max_length=255,
        unique=True,
        error_messages={
            "unique": _("A user with that email address already exists."),
        },
    )
    image_location = models.CharField(
        max_length=255,
        default="/til_app/media/default_user_logo.jpg",
        unique=False,
        null=True,
        blank=True
    )
    is_admin = models.BooleanField(
        _("admin status"),
        default=False,
        help_text=_("Designates whether the user can log into this admin site.")
    )
    is_active = models.BooleanField(
        _("active"),
        default=True,
        # Default is False, can be changed to True based on your needs
        help_text=_("Designates whether this user should be treated as active. "
                    "Unselect this instead of deleting accounts.")
    )
    date_joined = models.DateTimeField(_("date joined"), default=timezone.now)

    objects = CustomAccountManager()

    EMAIL_FIELD = "email"
    USERNAME_FIELD = "email"   # Set the email as the unique identifier
    REQUIRED_FIELDS = []       # Email and password are required by default

    def clean(self):
        super().clean()
        self.email = self.__class__.objects.normalize_email(self.email)

    def __str__(self):
        return self.email  # Display the email instead of the username

    @property
    def is_staff(self):
        return self.is_admin

Key design decisions to remember:

  • email is unique=True, while username is unique=False — the username is deliberately allowed to repeat.
  • USERNAME_FIELD = "email" makes email the unique identifier used for login.
  • objects = CustomAccountManager() wires in the custom manager.
  • is_staff is exposed as a property that simply returns is_admin, keeping the Django admin happy.
🧠
Memory hook: USERNAME_FIELD decides which field logs you in; EMAIL_FIELD tells Django where to send email. Both point at "email" here.

Step 4: Update the admin interface

To manage the custom user model in the Django admin, create a custom admin class:

# admin.py
class UserAdmin(BaseUserAdmin):
    # The forms to add and change user instances
    form = UserChangeForm
    add_form = UserCreationForm

    # The fields to be used in displaying the User model.
    # These override the definitions on the base UserAdmin
    # that reference specific fields on auth.User.
    search_fields = ('email', 'username')
    list_filter = ('email', 'username', 'is_active', 'is_admin')
    list_display = ('email', 'username', 'is_active', 'is_admin')

    fieldsets = (
        (None, {'fields': ('email', 'username', 'image_location',)}),
        ('Permissions', {'fields': ('is_admin', 'is_active')}),
    )
    add_fieldsets = (
        (None, {
            'classes': ('wide',),
            'fields': ('email', 'username', 'image_location',
                       'password1', 'password2', 'is_active', 'is_admin')}
        ),
    )
    ordering = ('date_joined',)

admin.site.register(CustomUser, UserAdmin)
✅
Exam tip: Without this UserAdmin, your CustomUser still exists in the database, but managing it through the admin site would be clunky or impossible.

Step 5: Migrate the database

Every time you update the model schema, run migrations to apply the changes:

python manage.py makemigrations
python manage.py migrate
⚠️
Common trap: If you already have migrations built around the default User model, switching to a custom user model can cause migration conflicts. You may need to remove the database file with rm db.sqlite3 and reapply migrations.

Alternative: extending rather than substituting

If you want extra user information without replacing the user model:

  • create a proxy model based on User, or
  • use a OneToOneField to a separate model holding the extra fields.
ℹ️
Note: With the OneToOneField approach, if you want email-based authentication instead of username, you must write a custom authentication backend.

Registration Form and View

Django's form framework handles rendering, validation and security for you — you subclass UserCreationForm, add rules, and let the view save.

Django provides a powerful form-handling framework that simplifies creation, validation and processing of forms, letting you manage user input without repetitive boilerplate.

Key advantages of Django forms:

  • Built-in validation: validates different field types, ensuring submitted data meets expected formats and constraints.
  • Automatic HTML generation: generates form field HTML with correct input types and attributes, reducing manual coding.
  • Security features: protects against common vulnerabilities such as Cross-Site Scripting (XSS) and Cross-Site Request Forgery (CSRF) by default.
  • Customisable and extendable: you can add your own validation logic, widgets and error messages.

Step 1: Define RegisterForm

RegisterForm extends django.contrib.auth.forms.UserCreationForm, which supplies basic user-creation behaviour, and adds custom email validation.

# til_app/forms.py
class RegisterForm(UserCreationForm):
    email = forms.EmailField(
        max_length=255, help_text="Required add a valid email address.")

    class Meta:
        model = CustomUser
        fields = ("email", "password1", "password2")

    def save(self, commit=True):
        user = super(RegisterForm, self).save(commit=False)
        user.email = self.cleaned_data['email']
        user.username = "user#" + user.email
        if commit:
            user.save()
        return user

    def clean_email(self):
        email = self.cleaned_data["email"].lower()
        # simple uni email validation
        try:
            pattern = r"^[a-z]{4}[0-9]{4}@uni\.sydney\.edu\.au$"
            if not re.fullmatch(pattern, email):
                raise forms.ValidationError(
                    _("Please provide a valid uni email"))
        except Exception:
            raise forms.ValidationError(
                _("Please provide a valid uni email"))

        # email uniqueness verification
        try:
            CustomUser.objects.get(email=email)
        except CustomUser.DoesNotExist:  # Model-level exception
            return email
        raise forms.ValidationError(
            _("A user with that email already exists."))

    def clean_password2(self):
        password1 = self.cleaned_data.get("password1", "")
        password2 = self.cleaned_data["password2"]
        if password1 != password2:
            raise forms.ValidationError(
                _("The two password fields didn't match."))
        return password2

What each piece does:

  • Meta.model = CustomUser and fields = ("email", "password1", "password2") tell the form which model and fields it manages.
  • save() uses commit=False to build the user object first, sets email, and synthesises a username as "user#" + user.email — since the model no longer uses username for login, it can be generated automatically.
  • clean_email() validates the format with the regex ^[a-z]{4}[0-9]{4}@uni\.sydney\.edu\.au$ (four lowercase letters, four digits, then the university domain) and then checks uniqueness.
  • clean_password2() compares password1 and password2 and raises an error if they differ.
🧠
Memory hook: A clean_<field>() method validates one field and must return its cleaned value; clean() validates the form as a whole.

Step 2: Define the register() view

The view handles both GET (display the form) and POST (process the submission):

# views.py
def register(request):
    form = RegisterForm()

    if request.method == 'POST':
        form = RegisterForm(request.POST)
        if form.is_valid():                    # Check if the form is valid
            user = form.save()                 # Save the user to the database

            # Authenticate the user
            email = form.cleaned_data.get('email')
            password = form.cleaned_data.get('password1')
            user = authenticate(request, email=email, password=password)

            if user is not None:               # Check if authentication was successful
                login(request, user)           # Log the user in
                messages.success(request,
                    'Your account has been successfully created and you are now logged in!')
                return redirect('index')

    return render(request, 'registration/register.html', {'form': form})
ℹ️
Note: You typically use authenticate() and login() together. authenticate() checks the credentials against the authentication backends defined in Django's settings and returns a User object if valid. If the credentials are correct, login() saves the user's ID (and the backend used) in the session, allowing the same authentication backend to fetch the user's details on a future request.

Login, Logout and Access Control

Django's built-in LoginView and LogoutView handle the hard parts; you supply templates and redirect settings, then guard views with @login_required.

Django provides built-in views for authentication: LoginView for logging in and LogoutView for logging out. They are robust, secure and easy to integrate.

ℹ️
Note: authenticate() was used in the registration view to log a user in automatically after signup. Unless you are writing your own authentication system, you will normally rely on LoginView/LogoutView instead.

Step 1: Import the built-in views

# urls
from django.contrib.auth.views import LoginView, LogoutView

urlpatterns = [
    path('login/', LoginView.as_view(), name='login'),
    path('logout/', LogoutView.as_view(), name='logout'),
    # ...
]

By default LoginView expects a template named registration/login.html, unless you specify another:

urlpatterns = [
    path('login/', LoginView.as_view(template_name='my_custom_login.html'), name='login'),
    # ...
]

Step 3: Configure login and logout redirects

In settings.py:

  • LOGIN_URL — where users are redirected when they need to log in (e.g. /til_app/login).
  • LOGIN_REDIRECT_URL — where users go after a successful login (e.g. /til_app).
  • LOGOUT_REDIRECT_URL — the landing page after logging out (e.g. /til_app).
# settings.py
LOGIN_URL = "/til_app/login"
LOGIN_REDIRECT_URL = "/til_app"
LOGOUT_REDIRECT_URL = "/til_app"

Step 4: Restrict access to the main page

Django offers several ways to restrict access to views. The most common is the @login_required decorator:

from django.contrib.auth.decorators import login_required

@login_required
def my_view(request):
    ...

login_required() does two things:

  • If the user is not logged in, it redirects to settings.LOGIN_URL, passing the current absolute path in the query string — for example /til_app/login/?next=/til_app/posts/.
  • If the user is logged in, it executes the view normally, so the view code is free to assume the user is authenticated.

Django File Storage and Uploads

FileField and ImageField store files, upload_to decides the folder, and request.FILES carries the upload from the browser to the model.

Django provides a robust file storage system for handling uploads and managing media files such as images and documents. When a user uploads a file, Django can save it to a local directory or to external storage such as AWS S3 or Google Cloud. The TIL app uses the Django File Storage API with local file storage.

Step 1: Set up basic file and image uploads

Django has built-in support for uploads through FileField and ImageField:

# models.py
class Post(models.Model):
    # ...
    image = models.ImageField(upload_to='post_images/', blank=False, null=False)  # ImageField to handle image uploads
ℹ️
Note: Django's ImageField requires the Pillow library and uses FileExtensionValidator to validate that the file extension is supported by Pillow. Pillow is a popular fork of the Python Imaging Library (PIL) that supports opening, manipulating and saving various image formats.

ImageField automatically handles the uploaded image and stores it in the specified folder (post_images/ in this case) within the media directory. The file is uploaded using a form and saved with the model instance.

# forms.py
class PostForm(forms.ModelForm):
    class Meta:
        model = Post
        fields = ['subject', 'contents', 'tags', 'image']

Step 2: Handle file uploads in views

def create_post(request):
    if request.method == 'POST':
        form = PostForm(request.POST, request.FILES)  # request.FILES to handle uploaded files
        if form.is_valid():
            form.save()
            return redirect('post_list')
    else:
        form = PostForm()
    return render(request, 'create_post.html', {'form': form})

The template must use enctype="multipart/form-data" or the file will never reach the server:

<!-- create_post.html -->
<form method="POST" enctype="multipart/form-data">
  {% csrf_token %}
  {{ form.as_p }}
  <button type="submit">Upload Post</button>
</form>
⚠️
Common trap: Forgetting enctype="multipart/form-data" is the classic upload bug — the form submits successfully but request.FILES is empty.
ℹ️
Note: These snippets are a guideline. In the TIL app, post creation is associated with tags and implemented using AJAX.

FileSystemStorage: Collisions and Overwrites

Django never silently overwrites an uploaded file — it appends _1, _2 and so on, unless you override the storage class.

Django's default FileSystemStorage does not overwrite files with the same name. Instead it appends a suffix such as _1, _2, etc. to the filename, ensuring previously uploaded files are not lost when a file with the same name is uploaded again.

If you need to overwrite an existing file with the same name, there are two main approaches.

Method 1: Manually delete then save

Call FileSystemStorage.delete() before saving the new file:

# views.py
from django.core.files.storage import FileSystemStorage

storage = FileSystemStorage()

def save_avatar(instance, file):
    file_name = "profile.jpg"
    if storage.exists(file_name):
        storage.delete(file_name)   # Delete existing file
    storage.save(file_name, file)   # Save new file

Method 2: Create a custom storage class

Extend FileSystemStorage and override get_available_name() so no suffix is appended, guaranteeing same-name files are overwritten:

# storage.py
from django.core.files.storage import FileSystemStorage

class OverwriteStorage(FileSystemStorage):
    def get_available_name(self, name, max_length=None):
        # If the filename already exists, remove it as if it was a true file system
        if self.exists(name):
            self.delete(name)
        return name

You then use this custom storage class in your models, as a callable, when defining file or image fields:

# models.py
from .storage import OverwriteStorage

class Thing(models.Model):
    image = models.ImageField(
        max_length=SOME_CONST,
        storage=OverwriteStorage(),
        upload_to=image_path
    )

Method 1 — delete then save

  • Uses the default FileSystemStorage
  • Explicit exists() check then delete()
  • Logic lives in the view or helper function
  • Fine for one-off cases like avatars

Method 2 — custom storage class

  • Subclasses FileSystemStorage
  • Overrides get_available_name()
  • Logic lives in storage, reusable everywhere
  • Attached via storage= on the field
🧠
Memory hook: get_available_name() is Django asking "what filename may I use?" — return the original name and you force an overwrite.

Media Configuration and Serving Files

MEDIA_URL is the public web address, MEDIA_ROOT is the disk folder, and static() wires the two together for development only.

To handle file uploads, Django needs two key settings:

  • MEDIA_URL — the public URL at which uploaded media files can be accessed.
  • MEDIA_ROOT — the absolute filesystem path to the directory that will hold uploaded files.
# settings.py
# Django Media Files configuration
# https://docs.djangoproject.com/en/stable/ref/settings/#media-root
MEDIA_URL = '/til_app/media/'
MEDIA_ROOT = os.path.join(BASE_DIR, 'til_app/media')

In development, Django serves files directly from the local filesystem. Enable this by appending to the project's urls.py:

# til_project/urls.py
urlpatterns = [
    # URL patterns
] + static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT)

This tells Django to serve files from the MEDIA_ROOT directory when they are requested via MEDIA_URL.

⚠️
Common trap: This is not suitable for production use. Django's development server is not optimised for serving static and media files; it can lead to security problems and performance/concurrency bottlenecks.

In production, media and static files should be served through a dedicated web server such as Nginx or Apache, or via a Content Delivery Network (CDN), which is designed for high-performance delivery and efficient caching.

🧠
Memory hook: URL is where the browser looks, ROOT is where the disk keeps it. static() is the development-only bridge between them.

Signals: Cleaning Up Deleted Files

Signals let decoupled code react to events — here, deleting a post should also delete its image file, because the database row and the file are separate things.

Django includes a signal dispatcher that helps decoupled applications get notified when actions occur elsewhere in the framework. Signals allow certain senders to notify a set of receivers that some action has taken place. They are especially useful when many pieces of code may be interested in the same events.

Signals are registered by importing signals.py in the app config's ready() method:

# apps.py
class TilAppConfig(AppConfig):
    default_auto_field = 'django.db.models.BigAutoField'
    name = 'til_app'

    def ready(self):
        import til_app.signals
⚠️
Common trap: Django signals are powerful but controversial. Some developers argue they increase complexity and make the codebase harder to trace and maintain. Alternatives such as custom model managers or overriding model methods are often recommended for more explicit logic. Still, understanding signals gives insight into Django's internal event system and extensibility.

The problem: files and records are separate

The file stored in the filesystem and the database record are separate entities — ImageField is effectively stored as a varchar path. When a model instance is deleted, Django only deletes the database record, not the associated file. To remove the file, override the delete method or use a signal.

Option 1: Use a signal for post deletion

Use the post_delete signal to delete the file whenever a post is deleted:

# til_app/signals.py
from django.db.models.signals import post_delete
from django.dispatch import receiver

@receiver(post_delete, sender=Post)
def delete_post_image(sender, instance, **kwargs):
    if instance.image:
        instance.image.delete(False)  # Deletes the file without updating or saving the model

Option 2: Override the delete method

class Post(models.Model):
    # ... other fields

    def delete(self, *args, **kwargs):
        # Deletes the file associated with this instance using the storage backend.
        self.image.delete(save=False)  # Without saving the instance again.
        # Calls the parent delete method to delete the instance from the database.
        super().delete(*args, **kwargs)

Signal approach

  • Lives in signals.py, decoupled from the model
  • Fires on any delete, including bulk/admin deletes
  • Multiple receivers can react to the same event
  • Harder to trace where behaviour comes from

Method override

  • Lives directly on the model class
  • Explicit and easy to follow
  • Only runs when that method is called
  • Couples cleanup logic to the model
🤔
Pause & predict: If a post's image is deleted with instance.image.delete(False), why does the argument matter — what would happen if it were True?

Enforcing Tag Rules with clean() and Signals

ManyToManyField cannot express "at least one", so validation and signals step in to keep tags meaningful and tidy.

Recall the relationship between Post and Tag: a Post can be associated with zero, one or many Tags, and a Tag can be applied to one or many Posts.

⚠️
Common trap: By default ManyToManyField() does not support an "at least one" constraint, so Django will not stop you creating a Tag with no associated posts.

Overriding clean() in the Tag model

The clean() method is a validation hook that can check whether a Tag has at least one associated Post:

# models.py
from django.core.exceptions import ValidationError

class Tag(models.Model):
    name = models.CharField(max_length=10, unique=True)
    creation_date = models.DateTimeField(auto_now_add=True)

    def clean(self):
        if not self.posts.exists():  # Check if the tag has no associated posts
            raise ValidationError("A tag must be associated with at least one post.")
⚠️
Common trap: In the built-in Django admin or form workflow, clean() is called before the object is saved. At that stage the Tag has no primary key, so accessing self.posts raises a ValueError — not a ValidationError. To enforce this rule at creation time through a form, use the ModelForm.clean() method instead, where the posts field is available from cleaned_data.

Creating tags in your own workflow

When creating tags during post creation, use get_or_create() to fetch or create the Tag and attach it to the Post:

# views.py
new_tags = request.POST.get('new_tags', '').split(',')
for tag in new_tags:
    if tag.strip():  # Avoid empty tag inputs
        tag_obj, created = Tag.objects.get_or_create(name=tag.strip())
        post.tags.add(tag_obj)
ℹ️
Note: get_or_create() calls create(), which does not trigger clean() automatically. To enforce Tag.clean() in your own workflow, call it after the object exists (so it has a primary key):
tag_obj.full_clean()  # or tag_obj.clean()

This avoids the ValueError caused by a missing primary key while still enforcing your custom rule.

Signal handler for pre_delete

When a Post is deleted, check each associated Tag: if the deleted post was its only link, delete the tag.

# signals.py
@receiver(pre_delete, sender=Post)
def delete_unused_tags(sender, instance, **kwargs):
    # Get all tags associated with the deleted post
    associated_tags = instance.tags.all()
    for tag in associated_tags:
        # Only current post is linked
        if tag.posts.count() == 1:
            tag.delete()
💡
Why it matters: pre_delete runs before the post is gone, so instance.tags.all() still returns the real set of links. If you used post_delete, the association would already be cleared.

Signal handler for m2m_changed

This fires when tags are removed from a Post (or posts removed from a Tag), so a Tag that becomes linked to nothing is deleted:

# signals.py
@receiver(m2m_changed, sender=Post.tags.through)
def delete_unused_tags_on_m2m(sender, instance, action, reverse, model, pk_set, **kwargs):
    if not reverse:  # instance = Post, model = Tag, pk_set are Tag IDs
        if action == "pre_clear":
            instance._old_tag_ids = list(instance.tags.values_list("pk", flat=True))
        elif action == "post_remove":
            if pk_set:
                for tag in model.objects.filter(pk__in=pk_set):
                    if tag.posts.count() == 0:
                        tag.delete()
        elif action == "post_clear":
            tag_ids = getattr(instance, "_old_tag_ids", [])
            if tag_ids:
                for tag in model.objects.filter(pk__in=tag_ids):
                    if tag.posts.count() == 0:
                        tag.delete()
            if hasattr(instance, "_old_tag_ids"):
                delattr(instance, "_old_tag_ids")
    else:  # reverse=True: instance = Tag, model = Post, pk_set are Post IDs
        if action in ("post_remove", "post_clear"):
            if instance.posts.count() == 0:
                instance.delete()

Key mechanics of m2m_changed:

  • sender=Post.tags.through targets the automatically generated join table linking Post and Tag.
  • reverse distinguishes direction: False means the instance is a Post and model is Tag; True means the instance is a Tag and model is Post.
  • action values include pre_clear, post_remove and post_clear.
  • pk_set holds the IDs of the related objects affected by the change.
  • Because post_clear does not supply the removed IDs, the handler caches them on pre_clear in instance._old_tag_ids and cleans them up afterwards.
🧠
Memory hook: pre_clear saves the IDs, post_remove and post_clear sweep for orphaned tags. Forward (reverse=False) guards Posts; reverse guards Tags.

Key Takeaways

If you remember nothing else, remember this.

1

HTTP is stateless: every request is independent, so the server only knows you if cookies and sessions carry that knowledge forward.

2

A session ID is a random token stored both in a browser cookie and on the server; only the ID crosses the wire, keeping personal data server-side and secure.

3

Cookies are limited to 4KB and are stealable, which is why user data lives in server-side sessions that can also hold complex objects.

4

Django sessions are enabled by SessionMiddleware, stored in the database by default, and configurable via SESSION_ENGINE, SESSION_COOKIE_AGE and SESSION_EXPIRE_AT_BROWSER_CLOSE.

5

A context processor returns a dictionary merged into every template's context, which is how the TIL app exposes remaining session time and last login globally.

6

Django separates authentication (who you are) from authorisation (what you may do); a custom user model lets you use email as the login identifier and add fields without extra tables.

7

Substituting the user model takes five steps: set AUTH_USER_MODEL, write CustomAccountManager, define CustomUser(AbstractUser, PermissionsMixin), register a custom UserAdmin, then migrate.

8

RegisterForm extends UserCreationForm, validates the university email format and uniqueness in clean_email(), and compares passwords in clean_password2().

9

authenticate() verifies credentials against configured backends and returns a user; login() stores that user's ID and backend in the session.

10

LoginView and LogoutView provide built-in login and logout, but the login input must be named username even when email is the identifier; logout requires POST plus {% csrf_token %}.

11

@login_required redirects anonymous users to LOGIN_URL with the original path in ?next=, and get_user_model() is the correct way to reference the user model after substitution.

12

ImageField requires Pillow, uploads need request.FILES and enctype="multipart/form-data", and FileSystemStorage avoids overwrites by appending _1, _2 suffixes unless you delete first or override get_available_name().

13

MEDIA_URL is the public URL and MEDIA_ROOT the disk path; serving them via static() works only in development and must be replaced by Nginx, Apache or a CDN in production.

14

Signals such as post_delete, pre_delete and m2m_changed clean up files and orphaned tags, but they trade explicitness for decoupling — custom managers or method overrides are the recommended alternatives.

Glossary

Every term you need to speak this week's language.

HTTP
HyperText Transfer Protocol, the stateless application-layer protocol governing client–server web communication.
Stateless
A property of HTTP meaning each request is independent and the server retains no memory of previous interactions.
Session
A semi-permanent exchange of information that lets a server remember who a user is across multiple stateless requests.
Cookie
A small (max 4KB) piece of data stored in the browser and sent with every request; used to carry a session ID.
Session ID
A random token created at login that identifies a user; stored in the browser cookie and matched to server-side data.
SessionMiddleware
The Django middleware that enables session support; present by default in a freshly generated settings.py.
SESSION_ENGINE
The Django setting choosing where session data is stored: database (default), cache, or filesystem.
Context processor
A function returning a dictionary that Django merges into the context of every template rendering, providing global data.
Authentication
The process of verifying a user's identity, typically by checking credentials such as email and password.
Authorisation
The process of determining what an authenticated user is permitted to do, via permissions and flags.
AUTH_USER_MODEL
The settings value pointing Django at the custom user model to use instead of the default User.
PermissionsMixin
An abstract Django model supplying the methods and database fields needed to support Django's permission model.
USERNAME_FIELD
The model field Django uses as the unique login identifier; set to "email" in CustomUser.
authenticate()
A Django function that checks credentials against configured authentication backends and returns a User object if valid.
login()
A Django function that saves the authenticated user's ID and backend into the session, effectively logging them in.
login_required
A decorator that redirects anonymous users to LOGIN_URL with the original path in the ?next= query parameter.
MEDIA_URL
The public URL prefix at which uploaded media files are served, e.g. '/til_app/media/'.
MEDIA_ROOT
The absolute filesystem path to the directory that stores uploaded files, built from BASE_DIR in the lab.
FileSystemStorage
Django's default storage backend, which avoids overwriting same-name files by appending _1, _2 suffixes.
Signal
Django's dispatcher mechanism letting senders notify receivers when actions such as deletion or m2m changes occur.
post_delete
A Django signal fired after a model instance is deleted, used here to remove the associated image file.
pre_delete
A Django signal fired before deletion, used here because the tag associations still exist at that point.
m2m_changed
A Django signal fired when a many-to-many relationship changes, including pre_clear, post_remove and post_clear actions.
clean()
A validation hook called before saving; in Tag it enforces that a tag has at least one associated post.

Practice Questions

Answer, reveal, then tick “Mastered”. Your progress is saved.
Q1

Why does HTTP being stateless force websites to use cookies and sessions?

Answer: Because each HTTP request is independent and the server keeps no memory of earlier requests, a user would be asked to log in again on every page. Cookies carry a small session ID in the browser, and the server matches that ID to stored user data, creating the illusion of a continuous session across stateless requests.
Q2

Describe the five steps of how a session plus cookie actually keeps you logged in.

Answer: 1) On login the server creates a random session ID. 2) The ID is stored as a cookie in the browser and, on the server, linked to the user's real data. 3) On each request the browser automatically sends the cookie. 4) The server reads the session ID and retrieves the corresponding data from memory or database. 5) The server therefore remembers the user without storing personal data in the browser.
Q3

Which middleware enables Django sessions, what is the default storage backend, and how do you change it?

Answer: django.contrib.sessions.middleware.SessionMiddleware in the MIDDLEWARE setting enables sessions; it is activated by default by django-admin startproject. By default sessions are stored in the database using django.contrib.sessions.models.Session. You change the backend with SESSION_ENGINE, e.g. 'django.contrib.sessions.backends.db' (default), '.cache', or '.file'.
Q4

Why substitute Django's default user model, and what are the five implementation steps?

Answer: Substitution is needed to use email instead of username for login, store extra fields such as profile images or roles, or customise user behaviour, all without creating additional models or tables. The steps are: 1) set AUTH_USER_MODEL = 'til_app.CustomUser' in settings.py; 2) create CustomAccountManager overriding create_user and create_superuser; 3) define CustomUser(AbstractUser, PermissionsMixin) with USERNAME_FIELD = "email" and objects = CustomAccountManager(); 4) register a custom UserAdmin in admin.py; 5) run makemigrations and migrate.
Q5

In RegisterForm, what do clean_email() and clean_password2() each validate, and how does save() produce a username?

Answer: clean_email() lowercases the email, checks it matches the pattern ^[a-z]{4}[0-9]{4}@uni\.sydney\.edu\.au$ using re.fullmatch, and verifies uniqueness by attempting CustomUser.objects.get(email=email) and returning the email only if it raises DoesNotExist. clean_password2() ensures password1 equals password2. save() calls the parent with commit=False, sets the email, and synthesises username as "user#" + user.email before saving.
Q6

What is the difference between authenticate() and login() in the register view?

Answer: authenticate() checks the supplied credentials against the authentication backends defined in Django's settings and returns a User object if they are valid, otherwise None. login() then saves the user's ID and the backend used into the session via Django's session framework, so future requests can fetch the user's details.
Q7

Even though email is the USERNAME_FIELD, what name must the login template's input use, and why?

Answer: It must use name="username". Django's authentication system and the default LoginView expect the field named "username"; the value is still mapped to the email identifier, so this keeps the custom user model compatible with the built-in view.
Q8

What exactly does @login_required do for anonymous versus authenticated users?

Answer: If the user is not logged in, it redirects to settings.LOGIN_URL and passes the current absolute path in the query string, e.g. /til_app/login/?next=/til_app/posts/. If the user is logged in, it executes the view normally, so the view code may assume an authenticated user.
Q9

What does Django's ImageField require, how does a view receive an uploaded file, and what must the HTML form include?

Answer: ImageField requires the Pillow library and uses FileExtensionValidator to check that the extension is supported. The view receives the file by passing request.FILES into the form, e.g. PostForm(request.POST, request.FILES). The HTML form must include enctype="multipart/form-data" (plus {% csrf_token %}).
Q10

What does FileSystemStorage do when a file with the same name is uploaded, and what are the two ways to force an overwrite?

Answer: It does not overwrite; it appends a suffix such as _1 or _2 to avoid losing the existing file. To force overwrite you can either call storage.exists() and then storage.delete() before storage.save(), or subclass FileSystemStorage and override get_available_name() to delete the existing file and return the original name, attaching it via storage=OverwriteStorage() on the field.
Q11

What are MEDIA_URL and MEDIA_ROOT, and why is serving media with static() in urls.py not production-ready?

Answer: MEDIA_URL is the public URL where uploaded media is accessed (e.g. '/til_app/media/'), while MEDIA_ROOT is the absolute filesystem path holding the uploaded files (e.g. os.path.join(BASE_DIR, 'til_app/media')). Appending static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT) lets the development server serve them, but that server is not optimised for static/media files and can cause security problems and performance/concurrency bottlenecks; production should use Nginx, Apache or a CDN.
Q12

Why does deleting a Post not automatically delete its image file, and how do the two cleanup options fix it?

Answer: The stored file and the database record are separate entities — ImageField is effectively a varchar path — so Django deletes only the record and leaves the file behind. Option 1 uses the post_delete signal with @receiver(post_delete, sender=Post) calling instance.image.delete(False). Option 2 overrides Post.delete() to call self.image.delete(save=False) and then super().delete(*args, **kwargs).
Q13

What is the danger of accessing self.posts inside Tag.clean() in the admin/form workflow, and what is the fix?

Answer: clean() runs before the object is saved, so a newly created Tag has no primary key and accessing self.posts raises a ValueError rather than a ValidationError. To enforce the rule at creation time through a form, use ModelForm.clean() where the posts field is available from cleaned_data; if enforcing it manually, call full_clean() or clean() only after the object exists and has a primary key.
Q14

Why is pre_delete used for removing orphaned tags, and what does the m2m_changed handler add?

Answer: pre_delete fires before the post is removed, so instance.tags.all() still returns the real set of associated tags and each can be checked with tag.posts.count() == 1 before deletion. The m2m_changed handler on sender=Post.tags.through covers cases where tags are removed from a post (or posts from a tag) without deleting the post: it uses pre_clear to cache the old tag IDs in instance._old_tag_ids, then post_remove and post_clear to delete any tag that ends up with zero posts, and handles reverse=True by deleting a Tag that has lost all its Posts.
