Starting Your First Django Web App: Projects, Views, URLs and Templates

A hands-on walkthrough of building the TIL (Today I Learned) web app in Django — installing the framework, scaffolding a project and an app, wiring views to URLs, rendering templates with context, serving static CSS/JS, and submitting forms asynchronously with AJAX.

Read this first: Django turns a web request into a response through one repeating loop — the URL dispatcher matches the incoming URL to a view, the view (optionally) reads data from a model, and then renders a template into HTML. Every file, command and snippet in this lab exists to set up or drive that loop, so keep it in mind and the whole framework falls into place.

What Django Is and Why It Exists

Django is a batteries-included Python web framework whose entire purpose is to let you build web applications with less code while keeping the design modular and maintainable.

Django is a Python web framework. A framework is a pre-built skeleton that supplies the common plumbing every web app needs (routing, database access, templating, security) so you only write the parts unique to your site. Django ships with a powerful set of tools out of the box and follows a clean architecture that encourages modular, maintainable design.

Key features

  • Built-in ORM (Object-Relational Mapper). You define your data models entirely in Python and never write raw SQL — the ORM creates and maintains the database tables for you.
  • Database via configuration. You connect your database through a config file and manage schema changes with the makemigrations and migrate commands.
  • MVT architecture (Model–View–Template). Separates business logic from presentation and data access.
  • Declarative URL routing. URLs are defined as readable patterns, which decouples URLs from views and keeps routing flexible.
ORM — An Object-Relational Mapper maps Python classes to database tables, so you manipulate rows as Python objects instead of writing SQL by hand.
💡
Why it matters: The ORM and declarative routing are the two features that most reduce the amount of code you write. Understanding that data is defined as Python classes (not SQL) and URLs are declared as patterns (not hard-coded) is the foundation for everything later in the lab.

The MVT Architecture

Django splits an application into three components — Model (data), View (logic) and Template (presentation) — so that data access, business logic and appearance can change independently.

Django encourages separating an application into three components. Each has a clear purpose and a set of responsibilities.

ComponentTypeDescription
ModelPurposeDefines the structure of your database and the relationships between data types. (Data)
Responsibilities1. Define database schema (tables, fields, relationships); 2. Manage data access and CRUD operations; 3. Provide an API for interacting with the data.
ViewPurposeHandles how data is processed and what gets displayed to the user. (Business Logic)
Responsibilities1. Handle user requests and responses; 2. Fetch or modify data from the Model; 3. Pass data to the Template.
TemplatePurposePresents the data to the user in HTML format. (Presentation)
Responsibilities1. Render HTML using data from the View; 2. Use Django's template language to inject dynamic content; 3. Manage layout, formatting and presentation rules.

MVT vs. MVC and MVP

You may have heard of the MVC (Model–View–Controller) or MVP (Model–View–Presenter) patterns. Django follows a similar idea but uses different terminology: MVT (Model–View–Template). The mapping is the part that trips people up:

  • In Django the View is actually the controller logic — a Python function or class that handles a request.
  • The Template is the presentation layer — what the user actually sees.
  • The framework itself plays the controller role by mapping URLs to views.

Django's naming emphasises a clear split between data (Model), logic (View) and presentation (Template). While not a strict MVP pattern, the structure loosely resembles it. As Django puts it: "It comes down to getting stuff done."

🧠
Memory hook: In Django, the View is the brain (logic), the Template is the face (presentation), and the Model is the memory (data). MVC's "Controller" job is done by Django's URL-mapping machinery, not by a class you write.

How a Request Flows Through Django, and Built-in Security

One request walks a fixed pipeline — dispatcher, view, optional model, template — and Django adds security (CSRF, XSS, hashing) around it by default.

The request lifecycle

Request→URL Dispatcher→View→Model (optional)→View→Template→Response

When a user triggers a request (for example, by clicking a button), Django:

  1. Uses the URL dispatcher to check whether the request matches a defined route.
  2. If it matches, Django calls the corresponding View function.
  3. The View may:
  • Query data from the Model (optional), and
  • Pass that data to a Template.
  1. The Template generates an HTML response, which is returned to the browser.
✅
Key idea: This pattern cleanly separates data access, business logic and presentation. The Model step is optional — a view can return a template immediately without touching the database.

Built-in security features

Django provides several security mechanisms by default, with minimal configuration:

  • CSRF tokens to protect against cross-site request forgery.
  • XSS protection through auto-escaping in templates.
  • Password hashing with salted hashes.
  • Secure cookie and session handling.
ℹ️
Note: These security features are explored in more detail in later labs, but you already use CSRF tokens in this lab's forms.

Installing Django

Django needs Python, and the recommended install path is pip — with a version-compatibility caveat for the course.

Being a Python web framework, Django requires Python. Python includes a lightweight database called SQLite, so you do not need to set up a database just yet. Django is recommended to be installed with pip:

python3 -m pip install Django
⚠️

Creating a Project and Running the Development Server

django-admin startproject generates the project scaffold, and manage.py runserver starts a local development server you can view in a browser.

Django can generate the stub of a project for us. Run:

django-admin startproject til_project

This creates the following directories and files:

til_project/
    manage.py
    til_project/
        __init__.py
        asgi.py
        settings.py
        urls.py
        wsgi.py

What each file is:

  • The outer til_project/ root directory is a container for your project. Its name does not matter to Django — you can rename it to anything.
  • manage.py: a command-line utility that lets you interact with this Django project in various ways.
  • The inner til_project/ directory is the actual Python package for your project. Its name is the Python package name you use to import anything inside it.
  • __init__.py: an empty file that tells Python this directory should be considered a Python package.
  • settings.py: settings/configuration for the project.
  • urls.py: the URL declarations for the project.
  • asgi.py: an entry point for ASGI-compatible web servers to serve your project.
  • wsgi.py: an entry point for WSGI-compatible web servers to serve your project.

Creating a Django Application

A project is the whole website's configuration; an app is a self-contained module of functionality — and this lab uses a single project with a single app.

A Django project can contain multiple applications. A project contains all the components necessary for the website to function. For now we use a single project and a single application: one app is enough for most websites built this semester, and creating multiple apps is not recommended because it causes confusion and requires a richer understanding of Python/Django to correct the import paths.

Project

  • A collection of configuration and apps for a particular website.
  • Can contain multiple apps.
  • Holds the site-wide settings and root URLs.

App

  • A self-contained module of functionality.
  • Can be part of multiple projects.
  • Example: accounts for authentication, transactions for deposits/withdrawals, support for customer service.

For example, in a bank system you might have separate apps like accounts for user authentication, transactions for handling deposits and withdrawals, and support for customer service. This modular approach allows organised, maintainable code where each app can be developed, tested and reused independently within the larger project.

Views and Your First URL

A view is a function that receives a request and returns a response; to reach it from a browser you must map it to a URL in a urls.py file.

In Django a view is a function or a class that receives a web request and returns a web response. It is the core component of Django's MVC/MTV architecture. Let's replace the default Django splash screen with our own index page.

Open til_app/views.py and create the first index view:

# til_app/views.py
from django.http import HttpResponse

def index(request):
    return HttpResponse("Hello, world. You're at the TIL index page.")

This is the most basic view possible in Django. To access it in a browser we must map it to a URL — and for that we need a URL configuration, or "URLconf" for short. These configurations are defined inside each Django app, in Python files named urls.py.

Create til_app/urls.py:

# til_app/urls.py
from django.urls import path
from . import views

urlpatterns = [
    path("", views.index, name="index"),
]

The next step is to configure the global URLconf in the til_project project to include the URLconf defined in til_app.urls. Add an import for django.urls.include in til_project/urls.py and insert an include() in the urlpatterns list:

# til_project/urls.py
from django.contrib import admin
from django.urls import path, include

urlpatterns = [
    path('admin/', admin.site.urls),
    path('til_app/', include('til_app.urls')),
]
ℹ️
Note: You have now wired an index view into the URLconf at localhost:8000/til_app/. If you visit localhost:8000/, you will see a "404 Page not found" error — that is expected, because no view has been set up for the root page.

The URL Dispatcher, path(), include() and Converters

Django matches incoming URLs top-down against declarative patterns, and path converters let you pull dynamic values (like an integer ID) straight out of the URL and into the view.

The URL dispatcher is Django's mechanism for routing incoming HTTP requests to the appropriate view based on the URL. A URL map matches URL patterns in incoming requests to individual view functions.

Mechanism

  • URL Matching: When a request is received, Django starts at the root urls.py and sequentially checks each pattern using a top-down approach.
  • Pattern Resolution: Each pattern is checked in order. If path() matches the beginning of the URL, Django passes control to the corresponding view function — or includes another urls.py module using include().
  • Capturing Parameters: If the pattern includes variables (e.g., <int:id>), these are captured and passed as arguments to the view.
  • No Match: If no pattern matches, Django returns a 404 error.

The path() function

path() maps a specific URL pattern to a view function or class-based view:

# path(route, view, kwargs=None, name=None)
path(
    route='hello/',          # URL pattern string
    view=views.index,        # Callable view function or class-based view
    kwargs=None,             # Optional dictionary of keyword arguments
    name='hello'             # Optional name for the URL pattern
)

The include() function

include() references other URL configuration modules, typically to include URLs from different apps, promoting a modular approach to URL management:

# include(module, namespace=None)
include(
    module='blog_app.urls',  # Module to include, typically another app's urls.py
    namespace=None           # Optional namespace string to prevent name collisions
)

Path converters

Path converters capture parts of a URL and pass them as arguments to the view function. They are used inside path() to extract dynamic segments such as integers, strings or slugs.

ConverterDescription
<str:>Matches any non-empty string (this is the default converter).
<int:>Matches an integer and passes it as an integer.
<slug:>Matches a slug string (letters, numbers, underscores or hyphens).
<uuid:>Matches a universally unique identifier (UUID).
<path:>Matches any non-empty string, including slashes (/).
urlpatterns = [
    path('post/<int:id>/', post_view, name='post_detail'),   # Captures an integer (Post ID)
    path('user/<str:username>/', user_profile_view),         # Captures a string (Username)
]

Regular expressions and re_path()

While path() is usually sufficient, re_path() lets you define URL patterns using regular expressions for more advanced matching:

from django.urls import path, re_path
from . import views

urlpatterns = [
    path("articles/2003/", views.special_case_2003),                 # 2003 only
    re_path(r"^articles/(?P<year>[0-9]{4})/$", views.year_archive),  # yyyy
    re_path(r"^articles/(?P<year>[0-9]{4})/(?P<month>[0-9]{2})/$", views.month_archive),  # yyyy/mm
    re_path(r"^articles/(?P<year>[0-9]{4})/(?P<month>[0-9]{2})/(?P<slug>[\w-]+)/$",
            views.article_detail),                                   # yyyy/mm/my-1st-article
]
✅
Exam tip: Regular expressions are supported via re_path(), but they are not commonly used in modern projects. Prefer designing clearer, more structured URL patterns with path() and converters.

Function-Based Views vs. Class-Based Views

Function-based views are simple, explicit and procedural; class-based views trade simplicity for reusability, inheritance and built-in generic behaviour.

Class-based views (CBVs) provide an alternative way to implement views as Python objects instead of functions. They do not replace function-based views (FBVs), but differ in useful ways:

AspectFunction-Based Views (FBVs)Class-Based Views (CBVs)
DefinitionA view defined as a Python functionA view defined as a Python class
SimplicitySimple and straightforward to implementMore complex, especially for beginners
ExplicitnessLogic is clear and contained in a single functionLogic may be spread across multiple methods and classes
ReusabilityLimited; requires repetition for similar viewsHighly reusable through inheritance and mixins
Code OrganisationProcedural style; all logic in one functionObject-oriented; logic can be organised into methods
Built-in SupportNo built-in support for common patternsOffers built-in generic views like ListView, DetailView, etc.
FlexibilityProvides complete control over view logicProvides structured flexibility through class inheritance
Use Case ExampleSimple form handling or custom logicDisplaying lists, detail views or handling forms with generic views
# Function-Based View
from django.http import HttpResponse

def hello_view(request):
    return HttpResponse("Hello, World!")
# Class-Based View
from django.views import View
from django.http import HttpResponse

class HelloView(View):
    def get(self, request):
        return HttpResponse("Hello, World!")
ℹ️
Note: Django provides many powerful built-in class-based views that can significantly reduce boilerplate code. You are also encouraged to write your own custom class-based views when needed.

Templates and the Template Language

Templates are HTML files with placeholders; you load one, fill a context dictionary, and render it to produce the final HTML response.

Templates are a powerful way to define the structure of your HTML pages. They let you dynamically generate HTML content based on data passed from your views.

First, create a directory called templates inside your Django project or app directory. You can organise templates at the project level or within each app — in the demo we create it under the app. Django will look for templates there.

til_project/
    til_app/
        templates/

Then add the templates directory to the DIRS option in the TEMPLATES setting within settings.py:

# settings.py
import os
from pathlib import Path

BASE_DIR = Path(__file__).resolve().parent.parent

TEMPLATES = [
    {
        'BACKEND': 'django.template.backends.django.DjangoTemplates',
        'DIRS': [os.path.join(BASE_DIR, 'til_app/templates')],
        'APP_DIRS': True,
        'OPTIONS': {
            'context_processors': [
                'django.template.context_processors.debug',
                'django.template.context_processors.request',
                'django.contrib.auth.context_processors.auth',
                'django.contrib.messages.context_processors.messages',
            ],
        },
    },
]
ℹ️
Note: The TEMPLATES setting describes how Django loads and renders templates. The default file configures a DjangoTemplates backend whose APP_DIRS option is True; by convention DjangoTemplates looks for a templates subdirectory in each of the INSTALLED_APPS.
⚠️
Common trap: Starting from Django 5.2, the context processor django.template.context_processors.debug is no longer included by default in newly generated projects. The change was made for better clarity and safety.

Now create an HTML file in the templates directory, e.g. templates/home.html:

<!-- home.html -->
<!DOCTYPE html>
<html lang="en">
<head>
  <title>Home Page</title>
</head>
<body>
  <h1>Welcome, {{ name }}!</h1>
  <p>Now is week {{ week }}</p>
</body>
</html>

Django's templating system generates HTTP responses from these files, which mix HTML with conditional templating logic to inject data and modify the output of a page. Now create the home view in til_app/views.py and wire urls.py to use the template:

# til_app/views.py
from django.http import HttpResponse
from django.template import loader

def view_home(request):
    template = loader.get_template('home.html')
    context = {"name": "ELEC3609", "week": 3}
    return HttpResponse(template.render(context, request))
# til_app/urls.py
urlpatterns = [
    # ...
    path("home", views.view_home, name="home"),
    # ...
]

The example loads home.html and passes it a context — a dictionary mapping template variable names to Python objects. Visit localhost:8000/til_app/home and you should see "Welcome, ELEC3609! Now is week 3".

Use render()

It is a very common idiom to load a template, fill a context and return an HttpResponse with the rendered result. Django provides a shortcut, render():

from django.shortcuts import render

def view_home(request):
    context = {"name": "ELEC9609", "week": 3}
    return render(request, 'home.html', context)
🧠
Memory hook: render(request, template, context) bundles the three steps — get template, fill context, return HttpResponse — into one line.

Static Files: CSS, JavaScript and External Libraries

Static files are the CSS, JS and images your templates link to; Django serves them from a static directory whose URL prefix and search paths you configure in settings.py.

Up to this point our pages have relied on the default styling browsers apply to HTML elements. To add our own styling and interaction:

Custom static files in Django. Similar to templates, you can create a static directory at the project level or within each app — in the demo we put statics within the TIL app:

til_project/
    til_app/
        static/
        templates/

Then define the base URL for serving static files and list the directories where Django should look for them:

# settings.py
STATIC_URL = '/til_app/static/'   # The URL prefix for serving static files.
STATICFILES_DIRS = [os.path.join(BASE_DIR, 'til_app/static')]  # Extra directories Django should search.

To use static files in templates, load the static template tag and reference the files:

{% load static %}

<link rel="stylesheet" type="text/css" href="{% static 'css/style.css' %}">
<script src="{% static 'js/script.js' %}"></script>

Inline styles and scripts

Use inline styles and scripts for simple, page-specific CSS/JS or quick adjustments that should not affect other pages:

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>Inline CSS/JS Example</title>
  <!-- Inline CSS -->
  <style>
    body { background-color: lightblue; }
    h1 { color: white; text-align: center; margin-top: 20px; }
    .custom-button { background-color: darkblue; color: white; padding: 10px 20px; border: none; cursor: pointer; }
  </style>
</head>
<body>
  <h1>Welcome to Django!</h1>
  <button class="custom-button" onclick="showMessage()">Click Me</button>
  <!-- Inline JavaScript -->
  <script>
    function showMessage() { alert("Hello, Django!"); }
  </script>
</body>
</html>

External libraries

You can include external CSS/JS libraries such as Bootstrap or jQuery by linking to them via a CDN (Content Delivery Network). External libraries are ideal for quickly adding well-tested, feature-rich functionality without managing the library files yourself:

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>External CSS/JS Example</title>
  <!-- External CSS (Bootstrap) -->
  <link href="https://cdn.jsdelivr.net/npm/bootstrap@5.3.0/dist/css/bootstrap.min.css" rel="stylesheet">
</head>
<body>
  <div class="container text-center">
    <h1 class="mt-5">Welcome to Django with Bootstrap!</h1>
    <button class="btn btn-primary mt-3" id="bootstrapButton">Click Me</button>
  </div>
  <!-- External JavaScript (Bootstrap and jQuery) -->
  <script src="https://code.jquery.com/jquery-3.6.0.min.js"></script>
  <script src="https://cdn.jsdelivr.net/npm/bootstrap@5.3.0/dist/js/bootstrap.bundle.min.js"></script>
  <!-- Custom JavaScript using jQuery -->
  <script>
    $(document).ready(function(){
      $('#bootstrapButton').click(function(){
        alert("Hello, Django with Bootstrap and jQuery!");
      });
    });
  </script>
</body>
</html>
✅
Exam tip: Using the browser Developer Tools (F12 or Ctrl+Shift+I in Chrome) is one of the best ways to learn and experiment with JavaScript and CSS. It offers immediate feedback, debugging, element inspection, network analysis, mobile emulation and performance monitoring.

AJAX and the Modern Frontend

AJAX updates a page asynchronously — sending data to the server and updating the DOM without a full reload — while modern frontend frameworks extend Django's server-side templating.

AJAX stands for Asynchronous JavaScript and XML. It enables a seamless website experience without the interruption of reloads: AJAX is a technique used in web development to make pages more interactive and responsive without needing to reload the entire page every time a user interacts with it.

While Django provides a powerful server-side templating system, many modern web applications rely on frontend libraries and frameworks like React to create more dynamic, interactive and responsive user interfaces. These tools are widely used to build fast, efficient and maintainable applications.

TechnologyDescription
TypeScriptA superset of JavaScript that adds static typing, helping catch errors early and making code more predictable and easier to refactor.
ReactA JavaScript library for building dynamic, interactive user interfaces, particularly single-page applications, using reusable components.
AngularA full-fledged JavaScript framework by Google for building large-scale, complex web apps with a focus on modularity and maintainability.

Note: AJAX itself is language-agnostic — it is a technique, not a library. In this lab it is implemented with the browser's fetch API.

Building TIL Features: View a Post, View Posts, Upload a Post

Three views bring the TIL app to life — a detail view driven by a path converter, a list view using template tags, and an AJAX upload that returns JSON.

7.1 View a Post

To keep things simple, we define a Post class directly and store a few sample posts in memory in til_app/views.py:

# til_app/views.py
class Post:
    def __init__(self, post_id, author, title, content=None, img=None, comments=None):
        self.post_id = post_id
        self.author = author
        self.title = title
        self.content = content
        self.img = img
        self.comments = comments

post1 = Post(1, 'Jwen', 'First Post', content='Cat', img='https://i.imgur.com/lVlPvCB.gif', comments=['Not bad', 'Cute cat'])
post2 = Post(2, 'Chloe', 'Second Post', img='https://i.imgur.com/6MKyVS4.jpeg')
post3 = Post(3, 'Emma', 'Third Post', img='https://i.imgur.com/PGGk9hn.jpeg')
posts = [post1, post2, post3]
⚠️
Common trap: Defining a Post class inside the view logic and storing posts in runtime memory (a Python list) works for demonstration but is bad design — the data is not persistent and disappears every time the server restarts. The next lab connects Django to a database, defines data models with the ORM, and stores posts persistently.

We then define a basic view function to return a post by ID:

# til_app/views.py
def view_post(request, post_id):
    post = next((p for p in posts if p.post_id == post_id), None)
    if post:
        return render(request, 'post/post.html', {'post': post})
    return render(request, 'post/post.html', {'error': 'Post not found'}, status=404)

To display a list of all posts, first create til_app/templates/post/posts.html:

  <meta name="viewport" content="width=device-width, initial-scale=1.0">
  <title>Posts</title>

  <ul id="postList">

        </a>
        <br>
        <img src="{{ post.img }}" alt="{{ post.title }}" width="100">
      </li>
    {% endfor %}
  </ul>
  <script src="{% static 'script.js' %}"></script>
</body>
</html>

This template introduces Django's template tags using {% %}:

  • {% load static %} loads Django's static file tag system so we can link to CSS/JS.
  • {% for post in posts %} loops through the list of posts passed from the view.
  • {% url 'view a post' post.post_id %} dynamically generates the URL to view a single post based on its ID.
ℹ️
Note: {% %} is used for logic and control structures (loops, loading static files). This is different from {{ }}, which is used to output variables like {{ post.title }} or {{ post.author }}.

Next define a simple view function in til_app/views.py:

# til_app/views.py
def view_posts(request):

    return render(request, 'post/posts.html', context)

And wire it to a URL in til_app/urls.py:

# til_app/urls.py
urlpatterns = [
    path("posts", views.view_posts, name="view posts"),
    # ...
]

Visiting localhost:8000/til_app/posts shows a list of posts with titles, authors and thumbnail images, each linking to its detailed view.

7.3 Upload a Post (AJAX)

To implement a feature with AJAX, start with an HTML form the user fills out. In til_app/templates/post/posts.html, add:

<form id="uploadForm">
  {% csrf_token %}
  <label for="author">Author:</label>
  <input type="text" id="author" name="author"><br>

  <label for="title">Title:</label>
  <input type="text" id="title" name="title"><br>

  <label for="content">Content:</label>
  <textarea id="content" name="content"></textarea><br>

  <label for="img">Image URL:</label>
  <input type="text" id="img" name="img"><br>

  <button type="submit">Submit Post</button>
</form>

<script src="{% static 'script.js' %}"></script>
⚠️
Common trap: The {% csrf_token %} tag ensures the form submission is secure by including a CSRF token. This token must be included in AJAX requests to prevent cross-site request forgery.

Then JavaScript submits the form via AJAX. In til_app/static/script.js:

// AJAX for 'Upload a Post'
document.getElementById('uploadForm').addEventListener('submit', function(event) {
  event.preventDefault();          // Prevent the default form submission (page reload)
  let formData = new FormData(this);  // Create a FormData from user input

  // Send the form data using the Fetch API
  fetch('/til_app/posts/upload', {
    method: 'POST',
    body: formData,
    headers: {
      'X-CSRFToken': formData.get('csrfmiddlewaretoken')  // Include the CSRF token
    },
  })
    .then(response => response.json())  // Parse the JSON response from the server
    .then(data => {
      if (data.custom_error_code === 0) {
        addPostToDOM(data);                              // Dynamically add the new post
        document.getElementById('uploadForm').reset();   // Clear the form fields
      } else if (data.error) {
        alert(data.error);                               // Display any error messages
      }
    })
    .catch(error => console.error('Error:', error));     // Handle any errors
});

On the Django side, add an upload_post view that handles the POST, processes the form data and returns a JSON response:

# til_app/views.py
def upload_post(request):
    if request.method == 'POST':
        author = request.POST.get('author')
        title = request.POST.get('title')
        content = request.POST.get('content')
        img = request.POST.get('img')

        # Bad Design !!!
        post_id = len(posts) + 1
        new_post = Post(post_id, author, title, content, img)
        posts.append(new_post)

        # Send a JSON response back to the client.
        return JsonResponse({
            "custom_error_code": 0,   # custom status code
            "post_id": post_id,
            "author": author,
            "title": title,
            "img": img
        }, status=200)
    return JsonResponse({'error': 'Invalid request'}, status=400)

And wire the view to the URL dispatcher in til_app/urls.py:

# til_app/urls.py
urlpatterns = [
    # ...
    path("posts/upload", views.upload_post, name="upload a post"),
]

How AJAX works in this context

  • Asynchronous: The form submission is handled asynchronously — the page doesn't reload, so the user can keep interacting while the data is processed.
  • Data Exchange: Data (the post) is sent to the server, which processes it, stores the post, and sends back a response indicating success or failure.
  • User Experience: The page remains responsive and the user gets immediate feedback (the new post appears, or an error message is shown).

Visit localhost:8000/til_app/posts to see the behaviour.

Key Takeaways

If you remember nothing else, remember this.

1

Django is a Python web framework that provides an ORM, declarative URL routing, MVT separation and security features out of the box.

2

MVT = Model (data), View (business logic), Template (presentation); Django's "View" is really the controller, and the framework does URL→view mapping.

3

A request flows: URL dispatcher → View → optional Model → Template → Response, with a 404 when no pattern matches.

4

Django is installed with python3 -m pip install Django; course materials target Django 5.2 LTS, and Django 6.0 requires Python 3.12+.

5

django-admin startproject til_project creates the project scaffold; the outer folder name is arbitrary, and manage.py is your command-line utility.

6

python3 manage.py runserver starts the dev server on port 8000 by default (runserver 8888 or runserver 0:8888 change the port/interface), and it auto-reloads on code changes.

7

A project holds configuration and apps; an app is a reusable module of functionality — the lab uses one project with one app (startapp til_app).

8

Views return responses; to reach a view you map it with path(route, view, kwargs, name) inside a urls.py, and include() composes app URLconfs into the project's.

9

Path converters (<int:>, <str:>, <slug:>, <uuid:>, <path:>) capture dynamic URL segments; re_path() supports regex but is rarely needed.

10

FBVs are simple and explicit; CBVs are reusable through inheritance and ship with generic views like ListView and DetailView.

11

Templates live in a templates/ directory; you load one, pass a context dictionary, and render(request, template, context) returns the HTML response.

12

Static files use STATIC_URL + STATICFILES_DIRS and the {% load static %} / {% static '...' %} tags; CSS/JS can be inline, local, or pulled from a CDN.

13

AJAX updates the page without reloading; a Django view handles the POST and returns JsonResponse, and the CSRF token must be sent via the X-CSRFToken header.

Glossary

Every term you need to speak this week's language.

Django
A Python web framework that provides an ORM, URL routing, templating and security tools out of the box, following the MVT pattern.
ORM (Object-Relational Mapper)
Maps Python classes to database tables so you define and query data in Python instead of writing raw SQL.
MVT (Model–View–Template)
Django's architecture separating data (Model), business logic (View) and presentation (Template).
Model
The component that defines the database schema, relationships and data-access API.
View
A Python function or class that receives a request and returns a response; in Django it holds the controller logic.
Template
An HTML file with templating logic that presents data from the view to the user.
URL dispatcher
Django's mechanism that matches an incoming URL to a view by checking patterns top-down.
path()
The function that maps a URL pattern (with optional converters) to a view, accepting route, view, kwargs and name.
include()
References another URLconf module so an app's URLs can be composed into the project's, optionally with a namespace.
Path converter
A token such as <int:> or <str:> that captures a URL segment and passes it to the view as an argument.
re_path()
Defines URL patterns using regular expressions for advanced matching; rarely needed in modern projects.
Function-based view (FBV)
A view written as a plain Python function; simple, explicit and procedural.
Class-based view (CBV)
A view written as a Python class; reusable via inheritance and mixins, with built-in generic views.
manage.py
The command-line utility used to run project commands such as runserver, startapp, makemigrations and migrate.
settings.py
The project's global configuration file controlling apps, database, templates, static files and more.
WSGI / ASGI
Entry points (wsgi.py / asgi.py) for synchronous and asynchronous web servers to serve the project.
Migration
A file generated by makemigrations and applied by migrate that changes the database schema.
Context
A dictionary mapping template variable names to Python objects, passed from the view to the template.
render()
A shortcut that loads a template, fills a context and returns an HttpResponse in one call.
Template variable {{ }}
Double-brace syntax used to output a variable's value in a template, e.g. {{ post.title }}.
Template tag {% %}
Brace-percent syntax used for logic and control structures such as loops and {% load static %}.
CSRF token
A per-request token that protects against cross-site request forgery; included with {% csrf_token %} and sent in AJAX via the X-CSRFToken header.
AJAX
Asynchronous JavaScript and XML — a technique that exchanges data with the server and updates the page without a full reload.
Static files
CSS, JavaScript and images served from a configured directory via STATIC_URL and STATICFILES_DIRS.

Answer, reveal, then tick “Mastered”. Your progress is saved.
Q1

What does MVT stand for, and how does Django's "View" differ from the View in MVC?

Answer: MVT is Model–View–Template: Model = data, View = business logic, Template = presentation. In Django the View actually plays the controller role (a Python function/class handling a request), the Template is the presentation layer, and the framework itself handles the URL-to-view controller mapping.
Q2

Write the exact command to install Django with pip, and the command to create a project named til_project.

Answer: Install: python3 -m pip install Django. Create project: django-admin startproject til_project.
Q3

Name the two files generated by startproject that serve as entry points for web servers, and say which is for synchronous vs asynchronous deployment.

Answer: wsgi.py is the entry point for WSGI-compatible (synchronous) web servers, and asgi.py is the entry point for ASGI-compatible (asynchronous) servers.
Q4

What is the difference between a Django project and a Django app?

Answer: A project is a collection of configuration and apps for a particular website and can contain multiple apps. An app is a self-contained module of functionality that can be reused across multiple projects (e.g. accounts, transactions, support in a bank system).
Q5

Which command creates a new app called til_app, and what file within it holds the views?

Answer: python3 manage.py startapp til_app creates the app; views.py holds the view functions that handle requests and return responses.
Q6

Given the route path("post/<int:post_id>", views.view_post, name="view a post"), what URL would display post 1, and how does the view receive the ID?

Answer: Visiting localhost:8000/til_app/post/1. The <int:post_id> converter captures the integer 1 from the URL and passes it to view_post as the post_id argument.
Q7

List the five common path converters and what each matches.

Answer: <str:> any non-empty string (default); <int:> an integer, passed as an integer; <slug:> a slug (letters, numbers, underscores, hyphens); <uuid:> a universally unique identifier; <path:> any non-empty string including slashes.
Q8

What is the difference between {{ }} and {% %} in Django templates?

Answer: {{ }} outputs a variable's value (e.g. {{ post.title }}), while {% %} is used for logic and control structures such as loops ({% for post in posts %}) and {% load static %}.
Q9

Show the shortest way to render a template with a context in a view.

Answer: Use the render() shortcut: return render(request, 'home.html', context), where context is a dictionary such as {"name": "ELEC3609", "week": 3}.
Q10

In the AJAX upload flow, how is the CSRF token transmitted, and why is it required?

Answer: The token comes from the form's {% csrf_token %} field and is sent in the request headers as X-CSRFToken (read via formData.get('csrfmiddlewaretoken')). It is required to prevent cross-site request forgery, which Django blocks by default.
Q11

What does the upload_post view return on success and on failure, and with what HTTP status codes?

Answer: On success it returns a JsonResponse with custom_error_code: 0 plus the post's id/author/title/img and status=200. If the request is not a POST it returns {'error': 'Invalid request'} with status=400.
Q12

Why is defining the Post class and a Python list of posts inside views.py described as "bad design"?

Answer: Because the data is stored only in runtime memory and is not persistent — it disappears every time the server restarts. The proper approach (covered next lab) is to define data models with Django's ORM and store them in a database.
Q13

Which two settings control where Django finds static files, and which template tag loads their reference system?

Answer: STATIC_URL sets the URL prefix for serving them and STATICFILES_DIRS lists the directories to search. The {% load static %} tag loads the static tag system, after which {% static 'path' %} references a file.
Q14

What are three advantages of using the browser Developer Tools when learning CSS/JS?

Answer: Immediate feedback, debugging, and element inspection — also network analysis, mobile emulation and performance monitoring.
