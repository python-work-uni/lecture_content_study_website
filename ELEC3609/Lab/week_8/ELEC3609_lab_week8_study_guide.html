Securing and Testing Django Web Applications

This lab covers the two halves of shipping a trustworthy Django app: defending against the classic web attacks (XSS, CSRF, SQL injection, clickjacking, and unencrypted traffic) using Django's built-in protections and safe deployment settings, and proving the app actually works by writing automated tests for models, forms, views, and templates, then measuring how much of your code those tests cover.

Read this first: Security and testing are the same discipline seen from two sides — you assume the app will be attacked and will break, so you build defences into every layer (templates escape output, forms carry CSRF tokens, the ORM parameterises SQL, settings lock down deployment) and you write tests that exercise each layer so a regression is caught before an attacker or a user finds it. Everything in this lab is either "how an attack works" or "how Django stops it / how you verify it."

  • Reason about CSRF risk when using JWT and Django REST Framework.
  • Structure a Django test suite using TestCase and test_-prefixed methods.
  • Write unit tests for models, forms, views, and templates using unittest assertions and Django's test client.
  • Use the test database with fixtures and setUpTestData to isolate tests from production data.
  • Measure test coverage with Coverage.py and choose frontend testing tools.

The Threat Landscape and Django's Defence-in-Depth

Every web app faces a predictable catalogue of attacks, and Django answers each one with a specific built-in mechanism rather than leaving you to invent a defence.

Web applications are exposed to a wide variety of attacks. The consequences are concrete: data breaches, loss of user trust, and downtime. This lab works through the most common security concerns in web development and deployment, then shows how Django mitigates them.

The threats you must be able to name and explain are:

  • Cross-Site Scripting (XSS) — attacker-injected scripts run in a victim's browser.
  • Cross-Site Request Forgery (CSRF) — a victim's authenticated browser is tricked into sending a state-changing request.
  • SQL Injection — attacker-supplied input alters the SQL your database runs.
  • Clickjacking — a victim's clicks are hijacked to a hidden malicious page.
💡
Why it matters: Security is not one feature you bolt on at the end. Each attack targets a different layer — the browser, the request, the database, the frame — so each defence lives in a different layer too. Knowing which layer an attack hits tells you where to look for the fix.
🧠
Memory hook: Think of the four classic attacks by where they strike: XSS hits the browser, CSRF hits the request, SQL injection hits the database, clickjacking hits the frame.

Cross-Site Scripting (XSS)

XSS happens when untrusted input reaches a page as executable code, so the victim's own browser runs the attacker's script with the victim's privileges.

XSS is a vulnerability where attackers inject malicious scripts into a website. Those scripts are then executed by users' browsers, and because they run in the page's origin they can:

  • Steal sensitive information such as cookies.
  • Hijack the user's session.
  • Perform malicious actions on the user's behalf.

How an XSS attack works

  1. The attacker finds a form or input field on your site that does not properly sanitise or escape user input. For example, a comment section renders:
<div>{{ user_comment }}</div>
  1. The attacker submits malicious JavaScript through that input. If user_comment is not properly escaped, the attacker can inject something like:
<script>alert('Your session has been hijacked');</script>

This script executes whenever any user visits the page containing the comment.

⚠️
Common trap: The danger is not the <script> tag itself — it is that user-controlled text was placed into an HTML context without escaping. The same problem exists for data injected into JavaScript or JSON, where HTML escaping alone is not enough.
🤔
Pause & predict: The template shows {{ user_comment }}. If Django autoescapes by default, why is this example still presented as vulnerable?

Defending Against XSS

Django escapes template output by default, and the remaining work is to avoid switching that off and to sanitise input for non-HTML contexts.

1. Django's built-in protection: autoescaping

Django automatically escapes dangerous characters in HTML templates, which prevents inputs such as <script> tags from being executed. By default in Django, every template automatically escapes the output of every variable tag. You can state the behaviour explicitly (or scope it) with the autoescape tag:

{% autoescape on %}
{{ body }}
{% endautoescape %}

2. Avoid the safe filter

Django provides a safe filter that marks a string as safe and stops escaping it. Use it cautiously — it can reintroduce XSS:

<p>{{ user_input|safe }}</p> <!-- Avoid this unless absolutely necessary -->

3. Input sanitisation in the backend

Even though Django's template system escapes content by default, it is good practice to sanitise input when it is stored or processed — especially data that will be used in non-HTML contexts such as JSON or JavaScript. Python libraries such as Bleach or nh3 can sanitise input before it is saved to the database:

import bleach
clean_input = bleach.clean(user_input)

4. Set HTTP-only cookies

Marking cookies HTTP-only makes it much harder for an attacker to escalate an XSS vulnerability into full session hijacking, because JavaScript cannot read the cookie. Django uses HTTP-only cookies for session management by default:

# settings.py
SESSION_COOKIE_HTTPONLY = True
✅
Exam tip: Four-layer XSS defence to recall: autoescape on → avoid |safe → sanitise on save (Bleach/nh3) → HTTP-only cookies. The last one limits the damage if an XSS slips through; the first three try to prevent it.

Cross-Site Request Forgery (CSRF)

CSRF abuses the fact that browsers attach a victim's session cookie automatically, letting an attacker trigger actions the victim never intended.

CSRF tricks users into making unwanted actions on a site where they are already authenticated. The attacker crafts a malicious request that rides on the victim's authentication credentials to perform actions such as transferring funds or changing account information.

A concrete CSRF attack

Alice is logged into her bank, http://bank.com, and has a valid session cookie stored in her browser. Malicious Maria wants to trick Alice into transferring money to Maria's account without consent. Using social engineering, Maria sends Alice a malicious link or embeds an image tag:

  • <a href="https://bank.com/transfer?acct=Maria&amount=10000">Check out this cool picture!</a>
  • Or as a hidden request: <img src="https://bank.com/transfer?acct=Maria&amount=10000" width="0" height="0">

When Alice clicks the link (or when the image loads), her browser automatically sends the session cookie to bank.com, executing the action without Alice's knowledge.

💡
Why it matters: The browser cannot tell a legitimate transfer request from a forged one — it just sees "request to bank.com, attach the cookie." The defence must therefore prove the request originated from your page, not from Maria's.

GET vs POST and CSRF

GET requests and CSRF:

  • GET requests are typically used to retrieve data and are not meant to modify state (e.g. transfer money, delete an account).
  • However, if an application incorrectly uses GET for sensitive actions, it becomes vulnerable to CSRF even with CSRF token protection.
  • Example: if the bank uses a GET request to transfer funds, an attacker can exploit it by simply phishing a user into clicking a malicious link.
  • Solution: avoid using GET requests for any state-changing actions.

POST requests and CSRF:

  • The only difference between GET and POST attacks is how the attack is executed by the victim.
  • Suppose the bank now uses POST to http://bank.com/transfer. Such a request cannot be delivered with standard <a> or <img> tags, but it can be delivered with a <form> submitted on Alice's behalf:
<form action="https://bank.com/transfer" method="POST">
  <input type="hidden" name="account" value="attacker_account">
  <input type="hidden" name="amount" value="1000">
</form>
<script>document.forms[0].submit();</script>
  • Solution: to prevent CSRF on POST requests, websites typically use CSRF tokens as an additional layer of security.
🧠
Memory hook: GET = click a link; POST = auto-submit a form. Both ride the cookie, but POST needs a hidden form because tags like <img> only issue GETs.

CSRF Tokens and Django's CSRF Protection

A CSRF token is a per-session secret that must accompany every state-changing request, so a request forged by another site cannot be valid.

A CSRF token is a unique, random value generated by the server and associated with the user's session. It is included in every form submission or AJAX request for state-changing actions. When the user submits, the token is sent alongside the session cookie, and the server checks both to confirm the request is legitimate.

CSRF token in a Django template

<form action="{% url 'transfer' %}" method="POST">
  {% csrf_token %}
  <input type="hidden" name="account" value="recipient_account">
  <input type="hidden" name="amount" value="1000">
  <button type="submit">Transfer</button>
</form>
<script>
  document.forms[0].submit(); // Automatically submits the form
</script>

CSRF token in AJAX requests

The token can be sent in a request header instead of the body:

fetch('/transfer', {
  method: 'POST',
  headers: {
    'X-CSRFToken': 'random_token_value'
  },
  body: JSON.stringify({ amount: 1000, to: 'Bob' })
});

The server validates the CSRF token before processing. If the token is missing or invalid, the server rejects the request — so a simple phishing email alone will not work.

How Django's CSRF protection works

Django's built-in CSRF protection secures POST requests by verifying a CSRF token embedded in forms or headers and ensuring it matches a CSRF cookie sent to the client. This prevents attackers from executing actions on behalf of authenticated users via cross-site requests. Specifically, CsrfViewMiddleware:

  • Checks for the CSRF token on unsafe requests (POST, PUT, DELETE).
  • Validates the Origin or Referer headers for requests over HTTPS, comparing them with trusted domains or subdomains to block cross-origin attacks.

GET requests are exempt, since they should not modify data. Additional points:

  • Using HTTPS and HSTS is essential to defend against man-in-the-middle attacks.
  • Disabling CSRF protection should only be done with caution.
  • Cross-subdomain POSTs can be allowed by configuring CSRF_TRUSTED_ORIGINS and CSRF_COOKIE_DOMAIN.
⚠️
Common trap: A CSRF token does not rescue an app that performs state changes over GET. Because GET is exempt from token checking, the correct fix is to make the action a POST, not to rely on the token.

JWT, CSRF, and Django REST Framework

Where you store a JWT decides whether CSRF is a risk, and DRF disables CSRF protection by default for API views.

When using JWT for authentication, whether CSRF protection is relevant depends on how the JWT is stored:

  • JWT in LocalStorage: it is not automatically sent with requests the way cookies are, which reduces CSRF risk. However, XSS becomes the concern because scripts can read LocalStorage.
  • JWT in cookies (HTTP-only): the browser automatically includes the cookie in every request, so CSRF attacks become possible and CSRF protection is still required. Mitigate with CSRF tokens or by configuring SameSite attributes on cookies.

CSRF in Django REST Framework (DRF)

In DRF, CSRF protection is disabled by default for API views unless you are using session-based authentication. DRF's APIView and ViewSet classes are typically CSRF exempt. It is important to explicitly re-implement CSRF protection, or take alternative measures, depending on your authentication and storage strategy.

💡
Why it matters: Storing a token in LocalStorage trades CSRF risk for XSS risk; storing it in a cookie trades XSS readability for CSRF risk. There is no free option — you must pick the threat you are better defended against and add the matching control.
🤔

Other Protections: SQL Injection and Clickjacking

The Django ORM parameterises SQL for you, and the X-Frame-Options middleware blocks your pages from being framed.

SQL injection protection

SQL injection vulnerabilities let attackers run arbitrary SQL code on your database, potentially modifying, accessing, or deleting data without proper authorisation. Django defends in two ways:

  • When you use Django's models and querysets (the Django ORM), the underlying database driver automatically escapes the SQL, which mitigates injection risk.
  • When you write raw SQL queries, you must explicitly prevent injection by safely parameterising inputs — the ORM cannot protect you.
⚠️
Common trap: "We use Django, so we're safe from SQL injection" is only true while you stay inside the ORM. The moment you drop to raw SQL with string formatting, you have opted out of the automatic protection.

Clickjacking protection

Clickjacking is an attack where a malicious user hijacks clicks meant for a top-level site and routes them to a hidden, malicious page underneath. Attackers may use it to display legitimate content — such as a bank's login page — while capturing user credentials in an invisible iframe they control.

Django combats this with the X-Frame-Options middleware, which prevents your site from being rendered inside an iframe in compatible browsers.

🧠
Memory hook: Clickjacking = invisible iframe + redirected clicks; the fix is literally an HTTP header named X-Frame-Options that says "do not frame me."

Enforcing TLS/HTTPS

HTTPS encrypts the whole conversation, and Django adds redirect, proxy, HSTS, and secure-cookie settings on top so plaintext traffic can never be used.

TLS/HTTPS encrypts communication between the server and client, ensuring sensitive data — including authentication credentials — is not sent in plain text. Enabling HTTPS is crucial for site security. Django offers additional protections once HTTPS is enabled:

  • SECURE_PROXY_SSL_HEADER — ensures security even when traffic passes through a non-HTTPS proxy.
  • SECURE_SSL_REDIRECT — automatically redirects all HTTP requests to HTTPS.
  • HTTP Strict Transport Security (HSTS) — an HTTP header that enforces HTTPS for all future connections to the site. Combined with redirecting HTTP to HTTPS, it ensures HTTPS is always used once a secure connection is established. Configure it with SECURE_HSTS_SECONDS and SECURE_HSTS_INCLUDE_SUBDOMAINS.
  • Secure cookies — setting SESSION_COOKIE_SECURE and CSRF_COOKIE_SECURE to True means cookies are sent only over HTTPS, further safeguarding sensitive information.
ℹ️
Note: HSTS is a browser memory mechanism. After the first secure connection, the browser refuses to attempt plain HTTP to your site for the duration set in SECURE_HSTS_SECONDS — which is why the redirect and HSTS are complementary.
🤔
Pause & predict: Why is SECURE_PROXY_SSL_HEADER needed specifically when a load balancer or reverse proxy terminates TLS before the request reaches Django?

Security Settings for Deployment

Production configuration is where most real breaches start, so lock down hosts, secrets, debug mode, cross-origin rules, database privileges, and file permissions.

  • ALLOWED_HOSTS — restrict which domains can serve your Django app, to prevent HTTP Host header attacks:
ALLOWED_HOSTS = ['yourdomain.com', 'www.yourdomain.com']
  • SECRET_KEY in .env — keep secret keys and sensitive data out of your codebase using environment variables stored in a .env file:
SECRET_KEY = os.getenv('SECRET_KEY')
  • DEBUG mode — never run with DEBUG=True in production, as it exposes sensitive information:
DEBUG = False
  • CORS and CSRF trusted origins — control which domains can interact with your API securely:
CORS_ALLOWED_ORIGINS = ['https://yourfrontend.com']
CSRF_TRUSTED_ORIGINS = ['https://yourfrontend.com']
  • Database permissions — ensure the database user that connects your Django application has limited permissions (avoid using root). Limit CREATE, ALTER, or DROP permissions to reduce the impact of SQL injections.
  • Linux file permission management — protect sensitive files by setting appropriate permissions, e.g.:
chmod 600 /path/to/.env
🧠
Memory hook: The production checklist is H·S·D·C·D·F — Hosts, Secret key, Debug off, CORS/CSRF origins, Database least privilege, File permissions (chmod 600).
💡
Why it matters: Least-privilege database permissions are a damage limiter: they do not stop SQL injection, but they stop an injection from dropping tables or creating users. Defence in depth means every layer assumes the layer above already failed.

Django Testing: Structure and Running Tests

Django builds testing on Python's unittest, so tests are classes derived from TestCase with methods named test_, discovered and run by one command.

Django provides a robust suite of built-in testing tools to ensure an application works as expected. Testing is critical to verify the functionality of your models, views, forms, databases, and even templates. You should write tests for anything crucial to your application — particularly features that handle user data, interact with the database, or display dynamic content. Django's testing framework integrates seamlessly with Python's unittest, making tests easy to create and manage.

Structure

  • Tests are organised in classes derived from TestCase.
  • Individual test methods are prefixed with test_.
  • Test files go inside an app's tests.py or a dedicated tests directory, for example:
til_app/
  tests.py
  tests/
    __init__.py
    test_models.py
    test_forms.py
    test_views.py

Running tests

python manage.py test

This command automatically discovers and runs all tests across your project and provides feedback on which tests pass or fail. The test runner offers many additional options.

ℹ️
Note: The test_ prefix is not cosmetic — the runner discovers methods by that prefix. A method named check_post_list() will silently never run.

What to Test: Models, Forms, Views, and Templates

Test each layer where it makes decisions — model defaults and logic, form validation, view responses, and template selection — using the test client to simulate real requests.

Testing models

Testing models ensures the database structure and logic behave correctly: verifying field default values, model methods, and database relationships.

from django.test import TestCase
from .models import Post

class PostModelTests(TestCase):
    def test_default_visibility_should_be_public(self):
        post = Post(subject="Test Post", content="This is a test post.")
        self.assertEqual(post.public, True)

assertTrue, assertFalse, and assertEqual are standard assertions provided by unittest. There are other standard assertions, plus Django-specific assertions such as assertRedirects (test that a view redirects) and assertTemplateUsed (test which template was used).

Testing forms

Forms are crucial for user input validation. Test that forms correctly validate input, handle missing fields, and reject invalid submissions.

from django.test import TestCase
from .forms import PostForm

class PostFormTests(TestCase):
    def test_post_form_valid(self):
        form_data = {'subject': 'Test Post', 'content': 'Test content'}
        form = PostForm(data=form_data)
        self.assertTrue(form.is_valid())

Testing views

Views are tested to verify the correct response, template rendering, and context variables. Simulate HTTP requests with Django's test client:

from django.test import TestCase
from django.urls import reverse

class PostViewTests(TestCase):
    def test_post_list_view(self):
        response = self.client.get(reverse('post_list'))
        self.assertEqual(response.status_code, 200)
        self.assertContains(response, "Post List")
⚠️
Common trap: The test client is not supposed to replace frontend testing. You still need something to verify that JavaScript functions as expected and to catch layout or styling issues.

Testing templates

Templates should be tested for correct rendering, dynamic content, and layout. The test client lets you verify the correct template is rendered with the expected content:

from django.test import TestCase
from django.urls import reverse

class TemplateTests(TestCase):
    def test_home_template(self):
        response = self.client.get(reverse('home'))
        self.assertTemplateUsed(response, 'home.html')

Using the test database

Use Django's test database to test model behaviour without affecting production data. Use fixtures or setUpTestData() to create data shared across tests:

from django.test import TestCase
from .models import Post

class PostDatabaseTests(TestCase):
    @classmethod
    def setUpTestData(cls):
        cls.post = Post.objects.create(subject="Test Post", content="Test content")

    def test_post_creation(self):
        self.assertEqual(Post.objects.count(), 1)

Usually constructing objects directly in setUpTestData() is sufficient for testing the database.

🧠
Memory hook: Match the test tool to the layer — model → assertEqual/assertTrue; form → is_valid(); view → status_code + assertContains; template → assertTemplateUsed; shared data → setUpTestData().

Code Coverage with Coverage.py

Coverage tells you what your tests didn't touch, which is exactly where untested bugs and unguarded security paths hide.

Code coverage helps identify parts of your code that are not covered by tests. Django integrates with the Coverage.py tool to measure how much of your codebase is tested. To use it:

  1. Install Coverage.py:
pip install coverage
  1. Run coverage with Django's test suite:
coverage run manage.py test
  1. View the report:
coverage report   # or coverage html for a more visual report
✅
Exam tip: Remember the three commands in order: pip install coverage → coverage run manage.py test → coverage report (or coverage html). The key idea is that coverage measures untested code; it does not prove the tests are good.

Frontend Testing Tools

Django's built-in tools cover the backend, so frontend logic, interactions, and layout need their own tools.

While Django's built-in testing tools focus on the backend, frontend testing is essential for validating JavaScript, user interactions, and layout consistency. Tools you can use:

  • Selenium — automates browser interactions, simulating real user actions such as clicks, form submissions, and navigation across multiple pages. Ideal for testing complete user flows in a browser.
  • Jest — a JavaScript testing framework designed for testing frontend logic, providing easy-to-use syntax for writing unit tests.
  • Jasmine — a behaviour-driven testing framework for JavaScript, often used for unit and integration tests, focusing on simple syntax and intuitive test writing.
ToolLanguage / domainBest for
SeleniumBrowser automationEnd-to-end user flows (clicks, forms, navigation)

ℹ️
Note: Backend tests (Django TestCase + test client) and frontend tests (Selenium/Jest/Jasmine) are complementary. Neither replaces the other.

Glossary

Every term you need to speak this week's language.

Cross-Site Scripting (XSS)
An attack that injects malicious scripts into a site so they execute in victims' browsers, enabling cookie theft, session hijacking, or actions as the user.
Autoescaping
Django's default behaviour of escaping dangerous characters in every template variable tag so injected HTML/script cannot execute.
safe filter
A Django template filter that marks a string as safe and disables escaping; dangerous because it can reintroduce XSS.
Bleach
A Python library used to sanitise user input before storing it, particularly for non-HTML contexts such as JSON or JavaScript (nh3 is an alternative).
SESSION_COOKIE_HTTPONLY
A settings flag that makes the session cookie unreadable by JavaScript, limiting XSS escalation to full session hijacking; True by default.
Cross-Site Request Forgery (CSRF)
An attack that tricks an authenticated user's browser into sending an unwanted state-changing request using the victim's credentials.
CSRF token
A unique random value tied to a user's session, included in state-changing form or AJAX requests and verified by the server alongside the session cookie.
CsrfViewMiddleware
Django middleware that checks for the CSRF token on unsafe methods (POST, PUT, DELETE) and validates Origin/Referer over HTTPS.
JSON Web Token (JWT)
A token-based authentication credential; its CSRF exposure depends on whether it is stored in LocalStorage or in cookies.
SQL injection
An attack that runs arbitrary SQL against a database by injecting untrusted input into queries, risking unauthorised read, modification, or deletion of data.
Django ORM
Django's models-and-querysets layer, whose database driver automatically escapes SQL, mitigating injection when used instead of raw SQL.
Clickjacking
An attack that hijacks clicks meant for a top-level site and routes them to a hidden malicious page, often via an invisible iframe.
X-Frame-Options
An HTTP header applied by Django middleware that prevents a site from being rendered inside an iframe in compatible browsers.
HTTP Strict Transport Security (HSTS)
An HTTP header that forces HTTPS for all future connections to a site, configured via SECURE_HSTS_SECONDS and SECURE_HSTS_INCLUDE_SUBDOMAINS.
SECURE_SSL_REDIRECT
A Django setting that automatically redirects all HTTP requests to HTTPS.
SECURE_PROXY_SSL_HEADER
A Django setting that preserves security awareness when traffic passes through a non-HTTPS proxy.
ALLOWED_HOSTS
A Django setting restricting which domains may serve the app, preventing HTTP Host header attacks.
TestCase
Django's base class (built on Python's unittest) for organising tests, with test_ prefixed methods and a test database.
Test client
Django's tool (self.client) for simulating HTTP requests to views and inspecting responses, templates, and context.
setUpTestData()
A classmethod that creates data once, shared across a TestCase's tests, avoiding repeated database setup.
Coverage.py
A tool integrated with Django that measures how much of the codebase the test suite exercises.
Selenium
A browser-automation tool that simulates real user actions such as clicks, form submissions, and navigation for end-to-end frontend testing.
Jest
A JavaScript testing framework designed for frontend logic unit tests.
Jasmine
A behaviour-driven JavaScript testing framework for unit and integration tests.

Practice Questions

Answer, reveal, then tick “Mastered”. Your progress is saved.
Q1

What is the core mechanism of an XSS attack, and what can an attacker achieve with it?

Answer: An attacker finds an input that is not properly sanitised or escaped, then injects malicious scripts that victims' browsers execute. This lets the attacker steal sensitive information such as cookies, hijack sessions, or perform malicious actions on the user's behalf.
Q2

Explain the CSRF attack on Alice's bank using a hidden image tag, and state why it works.

Answer: Maria sends Alice a link or embeds <img src="https://bank.com/transfer?acct=Maria&amount=10000" width="0" height="0">. When Alice clicks the link or the image loads, her browser automatically sends her bank session cookie to bank.com, executing the transfer without her knowledge. It works because browsers attach cookies automatically and cannot distinguish a forged request from a legitimate one.
Q3

Why can using GET for state-changing actions defeat even CSRF token protection?

Answer: GET requests are exempt from CSRF token checking because they are meant to retrieve data and not modify state. If an app performs a sensitive action over GET, an attacker can trigger it with a simple link or image load, and the token check never applies. The solution is to use POST for any state-changing action.
Q4

How does a CSRF token prevent an attack, and how is it delivered in a Django template versus an AJAX request?

Answer: The server generates a unique random token tied to the user's session; it is sent alongside the session cookie and the server verifies both, rejecting requests with a missing or invalid token. In a template you include {% csrf_token %} inside the POST form. In AJAX you send it as a header, e.g. 'X-CSRFToken': 'random_token_value'.
Q5

What does CsrfViewMiddleware check, and which HTTP methods does it treat as unsafe?

Answer: It checks for the CSRF token on unsafe requests (POST, PUT, DELETE) and validates the Origin or Referer headers for requests over HTTPS, comparing them with trusted domains or subdomains to block cross-origin attacks. GET requests are exempt because they should not modify data.
Q6

When using JWT, how does storage choice affect CSRF versus XSS risk?

Answer: If the JWT is stored in LocalStorage it is not automatically sent like a cookie, so CSRF risk is reduced but XSS becomes the concern because scripts can read it. If the JWT is stored in an HTTP-only cookie, the browser includes it automatically, so CSRF is possible and protection (CSRF tokens or SameSite attributes) is required.
Q7

What is DRF's default CSRF behaviour, and what should you do about it?

Answer: In Django REST Framework, CSRF protection is disabled by default for API views unless session-based authentication is used; APIView and ViewSet are typically CSRF exempt. You should explicitly re-implement CSRF protection or take alternative measures suited to your authentication and storage strategy.
Q8

How does Django protect against SQL injection, and where does that protection stop?

Answer: When using Django's models and querysets (the ORM), the underlying database driver automatically escapes the SQL, mitigating injection. The protection stops when you write raw SQL queries — there you must explicitly parameterise inputs to prevent injection.
Q9

What is clickjacking and how does Django prevent it?

Answer: Clickjacking hijacks clicks intended for a top-level site and routes them to a hidden malicious page underneath, often showing legitimate content like a bank login inside an invisible iframe to capture credentials. Django uses the X-Frame-Options middleware, which prevents the site from being rendered inside an iframe in compatible browsers.
Q10

List the HTTPS-related Django protections and what each does.

Answer: SECURE_PROXY_SSL_HEADER ensures security through a non-HTTPS proxy; SECURE_SSL_REDIRECT redirects all HTTP to HTTPS; HSTS (configured by SECURE_HSTS_SECONDS and SECURE_HSTS_INCLUDE_SUBDOMAINS) enforces HTTPS for all future connections; and SESSION_COOKIE_SECURE/CSRF_COOKIE_SECURE = True send cookies only over HTTPS.
Q11

What deployment settings should you verify before going live, and why?

Answer: Set ALLOWED_HOSTS to prevent Host header attacks; keep SECRET_KEY in a .env read via os.getenv('SECRET_KEY'); set DEBUG = False; configure CORS_ALLOWED_ORIGINS and CSRF_TRUSTED_ORIGINS; give the database user least privilege (no root, limit CREATE/ALTER/DROP); and protect files with chmod 600 (e.g. /path/to/.env).
Q12

How are Django tests structured and run?

Answer: Tests are classes derived from TestCase with methods prefixed test_, placed in an app's tests.py or a tests/ directory (e.g. test_models.py, test_forms.py, test_views.py). Run them with python manage.py test, which auto-discovers and runs all tests and reports pass/fail.
Q13

Why use the test database and setUpTestData(), and how do you measure coverage?

Answer: The test database lets you test model behaviour without affecting production data, and setUpTestData() (a classmethod) creates data once to share across tests. Coverage is measured with Coverage.py: pip install coverage, then coverage run manage.py test, then coverage report or coverage html.
Q14

Why is the Django test client not a substitute for frontend testing, and which tools fill the gap?

Answer: The test client exercises backend views but cannot verify JavaScript behaviour, user interactions, or layout/styling. Frontend tools fill the gap: Selenium automates real browser interactions for end-to-end flows, Jest tests frontend logic, and Jasmine provides behaviour-driven JavaScript unit and integration tests.
