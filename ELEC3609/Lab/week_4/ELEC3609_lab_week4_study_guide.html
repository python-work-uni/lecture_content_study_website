Django Models, the ORM and the Admin Interface

This lab shows how a Django application turns ordinary Python classes into database tables. You define models, connect them with relationships, let Django generate and apply the SQL schema through migrations, choose a database engine, and finally manage your data through the built-in admin site.

Read this first: Think of Django's ORM as a translator that sits between your Python objects and a relational database. You write Python classes; Django writes the SQL. Everything in this lab — models, fields, relationships, migrations, the admin — is a different view of the same translation.

By the end you will be able to

  • List the benefits and the limitations of using an ORM.

  • Create an admin superuser and expose models through the Django admin.

Why ORMs Exist

An ORM converts data between two incompatible worlds — object-oriented code and relational tables — so you can work in Python instead of SQL.

Object-Relational Mapping (ORM) is a programming technique used to convert data between incompatible systems, in particular between object-oriented programming languages and relational databases. An ORM lets developers interact with a database using their preferred programming language rather than writing raw SQL queries.

The core mapping is simple and worth memorising:

Object worldDatabase world
Class (e.g. Post)Table
Instance of the classA row in that table
Class attributeA column

So a Post class becomes a table, each Post object becomes one row, and attributes like title and content become columns.

ORM libraries exist for most languages. Examples include Hibernate for Java and Django ORM for Python.

💡
Why it matters: Databases are critical to application performance, scalability and security. They support high availability and fault tolerance and are essential in sensitive fields such as finance. Because they are complex, managing them often needs expert teams — so use an ORM when possible.
⚠️
Common trap: Don't drop down to raw SQL until it's actually necessary. Reach for hand-written SQL only when the ORM genuinely can't do the job.

What ORMs Give You — and What They Cost

ORMs trade some raw performance and a learning curve for speed, safety, portability and cleaner code.

Key features of an ORM

  • Mapping objects to tables: each class corresponds to a table, each instance to a row, each attribute to a column.
  • Abstracts SQL: common operations — CREATE, READ, UPDATE, DELETE (often called CRUD) — are expressed as object-oriented code instead of SQL strings.
  • Automatic data conversion: the ORM translates between database types (such as VARCHAR, INT) and language types (such as strings and integers).
  • Database-agnostic code: the same code can run against MySQL, PostgreSQL or SQLite with minimal changes, improving flexibility and portability.
  • Reduces boilerplate: less repetitive code for database interactions, which speeds up development and reduces SQL-related errors.

What an ORM can do

  • DRY principle: define your data model in one place, making code easier to update, maintain and reuse.
  • Encourages MVC architecture: promotes cleaner, more organised code.
  • Avoids poorly formed SQL: developers work in their native language (and, bluntly, most web programmers are bad at SQL).
  • Simplifies security practices: makes it easy to use prepared statements and transactions, which improves security.
  • Database abstraction: change the underlying database without rewriting queries.
  • Loose coupling: the data model is loosely bound to the application, allowing flexibility and reuse.
  • Supports OOP concepts: facilitates features like data inheritance.

What an ORM cannot do

  • Learning curve: ORMs can be complex and are not lightweight; they take time to learn and set up.
  • Performance limitations: ORM-generated queries are fine for typical work but may not match hand-written SQL in large-scale projects.
  • Impedance mismatch: the way a developer thinks in objects differs from how data is stored and joined in relational tables.
✅
Exam tip: Be ready to state the impedance mismatch as the root problem an ORM tries to solve — objects are in-memory graphs, while relational tables are flat, statically structured and joined at query time.
⚠️
Common trap: Avoid writing your own ORM for an application unless it is specifically for learning. Existing libraries are well-tested, optimised and feature-rich in ways that are hard to replicate from scratch.

Django Models: Classes That Become Tables

A Django model is a Python class that is the canonical definition of an entity — it drives both the database schema and the Python-side interface to that table.

In Django, models are implemented as Python classes and form the canonical representation of your entities. They are used to generate the underlying database schema and the Python-to-database interface for accessing those tables.

For this lab, all models live in a single file, models.py. In larger assignments you might split models into separate files once the file grows too large or complex (roughly 20+ models).

Model inheritance

Each model you want to include in your application must subclass django.db.models.Model. The attributes of your Python class become database fields.

from django.db import models

class Post(models.Model):
    title = models.CharField(max_length=100)
    content = models.TextField()

Model inheritance in Django works almost identically to normal Python class inheritance, but follow the documented basics. Use model inheritance with care — read the Django model inheritance documentation before relying on it.

💡
Why it matters: Every attribute is a promise about the schema. Because Django generates the database from the class, the class is the single source of truth — this is the DRY principle in action.

Choosing Field Types

Every attribute must be mapped to the right Field class so Django knows its type and can generate an accurate schema.

Each attribute of a model must be mapped to an appropriate Django Field class. This tells Django the type of each attribute and lets it generate an accurate schema. Fields can be further customised with default values, unique constraints and validations.

Common Django model field types

✅

🧠
Memory hook: If the data is a short string, CharField; if it can be arbitrarily long, TextField; if it includes time, add Time to the name (DateTimeField). Validation-aware strings get their own types (EmailField, URLField).

Modelling Relationships

Relationships are expressed with special field types, and the choice of field determines the cardinality.

Relationships between models are represented with dedicated field types.

The four relationship patterns

  • Many-to-one: models.ForeignKey placed on the many-side model.
  • Many-to-many: models.ManyToManyField placed on either (or both) models.
  • One-to-one: models.OneToOneField, or the alternative models.ForeignKey(..., unique=True).
  • Many-to-optional-one: models.ForeignKey(null=True, blank=True) on the many-side model.

Many-to-one

An Author can write many Book instances, but each Book has only one Author.

from django.db import models

class Author(models.Model):
    name = models.CharField(max_length=100)
    bio = models.TextField()

    def __str__(self):
        return self.name

class Book(models.Model):
    title = models.CharField(max_length=200)
    author = models.ForeignKey(Author, on_delete=models.CASCADE,
                               related_name='books')  # Many-to-one
    published_date = models.DateField()

    def __str__(self):
        return self.title

Many-to-many

A Student can enrol in many Course instances, and a Course can have many Student instances.

from django.db import models

class Student(models.Model):
    name = models.CharField(max_length=100)
    age = models.IntegerField()

    def __str__(self):
        return self.name

class Course(models.Model):
    name = models.CharField(max_length=100)
    description = models.TextField()
    students = models.ManyToManyField(Student, related_name='courses')  # Many-to-many

    def __str__(self):
        return self.name

One-to-one

A User can have exactly one UserProfile, and a UserProfile can belong to exactly one User.

from django.db import models
from django.contrib.auth.models import User

class UserProfile(models.Model):
    user = models.OneToOneField(User, on_delete=models.CASCADE)  # One-to-one
    bio = models.TextField()
    profile_picture = models.ImageField(upload_to='profiles/')

    def __str__(self):
        return self.user.username

The equivalent alternative uses a unique foreign key:

class UserProfile(models.Model):
    user = models.ForeignKey(User, on_delete=models.CASCADE,
                             unique=True)  # One-to-one alternative
    bio = models.TextField()
    profile_picture = models.ImageField(upload_to='profiles/')

    def __str__(self):
        return self.user.username

Many-to-optional-one

An Employee can belong to one Department, but not every Employee has to be assigned to a department.

from django.db import models

class Department(models.Model):
    name = models.CharField(max_length=100)

    def __str__(self):
        return self.name

class Employee(models.Model):
    name = models.CharField(max_length=100)
    department = models.ForeignKey(Department, on_delete=models.SET_NULL,
                                   null=True, blank=True)  # Many-to-zero

    def __str__(self):
        return self.name
ℹ️
Note: on_delete controls what happens to the dependent row when the referenced row is deleted — CASCADE deletes it too, while SET_NULL keeps it but clears the link. related_name sets the name used to go from the related object back to this one.
🧠
Memory hook: The foreign key always lives on the many side. If you can say "many of these belong to one of those", the "many" model carries the ForeignKey.

Direct vs String References and Circular Dependencies

You can point at a related model by its class name or by a string — strings let you define models in any order and break circular dependencies.

When defining relationships, you can refer to a related model in two ways: directly by class name, or using a string reference.

Referring directly by class name

If the related model is already defined in the file, refer to it by class name. This is straightforward and is used when there is no circular dependency, or when the order of definitions can be managed easily.

class Tag(models.Model):
    name = models.CharField(max_length=100)

class Post(models.Model):
    tag = models.ForeignKey(Tag, on_delete=models.CASCADE)  # Direct reference

Referring using a string reference

If the related model is not yet defined, refer to it with a string containing the model's name. This lets you define models in any order, including cases where two models refer to each other.

class Post(models.Model):
    tag = models.ForeignKey("Tag", on_delete=models.CASCADE)  # String reference

class Tag(models.Model):  # Defined later
    name = models.CharField(max_length=100)

String references are also known as lazy relationships. They also work when a model wants to reference itself.

Circular or two-way dependency

If two models refer to each other, reordering their definitions won't help because both depend on each other. Use a string reference to break the circular dependency.

class Author(models.Model):
    name = models.CharField(max_length=100)
    # This line errors if 'Book' is not yet defined:
    # favorite_book = models.ForeignKey(Book, on_delete=models.CASCADE, null=False)
    favorite_book = models.ForeignKey("Book", on_delete=models.CASCADE,
                                      null=False)  # String reference

class Book(models.Model):
    title = models.CharField(max_length=200)
    author = models.ForeignKey(Author, on_delete=models.CASCADE)  # null=False by default
⚠️
Common trap: Avoid circular foreign keys where both sides are required. Making Book.author and Author.favorite_book non-nullable creates a chicken-and-egg deadlock — you can't create either row first.
💡
Why it matters: Circular references in Django models are not inherently invalid but should be used with caution. They can create complex migration dependencies and maintenance challenges. This is because models eventually map to a relational database, which follows a static schema and enforces referential integrity. Unlike runtime memory, where objects can point at each other freely, a relational database needs every reference defined ahead of time. Circular references are often a sign the model design could be simplified.

The TIL Model in Practice

The TIL app turns a Post/Tag ERD into two Python classes — including a many-to-many relationship Django will implement with a hidden junction table.

The TIL ("Today I Learned") example uses a Post/Tag design: a Post can be associated with zero, one or many Tags, and a Tag can be applied to one or many Posts.

⚠️
Common trap: The ERD shown is not normalised — it omits the mapping (junction) table that a many-to-many relationship actually needs between Post and Tag.

Add the following to til_app/models.py:

# til_app/models.py
from django.db import models

class Tag(models.Model):
    name = models.CharField(max_length=10, unique=True)
    creation_date = models.DateTimeField(auto_now_add=True)

class Post(models.Model):
    subject = models.CharField(max_length=160)
    content = models.CharField(max_length=800)
    # creator = ???  # Django built-in auth user
    visibility = models.BooleanField(default=True)
    created_at = models.DateTimeField(auto_now_add=True)

    tags = models.ManyToManyField(Tag, related_name='posts', blank=True)
    # With related_name, we can do:
    # >>> tag_instance.posts.all()  # all posts associated with a Tag instance
ℹ️
Note: The creator of a Post is deliberately left out for now. You will use Django's built-in user system provided by the auth application in the next lab.
✅
Exam tip: related_name is the name used for the relation from the related object back to this one. Here it lets you call tag_instance.posts.all() to get every Post linked to a Tag.

Limits of ManyToManyField

ManyToManyField does not provide built-in support for constraints like "at least one". To guarantee a Tag is always associated with one or more Posts, you must implement custom validations and use signals — covered in a later lab.

Django automatically creates an intermediary model to manage a many-to-many relationship, but it may lack flexibility for complex cases. When you need more control — adding extra fields to the relationship or enforcing custom constraints — define an explicit mapping class instead of relying on ManyToManyField.

Activating Your App

Models do nothing until their application is listed in INSTALLED_APPS.

Django maintains a list of installed applications in settings.py, in the INSTALLED_APPS variable. By default, Django installs these applications:

INSTALLED_APPS = [
    'django.contrib.admin',
    'django.contrib.auth',
    'django.contrib.contenttypes',
    'django.contrib.sessions',
    'django.contrib.messages',
    'django.contrib.staticfiles',
]

Before you can generate the schema for your models, you must add your til application to the list. Do this by including the config class (for example TilAppConfig, defined in apps.py):

INSTALLED_APPS = [
    'til_app.apps.TilAppConfig',
    'django.contrib.admin',
    'django.contrib.auth',
    # ...
]
💡
Why it matters: makemigrations scans INSTALLED_APPS for models. If your app isn't listed, Django never sees your models and will happily generate nothing.

Schema Migrations: Make, Inspect, Apply

Django generates and manages the database schema from your model files; migrations are the versioned instructions that turn models into SQL.

Django can generate and manage the database schema directly from the Python model files. Once your models are defined and the app is installed, the internal tools can produce schemas.

1. Make migrations

python3 manage.py makemigrations <application>

With an application name, Django creates migrations only for that app. Without a name:

python3 manage.py makemigrations

Django then checks every app in INSTALLED_APPS and creates migrations for all apps with pending changes. Example output:

$ python3 manage.py makemigrations til_app
Migrations for 'til_app':
  til_app/migrations/0001_initial.py
    - Create model Tag
    - Create model Post

This generates a migration file but does not apply it yet. The file lives at til_app/migrations/0001_initial.py.

2. View the SQL behind a migration

To see the commands that will run against the database, use sqlmigrate:

python manage.py sqlmigrate til_app 0001
BEGIN;
-- Create model Tag --
CREATE TABLE "til_app_tag" (
    "id" INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
    "name" VARCHAR(10) NOT NULL UNIQUE,
    "creation_date" DATETIME NOT NULL
);
-- Create model Post --
CREATE TABLE "til_app_post" (
    "id" INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
    "subject" VARCHAR(160) NOT NULL,
    "content" VARCHAR(800) NOT NULL,
    "visibility" BOOL NOT NULL,
    "created_at" DATETIME NOT NULL
);
-- Create many-to-many table for Post and Tag relationship --
CREATE TABLE "til_app_post_tags" (
    "id" INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
    "post_id" BIGINT NOT NULL REFERENCES "til_app_post" ("id") DEFERRABLE INITIALLY DEFERRED,
    "tag_id" BIGINT NOT NULL REFERENCES "til_app_tag" ("id") DEFERRABLE INITIALLY DEFERRED
);
CREATE UNIQUE INDEX "til_app_post_tags_post_id_tag_id_3b9d1d8d_uniq"
    ON "til_app_post_tags" ("post_id", "tag_id");
CREATE INDEX "til_app_post_tags_post_id_96b51563" ON "til_app_post_tags" ("post_id");
CREATE INDEX "til_app_post_tags_tag_id_d18818ba" ON "til_app_post_tags" ("tag_id");
COMMIT;
✅
Exam tip: Notice that Django automatically creates a junction table, til_app_post_tags, to manage the ManyToManyField. It also adds a unique index on the (post_id, tag_id) pair (preventing duplicate links) and separate indexes on each column to speed up queries.
ℹ️
Note: This SQL was generated for SQLite. Changing the database engine is covered later. To experiment, try creating a circular dependency and inspecting how the ORM translates it to SQL.

3. Apply migrations

python3 manage.py migrate <application|optional>

This runs every migration from all installed apps that has not yet been applied. Example:

$ python manage.py migrate
Operations to perform:
  Apply all migrations: admin, auth, contenttypes, sessions, til_app
Running migrations:
  Applying contenttypes.0001_initial... OK
  Applying auth.0001_initial... OK
  Applying admin.0001_initial... OK
  ...
  Applying til_app.0001_initial... OK

The Migration Workflow and Staying in Sync

The workflow is three steps — edit models, make migrations, migrate — and the model files must always match the database schema.

Applying your models and getting them into the database involves three steps:

  1. Modify the model Python files (models.py).
  2. Run python manage.py makemigrations.
  3. Run python manage.py migrate.
⚠️
Common trap: Modifying model files without applying migrations, or modifying the database schema without modifying the models, causes many problems. It is critical to keep the two in sync.
✅
Exam tip: Examine the generated migration code before you run it, especially for complex changes. Always back up your data before running a migration.

Choosing the Database Engine

Django uses SQLite by default, but the engine is configured in one place — the DATABASES setting.

By default, Django uses SQLite, a standalone, file-based database. You may also use MySQL or PostgreSQL for eventual deployment into AWS.

The engine is configured in settings.py under the DATABASES variable:

DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.sqlite3',
        'NAME': BASE_DIR / 'db.sqlite3',
    }
}
ℹ️
Note: SQLite is typically sufficient for your group assignment if you are not familiar with database engine mechanisms. See Django's database reference for how to change engines.

Django Admin: Managing Data Out of the Box

Django ships with a powerful admin interface that lets you add, edit and delete models with very little code — but it is for administrators, not end users.

Django comes with a powerful admin interface automatically, out of the box, at http://127.0.0.1:8000/admin. It lets you add, edit and delete model data with very little application code. You must be running the app with python manage.py runserver to reach it.

⚠️
Common trap: Don't use the Django admin for end users. It is designed for site administrators and developers — a place for your ICT team to add, edit and delete data and perform site management. You can stretch it to serve end users (staff, managers, website admins), but you really should not; it is not designed for every site visitor.

Create an admin user

The admin interface is guarded by username/password credentials. The auth application exposes a command to create superusers:

python manage.py createsuperuser
$ python manage.py createsuperuser
Username (leave blank to use 'user'): user
Email address: user@user.com
Password:
Password (again):
Superuser created successfully.

These users get access to the admin interface and provide an easy way to bootstrap new admin users without touching the database directly.

✅
Exam tip: You can run createsuperuser multiple times to add more superusers.
⚠️
Common trap: The Django auth application has default rules preventing common and insecure passwords. You can bypass these restrictions, but it is not recommended.

Once the user exists, log in at http://127.0.0.1:8000/admin (or whatever port your server uses).

Registering Models and Securing the Admin

Models are not visible in the admin until you register them, and the admin deserves extra hardening because it grants special powers.

Register models

Models do not automatically appear in the admin interface. You must register them first by editing til_app/admin.py and calling admin.site.register(<model>):

from django.contrib import admin
from .models import Post, Tag

admin.site.register(Post)
admin.site.register(Tag)

Reload the admin interface and you will now see the TIL application and its exposed models.

✅
Exam tip: Play around with the admin interface to get familiar with it — you should be able to create, edit and delete data.

Secure the Django admin

Because the admin gives site admins special powers ordinary users don't have, it's good practice to make it extra secure.

Change the default admin URL

Django project co-leader Jacob Kaplan-Moss suggests (paraphrased) that using a different name — or even a different domain — for the admin is an easy extra layer of security. It also prevents attackers from easily profiling your site: attackers can sometimes tell which version of Django you're using, down to the point-release level, by examining the HTML of the login screen at admin/.

Limit admin access based on IP

Configure your web server to allow access to the Django admin only from certain IP addresses (look up the instructions for your particular server; for Nginx, see https://tech.marksblogg.com/django-admin-logins.html).

An acceptable alternative is to put this logic into middleware. This avoids modifying web server configuration (easy to implement) but introduces slight performance overhead from the extra middleware layer, so it is not as efficient as doing it at the web server level.

ℹ️
Note: You are not required to secure the Django admin for your assignments.

Key Takeaways

If you remember nothing else, remember this.

1

An ORM maps classes to tables, instances to rows and attributes to columns, letting you use Python instead of raw SQL.

2

ORMs give DRY code, MVC encouragement, fewer malformed queries, prepared statements/transactions, database abstraction, loose coupling and OOP support.

3

ORMs cost you a learning curve, some query performance, and suffer from the impedance mismatch between objects and relational tables.

4

Never write your own ORM for an application unless it is purely for learning.

5

Every Django model subclasses django.db.models.Model; its attributes become database fields.

6

Pick the correct Field class (CharField, TextField, DateTimeField, etc.) so Django can build an accurate schema.

7

Relationships use ForeignKey (many-to-one, on the many side), ManyToManyField, OneToOneField (or ForeignKey(unique=True)), and ForeignKey(null=True, blank=True) for many-to-optional-one.

8

Use string references (lazy relationships) to define models in any order or break circular dependencies; avoid circular FKs where both sides are required.

9

In the TIL model, Post.tags is a ManyToManyField with related_name='posts', enabling tag_instance.posts.all().

10

Register the app in INSTALLED_APPS, then run makemigrations, optionally inspect with sqlmigrate, then migrate.

11

Django auto-creates a junction table plus a unique index and per-column indexes for many-to-many relationships.

12

SQLite is the default database; the engine is set under DATABASES in settings.py.

13

The admin is for administrators, not end users; create access with createsuperuser and expose models via admin.site.register().

14

Harden the admin by changing its URL and restricting access by IP (server-level or middleware).

Glossary

Every term you need to speak this week's language.

ORM
Object-Relational Mapping: a technique that converts data between object-oriented code and relational databases, letting you use your language instead of raw SQL.
Relational database
A database that stores data in tables with rows and columns, follows a static schema, and enforces referential integrity.
Model
A Python class subclassing django.db.models.Model that is the canonical definition of an entity and generates both the schema and the Python database interface.
Field
A model attribute mapped to a Django Field class that determines the column type, defaults, constraints and validation.
CharField
A string field with a required max length, used for names, titles and short text.
TextField
A long text field with no maximum length in the database, used for article content and comments.
ForeignKey
A many-to-one relationship field placed on the many-side model; also used with unique=True for one-to-one.
ManyToManyField
A relationship field placed on either (or both) models for many-to-many relationships; Django creates an intermediary/junction table.
OneToOneField
A relationship field enforcing exactly one related record on each side.
related_name
The name used to access the reverse side of a relationship, e.g. tag_instance.posts.all().
on_delete
An option controlling what happens to a dependent row when the referenced row is deleted, e.g. CASCADE or SET_NULL.
Lazy relationship
A string reference to a not-yet-defined model, allowing any definition order and self-references.
Circular dependency
When two models reference each other; supported via string references but discouraged because it complicates migrations.
Impedance mismatch
The fundamental difference between how developers use objects and how relational tables store and join data.
Junction table
An automatically created table (e.g. til_app_post_tags) that stores many-to-many links between two models.
Migration
A generated, versioned file describing schema changes derived from your models.
makemigrations
The command that generates migration files for pending model changes without applying them.
migrate
The command that applies unapplied migrations to the database.
sqlmigrate
The command that prints the SQL that a given migration will run against the database.
INSTALLED_APPS
The settings list of applications Django loads; only listed apps have their models seen by migration tools.
DATABASES
The settings variable configuring the database engine, such as SQLite, MySQL or PostgreSQL.
Superuser
A privileged account created with createsuperuser that can access the Django admin interface.
Django admin
A built-in interface for administrators and developers to add, edit and delete model data.

Practice Questions

Look away from the page first — retrieval is what builds memory.

Answer, reveal, then tick “Mastered”. Your progress is saved.
Q1

What is an ORM and what three mappings does it establish between objects and tables?

Answer: Object-Relational Mapping converts data between object-oriented languages and relational databases. It maps a class to a table, an instance of the class to a row, and a class attribute to a column.
Q2

Give three benefits an ORM provides and three limitations it has.

Answer: Benefits: DRY single-place data model, database-agnostic code, reduced boilerplate, prepared statements/transactions for security, database abstraction, loose coupling, OOP support. Limitations: a learning curve (complex, not lightweight), performance limits versus hand-written SQL at scale, and the impedance mismatch between objects and relational tables.
Q3

What is the impedance mismatch?

Answer: It is the fundamental difference between how a developer uses objects (in-memory, free to reference each other) and how a relational database stores and joins data (static schema, well-defined references, referential integrity). It is the core problem ORMs exist to bridge.
Q4

How do you define a Django model, and what does each attribute represent?

Answer: Define a Python class that subclasses django.db.models.Model. Each attribute is assigned an appropriate Django Field class, which becomes a database column; the class itself becomes a table.
Q5

Match the field to its use: short string, long text, date and time, email, file upload.

Answer: Short string = CharField; long text = TextField; date and time = DateTimeField; email = EmailField (validated); file upload = FileField (or ImageField for images).
Q6

Which field represents a many-to-one relationship and on which model does it go?

Answer: models.ForeignKey, placed on the many-side model (e.g. Book.author = models.ForeignKey(Author, ...)).
Q7

How do you define a one-to-one relationship in two different ways?

Answer: Use models.OneToOneField(OtherModel, on_delete=...) or, as an alternative, models.ForeignKey(OtherModel, on_delete=..., unique=True).
Q8

How do you model a "many-to-optional-one" relationship?

Answer: Use models.ForeignKey(OtherModel, on_delete=models.SET_NULL, null=True, blank=True) on the many-side model, so the link is optional.
Q9

When should you use a string reference instead of a direct class reference?

Answer: Use a string reference when the related model is not yet defined, when you want to define models in any order, for self-references, or to break a circular/two-way dependency. Otherwise, a direct class reference is fine.
Q10

Why is a circular foreign key with both sides required a problem?

Answer: It creates a chicken-and-egg deadlock: because both foreign keys are non-nullable, you cannot create either row first. Circular references also complicate migration dependencies and maintenance.
Q11

Write the TIL models and explain what related_name='posts' enables.

Answer: Tag has name (CharField max_length=10, unique) and creation_date (DateTimeField auto_now_add). Post has subject, content, visibility, created_at and tags = models.ManyToManyField(Tag, related_name='posts', blank=True). related_name='posts' enables tag_instance.posts.all() to return all Posts linked to a Tag.
Q12

What does ManyToManyField not enforce, and what are the options for more control?

Answer: It does not enforce constraints such as "at least one". To enforce them you need custom validations and signals. For complex needs (extra fields or custom constraints) define an explicit mapping/intermediary model instead of relying on the automatic one.
Q13

What must you do before Django can generate a schema for your models?

Answer: Add the application (its config class, e.g. 'til_app.apps.TilAppConfig') to INSTALLED_APPS in settings.py, so makemigrations can discover the models.
Q14

State the three-step migration workflow and the difference between makemigrations and migrate.

Answer: Step 1 modify models.py; step 2 run python manage.py makemigrations (generates migration files, does not apply); step 3 run python manage.py migrate (applies unapplied migrations to the database).
Q15

What does sqlmigrate show, and what extra objects does Django create for a ManyToManyField?

Answer: sqlmigrate prints the SQL a migration will run. For a ManyToManyField, Django creates a junction table (til_app_post_tags) with foreign keys to both models, a unique index on the (post_id, tag_id) pair, and separate indexes on each column.
Q16

How is the database engine configured, and what is the default?

Answer: It is configured in settings.py under the DATABASES variable using the 'ENGINE' key; the default is SQLite (django.db.backends.sqlite3). MySQL and PostgreSQL can be used for AWS deployment.
Q17

How do you create an admin user and expose your models in the admin?

Answer: Run python manage.py createsuperuser and follow the prompts; then edit app/admin.py to import the models and call admin.site.register(Model) for each. Log in at http://127.0.0.1:8000/admin while runserver is running.
Q18

Why should the admin not be used for end users, and name two ways to secure it.

Answer: The admin is designed for site administrators/developers, not ordinary visitors. Secure it by changing the default admin URL (or domain) and by limiting access based on IP — either at the web server level (more efficient) or via middleware (easier, slight overhead).
