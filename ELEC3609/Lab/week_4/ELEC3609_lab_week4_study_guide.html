What Is an ORM?

ORM (Object-Relational Mapping) is a programming technique used to convert data between incompatible systems — in particular, between object-oriented programming languages and relational databases. ORMs let developers interact with a database using their preferred programming language, rather than writing raw SQL queries.

Key Features of an ORM

  • Mapping objects to database tables — each class (in Python, Java, C#, etc.) corresponds to a table; each instance represents a row; each class attribute corresponds to a column.
  • Abstracts SQL — ORMs hide SQL syntax and provide methods for common operations (CREATE, READ, UPDATE, DELETE) using object-oriented code.
  • Automatic data conversion — the ORM converts between database types (like VARCHAR, INT) and language types (like strings, integers).
  • Database-agnostic code — code written with an ORM can work with different databases (MySQL, PostgreSQL, SQLite) with minimal changes, increasing flexibility and portability.
  • Reduces boilerplate code — less repetitive database code, faster development, and fewer SQL-related errors.
ℹ️

Background:

There are many ORM libraries — for example Java's Hibernate and Python's Django ORM.
💡

Why It Matters:

Because the ORM is database-agnostic, you can develop on SQLite and later move to PostgreSQL/MySQL for deployment without rewriting your queries.
03

ORM Strengths & Trade-offs

What an ORM Can Do

  • DRY Principle — define your data model in one place, making code easier to update, maintain and reuse.
  • Encourages MVC architecture — promotes cleaner, more organised code.
  • Avoids poorly formed SQL — minimises SQL errors by letting developers work in their native language.
  • Simplifies security practices — makes it easy to use prepared statements and transactions.
  • Database abstraction — allows easy changes to the underlying database without rewriting queries.
  • Loose coupling — the data model is loosely bound to the application, allowing flexibility and reuse.
  • Supports OOP concepts — facilitates object-oriented features such as data inheritance.

What an ORM Cannot Do

  • Learning curve — ORMs can be complex and are not lightweight; they take time to learn and set up.
  • Performance limitations — while sufficient for typical queries, ORM-generated queries may not match hand-written SQL in large-scale projects.
  • Impedance mismatch — the way a developer uses objects differs from how data is stored and joined in relational tables.
⚠️

Common Trap — Don't drop down to raw SQL until it's necessary:

Databases are critical to performance, scalability and security, and are complex enough to require expert teams. Use ORMs when possible, and only drop to raw SQL when absolutely needed.
⚠️

Common Trap — Avoid writing your own ORM

for an application unless it is specifically for learning purposes. Existing ORM libraries are well-tested, optimised and feature-rich, and are difficult to replicate from scratch.

Defining Models in Django

Models in Django are implemented via Python classes, and they form the canonical representation of your entities. The models are used to generate the underlying database schema as well as the Python-database interfaces for accessing those tables.

For the examples in this lab, all models are placed in a single file, models.py. In assignments you might consider splitting models into separate files when the models file becomes too large or complex (20+).

⚠️

Common Trap — Model inheritance:

Django model inheritance works almost identically to normal Python class inheritance, but be careful. Each model you want in your application must subclass the django.db.models.Model class, and the attributes of your Python class become database fields.

A Basic Model

Each attribute must be mapped to an appropriate Django Field class, so Django knows the type of each attribute and can generate an accurate schema. Fields can be customised with default values, unique constraints and validations. For example, a Post model with a title and content:

from django.db import models

class Post(models.Model):
    title = models.CharField(max_length=100)
    content = models.TextField()
✅

Exam Tip:

Models are the single source of truth for your schema — Django generates the database tables from them, not the other way around.

06

Relationship Field Types

Relationships between models are represented with specific field types:

  • Many-to-one: models.ForeignKey on the many-side model.
  • Many-to-many: models.ManyToManyField on either (or both) models.
  • One-to-one: models.OneToOneField or models.ForeignKey(unique=True).
  • Many-to-optional-one: models.ForeignKey(null=True, blank=True) on the many-side model.

Many-to-One (ForeignKey)

An Author can write many Book instances, but each Book has only one Author.

from django.db import models

class Author(models.Model):
    name = models.CharField(max_length=100)
    bio = models.TextField()

    def __str__(self):
        return self.name

class Book(models.Model):
    title = models.CharField(max_length=200)
    author = models.ForeignKey(Author, on_delete=models.CASCADE, related_name='books')
    published_date = models.DateField()

    def __str__(self):
        return self.title

Many-to-Many (ManyToManyField)

A Student can enroll in many Course instances, and a Course can have many Student instances.

from django.db import models

class Student(models.Model):
    name = models.CharField(max_length=100)
    age = models.IntegerField()

    def __str__(self):
        return self.name

class Course(models.Model):
    name = models.CharField(max_length=100)
    description = models.TextField()
    students = models.ManyToManyField(Student, related_name='courses')

    def __str__(self):
        return self.name

One-to-One

A User can have exactly one UserProfile, and a UserProfile can belong to exactly one User.

from django.db import models
from django.contrib.auth.models import User

class UserProfile(models.Model):
    user = models.OneToOneField(User, on_delete=models.CASCADE)
    bio = models.TextField()
    profile_picture = models.ImageField(upload_to='profiles/')

    def __str__(self):
        return self.user.username

The one-to-one alternative uses ForeignKey(..., unique=True):

class UserProfile(models.Model):
    user = models.ForeignKey(User, on_delete=models.CASCADE, unique=True)
    bio = models.TextField()
    profile_picture = models.ImageField(upload_to='profiles/')

    def __str__(self):
        return self.user.username

Many-to-Optional-One

An Employee can belong to one Department, but not every Employee has to be assigned to a department.

from django.db import models

class Department(models.Model):
    name = models.CharField(max_length=100)

    def __str__(self):
        return self.name

class Employee(models.Model):
    name = models.CharField(max_length=100)
    department = models.ForeignKey(Department, on_delete=models.SET_NULL, null=True, blank=True)

    def __str__(self):
        return self.name
🧠

Memory Hook:

FK = many-to-one (on the many side), M2M = many-to-many, OneToOneField = one-to-one, and adding null=True, blank=True makes a FK optional.
07

Direct vs String References

When defining relationships between models, you can refer to a related model in two ways: directly by class name or using a string reference.

Referring Directly by Class Name

If the related model is already defined in the file, you can refer to it by its class name. This is straightforward and used when there is no circular dependency, or when the order of model definitions can be managed.

class Tag(models.Model):
    name = models.CharField(max_length=100)

class Post(models.Model):
    tag = models.ForeignKey(Tag, on_delete=models.CASCADE)  # Direct reference

Referring Using a String Reference

If the related model is not yet defined, refer to it using a string containing the model's name. This lets you define models in any order, including cases where two models refer to each other (mutual or circular references).

class Post(models.Model):
    tag = models.ForeignKey("Tag", on_delete=models.CASCADE)  # String reference

# Defined later
class Tag(models.Model):
    name = models.CharField(max_length=100)
ℹ️

Background — Lazy relationships:

String references (also known as lazy relationships) also work when a model wants to reference itself.
08

Circular Dependencies & Deadlocks

If two models refer to each other, reordering their definitions won't solve the problem because both depend on each other. In such cases you use a string reference to break the circular dependency.

class Author(models.Model):
    name = models.CharField(max_length=100)
    favorite_book = models.ForeignKey("Book", on_delete=models.CASCADE, null=False)  # String reference

class Book(models.Model):
    title = models.CharField(max_length=200)
    author = models.ForeignKey(Author, on_delete=models.CASCADE)  # null=False by default
⚠️

Common Trap — The example is a deadlock:

Avoid circular foreign keys where both sides are required. Making Book.author and Author.favorite_book non-nullable creates a chicken-and-egg situation: you cannot create either row first.
⚠️

Common Trap — Avoid circular dependency:

Circular references are not inherently invalid, but they should be used with caution. They can lead to complex migration dependencies and maintenance challenges. This complexity arises because Django models map to a relational database, which follows a static schema and enforces referential integrity. Unlike runtime memory, where objects can point to each other freely, relational databases require all references to be well-defined ahead of time. Circular references are often a sign that your model design could be simplified.

The TIL Models

In the TIL ERD, a Post can be associated with zero, one or many Tags, and a Tag can be applied to one or many Posts.

⚠️

Common Trap:

The ERD has not been normalised to show mapping tables (the many-to-many between Post and Tag).

Turning the TIL ERD into models gives the following Python classes in til_app/models.py:

# til_app/models.py
from django.db import models

class Tag(models.Model):
    name = models.CharField(max_length=10, unique=True)
    creation_date = models.DateTimeField(auto_now_add=True)

class Post(models.Model):
    subject = models.CharField(max_length=160)
    content = models.CharField(max_length=800)
    # creator = ???  # Django built-in auth user
    visibility = models.BooleanField(default=True)
    created_at = models.DateTimeField(auto_now_add=True)

    tags = models.ManyToManyField(Tag, related_name='posts', blank=True)  # Many-to-many relationship

With related_name, you can do things like tag_instance.posts.all(), which returns all posts associated with a Tag instance.

ℹ️

Background:

For now the creator of a Post is left out, because an in-built Django user system (the auth application) is introduced in the next lab.
⚠️

Common Trap:

The ManyToManyField in Django does not provide built-in support for enforcing constraints like "at least one." To ensure a Tag is always associated with one or more Posts, you need custom validations and signals (covered in a later lab).
ℹ️

Background:

While Django's ManyToManyField automatically creates an intermediary model for managing many-to-many relationships, it may lack flexibility for complex use cases. When you need more control — extra fields on the relationship or custom constraints — it is often better to define an explicit mapping class instead of relying on ManyToManyField.

Activating Your App

Now that models are defined, integrate them into the project. Django maintains a list of installed applications in settings.py under INSTALLED_APPS. By default, Django comes with these applications installed:

INSTALLED_APPS = [
    'django.contrib.admin',
    'django.contrib.auth',
    'django.contrib.contenttypes',
    'django.contrib.sessions',
    'django.contrib.messages',
    'django.contrib.staticfiles',
]

Before Django can generate the schema for your models, add your TIL application to the list of installed applications. This is done by including the TilAppConfig class defined in apps.py:

INSTALLED_APPS = [
    'til_app.apps.TilAppConfig',
    'django.contrib.admin',
    'django.contrib.auth',
    # ...
]
💡

Why It Matters:

If your app is not in INSTALLED_APPS, Django will not see your models, and makemigrations will produce nothing. This is a very common beginner mistake.

Making & Viewing Migrations

Django can generate and manage the database schema from your Python model files. Once models are defined and the app is installed, you use Django's tools to generate schemas.

Make Migrations

Create migrations for a specific app:

# Generate migrations for a specific app.
# The application name is optional.
# With no name, Django checks all installed apps.
python3 manage.py makemigrations <application>

Or check all installed apps for pending changes:

python3 manage.py makemigrations

The second form checks all apps listed in INSTALLED_APPS and creates migrations for all apps that have pending changes. For our example:

$ python3 manage.py makemigrations til_app
Migrations for 'til_app':
  til_app/migrations/0001_initial.py
    - + Create model Tag
    - + Create model Post

This generates a migration file at til_app/migrations/0001_initial.py but does not apply it yet.

View Migrations

To see the corresponding SQL commands that will be run against the database, use sqlmigrate:

python manage.py sqlmigrate til_app 0001

Example output (for SQLite):

BEGIN;
-- Create model Tag --
CREATE TABLE "til_app_tag" (
  "id" INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
  "name" VARCHAR(10) NOT NULL UNIQUE,
  "creation_date" DATETIME NOT NULL
);
-- Create model Post --
CREATE TABLE "til_app_post" (
  "id" INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
  "subject" VARCHAR(160) NOT NULL,
  "content" VARCHAR(800) NOT NULL,
  "visibility" BOOL NOT NULL,
  "created_at" DATETIME NOT NULL
);
-- Create many-to-many table for Post and Tag relationship --
CREATE TABLE "til_app_post_tags" (
  "id" INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
  "post_id" BIGINT NOT NULL REFERENCES "til_app_post" ("id") DEFERRABLE INITIALLY DEFERRED,
  "tag_id" BIGINT NOT NULL REFERENCES "til_app_tag" ("id") DEFERRABLE INITIALLY DEFERRED
);
CREATE UNIQUE INDEX "til_app_post_tags_post_id_tag_id_3b9d1d8d_uniq"
  ON "til_app_post_tags" ("post_id", "tag_id");
CREATE INDEX "til_app_post_tags_post_id_96b51563" ON "til_app_post_tags" ("post_id");
CREATE INDEX "til_app_post_tags_tag_id_d18818ba" ON "til_app_post_tags" ("tag_id");
COMMIT;
ℹ️

Background:

This SQL has been generated for SQLite; changing the database engine is discussed later in the lab.
✅

Exam Tip:

Notice that Django automatically creates a junction table til_app_post_tags to manage the ManyToManyField relationship — this is the normalised mapping table the Week 1 ERD taught you about.

Applying Migrations & Workflow

Apply Migrations

To apply your migration to the database, use the migrate command:

# Apply migrations to the database.
# The application argument is optional.
# With no argument, all unapplied migrations run.
python3 manage.py migrate <application|optional>

This runs any migrations from all installed applications that have not yet been applied:

$ python manage.py migrate
Operations to perform:
  Apply all migrations: admin, auth, contenttypes, sessions, til_app
Running migrations:
  Applying contenttypes.0001_initial... OK
  Applying auth.0001_initial... OK
  Applying admin.0001_initial... OK
  ...
  Applying sessions.0001_initial... OK
  Applying til_app.0001_initial... OK

The Workflow

Applying models and getting them into the database involves three steps:

  1. Modify the model Python files (models.py).
  2. Run python manage.py makemigrations.
  3. Run python manage.py migrate.
⚠️

Common Trap — Stay in sync:

Modifying model files without applying migrations, or modifying the database schema without modifying the models, can cause many issues. It is critical to keep these in sync.
✅

Exam Tip:

Examine the generated migration code before you run it, especially when complex changes are involved, and always back up your data before running a migration.
🧠

Memory Hook:

Model → makemigrations → migrate — "write, prepare, apply".

Choosing the Database Engine

By default, Django uses SQLite, a standalone file-based database, as its database engine. You may also use MySQL or PostgreSQL for eventual deployment into AWS.

The database engine is configured in settings.py under the DATABASES variable:

DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.sqlite3',
        'NAME': BASE_DIR / 'db.sqlite3',
    }
}
ℹ️

Background:

SQLite is typically sufficient for your group assignment if you are not familiar with database engine mechanisms. Changing the engine is documented in Django's database reference.

The Django Admin Interface

Django comes with a powerful admin interface automatically out of the box at http://127.0.0.1:8000/admin. It lets you add, edit and delete models with very little application code. You need to be running the app with python manage.py runserver to access it.

⚠️

Common Trap — Don't use Django admin for end users:

The admin interface is designed for site administrators/developers, not end users. It is a place for site administrators (like an ICT team) to add/edit/delete data and perform site management tasks. Although it is possible to stretch it into something end users could use, you really should not — it is not designed for every site visitor.

Create an Admin User

The admin interface is guarded by username/password credentials. The auth application exposes a command to create superusers:

python manage.py createsuperuser
$ python manage.py createsuperuser
Username (leave blank to use 'user'): user
Email address: user@user.com
Password:
Password (again):
Superuser created successfully.

These users have access to the admin interface and provide an easy way to bootstrap new admin users without touching the database directly. You can run createsuperuser multiple times to add more superusers.

⚠️

Common Trap:

The Django auth application has default rules preventing common and insecure passwords. While you can bypass them, it is not recommended. Once your user is created, log in at http://127.0.0.1:8000/admin (or whatever port you are using).

Add Models to Django Admin

Models are not automatically exposed through the admin interface. Register them from the TIL application by modifying til_app/admin.py and calling admin.site.register(<model>):

from django.contrib import admin
from .models import Post, Tag

admin.site.register(Post)
admin.site.register(Tag)

Reload the admin interface and you will see the TIL application and its exposed models.

Secure the Django Admin

Because the admin gives special powers, it is good practice to make it extra secure:

  • Change the default admin URL — Django co-leader Jacob Kaplan-Moss (paraphrased) suggests using a different name (or even a different domain) for the admin. It also prevents attackers from profiling your site: they can tell which version of Django you use, sometimes down to the point release, by examining the HTML of the login screen at admin/.
  • Limit admin access based on IP — configure your web server to allow access only from certain IP addresses. An acceptable alternative is to put this logic into middleware: easy to implement, no web-server changes, but it introduces slight performance overhead compared with doing it at the web-server level.
ℹ️

Background:

You are not required to secure the Django admin for your assignments.
✅

Exam Tip:

The admin is a development/administration tool. Your users interact with the views and templates you build — not the admin.

Further readings: Greenfeld & Roy Greenfeld, Two Scoops of Django 3.x: Best Practices for the Django Web Framework — especially Chapter 1 (Coding Style), Chapter 2 (Optimal Django Environment Setup), Chapter 3 (How to Lay Out Django Projects) and Chapter 5 (Settings and Requirements Files).

Key Takeaways

  1. 1
    An ORM maps objects to tables — classes become tables, instances become rows, and attributes become columns.
  2. 2
    ORMs abstract SQL — they handle data conversion, are database-agnostic, and reduce boilerplate code.
  3. 3
    ORM benefits include DRY, MVC, security and loose coupling — prepared statements and transactions come easily.
  4. 4
    ORM limits — a learning curve, possible performance gaps vs hand-written SQL, and the object/relational impedance mismatch.
  5. 5
    Use ORMs by default; drop to raw SQL only when necessary — and never write your own ORM for a real application.
  6. 6
    Django models are Python classes subclassing django.db.models.Model — they are the canonical source of the schema.
  7. 7
    Every attribute maps to a Field type — CharField, TextField, IntegerField, FloatField, BooleanField, Date/DateTimeField, EmailField, URLField, ImageField, FileField.
  8. 8
    Relationships have dedicated fields — ForeignKey (many-to-one), ManyToManyField (many-to-many), OneToOneField (one-to-one), and ForeignKey(null=True, blank=True) (many-to-optional-one).
  9. 9
    Refer to models directly or by string — string references (lazy relationships) let you define models in any order and break circular dependencies.
  10. 10
    Avoid required circular FKs — they create a chicken-and-egg deadlock; circular references add migration complexity and often signal over-complex design.
  11. 11
    Add your app to INSTALLED_APPS — otherwise Django cannot see your models.
  12. 12
    The migration workflow is Model → makemigrations → migrate — and sqlmigrate shows the SQL that will run.
  13. 13
    Django auto-creates junction tables for many-to-many — e.g. til_app_post_tags with a unique index on the pair of foreign keys.
  14. 14
    The admin is for administrators, not end users — create a superuser, register models, and consider hardening the admin URL and IP access.

Glossary

ORM

Object-Relational Mapping — a technique mapping objects to relational database tables.

Django ORM

Django's built-in ORM for defining models and querying the database in Python.

Hibernate

A well-known ORM library for Java.

Model

A Python class subclassing django.db.models.Model that defines a database table.

Field

A Django class describing a model attribute's type and constraints.

CharField

A string field with a maximum length.

TextField

A long text field without a database max length.

IntegerField

An integer field.

FloatField

A floating-point number field.

BooleanField

A true/false field.

DateField

A date field (no time).

DateTimeField

A date-and-time field.

EmailField

A string field for email addresses, with validation.

URLField

A string field for URLs, with validation.

ImageField

A field for uploading image files.

FileField

A field for uploading any file.

ForeignKey

A many-to-one relationship field placed on the many-side model.

ManyToManyField

A many-to-many relationship field.

OneToOneField

A one-to-one relationship field.

on_delete

The behaviour when the referenced row is deleted (e.g. CASCADE, SET_NULL).

CASCADE

Deletes dependent rows when the referenced row is deleted.

SET_NULL

Sets the foreign key to NULL when the referenced row is deleted (requires null=True).

related_name

The name used to access the reverse relation (e.g. tag_instance.posts.all()).

null=True

Allows the database column to store NULL.

blank=True

Allows the field to be left empty in forms/validation.

unique=True

Enforces uniqueness for the column.

Lazy relationship

A string reference to a model that is resolved later by Django.

Circular dependency

Two models referencing each other, requiring string references and careful migration handling.

Referential integrity

The database rule that all references must point to valid rows.

Impedance mismatch

The conceptual gap between object models and relational tables.

DRY

Don't Repeat Yourself — define a model once and reuse it.

MVC

Model–View–Controller — the architectural pattern ORMs encourage.

Migration

A file describing a schema change generated from your models.

makemigrations

The command that generates migration files from model changes.

migrate

The command that applies migrations to the database.

sqlmigrate

The command that prints the SQL a migration will run.

Junction table

A table Django auto-creates for a many-to-many relationship (e.g. til_app_post_tags).

INSTALLED_APPS

The settings list of apps Django should load and manage.

TilAppConfig

The app configuration class in apps.py, added to INSTALLED_APPS.

DATABASES

The settings variable defining the database engine and connection.

SQLite

Django's default standalone, file-based database engine.

PostgreSQL / MySQL

Relational databases often used for deployment (e.g. on AWS).

Admin site

Django's built-in interface (/admin) for administrators to manage data.

Superuser

A privileged account created by createsuperuser with admin access.

admin.site.register

The call that exposes a model in the admin interface.

Middleware

A layer that processes requests/responses globally, usable to restrict admin access by IP.

Worked Examples & Scenarios

Example 1

From ERD to models

The TIL ERD has a many-to-many between Post and Tag. This becomes:

class Tag(models.Model):
    name = models.CharField(max_length=10, unique=True)
    creation_date = models.DateTimeField(auto_now_add=True)

class Post(models.Model):
    subject = models.CharField(max_length=160)
    content = models.CharField(max_length=800)
    visibility = models.BooleanField(default=True)
    created_at = models.DateTimeField(auto_now_add=True)
    tags = models.ManyToManyField(Tag, related_name='posts', blank=True)

related_name='posts' lets you call tag_instance.posts.all() to get every post for a tag.

Example 2

Choosing a relationship field

  • Author writes many Books, each Book has one Author → ForeignKey(Author, on_delete=models.CASCADE, related_name='books') on Book.
  • Student enrolls in many Courses, a Course has many Students → ManyToManyField(Student, related_name='courses') on Course.
  • User has exactly one UserProfile → OneToOneField(User, on_delete=models.CASCADE).
  • Employee may or may not have a Department → ForeignKey(Department, on_delete=models.SET_NULL, null=True, blank=True).
Example 3

Breaking a circular reference

If Author needs a favorite_book and Book needs an author, define the reference as a string:

class Author(models.Model):
    favorite_book = models.ForeignKey("Book", on_delete=models.CASCADE, null=False)

class Book(models.Model):
    author = models.ForeignKey(Author, on_delete=models.CASCADE)

This compiles, but if both sides are non-nullable it is a deadlock — you cannot create the first row. Prefer making at least one side optional or redesigning.

Example 4

Tracing a migration to SQL

Run python3 manage.py makemigrations til_app, then python manage.py sqlmigrate til_app 0001. Django prints CREATE TABLE "til_app_tag", CREATE TABLE "til_app_post", and a junction table til_app_post_tags with post_id and tag_id foreign keys plus a unique index on the pair. This confirms the ORM translated your Python classes into normalised SQL.

Example 5

Exposing models in the admin

from django.contrib import admin
from .models import Post, Tag

admin.site.register(Post)
admin.site.register(Tag)

After createsuperuser and a server reload, log in at /admin and you can create, edit and delete Posts and Tags without writing any management views.
