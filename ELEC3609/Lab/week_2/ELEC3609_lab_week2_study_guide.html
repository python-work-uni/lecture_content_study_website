RESTful APIs and Team Collaboration: From Client Requests to GitHub Workflows

This lab explains how modern web applications talk to each other through RESTful APIs — the standard HTTP methods, request and response anatomy, authentication, and the architectural constraints behind them — and then shows how frontend and backend teams stay aligned using API contracts and GitHub collaboration habits.

Read this first: A RESTful API is a convention, not a technology. It says "treat everything as a resource with a URL, and act on it with the standard HTTP verbs GET, POST, PUT and DELETE." Once you internalise the request/response cycle and the constraints that make it work, every endpoint, status code and collaboration practice in this lab becomes predictable.

From Query-String Scripts to REST

REST exists because exposing implementation details in URLs made early web systems fragile and insecure.

In the late 1990s, web URLs often directly exposed server-side scripts and included explicit arguments that stated the action and the data. A typical URL looked like this:

getdata.php?user=123&action=fetch

This worked, but it had serious drawbacks:

  • It tightly coupled URL structure to specific implementation details, so systems became less flexible and harder to maintain.
  • It posed security risks by exposing methods and parameters directly in the URL.

As web development evolved, the need for more scalable, secure and maintainable solutions led to RESTful APIs.

RESTful API — An API design style that uses standardised HTTP methods, stateless communication, and resource-based URLs (for example GET /users/123) to abstract server implementation details away from the client.

A RESTful API is built on three ideas:

  1. Standardised HTTP methods — the same verbs (GET, POST, PUT, DELETE) mean the same thing everywhere.
  2. Stateless communication — each request carries everything the server needs to understand it.
  3. Resource-based URLs — the URL names a thing, not an action.

This shift enhances security by standardising access and using modern security practices, and it supports better scalability and flexibility across many client types, including mobile apps and other web services.

⚠️
Common trap: RESTful API is not a protocol, library, or tool. It is a style, convention, or set of design principles for building web APIs. REST uses HTTP as the underlying protocol and applies standardised methods like GET, POST, PUT and DELETE to interact with resources identified by URLs.

The Anatomy of a RESTful API Call

A RESTful API separates client and server so they can be developed and scaled independently.

The basic function of a RESTful API is similar to browsing the internet: the client contacts the server by making a request to retrieve or manipulate a resource, and the server responds with the result.

A typical RESTful API call works through four steps:

  1. The client sends an HTTP request to the server.
  2. The server authenticates the request if needed (for example, with an API key or token).
  3. The server processes the logic (for example, fetch, create, update or delete data).
  4. The server sends an HTTP response containing status and data (for example, JSON).
Client→HTTP Request→Server→Authentication→Business Logic→HTTP Response (status + data)→Client
💡
Why it matters: The client never needs to know how the server is implemented, and the server never stores client context. That separation is what "allows independent development and scalability" — the two sides can change, grow or be replaced without breaking the other.

Building the Client Request

Every RESTful API request is assembled from five parts: URL, method, headers, body, and parameters.

A RESTful API request typically includes the following components.

1. Unique Resource Identifier

Each resource is identified by a URL (Uniform Resource Locator), also known as the request endpoint. Example:

GET https://api.example.com/posts/22

2. HTTP Method

The HTTP method tells the server what action to perform on the resource (covered in the next section).

3. HTTP Headers

Headers provide metadata about the request and response format, authentication, and caching. Example:

Content-Type: application/json
Accept: application/json
Authorization: Bearer <token>

4. Request Body (Data)

For methods like POST and PUT, the client includes a data payload in the request body. Example:

{ "title": "New Post", "author": "User123" }

5. Parameters

Clients may send extra information through parameters to help the server process the request.

Parameter TypeDescription
Path ParametersPart of the URL to identify specific resources. E.g. /posts/22
Query ParametersProvide filtering or sorting logic. E.g. /posts?author=Admin
Cookie ParametersSent via cookies, often for session or quick auth purposes.

Worked example: a curl request

The following command updates an Imgur account's settings:

curl -X PUT https://api.imgur.com/3/account/ImgurUser/settings \
  -H "Authorization: Bearer YOUR_ACCESS_TOKEN" \
  -H "Content-Type: multipart/form-data" \
  -F "bio=Long time lurker..." \
  -F "public_images=false" \
  -F "messaging_enabled=true" \
  -F "accepted_gallery_terms=true" \
  -F "show_mature=true" \
  -F "newsletter_subscribed=true"
PartExplanation
-X PUTSpecifies the HTTP method as PUT, which updates a resource.
-HAdds a custom HTTP header. Here two headers are used.
Authorization: Bearer ...Passes the access token to authenticate the request.
Content-Type: multipart/form-dataTells the server you are sending form fields in a possibly file-like format.
-FSends a form field as a key-value pair. Multiple -F flags send multiple fields in the body.
🧠
Memory hook: U-M-H-B-P — URL, Method, Headers, Body, Parameters. Every request is those five, in that order of importance.

HTTP Methods: The Verbs of REST

The HTTP method tells the server which standard operation to perform on the resource.

MethodDescription
GETRetrieve data from the server. GET requests can be cached and may include query parameters.
POSTSend new data to the server. Repeating a POST may result in multiple records.
PUTUpdate an existing resource. Repeating a PUT gives the same result each time.
DELETERemove a resource. May fail if authentication is not valid.
💡
Why it matters: The difference between repeating POST and repeating PUT is the whole point of predictable APIs. POST is not safe to repeat — two identical POSTs can create two records. PUT is repeatable (idempotent) — sending it twice leaves the data in the same state. This is why updates use PUT and submissions use POST.
ℹ️
Note: GET requests are cacheable and frequently carry query parameters for filtering or sorting. DELETE removes a resource but will fail if the request is not authenticated correctly.
🤔

Authenticating RESTful Requests

A RESTful web service authenticates requests before sending responses, so only authorised users reach protected resources.

Authentication verifies the client's identity and ensures only authorised users can access protected resources. A RESTful web service authenticates requests before sending responses.

Common authentication methods

MethodDescriptionSecurity Notes
Basic AuthenticationSends a username and password in the HTTP header, encoded using Base64.Easy to implement but not secure unless used over HTTPS. Susceptible to interception.
Bearer AuthenticationSends an access token (a string) in the HTTP header as proof of identity.More secure than basic auth. Common in OAuth flows. The token should be kept secret.
API KeyA unique identifier (string) given to each client to access resources. Included in headers or query parameters.Simple to use but less secure. If exposed, anyone can use the key. Often rate-limited.
OAuthA robust framework that uses both a password and a token for access. Supports scopes, refresh tokens, and expiration.Highly secure. Ideal for third-party integrations. Can be complex to implement initially.
⚠️
Common trap (No HTTP): All authentication methods should be used over HTTPS to prevent credentials or tokens from being intercepted. Basic auth especially is only safe on top of HTTPS.
🧠
Memory hook: Order them by strength — Basic < API Key < Bearer < OAuth. OAuth earns its complexity by adding scopes, refresh tokens and expiry.

Reading the Server Response

When a RESTful API server receives a valid request, it returns a response made of a status line, a message body, and response headers.

1. Status Line

The status line includes a 3-digit HTTP status code that tells the client the result of the request.

Code RangeMeaningExamples
2xx SuccessThe request was successfully processed.200 OK, 201 Created
3xx RedirectionFurther action is required to complete the request.301 Moved Permanently
4xx Client ErrorThe request was incorrect or unauthorised.400 Bad Request, 404 Not Found
5xx Server ErrorThe server encountered an error.500 Internal Server Error
🧠
Memory hook: First digit names the culprit — 2 = everything fine, 3 = go elsewhere, 4 = you (client) made a mistake, 5 = they (server) broke.

2. Message Body

The message body contains the data returned by the server, often in JSON format. Example response body (JSON):

{ "id": 102, "name": "John", "age": 30, "email": "john@example.com" }
ℹ️
Note: The format (JSON or XML) is usually negotiated via the request header, for example Accept: application/json.

3. Response Headers

Response headers provide metadata about the response. They are not part of the main data but give useful context.

HeaderDescription
Content-TypeFormat of the response body (application/json)
Content-LengthSize of the body in bytes
ServerInfo about the server software
DateTimestamp of the response
Cache-ControlWhether/how long the response is cached
Access-Control-Allow-OriginCORS setting for cross-origin requests

Full response example (text format)

HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 67
Date: Tue, 22 Jul 2025 06:45:00 GMT
Server: nginx/1.18.0

{ "id": 102, "name": "John", "age": 30, "email": "john@example.com" }

REST as an Architectural Style

REST is not a protocol but an architectural style, defined by six constraints that make networked systems scalable, reliable and evolvable.

REST (Representational State Transfer) was introduced by Roy Fielding in his doctoral dissertation to describe a set of architectural constraints that, when applied, enable scalable, reliable, and evolvable systems — especially in web services.

These constraints are not exclusive to HTTP or web APIs. They represent a general model for designing distributed systems that emphasise clarity, separation of concerns, and stateless communication. RESTful APIs happen to be one concrete application of these principles over HTTP.

Architectural constraints of REST

ConstraintDescription
StatelessEach client request must contain all the information necessary to understand and process it. The server should not store any client context between requests. This improves scalability and reliability.
CacheableServer responses should explicitly indicate whether they are cacheable. This enables clients and intermediaries to reuse responses and reduces redundant requests.
Uniform InterfaceREST enforces a standardised way to communicate between client and server. This includes using HTTP methods (GET, POST, PUT, DELETE), predictable URIs, and common data formats like JSON.
Client–Server SeparationThe client and server operate independently. The client does not need to know about server implementation details, and the server does not manage client state. This allows greater portability and scalability.
Layered SystemREST allows intermediate layers (such as load balancers, proxies, or security filters) between client and server. These layers should not affect the request or response but can enhance performance, scalability, and security.
Code-on-Demand (optional)Servers can temporarily extend client functionality by transferring executable code (for example JavaScript). This constraint is optional and less commonly used in RESTful API design.
🧠
Memory hook: S-C-U-C-L-C — Stateless, Cacheable, Uniform interface, Client–server, Layered, Code-on-demand. Only the last is optional.

Designing Resource-Oriented APIs

A good RESTful API is a thoughtful, resource-oriented interface, not just a CRUD wrapper over HTTP.

When we design a RESTful API, we apply the architectural constraints to HTTP-based services. Follow the design principles of RESTful APIs to reduce redundancy and create a clear, interactive, and user-friendly interface.

"Non-CRUD" (resource-oriented) actions

The central move is: instead of calling an action, create a resource.

  • Instead of an action, create a resource. Rather than a URL like /activateAccount that directly calls an action, use /account-activation, which represents it as a resource.
  • Instead of "login", create a "session". Instead of /login, use /sessions to create a new session. The focus shifts from the act of logging in to the creation of a session resource.
  • Instead of "closing account", create a "closing". This rephrases the action as managing a resource, /accountclosings. This might involve POSTing to that resource to request an account closure.

Aligning with HTTP protocol semantics

HTTP is inherently designed to work with resources identified by URIs (Uniform Resource Identifiers). Methods (verbs) like GET, POST, PUT and DELETE are designed to perform standard operations on those resources. Using these methods in the way the HTTP specification intends makes your API predictable and aligned with web standards, which makes understanding and integration easier.

Simplifying and standardising endpoints

When APIs focus on resources rather than actions, the number of endpoints typically reduces and their purpose becomes clearer.

Resource-oriented

An endpoint like /sessions handles all actions related to session management. Creating a session (logging in) is a POST to /sessions; deleting a session (logging out) is a DELETE.

Action-oriented

Different actions need different endpoints, like /login for logging in and /logout for logging out — even though they relate to the same conceptual resource (user sessions).

✅
Exam tip: This approach reduces the cognitive load for developers who use your API, because they can often guess endpoint URLs from standard practices instead of memorising multiple endpoints for related actions.

API Contracts: The Team Interface

An API contract is the shared agreement that lets backend and frontend teams build against the same expectations.

An API contract defines the expectations and agreements between the API providers (the backend) and its consumers (the frontend). It is essential because:

  • With a clear contract, developers can build and integrate with the API more effectively.
  • It reduces the likelihood of misunderstandings and errors.
  • It serves as a reference point or verification for any updates or changes, ensuring all parties stay aligned on how the API should function.
💡
Why it matters: In a real team, the frontend cannot see or control the backend's code. The contract is the one artefact both sides can point to when something does not match — it is what makes parallel development possible.
ℹ️
Note: A template is provided on Canvas that shows exactly what an API contract should include. Use it when documenting your own endpoints.

REST APIs in Django (and DRF)

Django can serve JSON with plain views, but a dedicated framework makes APIs cleaner, more scalable and more feature-rich.

Traditional Django views

  • Traditional views in Django return HttpResponse objects, often rendering HTML.
  • You can return JSON manually using JsonResponse and manually serialising data.
  • However, this method:
  • Is not scalable or clean for building APIs.
  • Is more suitable for server-rendered web applications.
  • Concerns to consider: business logic separation, scalability, and performance optimisation.

The need for Django REST Framework (DRF)

  • In modern web applications (for example React SPAs, mobile apps), the backend often acts as an API-only layer.
  • All frontend–backend communication happens via JSON APIs.
  • This is known as a headless architecture, where frontend and backend are separated.
  • Django REST Framework (DRF):
  • Extends Django's capabilities to build Web APIs.
  • Is optimised for JSON and other content types.
  • Supports serialisation and deserialisation, permissions and authentication, and many features out of the box.

JsonResponse

A lightweight solution that returns JSON directly from any view. Requires only a small amount of code to serialise your data. Good for simple needs.

Django REST Framework

A cleaner, more scalable API design with serialisation, authentication and permissions built in. Recommended when you build a real API.

⚠️
Assignment requirement: You are allowed to use raw HttpResponse and return HTML using Django's built-in view functions to meet the basic requirements. However, your project must include API endpoints that return data in JSON format. This can be done with simple JsonResponse objects or by creating a separate set of endpoints dedicated to JSON output. Either is acceptable, but DRF is recommended.
ℹ️
Note: You will learn how to build RESTful APIs in Django using Django REST Framework (DRF) in the upcoming labs.

GitHub Collaboration Habits

Git's real value shows up in team development, so this section focuses on collaboration habits — not Git commands.

Git is a powerful version control system, but its real value and complexity become clear in team-based development. The point here is practical GitHub collaboration habits that help you avoid conflicts, stay organised, and communicate effectively — not memorising Git commands.

✅
Note: You are not expected to master every Git command now. Build the right habits so your future work becomes easier to manage and scale.

3.1 Getting started with GitHub tools

  • Git-SCM Book — a comprehensive guide to Git.
  • GitHub Getting Started — the official GitHub beginner guide.
  • GitHub Desktop — a GUI client for GitHub that simplifies version control for beginners.

GitHub Desktop is beginner-friendly and includes visualisation tools to help you manage changes without using the command line.

3.2 Work together with pull requests

  • Protect important branches. Use protected branches (for example main) to prevent accidental changes, and set conditions such as requiring CI tests or code reviews before merging.
  • Define push rules. Set rulesets to control what gets pushed (for example file types and sizes). Useful for internal repositories or larger teams with stricter controls.
  • Resolve merge conflicts before merging. GitHub blocks merging if there are unresolved conflicts between branches. Always check and resolve these using the file list shown above the merge button.

3.3 Track and plan with GitHub Issues

Use GitHub Issues to:

  • Track bugs, ideas, tasks, or any piece of work.
  • Link issues to pull requests for visibility and context.
  • Collaborate by assigning tasks to team members.

Helpful actions:

  • Link a PR to an issue.
  • Create a branch for an issue.
  • Assign issues and PRs.
✅
Exam tip: Defining a clear commit message guideline and a consistent branch naming convention helps your team organise the repository and speeds up reviews and debugging. See the further readings for suggested styles, or explore how mature open-source projects manage their repositories for real-world examples.

Glossary

Every term you need to speak this week's language.

REST
Representational State Transfer — an architectural style introduced by Roy Fielding describing constraints for scalable, reliable and evolvable networked systems.
RESTful API
An API that applies REST principles over HTTP using standardised methods and resource-based URLs.
Resource
Any entity a client interacts with, identified by a URL/endpoint, such as /posts/22.
Stateless
A constraint requiring each request to carry all information needed to process it, with no server-side client context stored between requests.
Uniform Interface
A REST constraint enforcing standardised HTTP methods, predictable URIs and common data formats like JSON.
Client–Server Separation
A REST constraint in which client and server operate independently, with neither managing the other's internals or state.
Layered System
A REST constraint allowing intermediaries such as load balancers, proxies and security filters between client and server.
Code-on-Demand
The optional REST constraint in which servers transfer executable code (e.g. JavaScript) to extend client functionality.
HTTP Method
The verb in a request (GET, POST, PUT, DELETE) that tells the server which standard operation to perform.
Path Parameter
A value embedded in the URL path that identifies a specific resource, e.g. /posts/22.
Query Parameter
A value appended to a URL after ? used for filtering or sorting, e.g. /posts?author=Admin.
Cookie Parameter
Data sent via cookies, often for session or quick authentication purposes.
Basic Authentication
Sends a Base64-encoded username and password in the HTTP header; easy but insecure without HTTPS.
Bearer Authentication
Sends an access token string in the HTTP header as proof of identity; common in OAuth flows.
API Key
A unique identifier string issued to each client for access, sent in headers or query parameters; simple but easily exposed.
OAuth
A robust access framework using a password plus a token, with scopes, refresh tokens and expiration; ideal for third-party integrations.
HTTP Status Code
A 3-digit number in the status line indicating the result of a request.
API Contract
The agreement defining expectations between API providers (backend) and consumers (frontend), used as a reference for changes.
Headless Architecture
A design in which the backend is an API-only layer and frontend and backend are separated, communicating via JSON APIs.
Django REST Framework
A Django extension for building Web APIs, optimised for JSON with serialisation, authentication and permissions built in.
JsonResponse
A lightweight Django class for returning JSON directly from a view with minimal serialisation code.
Pull Request
A GitHub mechanism for reviewing and merging proposed branch changes, blocked automatically when merge conflicts are unresolved.
Protected Branch
A branch (e.g. main) configured to prevent accidental changes, optionally requiring CI tests or code reviews before merging.
Ruleset
A GitHub setting controlling what may be pushed, such as permitted file types or sizes.

Practice Questions

Look away from the page first — retrieval is what builds memory.

Answer, reveal, then tick “Mastered”. Your progress is saved.
Q1

Why did the web move away from URLs like getdata.php?user=123&action=fetch toward RESTful APIs? Give two distinct reasons.

Answer: First, query-string script URLs tightly coupled URL structure to specific implementation details, making systems less flexible and harder to maintain. Second, exposing methods and parameters directly in the URL posed security risks. RESTful APIs solved both by abstracting implementation details behind standardised methods and resource-based URLs.
Q2

A classmate says "our RESTful API uses HTTPS, so REST is a protocol." Correct them and explain what REST actually is.

Answer: REST is not a protocol, library or tool. It is a style/convention or a set of design principles for building web APIs. REST uses HTTP as its underlying protocol, applying standardised methods like GET, POST, PUT and DELETE to resources identified by URLs.
Q3

List the four steps of a typical RESTful API call.

Answer: (1) The client sends an HTTP request to the server. (2) The server authenticates the request if needed, e.g. with an API key or token. (3) The server processes the logic — fetch, create, update or delete data. (4) The server sends an HTTP response containing status and data, for example JSON.
Q4

Name all five components of a RESTful API client request and give one example of each.

Answer: (1) Unique Resource Identifier — the URL/endpoint, e.g. GET https://api.example.com/posts/22. (2) HTTP method — e.g. PUT. (3) HTTP headers — e.g. Content-Type: application/json, Accept: application/json, Authorization: Bearer <token>. (4) Request body — for POST/PUT, e.g. { "title": "New Post", "author": "User123" }. (5) Parameters — path (/posts/22), query (/posts?author=Admin) or cookie.
Q5

What is the difference between a path parameter, a query parameter and a cookie parameter?

Answer: Path parameters are part of the URL and identify specific resources, e.g. /posts/22. Query parameters provide filtering or sorting logic, e.g. /posts?author=Admin. Cookie parameters are sent via cookies, often for session or quick authentication purposes.
Q6

In the curl example curl -X PUT ... -H "Authorization: Bearer YOUR_ACCESS_TOKEN" -H "Content-Type: multipart/form-data" -F "bio=...", what does each of -X, -H and -F do?

Answer: -X PUT specifies the HTTP method as PUT, which updates a resource. -H adds a custom HTTP header — here it adds an Authorization header carrying the access token and a Content-Type header declaring multipart/form-data. -F sends a form field as a key-value pair; multiple -F flags send multiple fields in the body.
Q7

Contrast POST and PUT in terms of repeating the same request.

Answer: Repeating a POST may result in multiple records — it is not repeatable-safe. Repeating a PUT gives the same result each time — it is idempotent. This is why POST is used to create/submit and PUT to update.
Q8

Match each authentication method — Basic, Bearer, API Key, OAuth — with its main security trade-off.

Answer: Basic Authentication sends a Base64 username/password in the header: easy to implement but insecure unless used over HTTPS and susceptible to interception. Bearer Authentication sends an access token in the header: more secure, common in OAuth flows, and the token must be kept secret. API Key is a unique identifier in headers or query parameters: simple but less secure (anyone can use an exposed key) and often rate-limited. OAuth uses a password plus a token with scopes, refresh tokens and expiration: highly secure and ideal for third-party integrations, but complex to implement initially.
Q9

What is the single most important rule that applies to all four authentication methods?

Answer: All authentication methods should be used over HTTPS, to prevent credentials or tokens from being intercepted.
Q10

Identify the three parts of a server response and one thing found in each.

Answer: (1) Status line — a 3-digit HTTP status code such as 200 OK. (2) Message body — the returned data, often JSON, e.g. an object with id, name, age and email. (3) Response headers — metadata such as Content-Type, Content-Length, Server, Date, Cache-Control or Access-Control-Allow-Origin.
Q11

What do the status code ranges 2xx, 3xx, 4xx and 5xx each mean? Give one example code per range.

Answer: 2xx Success — the request was successfully processed (200 OK, 201 Created). 3xx Redirection — further action is required to complete the request (301 Moved Permanently). 4xx Client Error — the request was incorrect or unauthorised (400 Bad Request, 404 Not Found). 5xx Server Error — the server encountered an error (500 Internal Server Error).
Q12

What does Accept: application/json control, and what does Content-Type: application/json describe?

Answer: Accept is a request header that negotiates the response format the client wants — here JSON (XML is the other common option). Content-Type describes the format of the body being sent or returned — in a response it tells the client the response body is application/json.
Q13

Who introduced REST, where, and name all six architectural constraints.

Answer: REST was introduced by Roy Fielding in his doctoral dissertation. The six constraints are: Stateless, Cacheable, Uniform Interface, Client–Server Separation, Layered System, and Code-on-Demand (which is optional and less commonly used).
Q14

Explain the Stateless constraint and why it improves scalability.

Answer: Each client request must contain all the information necessary to understand and process it, and the server must not store any client context between requests. With no per-client session state to manage, servers can handle requests independently, which improves scalability and reliability.
Q15

Rewrite these three action-oriented endpoints in resource-oriented form: /login, /logout, /activateAccount. Explain the benefit.

Answer: /login becomes POST /sessions; /logout becomes DELETE /sessions; /activateAccount becomes /account-activation. Framing actions as resources reduces the number of endpoints, makes purposes clearer, aligns the API with HTTP semantics, and lowers developers' cognitive load because they can often guess URLs from standard practices. (A related example is /accountclosings, to which a client POSTs to request an account closure.)
Q16

What is an API contract, who are the parties involved, and why does it matter across a project's life?

Answer: An API contract defines the expectations and agreements between API providers (the backend) and consumers (the frontend). It lets developers build and integrate more effectively, reduces misunderstandings and errors, and serves as a reference point or verification for updates and changes so all parties stay aligned on how the API should function.
Q17

Why might a team choose Django REST Framework over plain JsonResponse, and what does the assignment require regardless?

Answer: DRF extends Django to build Web APIs, is optimised for JSON and other content types, and provides serialisation/deserialisation, permissions and authentication, and many features out of the box — making it cleaner and more scalable than manually serialising with JsonResponse in server-rendered views. Regardless of approach, the assignment requires the project to include API endpoints that return data in JSON format (via JsonResponse or dedicated JSON endpoints).
Q18

What is a headless architecture, and what role does the backend play in it?

Answer: A headless architecture separates frontend and backend, with the backend acting as an API-only layer. All frontend–backend communication happens via JSON APIs, which suits modern clients such as React SPAs and mobile apps.
Q19

Describe three GitHub practices introduced for collaborating on pull requests.

Answer: (1) Protect important branches such as main to prevent accidental changes, setting conditions like required CI tests or code reviews before merging. (2) Define push rules using rulesets to control what gets pushed, e.g. file types and sizes — useful for internal repositories or larger teams. (3) Resolve merge conflicts before merging, because GitHub blocks merging when unresolved conflicts exist; the file list above the merge button shows what to fix.
Q20

What are GitHub Issues used for, and what three helpful actions link them to your workflow?

Answer: Issues track bugs, ideas, tasks or any piece of work, can be linked to pull requests for visibility and context, and let you assign tasks to team members. Helpful actions include linking a PR to an issue, creating a branch for an issue, and assigning issues and PRs.
Q21

What CI/CD limitation exists on USYD GitHub Enterprise, and what does ICT recommend instead?

Answer: GitHub Actions is not enabled on the USYD GitHub Enterprise Server. ICT recommends using external CI/CD tools such as Jenkins or AWS CodePipeline/CodeBuild instead.
