Why DRF Exists and What It Gives You

One Django codebase can serve web pages, native mobile apps and business partners — but only if it can hand back data, not just HTML.

A traditional Django app returns rendered HTML, which is perfect for a browser but useless to a mobile app or a third-party system that wants raw data. Modern developers must support web clients, native mobile apps, and business-to-business integrations simultaneously. The answer is a Web API that returns data (usually JSON) instead of pages.

Django REST Framework (DRF) is a powerful toolkit for building Web APIs in Django. It provides a flexible and powerful system for building and consuming RESTful APIs, with strong built-in authentication and authorization. It is the standard way the Django community exposes data over HTTP.

💡
Why it matters: DRF is not a separate framework — it is a set of reusable, composable pieces (serializers, views, pagination, permissions) layered on top of the Django you already know. Learning a few of those pieces lets you build an API in minutes instead of hand-writing JSON parsing and validation.

In the TIL (Today I Learned) project, a dedicated application called til_api holds all the contexts for RESTful APIs. You can inspect api_endpoints.json to explore the available TIL APIs.

✅
Exam tip: Remember the layering: Django = framework; DRF = toolkit on top of Django for APIs; Simple JWT = authentication plugin on top of DRF. Each layer adds one capability.

The rest of this chapter walks through the four pillars of DRF: serialization, request/response handling, views, and pagination, then authentication, permissions and throttling.

Serialization: Turning Models into JSON

Serializers are the "magic" of DRF — they convert complex Django objects to plain data going out, and validate plain data coming in.

Serialization in DRF allows complex data types — such as Django ORM model instances and querysets — to be converted into native Python data types that can then be easily rendered into JSON or other content types. Deserialization is the reverse: parsed incoming data is converted back into complex types and validated.

DRF serializers work very similarly to Django's Form and ModelForm classes. That similarity is the real "magic" DRF provides: if you understand forms, you already understand serializers.

A basic ModelSerializer

from rest_framework import serializers
from til_app.models import Post

class PostSerializer(serializers.ModelSerializer):
    class Meta:
        model = Post
        fields = ['id', 'subject', 'contents', 'created_at', 'visibility', 'tags', 'image']
  • PostSerializer defines a serializer for the Post model. By inheriting from ModelSerializer, it automatically generates fields based on the model.
  • DRF includes both Serializer and ModelSerializer. ModelSerializer is simply a shortcut for creating serializer classes with default implementations of .create() and .update().
  • class Meta is an inner class providing metadata about the serializer:
  • model = Post specifies the model to serialize.
  • fields = [...] lists the fields to include in the serialized representation.

Serializing objects (outbound)

post = Post.objects.first()
serializer = PostSerializer(post)   # Use PostSerializer to serialize a post.
print(serializer.data)
  • PostSerializer(post) creates a serializer instance for a single Post object.
  • serializer.data converts the object into a dictionary format suitable for rendering into JSON. The output looks like:
{
  "id": 1,
  "subject": "First Post",
  "contents": "This is the content of the first post.",
  "created_at": "2024-09-25T16:24:38.096845+10:00",
  "visibility": true,
  "tags": [
    { "id": 1, "name": "tag1", "creation_date": "2024-09-25T16:18:22.201810+10:00" }
  ],
  "image": "image_media_url"
}

Deserializing objects (inbound)

serializer = PostSerializer(data=request.data)
if serializer.is_valid():
    validated_data = serializer.validated_data
    print(validated_data)
  • PostSerializer(data=data) creates a serializer instance with raw input data.
  • serializer.is_valid() validates the input data against the serializer's fields and validation rules.
  • serializer.validated_data contains the validated data as a dictionary, which can be used to create or update a model instance.

Saving instances

class PostSerializer(serializers.ModelSerializer):
    class Meta:
        model = Post
        fields = ['subject', 'contents', 'visibility']

    def create(self, validated_data):
        # Custom creation logic, additional processing before saving
        return Post.objects.create(**validated_data)

serializer = PostSerializer(data=request.data)
if serializer.is_valid():
    post = serializer.save()   # Calls the create() method
    print(post)
  • def create(self, validated_data) is called when serializer.save() is used with no existing instance.
  • The validated_data dictionary holds the validated input data.
  • serializer.save() calls the create() method and returns the newly created Post object.

Validation

Field-level validation uses .validate_<field_name> methods on a Serializer subclass. These are similar to .clean_<field_name> on Django forms and take a single argument — the field value to validate.

def validate_subject(self, value):
    if len(value) < 5:
        raise serializers.ValidationError("The subject must be at least 5 characters long.")
    return value

Object-level validation overrides validate(). It takes a single argument — a dictionary of field values — and should raise a serializers.ValidationError if necessary, or just return the validated values.

def validate(self, data):
    if 'spam' in data['contents'].lower():
        raise serializers.ValidationError("The content contains prohibited words.")
    return data
🧠
Memory hook: Out = .data, In = is_valid() → .validated_data → .save(). Serialization writes; deserialization reads and checks.

Requests, Responses and the View Toolkit

DRF swaps Django's raw request/response plumbing for friendlier objects, then gives you a spectrum of views from full manual control to almost no code at all.

Request and Response objects

DRF provides enhanced Request and Response objects that make handling API data easier.

class ExampleView(APIView):
    def post(self, request):
        data = request.data
        return Response({'received_data': data})
  • request.data contains the parsed data from the body of the request. For POST, PUT and PATCH requests it is a dictionary-like object (QueryDict) containing the request data.
  • request.data includes all parsed content, both file and non-file inputs.
def example_function_view(request):
    data = {'message': 'Hello, world!'}
    return Response(data)
  • Response(data) instantiates a response object with the given data.
  • DRF handles conversion of that data into the appropriate content type (e.g., JSON) automatically — you do not call JsonResponse yourself.

Class-based views and generic API views

DRF provides an APIView class, which subclasses Django's View class.

class HelloWorldView(APIView):
    def get(self, request):
        return Response({"message": "Hello, world!"})
  • APIView is the base class for all DRF views.
  • def get(self, request) defines behaviour for HTTP GET requests (you add post, put, delete, etc. the same way).

DRF also provides pre-built generic views for commonly used patterns that map closely to database models:

class PostListView(generics.ListAPIView):
    queryset = Post.objects.all()
    serializer_class = PostSerializer
  • ListAPIView is a generic view for listing multiple objects.
  • queryset is the set of objects to be listed.
  • serializer_class is the serializer class used to format the response data.

Custom function-based views

DRF also supports regular function-based views, which offer more control and suit simple or highly customised logic.

@api_view(['GET', 'POST'])
@permission_classes([IsAuthenticated])
def post_list_create(request):
    if request.method == 'GET':
        posts = Post.objects.all()
        serializer = PostSerializer(posts, many=True)
        return Response(serializer.data)
    elif request.method == 'POST':
        serializer = PostSerializer(data=request.data)
        if serializer.is_valid():
            serializer.save()
            return Response(serializer.data, status=201)
        return Response(serializer.errors, status=400)
  • @api_view(['GET', 'POST']) specifies that this view only handles GET and POST requests.
  • @permission_classes([IsAuthenticated]) restricts access to authenticated users only.
  • Note PostSerializer(posts, many=True) — many=True is how you serialize a queryset of multiple objects.

Generic views

  • Least code; built around a queryset + serializer_class.
  • Ideal when a view maps cleanly to one model.
  • Pagination works automatically here.

Function-based views

  • More explicit control over each branch of logic.
  • Decorators (@api_view, @permission_classes) re-add the DRF behaviour.
  • Best for simple or highly customised endpoints.

Pagination: Serving Large Datasets Safely

Never dump every row in a table into one response — pagination splits results into pages and keeps responses fast.

DRF includes support for customisable pagination styles, making large datasets easier to manage.

Global pagination settings

# settings.py
REST_FRAMEWORK = {
    'DEFAULT_PAGINATION_CLASS': 'rest_framework.pagination.PageNumberPagination',
    'PAGE_SIZE': 10,
}
  • The pagination style may be set globally in the REST_FRAMEWORK settings dictionary.
  • Pagination is only performed automatically if you are using generic views or viewsets — plain APIView/function-based views must paginate manually.

Custom pagination classes

from rest_framework.pagination import PageNumberPagination

class CustomPagination(PageNumberPagination):
    page_size = 5
    page_size_query_param = 'page_size'
    max_page_size = 100
  • You can override pagination classes to modify particular aspects of the style.
  • page_size is the default number of items per page (5 here).
  • page_size_query_param = 'page_size' lets the client choose the page size via a query parameter.
  • max_page_size = 100 caps how large the client can make a page — a safeguard against abuse.

Applying pagination to a view

class PostListView(generics.ListAPIView):
    queryset = Post.objects.all()
    serializer_class = PostSerializer
    pagination_class = CustomPagination
  • pagination_class = CustomPagination specifies the custom pagination class for this view, overriding the global default.
ℹ️
Note: The same PageNumberPagination idea appears later as plain Django pagination (django.core.paginator.Paginator) for template-based infinite scroll. The concepts — page number, page size, cap — carry across.

Authentication, Permissions and Throttling

Three separate questions: who are you (authentication), are you allowed (permissions), and how often may you ask (throttling)?

Authentication in DRF verifies the identity of the user making a request, ensuring only authorized users can access or modify resources. DRF provides several mechanisms, including session-based, token-based, and JWT-based authentication.

Permissions determine whether a request should be granted or denied. DRF provides a variety of permission classes, which can be applied globally or at the view level. The example @permission_classes([IsAuthenticated]) from the previous section is a permission check.

Throttling controls the rate of requests that a user or client can make to an API. It helps prevent abuse such as spamming or excessive usage by limiting the number of API requests within a specified time period.

🧠
Memory hook: Auth = identity, Permission = access, Throttle = rate. In order: authenticate, authorize, then meter.
💡
Why it matters: These three are what turn a public endpoint into a production-safe one. Without authentication anyone is anonymous; without permissions an authenticated user could still delete someone else's data; without throttling a single client can starve the API.

Each can be configured globally (in REST_FRAMEWORK settings) or per-view, giving you coarse defaults with fine-grained overrides.

JSON Web Tokens: Structure and Workflow

A JWT is a signed, self-contained token — the server can trust it without looking anything up, because the signature proves it wasn't altered.

JWT (JSON Web Token) is a compact, URL-safe means of representing claims between two parties. It is a popular format for securely transmitting information as a JSON object, and it is signed using a secret or a public/private key pair to ensure the integrity and authenticity of the claims.

JWTs are powerful for authentication and authorization, especially in stateless and distributed environments. They offer scalability and flexibility but require careful handling of security concerns. They are not suitable for scenarios requiring immediate revocation or one-time use, where traditional tokens stored in a database are more appropriate.

Structure of a JWT

A JWT consists of three parts separated by dots (.):

header.payload.signature   /   xxxxx.yyyyy.zzzzz

1. Header — metadata about the token, such as the signing algorithm and token type:

{ "alg": "HS256", "typ": "JWT" }

2. Payload — the claims, which are statements about the user or additional data. Common claims include iss (issuer), exp (expiration time), sub (subject), and aud (audience):

{ "sub": "1234567890", "name": "John Doe", "admin": true }

3. Signature — ensures the token hasn't been altered. It is created by encoding the header and payload, then signing them with a secret or private key:

HMACSHA256(
    base64UrlEncode(header) + "." + base64UrlEncode(payload),
    secret
)

JWT workflow

  1. The server generates a token upon user authentication and returns it to the client.
  2. The client includes this token in the Authorization header of every subsequent HTTP request, using the Bearer schema.
  3. The server validates the token by checking the signature and ensuring it hasn't expired. If valid, the request is processed; otherwise, it is rejected.

Example of a JWT

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
🧠
Memory hook: Header = how, Payload = who/what, Signature = proof. The dot-separated order is always header.payload.signature.
⚠️
Common trap: The header and payload are only base64-encoded, not encrypted — anyone can read them. The signature proves integrity and authenticity, not secrecy. Never put secrets in a JWT payload.

JWT vs Sessions and Traditional Tokens

JWTs shine because they are stateless, but that same statelessness makes revocation hard — know the trade-off.

Common trap: Naive JWT implementation without additional measures is not good practice for authorization. Good practice is to use a token blacklist plus a short-lived access token with a refresh token.
ℹ️
Note: JWT alone is not sufficient for comprehensive authorization in modern applications — one reason OAuth 2.0 is often needed (see RFC 6749).

Why JWT is not a traditional token

  1. Self-contained and stateless — unlike traditional tokens, JWTs need no server-side storage. All necessary information is embedded in the token itself.
  2. Not meant for one-time expiration — traditional tokens (email verification, password reset) are one-time-use and server-managed. JWTs are used for continuous sessions with a defined expiration and are not inherently one-time use.
  3. Non-revocable by default — once issued, a JWT remains valid until it expires. Traditional tokens stored in a database can be easily invalidated or revoked by changing their state.

Use cases for traditional tokens

  • Email verification — a one-time-use token stored in the database, expiring after a single use or a set period.
  • Password reset — a temporary token allowing a password reset; typically expires after a few minutes.
  • Coupon or discount codes — tokens representing special offers, redeemed only once.

Simple JWT

Simple JWT is the plug-in that gives DRF a ready-made JWT authentication backend with conservative defaults.

Simple JWT provides a JSON Web Token authentication backend for Django REST Framework. It aims to cover the most common use cases of JWTs by offering a conservative set of default features, and it aims to be easily extensible in case a desired feature is not present.

In the TIL project, til_api is integrated with Simple JWT as the authentication backend. This is what lets API clients authenticate and receive tokens rather than relying on Django's session cookies.

✅
Exam tip: Distinguish the concept (JWT — the token format and workflow) from the implementation (Simple JWT — a Django/DRF library that implements that format). The library is the concrete tool; the RFC is the abstract specification.

The N+1 Query Problem

One innocent-looking loop can fire one database query per row — and the database round-trips grow linearly with your data.

There is an ORM performance problem so common it has a fancy name: the N+1 query problem. It occurs when a query inadvertently causes additional queries to look up related records that were not loaded by the original query. It typically happens when a separate database query is executed for each object in a set, resulting in N queries, where N is the number of objects, plus one initial query to retrieve the set itself. The total is N+1 queries — a loop.

Suppose you have a list of posts, and for each post you want its associated comments (or the creator's name, or the comment count). A separate query per post gives you:

  1. One query to fetch all posts.
  2. N additional queries to fetch data for each post.
# This results in N+1 trips to the database
posts = Post.objects.all()          # 1 hit
for post in posts:                  # N hits
    comments = Comment.objects.filter(post=post)
    # creator_name = post.creator.username                       # second N
    # comment_count = Comment.objects.filter(post=post).count()  # third N

Why it hurts

As the number of objects (N) increases, the number of queries increases linearly, causing significant slowdowns:

  • Higher resource consumption — the database and the application communicate multiple times, degrading CPU usage, memory consumption and I/O.
  • Increased latency — every query incurs delay from the time it takes for the request to travel to the server and back (Round-Trip Time, RTT).
ℹ️
Note: Modern databases with sophisticated query optimizers can handle complex queries efficiently — but they cannot rescue you from issuing N+1 separate statements.
⚠️
Common trap: Premature optimisation is bad. If your site is small- or medium-sized and pages load fine, it's okay to ignore the optimisation. Fix N+1 when it actually bottlenecks.
🤔
Pause & predict: a page shows 20 posts, each with an author name and a comment count. Counting only the queries described above, how many database round-trips happen — and how many would there be with 200 posts?

Finding N+1 Queries

You cannot fix what you cannot see — instrument the request and count the SQL.

To identify N+1 queries, use the Django Debug Toolbar. It lets you inspect the SQL queries generated for each request, so you can see the repeated per-row queries and the total count.

The TIL project ships with two endpoints to demonstrate the difference:

  • Problematic: http://127.0.0.1:8000/til_app/posts_n_plus_one/
  • Optimised: http://127.0.0.1:8000/til_app/posts_optimized/

These endpoints are implemented in til_app.views.post_comments_n_plus_one() and til_app.views.post_comments_optimized() respectively. Loading both with the Debug Toolbar open lets you compare the query count directly.

✅
Exam tip: The fastest diagnostic is to open the same page with the Debug Toolbar and watch the query count scale with the number of rows on the page. If queries grow with N, you have an N+1.

Fixing N+1 with Optimised QuerySets

Three QuerySet methods — select_related, prefetch_related, annotate — collapse N+1 queries into one or two.

Optimised QuerySets prevent the N+1 problem using methods like select_related, prefetch_related, and annotate.

select_related()

Use when fetching related objects via a foreign key relationship. It performs an SQL JOIN to fetch related objects in a single query.

posts = Post.objects.select_related('creator').all()
for post in posts:
    print(post)
    print(post.creator.username)

This returns a QuerySet where each post already carries its creator. The SQL:

SELECT "post"."id", "post"."subject", "post"."contents", "auth_user"."username"
FROM "post"
INNER JOIN "auth_user" ON ("post"."creator_id" = "auth_user"."id")

prefetch_related()

Use when fetching related objects via many-to-many or reverse foreign key relationships. Django performs two queries and then "joins" the results in Python.

posts = Post.objects.prefetch_related('post_comment').all()
for post in posts:
    print(post)
    for comment in post.post_comment.all():
        print(comment)

The two SQL queries:

SELECT "post"."id", "post"."subject" FROM "post";
SELECT "comment"."id", "comment"."post_id", "comment"."content"
FROM "comment" WHERE "comment"."post_id" IN (1, 2, 3, ...);  -- all post IDs from the first query

annotate()

annotate() aggregates data and performs calculations across related models without an additional query per related object.

posts = Post.objects.annotate(comment_count=models.Count('post_comment')).all()
for post in posts:
    print(post.comment_count)

The SQL:

SELECT "post"."id", COUNT("post_comment"."id") AS "comment_count"
FROM "post"
LEFT JOIN "post_comment" ON ("post"."id" = "post_comment"."post_id")
GROUP BY "post"."id"
🧠
Memory hook: select_related = one-to-many going up (FK) → JOIN. prefetch_related = many-to-many / reverse FK → two queries joined in Python. annotate = compute an aggregate (e.g. count) in the database.

Performing raw SQL queries

Django gives the ability to write custom SQL for complex use cases.

⚠️
Common trap: Be very careful whenever you write raw SQL — both for security concerns (injection) and performance. Prefer the ORM unless you genuinely need raw SQL.
🤔

When You Still Have N+1: Pagination, Lazy Loading, Caching

Sometimes N+1 is unavoidable — then you shrink the blast radius instead of eliminating it.

Sometimes you cannot avoid N+1 problems entirely. These strategies mitigate the performance impact.

Pagination (infinite scroll)

Load a few items at a time using Django's built-in pagination utilities.

from django.core.paginator import Paginator

paginator = Paginator(Post.objects.all(), 9)   # Show 9 posts per page
page_number = request.GET.get('page')
page_obj = paginator.get_page(page_number)

See til_app.views.posts() and templates/post/posts.html for how a simple pagination with infinite scroll is implemented. Because N is small per page, the N+1 cost stays small.

Lazy loading

Load only the data needed at a given time, avoiding unnecessary data fetching. This is commonly used in frontend optimisation for images and videos.

Caching in Django

Use caching mechanisms to store frequently accessed data and reduce database hits.

💡
Why it matters: These three strategies reduce how often and how much you query rather than removing the per-row query. They are complementary to the QuerySet fixes — you can combine all of them.

Asynchronous Task Queues (Optional)

Some work is too slow for a web request — hand it to a queue and let a background worker do it later.

ℹ️
Note: Chapters 4 and 5 of the source are optional reading and are NOT assessed in the final exam. Study them for breadth and for understanding the TIL project's design.

An asynchronous task queue is one where tasks are executed at a different time from when they are created, and possibly not in the same order they were created. This lets you execute background tasks outside the main application process, enabling non-blocking operations.

Basic concepts and definitions

  1. Task/Job — a unit of work to be performed asynchronously (sending an email, processing a file).
  2. Task Queue — a data structure that holds tasks to be executed.
  3. Broker/Message Queue — a middleware component handling storage and delivery of tasks. Examples: Redis, RabbitMQ, Amazon SQS.
  4. Producer — the entity (code, web app) that creates tasks and puts them in the queue.
  5. Worker — a process that fetches tasks from the queue and executes them. Multiple workers can run concurrently; most commonly each worker runs as a daemon under supervision.
ℹ️
Note: "Task queue" is not a traditional academic term. In the Django world, when someone says task queue, they usually mean asynchronous task queue. The concept is closely related to message queues and message-oriented middleware, rooted in distributed systems and concurrent computing.

When do you need a task queue?

  • Long-running tasks — sending emails, generating reports, processing large files, image processing; these should not block the main application thread.
  • Resource-intensive operations — heavy CPU or I/O such as video encoding or ML model training.
  • Scheduled tasks — backups, data synchronisation, periodic notifications.
  • Concurrency — managing concurrency so specific tasks run at controlled rates.
IssueUse Task Queue?Reason
Sending bulk emailYesEach send involves network I/O; bulk sends are slow inline
Modifying files (incl. images)YesFile/image processing is CPU/I/O intensive, may take seconds
Fetching large data from third-party APIsYesNetwork calls are slow and can exceed request timeouts

⚠️
Common trap (Danger): A task queue is not suitable for user-interactive tasks — the user is waiting, so deferring the work makes the experience worse.
ℹ️
Note: A task queue adds complexity but can improve user experience. It comes down to whether a piece of code causes a bottleneck and can be delayed until more free CPU cycles are available.

Implementations in Django

Celery is a robust, distributed task queue system supporting complex workflows and high concurrency. It is ideal for heavy background tasks like sending bulk emails, processing large datasets, and executing scheduled jobs. Celery works with multiple brokers (e.g. Redis, RabbitMQ) and offers task retry, chaining, and monitoring.

The TIL project uses Celery for asynchronous email services. Where the code lives:

  • til_api.views.RegisterView() — enqueues the email task during user registration.
  • til_api.tasks — contains the Celery task(s) that actually send the email.

Settings reminder (demo caveat):

  • The .env file uses placeholder values for email; replace them with a real email service configuration to make it work.
  • In settings, celery_task_always_eager = True is enabled, so tasks run synchronously in-process, not in a real background worker.

To get true asynchronous behaviour, change these settings and run Celery with a broker.

Django native asynchronous support: Django supports writing async views, and an entirely async-enabled request stack when running under ASGI. Async views still work under WSGI, but with performance penalties and without the ability to have efficient long-running requests.

Other lightweight task queues: Django Q, Huey.

🧠
Memory hook: Producer → Broker → Worker. The producer enqueues, the broker stores and delivers, the worker executes.

WebSockets and Django Channels (Optional)

HTTP is request/response; WebSocket is a persistent two-way pipe — and Channels is how Django speaks it.

ℹ️
Note: This chapter is optional and not assessed in the final exam.

WebSocket is a protocol that enables real-time, two-way communication between a client (like a web browser) and a server over a single, persistent connection. Unlike traditional HTTP, which requires separate requests for each interaction, WebSocket allows continuous, low-latency communication. This makes it ideal for chat applications, live notifications, online gaming, and collaborative tools.

The latest specification of the WebSocket protocol is RFC 6455, supported by Chrome, Safari, Firefox and others.

Django Channels

Django Channels extends Django beyond HTTP, enabling it to handle protocols that require long-running connections like WebSocket, MQTT and more. It lets Django applications manage real-time functionality such as chat rooms, live updates and notifications while maintaining compatibility with the standard Django ecosystem.

Key concepts:

  1. ASGI (Asynchronous Server Gateway Interface) — Channels uses ASGI instead of WSGI to support asynchronous protocols. ASGI is the asynchronous counterpart of WSGI, enabling Django to handle WebSockets and other long-lived connections.
  2. Consumers — the basic unit of Channels code; Django's equivalent of views for handling WebSocket and other asynchronous events. Consumers structure your code as functions called whenever an event happens (rather than making you write an event loop), and they let you write sync or async code while handling handoffs and threading for you.
  3. Routing — like Django's URL routing for HTTP, Channels uses routing to map WebSocket connections and other protocol events to specific consumers. This lets you combine and stack consumers (and other valid ASGI applications) to dispatch based on the connection type.
  4. Channel Layers — provide cross-process communication between different instances of the application, supporting group messaging and broadcast messaging. They use backends like Redis or in-memory storage.

Building a simple chat room

The demo extends the TIL project with real-time chat using Django Channels: WebSockets + a consumer + a frontend template in til_app. Test it at http://127.0.0.1:8000/til_app/chat/All/.

1. Settings and ASGI configuration

til_project/settings.py — add Channels and configure ASGI + channel layers:

ASGI_APPLICATION = 'til_project.asgi.application'
CHANNEL_LAYERS = {
    "default": {"BACKEND": "channels.layers.InMemoryChannelLayer"}
}

til_project/asgi.py — route HTTP to Django and WebSockets to Channels:

application = ProtocolTypeRouter({
    "http": django_asgi_app,
    "websocket": AllowedHostsOriginValidator(
        AuthMiddlewareStack(URLRouter(websocket_urlpatterns))
    ),
})

2. Routing and consumers

til_app/routing.py — define WebSocket URL patterns:

websocket_urlpatterns = [
    re_path(r'ws/chat/(?P<room_name>\w+)/$', consumers.ChatConsumer.as_asgi()),
]

til_app/consumers.py — handle WebSocket connections, save messages, and broadcast:

class ChatConsumer(WebsocketConsumer):
    def connect(self):
        self.room_name = self.scope['url_route']['kwargs']['room_name']
        self.room_group_name = f"chat_{self.room_name}"
        async_to_sync(self.channel_layer.group_add)(
            self.room_group_name, self.channel_name
        )
        self.accept()

    def receive(self, text_data):
        data = json.loads(text_data)
        async_to_sync(self.channel_layer.group_send)(
            self.room_group_name,
            {"type": "chat_message", "username": data["username"], "message": data["message"]}
        )

    def chat_message(self, event):
        self.send(text_data=json.dumps(event))

3. Views and URLs

til_app/views.py — serve the page and recent history:

@login_required

    return render(request, "chat/index.html", {"room_name": room, "messages": reversed(messages)})

Key Takeaways

If you remember nothing else, remember this.

1

DRF is a toolkit layered on Django for building Web APIs; in the TIL project the API contexts live in the til_api app.

2

Serialization converts model instances and querysets to native Python data (JSON); deserialization validates and converts incoming data back into objects.

3

ModelSerializer auto-generates fields and default .create()/.update(); class Meta sets model and fields.

4

Outbound serialization uses serializer.data; inbound uses is_valid() → validated_data → save(), which calls create() when no instance is supplied.

5

Field-level validation uses .validate_<field_name>; object-level validation overrides validate(), and both raise serializers.ValidationError.

6

DRF gives Request (request.data) and Response; views range from APIView to generic views (ListAPIView with queryset + serializer_class) to decorated function-based views (@api_view, @permission_classes).

7

Pagination can be set globally in REST_FRAMEWORK or via a custom PageNumberPagination subclass; it applies automatically only to generic views/viewsets.

8

Authentication verifies identity, permissions grant/deny access, and throttling limits request rate — each configurable globally or per view.

9

A JWT is header.payload.signature; header carries algorithm/type, payload carries claims (iss, exp, sub, aud), and the signature proves integrity via HMAC or a key pair.

10

JWT is stateless and scalable but hard to revoke; sessions are stateful and easy to revoke; traditional tokens are one-time-use and database-stored (email verification, password reset, coupons).

11

The N+1 problem fires one extra query per object plus one initial query; fix it with select_related (FK JOIN), prefetch_related (M2M/reverse FK, two queries joined in Python), or annotate (database aggregate).

12

When N+1 can't be removed, mitigate with pagination/infinite scroll, lazy loading, and caching — and remember premature optimisation is bad.

13

An asynchronous task queue (Celery being the robust choice) moves long-running, resource-intensive or scheduled work off the request path; it is unsuitable for user-interactive tasks.

14

Django Channels uses ASGI, consumers, routing and channel layers to add WebSocket real-time chat, as demonstrated by the TIL chat room.

Glossary

Every term you need to speak this week's language.

Django REST Framework (DRF)
A toolkit for building Web APIs on top of Django, providing serializers, views, authentication, permissions, pagination and throttling.
Serialization
Converting complex types such as model instances and querysets into native Python data (JSON); deserialization is the reverse.
ModelSerializer
A DRF serializer shortcut that auto-generates fields and default .create()/.update() implementations from a model.
request.data
The DRF Request attribute holding parsed body data (file and non-file) as a dictionary-like object.
APIView
The base class for all DRF views; subclasses Django's View and defines methods like get and post.
Generic view
A pre-built DRF view (e.g. ListAPIView) configured with queryset and serializer_class that maps closely to a model.
Pagination
Splitting a large result set into pages; configurable globally or via a custom PageNumberPagination class.
Throttling
Limiting how many API requests a user or client may make in a given time period to prevent abuse.
JSON Web Token (JWT)
A compact, URL-safe, signed token representing claims, structured as header.payload.signature.
Claim
A statement about the user or extra data inside a JWT payload, such as iss, exp, sub, or aud.
Simple JWT
A library providing a JWT authentication backend for DRF; used by the TIL project's til_api.
Token blacklist
A mechanism that records revoked tokens so JWTs can be invalidated before their exp expiry.
N+1 query problem
An ORM performance bug where one query to fetch a set is followed by one extra query per object, totalling N+1 queries.
select_related()
A QuerySet method that performs an SQL JOIN to fetch foreign-key related objects in a single query.
prefetch_related()
A QuerySet method that fetches many-to-many or reverse-FK relations in two queries and joins them in Python.
annotate()
A QuerySet method that adds aggregated values (e.g. Count) computed in the database, avoiding per-object queries.
Asynchronous task queue
A queue where tasks run later (and possibly out of order) outside the main application process, enabling non-blocking work.
Broker / message queue
Middleware (Redis, RabbitMQ, Amazon SQS) that stores and delivers tasks between producers and workers.
Worker
A supervised process that fetches tasks from the queue and executes them, often with many running concurrently.
Celery
A robust, distributed task queue system for Django supporting complex workflows, retries, chaining and monitoring.
Django Channels
An extension of Django that handles long-running protocols like WebSocket and MQTT using ASGI.
ASGI
Asynchronous Server Gateway Interface, the async counterpart of WSGI that enables WebSocket and long-lived connections.
Consumer
The basic unit of Channels code, the WebSocket equivalent of a view, handling events like connect, receive and broadcast.
Channel layer
A cross-process communication layer supporting group and broadcast messaging between application instances.

Practice Questions

Look away from the page first — retrieval is what builds memory.

Answer, reveal, then tick “Mastered”. Your progress is saved.
Q1

What problem does serialization solve in DRF, and what is the difference between serialization and deserialization?

Answer: Serialization converts complex Django types (model instances, querysets) into native Python data that can be rendered as JSON. Deserialization is the reverse: it takes parsed incoming data, validates it against the serializer's rules, and converts it back into complex Python types so model instances can be created or updated.
Q2

In a ModelSerializer, what does the inner class Meta specify, and why is ModelSerializer described as a shortcut?

Answer: class Meta provides metadata: model names the model to serialize and fields lists which fields to include. ModelSerializer is a shortcut because it automatically generates the serializer's fields from the model and supplies default .create() and .update() implementations, saving you from writing them by hand.
Q3

When does serializer.save() call create() versus update(), and what does it return?

Answer: create() is called when save() is used with no existing instance (the serializer was built with data=... only). If the serializer was built with an existing instance plus data, update() is called instead. save() returns the created or updated model instance.
Q4

How do you write field-level validation versus object-level validation in a DRF serializer?

Answer: Field-level validation uses a method named .validate_<field_name> (e.g. validate_subject) that takes the single field value and returns it or raises serializers.ValidationError — analogous to Django forms' .clean_<field_name>. Object-level validation overrides validate(), which takes the whole dictionary of field values, checks cross-field rules, and either raises ValidationError or returns the values.
Q5

What is request.data in DRF, and which request methods populate it?

Answer: request.data is a dictionary-like object (QueryDict) containing the parsed body of the request, including both file and non-file inputs. It is populated for POST, PUT and PATCH requests.
Q6

Compare a generic view and a function-based DRF view, giving one advantage of each.

Answer: A generic view (e.g. generics.ListAPIView) is configured declaratively with queryset and serializer_class, requires minimal code, and gets pagination automatically. A function-based view decorated with @api_view(['GET','POST']) and @permission_classes([IsAuthenticated]) gives explicit control over each branch of logic, which suits simple or highly customised endpoints.
Q7

How is pagination configured globally and per view in DRF, and when is it applied automatically?

Answer: Globally it is set in settings.py under REST_FRAMEWORK using DEFAULT_PAGINATION_CLASS (e.g. PageNumberPagination) and PAGE_SIZE. Per view you set pagination_class = CustomPagination, where a custom class can define page_size, page_size_query_param, and max_page_size. It is only applied automatically for generic views or viewsets.
Q8

Distinguish authentication, permissions and throttling in DRF.

Answer: Authentication verifies who the user is (session-based, token-based, or JWT-based). Permissions decide whether that request should be granted or denied (e.g. IsAuthenticated). Throttling controls the rate of requests to prevent abuse such as spamming, limiting requests within a time period. All can be configured globally or at the view level.
Q9

Name the three parts of a JWT and state what each contains.

Answer: The header contains metadata such as the signing algorithm and token type ({"alg":"HS256","typ":"JWT"}). The payload contains the claims — statements about the user or extra data, e.g. iss, exp, sub, aud. The signature ensures the token has not been altered, created by signing the base64url-encoded header and payload with a secret or private key.
Q10

Describe the JWT workflow from login to a validated API request.

Answer: On successful authentication the server generates a token and returns it to the client. The client stores it and includes it in the Authorization header of every subsequent request using the Bearer schema. The server validates the token by checking the signature and that it has not expired; if valid the request proceeds, otherwise it is rejected.
Q11

Why is a JWT described as stateless, and what is the main downside of that design?

Answer: A JWT is stateless and self-contained because all necessary information is embedded in the token itself and no server-side storage is needed; verification is local. The downside is that it is non-revocable by default — once issued it stays valid until it expires, so immediate revocation requires extra mechanisms such as a token blacklist.
Q12

Give three differences between JWT and server-side sessions.

Answer: Storage: JWT is client-side, sessions are server-side. State: JWT is stateless, sessions are stateful. Scalability: JWTs scale easily with no state to synchronise, while sessions are harder to scale due to centralised state. (Also: JWT expiry is built into the exp claim, sessions can be invalidated by the server; JWT revocation is hard, session revocation is easy.)
Q13

For which situations are traditional database tokens better than JWTs, and give examples.

Answer: Traditional tokens are better for one-time-use or immediately revocable actions: email verification (single use or set period), password reset (temporary, expires after minutes), and coupon/discount codes (redeemed once). These are stored server-side and can be invalidated by changing their state.
Q14

What is the N+1 query problem and why does it get worse as data grows?

Answer: It occurs when one initial query retrieves a set of objects and then a separate query runs for each object to fetch related data, giving N+1 total queries. Because the number of queries grows linearly with N, higher N means more database round-trips, higher resource consumption (CPU, memory, I/O) and increased latency from round-trip time.
Q15

How do you find an N+1 problem in a Django project?

Answer: Use the Django Debug Toolbar to inspect the SQL queries generated per request and watch the query count. The TIL project exposes a problematic endpoint (/til_app/posts_n_plus_one/) and an optimised one (/til_app/posts_optimized/), implemented by post_comments_n_plus_one() and post_comments_optimized(), for direct comparison.
Q16

When should you use select_related versus prefetch_related?

Answer: Use select_related for foreign-key (single-valued) relationships; it performs an SQL JOIN and fetches everything in one query. Use prefetch_related for many-to-many or reverse foreign-key relationships; Django runs two queries and joins the results in Python. Using the wrong one either fails to help or produces inefficient SQL.
Q17

How does annotate() help avoid N+1, and give the aggregate example from the lab.

Answer: annotate() computes aggregates in the database so you don't query per related object. The lab example annotates each post with a comment count: Post.objects.annotate(comment_count=models.Count('post_comment')).all(), producing a single query with COUNT(...), a LEFT JOIN and GROUP BY.
Q18

If N+1 cannot be eliminated, what mitigation strategies are recommended?

Answer: Use pagination / infinite scroll (e.g. Django's Paginator with 9 posts per page) so each page only touches a small N; use lazy loading to fetch only the data needed at a given time; and use Django's caching framework to store frequently accessed data and reduce database hits. Also remember premature optimisation is bad if the site performs fine.
Q19

When should you use an asynchronous task queue, and when should you not?

Answer: Use it for long-running tasks (bulk email, reports, file/image processing), resource-intensive operations (video encoding, ML training), scheduled tasks (backups, sync, notifications), and concurrency control. Do not use it for user-interactive tasks where the user is waiting, or for trivial fast operations like updating a profile or adding a blog post.
Q20

What are the five basic components of an asynchronous task queue?

Answer: Task/Job (a unit of asynchronous work), Task Queue (the data structure holding tasks), Broker/Message Queue (middleware such as Redis, RabbitMQ or Amazon SQS that stores and delivers tasks), Producer (the entity that creates and enqueues tasks), and Worker (a supervised process that fetches and executes tasks, potentially many concurrently).
Q21

What does Celery provide, and what demo caveat applies in the TIL project?

Answer: Celery is a robust, distributed task queue system supporting complex workflows and high concurrency, multiple brokers, task retry, chaining and monitoring — used in TIL for asynchronous email services. Caveat: the .env email values are placeholders and celery_task_always_eager = True makes tasks run synchronously in-process, so true async behaviour requires changing settings and running Celery with a broker.
Q22

What is a WebSocket, and how does it differ from HTTP?

Answer: A WebSocket is a protocol enabling real-time, two-way communication between client and server over a single persistent connection (RFC 6455). Unlike HTTP, which needs a separate request for each interaction, WebSocket allows continuous, low-latency communication — ideal for chat, live notifications, gaming and collaborative tools.
Q23

Explain the four key concepts of Django Channels.

Answer: ASGI — the asynchronous gateway interface used instead of WSGI to support long-lived connections. Consumers — the basic unit of Channels code, the WebSocket equivalent of views, handling events. Routing — maps WebSocket connections to consumers, like URL routing for HTTP. Channel layers — a cross-process communication layer (Redis or in-memory) supporting group and broadcast messaging between application instances.
Q24

In the TIL chat demo, what does the consumer do on connect and receive?

Answer: On connect, it reads room_name from the URL route, builds a group name chat_<room_name>, adds the channel to that group via group_add, and calls self.accept(). On receive, it parses the incoming JSON and calls group_send with a chat_message type plus username and message; the chat_message handler then serialises the event back to JSON and sends it to the client.
