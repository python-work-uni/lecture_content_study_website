From Laptop to Live Server: Deploying Your Django Project

A hands-on walkthrough of deploying a Django web application to a cloud production environment. You will launch an Ubuntu EC2 instance on AWS, connect securely over SSH, install the nginx + uWSGI + Django stack, clone your project, wire the two servers together, flip Django into production mode, and serve the site at a public URL.

Read this first: In development you run python3 manage.py runserver, a throwaway server that is slow, insecure and single-threaded. In production you split the job across three layers — nginx answers the public internet and serves static files, uWSGI speaks the WSGI protocol and runs your Python code, and Django provides the application itself. Almost every step in this lab is about getting those three layers installed, talking to each other, and reachable from outside the machine.

By the end you will be able to

  • Explain why the Django development server cannot be used in production and what each layer of the nginx + uWSGI + Django stack does.
  • Launch an Ubuntu EC2 instance with an appropriate instance type and a correctly locked-down key pair.
  • Connect to a remote server over SSH using a .pem key with safe file permissions on Windows and macOS.
  • Configure security-group rules so only ports 22, 80 and 443 are open and SSH is restricted to trusted IPs.
  • Install Python, pip, Django, nginx and uWSGI (with its Python plugin) on Ubuntu.
  • Diagnose the externally-managed-environment error and resolve it with a virtual environment.
  • Write an nginx server block that forwards dynamic requests to uWSGI and serves /static directly.
  • Write a uwsgi.ini file and set Django's DEBUG and ALLOWED_HOSTS for production.
  • Recognise exactly which extra configuration Assignment 3 requires beyond this lab.

Why Deployment Is Its Own Problem

Running code on your laptop and serving it to the internet are two different engineering problems.

During development you run your app with Django's built-in development server. That server is a convenience tool: it auto-reloads on code changes, prints friendly error pages, and serves every request in a single process with no concurrency, no caching and no security hardening. It is designed for one developer on localhost, not for strangers on the internet.

Production, by contrast, must handle many simultaneous users, serve static files efficiently, recover from crashes, run as a system user without root, and survive a reboot. A single Python process cannot do all of that well, so real deployments split the work across specialised programs.

Production deployment — The process of running an application on a remote, always-on server so that arbitrary users can reach it over the public internet, with settings and services chosen for reliability, security and performance rather than convenience.
💡
Why it matters: The lab's final DANGER warning is blunt — running python3 manage.py runserver 0.0.0.0:8000 on your AWS instance gives you a zero grade for project deployment. It appears to work because you can reach the app from the instance's IP address, but it fails every Assignment 3 requirement. The whole point of this lab is to build the real pipeline instead.
Development vs production
runserver (dev) → nginx + uWSGI + Django (production)

The Three-Layer Stack: nginx, uWSGI and Django

Each layer has one job, and requests flow through them in a fixed order.

The stack is a chain of responsibility. A browser's request arrives at the server's port 80, is handled first by nginx, is forwarded to uWSGI, which calls your Django application code, and the response travels back out the same way.

LayerRoleListens onSpeaks
nginxWeb server / reverse proxy. Terminates the public HTTP request, serves static files directly, forwards everything else.Port 80 (and 443 for HTTPS)HTTP
uWSGIApplication server. Loads and manages your Python application processes and translates requests into calls on your app.127.0.0.1:8000 (localhost only)uWSGI / WSGI protocol
DjangoThe application. Contains your views, models, templates and URLs — the logic that produces each response.Invoked by uWSGI, not listening itselfPython / WSGI

Why not let Django face the internet directly?

  • Static files. Images, CSS and JavaScript are the bulk of a page's bytes. nginx serves them from disk extremely fast; Django would have to route each one through Python, which is wasteful and unsafe in production.
  • Concurrency. nginx handles thousands of connections; uWSGI can run multiple worker processes and threads so requests are served in parallel.
  • Separation of trust. Django never needs to bind a public port. uWSGI only listens on the loopback address 127.0.0.1:8000, so it is invisible to the outside world and only nginx can talk to it.
🧠
Memory hook: Nginx faces the world, UWSGI runs the code, Django is the code — Nobody Uses Django directly.
Browser→nginx (port 80)→uWSGI (127.0.0.1:8000)→Django app→response back out

Step 0–1: Preparation and Finding EC2

Before touching the console, read the AWS Academy guidance and expect the environment to take time to build.

Step 0 is preparation. Read the AWS Academy Learner Lab – Student Guide and the AWS Academy Learner Lab – README first; they explain how your lab environment, credits and console access work.

✅
Exam tip: Make sure you have a stable network connection and be patient. The AWS Academy Lab can take several minutes to build the environment, and the setup only functions correctly once it has fully finished. Do not assume something is broken because a panel is slow.

Step 1 is finding the service. In the AWS Console, navigate to the EC2 section from the dashboard. If EC2 is not visible in the service list, type EC2 into the search bar at the top of the console and select it there.

ℹ️
Note: EC2 stands for Elastic Compute Cloud — AWS's service for renting virtual machines ("instances") by the hour.

Steps 2–5: Launching an EC2 Instance

You are renting a virtual server, so you choose its operating system and pay by the hour.

Step 2 — View running instances. Click Instance (running) to see any instances already active. This dashboard is also where you monitor the status of existing instances. If nothing is running, you launch a new one next.

Step 3 — Launch a new instance. Click Launch instances to begin creating a new virtual server.

Step 4 — Choose the operating system. Ubuntu is the recommended choice for this deployment. Everything in the rest of the lab (APT package names, systemd services, file paths) assumes Ubuntu.

Step 5 — Select the instance type. An instance type determines the CPU, memory and price of your virtual machine.

  • You have $50 in AWS credits, and instances are charged at an hourly rate, so cost management is part of the exercise.
  • Lower-tier instances such as t2.micro or t3.micro are generally sufficient for a Django project deployment.
  • Choose an instance type that fits your needs without exceeding your budget.
⚠️
Common trap: A larger instance is not "safer". Because billing is hourly, an oversized instance burns your $50 credits faster for no benefit — a micro instance is plenty for this workload.

Steps 6–7: Key Pairs and Locking Down the .pem File

The .pem key is your only credential, so its file permissions are a security control, not a formality.

Step 6 — Create a key pair. Click Create new key pair. AWS generates a .pem file. This file is essential: it is the private key you use to authenticate to your instance over SSH. Download it to your local machine and keep it secure, because it is used for authentication every time you connect.

⚠️
Common trap: You must use a key file to connect to your instance. There are penalties if you "simplify" access by allowing all traffic to your instance on SSH.

Step 7 — Configure key-pair permissions. Choose any key-pair name you like and leave the remaining settings at their defaults; clicking Create key pair downloads the .pem file to your computer. Now restrict who can read it, because an SSH client will refuse to use a key that other users can access.

Windows

Right-click the .pem file, select Properties > Security > Advanced, and disable inheritance. Then ensure only you, the admin, and the system have access to the file.

macOS

Restrict access with:

chmod 700 YourFile.pem
ℹ️
Note: chmod 700 means read, write and execute for the owner only — no permissions for group or other users. This matches the Windows goal of leaving only you, admin and system with access.
🤔
Pause & predict: Predict: what error will SSH give you if you skip this step and leave the key world-readable?

Step 8–10: Network Rules, Launch and SSH

A firewall you never configured is why most first deployments appear to succeed but are unreachable.

Step 8 — Set network settings. Before launching, configure the network settings to match the recommended values. You should allow traffic on exactly three ports:

PortProtocolPurpose
22SSHRemote terminal access for administration and deployment
80HTTPPublic, unencrypted web traffic to nginx
443HTTPSPublic, encrypted web traffic (needed for a production-grade site)

Double-check the security group rules so that SSH access is allowed only from trusted IPs. Opening port 22 to 0.0.0.0/0 (the whole internet) invites brute-force attacks and is penalised.

Step 9 — Launch the instance. Click Launch instance. The EC2 instance starts with the chosen operating system and settings. It may take a few minutes for the instance to fully initialise.

Step 10 — Connect to your instance. When the instance is up, it shows a "running" status in the Instances dashboard. Click the new instance to view its full details, then choose Connect. Open the SSH client tab, which shows a ready-made command you can paste into your terminal. Verify the file path to your .pem file is correct before running it.

ssh -i "ELEC3609.pem" ubuntu@ec2-54-165-46-8.compute-1.amazonaws.com

Note the ubuntu user: Ubuntu EC2 images do not let you log in as root — the default account is ubuntu, which you escalate with sudo when needed.

💡
Why it matters: The security group is a virtual firewall sitting in front of the instance. If a port is closed, no amount of correct nginx configuration will make the site reachable, because the traffic is dropped before it ever reaches your server.

Step 11: Installing the Software Stack

Five commands install everything the stack needs — and each one has a clear purpose.

Once connected, install the base software in order. Update the package index first, confirm Python, then add pip, Django and nginx.

sudo apt-get update
python3 --version
sudo apt-get install python3-pip
pip3 install django
sudo apt-get install nginx

Checking nginx

After installation, check whether nginx is running:

sudo service nginx status

If nginx is not running, start it:

sudo service nginx start

A running nginx already serves a default welcome page on port 80 — proof that your network rules and web server are working before you add your application.

🧠
Memory hook: Update → Verify Python → Pip → Django → Nginx. Think U-V-P-D-N down the stack from OS to web server.
ℹ️
Note: apt-get manages Ubuntu system packages; pip3 manages Python libraries. nginx comes from APT (it is a system service), Django comes from pip (it is a Python package). Mixing the two up is a common source of confusion later.

The externally-managed-environment Error and Virtual Environments

Modern Ubuntu protects its own Python, and this error is the clue that tells you so.

You may hit this error when installing a Python package globally:

ERROR: EXTERNALLY-MANAGED-ENVIRONMENT

It occurs when you try to install a Python package globally on a system where Python is managed by the operating system (for example Ubuntu or Debian). Installing packages globally is not recommended, because it can interfere with system-managed dependencies and potentially break built-in tools that rely on the system Python.

The fix: isolate your dependencies

Create a virtual environment and install your packages inside it. This keeps project dependencies separate and prevents system conflicts.

python3 -m venv .venv
source .venv/bin/activate
pip install <package_name>
  • python3 -m venv .venv creates a directory .venv containing a private Python interpreter and its own package space.
  • source .venv/bin/activate puts that environment first on your PATH; your prompt changes to show you are inside it.
  • From then on, pip install writes into .venv, never into the system Python.
💡
Why it matters: The OS itself ships tools written in Python. If you overwrite or upgrade the libraries those tools depend on, you can break the operating system's own utilities — which is exactly what the warning is trying to prevent.
✅
Exam tip: Be ready to explain both the cause (a globally managed system Python) and the remedy (a virtual environment), not just the error message.

Step 12: Installing uWSGI and Its Python Plugin

uWSGI needs two pieces: the program itself, and a plugin that teaches it to run Python 3.

To handle application serving, install uWSGI through pip:

pip3 install uwsgi

You also need the uWSGI Python plugin, installed through APT:

sudo apt-get install uwsgi-plugin-python3
uwsgi-plugin-python3 — The package that provides the Python 3 plugin for uWSGI, allowing uWSGI to run Python applications. Without it, uWSGI has no language runtime for your Django code.
ℹ️
Note: You can inspect the full list of available uWSGI plugins at /usr/lib/uwsgi/plugins/.
💡
Why it matters: This split is why starting uWSGI later uses the flag --plugin python3. The binary alone cannot execute Python; the plugin supplies that capability, so you must tell uWSGI which plugin to load.

Step 13–14: Clone Your Project and Configure nginx

nginx must be told two things: where the project lives, and which requests to hand to uWSGI.

Step 13 — Clone your project. Clone your project repository from GitHub into the EC2 instance. Critically, install any dependencies and libraries your project requires after cloning — a freshly cloned repo has none of your Python packages installed on the server.

Step 14 — Modify the nginx configuration. Navigate to /etc/nginx/nginx.conf and modify it so it points at the root and static directories for your project. Replace the placeholder paths with the real paths to your project's files, then apply the change:

sudo service nginx restart

What the configuration actually means

The relevant part of the file is the server block. In production the HTTP context also sets sane defaults: sendfile on, tcp_nopush on, tcp_nodelay on, keepalive_timeout 65, types_hash_max_size 2048, MIME types from /etc/nginx/mime.types, logging to /var/log/nginx/access.log and /var/log/nginx/error.log, and inclusion of /etc/nginx/conf.d/*.conf.

user www-data;
worker_processes auto;
error_log /var/log/nginx/error.log;
pid /run/nginx.pid;

include /usr/share/nginx/modules/*.conf;

events {
    worker_connections 1024;
}

http {
    log_format main '$remote_addr - $remote_user [$time_local] "$request"'
                    '$status $body_bytes_sent "$http_referer" '
                    '"$http_user_agent" "$http_x_forwarded_for"';

    access_log /var/log/nginx/access.log main;

    sendfile on;
    tcp_nopush on;
    tcp_nodelay on;
    keepalive_timeout 65;
    types_hash_max_size 2048;

    include /etc/nginx/mime.types;
    default_type application/octet-stream;

    include /etc/nginx/conf.d/*.conf;

    server {
        listen 80 default_server;
        listen [::]:80 default_server;
        root /var/www/til_project/;

        include /etc/nginx/default.d/*.conf;

        location / {
            include uwsgi_params;
            uwsgi_pass 127.0.0.1:8000;
        }

        location /static {
            alias /var/www/til_project/static/;
        }

        error_page 404 /404.html;
        location = /40x.html {}

        error_page 500 502 503 504 /50x.html;
        location = /50x.html {}
    }
}

Reading the key lines

  • listen 80 default_server; — this server block answers port 80, the default for HTTP.
  • root /var/www/til_project/; — the directory nginx treats as the document root.
  • location / { include uwsgi_params; uwsgi_pass 127.0.0.1:8000; } — every URL is forwarded to uWSGI on the loopback interface. uwsgi_params supplies the standard WSGI environment variables.
  • location /static { alias /var/www/til_project/static/; } — URLs beginning /static are served straight from disk by nginx, bypassing Python entirely.
  • error_page and location = /40x.html {} — friendly handlers for 404 and server-error pages.
⚠️
Common trap: Replace the placeholder paths (/var/www/til_project/…) with your project's actual paths. If root, alias or the uWSGI target path is wrong, nginx returns 404s or a 502 Bad Gateway instead of your site.
ℹ️
Note: This lab does not cover every static- and media-file configuration — for example CSS, JavaScript and uploaded images. You may need to add extra configuration to the nginx file, especially for Assignment 3.

Step 15: Writing the uwsgi.ini Configuration

uwsgi.ini is the contract that tells uWSGI which Python module to load, from where, and how many workers to run.

Go to your project folder, create a file named uwsgi.ini, and configure it for your project. Ensure the chdir, wsgi-file, module and socket settings accurately reflect your project's structure.

[uwsgi]
chdir = /var/www/til_project
wsgi-file = /var/www/til_project/til_project/wsgi.py
module = til_project.wsgi:application
socket = 127.0.0.1:8000
master = true
disable-logging = true
processes = 2
threads = 4

Every setting explained

SettingMeaning
chdirChange to this directory before loading the app — the project root.
wsgi-filePath to Django's WSGI entry point. Django generates wsgi.py in the project package when you start a project.
moduleThe Python import path to the application callable: package.wsgi:application.
socketBind to 127.0.0.1:8000 — the exact address nginx forwards to.
masterRun a master process that supervises and can restart workers.
disable-loggingSuppress per-request logging for performance.
processes / threadsRun 2 worker processes with 4 threads each — the source of concurrency.
🧠
Memory hook: chdir = where you stand, wsgi-file = the file, module = the callable, socket = the door nginx knocks on. All four must agree with each other or nothing connects.
💡
Why it matters: The socket value and the uwsgi_pass value in nginx are two halves of the same wire. If they disagree — :8001 versus :8000, or a public IP versus 127.0.0.1 — Django runs fine but nginx cannot reach it, and users see a 502 error.

Step 16–18: Production Settings, Starting uWSGI and Going Live

Three final changes turn a development project into a production site, then you test it from the outside.

Step 16 — Update Django project settings. In your project's settings.py, add your domain to ALLOWED_HOSTS and turn debug mode off. Use the Public IPv4 DNS shown for your instance in the AWS dashboard as the host value.

# SECURITY WARNING: don't run with debug turned on in production!
DEBUG = False

ALLOWED_HOSTS = [
    '.localhost',
    '127.0.0.1',
    '[::1]',
    'ec2-54-165-46-8.compute-1.amazonaws.com',
]
  • DEBUG = False disables Django's verbose error pages and development-only behaviour. Production must never expose debugging details to the public.
  • ALLOWED_HOSTS is the whitelist of hostnames/domains Django will answer for. A request whose Host header is not listed is rejected — a defence against host-header attacks.

Step 17 — Start uWSGI. Run it from the directory containing your .ini, loading the Python 3 plugin:

uwsgi uwsgi.ini --plugin python3

This initialises uWSGI with the configuration in uwsgi.ini.

Step 18 — Access your project. You should now be able to reach your project through your URL in a browser.

🤔
Pause & predict: It worked in your browser but a friend cannot reach it. Name three layers you would check, in request order, to find the fault.
⚠️
Common trap: Forgetting to replace the example hostname. If ALLOWED_HOSTS still contains only the sample ec2-54-165-46-8.compute-1.amazonaws.com and not your instance's DNS name, Django will refuse the very request you are testing.

Glossary

Every term you need to speak this week's language.

EC2
Elastic Compute Cloud — AWS's service for launching and running virtual servers ("instances"), billed by the hour.
Instance
A single virtual machine rented from AWS, for example an Ubuntu t3.micro server running your deployment.
Instance type
The CPU/memory/price profile of an instance; micro types such as t2.micro and t3.micro suffice for a Django project.
Key pair / .pem file
The private key downloaded when you create a key pair, used to authenticate SSH connections to your instance.
SSH
Secure Shell — an encrypted protocol for logging into a remote machine's terminal; used here over port 22.
Security group
A virtual firewall attached to an EC2 instance that controls which ports and source IPs may reach it.
Port 22 / 80 / 443
The three ports opened for deployment: SSH, HTTP and HTTPS respectively.
APT
Ubuntu's system package manager (apt-get), used for OS-level software like nginx and the uWSGI Python plugin.
pip
Python's package installer (pip3), used for Python libraries such as Django and uWSGI.
nginx
The web server and reverse proxy that faces the public internet, serves static files and forwards dynamic requests to uWSGI.
uWSGI
The application server that loads and runs your Django project, translating web requests into Python calls over the WSGI protocol.
uwsgi.ini
The configuration file specifying uWSGI's working directory, WSGI file, module, socket, and worker process/thread counts.
uwsgi-plugin-python3
The plugin package that lets uWSGI execute Python 3 applications; located under /usr/lib/uwsgi/plugins/.
WSGI
Web Server Gateway Interface — the standard contract between Python web applications and servers.
Reverse proxy
A server that receives client requests and forwards them to a backend service, here nginx forwarding to uWSGI.
Static files
Assets such as CSS, JavaScript and images served directly from disk, efficiently and without Python involvement.
externally-managed-environment
The error raised when installing a Python package globally on an OS-managed Python; solved with a virtual environment.
Virtual environment
An isolated Python installation created with python3 -m venv .venv, keeping project dependencies away from system packages.
DEBUG
The Django setting that must be False in production to avoid exposing verbose diagnostic error pages.
ALLOWED_HOSTS
Django's whitelist of hostnames the site will answer for; must include your instance's Public IPv4 DNS.
Public IPv4 DNS
The externally resolvable name of your EC2 instance, added to ALLOWED_HOSTS so Django accepts requests to it.
chmod 700
The macOS/Linux command restricting a file (here the .pem key) to owner read/write/execute only.
systemd
The Linux service manager used to make services start automatically and restart on failure — required for Assignment 3 but not covered by this lab.

No terms in this category.

Practice Questions

Look away from the page first — retrieval is what builds memory.

Answer, reveal, then tick “Mastered”. Your progress is saved.
Q1

Why does the lab forbid running python3 manage.py runserver 0.0.0.0:8000 on your AWS instance?

Answer: Django's development server is for testing only. It is slow, insecure, single-process and not hardened for the public internet, so it does not fulfil Assignment 3's requirements. Using it results in a zero grade for project deployment.
Q2

Describe the path a request takes from a user's browser through the three layers of the stack.

Answer: The request arrives at nginx on port 80. Nginx either serves a static file directly from disk (for /static URLs) or forwards the request via uwsgi_pass 127.0.0.1:8000 to uWSGI. uWSGI calls the Django application callable specified by module = til_project.wsgi:application. Django produces the response, which returns through uWSGI and nginx to the browser.
Q3

What are the three ports opened in the EC2 security group and what is each for? What extra rule applies to SSH?

Answer: Port 22 (SSH), port 80 (HTTP) and port 443 (HTTPS). SSH access must be restricted to trusted IPs only — allowing all traffic on SSH is penalised, because opening port 22 to the internet exposes the server to brute-force attacks.
Q4

What instance type is recommended, and why does the choice matter financially?

Answer: Lower-tier instances such as t2.micro or t3.micro are sufficient for a Django deployment. Instances are billed at an hourly rate against $50 of AWS credits, so an oversized instance wastes budget with no benefit for this workload.
Q5

How do you restrict the .pem key's permissions on Windows and on macOS, and why is this necessary?

Answer: On Windows: right-click the file, Properties > Security > Advanced, disable inheritance, then ensure only you, the admin and the system have access. On macOS: run chmod 700 YourFile.pem. It is necessary because the key is your authentication credential; SSH rejects keys that other users can read, and a readable key can be stolen.
Q6

List the software installed in Step 11 and the command used for each.

Answer: sudo apt-get update (refresh the package index), python3 --version (verify Python), sudo apt-get install python3-pip (install pip), pip3 install django (install Django), sudo apt-get install nginx (install nginx). Then check with sudo service nginx status and start it with sudo service nginx start if needed.
Q7

What causes ERROR: EXTERNALLY-MANAGED-ENVIRONMENT and how do you resolve it?

Answer: It occurs when installing a Python package globally on a system where Python is managed by the operating system (Ubuntu/Debian). Global installs can interfere with system-managed dependencies and break built-in tools. Resolve it by creating and activating a virtual environment: python3 -m venv .venv, source .venv/bin/activate, then pip install <package_name> inside it.
Q8

Which two commands install uWSGI and its Python support, and why do you need both?

Answer: pip3 install uwsgi installs the uWSGI application server itself, and sudo apt-get install uwsgi-plugin-python3 installs the Python 3 plugin that lets uWSGI run Python applications. Both are needed because the uWSGI binary alone has no Python runtime; that is why it is started with --plugin python3.
Q9

In the nginx server block, what is the difference between location / and location /static?

Answer: location / matches every URL and proxies the request to uWSGI with include uwsgi_params; uwsgi_pass 127.0.0.1:8000; — this handles dynamic content. location /static matches URLs under /static and serves them directly from disk with alias /var/www/til_project/static/;, bypassing Python for speed.
Q10

Write out the essential contents of uwsgi.ini and explain chdir, wsgi-file, module and socket.

Answer: The file contains a [uwsgi] section with chdir = /var/www/til_project, wsgi-file = /var/www/til_project/til_project/wsgi.py, module = til_project.wsgi:application, socket = 127.0.0.1:8000, master = true, disable-logging = true, processes = 2, threads = 4. chdir is the working directory, wsgi-file the path to Django's WSGI entry point, module the import path to the application callable, and socket the loopback address nginx forwards to.
Q11

Why must the socket in uwsgi.ini match uwsgi_pass in nginx.conf?

Answer: They are the two ends of the same connection. uWSGI listens on the address given by socket; nginx forwards requests to the address given by uwsgi_pass. If they differ, nginx cannot reach uWSGI and users see a 502 Bad Gateway even though Django is running correctly.
Q12

What two changes are required in Django's settings.py for production, and what does each do?

Answer: Set DEBUG = False, which disables verbose diagnostic error pages and development-only behaviour so internals are not exposed publicly. Add your instance's Public IPv4 DNS (plus localhost entries) to ALLOWED_HOSTS, the whitelist of hostnames Django will answer for, which also defends against host-header attacks.
Q13

What command starts uWSGI, and how do you confirm the deployment succeeded?

Answer: Run uwsgi uwsgi.ini --plugin python3 from the project directory so uWSGI loads your configuration and the Python 3 plugin. Success is confirmed by reaching your project through its URL in a browser (Step 18).
Q14

Name four things Assignment 3 requires that this lab does not cover.

Answer: Any four of: file permission management (chmod/chown); proper static and media file serving including CSS, JavaScript and uploaded images; automatic service setup so services start at boot and survive crashes (systemd); and additional security controls.
