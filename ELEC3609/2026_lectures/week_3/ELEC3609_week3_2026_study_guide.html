Web Servers, Application Architecture and Scaling

This week explains how a real web application is put together and then grown. You meet the classic LAMP/LEMP stacks, the three-layer split between web servers and application servers, the main web server products (IIS, Apache, Nginx), server-side languages and frameworks (HTML, ASP.NET, Python, Django, PHP), the storage layer (relational, NoSQL and cloud), and finally the production techniques that let a system survive growth — decoupling, load balancing, caching, replication and redundancy.

Read this first: Every web system is the same story at different sizes. Start with one server doing everything (an MVP), then split responsibilities into dedicated layers — web server, application server, database — and finally duplicate and balance each layer so no single failure or overload takes the whole site down. Hold that mental picture and every term in this guide has an obvious place to live.

By the end you will be able to

  • Name the components of the LAMP and LEMP stacks and explain why stacks are modular.
  • Distinguish a web server from an application server and describe the three-layer architecture.
  • Explain the single-server MVP, its pros and cons, and when to move past it.
  • Use DNS records and load balancers to solve the "server moved / server is slammed" problems.
  • Compare IIS, Apache and Nginx and choose one for a given deployment.
  • Explain how Python, PHP and .NET web applications are served, including WSGI and Django's Model-View-Template.
  • Classify storage options (disk, relational, NoSQL, object/cloud) and match each to a use case.
  • Define statelessness, scale-out vs scale-up, and the four availability qualities (durability, availability, reliability, resiliency).
  • Describe the standard scaling playbook: separate DB, load balancer, HTTP accelerator, master-slave replication.

The Big Picture: Stacks and the Modern Web Architecture

A web application is a set of interchangeable components, and the way you assemble them determines how easy it is to grow and operate.

A web application is rarely built from scratch as one monolith. Instead it is assembled from a stack — a set of cooperating software layers. The most common stacks are LAMP and LEMP, and they are the most ubiquitous ways to develop and deploy web applications.

LAMP and LEMP

Both stacks contain the same four roles; only the web server differs.

RoleLAMPLEMP
Operating systemLinuxLinux
Web serverApacheNginx
DatabaseMySQLMySQL
LanguagePHPPHP

The key property is their modular nature: because each role is a separate component, any piece can be swapped out. You could replace MySQL with Postgres, or PHP with Python, without redesigning the whole system. This modularity is what makes the stack reusable across very different applications.

🧠
Memory hook: LAMP and LEMP share the same L, M and P. Only the second letter changes — Apache versus Nginx (the "E" in LEMP is pronounced "engine-x").

The principles behind modern web architecture

A 2002 paper, Principled Design of the Modern Web Architecture, set out the goals that good web architectures aim for:

  • Scalability of component interactions
  • Generality of interfaces
  • Independent deployment of components
  • Intermediary components to reduce interaction latency
  • The ability to enforce security
  • The ability to encapsulate legacy systems
💡
Why it matters: These six goals are the design reasons behind everything later in this lecture. Load balancers and caches are "intermediary components". REST-style uniform interfaces give "generality of interfaces". Containerised microservices enable "independent deployment". When asked why a technique exists, point back to one of these principles.
🤔

Three-Layer Architecture: Web Server vs Application Server

Splitting a system into web, application and data layers gives each concern its own resources and its own job.

A standard production web application is organised into three layers. Understanding each layer's responsibility is the foundation for everything that follows.

  • Web Server — handles HTTP(S) traffic only. It listens on HTTP (port 80) or HTTPS (port 443) when encrypted.
  • Application Server — runs the business logic. It may also speak HTTP (80) or HTTPS (443) if encrypted, or it may use any designated TCP port (for example 8080).
  • Database / data layer — stores and serves the application's data.

Application server vs web server — the defining difference

The distinction is about what protocol and what work each handles:

Web ServerApplication Server
HandlesHTTP requests exclusivelyBusiness logic for application programs
ProtocolsHTTP/HTTPSAny number of protocols, possibly including HTTP
Application server — A server that serves business logic to application programs through any number of protocols, possibly including HTTP.
Web server — A server that exclusively handles HTTP requests.
ℹ️
Note: Because an application server can speak HTTP too, the two roles can look similar at a glance. The test is scope: the web server does only HTTP, whereas the application server runs your business logic and may use non-HTTP protocols.
💡
Why it matters: The three-layer split is the first real step away from a fragile single-server MVP. It lets you give different components dedicated resources, which is the theme of the Decoupling section later.

Single-Server Architecture and the MVP

The minimal viable product runs everything on one server — great for speed of development, dangerous as a long-term design.

The simplest way to stand up a web application is a single-server architecture: the web server, application server and database all live on one machine. This is often called an MVP (Minimal Viable Product).

A common local development setup has the web server talk to the application server over localhost:8080 — i.e. the same machine, port 8080.

Pros and cons of the MVP

ProsCons
Simple for debugging, usually fine as the first iterationNot production ready — a real configuration differs once things run on multiple layers and compute nodes
Good for demo or technical validation purposesArchitecturally things are not decoupled
Tough for troubleshooting
Not ready for horizontal scaling
⚠️
Common trap: The MVP's simplicity is a feature of development, not a plan for production. The configuration that works on one box ("just point it at localhost") breaks the moment components move to separate machines — which is exactly what the case studies explore.

Always develop on the deployment target

When you set up a development web server to build a sample website, develop on a system similar to what you intend to deploy on. For this course that means Linux. To get a matching environment locally, Vagrant is software that creates and configures virtual development environments.

✅
Exam tip: "Develop on a similar system to what you deploy on" is a design rule, not a throwaway line. Deploying to Linux but developing on Windows is a classic source of "works on my machine" failures.

Case Study 1: Moving the Application Server (IP vs DNS)

When a component moves to a new machine, hard-coded addresses break — DNS decouples the name from the location.

Imagine your web server talks to the application server at localhost:8080. Now the application server is moved to another server. How does the web server find it?

Option A — Use the IP address

Point the web server at, say, 10.100.0.2:8080.

  • Problem: what if that server dies and a new server comes up with a new IP address? The IP is hardcoded in a configuration file, so every failure requires editing config.

Option B — Use DNS (an A record)

Create a DNS A record so that application.mysite.com.au points to 10.100.0.2. The web server's config now says application.mysite.com.au instead of an IP.

Now if the application server dies and DHCP assigns a new address 10.100.0.4:

  • Simply change the DNS record to the new IP — this can be automated with scripts.
  • application.mysite.com.au = 10.100.0.4
  • The web server needs no configuration changes.
A record — A DNS record that maps a hostname (e.g. application.mysite.com.au) to an IPv4 address. | tech
💡
Why it matters: DNS adds a layer of indirection between "name" and "address". Indirection is the core trick that makes infrastructure movable. The same principle reappears with load balancers: the name points at the balancer, not at any individual server.
🤔
Pause & predict: Your application server is replaced three times in one week. With the IP approach, how many config edits happen? With DNS, how many web-server config edits happen?

Case Study 2: The Application Server Gets Slammed

When one machine can no longer cope, you either make it bigger or add more machines — and adding more needs a load balancer.

Everything works, but now the application server is overwhelmed. Two options improve performance:

  1. Scale up — a bigger instance with more CPUs (or a more powerful CPU) and more memory.
  2. Scale out — run more instances.

The problem with more instances

Suppose you now have two application servers: 10.100.0.2 and 10.100.0.4. But you still have only one DNS record for the application server: application.mysite.com.au. Which IP should it point to?

The solution: an internal load balancer

An internal load balancer now kicks in.

  • application.mysite.com.au points to the load balancer.
  • The load balancer routes traffic to one of the underlying servers.

This preserves the DNS indirection from Case Study 1 while allowing many backend servers behind a single name.

DNS name→Load Balancer→Application Server 1 / Application Server 2
🧠
Memory hook: Case 1 fixes where a component lives (DNS). Case 2 fixes how many there are (load balancer). Same name, smarter target.
ℹ️
Note: The load balancer is described as internal here because it sits behind the public entry point, distributing traffic among application servers rather than facing the internet directly.

Web Servers: IIS, Apache and Nginx

Three dominant web servers, each with a different origin, scaling model and ideal use case.

IIS — Internet Information Services

  • Microsoft's web server.
  • Released 1996.
  • Long history of security vulnerabilities — should be avoided if possible.
  • Use it when running an ASP or ASP.NET application (though still consider Apache), or to make use of Windows-specific features such as AD-integration.

Apache HTTP Server

  • Open source, now developed by the Apache Software Foundation.
  • Very commonly used; released 1995.
  • Dynamically loadable module system — you extend it by loading modules.
  • Can scale but can be tricky to set up.
  • Typically spawns threads to handle requests via mpm_prefork (other modes exist).

Nginx

  • Released 2004; designed from the beginning to scale easily.
  • Adoption has grown quickly.
  • Spawns worker processes.
  • Memory and CPU usage are typically relatively consistent, even under load.
  • Configured with a configuration file.
Web serverReleasedProcess/thread modelStandout trait
IIS1996(Windows service)Microsoft stack, AD integration; security history
Apache1995Threads via mpm_preforkDynamic modules; common but tricky to scale
Nginx2004Worker processesBuilt to scale; stable resource use under load
💡
Why it matters: Nginx was explicitly designed for scale from day one, which is why it is the "N" in LEMP and a common choice for load balancers and caches. Apache predates the modern scale-out era, which explains why scaling it is described as "tricky".
✅
Exam tip: If asked to pick a web server for a new high-traffic deployment, Nginx's consistent resource usage under load is the defensible answer. Pick IIS only when you need Windows/AD-specific features.

Languages and Frameworks: HTML, ASP.NET, Python and PHP

The server-side language turns static markup into dynamic applications — and for Python and PHP the rule is the same: always use a framework.

HTML

HyperText Markup Language (HTML) is the standard markup language used to create web pages. The World Wide Web Consortium (W3C) develops the HTML standards.

ASP and ASP.NET

  • Active Server Pages (ASP) was released in 1996, now known as Classic ASP or ASP Classic. It was Microsoft's first server-side script engine for dynamically generated web pages.
  • ASP.NET (released 2002) supersedes ASP.
  • ASP.NET uses a Common Language Runtime (CLR) to allow most .NET languages to be supported.

Python

  • Use a framework.
  • Python uses PEPs for language-evolution planning, so you know what to expect in the next few years.
  • Popular Python frameworks: Flask and Django.
  • These typically come with a built-in development server (a lightweight web server) for local work.
  • For production, set them up with Apache or Nginx using the WSGI (Web Server Gateway Interface) specification.

PHP

  • Use a framework.
  • Without proper planning it will become a mess — spaghetti code.
  • Popular PHP frameworks: CodeIgniter and CakePHP.
  • PHP can be set up with either Apache or Nginx.
WSGI — Web Server Gateway Interface — the specification that lets Python web applications run behind production web servers such as Apache and Nginx. | tech
PEP — Python Enhancement Proposal — the process Python uses to plan and document language evolution, giving predictable future changes. | concept
🧠
Memory hook: The built-in dev server is a toy; WSGI is the adult connection between Python code and a real web server.
💡
Why it matters: "Use a framework" appears for both Python and PHP. The lecture is making a general engineering point: frameworks enforce separation of concerns, which is what stops a project collapsing into spaghetti as it grows.
🤔
Pause & predict: Why would you ship a Django app behind Nginx + WSGI instead of using Django's built-in development server in production?

Django: Model, View, Template (MVT)

Django reshapes the familiar MVC idea into Model-View-Template, where "View" means something different than in MVC.

Django organises an application around three responsibilities. Note carefully how its "View" differs from the View in classic MVC.

The three parts

  • Model — represents how data is organised in the database; similar to MVC's Model, it handles the data and logic and maintains a connection with the database.
  • View — works differently from the View layer of MVC: here the view accepts requests and sends out responses (it is closer to a controller).
  • Template — the presentation layer, commonly coded in HTML or DTL (Django Template Language).

A short way to remember the first two: a view is what you see when you visit a site; a controller controls the flow of information.

Classic MVC

  • Model: data and logic
  • View: what the user sees (presentation)
  • Controller: controls the flow of information

Django MVT

  • Model: data and logic, connected to the database
  • View: accepts requests and sends responses (controller-like)
  • Template: presentation layer (HTML or DTL)
⚠️
Common trap: In Django, the component that accepts requests and returns responses is called the View — even though that job is the controller's job in MVC. Mixing up Django's View with MVC's View is a classic exam slip.
DTL — Django Template Language — the templating syntax Django uses for its presentation layer, alongside HTML. | tech

Data Storage: Media, Disks and Relational Databases

Storage is layered from raw hardware up to relational databases — and each level has trade-offs in speed, flexibility and schema rigidity.

Storage media and hardware form factors

  • Hardware form factor: magnetic (spinning) HDD vs Solid State Drive (flash) SSD.
  • SAN storage — interconnected with Ethernet (iSCSI) or Fibre Channel.
  • NAS — Network Attached Storage.
  • In-memory storage.
  • Object store — e.g. AWS S3, Google Cloud Storage.
  • Block store — e.g. disks.
  • File store — e.g. NFS, Samba, CephFS, HDFS (Hadoop).

Disk

  • Used for static files (HTML, images, CSS).
  • SSD vs spinning.
  • Leverage OS RAM caching.

Relational databases

  • Maintain and enforce relationships between data.
  • Organise data into one or more tables of columns and rows.
  • Typically each table represents an entity (such as a customer or product).
  • Rows represent instances of that entity.
  • Columns represent values attributed to that instance (such as address or price).
  • A schema change often results in system downtime and planned maintenance.
Relational database — A database that stores data in tables of rows and columns, enforces relationships between data, and maps each table to an entity. | tech
⚠️
Common trap: The rigid schema is a relational database's strength and its weakness. It guarantees integrity, but schema changes can force downtime — a key reason NoSQL exists.

SQL Standards and the Major Relational Engines

There is an ANSI/ISO SQL standard, but real databases diverge — mostly in advanced features.

SQL — who needs a standard?

  • There has been an ANSI/ISO SQL standard since 1986.
  • Most SQL is not completely portable among RDBMS (Relational Database Management Systems).
  • Divergence typically affects only more advanced features — e.g. Teradata doesn't support pivots.
  • Transact-SQL (TSQL) is typically more feature-rich.

The major engines

EngineStrengthsWeaknesses / notes
MySQL / MariaDBMost popular and commonly used; lots of third-party tools and librariesDoes not implement the full SQL standard; concurrency can be an issue
PostgresANSI/ISO SQL standards; complete support for reliable transactions (ACID); great spatial extensionReplication can be tricky
Microsoft SQL Server (MSSQL)Good for the MS stack; integrates into BI/DW stack easily (SSIS, SSAS, SSRS); generally cheaper than Oracle and TeradataWatch license costs (even in the cloud); needs DBAs

The MySQL operator trap

MySQL does not implement the full standard. For example, 'foo' || 'bar' means 'foo' OR 'bar' in MySQL, whereas the SQL standard defines || as string concatenation.

ACID — Atomicity, Consistency, Isolation, Durability — the four guarantees Postgres fully supports for reliable transactions. | law
TSQL — Transact-SQL — Microsoft's SQL dialect, typically more feature-rich than the base standard. | tech
⚠️
Common trap: || is not portable. In standard SQL it concatenates strings, but in MySQL it means OR. Never assume SQL written for one engine runs unchanged on another.
ℹ️
Note: MSSQL's BI/DW integration stack is remembered as SSIS, SSAS, SSRS (Integration, Analysis and Reporting Services).

NoSQL and NewSQL: Four Data Stores

When schemas must bend and data must scale, non-relational stores trade strict consistency for flexibility.

Non-relational databases store data more like loose pages and do not store data in the same relational manner. Their characteristics:

  • New data structure
  • More flexible schemas, or no schemas at all
  • Better scalability
  • Eventually consistent rather than strictly consistent

Redis — key/value based

  • Written in C — blazing fast.
  • Protocol: Telnet-like, binary safe.
  • Disk-backed in-memory database, master-slave replication, automatic failover.
  • Simple values or data structures by keys.
  • Supports INCR & co, bit and bitfield operations, sets, lists, hashes and sorted sets.
  • Values can be set to expire (as in a cache).
  • Pub/Sub lets you implement messaging.

Cassandra — column based

  • Written in Java.
  • Main point: store huge datasets in "almost" SQL.
  • Protocol: CQL3 & Thrift.
  • CQL3 is very similar to SQL but with limitations imposed by scalability — most notably no JOINs and no aggregate functions.
  • Querying by key, or key range (secondary indices also available).
  • Data can have expiration (set on INSERT).
  • Map/reduce possible with Apache Hadoop.

MongoDB — document based

  • Written in C++.
  • Main point: JSON document store.
  • Master/slave replication (auto failover with replica sets).
  • Sharding built-in.
  • Queries are JavaScript expressions.
  • Geospatial queries and indexing.
  • Multiple storage engines with different performance characteristics.
  • Journaling.
  • Text search integrated.
  • Deployment requires heavy lifting for HA — e.g. voting systems using ZooKeeper.

ElasticSearch — document based

  • Written in Java.
  • Main point: advanced search; stores JSON documents.
  • Protocol: JSON over HTTP (plugins: Thrift, memcached).
  • Parent and children documents with versioning & timeouts.
  • Very versatile and sophisticated querying, scriptable.
  • Write consistency: one, quorum or all; asynchronous replication.
  • Sorting by score, geo distance.
  • Fuzzy searches (approximate date, etc.).
  • Use cases: dynamic web search with auto-suggest; the ELK stack for log analysis.
  • ELK = ElasticSearch, LogStash, Kibana.
StoreTypeWritten inSignature strength
RedisKey/valueCIn-memory speed, expiry, Pub/Sub
CassandraColumnJavaHuge datasets, CQL3, no JOINs
MongoDBDocumentC++JSON documents, sharding, geospatial
ElasticSearchDocumentJavaAdvanced/fuzzy search, ELK stack

Memory hook: Redis = Ram (in-memory cache). Cassandra = Columns at massive scale. Mongo = Many JSON documents. Elastic = Extraordinary search.
🤔

Cloud Storage and Amazon S3

Cloud storage abstracts physical disks into logical pools managed by a third party.

Cloud storage is a model of data storage in which:

  • Data is stored in logical pools.
  • The physical storage spans multiple servers (and often multiple locations).
  • The physical environment is typically owned and managed by a third party.

Many offerings exist: Azure Storage, Google Cloud Storage, Amazon S3.

Amazon S3

Amazon Simple Storage Service (S3) is a cost-effective, simple-to-use service that can store and retrieve any amount of data, at any time, from anywhere on the web.

Cloud storage — A storage model where data lives in logical pools spanning many servers/locations, with the physical environment owned and managed by a third party. | concept
💡
Why it matters: Object stores like S3 are the "disk" of the cloud era. They decouple your application from any single physical machine, which is the same indirection principle as DNS and load balancing — applied to storage.

Best Practices: Decoupling, Scalability and Redundancy

Production systems are built on three pillars — give components dedicated resources, keep them stateless, and remove every single point of failure.

Decoupling

Give different components dedicated resources: web servers, app servers and the database each get their own.

Benefits:

  • A well-understood scope of work for each component
  • Reduced blast radius when something fails
  • Easier troubleshooting and incident response

The trade-off: smaller but more components — a move towards microservices architecture.

Scalability

  • Statelessness is the foundation of all scalability. Stateful applications won't scale.
  • Components of the same layer should not share anything between them.
  • Refer to the 12 Factor App principles (https://12factor.net/).
  • Scale out vs scale up:
  • Scale-out (horizontal scaling): the model supercomputing has been using; load balancing is IMPORTANT.
  • Scale-up: "bigger, bigger and bigger" — often not realistic due to physical laws and economics.
  • Scalability applies not only to compute and memory, but also to IO:
  • IOPS (IO per second)
  • Bandwidth
  • Latency
Statelessness — The property that components of the same layer share no state between them; the foundation of all scalability, because any instance can serve any request. | concept

Redundancy

  • Remove all SPOFs (single points of failure).
  • Use Master/Slave and Replications.
  • Take a guess at AWS S3's durability (it is famously very high).
  • Four related but distinct qualities:
QualityMeaning
DurabilityIs the data stored securely in the event of failures?
AvailabilitySystem uptime — the percentage of time able to serve requests.
ReliabilitySimilar to availability; a system can be available but not functioning correctly.
ResiliencyThe ability to recover in the event of failures — self-healing.
  • Some software defects relate to performance and cannot be replicated when the load is low.
  • Think about avalanche / cascading effects (one failure triggering others).
  • Extended reading: Chaos Monkey.
🧠
Memory hook: Durability = is my data safe? Availability = is the service up? Reliability = is it doing the right thing? Resiliency = can it heal itself?
SPOF — Single Point Of Failure — any component whose failure takes down the whole system; redundancy aims to remove all of them. | concept
🤔
Pause & predict: A server is "up" and returning HTTP 200 responses, but every response contains wrong data. Which of the four qualities has failed — availability, reliability, or both?

Scaling Web Architecture: The Standard Playbook

Start from a single server, then apply four moves in order — separate the DB, add a load balancer, add caching, then replicate the database.

This section is the practical sequence you apply as a system grows. Each move solves a specific bottleneck.

1. Separate DB Server

Separate the database from the application server:

  • Eliminates resource contention (the DB and app no longer compete for the same CPU/RAM/disk).
  • Increases security by removing the database from the DMZ, or public internet.

2. Load Balancer

A load balancer (LB) improves performance and reliability by distributing workload across multiple servers. If one load-balanced server fails, the others handle the incoming traffic until the failed server becomes healthy again.

  • Typical implementations: HAProxy, Nginx, Varnish.

3. HTTP Accelerator

An HTTP accelerator — or caching HTTP reverse proxy — reduces the time to serve content using a variety of techniques. Typically the response from a web or application server is cached for a period of time in memory.

  • Examples: Varnish, Squid, Nginx.

4. Master-Slave Database Replication

For a database that performs many reads compared to writes (such as a CMS), use master-slave replication. It requires:

  • a master node, and
  • one or more slave nodes.

All updates go to the master; reads can be distributed across all nodes.

5. Combinations

It is possible to load balance the caching servers, in addition to the application servers, and to use database replication in a single environment. The purpose of combining these techniques is to reap the benefits of each without introducing too many issues or complexity.

Single Server→Separate DB→Load Balancer→HTTP Accelerator→Master-Slave Replication→Combinations
Load balancer — A component that distributes workload across multiple servers, improving performance and reliability by keeping traffic flowing when one server fails. | tech
HTTP accelerator — A caching HTTP reverse proxy (e.g. Varnish, Squid, Nginx) that caches web/application responses in memory for a period of time to serve content faster. | tech
Master-slave replication — A database setup with one master that receives all updates and one or more slaves that serve reads, ideal for read-heavy systems such as a CMS. | method
⚠️
Common trap: Don't add every technique at once. The lecture explicitly warns that combinations should avoid "too many issues or complexity". Add each layer only when you have the problem it solves.
✅
Exam tip: Match the technique to the symptom: DB competing with app → separate DB server; one server overloaded → load balancer; slow repeated responses → HTTP accelerator; read-heavy database → master-slave replication.

Key Takeaways

If you remember nothing else, remember this.

1

Web applications are assembled from modular stacks; LAMP and LEMP differ only in the web server (Apache vs Nginx).

2

Modern web architecture pursues scalability, general interfaces, independent deployment, low-latency intermediaries, security and legacy encapsulation.

3

Three-layer architecture splits web server (HTTP only, ports 80/443), application server (business logic, any protocol) and data layer.

4

A single-server MVP is easy to debug but not decoupled, hard to troubleshoot and not ready for horizontal scaling.

5

Moving an application server is solved by DNS indirection: change the A record, not every web server's config.

6

When one application server is slammed, scale up (bigger) or scale out (more), and put a load balancer behind a single DNS name.

7

IIS (1996, Microsoft, security-prone), Apache (1995, dynamic modules, mpm_prefork) and Nginx (2004, worker processes, stable under load) are the three main web servers.

8

Server-side stacks: HTML is the markup standard (W3C); ASP (1996) → ASP.NET (2002, CLR); Python (Flask/Django, WSGI); PHP (CodeIgniter/CakePHP).

9

Django's Model-View-Template differs from MVC — its View accepts requests and returns responses, and its Template is the presentation layer.

10

Storage spans hardware media, disks (static files, OS RAM caching), relational databases (tables/rows/columns, schema changes cause downtime) and object stores.

11

SQL has an ANSI/ISO standard since 1986 but is not fully portable; MySQL, Postgres (ACID, spatial) and MSSQL (SSIS/SSAS/SSRS) each have trade-offs.

12

NoSQL trades strict consistency for flexible schemas and scale: Redis (K/V), Cassandra (column, CQL3, no JOINs), MongoDB (document, sharding), ElasticSearch (search, ELK).

13

Best practices are decoupling (dedicated resources, reduced blast radius), statelessness/scale-out for scalability, and redundancy to remove SPOFs.

14

Durability, availability, reliability and resiliency are distinct; the scaling playbook adds separate DB, load balancer, HTTP accelerator and master-slave replication in order.

Q1

What are the four components of the LAMP stack, and how does LEMP differ?

Answer: LAMP = Linux, Apache, MySQL, PHP. LEMP replaces Apache with Nginx; Linux, MySQL and PHP are unchanged. Their modular nature means any component can be swapped out.
Q2

What is the defining difference between a web server and an application server, and which ports do they use?

Answer: A web server exclusively handles HTTP requests (HTTP on port 80, HTTPS on port 443). An application server serves business logic to application programs through any number of protocols, possibly including HTTP, and may use any designated TCP port.
Q3

List two pros and two cons of the single-server MVP.

Answer: Pros: simple for debugging, and good for demo or technical validation. Cons: not production ready (a real configuration differs across multiple layers and compute nodes) and architecturally not decoupled; it is also tough to troubleshoot and not ready for horizontal scaling.
Q4

A web server talks to an application server by hardcoded IP. The application server is replaced and gets a new DHCP address, then a second application server is added. Explain how DNS and a load balancer solve both problems.

Answer: Create an A record mapping application.mysite.com.au to an address and configure the web server to use the hostname; when the IP changes, update the DNS record (automatable with scripts) and the web server needs no config change. To use multiple servers, point the DNS name at a load balancer, which routes traffic to one of the backend application servers.
Q5

Compare IIS, Apache and Nginx by release year and request-handling model.

Answer: IIS (1996) is Microsoft's server; Apache (1995) typically spawns threads via mpm_prefork and uses dynamically loadable modules; Nginx (2004) spawns worker processes and keeps memory/CPU usage relatively consistent even under load.
Q6

What is WSGI and why is it needed for Python web applications?

Answer: WSGI (Web Server Gateway Interface) is the specification that connects Python web applications to production web servers such as Apache and Nginx. Frameworks like Flask and Django ship only a lightweight development server, which is not suitable for production.
Q7

Explain Django's Model, View and Template, and how the View differs from MVC's View.

Answer: Model handles data and logic and connects to the database; Template is the presentation layer (HTML or DTL); View accepts requests and sends responses. Django's View is controller-like, unlike MVC's View, which is the presentation layer.
Q8

What is the relational database schema trade-off?

Answer: Relational databases enforce relationships and organise data into tables, rows and columns, giving integrity — but a schema change often results in system downtime and planned maintenance.
Q9

Name one strength and one weakness each of MySQL, Postgres and MSSQL, and explain the || portability trap.

Answer: MySQL/MariaDB: most popular with lots of tools, but does not implement the full SQL standard (e.g. 'foo' || 'bar' means 'foo' OR 'bar' instead of the standard string concatenation) and can have concurrency issues. Postgres: ANSI/ISO SQL with full ACID transactions and a great spatial extension, but replication can be tricky. MSSQL: good for the MS stack, integrates into BI/DW (SSIS, SSAS, SSRS) and is cheaper than Oracle/Teradata, but license costs and DBAs must be considered.
Q10

What do NoSQL databases trade away, and how do Redis, Cassandra, MongoDB and ElasticSearch each store data?

Answer: NoSQL gives up strict consistency (it is eventually consistent) and relational structure, storing data more like loose pages with flexible or no schemas. Redis is key/value, Cassandra is column based, MongoDB is document based, and ElasticSearch is document based for advanced search.
Q11

What are Cassandra's most notable CQL3 limitations, and what does ELK stand for?

Answer: CQL3 has no JOINs and no aggregate functions, limitations that come from the design choices enabling its scalability. ELK = ElasticSearch, LogStash and Kibana, used for log analysis.
Q12

Define statelessness and distinguish scale-out from scale-up.

Answer: Statelessness means components of the same layer share nothing between them; it is the foundation of scalability because stateful applications won't scale, so any instance can serve any request. Scale-out is horizontal scaling by adding more machines (the supercomputing model, where load balancing is important). Scale-up is vertical scaling by making one machine bigger, often unrealistic due to physical laws and economics.
Q13

Distinguish durability, availability, reliability and resiliency, and define a SPOF.

Answer: Durability: is data stored securely in the event of failures? Availability: system uptime, the percentage of time able to serve requests. Reliability: similar to availability, but a system can be available yet not functioning correctly. Resiliency: the ability to recover from failures — self-healing. A SPOF (single point of failure) is a component whose failure takes down the system; it is removed with redundancy such as master/slave and replication.
Q14

Describe the standard scaling playbook in order, and what each move solves.

Answer: (1) Separate DB server — removes resource contention and increases security by taking the database out of the DMZ/public internet. (2) Load balancer (HAProxy, Nginx, Varnish) — distributes workload for performance and reliability. (3) HTTP accelerator (Varnish, Squid, Nginx) — caches responses in memory to speed content delivery. (4) Master-slave replication — sends all updates to the master and distributes reads across all nodes, suiting read-heavy systems like a CMS. These can be combined without introducing too much complexity.
