From URL to Web Host: Requests, Responses and Requirements

This week has two halves. First you follow a single URL from the browser to a database and back again, learning the protocols and architecture that make the web work: URLs, caches, DHCP, DNS, TCP/UDP, HTTP methods, load balancers, app servers, SQL/NoSQL databases, status codes, the DOM and rendering engines. Second you learn how a team plans the software it is about to build: use cases, sequence/state/wireframe diagrams, the Software Requirements Specification (SRS) and task-management tools.

Read this first: Think of the web as a relay race with a strict baton-passing order. A request travels down through many layers (browser → OS → network → server → database) and the response travels back up through just as many. Every acronym this week is simply one runner in that relay. Once you can trace the baton end-to-end, the individual pieces stop being trivia and become a story you can retell.

By the end you will be able to

  • Trace, step by step, what happens from the moment a URL is typed until a page is rendered.
  • Decompose any URL into scheme, subdomain, domain, gTLD/ccTLD and path.
  • Explain what DHCP and DNS do, and how a domain name becomes an IP address.
  • Compare TCP and UDP, and recall the standard ports for HTTP, HTTPS and DNS.
  • Describe the roles of load balancers, app servers and databases in a typical web architecture.
  • Explain master/slave replication and the problem of slave drift.
  • Interpret HTTP status code categories and how the browser reacts to 200 and 302.
  • Turn problem statements into use cases and document them with the SRS.
  • Choose appropriate project-management, diagramming and task-management tools.

The Journey of a URL: Client to Server and Back

A single page load is a long chain of small, specialised steps — understand the chain and every later concept has a place to sit.

Entering a URL triggers a coordinated sequence. The browser first parses the URL's components (scheme, domain, path/file), then performs the request and renders the returned content.

Client steps (the request)

  1. Browser: Parse URL
  2. Browser: Check cache
  3. OS: Identify network
  4. OS: Resolve using DNS
  5. OS: Establish TCP connection to the web server
  6. Browser: Submit HTTP request to the web server

Server steps (the processing)

  1. Load balancers (LB) establish the TCP connection and receive the HTTP request.
  2. LB software parses the HTTP header, then routes and forwards the request to an application (app) server.
  3. The app server executes back-end website logic, probably connecting to one or more databases.
  4. The app server renders a response and returns it over the TCP connection.

Client continues (the rendering)

  1. Browser: Parse response
  2. Browser: Fetch additional resources
  • Fetch assets (CSS, JS, Images)
  • Establish web socket connection(s)
  • Load browser plugins
  1. Render page
Parse URL→Check cache→Identify network→Resolve DNS→Open TCP→Send HTTP request→LB routes→App server + DB→Return response→Fetch assets→Render
🤔
Pause & predict: Before reading on, list the three stages above from memory. Which stage is the browser not involved in at all?
💡
Why it matters: Almost every topic this week — DNS, TCP, HTTP, load balancing, databases, the DOM — is just one of these boxes zoomed in. Keeping the map in your head tells you where a new term belongs.

Anatomy of a URL and the Browser Cache

A URL is a structured address, and the browser's cache is the shortcut that lets it skip the whole journey for assets it already has.

Parsing a URL

A URL follows a fixed shape:

URL format
protocol://domain.tld/path/file.ext

Worked example: https://cusp.sydney.edu.au/students/view-unit-page/uos_id/101257

  • Protocol: Hyper Text Transfer Protocol (Secure) — HTTPS.
  • Domain: cusp.sydney.edu.au
  • Subdomain: cusp
  • Domain: sydney
  • Generic top-level domain (gTLD): edu
  • Country code top-level domain (ccTLD): au
  • Path: /students/view-unit-page/uos_id/101257
✅
Exam tip: A hostname reads right-to-left in terms of scope: the ccTLD/gTLD is the broadest category, then the registered domain, then the subdomain narrows it down to a specific host.

Checking the browser cache

The browser cache stores copies of all kinds of assets so they need not be re-downloaded:

  • JavaScript files
  • CSS files
  • Images
  • Fonts

If a needed asset is in the cache and still valid, the browser can reuse it instead of issuing another network request — a major speed-up.

🧠
Memory hook: The cache holds the "4 F's of front-end assets" — Files of script, Formatting (CSS), Fotographs (images) and Fonts. (Spelling optional, the categories are not.)

Network Foundations: DHCP, DNS and the OSI Model

Before any request leaves your machine, the OS must know where "local" ends and the internet begins, and must translate names into numbers.

Identify the network landscape (DHCP)

When you connect to a network, your computer is usually configured with the Dynamic Host Configuration Protocol (DHCP). DHCP provides four things:

  • IP Address: Identifies your computer on the local network.
  • Subnet Mask: Defines what "local" means regarding your IP address.
  • Default Gateway: A host that can route packets to non-local IP addresses.
  • Nameservers: A host used to resolve domain names (a DNS server).
⚠️
Common trap: If you cannot reach any web sites at all, the very first thing to check is your DHCP-provided network configuration. One bad gateway or nameserver breaks everything downstream.

Resolving a domain name to an IP (DNS)

We cannot open a connection to cusp.sydney.edu.au directly — we need its IP address. The operating system resolves a domain name roughly as follows:

  1. Check OS local DNS entries (e.g. /etc/hosts/).
  2. Identify nameservers (a.k.a. DNS servers).
  • Usually provided by DHCP
  • Specified in /etc/resolv.conf
  1. Submit a UDP request to a nameserver on port 53.
  2. Nameservers keep recursively asking their parent nameserver until one knows the IP.
  3. The IP is returned according to a matching A-record for the domain.
💡
Why it matters: DNS is the internet's phone book. Humans remember names; routers need numbers. Every single request begins with this translation unless a cached IP is available.

Recap: the OSI model

The OSI Model conceptualises network systems as a stack, where each layer is an abstraction of the one below it. Representative layers from the lecture:

  • Layer 1: Copper line, COAX, Fibre, etc. (physical)
  • Layer 2: IEEE 802.11a/b/g/n (data link / Wi-Fi)
  • Layer 4: TCP/UDP (transport)
  • Layer 7: HTTPS (application)
🧠
Memory hook: Names matter at the top (layer 7), numbers move at the bottom. DNS is a name service but rides on a number-level transport (UDP).

TCP, UDP and Ports

TCP promises reliable, ordered delivery; UDP promises speed and nothing else — and ports tell the OS which application a packet belongs to.

TCP lives on layer 4 of the OSI model. It is not responsible for addressing or segregation like the layers below it; instead it is responsible for delivery of packets. TCP guarantees in-order delivery of data for the application layers above it.

TCP segments are assigned to particular ports, which define what application they are intended for. Standard defaults:

  • HTTP: Port 80
  • HTTPS: Port 443

Web servers can run on non-standard ports; 80 and 443 are conventions, not laws.

Aside: User Datagram Protocol (UDP)

UDP also lives on layer 4 alongside TCP but does not guarantee delivery at all. It is a best-effort protocol sending datagrams instead of TCP's segments. Packet deliveries are not acknowledged and packets are not re-transmitted (unless performed explicitly at the application layer). UDP operates on a particular port, though TCP and UDP ports are considered different. DNS operates on UDP port 53 and does not use TCP.

⚠️
Common trap: "Port 53" and "port 22" are only meaningful together with their transport protocol. TCP/53 is a different endpoint from UDP/53. Never say "port 53" without saying which protocol.
🧠
Memory hook: TCP = Trusted, Checked, Patient (handshake, in-order, retransmits). UDP = Unreliable, Dashing, Prompt (fire and forget — perfect for tiny DNS lookups).

HTTP Messages and Request Methods

HTTP is a simple text protocol built from a header plus an optional body, and its methods say what you want done to a resource.

A HTTP request or response consists of two parts:

  • Header: Contains meta-data such as cookie and connection information.
  • Body: Contains the data to be sent with the transmission (optional).

Once we have an open TCP connection to the web server, we send an HTTP request through that connection.

Request methods

  • GET: A simple request, header only.
  • POST: A request containing data in the body, e.g. form data, file upload.
  • HEAD: Same as GET, except the server omits the body in the response (only sends the header).
  • PUT: Replace a target resource on the server.
  • DELETE: Delete a target resource on the server.
  • OPTIONS: Ask the server which request types are allowed against a particular resource.

A representative HTTP request

GET /students/view-unit-page/uos_id/101257 HTTP/1.1
Host: cusp.sydney.edu.au
User-Agent: Mozilla/5.0
Accept: text/html
Connection: keep-alive
ℹ️
Note: The method is the verb, the path is the noun, and the headers are the context. GET carries no body; POST and PUT do.
🤔
Pause & predict: Which single method would you use to find out whether a URL exists without downloading its content, and why is it the cheapest choice?

Server-Side Architecture: Load Balancers, App Servers, Databases

Real websites are layered: something routes traffic, something runs your code, and something stores your data — and each layer is designed to survive failure.

Typical architecture — three layers

Using AWS IaaS services as an example:

  • End-to-end encryption in transit
  • Elastic Load Balancing (ELB)
  • Elastic Cloud Compute (EC2)
  • Relational Database Services (RDS)
  • Load balancing
  • Route traffic based on performance and health status
  • Route traffic based on contents
  • SSL offloading (HTTPS)
  • Port forwarding (HTTP to HTTPS)
  • Web Server / App Server / RDS
  • Master/Slave configuration for high availability (HA)

Internet-facing web servers

An internet-facing web server can directly receive HTTP requests from clients. Usually the first recipient of the HTTP request is not the service that provides the response. Instead it is often:

  • A load balancer (LB): Routes requests to appropriate servers for processing. LBs allow a pool of servers to handle incoming requests by forwarding each request to an available resource.
  • DDoS mitigation services (e.g. a web application firewall): Often the first layer for large websites. Their purpose is to ensure incoming requests are not part of a cyber attack.
  • Legitimate packets are forwarded (often to the regular LB)
  • Attack packets are dropped
  • E.g. CloudFlare
  • Content Delivery Network (CDN).

Secured HTTP = HTTPS, achieved using TLS protocols (SSL is obsolete).

Application servers

App servers do the actual processing of HTTP requests. They contain:

  • Back-end website code
  • Business logic
  • Database interface methods
  • Caching layers

Typical forms of web servers:

  • Virtual machines (IaaS): EC2, GCE
  • Containers: Docker
  • Serverless: Lambda, Google Cloud Function

This is where the majority of the work lies in a typical web architecture.

App server programming models

Developers usually work within a web framework rather than reinventing the wheel. Languages and associated frameworks:

  • Python (e.g. Instagram): Flask, Django
  • PHP (e.g. Facebook): Codeigniter, CakePHP
  • Ruby (e.g. GitHub): Ruby On Rails (RoR)
  • JavaScript (e.g. Groupon): Express.js (on Node.js)
🧠
Memory hook: Frameworks save you from rebuilding auth, routing and templating. Learn the pattern (MVC, routing, templating) once and the framework names become interchangeable.

Databases, Replication and Slave Drift

Databases are split by shape (SQL vs NoSQL) and by role (master vs slave), and the gap between master and slaves creates a timing hazard you must design around.

Persistent data — two main types

App servers typically read information from databases, split into two main types:

  • SQL (Relational): Maintain and enforce relationships between data. Examples: MySQL, PostgreSQL, SQLite, Microsoft SQL Server.
  • NoSQL (Non-relational): Store data like loose pages, often without schemas. Examples: MongoDB, Redis, DynamoDB, Cloud Data Store.

Databases can reside on the same host as the app server, or separately (recommended).

Slave/Master databases

To spread the load on the database, read and write operations are separated onto slave and master DBs respectively:

  • Master/Primary: Accepts read and write operations. There is usually only one master database.
  • Slaves/Replicas: Updates to the master are quickly replicated to all slave databases.
  • Slaves can be used for read operations only.
  • Since data is not modified on slaves, there can be many replicated slaves, improving parallelisability of DB reads.

Slave drift

Changes applied to the master DB are replicated to slave databases, but this does not occur instantaneously. There is a small but significant time delay between a write to the master and propagation to all slave DBs. This is called slave-drift (or replication delay) and must be managed appropriately by your application.

  • DB reads that lead to important decisions (e.g. payments) should usually be made against the master to prevent race conditions or side-effects from reading stale data.
  • Some replication configurations avoid this problem but come with other trade-offs, such as delayed writes and/or reduced fault tolerance.
⚠️
Common trap: Reading from a slave immediately after writing to the master can return stale data. If the read drives a decision (payment, balance, permission), read from the master.
🤔
Pause & predict: You scale reads by adding slaves. What new problem did you just create, and which class of queries must ignore the slaves?

Generating and Returning an HTTP Response

Once business logic decides the answer, the server fills a template to build the response, then sends a header plus an optional body back over the same TCP connection.

Generating the response

Once the application server has performed all the business logic to decide how it will respond, it must generate the response. Typically this involves insertion of data into a template, which forms the HTTP response.

  • Variables in the application code are inserted between {{ and }}.
  • Code can also be specified between {% and %}.
✅
Exam tip: Remember the two delimiter pairs by role: {{ }} = value (output a variable), {% %} = logic (control statements). This is the templating convention used by many frameworks, e.g. Jinja-style engines.

Returning the response

Similar to an HTTP request, an HTTP response also contains two sections:

  • Header: Contains meta-data such as HTTP status code, content type, length.
  • Body: Typically contains the HTML or the contents of a requested resource (optional).
Business logic→Insert data into template→Assemble header + body→Return over TCP
ℹ️
Note: Request and response share the same header/body structure — symmetry is the point. Learn it once and it applies in both directions.

Parsing a Response: Status Codes, the DOM and Rendering

The status code tells the browser what to do; the DOM is the browser's live model of the page; the rendering engine paints it.

HTTP status codes

HTTP code categoryDefinitionExample
1xxInformational100: Continue; 101: Switching Protocols
2xxSuccess200: OK — the standard response
3xxRedirection301: Moved Permanently; 302: Found/Moved Temp. (similar to 303 & 307); 304: Not Modified
4xxClient404: Not found
5xxServer502: Bad gateway

Client rendering

The HTTP status codes instruct the client on how to handle the response.

  • A 302 (Found) causes the browser to immediately follow the URL specified in the Location field in the response header.
  • A 200 (OK) response is usually accompanied by a resource in the response body, which is rendered by the browser.
🧠
Memory hook: 1-info, 2-good, 3-go elsewhere, 4-you erred, 5-they erred. The first digit is the whole story.

Parse HTML into the DOM

If an HTTP response contains HTML, the browser parses this HTML to build the Document Object Model (DOM). The DOM forms the browser's internal representation of the web page.

  • The relationships between HTML elements (such as <div> or <img> tags) are defined and can be manipulated via the DOM.
  • JavaScript libraries, such as jQuery, commonly manipulate the DOM to modify the layout of web pages.
  • Browser plugins often interact with browsers at this level.

DOM resources

While HTML specifies how components of the web page are structured, many other resources define how the page behaves:

  • CSS (Cascading Style Sheets): Specify positional and appearance attributes of DOM elements. CSS can be inside <style> tags, or in external files included via <link> tags in the <head> section.
<link rel="stylesheet" href="/styles/cusp_style.css" type="text/css" />
  • JS (JavaScript): Can be used in the browser to perform arbitrary computation, often including live manipulation of DOM elements. JS can be inside <script> tags directly, or included from an external file using the src attribute.
<script type="text/javascript" src="/scripts/util/Util.js"> </script>

Fetching DOM resources

The browser must perform many subsequent HTTP (or other) requests to the web server to collect these additional resources. These resources may be on the same server as the web server, or on different servers.

Browser plugins

Plugins in your browser can interfere with and/or modify the response. For example, AdBlock prevents ads from showing.

Browser rendering engines

The rendering engine (web browser engine) renders the page to the graphical content you see. It decides how things like check-boxes on forms are displayed. Examples:

  • Blink: Google Chrome
  • EdgeHTML: Microsoft Edge
  • WebKit: Apple Safari
  • Gecko: Mozilla Firefox
💡
Why it matters: The DOM is the bridge between static HTML and dynamic behaviour. When JS "changes the page", it is really changing the DOM, and the rendering engine repaints from that model.

Web Hosts: Server Software, Operating Systems and Stacks

The server side is a marketplace of choices — pick the web server, OS and stack that match your scale and skill.

  • MEAN: MongoDB, Express.js, Angular.js, Node.js

🧠
Memory hook: Stacks are just acronyms for the same four jobs — OS, web server, database, language. LAMP is the classic; MEAN is the all-JavaScript one.

Requirement Analysis and Use Cases

Requirements start as problems, become actions and actors, and finally become documented use cases a team can build against.

Step one: Identify problems

Ask: what are the core issues you are trying to solve?

  • Identify reasons why someone would want to use your website/solution.
  • What problem does your website solve for people?
  • Create a series of problem statements, e.g.:
  • "Buyers have no way of expressing how much they want to pay for an item"
  • "Sellers have difficulty determining the price to sell at"
  • "Non-technical people have no way of getting a website built"

Step two: Determine use cases

Convert your problem statements into use cases. Use cases are made up of actions, which are performed by actors.

  • Action: A simple, distinct, and easily defined action performed by an actor.
  • Actor: A role within the system, not an individual.

Process:

  1. Identify flow of events
  2. Extract distinct actions
  3. Group associated actions into a high-level use case
  4. Expand use cases into extensions

UML use case diagram

UML stands for Unified Modelling Language. A use case diagram models the actors and the use cases they participate in (the lecture's example is a use case model of a restaurant business).

Use case documentation — flow of events

Create a big table listing the use cases. Describe each use case using fields such as:

  • Name: A short name for the use case.
  • Goal: The main goal the use case tries to achieve.
  • Actors: Actors who initiate and/or are involved in the use case.
  • Preconditions: Conditions that must be met before the use case starts.
  • Main flow: A full description of the use case.
  • Subflows: Actions or use cases on which the use case depends.
  • Alternative flows: Alternative action flows, e.g. from error scenarios.
  • Priority: Importance of the use case to the system or the MVP.
💡
Why it matters: Actors are roles, not people. One person can be several actors, and one actor can be played by many people — this abstraction keeps requirements stable as staffing changes.
🤔
Pause & predict: Turn this problem into a use case: "Buyers have no way of expressing how much they want to pay." Who is the actor, and what is the action?

Diagramming the Design: Sequence, State and Wireframes

Different diagrams answer different questions: sequence shows order of interaction, state shows how things change over time, wireframes show rough layout.

Sequence diagrams

  • Describe how objects interact with each other and in what order.
  • Very useful for communicating how several systems interact, or for providing detail around how various actors interact with system components in a multi-step process.
  • Example: a computer asking a server for emails.

State diagrams

  • Also known as state machine diagrams; they describe the various states of system components.
  • Essential for communicating how abstract concepts — such as tickets or user accounts — progress through the system.
  • States are defined, as are state transitions, which constrain how objects are allowed to transition between states.
  • Example: a UML State Diagram.

Wireframes

  • Wireframing allows designers to gain a visual "feel" for the site without focussing on graphical detail.
  • The idea is to create a "cartoon" version of the website that enables a preliminary website experience.
  • Wireframes are usually a series of images, but can sometimes include clicking and linkage between images in the form of a storyboard.
  • Example: a Profile Page Wireframe.
DiagramQuestion it answers
Use caseWho does what with the system?
SequenceIn what order do objects/systems interact?
StateWhat states exist and how do we move between them?
WireframeWhat does the layout roughly look and feel like?
🧠
Memory hook: Sequence = time, State = lifecycle, Wireframe = layout. Match the diagram to the question you are asking.

Documentation: The Software Requirements Specification

The SRS is the single source of truth that says what the system does and does not do — it is how you eventually declare the project "finished".

A Software Requirements Specification (SRS) details exactly what the system does and does not do. In essence, the SRS is a communication tool between project stakeholders and software designers.

It is very important because:

  • It allows you to say the project is "finished".
  • It mitigates scope creep.
  • It forms the primary specification document and should capture all information regarding the project.
⚠️
Common trap: Any diagrams should not introduce new information not contained within the SRS. Diagrams provide additional context/clarification only — never new requirements.

SRS: Introduction

The introduction should encapsulate enough information for a business executive to understand what the project is about, including all important considerations, without too much depth.

  • Purpose
  • Definitions
  • System Overview
  • References

SRS: Overall description

The overall description discusses the project from a high level, but still examines details such as how it's used, how it works, the scope of the system, dependencies and requirements, and constraints.

  • Product Perspective
  • System Interfaces
  • User Interfaces
  • Hardware/software/communication interfaces
  • Memory constraints
  • Design Constraints
  • Operations
  • Site adaptation requirements
  • Product functionality
  • User characteristics
  • Constraints, assumptions and dependencies

SRS: Specific requirements

The specific requirements section gets down to the nitty-gritty details and contains highly granular requirements. It should be easy to identify whether a system does or does not satisfy these requirements.

  • External interface requirements
  • Functional requirements
  • Performance requirements
  • Logical database requirements
  • Software system attributes
  • Reliability
  • Availability
  • Security
  • Maintainability
  • Portability
💡
Why it matters: Without an SRS there is no agreed definition of "done", so a project can never actually finish — every new idea silently expands the scope. The SRS is the fence that protects the team's time.

Key Takeaways

If you remember nothing else, remember this.

1

A page load is a relay: parse URL → check cache → identify network → resolve DNS → open TCP → send HTTP request → load balancer routes → app server + database → return response → fetch assets → render.

2

A URL is protocol://domain.tld/path/file.ext; cusp.sydney.edu.au splits into subdomain cusp, domain sydney, gTLD edu and ccTLD au.

3

The browser cache stores JS, CSS, images and fonts so repeat visits skip network requests.

4

DHCP supplies the IP address, subnet mask, default gateway and nameservers; bad DHCP is the first thing to check when no site loads.

5

DNS resolves names to IPs: check local entries, find nameservers (from DHCP / /etc/resolv.conf), query a nameserver on UDP port 53, recurse upward, return the matching A-record.

6

TCP (layer 4) guarantees in-order delivery and uses ports 80/443 for HTTP/HTTPS; UDP is best-effort datagrams, used by DNS on UDP port 53, and TCP/UDP ports are distinct.

7

HTTP messages are header + optional body; methods are GET, POST, HEAD, PUT, DELETE and OPTIONS.

8

Typical architecture layers a DDoS-mitigating edge, a load balancer, app servers (code, business logic, DB interfaces, caching) and databases, with HTTPS provided by TLS.

9

SQL databases enforce relationships; NoSQL databases are schema-light. Master DBs take reads and writes; read-only slaves are replicated for scale.

10

Slave drift (replication delay) means a read after a write can be stale; decision-critical reads (e.g. payments) must hit the master.

11

The app server fills a template ({{ }} for values, {% %} for code) to produce the response, which returns header (status code, content type, length) plus body.

12

Status codes: 1xx info, 2xx success (200 OK), 3xx redirect (302 follows the Location header), 4xx client error (404), 5xx server error (502).

13

The browser builds the DOM from HTML, styles it with CSS, manipulates it with JS, and paints it with a rendering engine (Blink, EdgeHTML, WebKit, Gecko).

14

Requirements flow from problem statements → actions/actors → use cases → SRS, and diagrams (sequence, state, wireframe) clarify but never add new requirements.

Q1

List, in order, the six client-side steps from typing a URL to sending the HTTP request.

Answer: (1) Browser parses the URL, (2) browser checks its cache, (3) the OS identifies the network, (4) the OS resolves the name using DNS, (5) the OS establishes a TCP connection to the web server, and (6) the browser submits the HTTP request to the web server.
Q2

Decompose https://cusp.sydney.edu.au/students/view-unit-page/uos_id/101257 into its parts.

Answer: Protocol = HTTPS; domain = cusp.sydney.edu.au, made up of subdomain cusp, domain sydney, gTLD edu and ccTLD au; path = /students/view-unit-page/uos_id/101257.
Q3

What four things does DHCP provide, and why is DHCP the first thing to check when no website loads?

Answer: DHCP provides the IP address, subnet mask, default gateway and nameservers. If any of these are wrong, the machine cannot correctly identify what is local, route packets off-network, or resolve names — so every request fails, regardless of the destination site.
Q4

Describe how the OS resolves a domain name to an IP address.

Answer: It first checks local OS DNS entries (e.g. /etc/hosts), identifies the nameservers (usually from DHCP, listed in /etc/resolv.conf), submits a UDP request to a nameserver on port 53, and the nameservers recursively query parent nameservers until one knows the address; the IP is returned according to the domain's matching A-record.
Q5

Compare TCP and UDP in terms of guarantees, terminology and ports.

Answer: TCP (layer 4) guarantees in-order delivery for the layers above, uses a handshake and calls its units segments; it is vulnerable to TCP flooding attacks, and standard ports include 80 (HTTP), 443 (HTTPS) and 22 (SSH). UDP is a best-effort layer-4 protocol that sends datagrams, does not acknowledge or retransmit packets (unless the application does so explicitly) and enforces no handshake; DNS uses UDP port 53. TCP and UDP ports are treated as different.
Q6

What are the parts of an HTTP request/response, and what does each HTTP method do?

Answer: Every HTTP message has a header (meta-data such as cookies, connection info, or for responses the status code, content type and length) and an optional body (the transmitted data). GET is a header-only simple request; POST sends data in the body (form data, file upload); HEAD is like GET but the response omits the body; PUT replaces a target resource; DELETE removes a target resource; OPTIONS asks which methods are allowed against a resource.
Q7

What is the role of a load balancer, and what other services often sit in front of it?

Answer: A load balancer routes requests to appropriate servers for processing, allowing a pool of servers to share incoming requests by forwarding each to an available resource; it can route on health/performance or content, do SSL offloading and port-forward HTTP to HTTPS. In front of or alongside it sit DDoS-mitigation services such as a web application firewall (e.g. CloudFlare), which forwards legitimate packets and drops attack packets, and a Content Delivery Network (CDN).
Q8

Explain master/slave database replication and the danger of slave drift.

Answer: The master (primary) accepts both reads and writes and there is usually only one; slaves (replicas) receive replicated updates and serve reads only, so many slaves can be added to parallelise reads. Because replication is not instantaneous, there is a small but significant delay — slave drift, or replication delay — so a read shortly after a write may return stale data. Reads that drive important decisions such as payments should go to the master to avoid race conditions; some configurations avoid drift but trade off delayed writes or reduced fault tolerance.
Q9

How does an app server turn business logic into an HTTP response, and what delimiters are used in templates?

Answer: It inserts data into a template to form the response, where variables are inserted between {{ and }} and code can be specified between {% and %}. The resulting response has a header (status code, content type, length) and an optional body (typically HTML or the requested resource).
Q10

Give the meaning of status categories 1xx–5xx and state how a browser handles 200 and 302.

Answer: 1xx = informational (100 Continue, 101 Switching Protocols); 2xx = success (200 OK); 3xx = redirection (301 Moved Permanently, 302 Found/Moved Temporarily, 304 Not Modified); 4xx = client error (404 Not Found); 5xx = server error (502 Bad Gateway). A 302 makes the browser immediately follow the URL in the Location response header, while a 200 is usually accompanied by a resource in the body that the browser renders.
Q11

What is the DOM, and how do CSS, JavaScript and rendering engines relate to it?

Answer: The DOM (Document Object Model) is the browser's internal tree representation of the page, built by parsing HTML; the relationships between elements such as <div> and <img> are defined in it and can be manipulated (e.g. by jQuery). CSS specifies positional and appearance attributes of DOM elements, either inside <style> tags or external files linked via <link> in the head; JavaScript performs arbitrary computation and live DOM manipulation, inline in <script> tags or via the src attribute. The rendering engine (Blink in Chrome, EdgeHTML in Edge, WebKit in Safari, Gecko in Firefox) paints the DOM to the screen.
Q12

Turn "Sellers have difficulty determining the price to sell at" into a use case, naming the actor and action.

Answer: The actor is the Seller (a role, not an individual) and the action is setting/listing a price for an item. Grouped with related actions (creating a listing, editing the price) this forms a high-level use case such as "Sell an item", which would then be documented with its name, goal, actors, preconditions, main flow, subflows, alternative flows and priority.
Q13

What is the difference between sequence diagrams, state diagrams and wireframes?

Answer: Sequence diagrams show how objects interact and in what order (useful for multi-step interactions between systems or actors). State (state machine) diagrams define the states of a component and the allowed transitions between them, useful for tracking things like tickets or user accounts. Wireframes are rough "cartoon" layouts that give a visual feel without graphical detail and may be linked into a storyboard.
Q14

What is an SRS and why is it important? What must diagrams never do?

Answer: A Software Requirements Specification details exactly what the system does and does not do, acting as a communication tool between stakeholders and designers; it lets you declare the project "finished" and mitigates scope creep, and it should capture all project information. Diagrams may provide additional context or clarification but must never introduce new information not already contained in the SRS.
