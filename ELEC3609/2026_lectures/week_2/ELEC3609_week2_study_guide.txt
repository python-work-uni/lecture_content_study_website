SECTION 1: WHAT HAPPENS WHEN YOU ENTER A URL
------------------------------------------------

When you type a URL and hit Enter, the browser and OS work together through a precise sequence of steps:

**Client-side steps:**
1. **Parse URL** — Break into scheme (https), domain (cusp.sydney.edu.au), and path (/students/...)
2. **Check cache** — Browser looks for cached copies of HTML, CSS, JS, images, fonts
3. **Identify network** — OS reads DHCP config: your IP, subnet mask, default gateway, DNS servers
4. **Resolve DNS** — OS asks a nameserver (port 53/UDP) for the domain's IP address
5. **Establish TCP connection** — Three-way handshake to the web server on port 443 (HTTPS)
6. **Send HTTP request** — Browser transmits the request over the open TCP connection

**Server-side steps:**
1. **Load balancer receives** — Establishes TCP, parses HTTP headers, routes to app server
2. **App server processes** — Runs backend logic, queries databases (master for writes, slaves for reads)
3. **Generate response** — Renders HTML via template engine (variables in {{ }}, logic in {% %})
4. **Return response** — Sends HTTP response back through the load balancer

**Client continues:**
1. **Parse response** — Check status code (200 = OK, 302 = redirect, etc.)
2. **Fetch additional resources** — CSS, JS, images, web sockets, plugins
3. **Render page** — Browser engine builds DOM, applies CSS, executes JS, paints pixels

💡 **Why it matters:** This is the complete request/response lifecycle. Every web application you build lives inside this flow. Understanding each step lets you debug performance issues, security problems, and architecture decisions.

**Memory aid — "P-C-D-T-H-F" for Client Steps:**
- **P**arse URL
- **C**heck Cache
- **D**NS resolution
- **T**CP handshake
- **H**TTP request
- **F**etch resources & render

**Worked example — URL breakdown:**
```
https://cusp.sydney.edu.au/students/view-unit-page/uos_id/101257
│    │              │                    │
│    │              │                    └── Path
│    │              └─────────────────────── Domain (subdomain.domain.gTLD.ccTLD)
│    └────────────────────────────────────── Protocol (HTTPS = HTTP over TLS)
```

SECTION 2: MAKING A WEB REQUEST — URL, CACHE, DNS, TCP, HTTP
------------------------------------------------

**URL Components:**
- **Protocol/scheme** — HTTPS (HTTP over TLS/SSL), HTTP (plaintext)
- **Domain hierarchy** — subdomain.domain.gTLD.ccTLD (e.g., cusp.sydney.edu.au)
- **Path** — Resource identifier on the server

**Browser Cache:** Stores JS, CSS, images, fonts. If cached and fresh, browser skips network entirely.

**Network Configuration (DHCP provides):**
- **IP Address** — Your machine's local identity
- **Subnet Mask** — Defines "local" vs "remote" IPs
- **Default Gateway** — Router that forwards packets outside your subnet
- **Nameservers** — DNS servers for domain resolution (check /etc/resolv.conf)

**DNS Resolution (recursive, UDP port 53):**
1. Check local /etc/hosts
2. Query configured nameserver
3. Nameserver recursively asks parent servers (root → TLD → authoritative)
4. Returns A-record (IPv4) or AAAA-record (IPv6)

💡 **Why it matters:** DNS is often the first failure point. If you can't reach sites, check DNS first (dig, nslookup).

**TCP vs UDP (Layer 4 of OSI):**

| Feature | TCP | UDP |
|---------|-----|-----|
| Delivery | Guaranteed, in-order | Best-effort, no ordering |
| Mechanism | 3-way handshake, ACKs, retransmission | Fire-and-forget datagrams |
| Overhead | Higher (connection state) | Lower |
| Use cases | HTTP, SSH, Email | DNS, streaming, gaming |
| Port examples | 80 (HTTP), 443 (HTTPS), 22 (SSH) | 53 (DNS) |

**TCP Three-Way Handshake:**
1. Client → SYN
2. Server → SYN-ACK
3. Client → ACK
Connection now established.

**HTTP Request Structure:**
- **Header** — Metadata: cookies, auth, content-type, connection info
- **Body** — Optional payload (POST, PUT)

**HTTP Methods:**
- **GET** — Retrieve resource (header only)
- **POST** — Submit data (form, file upload)
- **HEAD** — Like GET but no response body
- **PUT** — Replace resource entirely
- **DELETE** — Remove resource
- **OPTIONS** — Ask what methods are allowed

💡 **Why it matters:** Method semantics matter for REST APIs. GET must be safe/idempotent; POST is not idempotent.

SECTION 3: RESPONDING TO A WEB REQUEST — SERVER ARCHITECTURE
------------------------------------------------

**Typical Three-Layer Architecture (AWS example):**

```
Internet → [DDoS Protection/CDN] → [Load Balancer] → [App Servers] → [Database]
              (CloudFlare)          (ELB)            (EC2/Lambda)      (RDS)
```

**Layer 1: Internet-Facing (Edge)**
- **DDoS mitigation / WAF** — CloudFlare, AWS Shield. Filter attack traffic before it hits your infra.
- **CDN** — Cache static assets globally (CloudFront, CloudFlare). Reduces latency, offloads origin.

**Layer 2: Load Balancer (ELB)**
- Routes based on health, performance, request content
- **SSL termination** — Decrypts HTTPS, forwards HTTP to backend (reduces backend CPU)
- **Port forwarding** — Redirect HTTP → HTTPS

**Layer 3: Application Servers**
- Run backend code (business logic, DB access, caching)
- **Deployment models:**
  - **VMs (IaaS)** — EC2, GCE. Full OS control, more ops burden.
  - **Containers** — Docker. Portable, consistent environments.
  - **Serverless** — Lambda, Cloud Functions. Auto-scale, pay-per-invocation.

**App Server Frameworks by Language:**
- Python: Flask, Django
- PHP: CodeIgniter, CakePHP, Laravel
- Ruby: Rails
- JavaScript: Express.js (Node.js)

**Databases — Persistent Data:**

| Type | Examples | Characteristics |
|------|----------|-----------------|
| **SQL (Relational)** | MySQL, PostgreSQL, SQLite, SQL Server | Schema-enforced, ACID, JOINs, relationships |
| **NoSQL (Non-relational)** | MongoDB, Redis, DynamoDB, Cloud Datastore | Flexible schema, horizontal scale, eventual consistency |

**Master/Slave (Primary/Replica) Replication:**
- **Master/Primary** — Accepts reads AND writes. Single writer.
- **Slaves/Replicas** — Read-only copies. Async replication from master.
- **Benefit** — Scale reads horizontally (many slaves), single write path.

**Slave Drift (Replication Lag):**
- Writes to master → async propagate to slaves → **delay exists**
- **Critical reads** (payments, auth decisions) must hit **master** to avoid stale data
- Trade-off: Synchronous replication = no drift but slower writes + lower availability

**HTTP Response Generation:**
- Template engine inserts data: `{{ variable }}` for values, `{% logic %}` for control flow
- Response = Header (status, content-type, length) + Body (HTML/JSON/resource)

SECTION 4: PARSING A WEB RESPONSE — CLIENT SIDE
------------------------------------------------

**HTTP Status Code Categories:**

| Category | Meaning | Key Codes |
|----------|---------|-----------|
| **1xx** | Informational | 100 Continue, 101 Switching Protocols |
| **2xx** | Success | **200 OK**, 201 Created, 204 No Content |
| **3xx** | Redirection | **301 Moved Permanently**, **302 Found**, 304 Not Modified |
| **4xx** | Client Error | **400 Bad Request**, 401 Unauthorized, 403 Forbidden, **404 Not Found** |
| **5xx** | Server Error | **500 Internal Server Error**, **502 Bad Gateway**, 503 Service Unavailable |

**Browser Behavior on Key Codes:**
- **302** — Follow `Location` header immediately (redirect)
- **200** — Render response body (usually HTML)
- **304** — Use cached version (conditional GET with ETag/If-Modified-Since)

**HTML → DOM Parsing:**
- Browser builds **Document Object Model (DOM)** — tree of nodes representing HTML elements
- JS (jQuery, React, vanilla) manipulates DOM to update UI
- Browser extensions also hook into DOM

**DOM Resources (fetched via additional requests):**
- **CSS** — `<link rel="stylesheet" href="...">` or `<style>...</style>`
- **JavaScript** — `<script src="..."></script>` or inline `<script>...</script>`
- **Images, fonts, WebSocket connections, plugins**

**Browser Rendering Engines:**
- **Blink** — Chrome, Edge, Opera
- **WebKit** — Safari
- **Gecko** — Firefox

💡 **Why it matters:** Rendering pipeline determines page load performance. Critical rendering path = HTML → DOM → CSSOM → Render Tree → Layout → Paint.

SECTION 7: USE CASES — REQUIREMENTS ANALYSIS
------------------------------------------------

**Two-Step Process:**

**Step 1: Identify Problems**
- What core issues does the system solve?
- Write **problem statements**:
  - "Buyers have no way to express max price"
  - "Sellers can't determine optimal listing price"
  - "Non-technical users can't get websites built"

**Step 2: Convert to Use Cases**
- **Actor** — A *role* (not a person): Customer, Admin, Payment Gateway
- **Action** — Simple, distinct, testable step
- **Use Case** — Group of related actions achieving a goal

**Process:**
1. Identify flow of events
2. Extract distinct actions
3. Group into high-level use cases
4. Expand into extensions (alternative/error flows)

**Use Case Documentation Fields:**
| Field | Purpose |
|-------|---------|
| Name | Short identifier |
| Goal | What the use case achieves |
| Actors | Who initiates/participates |
| Preconditions | Must be true before start |
| Main Flow | Happy path, step by step |
| Subflows | Dependent use cases |
| Alternative Flows | Errors, edge cases |
| Priority | MVP importance |

💡 **Why it matters:** Use cases bridge business needs and technical design. They drive test cases and acceptance criteria.

**Memory aid — "A-P-M-S-A-P" for Use Case Doc Fields:**
- **A**ctors
- **P**reconditions
- **M**ain Flow
- **S**ubflows
- **A**lternative Flows
- **P**riority

SECTION 8: SEQUENCE DIAGRAMS
------------------------------------------------

**Purpose:** Show *how objects interact* and *in what order* over time.

**Elements:**
- **Lifelines** — Vertical dashed lines (objects/actors)
- **Messages** — Horizontal arrows (sync=filled, async=open, return=dashed)
- **Activation bars** — Rectangles on lifelines showing active execution
- **Fragments** — `alt`, `opt`, `loop`, `par` for control flow

**When to use:**
- Multi-system interactions (client → LB → app → DB)
- Complex multi-step processes (checkout, auth flow)
- API contract clarification

**Example:** Computer → Server email retrieval:
```
Client          Server
  │               │
  ├─LOGIN────────►│
  │◄─OK───────────┤
  ├─LIST─────────►│
  │◄─EMAIL LIST───┤
  ├─FETCH 1──────►│
  │◄─EMAIL 1──────┤
```

------------------------------------------------
SECTION 9: STATE & FLOW DIAGRAMS
------------------------------------------------

**State Diagrams (State Machines):**
- Show **states** of an object and **valid transitions** between them
- Essential for entities with lifecycle: Order, Ticket, User Account, Payment

**Key concepts:**
- **State** — Condition at a point in time (e.g., "Cart: Empty", "Order: Paid")
- **Transition** — Event-triggered move (e.g., "Add item" → "Cart: Active")
- **Guard conditions** — Transition only if condition met
- **Initial/Final states** — Filled circle → start; bullseye → end

**Example: Order State Machine**
```
[Created] ──pay──► [Paid] ──ship──► [Shipped] ──deliver──► [Delivered]
    │                  │
    └──cancel──────────┘
```

💡 **Why it matters:** Prevents invalid states (shipping an unpaid order). Maps directly to DB status columns and business logic.

SECTION 11: DOCUMENTATION — SOFTWARE REQUIREMENTS SPECIFICATION (SRS)
------------------------------------------------

**SRS Purpose:** Single source of truth defining what the system **does and does not do**. Communication tool between stakeholders and developers. Prevents scope creep. Defines "done."

**SRS Structure (IEEE 830 style):**

**1. Introduction**
- **Purpose** — Why this document exists
- **Definitions** — Glossary of terms, acronyms
- **System Overview** — High-level summary
- **References** — Related docs, standards

**2. Overall Description**
- **Product Perspective** — System interfaces, user interfaces, HW/SW/comms interfaces, memory constraints
- **Design Constraints** — Operations, site adaptation, regulatory
- **Product Functionality** — Feature summary
- **User Characteristics** — Who uses it, technical level
- **Constraints, Assumptions, Dependencies**

**3. Specific Requirements (granular, testable)**
- **External Interface Requirements** — APIs, UI, hardware
- **Functional Requirements** — "The system shall..." (use case traces)
- **Performance Requirements** — Response time, throughput, capacity
- **Logical Database Requirements** — Schema, relationships, retention
- **Software System Attributes (Quality Attributes):**
  - **Reliability** — MTBF, recovery time
  - **Availability** — Uptime % (99.9% = ~8.76h/yr downtime)
  - **Security** — AuthZ, AuthN, encryption, audit
  - **Maintainability** — Modularity, testability, deployability
  - **Portability** — Platform independence, containerisation

💡 **Golden Rule:** Diagrams **clarify** — they must not introduce new requirements not in the SRS text.

**Memory aid — "FURPS+" for Quality Attributes:**
- **F**unctionality (Functional requirements)
- **U**sability
- **R**eliability
- **P**erformance
- **S**upportability (Maintainability)
- **+** = Security, Portability, etc.

================================================
KEY TAKEAWAYS
================================================

• **Web request lifecycle** is deterministic: Parse URL → Cache → DNS → TCP → HTTP → Server processing → Response → DOM → Render. Every step is a potential failure/optimisation point.

• **DNS uses UDP/53** (fast, no handshake); **HTTP uses TCP/80 or 443** (reliable, ordered). TLS terminates at load balancer (SSL offloading).

• **Master/Slave databases** scale reads but introduce **replication lag** — critical decisions must read from master.

• **HTTP methods have semantics**: GET=safe/idempotent, POST=neither, PUT= idempotent, DELETE=idempotent. Design APIs accordingly.

• **Status codes drive client behavior**: 3xx=redirect, 2xx=render, 4xx=fix request, 5xx=retry/server fix.

• **Browser rendering pipeline**: HTML→DOM, CSS→CSSOM, merge→Render Tree→Layout→Paint→Composite. Blocking resources (sync JS, CSS in head) delay first paint.

• **Nginx > Apache** for high concurrency (event-driven vs process-per-request). Linux dominates server OS (>60%).

• **Use cases** translate business problems into testable scenarios. Document with: Actors, Preconditions, Main Flow, Alternatives, Priority.

• **Sequence diagrams** = time-ordered interactions. **State diagrams** = valid lifecycle transitions. Both prevent design bugs.

• **SRS is the contract**. Specific requirements must be **testable** ("system shall respond in <200ms" not "system shall be fast"). Quality attributes (FURPS+) are non-functional requirements.

• **Task management tool** should match team process: GitHub for dev-centric agile, Jira for enterprise SDLC, Trello/Asana for lightweight visual.

CONCRETE EXAMPLES / ANALOGIES
================================================

**Analogy 1: DNS = Phone Book + Recursive Lookup**
You want to call "Jiawen Wen." You don't know the number. You ask your local directory (nameserver). If they don't know, they ask the state directory, then national, until someone has the listing. The number (IP) comes back. You dial (TCP connect).

**Analogy 2: Master/Slave DB = Authoritative Ledger + Photocopies**
The Master is the single official ledger. Every write goes there. Slaves are photocopies distributed to reading rooms. Photocopying takes time (replication lag). If you need the absolutely latest entry (payment confirmation), you go to the official ledger (master), not a photocopy (slave).

**Analogy 3: TCP vs UDP = Registered Mail vs Postcard**
TCP = Registered mail: Tracked, signed for, re-sent if lost, arrives in order. UDP = Postcard: Dropped in box, no tracking, might arrive out of order or not at all. DNS uses postcards (speed critical, small payload). HTTP uses registered mail (correctness critical).

**Worked Example: HTTP Request/Response Pair**
```
REQUEST:
GET /api/users/42 HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOi...
Accept: application/json

RESPONSE:
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 127
ETag: "abc123"

{"id":42,"name":"Jiawen","role":"lecturer","enrolled":["ELEC3609"]}
```

**Worked Example: Slave Drift Bug**
1. User A posts comment → writes to Master (comment_id=100)
2. User B loads page → reads from Slave (replication lag 200ms)
3. Slave doesn't have comment_id=100 yet → User B doesn't see comment
4. User B thinks comment failed → posts duplicate
5. Both comments appear after replication catches up

COMPLEXITY / QUANTITATIVE NOTES
================================================

**DNS Resolution**: Typically 1-3 round trips (client → resolver → root → TLD → authoritative). Cached = 0 RTT.

**TCP Handshake**: 1 RTT (SYN → SYN-ACK → ACK) before first HTTP byte. TLS 1.2 = +1 RTT; TLS 1.3 = 0 RTT (resumption) or 1 RTT (full).

**HTTP/1.1 vs HTTP/2**: H1.1 = 1 request per connection (pipelining broken). H2 = multiplexed streams over 1 connection. H3 (QUIC) = UDP-based, 0-RTT.

**Availability Math**:
- 99% = 3.65 days/year downtime
- 99.9% = 8.76 hours/year
- 99.99% = 52.6 minutes/year
- 99.999% = 5.26 minutes/year ("five nines")

**Replication Lag**: Typically 10-500ms in same region; cross-region = 50-500ms+. Synchronous = zero lag but write latency = slowest replica.

**Nginx Worker Model**: `worker_processes auto;` (1 per CPU core). Each worker handles thousands of connections via epoll/kqueue. Memory per connection ~2-5KB vs Apache ~8MB.
