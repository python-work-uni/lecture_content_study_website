SECTION 1: Entering a URL: Full Journey
------------------------------------------------
When a user types a URL and presses Enter, the browser and the operating system cooperate through a fixed sequence of steps. The browser parses the URL into its components (scheme, domain, path/file), performs the request, and then renders whatever comes back. This sequence is the backbone of every web application you will ever build, so learn it as a story rather than as isolated facts.

### Client Steps (before the request leaves your machine)
1. **Browser: Parse URL** — split the address into protocol, domain and path.
2. **Browser: Check cache** — look for a locally stored copy of the page's assets.
3. **OS: Identify network** — read the DHCP configuration (your IP, subnet mask, gateway, nameservers).
4. **OS: Resolve using DNS** — turn the domain name into an IP address.
5. **OS: Establish TCP connection** — open a reliable connection to the web server.
6. **Browser: Submit HTTP request** — send the request over that open connection.

### Server Steps (what happens at the other end)
1. **Load balancer (LB)** establishes the TCP connection and receives the HTTP request.
2. The **LB software** parses the HTTP header, then routes and forwards the request to an application (app) server.
3. The **app server** executes back-end website logic, probably connecting to one or more databases.
4. The **app server** renders a response and returns it over the TCP connection.

### Client Continues (turning the response into a page)
1. **Parse response** — read the status code and headers.
2. **Fetch additional resources** — assets (CSS, JS, images), establish web socket connections, and load browser plugins.
3. **Render page** — the browser paints the result on screen.

🧠 **Memory Hook:** Remember the client path as **Parse → Cache → Network → DNS → TCP → HTTP → Render**. Each arrow is a chance for the page to be slow or to fail.

💡 **Why It Matters:** If you can name every step, you can debug almost any "the site won't load" problem by asking *which step broke*.

SECTION 2: URL Anatomy & Browser Cache
------------------------------------------------
Every URL follows a simple shape:

**URL Format**: `protocol://domain.tld/path/file.ext`

A real example from the lecture:

```
https://cusp.sydney.edu.au/students/view-unit-page/uos_id/101257
  |              |                        |
protocol       domain                    path
```

- **Protocol (scheme)** — the rules for the conversation. For the example it is **HTTPS**, meaning *HyperText Transfer Protocol (Secure)*.
- **Domain** — `cusp.sydney.edu.au`, read from most specific to least specific:
  - **Subdomain** — `cusp`
  - **Domain** — `sydney`
  - **Generic top-level domain (gTLD)** — `edu`
  - **Country code top-level domain (ccTLD)** — `au`
- **Path** — `/students/view-unit-page/uos_id/101257`, which identifies the specific resource on the server.

### The Browser Cache
Before doing anything expensive, the browser checks its own cache. The cache stores copies of many kinds of assets:
- JavaScript files
- CSS files
- Images
- Fonts

If a fresh copy is already stored, the browser can skip a network round trip entirely. This is why a page you have visited often feels instant the second time.

📌 **Info:** The cache is the browser's short-term memory. It trades freshness for speed — a cached asset may be stale, which is why servers send cache-control headers.

SECTION 3: Network, DNS & the OSI Model
------------------------------------------------
### Identifying the Network Landscape
When you join a network, your computer is usually configured automatically by **DHCP (Dynamic Host Configuration Protocol)**. DHCP provides four things:

| Setting | Meaning |
| --- | --- |
| **IP Address** | Identifies your computer on the local network |
| **Subnet Mask** | Defines what "local" means relative to your IP address |
| **Default Gateway** | A host that can route packets to non-local IP addresses |
| **Nameservers** | A host (DNS server) used to resolve domain names |

📌 **Info:** If you cannot reach any website at all, checking the network configuration is the first thing to do.

### Resolving a Domain with DNS
We cannot connect to `cusp.sydney.edu.au` directly — the network needs an IP address. The OS resolves the name roughly as follows:

1. Check OS local DNS entries (e.g. `/etc/hosts/`).
2. Identify the nameservers — usually provided by DHCP and specified in `/etc/resolv.conf`.
3. Submit a **UDP request to a nameserver on port 53**.
4. Nameservers keep **recursively asking their parent nameserver** until one of them knows the IP.
5. The IP is returned according to a matching **A-record** for the domain.

🧠 **Memory Hook:** DNS is a *recursive phone book* — you ask your local directory, which asks bigger directories until someone knows the number, then hands the number back to you.

### The OSI Model (a Conceptual Recap)
The **OSI Model** is a way to conceptualise network systems, where each layer is an abstraction of the one below it. The lecture highlights four layers:

- **Layer 1** — the physical medium: copper line, coax, fibre, etc.
- **Layer 2** — local wireless/link standards such as IEEE 802.11a/b/g/n.
- **Layer 4** — transport protocols: **TCP / UDP**.
- **Layer 7** — application protocols: **HTTPS**.

💡 **Why It Matters:** OSI tells you *which layer to inspect* when something breaks. DNS failures are layer 7 naming, TCP failures are layer 4, and a cut cable is layer 1.

SECTION 4: TCP, UDP & the Handshake
------------------------------------------------
**TCP (Transmission Control Protocol)** and **UDP (User Datagram Protocol)** both live on **Layer 4** of the OSI model. They are *not* responsible for addressing or segregation (the layers below handle that) — they are responsible for delivering packets to the application above.

| | TCP | UDP |
| --- | --- | --- |
| **Layer** | 4 | 4 |
| **Mechanism** | Guarantees in-order delivery for the layers above; uses a handshake | "Best effort" — sends datagrams rather than TCP segments; no acknowledgement, no retransmission unless done explicitly at the application layer; no handshake |
| **Port designation** | Needed, e.g. SSH on TCP/22 | Needed, e.g. DNS on UDP/53 |

⚠️ **Common Trap:** A famous attack pattern against TCP is **TCP flooding** — overwhelming the handshake machinery with connection attempts.

### Establishing a TCP Connection
TCP segments are assigned to particular **ports**, which define which application they are intended for. Standard default ports:
- **HTTP: port 80**
- **HTTPS: port 443**

Web servers can run on non-standard ports — 80 and 443 are just conventions.

The TCP handshake is the three-message exchange that opens a connection:
```
Client → SYN → Server → SYN-ACK → Client → ACK
```
After the client's final ACK, the connection is established and HTTP can flow.

### Aside: User Datagram Protocol
UDP does **not** guarantee delivery at all. It sends **datagrams** instead of TCP's **segments**; deliveries are not acknowledged and packets are not re-transmitted unless the application explicitly does so. UDP operates on ports, but TCP and UDP ports are considered different. Crucially, **DNS operates on UDP port 53 and does not use TCP.**

🧠 **Memory Hook:** TCP = registered mail (tracked, ordered, re-sent). UDP = a postcard (fast, cheap, may never arrive). DNS picks the postcard; HTTP picks registered mail.

SECTION 5: HTTP Requests & Methods
------------------------------------------------
### HTTP Structure
An HTTP request or response consists of two sections:
- **Header** — meta-data such as cookie and connection information.
- **Body** — the data to be sent with the transmission (optional).

**HTTP Request Line**: `GET /path HTTP/1.1`

### Types of Web Requests
| Method | What it does |
| --- | --- |
| **GET** | A simple request; header only |
| **POST** | A request containing data in the body, e.g. form data or a file upload |
| **HEAD** | Same as GET, except the server omits the body in the response (only sends the header) |
| **PUT** | Replace a target resource on the server |
| **DELETE** | Delete a target resource on the server |
| **OPTIONS** | Ask the server which request types are allowed against a particular resource |

Once you have an open TCP connection to the web server, you send the HTTP request through that connection. The server processes it and returns a response made of a **header** (status code, content type, length) and a **body** (typically the HTML or the requested resource).

💡 **Why It Matters:** Methods carry meaning. GET should be safe to repeat and should not change state; POST submits new data. Choosing the right method is the basis of a clean REST API.

SECTION 6: Server Architecture: Edge to DB
------------------------------------------------
Real websites use a **three-layer architecture**. The lecture uses **AWS IaaS services** as the worked example, featuring **end-to-end encryption in transit** across:
- **Elastic Load Balancing (ELB)**
- **Elastic Compute Cloud (EC2)**
- **Relational Database Service (RDS)**

The three layers, from the outside in:

### Layer 1 — Internet-Facing Edge
A request rarely reaches the application directly. The first recipient is usually one of:
- **Load balancer (LB)** — routes requests to appropriate servers. LBs let a *pool* of servers handle incoming requests by forwarding each request to an available resource.
- **DDoS mitigation service / web application firewall** — serves as the first layer on large websites to ensure incoming requests are not part of a cyber attack. Legitimate packets are forwarded (often to the regular LB); attack packets are dropped. Example: **CloudFlare**.
- **Content Delivery Network (CDN)** — a geographically distributed cache of content.

### Layer 2 — Load Balancer Capabilities
Load balancing can:
- Route traffic based on **performance and health status**
- Route traffic based on **contents**
- Perform **SSL offloading (HTTPS)**
- Perform **port forwarding (HTTP to HTTPS)**

📌 **Info:** **Secured HTTP is HTTPS**, achieved using **TLS protocols** — SSL is obsolete.

### Layer 3 — Web / App Server / RDS
Web and application servers run the actual code, and databases use a **Master/Slave configuration for high availability (HA)**. This is where the majority of the work lies in a typical web architecture.

💡 **Why It Matters:** Each layer adds resilience. If one app server dies, the LB routes around it; if attack traffic spikes, the WAF absorbs it; the database stays private behind the app layer.

SECTION 7: App Servers, Frameworks & Databases
------------------------------------------------
### Application Servers
App servers do the actual processing of HTTP requests. They contain:
- Back-end website code
- Business logic
- Database interface methods
- Caching layers

Typical forms a web server can take:
- **Virtual machines (IaaS)** — EC2, GCE
- **Containers** — Docker
- **Serverless** — Lambda, Google Cloud Function

### App Server Programming Models
Developers usually work within a **web framework** rather than reinventing the wheel. Some languages, frameworks, and the real companies that use them:
- **Python** (e.g. Instagram) — Flask, Django
- **PHP** (e.g. Facebook) — Codeigniter, CakePHP
- **Ruby** (e.g. GitHub) — Ruby On Rails (RoR)
- **JavaScript** (e.g. Groupon) — Express.js (on Node.js)

### Databases — Persistent Data
App servers typically read information from databases, split into two main types:
- **SQL (relational)** — maintain and enforce relationships between data. Examples: MySQL, PostgreSQL, SQLite, Microsoft SQL Server.
- **NoSQL (non-relational)** — store data like loose pages, often without schemas. Examples: MongoDB, Redis, DynamoDB, Cloud Data Store.

Databases can reside on the same host as the app server, or **separately (recommended)**.

### Slave/Master Databases
To spread the load, separate reads from writes:
- **Master/Primary** — accepts reads *and* write operations. There is usually only **one** master.
- **Slaves/Replicas** — updates to the master are quickly replicated to all slaves. Slaves are used for **read operations only**. Because data is not modified on slaves, there can be many, improving parallelisability of reads.

### Slave Drift
Replication is not instantaneous. There is a small but significant delay between a write to the master and propagation to all slaves — this is **slave drift**, also called **replication delay**, and your application must manage it.

- DB reads that lead to **important decisions (e.g. payments)** should usually hit the **master** to prevent race conditions or side effects from stale data.
- Some replication configurations avoid this problem but bring other trade-offs, such as **delayed writes and/or reduced fault tolerance**.

⚠️ **Common Trap:** Reading a just-written record from a slave can make a successful write look like it failed, tempting the user to repeat the action and create a duplicate.

### Generating & Returning a Response
Once the app server has performed its logic, it generates the response — typically by **inserting data into a template**, which forms the HTTP response:
- **Variables** in the application code are inserted between `{{` and `}}`.
- **Code/logic** can be specified between `{%` and `%}`.

The response mirrors the request: a **Header** (HTTP status code, content type, length) and a **Body** (usually HTML or the requested resource, optional).

SECTION 8: Parsing a Web Response
------------------------------------------------
### HTTP Status Codes
The response can specify an **HTTP status code** that tells the client how to interpret what happened.

| Category | Definition | Example |
| --- | --- | --- |
| **1xx** | Informational | 100: Continue; 101: Switching Protocols |
| **2xx** | Success | 200: OK — the standard response |
| **3xx** | Redirection | 301: Moved Permanently; 302: Found/Moved Temporarily (similar to 303 & 307); 304: Not Modified |
| **4xx** | Client error | 404: Not found |
| **5xx** | Server error | 502: Bad gateway |

### Client Rendering
The status codes instruct the client on how to handle the response:
- A **302 (Found)** causes the browser to immediately follow the URL in the **Location** field of the response header.
- A **200 (OK)** is usually accompanied by a resource in the response body, which the browser renders.

### Parse HTML into the DOM
If the response contains HTML, the browser parses it into the **Document Object Model (DOM)** — the browser's internal, tree-like representation of the web page.
- Relationships between HTML elements (such as `<div>` or `<img>` tags) are defined and can be manipulated through the DOM.
- JavaScript libraries such as **jQuery** commonly manipulate the DOM to change the layout.
- **Browser plugins** often interact with the browser at this level.

### DOM Resources
HTML defines structure, but other resources define behaviour:
- **CSS (Cascading Style Sheets)** — positional and appearance attributes of DOM elements. Can be inside `<style>` tags or external files linked in the `<head>`: `<link rel="stylesheet" href="/styles/cusp_style.css" type="text/css" />`
- **JavaScript** — arbitrary computation in the browser, often live DOM manipulation. Can be inline `<script>` tags or an external file via the `src` attribute: `<script type="text/javascript" src="/scripts/util/Util.js"> </script>`

### Fetching DOM Resources
The browser must perform **many subsequent HTTP (or other) requests** to collect these additional resources. They may live on the same server as the web server, or on entirely different servers.

### Browser Plugins
Plugins can interfere with and/or modify the response — for example, **AdBlock** prevents ads from showing.

### Browser Rendering Engines
The **rendering engine (web browser engine)** turns code into the graphical content you see, and decides things like how check-boxes appear. Examples:
- **Blink** — Google Chrome
- **EdgeHTML** — Microsoft Edge
- **WebKit** — Apple Safari
- **Gecko** — Mozilla Firefox

🧠 **Memory Hook:** Engines — **B**link (Chrome), **E**dgeHTML (Edge), **W**ebKit (Safari), **G**ecko (Firefox).

SECTION 9: Web Hosts & Tech Stacks
------------------------------------------------
### Web Server Software
| Web Server | Description |
| --- | --- |
| **Apache** | Pretty simple, good for smaller websites. Typically spawns a whole new process to handle each request, which has a lot of overhead. |
| **Nginx** | Technically a reverse proxy and one of the most common web servers on the internet. A series of worker processes handle incoming requests, making it much more scalable. |
| **IIS** | Internet Information Services is Microsoft's web server. It has a long history of security vulnerabilities and should be avoided if possible. |

### Server Operating System
- **Linux or Unix-like OSes** make up over **60%** of all server OS.
- **Windows Server** makes up less than **40%**.
- The **top 100 supercomputers all use Linux or Unix**.

### Common Stacks
- **LAMP** — Linux, Apache, MySQL, PHP
- **MEAN** — MongoDB, Express.js, Angular.js, Node.js
- **LYME** — Linux, Yaws, Mnesia or CouchDB, Erlang

💡 **Why It Matters:** Stack choice locks in your language, database model, community, and scaling characteristics. Swapping a single component is easy because stacks are modular — but each combination has its own personality.

SECTION 11: Use Cases & Requirements
------------------------------------------------
### Step One: Identify Problems
Ask what core issues you are trying to solve:
- Why would someone want to use your website/solution?
- What problem does your website solve for people?
- Create a series of **problem statements**, e.g.:
  - "Buyers have no way of expressing how much they want to pay for an item"
  - "Sellers have difficulty determining the price to sell at"
  - "Non-technical people have no way of getting a website built"

### Step Two: Determine Use Cases
Convert problem statements into **use cases**. Use cases are made up of **actions** performed by **actors**:
- **Action** — a simple, distinct, and easily defined action performed by an actor.
- **Actor** — a **role** within the system, *not* an individual person.

### The Process
1. Identify the flow of events.
2. Extract distinct actions.
3. Group associated actions into a high-level **use case**.
4. Expand use cases into **extensions**.

**UML** stands for **Unified Modelling Language**. A UML **use case diagram** models the actors and use cases of a business (the lecture uses a restaurant business as an example).

### Use Case Documentation — Flow of Events
Describe each use case with a set of fields:

| Field | Purpose |
| --- | --- |
| **Name** | A short name for the use case |
| **Goal** | The main goal the use case tries to achieve |
| **Actors** | Actors who initiate and/or are involved |
| **Preconditions** | Conditions that must be met before the use case starts |
| **Main flow** | A full description of the use case |
| **Subflows** | Actions or use cases on which it depends |
| **Alternative flows** | Alternative action flows, e.g. from error scenarios |
| **Priority** | Importance of the use case to the system or the MVP |

📌 **Further reading:** A detailed breakdown is on Canvas — the *Monopoly Requirements Specification*, pages 11–19 (*UseCaseRequirements.pdf*).

🧠 **Memory Hook:** Use-case documentation fields: **N-G-A-P-M-S-A-P** — Name, Goal, Actors, Preconditions, Main flow, Subflows, Alternative flows, Priority.

SECTION 12: Diagramming Design
------------------------------------------------
Three diagram types describe a system before it is built.

### Sequence Diagrams
- Describe **how objects interact with each other and in what order**.
- Very useful for communicating how several systems interact, or for detailing how actors interact with system components in a **multi-step process**.
- The lecture's example: a computer asking a server for emails.

💡 **Why It Matters:** A sequence diagram is the clearest way to show an API contract — who calls whom, in what order, and what comes back.

### State Diagrams
- Also known as **state machine diagrams**; they describe the various **states** of system components.
- Essential for communicating how abstract concepts such as **tickets or user accounts** progress through the system.
- **States are defined, as are state transitions**, which constrain how objects are allowed to move between states.

Example shape of an order:
```
[Created] --pay--> [Paid] --ship--> [Shipped] --deliver--> [Delivered]
```
⚠️ **Common Trap:** Without explicit states and transitions, a system can end up doing something nonsensical like shipping an unpaid order.

### Wireframes
- Allow designers to gain a visual **"feel"** for the site **without focusing on graphical detail**.
- The idea is to create a **"cartoon" version** of the website that enables a preliminary website experience.
- Usually a series of images, but can sometimes include **clicking and linkage between images** in the form of a **storyboard**.

📌 **Info:** Wireframes capture structure and flow; save colour, typography, and polish for later.

SECTION 13: Documentation: The SRS
------------------------------------------------
The **Software Requirements Specification (SRS)** is one of the most important documents in a project:
- It details **exactly what the system does and does not do**.
- In essence, it is a **communication tool between project stakeholders and software designers**.
- It lets you declare the project **"finished"** and **mitigates scope creep**. It is the primary specification document and should capture all information about the project.
- **Diagrams must not introduce new information** not contained within the SRS. Diagrams provide additional context and clarification only.

### SRS: Introduction
Should encapsulate enough for a business executive to understand the project — without too much depth:
- **Purpose**
- **Definitions**
- **System Overview**
- **References**

### SRS: Overall Description
Discusses the project at a high level but still examines details — how it is used, how it works, the scope, dependencies, requirements, and constraints:
- **Product Perspective** — system interfaces, user interfaces, hardware/software/communication interfaces, memory constraints.
- **Design Constraints** — operations, site adaptation requirements.
- **Product functionality**
- **User characteristics**
- **Constraints, assumptions and dependencies**

### SRS: Specific Requirements
Gets down to the nitty-gritty with **highly granular requirements**. It should be easy to identify whether a system does or does not satisfy them:
- **External interface requirements**
- **Functional requirements**
- **Performance requirements**
- **Logical database requirements**
- **Software system attributes** — Reliability, Availability, Security, Maintainability, Portability

✅ **Exam Tip:** Specific requirements must be **testable**. Write "the system shall ..." statements you can verify, not vague adjectives.

SECTION 14: Task Management
------------------------------------------------
Building a website is hard: there are lots of tasks to complete, and teams need to ensure everyone knows what they are doing and that nobody is "stepping on each other's toes." The answer is task-management software.

### GitHub (course primary tool)
- The most popular **source control** (software configuration management) tool.
- Integrated with **task management** — tickets/issues/defects.
- **Code review/scan**; security and compliance.
- **Platform deployment**.

### JIRA
- Bug/issue tracking and tasks.
- Service tickets and timesheets.
- Extendible through a **marketplace/ecosystem**.

### Asana
- Tasks are visualised and categorised as **tiles**.
- Similar tool: **Trello**.

### Microsoft Project
- **Gantt chart**.
- Integration with Microsoft Office.
- Similar tool: **SmartSheets**.

💡 **Why It Matters:** The tool shapes the process. A lightweight board suits a small agile team; a heavyweight tool with workflows and timesheets suits an enterprise.

KEY TAKEAWAYS
================================================
1. **The web request is a fixed story** — Parse URL → Check cache → Identify network → DNS → TCP → HTTP → server processing → response → fetch resources → render.
2. **DHCP configures four things** — IP address, subnet mask, default gateway, and nameservers. If nothing loads, check these first.
3. **DNS runs on UDP port 53** and resolves recursively via A-records; **HTTP runs on TCP 80/443** with a SYN/SYN-ACK/ACK handshake.
4. **TCP is reliable and ordered; UDP is best-effort** — that is why DNS tolerates UDP but web pages need TCP.
5. **HTTP splits into header and body**; methods (GET, POST, HEAD, PUT, DELETE, OPTIONS) carry meaning about what the request does.
6. **Real architecture is layered** — edge (WAF/DDoS, CDN, load balancer) → app servers → database, with HTTPS terminated via TLS.
7. **Master/slave databases scale reads but introduce slave drift** — critical reads such as payments must hit the master.
8. **Responses are generated from templates** — `{{ }}` inserts variables, `{% %}` executes logic.
9. **Status codes drive client behaviour**: 2xx success, 3xx redirect, 4xx client error, 5xx server error. A 302 follows the Location header.
10. **The DOM is the browser's tree model of HTML**, manipulated by JavaScript; CSS and JS are fetched as additional requests.
11. **Pick web servers and stacks deliberately** — Nginx scales via workers, Apache spawns processes, IIS is best avoided; Linux dominates servers.
12. **Use cases translate problems into actors and actions**, documented with Name, Goal, Actors, Preconditions, Main flow, Subflows, Alternative flows, Priority.
13. **Sequence, state, and wireframe diagrams** communicate interaction order, valid lifecycle transitions, and structure — before code exists.
14. **The SRS is the contract** that says what the system does and does not do, prevents scope creep, and must not be contradicted by diagrams.
15. **Task management keeps teams uncollided** — GitHub for source control + issues, Jira for enterprise workflows, Asana for visual tiles, Microsoft Project for Gantt charts.

**Slave drift**: Delay between a master write and its visibility on replicas.
**Slave/Replica DB**: Read-only copy of the master, used to scale reads.
**SRS**: Software Requirements Specification — the definitive "what the system does and does not do" document.
**State diagram**: UML diagram describing states and allowed transitions of a component.
**Subflow**: An action or use case that another use case depends on.
**Subdomain**: The most specific part of a domain, e.g. `cusp`.
**Subnet mask**: Defines which IP addresses count as local.
**TCP**: Transport Control Protocol — layer 4, reliable, in-order, handshake-based.
**TCP flooding**: Attack pattern that abuses TCP connection handling.
**TLS**: Current encryption protocol securing HTTPS.
**UML**: Unified Modelling Language — notation for use case, sequence and state diagrams.
**UDP**: User Datagram Protocol — layer 4, best-effort datagrams, used by DNS on port 53.
**Use case**: A goal-oriented grouping of actions performed by actors.
**WebKit**: Rendering engine used by Apple Safari.
**Web framework**: A toolkit (e.g. Django, Flask) that removes the need to reinvent common web plumbing.
**Wireframe**: A low-fidelity "cartoon" layout of a page focused on structure, not graphics.

MNEMONICS & QUICK RECALL
================================================
**Client Request Steps**: **P-C-N-D-T-H-R** — Parse, Cache, Network, DNS, TCP, HTTP, Render.
**TCP Handshake**: **S-S-A** — SYN, SYN-ACK, ACK.
**DNS vs HTTP Transport**: **DNS = UDP/53 (fast, no handshake); HTTP = TCP/80 or 443 (reliable, ordered).**
**HTTP Method Recall**: **G-P-H-P-D-O** — GET, POST, HEAD, PUT, DELETE, OPTIONS.
**Status Code Families**: **1 info, 2 OK, 3 go elsewhere, 4 you broke it, 5 we broke it.**
**Use Case Doc Fields**: **N-G-A-P-M-S-A-P** — Name, Goal, Actors, Preconditions, Main flow, Subflows, Alternative flows, Priority.
**Rendering Engines**: **B-E-W-G** — Blink, EdgeHTML, WebKit, Gecko.
**Tech Stacks**: **LAMP** = Linux/Apache/MySQL/PHP; **MEAN** = Mongo/Express/Angular/Node; **LYME** = Linux/Yaws/Mnesia/CouchDB/Erlang.

WORKED EXAMPLES
================================================
### Example 1: Tracing a URL Request End to End
Scenario: a user enters `https://cusp.sydney.edu.au/students/view-unit-page/uos_id/101257`.
1. Browser parses the URL — protocol `https`, domain `cusp.sydney.edu.au`, path `/students/...`.
2. Browser checks its cache for recently stored assets.
3. OS reads DHCP config to learn its IP, subnet mask, gateway, and nameservers.
4. OS asks a nameserver on **UDP port 53** to resolve `cusp.sydney.edu.au`, returning an A-record IP.
5. OS opens a TCP connection to the server on **port 443** using the SYN → SYN-ACK → ACK handshake.
6. Browser sends the HTTP request; a load balancer receives it, parses the header and forwards it to an app server.
7. The app server runs back-end logic, queries the database, renders a template with `{{ }}` variables, and returns a response.
8. Browser parses the response status (e.g. 200), fetches CSS/JS/images, builds the DOM, and paints the page.

### Example 2: The Slave Drift Bug
1. A user posts a new comment — the write goes to the **master** database.
2. The same user (or another) reloads the page moments later.
3. The app reads from a **slave**, but replication has not propagated the new comment yet (slave drift).
4. The page shows no comment, so the user thinks it failed and posts again.
5. Replication catches up and both comments appear — a duplicate the user never intended. Lesson: route decision-critical reads (payments, "did my write succeed?") to the master.

### Example 3: Reading a Response — 200 vs 302
- A **200 OK** arrives with an HTML body — the browser renders that body and starts fetching its DOM resources.
- A **302 Found** arrives instead — the browser does not render a page; it immediately issues a new request to the URL in the **Location** header.

### Example 4: Wireframe vs Sequence Diagram
The same checkout feature can be looked at two ways. A **wireframe** shows what the cart and payment pages *look like* — boxes for the item list, price, and a "Pay" button. A **sequence diagram** shows *what happens when Pay is clicked* — the browser sends a POST, the app server calls the payment gateway, the gateway replies, and a confirmation is returned, in that exact order. Structure versus behaviour.

================================================
EXAM FOCUS
================================================
1. List the six client-side steps performed when a URL is entered. → Answer: Parse URL, check cache, identify network, resolve DNS, establish TCP connection, submit HTTP request.
2. What four settings does DHCP provide, and which should you check first when no website loads? → Answer: IP address, subnet mask, default gateway, nameservers. Check the network configuration first.
3. Explain how DNS resolves a domain name. → Answer: Check local host entries, identify nameservers (from DHCP/`/etc/resolv.conf`), send a UDP request to port 53, and recursively query parent nameservers until a matching A-record returns the IP.
4. Contrast TCP and UDP, with ports. → Answer: TCP is reliable and ordered, uses a handshake, and commonly runs SSH on port 22 and HTTP/HTTPS on 80/443. UDP is best-effort, sends datagrams without acknowledgement or retransmission, and runs DNS on port 53.
5. Describe the TCP three-way handshake. → Answer: Client sends SYN; server replies SYN-ACK; client sends ACK. The connection is then established.
6. What is the difference between an HTTP request header and body? → Answer: The header carries meta-data such as cookies and connection information; the body carries optional data (e.g. form data or file uploads) sent with the transmission.
7. Name and describe four HTTP methods. → Answer: GET retrieves (header only); POST submits data in the body; PUT replaces a resource; DELETE removes a resource. (Also HEAD = GET without body, OPTIONS = asks allowed methods.)
8. What are the three layers of a typical AWS-style web architecture? → Answer: The internet-facing edge (DDoS mitigation/WAF, CDN, load balancer with SSL offloading and port forwarding), the application servers (VMs, containers, or serverless), and the database layer (master/slave for high availability).
9. Why separate reads and writes across master and slave databases? → Answer: The master accepts both reads and writes and there is usually only one; slaves replicate and serve reads only, so many replicas can be added to parallelise reads.
10. What is slave drift and how do you manage it? → Answer: The delay between a write on the master and its propagation to slaves. Manage it by sending decision-critical reads (e.g. payments) to the master, accepting the trade-offs of other replication configurations.
11. How is a dynamic HTTP response generated? → Answer: The app server inserts data into a template — variables between `{{ }}` and logic between `{% %}` — forming a response with a header (status, content type, length) and body (usually HTML).
12. What does a 302 status code cause the browser to do? → Answer: Immediately follow the URL specified in the Location field of the response header.
13. Compare Apache, Nginx and IIS. → Answer: Apache spawns a process per request (simple, higher overhead); Nginx uses worker processes and scales well; IIS is Microsoft's server with a long history of security vulnerabilities and should be avoided if possible.
14. What is the SRS and why is it important? → Answer: The Software Requirements Specification details exactly what the system does and does not do, acts as the communication tool between stakeholders and designers, helps declare the project finished, and mitigates scope creep. Diagrams may clarify but must not add new requirements.
15. What eight fields document a use case? → Answer: Name, Goal, Actors, Preconditions, Main flow, Subflows, Alternative flows, Priority.
16. Distinguish sequence diagrams, state diagrams and wireframes. → Answer: Sequence diagrams show object interactions and their order; state diagrams show an object's states and allowed transitions; wireframes are low-fidelity "cartoon" layouts focused on structure, not graphics.
