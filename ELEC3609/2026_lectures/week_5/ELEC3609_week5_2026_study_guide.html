Lecture overview

This lecture covers the two ends of a web application: how the client and server exchange data, and how the backend is designed, modelled and built. The first half explains data formats (XML and JSON), the HTTP request/response protocol in detail, and the headers that carry real meaning — Content-Type, cookies, Referer and User-Agent. The second half turns to backend work: data modelling with entity-relationship diagrams (using the "TIL" platform as a running example), the Model-View-Controller and Model-View-Template patterns, and the development environment every backend developer needs — version control, Python, package managers, virtual environments and IDEs.

01

Client-Server Communication

Client-server communication needs both a format and a way to transmit and receive data.

General Mechanisms

Some general client-server communication mechanisms:

  • Sockets
  • Remote procedure calls
  • Pipes

MIME Types

MIME (Multipurpose Internet Mail Extensions) type determines the file format and format contents. MIME types are standardised by the IANA.

Common examples:

  • text/html
  • image/png
  • application/json
  • text/css

Human vs Machine

The lecture contrasts human-facing and machine-facing exchange: the same information can be shown to a person (a rendered page) or handed to a program (structured data). This distinction motivates the two data formats that follow.

💡

Why It Matters:

The MIME type is how a client knows how to interpret the bytes it receives. Send HTML where JSON was expected and nothing useful happens.
02

XML: A Schema Contract

Extensible Markup Language (XML) defines a set of rules for encoding documents. It is:

  • A language for describing the rules of other languages.
  • A way to define schemas for tag-based languages.

A schema is a contract for communication between client and server.

XML is also:

  • A markup language, not a programming language.
  • Human-readable.
  • Machine-readable.
  • Designed to be self-descriptive.
  • Designed to carry and transport data, not to display data.
📌

Info:

Because a schema is agreed in advance, both sides know which fields to expect — that is what makes XML a communication contract rather than just a file format.
03

XML Terminology & DTD

Core Terminology

  • Markup — elements that define the structure of the document. Usually enclosed by:
  • < and >
  • & and ;
  • Content — all the information between markup.
  • Tag — a type of markup that begins with < and ends with >, in three flavours:
  • start tag — <section>
  • end tag — </section>
  • empty-element tag — <img src="dog.jpg"/>
  • Attribute — markup on a start tag or empty-element tag that defines key-value pairs about that element:
  • <img src="dog.jpg" alt="woof"/>

XML Document Type

To define what types of fields are allowed in an XML document, and in what structure, a document type declaration (DOCTYPE) is provided.

  • The DOCTYPE identifies a document type definition (DTD), which defines the fields and their structure.

For the lecture's XML book document example, the DTD is:

<!ELEMENT book (title , chapter+)>
<!ELEMENT chapter (heading , paragraph*)>
<!ELEMENT heading (#PCDATA)>
<!ELEMENT paragraph (#PCDATA)>
<!ATTLIST book
  language CDATA #REQUIRED
  author CDATA #REQUIRED
>

Reading this DTD: a book contains one title followed by one or more chapters (+); a chapter contains one heading and zero or more paragraphs (*); heading and paragraph hold parsed character data (#PCDATA); and a book must have language and author attributes (#REQUIRED).

🧠

Memory Hook:

DOCTYPE declares, DTD defines — the declaration points at the definition that lists fields and structure.
04

JSON

JavaScript Object Notation (JSON) is an open-standard format for representing data online. As the name suggests, it is based on the representation of objects in JavaScript.

  • It is language-independent and supported by most programming languages.
  • It is typically used for:
  • API requests/responses
  • Serialization
  • Configuration files

Compared with XML, JSON is lighter-weight and maps naturally onto program objects, which is why it dominates modern APIs.

💡

Why It Matters:

JSON is the default payload of the modern web API — you will read and write it constantly on the backend.
05

HTTP Revisited & Status Codes

Hypertext Transfer Protocol (HTTP) is designed to allow communication between an HTTP client and HTTP server. It works as a request-response protocol: a client makes a request and the server responds, generally with a web page. A response is then rendered by a browser to display a web page.

Once you have an open TCP connection to the web server, you send the HTTP request through that connection.

HTTP Status Codes

The response can specify an HTTP status code which indicates what happened:

HTTP code categoryDefinitionExample
1xxInformational100: Continue; 101: Switching Protocols
2xxSuccess200: OK — the standard response
3xxRedirection301: Moved Permanently; 302: Found/Moved Temporarily (similar to 303 & 307); 304: Not Modified
4xxClient404: Not found
5xxServer502: Bad gateway
🧠

Memory Hook:

1 info, 2 OK, 3 go elsewhere, 4 you broke it, 5 we broke it.
06

HTTP Methods & Content-Type

HTTP Structure

A HTTP request or response consists of:

  • Header — contains metadata such as cookie and connection information.
  • Body — contains the data to be sent with the transmission (optional).

Types of Web Requests

MethodBehaviour
GETA simple request; header only
POSTA request containing data in the body, e.g. form data, file upload, etc.
HEADThe same as GET, except the server omits the body in the response (only sends the header)
PUTReplace a target resource on the server
PATCHPartially modify
DELETEDelete a target resource on the server
OPTIONSAsk the server which request types are allowed against a particular resource

HTTP Content Type

  • Generally, an HTTP request uses the Accept header to indicate to the server which data types it will accept in the response. A client can define multiple data types that it supports.
  • An HTTP response defines the Content-Type header, which determines what type of data is contained in the body of the response. This is an indication to the browser as to how it should interpret the response.
  • Content-Type applies to both request and response bodies.
⚠️

Common Trap:

Accept (what the client wants) and Content-Type (what the body actually is) point in opposite directions. Don't confuse them.
07

Cookies & the Login Flow

HTTP Cookies

  • A HTTP cookie is a small piece of data, set by a website, which is stored in the user's browser.
  • Browsers automatically include all the cookies set by a server with every HTTP request sent to that server.
  • Two HTTP headers control cookies on the web:
  • Requests: Cookie
  • Cookie: username=abc123; authToken=4f3e
  • Responses: Set-Cookie
  • Set-Cookie: username=abc123
  • Set-Cookie: authToken=4f3e

Cookies are often used for tracking users and authentication. A typical login flow:

  1. User visits website for first time — no cookie.
  2. User submits login form to the server with username + password — still no cookie.
  3. Server generates an authentication token (auth-tok) — the server responds with Set-Cookie: token=[auth-tok].
  4. User visits the website again — the client sends Cookie: token=[auth-tok].
  5. Server recognises (auth-tok) and knows the request came from that User.

The lecture also flags three cookie attributes worth knowing: HttpOnly, Secure, SameSite.

💡

Why It Matters:

Cookies are how stateless HTTP remembers who you are. The same mechanism that keeps you logged in is why cookie security attributes matter.
08

Referer, User-Agent & Origins

HTTP Referer

  • The HTTP Referer header is sent with requests made by a browser. It indicates to the server the previous page that the user was on.
  • Example:
  • I go to www.google.com and search for "elec3609".
  • I click the link to the www.elec3609.com website.
  • The browser's request to www.elec3609.com includes a Referer header containing our previous address: https://www.google.com/.

HTTP User-Agent

  • The HTTP User-Agent header tells the server what type of software the client is using.
  • Typically it includes information like:
  • Browser
  • Rendering Engine
  • Operating System

When Frontend and Backend Run on Different Origins/Ports

  • Two URLs have the same origin if the protocol, port (if specified), and host are the same for both.
  • The lecture works through an example such as http://store.company.com/dir/page.html to show which URLs match that origin and which do not.
📌

Info:

Origin matters because a browser treats requests between different origins more cautiously — this is the web's core security boundary.

Data Modelling & the TIL ERD

What Data Modelling Is

Data modelling is the process of defining and analysing data requirements of an information system.

The process of data modelling involves:

  1. Identifying the detailed system requirements
  2. Normalising the entities
  3. Writing the data model

We use UML to develop a formalised entity-relationship diagram (ERD), using Crow's foot notation.

The TIL Example Platform

The running example is TIL — a social "Today I learned" platform.

TIL rough requirements:

  • A user can sign up with a username and password.
  • Users can make posts, consisting of:
  • Subject
  • Content
  • Post date
  • Posts can be:
  • public (visible to all users) or private (visible only to the creator)
  • associated with zero, one or more tags
  • Tags are free-form text labels that are dynamically created when first used.
💡

Why It Matters:

The ERD is where business rules (public/private, many tags) become a concrete database structure. Get the diagram right and the database follows.
10

Models, Keys & Relationships

Models

  • A model describes the fields which hold information about a particular entity.
  • Each attribute of a model has a designated type, such as:
  • String
  • Numeric
  • Boolean
  • Date/Time
  • An entity is represented by a single table in a database.
  • Each table should have an id field, which uniquely identifies each row, as the primary key.
  • Each of the entities in an ERD can be considered a model.

Foreign Keys

  • Models rarely exist in isolation; they have relationships with other models.
  • A relationship to another model is expressed through a Foreign Key (FK).
  • Foreign keys specify a "one-to-many" relationship.
  • "one-to-many": A mother may have many children, but a child has only one mother.
  • TIL example: A Post can be associated with one User. Posts contain a foreign key to their associated User.

Many-to-Many Relationships

  • "many-to-many": An Author can write several Books, and a Book can be written by several Authors.
  • To achieve a many-to-many relationship, we typically use intermediate tables to express the relationship.
  • TIL example: A Post can be associated with many Tags, and a Tag can be applied to many Posts.
RelationshipHow it is storedTIL example
One-to-manyForeign key on the "many" sidePost → User
Many-to-manyIntermediate (join) tablePost ↔ Tag
🧠

Memory Hook:

One-to-many needs a foreign key; many-to-many needs an extra table in the middle.

MVC & MVT (Django)

Model-View-Controller Architecture

A common way to structure the code of a web application is using the model-view-controller (MVC) architecture. In this pattern, code functionality is separated into three responsibilities:

  • Model — handles the data.
  • View — renders data into views (usually HTML).
  • Controller — interprets requests and encapsulates business logic.

Model-View-Template Architecture

Django uses a closely related pattern with different names:

  • Model — similar to MVC; handles the data and logic part and maintains a connection with the database.
  • View — works differently than the View layer of MVC: here the view accepts the requests and sends out the response.
  • Template — the presentation layer, commonly coded in HTML or DTL (Django Template Language).
⚠️

Common Trap:

In Django, the responsibilities of MVC's Controller live in the View, and MVC's View is the Template. The names map across, but not one-to-one.

Django

Django is the concrete framework used to apply the MVT pattern to the TIL example and beyond.

Version Control with Git

What Version Control Solves

A version control system (VCS) helps to keep track of the changes to a file or files. It helps avoid a situation like this pile of file names:

  • Report_draft.doc
  • Report_draft_final.doc
  • Report_draft_finalv2.doc
  • Report_draft_final - Copy.doc
  • Report_fixed.doc
  • Report_SUBMITTED.doc

Other benefits:

  • Improved ability to collaborate
  • Compare changes made to a file over time
  • Revert to a previous version of a file

Common Version Control Software

  • Git — the industry standard, and what we will use in this course. Git integration is supported by GitHub and BitBucket, two leading online repository hosting providers.
  • SVN (Apache Subversion) — an older VCS that is fading in popularity.
  • Hg (Mercurial) — an alternative VCS written in Python.

Practise Git! Git is used extensively in this course and in your career; the sooner you master it, the easier your life will be. If you are unfamiliar, the lecture points to a Simple Git Guide, GitHub's interactive introduction, and the Git Book — Basics.

💡

Why It Matters:

Version control is the safety net for every other development activity — branches, review, and rollback all depend on it.

Python, Packages & Virtual Environments

Python

  • Python is the prescribed backend language for this course.
  • It is an interpreted high-level programming language.
  • The lecture points to tutorials (W3Schools, learnpython.org, and the unit's own INFO1110 and ELEC1005), the Python documentation, and an installation guide.

Package Managers

  • A package manager is software for managing dependencies — libraries or extensions that add functionality or features to the language.
  • Common package managers:
  • Python: pip
  • Node: NPM
  • PHP: Composer
  • Ruby: RubyGems

Python's pip

  • pip is the standard Python package manager, letting you easily install packages.
  • pip install django will fetch and install the Django package and its dependencies.

Conflicting Project Dependencies

  • Python only allows us to install one version of a package at a time.
  • This creates conflicts. Example requirements:
  • Awesome Website: simplejson == 3.16, django == 3.1
  • Better Website: simplejson <= 3.17, django >= 3.2
  • It is not possible to find a set of requirements that satisfies the desired versions — leading to workarounds such as symbolic links (symbolic links?) and venv.

Virtual Environments

  • To solve this, we use Python Virtual Environments.
  • They allow multiple, isolated installations of Python; each environment has its own dependencies without conflicting with others.
  • A virtual environment must be activated before it can be used.
  • Do not commit your virtual environment into your repository.

Virtual environments in Python 3:

  • The venv module has shipped since Python 3.3, so support is built-in.
  • Each venv has its own site-packages and Python executable, isolated from the system install.
  • Create one with:
Create venvpython3 -m venv myenvname
✅

Exam Tip:

Know the conflict story end to end: one version at a time → unsatisfiable requirements → isolated virtual environments, activated before use, never committed.

  • Syntax highlighting
  • Version control

Some commonly used IDEs:

Worked Examples & Scenarios

Example 1

A Login Cookie Flow

  1. The user visits the site for the first time — no cookie is sent.
  2. They submit the login form with username and password — still no cookie.
  3. The server verifies and generates an authentication token, responding Set-Cookie: token=[auth-tok].
  4. On the next visit the browser automatically sends Cookie: token=[auth-tok].
  5. The server recognises the token and knows the request came from that user.
Example 2

Mapping the TIL Platform to an ERD

  1. From the requirements, the entities are User, Post and Tag.
  2. Post → User is one-to-many (a Post has one User), so Post carries a foreign key to User.
  3. Post ↔ Tag is many-to-many (a Post has many Tags; a Tag applies to many Posts), so an intermediate table expresses it.
  4. Each table gets an id primary key; each attribute gets a type (Subject: String, Content: String, Post date: Date/Time, public/private: Boolean).
  5. tags are created dynamically on first use, so the data model must allow new Tag rows at runtime.
Example 3

Reading HTTP Headers on a Request

A browser navigates from a Google search result to www.elec3609.com:

  • Referer: https://www.google.com/ — tells the server the previous page.
  • User-Agent: identifies the browser, rendering engine and operating system.
  • Accept: lists the data types the browser will accept (it can list several).
  • Cookie: includes every cookie previously set by www.elec3609.com. The server answers with a response whose Content-Type tells the browser how to interpret the body.
Example 4

Resolving Conflicting Python Dependencies

  • Awesome Website wants simplejson == 3.16 and django == 3.1.
  • Better Website wants simplejson <= 3.17 and django >= 3.2.
  • Because Python allows only one version of a package at a time, no single set of installed versions satisfies both.
  • The fix: create isolated virtual environments — python3 -m venv myenvname — one per project, each with its own site-packages, activated before use and never committed.
Example 5

The Same URL, Different Origins

Using http://store.company.com/dir/page.html as the reference:

  • The origin is the combination of protocol (http), host (store.company.com) and port.
  • A URL with the same protocol and host is the same origin; change the protocol (e.g. to https) or the port, and it is a different origin. This is why a frontend and backend served from different ports are treated as separate origins by the browser.

AnswerPython only allows one version of a package at a time, so conflicting requirements between projects can be unsatisfiable. Virtual environments provide multiple isolated Python installations, each with its own dependencies, activated before use and never committed. The venv module has been built in since Python 3.3 and is created with python3 -m venv myenvname.
