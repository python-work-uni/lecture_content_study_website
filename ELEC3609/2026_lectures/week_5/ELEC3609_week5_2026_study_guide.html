The Client–Server Communication Problem

A client and a server can only exchange data if they agree on both a channel to send it through and a format to encode it in.

Any two programs that talk to each other face the same two-part question: how do we transmit the bytes, and how do we interpret them? A web browser and a web server are no different.

General client–server communication mechanisms

There are several long-established ways for one process to talk to another:

  • Sockets — a low-level, bidirectional connection between two endpoints; the raw foundation that most web traffic is built on.
  • Remote procedure calls (RPC) — the client calls a function that appears local, but actually executes on a remote machine.
  • Pipes — a one-way stream of bytes passed from one process to another.

Why format matters

Once you have a channel, both sides still need to agree on what the bytes mean. A stream of bytes is meaningless until you know whether it is HTML, an image, JSON, or a stylesheet.

💡
Why it matters: A message needs both a transport (socket, RPC, pipe) and a type. Get the transport right but the type wrong and the receiver will happily download your JSON and try to render it as a picture.
🤔
Pause & predict: if you open a raw TCP connection to a web server and send random bytes, what does the server need from your message before it can respond usefully? (Hint: think about what it must parse first.)

MIME Types: Labelling What's Being Sent

A MIME type is a short label that tells the receiver the exact format of the content, so it knows how to interpret it.

MIME stands for Multipurpose Internet Mail Extensions. A MIME type determines both the file format and the format of the contents. MIME types are standardised and registered by IANA (the Internet Assigned Numbers Authority), so the label text/html means the same thing on every machine in the world.

The type is written as type/subtype, for example text/html.

Common MIME types

MIME typeMeaning
text/htmlAn HTML web page
image/pngA PNG image
application/jsonA JSON data payload
text/cssA CSS stylesheet
🧠
Memory hook: The slash separates family from specific format: text/html = text family, HTML format; image/png = image family, PNG format.
ℹ️
Note: MIME types are not invented by the sender on the fly — they are registered standards. That is exactly why they are reliable enough to drive how a browser behaves.

XML: A Schema Language for Tag-Based Data

XML is a markup language that defines rules for encoding documents — and, crucially, a language for describing the rules of other languages.

Extensible Markup Language (XML) defines a set of rules for encoding documents. The word "extensible" is the key: XML lets you invent your own tags. It is a language for describing the rules of other languages, which means you can use it to define schemas for tag-based languages.

A schema is best understood as a contract for communication between client and server: if both sides agree on the schema, each knows exactly which fields will appear and in what structure.

What XML is (and is not)

XML is:

  • a markup language, not a programming language — it describes data, it does not compute;
  • human-readable;
  • machine-readable;
  • designed to be self-descriptive — the tags explain the data;
  • designed to carry and transport data, not to display it.
⚠️
Common trap: XML does not display anything. Presentation is someone else's job. If a question asks what XML is for, the answer is transporting and describing data.
🤔
Pause & predict: HTML and XML look similar — both use angle-bracket tags. What is the fundamental difference in their purpose?

XML Terminology and Document Types

XML has a precise vocabulary — markup, content, tag, attribute — and a document type definition that acts as the schema.

Core vocabulary

  • Markup — elements that define the structure of the document. Usually enclosed by < and > or & and ;.
  • Content — all the information between markup.
  • Tag — a type of markup beginning with < and ending with >. Tags come in three flavours:
  • start tag: <section>
  • end tag: </section>
  • empty-element tag: <img src="dog.jpg"/>
  • Attribute — markup on a start tag or empty-element tag that defines key–value pairs about that element, e.g. <img src="dog.jpg" alt="woof"/>.

Document Type Declaration and DTD

To define what types of fields are allowed in an XML document, and in what structure, a document type declaration (DOCTYPE) is provided. The DOCTYPE identifies a document type definition (DTD), which defines the fields and their structure.

For the XML book example, the DTD is:

<!ELEMENT book (title, chapter+)>
<!ELEMENT chapter (heading, paragraph*)>
<!ELEMENT heading (#PCDATA)>
<!ELEMENT paragraph (#PCDATA)>

<!ATTLIST book
  language CDATA #REQUIRED
  author   CDATA #REQUIRED
>

Reading the DTD symbols

  • title — the element must contain exactly one title.
  • chapter+ — one or more chapters (the + means "one or more").
  • paragraph* — zero or more paragraphs (the * means "zero or more").
  • #PCDATA — parsable character data, i.e. plain text content.
  • #REQUIRED on an attribute — the attribute must be supplied.
🧠
Memory hook: + = at least one, * = any number including zero. Think of + as "add more" and * as "anything".
✅
Exam tip: A DTD is a contract. If a document violates it, the document is invalid against that schema — that is the whole point of having one.

JSON: The Modern Data Interchange Format

JSON is an open-standard, language-independent format for representing data online, based on how objects are written in JavaScript.

JavaScript Object Notation (JSON) is an open-standard format for representing data online. As the name suggests, it is based on the representation of objects in JavaScript — but do not let that fool you.

The defining property: language independence

JSON is language-independent and supported by most programming languages. That is what makes it the default choice for data moving between systems written in different languages.

Where JSON is typically used

  • API requests/responses — the payload exchanged with web services.
  • Serialization — converting an in-memory object into a transferable/storable form.
  • Configuration files — settings written in a simple, structured format.

XML

  • Markup language with user-defined tags
  • Can define schemas (DTD) that act as a contract
  • Verbose but very explicit and self-descriptive
  • Good for document-like, structured interchange

JSON

  • Object-notation format, not a markup language
  • Language-independent, supported almost everywhere
  • Compact and easy to parse
  • Default for API requests/responses and config
🤔
Pause & predict: your frontend is written in JavaScript and your backend in Python. Why is a language-independent format like JSON more convenient than sending a Python object directly?

HTTP: The Request–Response Protocol

HTTP is a request–response protocol: the client makes a request and the server responds, generally with a web page.

Hypertext Transfer Protocol (HTTP) is designed to allow communication between an HTTP client and an HTTP server. It works as a request–response protocol: a client makes a request and the server responds, generally with a web page.

The two directions

  • HTTP request — the client sends a request to the server, e.g. a request to www.elec3609.com/index.html.
  • HTTP response — the server sends a response back; the browser renders that response to display a web page.

A concrete request

Once an open TCP connection to the web server exists, the client simply sends an HTTP request through that connection. A request for www.elec3609.com/index.html looks like:

GET /index.html HTTP/1.1
Host: www.elec3609.com
Accept: text/html

The first line names the method (GET), the path (/index.html) and the protocol version (HTTP/1.1). The following lines are headers.

A concrete response

The server replies with a status line, its own headers, and (optionally) a body:

HTTP/1.1 200 OK
Content-Type: text/html

<html>...</html>
💡
Why it matters: Every page load, every API call, every image on a website is one of these exchanges. Understanding the request/response shape lets you debug anything on the web.
TCP connection opens→client sends HTTP request→server processes→server sends HTTP response→browser renders the page

HTTP Structure, Methods and Status Codes

A message is a header plus an optional body, the method says what you want done, and the status code says how it went.

Anatomy of an HTTP message

A HTTP request or response consists of:

  • Header — contains meta-data such as cookie and connection information.
  • Body — contains the data to be sent with the transmission (optional).

The request methods

MethodWhat it does
GETA simple request, header only
POSTA request containing data in the body, e.g. form data, file upload
HEADSame as GET, except the server omits the body in the response (only sends the header)
PUTReplace a target resource on the server
PATCHPartially modify a resource
DELETEDelete a target resource on the server
OPTIONSAsk the server which request types are allowed against a particular resource

Status codes

The response can specify an HTTP status code, which indicates the outcome. Codes are grouped by their first digit:

CategoryDefinitionExample
1xxInformational100: Continue; 101: Switching Protocols
2xxSuccess200: OK — the standard response
3xxRedirection301: Moved Permanently; 302: Found/Moved Temporarily (similar to 303 & 307); 304: Not Modified
4xxClient404: Not found
5xxServer502: Bad gateway
🧠
Memory hook: the first digit tells you who is at fault or what happened: 2 = success, 3 = move along, 4 = you (client) messed up, 5 = they (server) messed up.
⚠️
Common trap: HEAD is not "GET without a request body" — it is GET with the response body omitted. The client still asks for the resource; the server just replies with headers only.
🤔
Pause & predict: you upload a profile photo through a form. Which method carries that data, and where does the data physically live in the message?

Content Negotiation, Referer and User-Agent

Headers let the two sides describe what they can accept, where the user came from, and what software is asking.

Content type negotiation

  • A request uses the Accept header to tell the server which data types it will accept in the response. A client can define multiple data types that it supports.
  • A response defines the Content-Type header, which determines what type of data is contained in the body of the response. This is an indication to the browser as to how it should interpret the response.
  • Content-Type applies to both request and response bodies.
🧠
Memory hook: Accept = "what I can take" (request); Content-Type = "what this actually is" (both directions, but especially response).

Referer

The Referer header is sent with requests made by a browser. It tells the server the previous page the user was on.

Example: you go to www.google.com, search for "elec3609", then click the link to www.elec3609.com. The browser's request to www.elec3609.com includes a Referer header containing the previous address:

Referer: https://www.google.com/

User-Agent

The User-Agent header tells the server what type of software the client is using. It typically includes:

  • Browser
  • Rendering Engine
  • Operating System
ℹ️
Note: The misspelling "Referer" (one r in the middle) is the official spelling in the HTTP specification — servers expect exactly that.
✅
Exam tip: Be able to say which header does what in one line: Accept (client capability), Content-Type (actual body format), Referer (previous page), User-Agent (client software).

Cookies and Session Authentication

A cookie is a small piece of data a website stores in the browser, and the browser automatically sends it back on every request — which is exactly what makes logins possible.

An HTTP cookie is a small piece of data, set by a website, which is stored in the user's browser. Browsers automatically include all the cookies set by a server with every HTTP request sent to that server.

The two controlling headers

  • Requests use the Cookie header:
Cookie: username=abc123; authToken=4f3e
  • Responses use the Set-Cookie header:
Set-Cookie: username=abc123
Set-Cookie: authToken=4f3e

Why cookies matter

Cookies are often used for tracking users and authentication. HTTP itself is stateless, so without cookies the server could not tell two requests apart as coming from the same person.

A typical login flow

  1. User visits the website for the first time — no cookie exists yet.
  2. User submits the login form to the server with username + password — still no cookie.
  3. Server generates an authentication token (auth-tok) and responds with Set-Cookie: token=[auth-tok].
  4. User visits the website again — the client sends Cookie: token=[auth-tok].
  5. Server recognises the auth-tok and knows the request came from that user.

Cookie security attributes

Three attributes control how a cookie may be used: HttpOnly, Secure and SameSite.

  • HttpOnly — the cookie cannot be read by client-side scripts.
  • Secure — the cookie is only sent over secure (HTTPS) connections.
  • SameSite — restricts the cookie from being sent on cross-site requests.
💡
Why it matters: The auth token in a cookie is the user's identity. If an attacker steals it, they become that user — which is why the security attributes exist.
⚠️
Common trap: Cookies are set by the server (via Set-Cookie) but stored and automatically re-sent by the browser. A cookie is not created by the client on a whim.
🤔
Pause & predict: after logging in, you close the tab and open the site again — you are still logged in. Which header carried your identity on that new request?

Same-Origin Policy: Frontend and Backend on Different Ports

Two URLs share an origin only if their protocol, host and port all match — change any one and they are different origins.

When a frontend and backend run separately, they often live on different ports. That matters because browsers reason about trust in terms of origin.

Two URLs have the same origin if the protocol, port (if specified) and host are the same for both.

Take the reference URL:

http://store.company.com/dir/page.html

Its origin is the combination http + store.company.com + port 80 (the default for HTTP). Change any component — say https instead of http, or a different port, or a different host — and the two URLs are different origins, even if they serve the same application.

💡
Why it matters: In development it is common to run the frontend on one port (e.g. a dev server) and the backend API on another. Because they are different origins, the browser treats requests between them as cross-origin, which affects how cookies and requests behave.
🧠
Memory hook: origin = scheme + host + port, like a three-part address. All three must match; the path does not count.

Data Modelling and the TIL Example

Data modelling is the disciplined process of defining and analysing the data requirements of a system before you build it.

Data modelling is the process of defining and analysing the data requirements of an information system. It is where you decide what things the system stores and how they relate, before writing any code.

The three-step process

  1. Identify the detailed system requirements.
  2. Normalise the entities.
  3. Write the data model.

We use UML to develop a formalised entity-relationship diagram (ERD), using Crow's foot notation.

The running example: TIL

The lecture's example website is a social "Today I Learned" platform — TIL. Its rough requirements are:

  • A user can sign up with a username and password.
  • Users can make posts, consisting of:
  • Subject
  • Content
  • Post date
  • Posts can be:
  • public (visible to all users) or private (visible only to the creator);
  • associated with zero, one or more tags.
  • Tags are free-form text labels that are dynamically created when first used.
ℹ️
Note: "Free-form and dynamically created" means you do not pre-define a fixed list of tags. A brand-new tag springs into existence the first time someone types it.
🤔
Pause & predict: from those requirements, which nouns would become entities in the ERD? (Think about what needs its own table.)

Models, Keys and Relationships

A model is the code representation of an entity, and relationships between models are expressed through foreign keys.

What a model is

A model describes the fields which hold information about a particular entity. Each attribute of a model has a designated type, such as:

  • String
  • Numeric
  • Boolean
  • Date/Time

An entity is represented by a single table in a database. Each table should have an id field which uniquely identifies each row — this is the primary key. Each entity in an ERD can be considered a model.

Foreign keys and one-to-many

Models rarely exist in isolation; they have relationships with other models. A relationship to another model is expressed through a foreign key (FK).

Foreign keys specify a "one-to-many" relationship. The classic illustration: a mother may have many children, but a child has only one mother.

TIL example: a Post can be associated with one User. Posts therefore contain a foreign key pointing to their associated User.

Many-to-many and intermediate tables

A "many-to-many" relationship is when both directions are plural: an Author can write several Books, and a Book can be written by several Authors.

To achieve a many-to-many relationship, we typically use an intermediate table to express the relationship.

TIL example: a Post can be associated with many Tags, and a Tag can be applied to many Posts. That is many-to-many, so it needs an intermediate (join) table.

🧠
Memory hook: one-to-many = a foreign key column on the "many" side. Many-to-many = a whole extra table in the middle.
⚠️
Common trap: You cannot model many-to-many with a single foreign key. If both sides can have many, you must add the intermediate table — no exceptions.
🤔
Pause & predict: the TIL spec says a post has "zero, one or more tags". Which relationship type is that, and what extra table do you need to build?

MVC vs MVT: Structuring Backend Code

Both patterns split an application into layers so that data, request handling and presentation do not get tangled together.

Model-View-Controller (MVC)

A common way to structure the code of a web application is the model-view-controller (MVC) architecture. In this pattern, code functionality is separated into three responsibilities:

  • Model — handles the data.
  • View — renders data into views (usually HTML).
  • Controller — interprets requests and encapsulates business logic.

Model-View-Template (MVT)

The MVT variant renames and shifts some responsibilities:

  • Model — similar to MVC, handles the data and logic part, and maintains a connection with the database.
  • View — works differently from the View layer of MVC. Here, the view accepts the requests and sends out the response (it behaves like MVC's controller).
  • Template — the presentation layer. It is commonly coded in HTML or DTL (Django Template Language).

MVC

  • Model: handles the data
  • View: renders data into views (usually HTML)
  • Controller: interprets requests, holds business logic
  • Controller sits in the middle of the request flow

MVT

  • Model: data + logic, connects to the database
  • View: accepts requests and sends responses
  • Template: presentation layer (HTML / DTL)
  • The "View" does the controller's job; "Template" does the view's job
⚠️
Common trap: MVC's View and MVT's View are not the same thing. In MVT, the View handles requests (controller-like) and the Template handles presentation (view-like). Do not confuse them.
ℹ️
Note: The framework used in this course is Django, which follows the MVT pattern with Django Template Language.

The Development Environment Toolchain

Professional backend work rests on four tools: version control, a language runtime, a package manager, and an editor that understands your code.

Version control

A version control system (VCS) helps keep track of the changes to a file or files. It saves you from the classic disaster:

Report_draft.doc
Report_draft_final.doc
Report_draft_finalv2.doc
Report_draft_final - Copy.doc
Report_fixed.doc
Report_SUBMITTED.doc

Other benefits:

  • Improved ability to collaborate
  • Compare changes made to a file over time
  • Revert to a previous version of a file

Common version control software:

  • Git — industry standard, and the tool used in this course. Git integration is supported by GitHub and BitBucket, two leading online repository hosting providers.
  • SVN (Apache Subversion) — an older VCS that is fading in popularity.
  • Hg (Mercurial) — an alternative VCS written in Python.
✅
Exam tip: Practise Git. It is used extensively in this course and in your career — the sooner you master it, the easier your life will be.

Python

Python is the prescribed backend language for this course. It is an interpreted high-level programming language.

Package managers

A package manager is software for managing dependencies — libraries or extensions that add functionality to a language. Common examples:

LanguagePackage manager
Pythonpip
NodeNPM
PHPComposer
RubyRubyGems

pip is the standard Python package manager. It installs Python packages easily:

pip install django

This fetches and installs the Django package and its dependencies.

The dependency conflict problem

Python only allows you to install one version of a package at a time. Consider two projects:

  • Awesome Website requirements: simplejson == 3.16, django == 3.1
  • Better Website requirements: simplejson <= 3.17, django >= 3.2

It is not possible to find a single set of installed versions that satisfies both. Symbolic links do not solve it — virtual environments do.

Virtual environments

Python virtual environments allow multiple, isolated installations of Python. Each environment can have its own dependencies without conflicting with the others.

  • A virtual environment must be activated before it can be used.
  • Do not commit your virtual environment into your repository.
  • The venv module shipped in Python 3.3, so support is built in.
  • Each venv has its own site-packages and its own Python executable, isolated from the system install.

Create one with:

python3 -m venv myenvname

Integrated Development Environments

An Integrated Development Environment (IDE) makes writing code easier by combining a text editor with extra features:

  • Debugger
  • Syntax highlighting
  • Version control
  • Refactoring
  • Search

Commonly used IDEs: Visual Studio Code, PyCharm, Eclipse.

💡
Why it matters: Without an isolated environment, one project's upgrade silently breaks another. The venv is what makes "works on my machine" reproducible.
⚠️
Common trap: A venv that is never activated does nothing — pip install will go to your global Python instead. Also never commit the venv folder; it is huge and machine-specific.
🤔
Pause & predict: two projects need incompatible versions of the same library. What single command creates the isolation that fixes this?

Practice Questions

Answer, reveal, then tick “Mastered”. Your progress is saved.
Q1

What two things must a client and server agree on before exchanging data, name three general communication mechanisms, and define a MIME type with four examples.

Answer: They must agree on a way to transmit/receive data and on a format for that data. General mechanisms include sockets, remote procedure calls (RPC) and pipes. A MIME type (Multipurpose Internet Mail Extensions) determines the file format and the format of the contents; MIME types are registered by IANA. Examples: text/html, image/png, application/json and text/css.
Q2

List the properties that describe what XML is and is not, then define markup, content, tag and attribute.

Answer: XML is a markup language (not a programming language), human-readable, machine-readable, designed to be self-descriptive, and designed to carry and transport data rather than display it. Markup defines document structure, usually enclosed by < > or & ;. Content is all information between markup. A tag is markup starting with < and ending with > (start, end or empty-element). An attribute is markup on a start or empty-element tag defining key-value pairs.
Q3

What is the relationship between DOCTYPE and DTD, and in <!ELEMENT chapter (heading, paragraph)> what do and + mean and what does #REQUIRED mean?

Answer: A document type declaration (DOCTYPE) is provided to define what field types are allowed and in what structure; it identifies a document type definition (DTD), which defines the fields and their structure. * means zero or more (paragraph may appear any number of times, including zero). + means one or more. #REQUIRED means the attribute must be supplied.
Q4

What is JSON, what is its key property, and name three typical uses?

Answer: JSON (JavaScript Object Notation) is an open-standard format for representing data online, based on JavaScript object representation. Its key property is being language-independent and supported by most programming languages. Typical uses: API requests/responses, serialization, and configuration files.
Q5

Distinguish the Accept, Content-Type, Referer and User-Agent headers.

Answer: Accept (request) tells the server which data types the client will accept in the response; multiple types may be listed. Content-Type (response, and request bodies) declares what type of data the body contains so the browser knows how to interpret it. Referer indicates the previous page the user was on (e.g. https://www.google.com/ after a Google search). User-Agent tells the server the client's browser, rendering engine and operating system.
Q6

Describe each of the seven HTTP request methods and say what distinguishes HEAD from GET.

Answer: GET: simple request, headers only. POST: request with data in the body (form data, file upload). HEAD: same as GET except the server omits the body in the response. PUT: replace a target resource. PATCH: partially modify a resource. DELETE: delete a target resource. OPTIONS: ask the server which request types are allowed for a resource. HEAD differs from GET only in that the response carries no body.
Q7

A response returns 301, 404 and 502. Categorise each and explain the 1xx-5xx category meanings.

Answer: 301 is 3xx Redirection (Moved Permanently). 404 is 4xx Client (Not found — the client requested something that doesn't exist). 502 is 5xx Server (Bad gateway — the server side failed). Categories: 1xx informational, 2xx success, 3xx redirection, 4xx client error, 5xx server error.
Q8

Explain what a cookie is and how the Cookie and Set-Cookie headers differ.

Answer: A cookie is a small piece of data set by a website and stored in the user's browser; browsers automatically include cookies set by a server with every request to that server. Set-Cookie is a response header the server uses to set a cookie (e.g. Set-Cookie: username=abc123). Cookie is a request header the client sends back (e.g. Cookie: username=abc123; authToken=4f3e).
Q9

Walk through the cookie login flow, and explain the HttpOnly, Secure and SameSite attributes.

Answer: 1) User visits for the first time — no cookie. 2) User submits the login form with username + password — still no cookie. 3) Server generates an authentication token (auth-tok) and responds with Set-Cookie: token=[auth-tok]. 4) User visits again — the client sends Cookie: token=[auth-tok]. 5) The server recognises the token and knows the request came from that user. HttpOnly prevents client-side scripts from reading the cookie; Secure ensures it is only sent over HTTPS; SameSite restricts it from being sent on cross-site requests.
Q10

When do two URLs have the same origin, and why does this matter for a frontend and backend on different ports?

Answer: Two URLs have the same origin if the protocol, port (if specified) and host are the same for both. If a frontend and backend run on different ports, they are different origins, so the browser treats requests between them as cross-origin, affecting how requests and cookies behave.
Q11

Define data modelling, list its three steps, name the diagram notation, and list the TIL platform's rough requirements.

Answer: Data modelling is the process of defining and analysing the data requirements of an information system. Steps: 1) identify detailed system requirements, 2) normalise the entities, 3) write the data model. The ERD uses UML with Crow's foot notation. TIL: a user signs up with username and password; users make posts of subject, content and post date; posts are public or private; posts can have zero, one or more tags; tags are free-form text labels dynamically created when first used.
Q12

What is a model and a primary key, and explain one-to-many and many-to-many relationships using the TIL example.

Answer: A model describes the fields holding information about a particular entity, and each entity is represented by a single table in a database. Each table should have an id field uniquely identifying each row — the primary key. One-to-many is expressed with a foreign key: a mother may have many children but a child has only one mother; in TIL a Post is associated with one User, so posts contain a foreign key to their User. Many-to-many is when both directions are plural — a Post can have many Tags and a Tag can apply to many Posts — and is implemented with an intermediate table.
Q13

Compare MVC and MVT, naming each layer's responsibility.

Answer: MVC: Model handles the data; View renders data into views (usually HTML); Controller interprets requests and encapsulates business logic. MVT: Model handles data and logic and maintains a connection with the database; View accepts requests and sends responses (controller-like); Template is the presentation layer, commonly coded in HTML or DTL (Django Template Language).
Q14

What problem do virtual environments solve and how do you create one? Give one package manager per language and say how to install Django.

Answer: Python allows only one version of a package at a time, so conflicting project dependencies cannot be satisfied simultaneously. Virtual environments allow multiple isolated Python installations, each with its own dependencies, own site-packages and own Python executable. Create one with: python3 -m venv myenvname. It must be activated before use and should not be committed to the repository. Package managers: Python pip, Node NPM, PHP Composer, Ruby RubyGems. Install Django with: pip install django (fetches Django and its dependencies).
