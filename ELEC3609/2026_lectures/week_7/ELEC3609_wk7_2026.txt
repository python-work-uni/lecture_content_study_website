### **Getting Hacked: What?** 

##### **What does it mean to get hacked?** 

##### Servers: 

- The most obvious way to attack a website is to compromise the server(s) running the website. This is done through manipulation of the server-side code: 

   - SQL Injection 

   - Remote Code Execution 

   - Local/Remote File Inclusion 

##### Users: 

- A less obvious method of hacking is to attack the users, whilst they use the web server for its intended purpose. This is done through altering or intercepting data on a user’s computer: 

   - Cross-Site Scripting (XSS) 

   - Cross-Site Request Forgery (CSRF)

### **Focus on the Important Risks** 

**1. Severe:** Must be managed by senior management with a detailed plan. 

**2. High:** Detailed research and management required at senior levels. **3. Major:** Senior management attention is needed. 

**4. Significant:** Management responsibility must be specified. 

**5. Moderate:** Managed by specific monitoring or response procedures.

**7. Trivial:** Unlikely to need specific application of resources.

- **Likelihood** of the component being exploited. 

- **Damage** if exploited. 

- **Mitigation cost** to prevent exploitation.

### **SQL Injection** 

- SQL Injection arises from failing to properly sanitize user input before inserting it into a database string. 

- If the input can be used to modify an SQL query, then it is possible to modify it to do any database query. 

- Very common. 

- Can lead to complete compromise. 

- Many automated tools to detect (also many to automatically exploit). 

- Using an ORM or database library can defend against this.

### **Cross Site Scripting (XSS)** 

- For example, we had a HTML template like this to insert the user’s name into the heading of the page: 

```
<H1>Hello {% user.name %}</H1>
```

- This works fine for regular users, but what if we had a user whose name was: 

```
<script>alert("LOL");</script>
```

- In this case, loading the page will render the following HTML snippet, which will display an alert when this user loads the page: `<H1>Hello <script>alert("LOL");</script></H1>` 

- In this example, an alert is only shown to this particular user, but if this snippet were running on a public page (e.g., a list of users, or a blog post showing an author’s name) and was more malicious than a simple `alert` , the effects can be devastating.

### **Preventing XSS** 

How can we stop XSS? 

- One approach is to just strip all `<script>` tags from user input. 

   - It’s not immediately obvious why, but this is WRONG. `<s<script>cript>…</script>` 

   - would be turned into: 

```
<script>…</script>
```

- There are many, many ways to perform XSS attacks, and it’s impossible to recognise them all. 

   - For example, you can use an <img> tag: `<img src=“img.jpg” onerror=“alert(1)” />`

### **Preventing XSS** 

The best way to stop XSS is to do so via HTML escaping with our templating library. 

1.User input is stored in the database as-is, even it if includes HTML tags. 2.Upon displaying any data, it is HTML escaped by default. 

In the case from before, we had a user with the name: 

```

```

When HTML escaped, the output will be: 

```

```


This will print the HTML to _the screen_ – it will not be interpreted as actual HTML and rendered by the browser.

### **Cross Site Request Forgery (CSRF)** 

- Cross Site Request Forgery (CSRF) is a type of exploit against a website. 

- CSRF exploits arise when only the browser is authenticated (e.g., via a cookie), but the user’s request is not properly authenticated. 



The University of Sydney 

Page 28 

### **Preventing CSRF** 

Typically, we prevent CSRF by including a CSRF token when making requests which change data (e.g. POST, but not GET). When submitting requests to the server, the website can use JavaScript to also submit a special token from a cookie as one of the POST request variables, which only it has access to. 

This CSRF token typically appears somewhere in the HTML or in the cookies. 

Checking for the presence of a CSRF token in the cookie is not enough 

- it must be included as a variable to authenticate the request.

### **Authentication** 

Logging in is pretty straightforward on most websites: 

1. User sees login form and provides username and password. 

2. Server hashes the password and compares the computed hash with its stored password hash for the user. 

3. If the hashes match, the user has been authenticated and the server responds with an authentication cookie/token. 

The University of Sydney 

Page 31 

### **Password Storage** 

- If we stored passwords in our database as regular plaintext, an attacker who gains access to the database could authenticate as anyone. 

- As such, we store password hashes, so that if the database is breached, an attacker would not be able to use the information as-is. 

- To use the hashes, an attacker would need to reverse the hash to get the original passwords. 

The University of Sydney 

Page 32 

### **Hash Functions: Overview** 

- Hash functions are functions that map an input string to an output hash. 

- Desirable properties: 

- One way 

   - Given a hash, the original 

   - string cannot be computed. 

- Unpredictable – Cannot choose an input string to get a particular output hash. 

- Non-collision – Cannot find two input strings that map to the same output hash. 



The University of Sydney 

Page 33 

### **Cracking Passwords** 

- If an attacker wanted to reverse some hashes obtained from our DB to discover the original passwords, they could theoretically compute the hash of all possible passwords and match it up to their hash list. 

- This is possible because passwords are hard to make up and remember – most human-generated passwords can be found in a dictionary, either as a word or a concatenation of multiple words. 

- There is a major extension to this attack: rainbow tables. These contain lists of commonly used passwords (e.g., password1, ilikecats123, etc.) and are used to supplement dictionary attacks with additional words. 

- These attacks won’t work on every user (e.g., if the password is unique gibberish), but it’s been shown to work on large portions of leaked password hash sets. 

The University of Sydney 

Page 34 

### **Salting Passwords** 

To mitigate the effects of a **dictionary attack** without forcing stricter password requirements on users, passwords can instead be salted. 

Before being fed into the hash function, the raw password is concatenated with another string, which is known as the salt. 

- Salts are usually stored in plaintext in the database, right next to the password hashes. 

   - For further security, a different salt can be used for each user. 

- This thwarts dictionary attacks that rely on massive precomputation. 

- Once the salt is known however, brute-force dictionary attacks may be run. 

The University of Sydney

### **Authentication Cookies** 

- After a user has provided their password and been authenticated, they are provided with an auth token, which is provided in the cookies. 

- There are two main ways to manage this token: 

   - **Statefully** : store valid tokens & expiry in a database (e.g., Redis). 

   - **Statelessly** : calculate valid tokens using a hash of details and a secret. 

- Storing valid tokens in a database is obvious, but calculated tokens are less so. 

Page 36 

The University of Sydney 

### **Calculated Authentication Tokens** 

- Calculated authentication tokens allow the server to check if a user has been authenticated without storing tokens. 

- This is done by calculating a value which can be re-computed after every request, then checking if the provided token matches the calculated one. 



- While this adds computational overhead (since the token must be re-computed for every request), it reduces the memory overhead. 

The University of Sydney 

Page 37 

### **Calculated Authentication Tokens** 

```
def build_auth_token(self):
max_validity_duration_seconds = 21600 # 6 hours
timestamp = int(
datetime.datetime.utcnow().strftime("%s")
)
validity_timestamp = int(
timestamp - (timestamp %
max_validity_duration_seconds)
)
auth_token = hashlib.sha512(
self.secret_key[0] +
str(validity_timestamp) +
str(self.id) +
self.secret_key[1]
)
return auth_token.hexdigest()
```

```
def validate_auth_token(self, token):
return self.build_auth_token() == token;
```

### **Storing/Sending Cookies** 

Some tips for storing and managing cookies: 

- Always access the website over HTTPS. 

   - This prevents network <u>MITM attacks from sniffing auth cookies.</u> 

- Set the cookie’s <u>secure attribute.</u> 

   - This ensures the cookie will only be sent if connecting via HTTPS. 

- Set the cookie’s <u>HttpOnly attribute.</u> 

   - This ensures that scripts on the page cannot read the cookie (e.g., via XSS), and that cookies are only sent with HTTP(S) requests.

### **Local/Remote File Inclusion** 

- <u>Local/Remote File Inclusion (file:///) is a vulnerability where the web application is manipulated into loading an unexpected file. This can be used</u> to obtain the contents of a file or dynamically change the behaviour of the program. 

```
$page = $_GET[“page"];
include($page);
```

- Simply visiting the following site: 

   - <u>http://example.com/index.php?page=/etc/passwd</u> 

- will output the `/etc/passwd` file if not configured correctly. 

- While this is a very simple example and looks quite obvious, this is a very common bug. 

- **Local** = files already on the server, as above. 

- **Remote** = get the server to load a file from a remote location. 

- **Don’t allow user parameters to govern what files can be included.** 

The University of Sydney 

Page 40 

### **Remote Code Execution** 

- <u>Remote/Arbitrary Code Execution refers to a vulnerability</u> where an attack can provide some code which will be run on the remote server. 

- This is considered the worst type of exploit, as it quickly leads to full server compromise. 

- There are a few ways this can happen, but the most common culprits are: 

- The `eval()` function (or equivalent). 

- PHP `unserialize()` . 

- Regular Expressions with the ‘ `e` ’ flag.

### **Distributed Denial of Service** 

- Denial of Service attacks prevent anyone from accessing a particular website. 

- Typically, this is performed by flooding the website with a very large amount of traffic so that legitimate user requests cannot be processed. 

- Defence is very difficult – detection mechanisms can introduce a large amount of overhead for legitimate requests. The only real way to defend your system is to ‘absorb’ the attack traffic.
