How to take someone else's finished software — a CMS, a forum, a database, a container image — and run it safely on your own infrastructure. Pre-packaged Software: The Trade You Are Making

Pre-packaged software gets you running fast — but you are adopting someone else's code, and all of its baggage, into your system.

Pre-packaged web software is ready-made application software, commonly used to get something up and running quickly. Instead of writing a blog, a forum or a wiki from scratch, you install a project that already does it.

Common examples

📝 WordPress

A content management system (CMS) — the software behind a large share of the web's blogs and business sites.

💬 vBulletin

Internet forum software — discussion boards with threads, user accounts and moderation.

📚 MediaWiki

An open-source wiki platform — collaborative, versioned pages (the engine behind Wikipedia).

🛠️ Phabricator

A project management tool — task tracking, code review and planning in one package.

💡
Why it matters: Using someone else's software is a head start, not a free pass. The moment you run it in production, its security, configuration and updates become your responsibility.
🤔

The Three Components Every Package Has

Like any website, a package is application code plus configuration plus a database — and the package only supplies the first part.

Just like any other website, pre-packaged software typically consists of three parts. The package provides one of them; you must handle the other two.

  1. Application code — the program itself. This is the part the package gives you.
  2. Configuration files — the settings that tell the application how to behave in your environment.
  3. A database — where the application stores its data.
⚠️
Common trap: The prepacked software provides the application code, but it is up to the deployer to configure the application and the infrastructure. Downloading is the easy 10%; configuring is the real work.
Memcached — an in-memory caching service often added alongside a package to speed up dynamic sites by keeping frequently used data in RAM.
🤔

Supply-Chain Security: You Inherit the Dependencies

When you deploy a package, you inherit not just its code but its entire dependency tree — and every weak link in it becomes your weak link.

The first security question to ask about any package is not about the package itself, but about everything it drags in with it.

The core risk

You are inheriting not just the main application code, but also all of its dependencies. Each layer is code someone else wrote and someone else could attack.

Dependency management

  • Libraries & frameworks — the supporting code the app is built on.
  • Plugins / extensions — optional add-ons, often from third parties.
  • Container images — pre-built images you pull rather than build.
  • System packages — OS-level packages installed inside the host or image.

Supply-chain risks to watch

⛓️ Supply-chain attacks

An attacker compromises a dependency or plugin upstream so that everyone who installs it inherits the malware.

🕰️ Outdated dependencies

Old libraries carry known, published vulnerabilities that attackers can look up and exploit directly.

🧩 Plugin ecosystem

Plugins are frequently the weakest link: written by many authors, with varying quality and update habits.

⚠️
Common trap: Trust in public registries is not the same as trust in a specific package. A Docker Hub image or a plugin can be popular, abandoned, or malicious — popularity is not a security guarantee.

Auditing the Application Code

It can be dangerous to blindly run other people's code — so before you deploy, investigate what you are actually running.

It can be dangerous to blindly run other people's code, especially when it is old and complex. Auditing the application code is the first of three audits you should perform.

Four questions to ask

  • What is it written in?
  • Is the codebase mature?
  • How active is development on the project?
  • Does the software have a history of security vulnerabilities?

Practical checks

  • Identify other users — if large companies have adopted the software, it is likely they reviewed it before deciding.
  • Identify potential support avenues — is support available from the supplier? Do they provide direct support, and at what cost?
  • Check the frequency of commits — for open-source software, look at the code repository. More frequent and recent commits mean more active development.
  • Scan for vulnerabilities — use a static source-code vulnerability scanner appropriate to the language and tooling.
  • Search for known vulnerabilities — check disclosure sites such as cvedetails.com.

Tools to know

ToolWhat it does
npm auditAudits Node/JavaScript dependencies for known vulnerabilities.
pip-auditAudits Python package dependencies.
OWASP Dependency-CheckScans project dependencies against known-vulnerability databases.
Snyk Vulnerability DBA vulnerability database and scanner for dependencies.
✅
Do this: Treat a dependency scan as a pre-deployment checklist item, not an optional extra. Run it before you expose anything, and re-run it when dependencies change.

Auditing Configuration and the Database

Packages often ship with insecure defaults and more features than you need; the database deserves the same scrutiny.

Configuration

While it is good practice to release software that is secure-by-default, many software packages come with insecure configuration. It is critical to review all configuration options before deployment.

Questions to ask:

  • What configuration options are available?
  • Are the default values for these options secure?
  • Are there any features enabled that you are not using?
  • Can you disable these features?

How to audit configuration:

  • Identify all configuration options — read the documentation and view example configurations.
  • Search the internet for example configurations — they are readily available, but do not blindly trust them; evaluate them.
  • Identify all features and components — general-purpose software often has functionality beyond what you need.
  • Disable unwanted features — this reduces complexity and the surface area for possible attacks.

Database

It is usually the responsibility of the deployer to configure the database required by pre-packaged software. Care must be taken.

Questions to ask:

  • Does the package need its own database, or can it share one?
  • What database permissions are required?
  • If the application is vulnerable, will a database compromise lead to system compromise?

How to audit the database:

  • Identify database requirements — does the software create a single database for all of its tables, or multiple databases?
  • Evaluate database permissions — give the minimum set of permissions. Start minimal and extend only when necessary.
  • Evaluate the scope of a DB compromise — an SQL injection could let an attacker run arbitrary commands on the database.
🧠
Memory hook: The golden rule for both configuration and database is least privilege — enable only what you use, and grant only the permissions you need.
💡
Why it matters: Disabling unused features does not just simplify the app; it removes entire categories of attack. A feature that is off cannot be exploited.

Deployment and the Reverse Proxy

Never expose a package's own HTTP interface directly to the internet — put a layer you control in front of it.

Software packages can come with their own web/HTTP interface. We do not want that interface directly exposed to the internet. Instead, we want our own layer that we control sitting in between.

A reverse proxy (Nginx, Apache) or a load balancer can give us finer control over which requests can reach the application. This is especially important if the application exposes an admin or control interface without authentication.

Internet→Reverse proxy / load balancer→Application→Database

What a reverse proxy buys you

📈 Scaling

Use the reverse proxy as a load balancer to increase concurrent connections. Run many instances of the app and scale horizontally. The database is still a bottleneck for shared state.

🔐 Request authentication

If the app is an internal service, perform basic authentication at the proxy so anonymous web users cannot reach it at all.

🛡️ Web Application Firewall

A WAF can inspect incoming requests and reject those that look like attack vectors.

💡
Why it matters: A malicious user cannot reach the application at all if the reverse proxy blocks them first. The proxy is your choke point — the single place where you can observe and filter traffic.
🤔
Pause & predict: your package ships an admin panel with no login. Which single piece of infrastructure most improves your security posture, and why?

HTTP Basic Auth and the Web Application Firewall

Basic auth is a simple challenge–response gate; a WAF is a rule engine that filters out malicious requests before they arrive.

HTTP Basic Authentication

HTTP Basic Authentication requires HTTP requests to include a username and password to be considered authorised. If a request arrives without valid credentials, the server responds with 401 Unauthorized.

The mechanics happen in two steps:

  1. Server side: the server responds to the initial request with a 401 Unauthorized response containing the header WWW-Authenticate: Basic realm="User Visible Realm".
  2. Client side: the browser prompts the user for a username and password, combines them with a colon (Aladdin:OpenSesame), encodes that string in base64, and resends the request with an Authorization header.
Authorization: Basic QWxhZGRpbjpPcGVuU2VzYW1l
⚠️
Common trap: Basic auth is encoding, not encryption. Base64 is trivially reversible, so credentials are only safe over HTTPS.

Web Application Firewall (WAF)

A WAF applies rules and/or filters to incoming HTTP requests. It tries to identify requests that appear to contain exploitation code and rejects them.

  • All requests should go through the WAF, so it usually sits at the edge / web layer in front of your application.
  • A WAF is only as good as the rules it evaluates — keep the rule/filter sets up to date.
ℹ️
Note: Reverse proxy authentication and WAF filtering are complementary. Basic auth decides who may enter; the WAF decides what requests are safe to pass through.

Virtual Machines vs Linux Containers

A virtual machine virtualises hardware and needs a whole guest OS; a container virtualises the operating system and needs only your app.

Before Docker, the standard way to isolate software was the virtual machine. Understanding the difference explains why containers won.

Virtual machine

  • A hypervisor enables execution of virtual machines inside a host OS.
  • Each VM installs a full guest operating system.
  • Heavier: more disk, more memory, slower to start.

Linux container

  • Removes the need for a guest OS.
  • Allows multiple isolated Linux systems on a single host OS.
  • Lighter and faster to start; shares the host kernel.

Docker

Docker is an open-source project that automates the deployment of applications inside Linux containers. It makes it easy to deploy packaged applications, including any necessary dependencies.

Multiple services/containers can be combined using the tool Docker Compose.

🧠
Memory hook: A VM virtualises hardware (so it needs an OS). A container virtualises the operating system (so it needs only your app). Fewer layers means less weight.
🤔
Pause & predict: if ten containers share one host kernel, what is the main resource saving compared with ten virtual machines?

Docker Images, Volumes and Networking

A container is created from an image; it stores nothing permanently, so data lives in volumes, and containers talk to each other over controlled links.

Containers and images

Instead of running virtual machines, Docker lets us run containers. A Docker container can be thought of as a minimalistic Linux host: you can install any application you like, and the container itself can be almost any Linux distribution.

A container is created from a Docker image. The image describes the base operating system and any modifications that need to be made, such as dependencies.

A sample image that uses Ubuntu 18.04, runs make, copies the app and sets the entry point:

FROM ubuntu:18.04
RUN make /app
COPY . /app
CMD python /app/app.py

Volumes: solving statelessness

Containers are good for running applications but not good for storing data — they do not maintain state. We mount volumes into containers to allow persistence.

  • For a database container such as MySQL, the data directory should be stored in an attached volume.
  • The mounted volume is a folder on the host machine, outside the container.
  • We can now destroy the container without losing data.

Networking

Docker containers can be linked to each other, and nominated ports can be forwarded from the host OS to a container.

  • Example: one container for a WordPress application and a separate container for its MySQL database.
  • By linking them, WordPress can talk to MySQL directly. No other container or system can reach the database unless explicitly allowed via Docker.
  • This segmentation significantly improves security and ease of deployment.
⚠️
Common trap: Data written inside a container is lost when the container is destroyed. If it needs to survive, it belongs in a volume, not in the container's filesystem.
🤔

Docker Hub and Container Orchestration

You can start from pre-built images instead of writing your own — but at scale you need an orchestrator to manage the fleet.

Docker Hub

Why re-create the wheel? The Docker project runs a service called Docker Hub, which contains pre-built Docker images that can be used as a starting point for building services.

  • Many large software companies and projects have released Docker Hub images for their software.
  • Security is a factor to consider here — a pre-built image is still third-party code.

Container orchestration

When running containers in production, it is common to have fleets of 10s to 1000s of containers. Managing them by hand does not scale, so we use orchestration:

☸️ Kubernetes (GKE)

Google offers the Kubernetes Engine (GKE), an open-source cluster management system for deploying and managing containerised applications on Google Cloud. Kubernetes can also run outside Google Cloud.

🟧 AWS ECS

AWS offers the Elastic Container Service (ECS) for deploying Linux containers within the AWS ecosystem.

ℹ️
Note: Orchestration answers "how do I run and manage many containers?" — scheduling, scaling, health checks and networking across a fleet.

Monitoring: What to Watch

When running a large-scale website, you must monitor everything — user behaviour, errors, and infrastructure health.

When running a large-scale website, it is essential to monitor everything. Four facets to consider:

🖱️ User interaction

Who clicks on what?

📊 User analytics

What local time do users usually come online?

🚨 HTTP error rate

What pages are throwing 500s and impacting users?

🖥️ Infrastructure metrics

How is our infrastructure performing? Can we handle 2× load? 10×?

Prometheus and Grafana

Prometheus stores metrics by scraping services over HTTP; Grafana turns those metrics into dashboards and alerts.

Prometheus

Prometheus is an open-source system for storing and graphing highly dimensional data and metrics.

  • It efficiently stores metrics in a custom format and scales through functional sharding and federation.
  • Data is scraped from monitored services over HTTP, rather than the applications publishing metrics to Prometheus. This pull model is a defining feature.
  • Originally developed at SoundCloud, now a member of the Cloud Native Computing Foundation.

Grafana

Grafana lets you visualise, query and alert on key metrics, regardless of where they are stored. It can have multiple backend metrics systems, so it is not tied to Prometheus.

🖥️ System metrics

  • CPU usage
  • Memory usage
  • Disk space and I/O
  • Network traffic and bandwidth
  • Load averages
  • System uptime

📱 Application metrics

  • Response times
  • Throughput
  • Error rates
  • Requests per second
  • Latency
  • User activity metrics
🧠
Memory hook: Prometheus pulls, Grafana draws. Prometheus is the store (and scrapes metrics); Grafana is the window (dashboards/alerts on top of any store).

Logging and Alerting: ELK, Nagios, Sentry

At scale you cannot read logs host by host, so you centralise logs, watch infrastructure, and aggregate errors into one feed.

ELK stack — centralised logging

Once a website reaches a certain size, manually looking at logs on each host is not feasible. The ELK stack (Elasticsearch, Logstash, Kibana) is a commonly used industry pattern for ingesting and querying large volumes of logs (application, web access/error, etc.) in a centralised location.

  • Elasticsearch — the service that stores and indexes your logs.
  • Logstash — ingests and processes the logs.
  • Kibana — an open-source data-visualisation plugin for Elasticsearch, offering a simple interface for querying your logs.

Nagios — infrastructure monitoring

Nagios is an open-source "industry standard" for monitoring infrastructure. Many custom metrics can be configured, including network transfer rates, server performance and application metrics. It has integrations that let it send email, integrate with chat programs and trigger alerts when metrics are exceeded.

Sentry — error detection

Sentry collects errors from your website, both front-end and back-end, and consolidates and aggregates them into a single feed of events. It allows real-time monitoring of errors experienced while using your website and is critical infrastructure for large-scale sites.

ℹ️
Note: Each tool answers a different question. ELK: "what happened, across all hosts?" Nagios: "is the infrastructure healthy, and warn me before it fails?" Sentry: "what errors are users hitting, right now?"
🤔
Pause & predict: why is hunting through logs on each individual host a losing strategy as a site grows?

Tracking, ETL and MapReduce

Off-the-shelf analytics may be too heavy or too limited — in that case you build the beginnings of a data warehouse.

Off-the-shelf tracking

Common products include Google Analytics and KISSmetrics. They are quick to adopt but may not fit every need.

Custom tracking / analytics

You may find that readily available tracking systems are too heavy (performance) or do not meet your needs. In those cases you may need to build the beginnings of a data warehouse solution.

The core problem: database schemas are generally optimised for user performance, not for analytics. Calculating one user's balance by summing their deposits is straightforward; calculating the balance for all users is far less bounded.

The most common ways to deal with this are:

  • Transform the database into a format better optimised for queries, or
  • Import the data into another service dedicated to analytics.

ETL — Extract, Transform, Load

When building a custom tracking system, a common approach is the ETL process:

Extract→Transform→Load
  1. Extract — pull data from various sources: user clicks from JavaScript, web access logs, database changes.
  2. Transform — put the data into a consistent format or structure.
  3. Load — load the transformed data into a final application.

MapReduce — distributed analytics

For very computationally intensive analytics across a large data set, MapReduce is a useful technique. It performs the analytics in a distributed sense, split over two steps:

  • Map — performs filtering and sorting.
  • Reduce — consolidates data into a summary format.
⚠️
Common trap: Do not run heavy analytics queries directly against your live application database. It is tuned for user transactions, and an analytics query can degrade the experience for everyone.
🧠
Memory hook: ETL moves and reshapes data into an analytics-friendly store; MapReduce then crunches that data in parallel (map = filter/sort, reduce = summarise).

Q1

What is pre-packaged software, and give four examples with the category each belongs to.

Answer: Pre-packaged web software is ready-made application software commonly used to get something up and running quickly. Examples: WordPress (content management system), vBulletin (internet forum software), MediaWiki (open-source wiki platform), Phabricator (project management tool).
Q2

Name the three components of a typical web package, and say which one the package provides and who handles the rest.

Answer: Application code, configuration files and a database. The prepackaged software provides the application code; it is up to the deployer to configure the application and the infrastructure (including the database).
Q3

Why is supply-chain security a concern with pre-packaged software, and what four kinds of dependency can you inherit?

Answer: You inherit not just the main application code but all of its dependencies, so a weakness anywhere upstream becomes your weakness. The four dependency kinds are libraries & frameworks, plugins/extensions, container images and system packages. Key risks: supply-chain attacks, outdated dependencies, plugin/extension ecosystem quality, and trust in Docker Hub images.
Q4

List the four questions to ask when auditing application code, and name four vulnerability/dependency tools.

Answer: Questions: What is it written in? Is the codebase mature? How active is development? Does it have a history of security vulnerabilities? Tools: npm audit, pip-audit, OWASP Dependency-Check, Snyk Vulnerability DB. Also useful: check other users, support avenues, commit frequency, and known vulnerabilities on cvedetails.com.
Q5

How should you audit a package's configuration, and why disable unused features?

Answer: Many packages ship with insecure configuration even though secure-by-default is best practice, so review every option before deployment. Ask what options exist, whether defaults are secure, whether features are enabled that you do not use, and whether those can be disabled. Identify all options from docs and examples, search for example configurations (but evaluate, don't blindly trust), identify all features/components, and disable unwanted ones — reducing complexity and the attack surface.
Q6

What database questions and checks should you perform before deploying a package?

Answer: Questions: does the package need its own database or can it share? What DB permissions are required? If the application is vulnerable, will a DB compromise lead to system compromise? Checks: identify database requirements (single DB for all tables, or multiple), evaluate permissions (give the minimum, extend only when necessary), and evaluate the scope of a DB compromise (an SQL injection may allow arbitrary commands).
Q7

Why should a package not be exposed directly to the internet, and what three advantages does a reverse proxy provide?

Answer: Packages may come with their own web/HTTP interface, and exposing it directly is risky — especially if it exposes an admin/control interface without authentication. A reverse proxy (Nginx, Apache) or load balancer sits in between and gives finer control over which requests reach the application. Advantages: scaling (load balancing, horizontal scaling, though the database remains a shared-state bottleneck), request authentication (e.g. basic auth for an internal service), and Web Application Firewall (inspect and reject attack-like requests).
Q8

Explain the mechanics of HTTP Basic Authentication from the server's challenge to the client's response.

Answer: Server side: the server answers the initial request with 401 Unauthorized containing the header WWW-Authenticate: Basic realm="User Visible Realm". Client side: the browser prompts for username/password, combines them with a single colon (e.g. Aladdin:OpenSesame), encodes the string in the RFC2045-MIME variant of base64, and sets the Authorization header, e.g. Authorization: Basic QWxhZGRpbjpPcGVuU2VzYW1l. Basic auth encodes rather than encrypts, so HTTPS is essential.
Q9

What is a WAF, where does it sit, and what limits its effectiveness?

Answer: A Web Application Firewall applies rules and/or filters to incoming HTTP requests, trying to identify requests that appear to contain exploitation code and reject them. All requests should pass through it, so it usually sits at the edge/web layer in front of the application. A WAF is only as good as the rules it evaluates, so the rule/filter sets must be kept up to date.
Q10

Contrast a virtual machine with a Linux container and state what Docker and Docker Compose add.

Answer: A hypervisor runs virtual machines inside a host OS, and each VM installs a full guest operating system. Linux containers remove the need for a guest OS, letting multiple isolated Linux systems run on a single host OS. Docker is an open-source project that automates deploying applications inside Linux containers, including dependencies; Docker Compose combines multiple services/containers.
Q11

Describe Docker images, volumes and networking, and explain why volumes are needed.

Answer: A container is a minimalistic Linux host created from a Docker image; the image describes the base OS and modifications (e.g. dependencies, files, entry point), as in FROM ubuntu:18.04 / RUN make /app / COPY . /app / CMD python /app/app.py. Containers do not maintain state, so they are poor for storing data; we mount volumes (host folders outside the container) to persist data — e.g. a MySQL data directory. Networking: containers can be linked and ports forwarded from the host; a WordPress container can talk directly to a MySQL container, and no other container/system can reach the DB unless explicitly allowed via Docker, improving security.
Q12

What is Docker Hub, and what two options exist for orchestrating containers at scale?

Answer: Docker Hub is a service containing pre-built Docker images usable as a starting point; many companies and projects publish images there. Security is a factor to consider — a pre-built image is still third-party code. Orchestration: Google's Kubernetes Engine (GKE), an open-source cluster management system (Kubernetes can also run outside Google Cloud), and AWS Elastic Container Service (ECS) for deploying Linux containers in the AWS ecosystem.
Q13

Name the four facets of monitoring and match Prometheus, Grafana, ELK, Nagios and Sentry to their jobs.

Answer: Facets: user interaction (who clicks what), user analytics (when users come online), HTTP error rate (what pages throw 500s) and infrastructure metrics (how infrastructure performs, can it handle 2×/10× load). Prometheus: metrics (open-source, scrapes over HTTP, CNCF, originally SoundCloud). Grafana: visualise/query/alert on metrics with multiple backend systems. ELK (Elasticsearch, Logstash, Kibana): centralised logging. Nagios: infrastructure monitoring with alerts. Sentry: error detection, aggregating front-end and back-end errors into one feed.
Q14

Why might you build custom tracking instead of using Google Analytics or KISSmetrics, and how do ETL and MapReduce help?

Answer: Available tracking systems may be too heavy (performance) or not meet your needs, so you build the beginnings of a data warehouse. The problem is that database schemas are optimised for user performance, not analytics — summing one user's deposits is easy, but the same for all users is far less bounded. Solutions: transform the database into a query-friendly format, or import the data into another service. ETL: Extract (clicks, web access logs, DB changes), Transform (consistent format), Load (into a final application). MapReduce: distributed analytics with Map (filter/sort) and Reduce (consolidate into a summary).
