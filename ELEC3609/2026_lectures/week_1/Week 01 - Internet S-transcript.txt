[00:30] 3. CONCEPTUAL FOUNDATIONS: INTERNET, SOFTWARE & PLATFORMS
--------------------------------------------------------------------------------

SPEAKER 1 (Jiawen Wen):
The title of this unit contains three distinct terms: Internet, Software, and Platforms. Ultimately, software engineering is about synthesizing these three concepts into a cohesive system.

1. THE INTERNET:
Why do we call it the "Internet" rather than just a "network"? The word comes from "interconnected networks"—connecting isolated local area networks (home networks, university networks, enterprise networks) into a global infrastructure.

Crucial distinction: The Internet is NOT the World Wide Web.
- The Internet is the underlying network infrastructure and protocols.
- The Web (World Wide Web) is a service running ON TOP OF the Internet, operating alongside other Internet services like Email (SMTP), File Transfer (FTP), SSH, and video streaming.

On the Web, resources are identified using URIs (Uniform Resource Identifiers) and URLs (Uniform Resource Locators). A URL specifies the transfer protocol (e.g., HTTPS), domain name, and resource path. (We will explore the distinction between URIs and URLs in Week 2).

2. SOFTWARE:
When people think of software, they usually think only of source code. But a real-world software system encompasses far more than source code:
- Compiled modules and build artifacts
- Configuration files and environment variables
- Operating systems, runtime dependencies, and server hardware

"It works on my machine" does not mean a software system is ready for production. Software requires systematic testing across environments.

3. PLATFORMS:
Historically, running a software platform meant purchasing physical server hardware, installing it in a server rack, and manually maintaining operating systems and networking. 

Today, while physical hardware still exists, we manage infrastructure through Cloud Platforms (AWS, Azure, Google Cloud). We use Infrastructure as Code (IaC)—writing configuration scripts that automatically provision, deploy, scale, and manage resources.

4. THE DEVOPS LIFECYCLE:
Software engineering is never a one-shot action. It is a continuous, iterative loop:
Plan -> Design -> Build -> Test -> Deploy -> Release -> Monitor -> Gather Feedback -> Redesign.

Examples of Systems:
- Real-Time Train Station Display: Raw sensor data is collected across transport networks, ingested into a processing pipeline, analyzed, and presented on station displays. The user sees a simple message ("Train arriving in 2 mins"), but behind it lies a complex data pipeline.
- Cloud Automation (e.g., Qantas): A relatively small cloud engineering team supports thousands of enterprise deployments through automated CI/CD pipelines and infrastructure reliability.

[00:50] 4. SOFTWARE ENGINEERING & ARCHITECTURE IN THE AI ERA
--------------------------------------------------------------------------------

SPEAKER 1 (Jiawen Wen):
At the end of last year, a talented student built an impressive project using Claude Code and asked me an important question:
"Since AI can generate code and build entire websites, what is the role of ELEC3609? Why do we still need to learn software engineering foundations?"

Let me address this from a historic and engineering perspective.

Four years ago, when I took ELEC3609 as an undergraduate student, we had primitive tools (like early GPT-3.5). It functioned like a basic search engine, so we had to write all code manually. At the end of that semester, half of the class struggled to deliver a functional front-end, and many teams failed their final demonstrations simply because they couldn't resolve basic Git merge conflicts.

Today, AI allows students to build sophisticated prototypes rapidly. But writing code with AI does NOT automatically make someone a good software engineer.

Case Study: OpenAI Codex Workflow Bug
Consider a real-world example from OpenAI Codex's GitHub issue tracker. If a developer moves their project folder to a new directory path on their machine:
- Git preserves the repository history because the `.git` folder moves with the project.
- OpenAI Codex, however, bound active chat threads to absolute local file paths rather than relative paths.
- As a result, moving a project folder caused Codex to lose thread context and fail with permission errors, forcing developers to abandon their active thread history.

Despite user complaints spanning over 6 months, OpenAI's eventual patch merely allowed attaching new folder paths rather than supporting true project folder migration. 

What does this tell us? Even state-of-the-art AI developer tools suffer from fundamental software architecture and workflow flaws. Software engineering is NOT just writing lines of code—it requires:
- Understanding user workflows and product requirements.
- Architecting resilient, maintainable systems.
- Prioritizing feature backlogs under time and resource constraints.
- Developing engineering taste and critical judgment.

[01:10] 5. SECURITY & HUMAN RESPONSIBILITY
--------------------------------------------------------------------------------

SPEAKER 1 (Jiawen Wen):
As my research is in software security, I must emphasize: NEVER blindly trust AI-generated code.

AI is fantastic for prototyping, but a "working" application is not necessarily a "correct" or "secure" application.
- A generated login page might authenticate users, but is it storing passwords securely using salted password hashes?
- A payment processing endpoint might execute transactions, but does it leak sensitive PII or suffer from Insecure Direct Object References (IDOR)?

Security requires formal requirements review, static analysis, dynamic testing, and adherence to security standards (such as the Web Coding Security Checklist and Meta's Purple Llama safety framework). Ultimately, human engineers—not AI—must take legal and technical responsibility for system integrity.
