Production Infrastructure: Linux, Networking and the Cloud

What it takes to move a project from your laptop to a real server. We cover the Linux foundations you need on the command line (users, capabilities, SSH), the AWS building blocks for hosting (EC2, EBS, RDS, Route 53, VPC), how ports and firewalls control traffic, and the server applications — nginx, a WSGI/ASGI interface and a database — that make up a production deployment.

Read this first: Production is about running your app where the internet can reach it, safely. Keep four questions in mind: who can log in (Linux users, SSH keys), where it runs (EC2, EBS, RDS, VPC), what may connect (ports, firewalls, security groups), and how requests reach the app (nginx → WSGI/ASGI → Django → database). The whole week is those four layers stacked up.

Linux: The Dominant Server Platform

Linux is an open-source Unix-like OS whose kernel runs the overwhelming majority of the world's web servers.

Linux is an open-source UNIX-like operating system, whose defining feature is the Linux kernel. It was released in 1991 by Linus Torvalds.

A Linux distribution defines a collection of software that comes prepackaged as a complete operating system. For example:

  • Package managers — apt-get or pacman.
  • Window managers — GNOME or i3.
  • Text editors.

Linux has become the most widely installed general-purpose OS due to the proliferation of Android. It is also the most dominant OS for web servers (>90%).

💡
Why it matters: When you deploy to the cloud, you are almost certainly deploying onto Linux. The rest of this section is the minimum command-line and privilege knowledge you need to operate that server safely.
🤔

Linux Users and Privilege

Every program runs as some user, and the privileges of that user bound what a compromise can do.

The root user (aka the superuser) is the most privileged user on a Linux system. While root can do anything on the system, other users can have a wide variety of privileges.

Programs execute as a particular user. If a program requires special privileges, it may need to execute as root.

ps aux

The command ps aux lists all processes running on the system and the user they are running as.

Program-specific Linux users

Usually a program does not need root, and so will (or at least should) run as a different user. If such a program is compromised, it can only perform malicious actions that its running user could perform.

ProgramRuns as
Web servers (including nginx)www-data
MySQL (including mysqld)mysql
Programs needing almost no privilegesnobody
🧠
Memory hook: Run each service as its own low-privilege user. Then the blast radius of a bug is capped at that user's permissions — never at root's.
⚠️
Common trap: "It works when I run it as root" is not a solution. A service that needs root to start is a service that, when hacked, hands over the whole machine.

Capabilities: Fine-Grained Privilege

Capabilities break root's all-or-nothing power into small units, so a process gets only the privileges it truly needs.

Traditional root vs capabilities

Classic UNIX/Linux model

  • root (UID 0) has all privileges.
  • If a process is compromised while running as root, the attacker gains full control of the system.

Capabilities

  • Split root privileges into smaller, fine-grained units.
  • Examples: CAP_NET_BIND_SERVICE, CAP_SYS_ADMIN, CAP_DAC_OVERRIDE.
  • Each process can be assigned only the subset it really needs.

Why it improves security

  • Least privilege — grant the minimum.
  • Damage containment — a compromise is capped at the granted capability.
  • Reduced attack surface — the process cannot perform unrelated privileged operations.

Worked example: running nginx

  • Traditionally: nginx needed root just to bind port 80.
  • With capabilities: run it as an unprivileged user but grant only CAP_NET_BIND_SERVICE.
  • If nginx is then hacked, the attacker cannot: create raw sockets (CAP_NET_RAW), mount filesystems (CAP_SYS_ADMIN), or change ownership of files (CAP_CHOWN).
💡
Why it matters: Binding to a privileged port is the only reason nginx needs elevated power. Capabilities let you grant exactly that one thing instead of everything.
🤔
Pause & predict: why is "run nginx as root" a bigger risk than "run nginx as www-data with CAP_NET_BIND_SERVICE"?

Secure Shell (SSH)

SSH is the secure replacement for Telnet, letting you reach a remote machine's shell — and it is an essential tool for anyone running Linux servers.

Secure Shell (SSH) is a secure replacement for the old Telnet protocol. SSH enables a user to access the shell or terminal on a remote machine, and is an essential tool for any web master, since Linux is the dominant server platform on the internet.

The SSH server

The most common SSH server software is OpenSSH, which originates from the OpenBSD project. An SSH server:

  • Listens for incoming connections on TCP port 22.
  • Authenticates connecting users using passwords or public/private keys.

The SSH client

OpenSSH also provides an SSH client, the client-side software that connects to the SSH server. There are many alternative clients depending on the platform; on macOS, Linux and Windows you can use ssh via OpenSSH.

🧠
Memory hook: Port 22 is SSH. Remember it the same way you remember HTTP is 80 and HTTPS is 443.

SSH Keys and Public-Key Authentication

SSH provides both authentication and encryption, and it uses two different key pairs — one for the server, one for the user.

SSH provides authentication and encryption. The obvious way to log in is using the remote user's password — but this is bad. Instead, we want to use SSH keys.

The two sets of keys

Server host key

  • The SSH server has a long-term public/private host key pair.
  • The host key is used to authenticate the server to the client.
  • During connection setup, SSH performs a key-exchange to derive shared symmetric session keys.
  • The server proves possession of its private host key by signing data associated with the key exchange.
  • The private host key is never sent to the client.

Client / user key

  • Each user may have a public/private key pair for authentication.
  • The public key is stored on the server.
  • The client proves possession of the corresponding private key without sending it to the server.

Public-key authentication and digital signatures

A public/private key pair authenticates by proving possession of the private key without revealing it:

  • Private key — kept secret; used to create a digital signature.
  • Public key — can be shared; used to verify the signature.
ℹ️
Note: SSH session encryption keys are established separately through the SSH key-exchange protocol. Do not conflate authentication keys with session keys.
⚠️
Common trap: The private key never travels over the network. The client proves it holds the private key (by signing); it never sends it.
🤔
Pause & predict: two key pairs are involved in a key-based SSH login. What does each one authenticate?

Server Keys, authorized_keys and ssh-agent

known_hosts protects you from impostor servers, authorized_keys decides who may log in, and ssh-agent saves you retyping a passphrase.

SSH server keys and known_hosts

The server typically stores its key pairs as:

/etc/ssh/ssh_host_*_key
/etc/ssh/ssh_host_*_key.pub

When first connecting to an unknown server, you get a warning. By accepting it, a new entry is added to your ~/.ssh/known_hosts file. By keeping track of known SSH server public keys, SSH clients can minimise the potential for a MITM attack.

SSH client keys and authorized_keys

To authenticate a user on the SSH server, a client proves ownership of a private key corresponding to an authorised public key. For example, to connect as user myuser, the server has a file in that user's home directory:

/home/myuser/.ssh/authorized_keys

This file contains the public keys of anyone authorised to connect as this user. The SSH server checks that any connecting client possesses the private key corresponding to a public key in that file; if so, the connection is authorised.

ssh-agent and agent forwarding

ssh-agent is a useful program for storing the unencrypted SSH private key in memory. SSH typically reads private keys from ~/.ssh/id_rsa, which is encrypted, so every run of SSH needs the passphrase. To make things easier, the unencrypted key can be stored in memory by attaching it to a running process — that process is ssh-agent.

With the ForwardAgent option, we can allow remote SSH clients to access our local ssh-agent process — and therefore our unencrypted private key.

⚠️
Common trap: Agent forwarding extends trust to the remote host. If that host is compromised, so is your agent — and thus your key. Forward only to hosts you trust.
🤔
Pause & predict: known_hosts and authorized_keys both contain public keys, but they protect opposite directions. Which protects whom?

Amazon Web Services: The Cloud Toolkit

AWS lets you rent the infrastructure instead of buying hardware, and it supplies a whole toolkit of services around the servers.

Amazon Web Services (AWS) is an extremely popular cloud hosting provider. Using AWS:

  • Removes the need to set up dedicated hardware to host a website.
  • Often takes care of software installation and configuration.
  • Provides a wide range of services that can assist in creating website infrastructure.
💡
Why it matters: The cloud turns capital expense (buying servers) into operating expense (renting capacity), and lets you scale up or down in minutes instead of weeks.
🤔
Pause & predict: you need a server, a hard drive for the database, a managed database and a domain name. Which AWS services come to mind?

EC2, EBS, RDS and Route 53

These four services cover compute, storage, managed databases and DNS — the core of a hosted web application.

Elastic Compute Cloud (EC2)

  • Provides access to server instances.
  • EC2 is the most common and fundamental part of the AWS suite, and you will need it for your project deployment.
  • Instances can be created in one of many availability zones (AZs) in various regions of the world.

Elastic Block Store (EBS)

  • Provides hard-drive volumes that can be attached to EC2 instances.
  • Useful for separating data storage from the server that executes your software.
  • When attaching a volume to an instance, both must be in the same Availability Zone.

Relational Database Service (RDS)

  • Provides managed database servers.
  • Useful for a scalable, backed-up version of your data.
  • Supports Aurora, PostgreSQL, MySQL, MariaDB, Oracle Database and SQL Server.

Route 53

  • Provides the ability to route requests to AWS infrastructure, e.g. www.example.com => 53.96.54.23.
  • Operates a Domain Name System (DNS) web service.
🧠
Memory hook: EC2 = computer, EBS = disk, RDS = managed database, Route 53 = DNS. Four nouns, four jobs.
⚠️
Common trap: An EBS volume and the EC2 instance it attaches to must be in the same Availability Zone. A volume in the wrong AZ simply cannot attach.

VPC and Container Deployment (ECS/EKS)

A VPC gives you network control around your instances; ECS and EKS are AWS's managed ways to run containers instead of full VMs.

Virtual Private Cloud (VPC)

  • Provides support for network segregation and greater control over EC2 instances.
  • Very useful for web infrastructure, but its configuration can be complex.
  • Not necessary for the project — instead we use the default VPC created by AWS (EC2-VPC: using a VPC within EC2).

VM deployment vs container deployment

Amazon ECS

  • Elastic Container Service — AWS's own fully managed container orchestration service.

Amazon EKS

  • Elastic Kubernetes Service — AWS's managed Kubernetes service.
ℹ️
Note: Week 6 introduced containers and Docker. This is the AWS-managed way to run those containers: ECS if you want AWS's own orchestration, EKS if you want Kubernetes.

Ports, the OSI Model and Firewalls

Applications listen on TCP ports, and firewalls decide which traffic is allowed to reach them.

Ports and the OSI model

Recall the 7-layer OSI model. In particular:

  • TCP/UDP ports — Layer 4.
  • Firewalls and load balancers operate around this layer.
  • Public IPs — Layer 3.

We say applications listen on a particular TCP port. This lets multiple applications run on the same host, each listening on a different port. Any application can choose any port, but there are standard port numbers for particular application types.

Whenever a network service starts on a host, it attempts to listen on a particular port. Only one running application may listen to a port at a time.

Firewalls

A firewall is a security system that can allow or disallow network traffic to pass according to a set of rules. Firewalls come in many shapes and sizes:

🏠 Home router

Makes decisions about incoming/outgoing traffic and prevents attackers from gaining access to your network.

🧱 Software firewall

Runs on a host machine and provides rules about the traffic allowed to enter that host.

🧠
Memory hook: An IP address finds the host (Layer 3); a port finds the application on that host (Layer 4). The firewall sits between the internet and your listening ports.
🤔
Pause & predict: two web apps on one server both want to be reached by browsers. How do ports let that work?

AWS Security Groups

A security group is a stateful virtual firewall whose rules form a whitelist — anything not explicitly allowed is dropped.

AWS Security Groups (SGs) are stateful virtual firewalls. When first configuring an EC2 instance, you can either create a new security group or add the instance to an existing one.

To configure a security group, you must specify:

📡 Protocol

TCP / UDP / ICMP.

🔌 Port(s)

The TCP/UDP port(s) the rule applies to.

📍 Source

Which source IP address(es) the rule applies to.

The rules are a whitelist: any packets not matching a rule are automatically dropped (disallowed).

SSH ruleVerdict
SSH 22 ← 0.0.0.0/0Bad — the whole internet may attempt SSH.
SSH 22 ← your IP onlyBetter — restrict the source.
AWS Systems Manager Session ManagerBest cloud-native option — avoid exposing the port at all.
⚠️
Common trap: Opening SSH (22) to 0.0.0.0/0 exposes the port to continuous brute-force attempts. Restrict the source, or use Session Manager so no inbound SSH port is open.
🤔
Pause & predict: a security group is a whitelist. What happens to a packet that matches no rule at all?

Elastic Load Balancing and Elastic IPs

A load balancer spreads traffic across instances for scaling, and an Elastic IP keeps an instance's address stable across restarts.

Elastic Load Balancer (ELB)

  • Provides a load balancing service for EC2 instances.
  • Useful for production websites, allowing for easy horizontal scaling.
  • For your project, you should learn how to utilise ELB and configure it for your deployment.

IPs vs DNS

  • When you start an EC2 instance, AWS assigns it a public IP address. If you stop and start the instance, it can be reassigned to a different IP — which means updating DNS records.
  • To maintain a consistent IP address between restarts, assign the instance an Elastic IP address. Once assigned, the instance always has this IP whenever it is created.
💡
Why it matters: A stable address (Elastic IP) plus a stable name (Route 53 DNS) means users and clients do not break when you restart or replace a server.
🧠
Memory hook: ELB = spread the load across many instances; Elastic IP = pin the address so one instance keeps the same IP.

From Development Server to Production: nginx and WSGI/ASGI

A production server stacks a web server in front of an application interface, which talks to your framework and database.

You will need to configure several applications on your server:

Web server→Application interface→Web application→Database

Recommended web server: nginx

nginx (pronounced "engine-X") is a fast web server that can also act as a reverse proxy. Due to its widespread use and ease of configuration, it is highly recommended for the project.

  • nginx can receive and process an HTTP request, but it does not interpret web application code.
  • Instead, we ask nginx to proxy_pass HTTP requests to the application interface.

WSGI vs ASGI

Both are interface standards. Both define how Python web application servers communicate with frameworks such as Django.

WSGI

  • Designed for conventional request–response web applications.

ASGI

  • Extends the model for asynchronous and real-time communication.
💡
Why it matters: The split keeps responsibilities clean: nginx handles connections and static assets efficiently; the application server runs your Python framework; the interface (WSGI/ASGI) is the agreed contract between them.

Databases and Separation of Data

Most apps need a relational database, and its data should live on a separate volume from your code.

  • Most web applications require persistent storage of data.
  • You will most likely need a relational database management system (RDBMS).
  • We recommend MySQL (feature-rich and relatively easy to use); PostgreSQL and MariaDB are acceptable alternatives.

Rough setup steps

  1. Install the DB software.
  2. Configure users (username & password).
  3. Configure application code to use the DB, connecting with the username & password.

Separation of data

  • You should always separate your data from your application code.
  • Typically this means configuring your DB to save data to a separate volume from where the operating system and web application are installed.
  • On EC2, use a separate EBS volume for database storage, then configure the RDBMS to store data on the new volume (for MySQL, this means moving the data directory).
💡
Why it matters: If code and data share a volume, redeploying or rebuilding the app can destroy the data. A separate volume lets you replace the application without touching the database — and back it up independently.
⚠️
Common trap: Putting the database data directory on the same volume as the OS means a rebuilt instance loses everything. Attach a dedicated EBS volume and point the RDBMS at it.
🤔
Pause & predict: you need to rebuild your EC2 instance. What must have been separated for your data to survive?

Q1

What is Linux, what is a distribution, and why is Linux so important for web servers?

Answer: Linux is an open-source UNIX-like operating system whose defining feature is the Linux kernel, released in 1991 by Linus Torvalds. A distribution is a collection of software packaged as a complete OS, including package managers (apt-get, pacman), window managers (GNOME, i3) and text editors. Linux is the most widely installed general-purpose OS (largely due to Android) and the most dominant web-server OS (>90%).
Q2

Who is root, why do programs run as particular users, and which users do nginx, MySQL and minimal programs use?

Answer: root (the superuser) is the most privileged user and can do anything; other users have a variety of privileges. Programs execute as a particular user, and a program needing special privileges may run as root — but usually it should not, so a compromise is limited to that user's abilities. nginx (web servers) usually runs as www-data, mysqld (MySQL) as mysql, and programs needing almost no privileges as nobody. Use ps aux to see processes and their users.
Q3

Explain Linux capabilities, why they improve security, and how they apply to running nginx.

Answer: In the classic model root (UID 0) has all privileges, so a compromised root process means full system control. Capabilities split root into fine-grained units — e.g. CAP_NET_BIND_SERVICE, CAP_SYS_ADMIN, CAP_DAC_OVERRIDE — and each process can be assigned only the subset it needs. Benefits: least privilege, damage containment, reduced attack surface. For nginx: traditionally it needed root just to bind port 80; with capabilities it runs as an unprivileged user granted only CAP_NET_BIND_SERVICE, so if hacked the attacker cannot create raw sockets (CAP_NET_RAW), mount filesystems (CAP_SYS_ADMIN) or change file ownership (CAP_CHOWN).
Q4

What is SSH, what does the SSH server do, and why prefer keys over passwords?

Answer: SSH (Secure Shell) is a secure replacement for Telnet that lets a user access the shell/terminal on a remote machine; it is essential for web masters since Linux dominates servers. The server software is usually OpenSSH (from OpenBSD); it listens on TCP port 22 and authenticates users with passwords or public/private keys. The obvious password login is bad; instead use SSH keys, which provide authentication and encryption.
Q5

Describe the two SSH key pairs and how public-key authentication uses a digital signature.

Answer: Server host key: a long-term public/private pair that authenticates the server to the client; during connection setup SSH performs a key exchange to derive shared symmetric session keys, and the server proves possession of its private host key by signing key-exchange data. The private host key is never sent to the client. Client/user key: each user may have a key pair; the public key is stored on the server, and the client proves possession of the matching private key without sending it. A private key is kept secret and used to create a digital signature; the public key is shared and used to verify it. Note session encryption keys are established separately via the SSH key-exchange protocol.
Q6

Where are SSH server keys stored, what is known_hosts for, and what does authorized_keys do?

Answer: Server keys are typically stored at /etc/ssh/ssh_host_*_key and /etc/ssh/ssh_host_*_key.pub. On first connecting to an unknown server you get a warning; accepting it adds an entry to your ~/.ssh/known_hosts file. By tracking known server public keys, SSH clients minimise the potential for a MITM attack. authorized_keys lives in a user's home directory (/home/<user>/.ssh/authorized_keys) and lists the public keys of anyone authorised to connect as that user; the server checks the client possesses the matching private key.
Q7

What does ssh-agent do, and what risk does agent forwarding introduce?

Answer: ssh-agent stores the unencrypted SSH private key in memory by attaching it to a running process, so you do not need to enter the passphrase for ~/.ssh/id_rsa every time SSH runs. With the ForwardAgent option, remote SSH clients can access the local ssh-agent process — and therefore the unencrypted private key. That extends trust to the remote host: if it is compromised, so is your key, so forward only to trusted hosts.
Q8

Match EC2, EBS, RDS and Route 53 to their jobs, and state the Availability Zone rule for EBS.

Answer: EC2 (Elastic Compute Cloud) provides server instances and is the fundamental AWS service you need for project deployment; instances live in availability zones in regions worldwide. EBS (Elastic Block Store) provides hard-drive volumes attachable to EC2 instances, useful for separating data storage from the server; the volume and instance must be in the same Availability Zone. RDS (Relational Database Service) provides managed, scalable, backed-up database servers supporting Aurora, PostgreSQL, MySQL, MariaDB, Oracle and SQL Server. Route 53 provides DNS routing to AWS infrastructure.
Q9

What is a VPC, is it required for the project, and what is the difference between ECS and EKS?

Answer: A Virtual Private Cloud provides network segregation and greater control over EC2 instances; it is very useful for web infrastructure but complex to configure. It is not necessary for the project — the default VPC created by AWS is used (EC2-VPC). ECS (Elastic Container Service) is AWS's own fully managed container orchestration service; EKS (Elastic Kubernetes Service) is AWS's managed Kubernetes service.
Q10

How do ports and firewalls control traffic, and which OSI layers are involved?

Answer: Applications listen on a particular TCP port so multiple apps can share a host; only one running application may listen to a port at a time; standard port numbers exist for common application types. In the 7-layer OSI model, TCP/UDP ports are Layer 4 (firewalls and load balancers sit around here), and public IPs are Layer 3. A firewall allows or disallows traffic according to rules — examples include a home router (deciding on incoming/outgoing traffic) and a host software firewall.
Q11

What is an AWS Security Group, what three things configure its rules, and what is the best practice for SSH?

Answer: Security Groups are stateful virtual firewalls attached when configuring an EC2 instance. Rules specify Protocol (TCP/UDP/ICMP), Port(s), and Source (source IP address(es)). Rules are a whitelist — any packet not matching a rule is automatically dropped. Bad: SSH 22 ← 0.0.0.0/0 (whole internet). Better: SSH 22 ← your IP only. Best cloud-native option: AWS Systems Manager Session Manager.
Q12

What does an Elastic Load Balancer do, and why use an Elastic IP?

Answer: ELB provides a load-balancing service for EC2 instances, useful for production sites and easy horizontal scaling; you should learn to configure it for your deployment. When an EC2 instance starts it gets a public IP that can change if you stop and start it (requiring DNS updates). An Elastic IP is a consistent address you assign so the instance always has that IP whenever it is created.
Q13

Describe the production server stack, the role of nginx, and the difference between WSGI and ASGI.

Answer: Configure a web server, an application interface, the web application and a database. nginx (pronounced "engine-X") is a fast web server that can also act as a reverse proxy, and is recommended; it does not interpret application code, instead proxy_pass-ing HTTP requests to the application interface. WSGI and ASGI are interface standards defining how Python app servers communicate with frameworks such as Django; WSGI is for conventional request–response apps, while ASGI extends the model to asynchronous and real-time communication.
Q14

What database do we recommend, what are the setup steps, and why separate the data?

Answer: Most apps need persistent storage and a relational DBMS; MySQL is recommended (feature-rich, easy), with PostgreSQL and MariaDB acceptable. Setup: install the DB software, configure users (username & password), and configure the application code to connect using those credentials. Always separate data from application code: configure the DB to save data to a separate volume from the OS and web app. On EC2, use a separate EBS volume for database storage and point the RDBMS at it (for MySQL, move the data directory). This means rebuilding the application does not destroy the data.
