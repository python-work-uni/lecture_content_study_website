Front-End Development: Building for the Browser · 2026 Session

This lecture is about everything that runs in the user's browser. It starts with user experience — what makes an interface feel sensible…

Lecture Overview: This lecture is about everything that runs in the user's browser. It starts with user experience — what makes an interface feel sensible and effortless — and the design artefacts (wireframes, mockups, prototypes) that teams use before writing code. It then moves through the browser itself (why no two browsers are equal, and how to test across them), the three core web technologies (HTML, CSS, JavaScript), modern approaches like Single Page Applications and AJAX, and the build tools (Bower, Grunt, Webpack) that keep front-end code manageable. The theme is that the front end is the presentation layer between the user and the backend, and that good front-end work is structured, testable engineering rather than guesswork.

Front-End Fundamentals & UX

What the Front End Is

  • The frontend is the presentation layer.
  • It is the interface between the user and the backend (data access, computations, etc).
  • This lecture deals with the software components that execute in the browser.
📌
Info:: The lecture opens with a memorable line: "Mobile is a magnifying glass for your usability problems." Small screens expose bad design that a large desktop can hide.

Good User Experience

  • Building effective user interfaces is not art.
  • Effective user interfaces are sensible, consistent and structured.
  • If you can develop software, you can build an effective user interface — if you dedicate the time to it.

What Users Expect

  • Users shouldn't need instructions.
  • There should be simple steps to achieve common tasks.
  • Every click matters.
  • Make the user happy!

The lecture reinforces this with a Steve Jobs quote: "It's not just what it looks like and feels like. Design is how it works." Usability problems show up everywhere — the lecture points to examples like confusing "bad doors" and the notoriously cluttered LingsCars site as cautionary tales, alongside interfaces that get it right (Google Inbox, Medium, Slack).

💡
Why It Matters:: A backend can be perfect and still fail if the user cannot figure out the interface. UX is engineering discipline applied to human attention.
02

UX vs UI Roles

"UX" and "UI" are often used interchangeably, but they are different jobs with different experts.

UX Designer — the Interaction Designer

  • Charts the user pathway (the sequence a user travels through).
  • Plans the information architecture (how information is organised and found).
  • Is an expert in wireframes, prototypes, and research.

UI Designer — the Visual Designer

  • Chooses colour and typography.
  • Plans the visual aesthetic.
  • Is an expert in mockups, graphics, and layouts.

The lecture also raises the question of "Technical Artists?" — people who bridge the visual and technical sides.

🧠
Memory Hook:: UX = the journey (pathway, architecture, research). UI = the look (colour, type, layout).
03

Design Artefacts

Before implementing a page, teams produce progressively more detailed design artefacts. The key is knowing what each one is for.

ArtefactKey informationDetail level
WireframeThe information that will be displayed; an outline of the structure and layout of componentsLow — a blueprint for each page
MockupThe visual appearance of the pageMore detailed than a wireframe
PrototypeHow the page worksLow or high fidelity; users should be able to use and interact with it
  • A wireframe is a blueprint for each page that will be implemented.
  • A mockup answers "what does it look like?" in more visual detail.
  • A prototype focuses on behaviour, and its fidelity can be low or high.
⚠️
Common Trap:: Don't reach for a high-fidelity mockup when the question is still about structure and flow — that is wireframe territory.
04

The Browser Landscape

Not All Browsers Are Created Equal

Each browser is different, and so is each version of a browser, and each version is different on each OS. Add different screen resolutions and mobile devices to the mix, and the combinations multiply.

  • You must consider interoperability between browsers, browser versions and operating systems when writing web applications.
  • caniuse.com provides a quick reference on browser compatibility for features and limitations.

Cross-Compatibility Testing

  • If your application must run on a certain browser, you must test it on that browser. Never assume it will work.
  • Different browsers can be tested on your own local machine.
  • Different operating systems can be tested by emulating them with virtual machines — but beware, virtualisation can introduce bugs itself.
  • Professional solutions exist for testing cross-compatibility, often with the ability to test on real hardware and devices.

You Don't Need To Support ALL Browsers

  • You don't need to (and probably shouldn't) support all browsers, versions and operating systems.
  • At the start of your project, decide what you will and won't support, based on your intended customer base.
  • Know your intended audience.
✅
Exam Tip:: Cross-browser support is a product decision, not a technical default. Justify it with your audience.

Design Practice

Two design practices shape how a front end behaves across people and devices.

Responsive Design

Designing so that a page adapts to different screen sizes and devices.

Inclusive Design

Design that does not exclude people on the basis of:

  • Disability, religion, gender identity
  • Race, language, sexual orientation
  • Ethnicity, pronunciation, age

Resources

The lecture points to reference libraries of patterns:

  • https://ui-patterns.com/patterns
  • https://hike.one/
  • https://www.uxlibrary.org/
💡
Why It Matters:: Responsive design handles the device; inclusive design handles the person. Together they widen the audience a single codebase can serve.

Web Components

A Web Component is:

  • A set of custom HTML elements and the technologies that facilitate their development.
  • Components on the web.
  • Any reusable blob of HTML, CSS, and JS.

Web components bring four properties that make them powerful:

  • Reactivity — they can respond to changes.
  • Encapsulation — internals are kept contained.
  • Modularity — they are self-contained pieces.
  • Reusability — the same component can be used in many places.
🧠
Memory Hook:: Web components are R-E-M-R — Reactive, Encapsulated, Modular, Reusable.

HTML Versions & Document Structure

HTML Versions Timeline

HTML is a constantly evolving specification. A summarised timeline:

  • 1997 — HTML 3.2
  • 1999 — HTML 4.01
  • 2007 — HTML5 Draft Published
  • 2014 — HTML5 Published as W3C Recommendation

Crucially, browsers implement subsets of the HTML specifications — a feature can be standardised and still not work everywhere. Representative additions:

  • <audio> and <video> elements
  • data, time and color input types in HTML5

A Minimal HTML5 Document

A simple HTML5 document implements CSS and JavaScript — this is the skeleton every page starts from.

The DOCTYPE Tag

  • It is not an HTML tag. It is an instruction to the browser about the version of HTML used by the page.
  • It must be the very first line in your document.
  • The HTML5 DOCTYPE declaration is <!DOCTYPE html>. It will masquerade as HTML4 for older browsers.
  • HTML 4 DOCTYPEs are more complex, e.g.: <!DOCTYPE HTML PUBLIC "-//W3C//DTD HTML 4.01//EN" "http://www.w3.org/TR/html4/strict.dtd">
📌
Info:: <!DOCTYPE html> is short because HTML5 does not use a DTD reference the way HTML4 did — but the parser still receives a version instruction.
08

Core HTML Tags & Attributes

The lecture names the structural elements <html>, <head>, <title>, <body>, <h1> and <p> as the meaningful containers of a document.

HTML Tag

  • Encapsulates the entire HTML document.
  • Can specify the language used in the document.

HEAD Tag

  • Contains meta information that is separate from the content.
  • Its elements are not rendered in the view.
  • CSS files are generally imported here.
  • JS imported here will delay rendering of the page until the scripts are loaded. JS can instead be imported in the body to speed up page loading.
  • The Title tag is mandatory in this section.

BODY Tag

  • Contains the HTML elements to be rendered to the view.
  • If placing script tags in the body, convention is to place them just before the closing body tag.
  • Body is a mandatory tag for an HTML document.
  • Never skip the end tag.
  • Empty elements such as <br> exist.

Attributes

Attributes parametrise elements — an anchor's destination, an image's source, an inline style:

  • <a href="https://www.sydney.edu.au/">Visit USYD</a>
  • <img src="img_girl.jpg">
  • <p style="color:red;" title="I'm a tooltip">This is a red paragraph.</p>

Rules for good HTML:

  • Always use lowercase attributes.
  • Always quote attribute values.
  • You may use single or double quotes (be consistent).
💡
Why It Matters:: Where you put <script> literally changes when the user sees content. Blocking JS in the head delays rendering; scripts at the end of the body let the page paint first.

The DOM & JavaScript

The Document Object Model

  • The DOM treats an HTML document as a tree-like structure of objects.
  • Manipulating the DOM is possible from JavaScript, and forms the majority of JavaScript usage in the browser.

Finding Elements

JavaScript can find elements by:

  • Id — getElementById
  • Tag name — getElementsByTagName
  • Class Name — getElementsByClassName
  • and other approaches.

What DOM Scripting Can Do

  • Changing HTML content
  • Updating values of an attribute
  • Dynamic HTML content (i.e. Date())
  • Write directly to the HTML output stream

The lecture includes a DOM behaviour question ("What gets logged?" with options connected/disconnected/nothing) to test understanding of when DOM events fire during page parsing.

📌
Info:: The DOM is the bridge between static markup and dynamic behaviour — without it, JavaScript would have nothing to modify.
10

CSS & CSS Frameworks

Cascading Style Sheets

  • Describes the presentation of an HTML document.
  • Enables a separation of concerns between "what's in a document" (HTML) and "what a document looks like" (CSS).
  • Like HTML, CSS has different versions and varying support across browsers.
  • CSS can be difficult to get right but is 100% worth it.

CSS Syntax

CSS Rule
selector { property:value; }
  • Selector — points to the HTML element the style should apply to.
  • Property — the attribute that should be modified.
  • Value — what the value should be updated to.
  • {} — the declaration block; it can contain multiple property/value pairs.

Selector Types

SelectorBehaviour
ElementSelects HTML elements by tag, e.g. selects body, applies a background colour, defines a font
ClassAny elements with the class (e.g. dog) get the style; a class may be applied to multiple elements, and elements may have multiple classes
IDSelects only one element; an element may have only one id

Media Queries

  • Media queries customise how a document displays on a range of devices by applying conditions to CSS rules.
  • CSS is applied if the @media query returns true.
  • They are great for creating responsive pages.

CSS Frameworks

The lecture's punchline: "The best CSS is written by someone else. Use a framework." Popular frameworks:

  • Bootstrap
  • Foundation
  • Materialize

Choose your framework carefully — switching between frameworks can be laborious and time-consuming. Consider:

  • Aesthetics
  • Grid system
  • Community support
  • Cross-browser compatibility
🧠
Memory Hook:: CSS selectors: element styles a tag, class (.) styles a group, id (#) styles exactly one thing.
11

JavaScript Language & TypeScript

JavaScript

JavaScript is a high-level, dynamic, un-typed, interpreted programming language.

  • It allows pages to become dynamic by manipulating the HTML DOM with code.
  • Alongside HTML and CSS, it forms a fundamental core of today's modern web.
  • Learning to appreciate JavaScript will improve your applications and make you more employable.

JavaScript Issues

Early versions were hard to develop in because of:

  • Weird equality / automatic conversion
  • The behaviour of this
  • Lack of a type system
  • Weak static analysis support; poor tooling
  • Lack of a module system

The language is constantly evolving and has improved significantly with more recent versions. The lecture's verdict: "JavaScript isn't perfect but it's here to stay."

TypeScript

  • TypeScript is an open-source programming language that implements a superset of JavaScript while adding optional static types.
  • Developed and maintained by Microsoft, and designed for the development of large web applications.
  • It is transpiled back to JavaScript.
  • It adds support for:
    • types
    • modules / namespaces
    • classes
💡
Why It Matters:: TypeScript addresses several of JavaScript's classic weaknesses (no types, no modules), which is why it is popular for large codebases even though browsers only run JavaScript.
12

jQuery & Single Page Applications

jQuery

  • jQuery — the Swiss army knife!
  • Commonly used on web pages.
  • Highly supported and has an active community.
  • Likely to have everything you need to interact with the DOM.
  • Great for cross-platform support.
  • It is becoming less popular due to modern frameworks superseding jQuery's functionality and browsers implementing native versions of a lot of the library.

Single Page Applications (SPAs)

  • SPAs load a single HTML document and use JS to update the user's view without a hard refresh.
  • They move a lot of work to the client-side (browser) and typically create a smoother, more fluid user experience. They allow for significantly more powerful web applications.

Pros:

  • Provide a faster interface
  • Encourage separation of concerns
  • Reusable
  • Allow for "serverless" browser applications
  • Simpler binding of data to views
  • Easy to serve from a CDN, decreasing user load time
  • Removes load from backend servers

Cons:

  • Typically require more work
  • Typically require more experienced developers due to complexity
  • A new frontier — frameworks are rapidly evolving
  • Pushes workload into the browser, which is bad for low-spec/mobile devices
⚠️
Common Trap:: SPAs are not free performance. They remove backend work but add client work — a net loss on low-powered phones.

AJAX & JavaScript Frameworks

AJAX — Asynchronous JavaScript and XML

  • Allows the page to be updated with external data without a full refresh.
  • AJAX is a fundamental aspect of the modern web.
  • Traditionally we would use XHR (XMLHttpRequest), which can be clunky and cumbersome.
  • JavaScript libraries like jQuery improved the situation.
  • Native browser APIs, such as Fetch, are also an option where supported.

Popular JavaScript Frameworks

  • Angular (Google)
  • React (Facebook)
  • Ember
  • Backbone.js
📌
Info:: AJAX is the mechanism; a framework (Angular, React, etc.) is the structure you build a large SPA around. XHR and Fetch are two ways to make the underlying asynchronous request.

Front-End Build Tools

Three Node.js-based tools automate and organise front-end work.

Bower — a Package Manager for the Web

  • Imagine pip but for frontend HTML, JS and CSS libraries.
  • It is a Node.js application, installed via npm.
  • Can fetch packages and their dependencies.
  • Makes it much easier to update packages.
  • Document your dependencies in a bower.json file.

Grunt — a JavaScript Task Runner

  • Similar to a Makefile but for HTML frontends.
  • Also a Node.js application, installed via npm.
  • Automates boring, repetitive tasks:
    • minification of images, CSS, JS, HTML
    • dependency linking
    • linting (error/style checking)
    • testing
  • Gulp is another popular JS task runner.

Webpack

  • A JavaScript module bundler.
  • Generates static assets with only the dependencies needed.
💡
Why It Matters:: Modern front ends are many files and many dependencies. Package managers track what you depend on, task runners automate the repetitive chores, and bundlers ship only what the page actually needs.

Worked Scenarios & Calculations

Scenario 1 • Picking the Right Design Artefact

Picking the Right Design Artefact

A team debates how to show a new checkout page.

  • Early on, they sketch a wireframe — boxes for item list, price and Pay button — to agree on structure and content.
  • The visual designer then produces a mockup with brand colours and typography.
  • Finally, they build a prototype where clicking Pay actually moves to a confirmation screen, so they can watch real users interact. Each artefact answers a different question: what is on the page, what does it look like, and how does it behave.
Scenario 2 • Why Script Placement Matters

Why Script Placement Matters

A page puts a large <script src="..."> in the <head>.

  1. The browser must download and execute that script before it can continue rendering.
  2. Result: the page stays blank longer — JS in the head delays rendering. The fix from the lecture: import JS in the body, conventionally just before the closing body tag, so the visible content paints first.
Scenario 3 • The SPA Trade-off

The SPA Trade-off on a Budget Phone

A team builds a Single Page Application.

  • Pros: a faster interface, simpler data binding, reusable components, easy CDN hosting and less backend load.
  • Cons: more work and more experienced developers, a rapidly evolving framework frontier, and a workload pushed into the browser. On a low-spec mobile device, that last con dominates — the same app that feels instant on a laptop may feel sluggish on a cheap phone.
Scenario 4 • Taming a Front

Taming a Front End with Build Tools

A project has many JS libraries, large CSS files and images.

  1. Bower fetches each library and its dependencies, recorded in bower.json so updates are easy.
  2. Grunt automates the boring chores: minify images/CSS/JS/HTML, link dependencies, lint for errors and run tests.
  3. Webpack bundles the JavaScript modules, emitting static assets that include only the dependencies actually needed.
Scenario 5 • Cross-Browser Testing in Practice

Cross-Browser Testing in Practice

An app "must run" on a specific browser.

  1. Never assume it works — test on that exact browser.
  2. Test other browsers on your local machine where possible.
  3. Emulate other operating systems with virtual machines, remembering that virtualisation can itself introduce bugs.
  4. For high confidence, use professional cross-compatibility services that test on real hardware and devices.

Potential Exam Focus & Practice

Progress: 0 / 19 Mastered
Q1
What is the frontend and what layer does it occupy?
Answer:
The frontend is the presentation layer — the interface between the user and the backend (data access, computations), consisting of software components that execute in the browser.
Q2
What makes a good user interface?
Answer:
It is not art; effective interfaces are sensible, consistent and structured. Users shouldn't need instructions, common tasks should take simple steps, every click matters, and the aim is to make the user happy.
Q3
Contrast the UX designer and the UI designer.
Answer:
The UX designer is an interaction designer who charts the user pathway, plans information architecture, and is expert in wireframes, prototypes and research. The UI designer is a visual designer who chooses colour and typography, plans the visual aesthetic, and is expert in mockups, graphics and layouts.
Q4
Distinguish wireframe, mockup and prototype.
Answer:
A wireframe shows the information to display and outlines structure/layout — a blueprint for each page. A mockup shows the visual appearance and is more detailed than a wireframe. A prototype shows how the page works and can be low or high fidelity; users should be able to interact with it.
Q5
Why must you test across browsers, and how?
Answer:
Each browser, browser version and OS differs, as do screen resolutions and mobile devices, so you must consider interoperability and never assume it works. Test on your local machine, emulate operating systems with virtual machines (caveat: virtualisation can introduce bugs), and use professional services that test on real hardware. caniuse.com is a quick compatibility reference.
Q6
Should you support all browsers?
Answer:
No — you probably shouldn't. At the start of a project decide what you will and won't support based on your intended customer base; know your audience.
Q7
What are web components and what properties do they offer?
Answer:
Custom HTML elements and the technologies that facilitate them — any reusable blob of HTML, CSS and JS. They offer reactivity, encapsulation, modularity and reusability.
Q8
What is the DOCTYPE and what are the rules for it?
Answer:
It is not an HTML tag but an instruction to the browser about the HTML version. It must be the very first line. <!DOCTYPE html> is the HTML5 form and masquerades as HTML4 for older browsers; HTML4 DOCTYPEs are more complex.
Q9
What is the difference between the HEAD and BODY tags?
Answer:
HEAD contains meta information separate from the content; its elements are not rendered and the title tag is mandatory. BODY contains the elements rendered to the view, is mandatory, and should never have its end tag skipped; scripts in the body conventionally go just before the closing body tag.
Q10
Why does placing JavaScript in the head matter?
Answer:
JS imported in the head delays rendering of the page until the scripts are loaded; importing it in the body can speed up page loading.
Q11
What is the DOM and how is it used?
Answer:
The Document Object Model treats an HTML document as a tree-like structure of objects. JavaScript manipulates it — the majority of JS usage in the browser — finding elements by id, tag name or class name, and changing content, attributes, dynamic content or writing to the output stream.
Q12
Give the CSS rule syntax and explain each part.
Answer:
selector { property:value; } — the selector points to the element to style, the property is the attribute to modify, the value is the new value, and {} is the declaration block that can hold multiple property/value pairs.
Q13
Compare CSS element, class and id selectors.
Answer:
Element selects by tag; a class may be applied to multiple elements and an element may have multiple classes; an id selects only one element, and an element may have only one id.
Q14
What are media queries and why use a CSS framework?
Answer:
Media queries apply CSS conditionally when an @media condition is true, which is great for responsive pages. The lecture's advice is that the best CSS is written by someone else — use a framework such as Bootstrap, Foundation or Materialize, choosing carefully because switching is laborious; consider aesthetics, grid system, community support and cross-browser compatibility.
Q15
Characterise JavaScript and list its early issues.
Answer:
JavaScript is high-level, dynamic, un-typed and interpreted, and manipulates the DOM. Early issues included weird equality/automatic conversion, the behaviour of this, lack of a type system, weak static analysis and poor tooling, and lack of a module system. It is constantly evolving and has improved significantly.
Q16
What is TypeScript and what does it add?
Answer:
An open-source superset of JavaScript adding optional static types, developed by Microsoft for large web applications and transpiled back to JavaScript. It adds types, modules/namespaces and classes.
Q17
What are the pros and cons of Single Page Applications?

Q18
What is AJAX and how has it evolved?
Answer:
Asynchronous JavaScript and XML updates a page with external data without a full refresh and is fundamental to the modern web. Traditionally XHR was clunky and cumbersome, jQuery improved it, and native browser APIs such as Fetch are an option where supported.
Q19
What do Bower, Grunt and Webpack each do?
Answer:
Bower is a package manager for front-end HTML/JS/CSS libraries (like pip for the frontend), installed via npm and documented in bower.json. Grunt is a JavaScript task runner (like a Makefile for HTML front ends) installed via npm that automates minification, dependency linking, linting and testing (Gulp is an alternative). Webpack is a JavaScript module bundler that generates static assets with only the needed dependencies.
