Front-end Development: Building for the Browser

How the presentation layer of a web application is built. Starting from user experience and design artefacts, this guide works through the browser as a platform, HTML markup and the DOM, CSS presentation and selectors, JavaScript and its ecosystem, and the tooling used to manage front-end dependencies and assets.

Read this first: The frontend is the presentation layer — everything the user sees and touches. It lives in the browser and is built from three technologies that each own one concern: HTML describes what is in the document (structure), CSS describes what it looks like (presentation), and JavaScript describes how it behaves (behaviour). Hold that separation of concerns in mind and every later topic — components, frameworks, tooling — slots into place.

The Frontend and the Presentation Layer

The frontend is the presentation layer: the software the user actually sees, running inside the browser, acting as the interface between the user and the backend.

The frontend is the presentation layer of an application. It is the interface between the user and everything behind the scenes — the backend, which handles data access, computation and storage.

Everything in this lecture concerns the software components that execute in the browser. Unlike backend code that runs on a server you control, frontend code runs on the user's machine, in a program you did not write, on hardware you cannot see.

💡
Why it matters: Because the frontend is the user's only window into your system, its quality determines whether the application feels good to use. A brilliant backend behind a clumsy interface is a clumsy product.
ℹ️
Note: "Mobile is a magnifying glass for your usability problems." A small screen strips away space and makes poor design choices — cramped layouts, tiny targets, unclear navigation — impossible to hide.
🤔
Pause & predict: Name three things the backend does that the user never directly interacts with. Why does that division of labour make the frontend the "presentation" layer?

Good User Experience

Building an effective user interface is not an art — it is an engineering discipline with rules, and the rules are sensible, consistent and structured.

Building effective user interfaces is not art. Effective interfaces are sensible, consistent and structured. The encouraging consequence: if you can develop software, you can build an effective user interface — provided you dedicate the time to it.

What good UX feels like

  • Users shouldn't need instructions.
  • Simple steps to achieve common tasks.
  • Every click matters.
  • Make the user happy.
🧠
Memory hook: Good design is invisible. If a user has to read a manual to send an email, the design failed — not the user.

The clearest statement of the mindset comes from Steve Jobs:

> "Most people make the mistake of thinking design is what it looks like. People think it's this veneer – that the designers are handed this box and told, 'Make it look good!' That's not what we think design is. It's not just what it looks like and feels like. Design is how it works."

Learn from failure and success

  • Bad doors are everywhere. Everyday physical objects (doors you push when you should pull) show how poor affordances confuse people. The same failure happens in software.
  • LingsCars is a classic example of an interface that prioritises noise over clarity.
  • Google Inbox, Medium and Slack are held up as examples of interfaces that get it right: clear, calm and task-focused.

Design Artefacts: Wireframes, Mockups and Prototypes

Before writing code you make three progressively richer artefacts — wireframe, mockup, prototype — each answering a different design question.

Professional design proceeds through three artefacts. They differ in what question they answer and in how detailed they are.

Wireframe — An outline of the structure and layout of components. It shows the information that will be displayed and acts as a blueprint for each page that will be implemented.
Mockup — Shows the visual appearance of the page. It should be more detailed than a wireframe — colour, typography, imagery and spacing.
Prototype — Shows how the page works. It can be low or high fidelity; the focus is on behaviour, and users should be able to use and interact with it.

The Browser Landscape and Cross-Compatibility

There is no single "browser" — every browser, version, operating system and screen size behaves differently, so you must plan for interoperability and test deliberately.

Not all browsers are created equal

  • Each browser is different.
  • … and so is each version of a browser.
  • … and each version is different on each operating system.
  • … and don't forget different screen resolutions.
  • … or mobile devices.

You must consider interoperability between browsers, browser versions and operating systems when writing web applications.

Can I Use? — caniuse.com provides a quick reference on browser compatibility for features and limitations. Check it before you commit to a feature.

Cross-compatibility testing

  • If our application must run on a certain browser, we must test it on that browser. Never assume it will work.
  • Different browsers can be tested on your own local machine.
  • Different operating systems can be tested by emulating them with virtual machines — but note that virtualisation can introduce bugs of its own.
  • Many professional tools and services exist for testing cross-compatibility, often with the ability to test on real hardware and devices (e.g. Windows Phone).

You don't need to support ALL browsers

  • You don't need to (and probably shouldn't) support all browsers, versions and operating systems.
  • At the start of your project, make a decision about what you will and won't support.
  • Base that decision on your intended customer base — know your audience.
💡
Why it matters: Supporting everything multiplies your testing burden and slows delivery. A deliberate, audience-based support matrix is a design decision, not laziness.
⚠️
Common trap: "It works on my machine" is not evidence. Browsers, versions and operating systems each vary, so an untested browser is an unsupported browser.

Design Practice: Responsive and Inclusive Design

Two design practices keep a single site usable everywhere and by everyone: responsive design and inclusive design.

Responsive design

Responsive design makes one document adapt its layout to the device and viewport it is displayed on (see media queries later in this guide). It is how a page stays usable from a phone to a large desktop.

Inclusive design

Inclusive design is design that does not exclude on the basis of:

  • Disability, religion, gender identity
  • Race, language, sexual orientation
  • Ethnicity, pronunciation, age
💡
Why it matters: An interface that only works for users who look, sound or think like its author excludes real customers. Inclusive design widens your audience and is an ethical baseline.

Web Components

A web component is any reusable blob of HTML, CSS and JavaScript that behaves like a custom HTML element.

A web component is:

  • Custom HTML elements, plus the technologies that facilitate their development.
  • Components on the web.
  • Any reusable blob of HTML, CSS and JavaScript.

Web components exist to deliver four properties:

  • Reactivity — it updates in response to changes.
  • Encapsulation — its internals are hidden from the rest of the page.
  • Modularity — it is a self-contained unit.
  • Reusability — it can be dropped into many pages.
🧠
Memory hook: Components give you R·E·M·R — Reactivity, Encapsulation, Modularity, Reusability.
ℹ️
Note: Think of a component as a custom tag you define once (e.g. a <user-card>) and then reuse everywhere without rewriting its markup, styles or logic.

HTML Markup and Document Structure

HTML is an evolving markup language that gives a document its structure; a valid page starts with a DOCTYPE and organises content into head (metadata) and body (rendered content).

HTML versions

HTML is a constantly evolving specification. A summarised timeline:

  • 1997: HTML 3.2
  • 1999: HTML 4.01
  • 2007: HTML5 draft published
  • 2014: HTML5 published as a W3C Recommendation

Browsers implement subsets of the HTML specifications. HTML5 added features such as the <audio> and <video> elements and the data, time and color input types.

A minimal HTML5 document

A simple HTML5 document implementing CSS and JavaScript:

<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="utf-8">
    <title>My Page</title>
    <link rel="stylesheet" href="styles.css">
  </head>
  <body>
    <h1>Hello</h1>
    <p>This is a paragraph.</p>
    <script src="app.js"></script>
  </body>
</html>

The DOCTYPE

  • It is not an HTML tag. It is an instruction to the browser about which version of HTML the page uses.
  • It must be the very first line in your document.
  • The HTML5 DOCTYPE declaration will masquerade as HTML4 for older browsers.
  • HTML 4 DOCTYPES are more complex, for example:
<!DOCTYPE HTML PUBLIC "-//W3C//DTD HTML 4.01//EN" "http://www.w3.org/TR/html4/strict.dtd">

versus the HTML5 form:

<!DOCTYPE html>

Elements and core tags

Common elements include <html>, <head>, <title>, <body>, <h1> and <p>.

  • <html> encapsulates the entire HTML document and can specify the language used in the document.
  • <head> contains meta information separate from the content. Its elements are not rendered in the view. CSS files are generally imported here. JS imported here delays rendering until the scripts are loaded; JS can instead be imported in the body to speed up page loading. The <title> tag is mandatory in this section.
  • <body> contains the HTML elements to be rendered to the view. If placing script tags in this section, convention is to place them just before the closing body tag. The body is a mandatory tag. Never skip the end tag. Empty elements such as <br> have no closing tag.

Attributes

Example usages:

<a href="https://www.sydney.edu.au/">Visit USYD</a>
<img src="img_girl.jpg" alt="A girl">
<p style="color:red;" title="I'm a tooltip">This is a red paragraph.</p>

Rules of thumb:

  • Always use lowercase attributes.
  • Always quote attribute values.
  • Single or double quotes are both acceptable — be consistent.
⚠️
Common trap: The DOCTYPE is not a tag, and putting it anywhere other than the first line can trigger quirks behaviour. Also remember the <title> and <body> are mandatory.
✅
Exam tip: If asked how to speed up page load, a classic answer is to move <script> tags to just before the closing </body> so they don't block rendering.

The DOM

The Document Object Model turns an HTML document into a tree of objects that JavaScript can read and change — and that manipulation is the bulk of JavaScript's work in the browser.

  • The Document Object Model (DOM) treats an HTML document as a tree-like structure of objects.
  • Manipulating the DOM from JavaScript is possible, and it forms the majority of JavaScript usage in the browser.

Finding elements

You locate elements in the DOM by:

  • Id — getElementById
  • Tag name — getElementsByTagName
  • Class name — getElementsByClassName
  • … and more.

What a custom element does

An HTML custom element consists of:

  • Changing HTML content
  • Updating values of an attribute
  • Dynamic HTML content (e.g. Date())
  • Writing directly to the HTML output stream

Worked example: what gets logged?

A custom element defines lifecycle callbacks. Given the options —

  • a. 'connected', 'disconnected'
  • b. Nothing
  • c. 'disconnected'
  • d. 'connected'

— the correct answer is a. 'connected', 'disconnected': when the element is inserted into the document the connected callback fires, and when it is removed the disconnected callback fires.

🧠
Memory hook: The DOM is a tree; JavaScript is the gardener that can add, move, relabel or prune branches.
🤔
Pause & predict: If an element is created but never inserted into the document, which callbacks fire? (Answer: neither — nothing is logged.)

CSS: Cascading Style Sheets

CSS describes how an HTML document is presented, cleanly separating "what's in the document" from "what it looks like".

  • CSS describes the presentation of an HTML document.
  • It enables a separation of concerns between "what's in a document" (HTML) and "what a document looks like" (CSS).
  • Similar to HTML, CSS has different versions and varying support across browsers.
  • CSS can be difficult to get right but is 100% worth it.

CSS syntax

selector { property: value; }
  • Selector — points to the HTML element the style should apply to.
  • Property — the attribute that should be modified.
  • Value — what the value should be updated to.
  • {} — the declaration block; it can contain multiple property/value pairs.
💡
Why it matters: Keeping structure (HTML) and presentation (CSS) separate means you can restyle an entire site by editing stylesheets rather than rewriting markup — a maintainability win.
ℹ️
Note: The word cascading refers to the rule system that decides which declaration wins when several apply to the same element.

CSS Selectors and Media Queries

Selectors decide which elements a rule targets, and media queries decide when a rule applies so pages can respond to different devices.

Selectors

Element selector — selects the HTML element by name, e.g. targets body, applies a background colour and defines a font for text:

body { background-color: #f5f5f5; font-family: Arial, sans-serif; }

Class selector — any elements with the dog class get bolded, blue font:

.dog { font-weight: bold; color: blue; }
  • A class may be applied to multiple elements.
  • Elements may have multiple classes.

ID selector — the first element with the dog-name id becomes underlined with red font:

#dog-name { text-decoration: underline; color: red; }
  • An id is used to select only one element.
  • An element may have only one id.
SelectorSyntaxScope
ElementpEvery element of that type
Class.dogMany elements; an element may have several classes
ID#dog-nameExactly one element; one id per element

Media queries

  • Media queries let us customise how our document displays on a range of devices by applying conditions to CSS rules.
  • CSS is applied if the @media query returns true.
  • They are great for creating responsive pages.
⚠️
Common trap: Confusing class (.) and id (#). Classes are reusable and many-to-many; ids are unique and one-per-element.
🧠
Memory hook: . = class = many; # = id = one.
🤔
Pause & predict: Write the selector you would use to style every element that has the class card, and a separate rule for the single element with id hero.

CSS Frameworks

The best CSS is written by someone else — use a framework, but choose it deliberately because switching later is expensive.

The best CSS is written by someone else. Use a framework.

Popular frameworks:

  • Bootstrap
  • Foundation
  • Materialize

Choose your framework carefully — switching between frameworks can be laborious and time-consuming. When choosing, consider:

  • Aesthetics
  • Grid system
  • Community support
  • Cross-browser compatibility
✅
Exam tip: The four framework-selection criteria — aesthetics, grid system, community support, cross-browser compatibility — are easy marks. Memorise them.

JavaScript: The Language of the Browser

JavaScript is a high-level, dynamic, un-typed, interpreted language that makes pages dynamic by manipulating the DOM.

  • JavaScript is a high-level, dynamic, un-typed, interpreted programming language.
  • It allows pages to become dynamic by manipulating the HTML DOM with code.
  • Alongside HTML and CSS, it forms a fundamental core of today's modern web.
  • Learning to appreciate JavaScript will improve your applications and make you more employable.

JavaScript's historical issues

Early versions were hard to develop in because of:

  • Weird equality / automatic conversion.
  • Behaviour of this.
  • Lack of a type system.
  • Weak static analysis support and poor tooling.
  • Lack of a module system.

JavaScript is constantly evolving and has improved significantly in more recent versions. JavaScript isn't perfect but it's here to stay.

💡
Why it matters: The listed weaknesses are exactly what TypeScript and modern frameworks were created to fix — knowing the problems explains the tools.
🧠
Memory hook: The big five complaints: equality, this, no types, weak tooling, no modules.

TypeScript, jQuery, SPAs and AJAX

The JavaScript ecosystem adds static types (TypeScript), a convenience library (jQuery), a whole app style (SPAs) and a data-fetching technique (AJAX).

TypeScript

  • An open-source programming language that implements a superset of JavaScript while adding optional static types.
  • Developed and maintained by Microsoft and designed for the development of large web applications.
  • Transpiled back to JavaScript (so browsers can run it).
  • Adds support for: types, modules/namespaces, and classes.

jQuery

  • "The Swiss army knife" — commonly used on web pages.
  • Highly supported with an active community.
  • Likely to have everything you need to interact with the DOM.
  • Great for cross-platform support.
  • Becoming less popular because modern frameworks supersede its functionality and browsers implement native versions of much of the library.

Single Page Applications (SPAs)

  • Load a single HTML document and use JS to update the user's view without a hard refresh.
  • Move a lot of work to the client side (browser) and typically create a smoother, more fluid user experience, allowing for significantly more powerful web applications.

Pros:

  • Provide a faster interface.
  • Encourage separation of concerns.
  • Reusable.
  • Allow for "serverless" browser applications.
  • Simpler binding of data to views.
  • Easy to serve from a CDN, decreasing user load time.
  • Removes load from backend servers.

Cons:

  • Typically require more work.
  • Typically require more experienced developers due to complexity.
  • New frontier — frameworks are rapidly evolving.
  • Push workload into the browser, which is bad for low-spec/mobile devices.

AJAX (Asynchronous JavaScript and XML)

  • Allows the page to be updated with external data without a full refresh.
  • AJAX is a fundamental aspect of the modern web.
  • Traditionally we used XHR (XMLHttpRequest), which can be clunky and cumbersome.
  • JavaScript libraries like jQuery improved the situation.
  • Native browser APIs such as Fetch are also an option where supported.

Popular JavaScript frameworks

  • Angular (Google)
  • React (Facebook)
  • Ember
  • Backbone.js
🧠
Memory hook: Angular = Google, React = Facebook (Meta). Two free recall marks.
🤔
Pause & predict: An SPA loads once and never hard-refreshes. Where does the extra work go, and which users does that hurt most?

Front-end Development Tools

Three Node.js-based tools keep front-end projects manageable: Bower for dependencies, Grunt for tasks, and Webpack for bundling.

Bower — a package manager for the web

  • Imagine pip but for frontend HTML, JS and CSS libraries.
  • A Node.js application, installed via npm.
  • Can fetch packages and their dependencies.
  • Much easier to update packages.
  • Document your dependencies in a bower.json file.

Grunt — a JavaScript task runner

  • Similar to a Makefile but for HTML frontends.
  • Also a Node.js application, installed via npm.
  • Automates boring, repetitive tasks:
  • minification of images, CSS, JS and HTML
  • dependency linking
  • linting (error/style checking)
  • testing
  • Gulp is another popular JS task runner.

Webpack

  • A JavaScript module bundler.
  • Generates static assets with only the dependencies needed.

Practice Questions

Look away from the page first — retrieval is what builds memory.

Answer, reveal, then tick “Mastered”. Your progress is saved.
Q1

What is the frontend, and what role does it play relative to the backend?

Answer: The frontend is the presentation layer of an application. It runs in the browser and serves as the interface between the user and the backend, which handles data access, computations and storage.
Q2

What three properties characterise an effective user interface, and what does that imply about building one?

Answer: Effective interfaces are sensible, consistent and structured. Because UI design is not art but a discipline, any capable software developer can build an effective interface if they dedicate the time.
Q3

Distinguish a wireframe, a mockup and a prototype by the question each answers.

Answer: A wireframe answers "what information is displayed and how is it laid out?" (structure, a blueprint). A mockup answers "what does it look like?" (visual appearance, more detailed than a wireframe). A prototype answers "how does it work?" (behaviour; low or high fidelity and interactable).
Q4

What four things distinguish one browser environment from another, and how should you test for them?

Answer: Each browser is different; each version differs; each version differs on each operating system; screen resolutions and mobile devices vary. Test on the actual target browser — never assume it will work — using your local machine, virtual machines for other OSes (noting virtualisation can introduce bugs), or professional services that test on real hardware and devices.
Q5

Must you support every browser? Justify your answer.

Answer: No. You don't need to (and probably shouldn't) support all browsers, versions and operating systems. At the start of a project, decide what you will and won't support based on your intended customer base — know your audience.
Q6

What is inclusive design, and give at least four grounds on which design must not exclude.

Answer: Inclusive design does not exclude on the basis of disability, religion, gender identity, race, language, sexual orientation, ethnicity, pronunciation or age. (Any four of these are correct.)
Q7

What is a web component, and what four properties does it provide?

Answer: A web component is any reusable blob of HTML, CSS and JavaScript (custom HTML elements and their supporting technologies). It provides reactivity, encapsulation, modularity and reusability.
Q8

What is the DOCTYPE, and what belongs in the <head> versus the <body>?

Answer: The DOCTYPE is not an HTML tag but an instruction to the browser about which HTML version the page uses; it must be the very first line, and <!DOCTYPE html> is the HTML5 form that masquerades as HTML4 for older browsers. <head> holds non-rendered meta information, generally imports CSS and must contain a <title>; <body> holds the rendered elements and is mandatory. Scripts in <head> delay rendering, so they are conventionally placed just before </body>.
Q9

What is the DOM, and name three ways JavaScript finds elements in it?

Answer: The DOM treats an HTML document as a tree-like structure of objects; manipulating it from JavaScript forms the majority of JavaScript's browser usage. Elements are found by id (getElementById), tag name (getElementsByTagName) and class name (getElementsByClassName).
Q10

State the CSS syntax and define each part, then contrast class and id selectors and explain media queries.

Answer: Syntax is selector { property: value; } — the selector points to the element, the property is the attribute to modify, the value is the new setting, and {} is the declaration block that can hold multiple pairs. A class (.name) may apply to multiple elements and an element may have multiple classes; an id (#name) selects only one element and an element may have only one id. Media queries apply CSS only when an @media condition returns true, customising display across devices for responsive pages.
Q11

What are the four criteria for choosing a CSS framework, and name three popular frameworks.

Answer: Consider aesthetics, grid system, community support and cross-browser compatibility. Popular frameworks include Bootstrap, Foundation and Materialize. Choose carefully because switching frameworks is laborious and time-consuming.
Q12

Describe JavaScript's language characteristics, list its historical weaknesses, and say what TypeScript adds.

Answer: JavaScript is high-level, dynamic, un-typed and interpreted, making pages dynamic by manipulating the DOM. Historical issues included weird equality/automatic conversion, confusing behaviour of this, no type system, weak static analysis and poor tooling, and no module system. TypeScript, an open-source superset of JavaScript by Microsoft, adds optional static types, modules/namespaces and classes, and is transpiled back to JavaScript.
Q13

Define a single page application and AJAX, and give two pros and two cons of SPAs.

Answer: An SPA loads a single HTML document and updates the user's view with JavaScript without a hard refresh; AJAX (Asynchronous JavaScript and XML) updates a page with external data without a full refresh, traditionally via XHR, improved by jQuery, or natively via Fetch. SPA pros include a faster interface, separation of concerns, reusability, serverless browser apps, simpler data binding, easy CDN serving and reduced backend load; cons include more work, needing more experienced developers, rapidly evolving frameworks, and pushing workload into the browser (bad for low-spec/mobile devices).
Q14

What are Bower, Grunt and Webpack, and what do they have in common?

Answer: Bower is a frontend package manager (like pip for HTML/JS/CSS libraries, dependencies in bower.json). Grunt is a JavaScript task runner (like a Makefile for frontends, automating minification, dependency linking, linting and testing). Webpack is a JavaScript module bundler producing static assets with only the needed dependencies. They are all Node.js applications installed via npm.
