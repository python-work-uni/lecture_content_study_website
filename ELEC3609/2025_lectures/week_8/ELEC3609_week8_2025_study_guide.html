Linux, Networking and the Cloud: From Servers to AWS Deployment

This week explains the operating system that runs the internet and the cloud infrastructure you deploy onto. It covers Linux and its user/permission model, remote administration with SSH, then the AWS building blocks (EC2, EBS, VPC, RDS, Route 53, EKS/ECS), networking concepts (TCP/UDP ports, firewalls, security groups, load balancers, Elastic IPs), and finally the server application stack — web server, application interface, database — plus why data must live on a separate volume.

Read this first: Think of deploying a website as building a house on rented land. Linux is the land and its rules; SSH is your only door key; AWS provides the land (EC2), the shed for storage (EBS), the address (Route 53), the fences (VPC/security groups), and the traffic cop (ELB); and the server applications (nginx → uWSGI → database) are the rooms you furnish inside. Every concept below exists to answer one question: how does a request travel from a user's browser to your code and data, safely?

Linux: The Operating System Behind the Internet

Linux is an open-source UNIX-like operating system whose defining feature is the kernel, and it now runs most of the world's servers.

Linux is an open-source, UNIX-like operating system. Its defining feature is the Linux kernel — the core component that manages hardware, processes and memory. It was released in 1991 by Linus Torvalds.

A Linux distribution (or "distro") is a collection of software packaged together into a complete, ready-to-use operating system. A distribution bundles, for example:

  • Package managers — such as apt-get or pacman, used to install and update software.
  • Window managers — such as GNOME or i3, which control the graphical desktop.
  • Text editors and other user-facing tools.
💡
Why it matters: Linux is the most widely installed general-purpose OS in the world. The main driver is the proliferation of Android (which is built on Linux). More importantly for this course, it is the dominant OS for web servers, with over 90% market share. That is why a web master must be fluent in Linux.
🧠
Memory hook: Kernel = the engine. Distribution = the whole car (engine + seats + dashboard + wheels). You buy a distro; the kernel is what makes it Linux.
🤔

Linux Users and the Principle of Least Privilege

Every program runs as some user, and choosing the right user is the first line of defence against a compromised program.

The root user (also called the Superuser) is the most privileged user on a Linux system. The root user can do anything on the system. Other users may hold a wider or narrower variety of privileges than each other.

Key facts about users:

  • Programs execute as a particular user. A running program inherits that user's privileges.
  • If a program requires special privileges, it may need to execute as the root user.
  • The command ps aux lists all processes running on the system and the user each is running as.

Program-Specific Users

Usually a program does not need root access. It should run as a different, dedicated user. The security benefit is containment: if the program is compromised, the attacker can only perform actions that that user could perform — not the whole system.

Common examples:

  • Web servers, including nginx, usually run as the user www-data.
  • MySQL programs, including mysqld, usually run as the user mysql.
  • Linux systems often include a nobody user, for programs that need almost no privileges at all.
💡
Why it matters: This is the least privilege principle in action. Give each program only the access it genuinely needs, so a single break-in cannot escalate into full system control.
⚠️
Common trap: Do not run your web server or database as root just because it is "easier". If it is compromised, the attacker gains full control of the machine.

Capabilities: Splitting Root Into Fine-Grained Privileges

Capabilities break the all-or-nothing power of root into small, assignable units so a process gets exactly the privileges it needs.

In the classic UNIX/Linux model, root (UID 0) has all privileges. The problem: if a process is compromised while running as root, the attacker gains full control of the system.

Capabilities solve this by splitting root privileges into smaller, fine-grained units. Each process can be assigned only the subset it really needs. Examples of individual capabilities:

CapabilityGrants
CAP_NET_BIND_SERVICEBind to privileged network ports (e.g. port 80)
CAP_SYS_ADMINMount filesystems and other system administration
CAP_DAC_OVERRIDEBypass file read/write/execute permission checks
CAP_NET_RAWCreate raw network sockets
CAP_CHOWNChange ownership of files

Why capabilities improve security

  • Least privilege principle — grant only what is needed.
  • Damage containment — a compromise affects fewer operations.
  • Reduced attack surface — fewer privileged operations are exposed to attack.

Worked example: running nginx

  • Traditionally: nginx needed root just to bind port 80.
  • With capabilities: run nginx as an unprivileged user but grant only CAP_NET_BIND_SERVICE.
  • If nginx is hacked, the attacker cannot create raw sockets (CAP_NET_RAW), mount filesystems (CAP_SYS_ADMIN), or change file ownership (CAP_CHOWN).
🧠
Memory hook: Root is one giant master key. Capabilities are a ring of small keys — hand out only the ones a process actually needs.

Secure Shell (SSH): Remote Access Done Safely

SSH is the encrypted way to get a terminal on a remote machine, and it is the essential tool for anyone managing a Linux server.

Secure Shell (SSH) is a secure replacement for the old Telnet protocol (Telnet sent everything, including passwords, in plain text). SSH lets a user access the shell or terminal on a remote machine. It is an essential tool for any web master because Linux is the dominant server platform on the internet.

The SSH server

  • The most common SSH server software is OpenSSH, which originates from the OpenBSD project.
  • An SSH server:
  • Listens for incoming connections on TCP port 22.
  • Authenticates connecting users using either passwords or public/private keys.

The SSH client

  • OpenSSH also provides a client — the client-side software that connects to the SSH server.
  • Alternatives exist per platform:
  • On Linux, stick with the default OpenSSH.
  • On Windows, PuTTY might be a better option.
💡
Why it matters: Because SSH is your only door into a remote server, it is also the primary target for attackers. Understanding its authentication model is a security skill, not just a convenience.

SSH Authentication: Keys, Signatures and known_hosts

SSH uses two independent key pairs — one for the server, one for each client — to encrypt the connection and prove identity without ever revealing a private key.

SSH provides both authentication and encryption. Logging in with a password is "the obvious way" — and it is bad practice. Instead, use SSH keys.

Public key cryptography and signatures

An encryption/decryption key pair is generated to provide effective authentication. Authentication works by demonstrating possession of the private key without revealing it.

  • Private key — held by you, never shared. Only you can sign a request with your private key.
  • Public key — shared publicly. Anyone can verify your signature using your public key.

Two sets of keys

1. Server keys — the server has its own key pair. It allows initial connections to be encrypted with its public key and lets clients authenticate the server. Only the server possessing the private key can read incoming connections. Server keys are typically stored as:

/etc/ssh/ssh_host_rsa_key
/etc/ssh/ssh_host_rsa_key.pub

When you first connect to a server you have never connected to before, you get a warning. Accepting it adds a new entry to your ~/.ssh/known_hosts file. By keeping track of known server public keys, clients minimise the potential for a man-in-the-middle (MITM) attack.

2. Client keys — each client has its own key pair, used to authenticate when connecting to the server. To authenticate a user (say myuser), the client proves ownership of a private key corresponding to an authorised public key. On the server, this file lives in the user's home directory:

/home/myuser/.ssh/authorized_keys

It contains the public keys of anyone authorised to connect as that user. The SSH server checks that a connecting client possesses the private key matching one of those public keys; if so, the connection is authorised.

🧠
Memory hook: known_hosts on the client remembers servers; authorized_keys on the server admits users.
⚠️
Common trap: Accepting a changed server key warning without checking can mean you are talking to an impostor. The warning exists precisely to stop MITM attacks.

The SSH agent

The SSH agent keeps your decrypted private key in memory so you type your passphrase once instead of on every connection.

  • ssh-agent is a program that stores the unencrypted SSH private key in memory.
  • SSH typically reads private keys from ~/.ssh/id_rsa, which is encrypted. Every time SSH runs, it would need the password to use the key.
  • To make this easier, the unencrypted version can be stored in memory by attaching it to a running process.
  • Rather than storing it in every SSH client process, we run ssh-agent once to store it for us.

Agent forwarding

  • ssh-agent runs on the client. As new SSH processes connect to it, they ask it to perform signing operations using the private key.
  • With the ForwardAgent option, you allow remote SSH clients to access your local ssh-agent process — and therefore your unencrypted private key.
⚠️
Common trap: Agent forwarding means a compromised remote host could use your key while you are connected. Enable it only when you trust the remote server.

Desktop editors like Atom or Notepad++ are graphical applications, so they cannot be used on a remote server over SSH. Instead you need a command-line text editor, typically used to edit configuration files on the remote server.

Package Managers and When to Install Manually

A package manager installs and updates software automatically, but you sometimes have no choice but to compile and install by hand.

Ubuntu's package manager is the Advanced Packaging Tool (APT). Installing software on servers via the package manager is easiest because it can automatically update the software for you.

However, you may need to install software manually when the package manager cannot do the job:

  • There is no package for the software you want.
  • The packaged software is out of date.
  • You want to install into a different location.
  • The software must be compiled with different options than the package manager provides.
💡
Why it matters: Automated package management is the norm, but production systems often need custom builds. Recognising the four situations above tells you when to reach for a manual install.

AWS Core Services: EC2, EBS, VPC, RDS, Route 53, EKS/ECS

AWS turns physical infrastructure into on-demand services, and each service maps to one part of the deployment puzzle.

Amazon Web Services (AWS) is an extremely popular cloud hosting provider. Using AWS removes the need to set up dedicated hardware to host a website, and it often takes care of software installation and configuration. AWS provides a wide range of services that assist in building website infrastructure.

Compute and storage

Elastic Compute Cloud (EC2) — provides access to server instances. It is the most common and fundamental service in the AWS suite, and you must use it for your project deployment. EC2 instances can be created in one of many availability zones (AZs) located in various regions of the world.

Elastic Block Store (EBS) — provides hard drive volumes that can be attached to EC2 instances. Useful for separating data storage from the server that executes your software. When attaching an EBS volume to an EC2 instance, both the volume and the instance must be in the same Availability Zone.

Databases and DNS

Relational Database Service (RDS) — provides managed database servers. Useful for having a scalable, backed-up version of your data. Supports: Aurora, PostgreSQL, MySQL, MariaDB, Oracle Database and SQL Server.

Route 53 — provides the ability to route requests to AWS infrastructure, e.g. www.example.com => 53.96.54.23. It operates a Domain Name System (DNS) web service.

Networking and orchestration

Virtual Private Cloud (VPC) — provides support for network segregation and greater control over EC2 instances. Very useful for web infrastructure, but its configuration can be complex. It is not necessary for the project — instead you will use the default VPC created by AWS.

  • EC2-VPC: using a VPC within EC2.
  • EC2-Classic: not using a VPC.

Amazon Elastic Kubernetes Service (EKS) — provides a managed Kubernetes service. It maintains the availability and scalability of the Kubernetes control plane and integrates with other AWS technologies.

Amazon Elastic Container Service (ECS) — provides a managed container orchestration service. It is Amazon's solution to Kubernetes and also integrates with other AWS technologies.

🧠
Memory hook: EC2 = computer, EBS = hard drive, RDS = database, Route 53 = phone book, VPC = private network, EKS/ECS = container conductors.

Networking Foundations: OSI Model, TCP and UDP Ports

Ports let many applications share one host, and TCP versus UDP determines whether delivery is guaranteed or merely best-effort.

All the software we run responds to network requests, so understanding networking is necessary.

The OSI Model

The OSI Model is a way to conceptualise network systems, with each layer being an abstraction of the previous one. You should be quite familiar with it to understand how technologies interact. Relevant layers here:

  • Layer 3 — where public IPs live.
  • Layer 4 — where TCP/UDP ports live.

TCP ports

Most web software communicates via the Transmission Control Protocol (TCP). TCP:

  • Establishes an end-to-end connection.
  • Ensures delivery of packets in the order they were sent.

Applications "listen" on a particular TCP port. This lets multiple applications run on the same host, each listening on a different port. Any application can choose any port, but there are standard port numbers used for particular application types.

Whenever a network service starts on a host, it attempts to listen on a particular port. Only one running application may listen to a port at a time.

UDP ports

The User Datagram Protocol (UDP) is a connectionless protocol. It is a "best-effort" protocol and makes no guarantees that packets arrive in order — or arrive at all. UDP has its own separate set of ports: TCP port 80 is different from UDP port 80.

TCPUDP
ConnectionConnection-oriented (end-to-end)Connectionless
DeliveryGuaranteed, in orderBest-effort, no guarantees
UseMost web softwareReal-time / low-overhead traffic
🧠
Memory hook: TCP is a registered parcel with tracking; UDP is a postcard that might never arrive.

Firewalls, Security Groups, Load Balancers and Elastic IPs

Firewalls decide which traffic is allowed in, and AWS layers load balancing and stable addressing on top for production.

Firewalls

A firewall is a security system that can allow or disallow network traffic to pass according to a set of rules. Firewalls come in many shapes:

  • Your home router — makes decisions about incoming/outgoing traffic and prevents attackers from gaining access to your network.
  • Software firewalls — run on a host machine and provide rules about the traffic allowed to enter that host.

AWS Security Groups

AWS Security Groups (SGs) are sets of firewall rules applied to EC2 instances. When first configuring an EC2 instance you can either create a new security group or add the instance to an existing one.

To configure a security group you must specify:

  • Protocol: TCP / UDP / ICMP.
  • Port(s): the TCP/UDP port(s) the rule applies to.
  • Source: which source IP address(es) the rule applies to.

The rules are a whitelist — any packet not matching a rule is automatically dropped. For development, it is useful to add a rule for SSH access from any source (0.0.0.0/0).

Elastic Load Balancer (ELB)

Provides a load balancing service for EC2 instances. Useful for production websites, allowing for easy horizontal scaling. For your project you should learn to use ELB, configuring it for your deployment.

Elastic IPs

When you start an EC2 instance, AWS assigns it a public IP address. If you restart the instance, it can be reassigned to a different IP, which makes updating dependent configurations (such as DNS records) difficult. To maintain a consistent IP address across restarts, assign the instance an Elastic IP — once assigned, the instance will always have that IP whenever it is created.

⚠️
Common trap: 0.0.0.0/0 opens a port to the entire internet. It is fine for SSH during development but is a serious risk in production.

The Server Application Stack

Deploying a website means installing four cooperating layers: a web server, an application interface, the web application, and a database.

To deploy a website properly, you must configure several applications on your server. In particular, install:

  1. A web server.
  2. An application interface.
  3. The web application.
  4. A database.

Web servers

A web server receives incoming HTTP requests, processes them, and usually provides an HTTP response. Common web server software includes Apache, Nginx and IIS.

Recommended: nginx. nginx (pronounced "engine-X") is a fast web server that can also act as a reverse proxy. It is recommended for the project due to its widespread use and ease of configuration. Crucially, nginx does not interpret web application code. Instead, we ask nginx to proxy_pass HTTP requests to the application interface.

Application interfaces

A web application interface provides a simple interface between the web server and the application server. It runs multiple application "workers" so the application can process requests concurrently.

WSGI is a specification for such an interface, implemented by the uWSGI software. uWSGI is designed for Python programs and has good support for Django.

Databases

Most web applications require persistent storage of data. You will most likely need a relational database management system (RDBMS). MySQL is recommended — feature-rich and relatively easy to use. PostgreSQL and MariaDB are acceptable alternatives.

Regardless of the RDBMS chosen, the rough setup steps are:

  1. Install the DB software.
  2. Configure users (username & password).
  3. Configure application code to use the DB, connecting with the username & password.
Browser→nginx (proxy_pass)→uWSGI application interface→Web application→RDBMS

Separating Data from Application Code

Always store data on a separate volume from the operating system and application code, so data survives and scales independently.

You should always separate your data from your application code. Typically this means configuring your database to save data to a separate volume from where your operating system and web application are installed.

If working on EC2, use a separate EBS volume for database storage. With the volume attached, configure your RDBMS to store data on the new volume (MySQL has documented steps for moving its data directory).

💡
Why it matters: Separation means you can grow storage, back up, or rebuild the server without risking the data — and it aligns with the AWS principle of decoupling storage from compute.
🧠
Memory hook: Code is replaceable; data is precious. Keep them on different volumes.

Putting It Together: Your Task

The deliverable is a deployed web application on AWS, wired together from the services and applications covered this week.

Your task ties the whole week together. You will deploy onto AWS, which means in practice:

  1. Launch an EC2 instance in an availability zone, using the default VPC.
  2. Configure a Security Group to whitelist the ports you need (including SSH for development).
  3. Optionally assign an Elastic IP so the address stays stable across restarts.
  4. Install and configure the server stack: nginx as the web server, a WSGI interface (uWSGI) for your Python application, and an RDBMS such as MySQL.
  5. Attach a separate EBS volume for database storage and point the RDBMS at it.
  6. Use an Elastic Load Balancer for production-style horizontal scaling, and consider RDS for a managed, backed-up database and Route 53 for DNS.

Practice Questions

Look away from the page first — retrieval is what builds memory.

Answer, reveal, then tick “Mastered”. Your progress is saved.
Q1

What is the defining feature of Linux, who released it, and in what year?

Answer: The defining feature is the Linux kernel. It was released in 1991 by Linus Torvalds. Linux is an open-source UNIX-like operating system.
Q2

What exactly is a Linux distribution, and give three examples of the kinds of software it bundles.

Answer: A Linux distribution is a collection of software packaged together as a complete operating system. It bundles things such as package managers (apt-get, pacman), window managers (GNOME, i3), and text editors.
Q3

What is the root user, and why should ordinary programs not run as root?

Answer: The root user (Superuser, UID 0) is the most privileged user and can do anything on the system. Ordinary programs should run as dedicated users so that if they are compromised, the attacker can only perform actions that the running user could — not full system control.
Q4

Which command lists all running processes and the user each runs as, and which users do nginx and mysqld typically run as?

Answer: The command is ps aux. nginx typically runs as www-data and MySQL programs such as mysqld typically run as mysql. Linux systems often also have a nobody user for programs needing almost no privileges.
Q5

How do Linux capabilities improve on the traditional root model? Name three capabilities and what they grant.

Answer: Capabilities split root's all-or-nothing privileges into fine-grained units, so each process is assigned only the subset it needs. This enforces least privilege, contains damage, and reduces the attack surface. Examples: CAP_NET_BIND_SERVICE (bind privileged ports like 80), CAP_SYS_ADMIN (mount filesystems), CAP_DAC_OVERRIDE (bypass file permission checks), CAP_NET_RAW (raw sockets), CAP_CHOWN (change file ownership).
Q6

Explain how running nginx with capabilities changes the impact of a compromise.

Answer: Traditionally nginx needed root just to bind port 80. With capabilities it runs as an unprivileged user granted only CAP_NET_BIND_SERVICE. If hacked, the attacker cannot create raw sockets (CAP_NET_RAW), mount filesystems (CAP_SYS_ADMIN), or change file ownership (CAP_CHOWN).
Q7

What protocol does SSH replace, what port does an SSH server listen on, and what are the two authentication methods?

Answer: SSH replaces Telnet. An SSH server listens on TCP port 22. It authenticates users using passwords or public/private keys. The most common server software is OpenSSH, from the OpenBSD project.
Q8

In SSH, what is the difference between the server's key pair and a client's key pair?

Answer: The server has its own key pair so initial connections can be encrypted with its public key and clients can authenticate the server; only the server with the private key can read incoming connections. Each client has its own key pair used to authenticate to the server by proving possession of a private key matching an authorised public key.
Q9

Where are server SSH keys stored, what file records them on the client, and what attack does this prevent?

Answer: Server keys are typically stored as /etc/ssh/ssh_host_rsa_key and /etc/ssh/ssh_host_rsa_key.pub. When a client first connects and accepts the key, an entry is added to ~/.ssh/known_hosts. Tracking known server public keys minimises the potential for a man-in-the-middle (MITM) attack.
Q10

How does a client authenticate as a particular user on an SSH server? Name the relevant file.

Answer: The client proves ownership of a private key corresponding to an authorised public key. On the server, /home/<user>/.ssh/authorized_keys (e.g. /home/myuser/.ssh/authorized_keys) contains the public keys of everyone authorised to connect as that user. If the client's private key matches one, the connection is authorised.
Q11

What does ssh-agent do, and what does ForwardAgent enable?

Answer: ssh-agent stores the unencrypted SSH private key in memory so you do not re-enter the passphrase for the encrypted key in ~/.ssh/id_rsa on every connection; new SSH processes ask it to perform signing operations. ForwardAgent allows remote SSH clients to access the local ssh-agent, and therefore the unencrypted private key.
Q12

Compare Nano and Vim as terminal editors, including their key commands.

Answer: Nano is very simple, often the default on many Linux versions, uses arrow keys, and exits with Ctrl+X or writes with Ctrl+O. Vim is very flexible and fully featured but challenging to learn: i enters insert mode, Esc exits a mode, : accesses commands, q quits and wq writes and quits.
Q13

Why can't you use Atom or Notepad++ on a remote server, and what is the usual purpose of the terminal editor you use instead?

Answer: They are graphical applications, so they cannot run over SSH. Instead you use a command-line text editor, typically to edit configuration files on the remote server.
Q14

Name the four situations in which you must install software manually instead of using a package manager, and state Ubuntu's package manager.

Answer: Ubuntu's package manager is APT (Advanced Packaging Tool). Install manually when: there is no package for the software; the packaged software is out of date; you want to install into a different location; or the software must be compiled with different options than the package manager provides.
Q15

Match each AWS service to its purpose: EC2, EBS, RDS, Route 53, VPC, EKS, ECS.

Answer: EC2 provides server instances (the fundamental service used for deployment). EBS provides attachable hard drive volumes. RDS provides managed database servers. Route 53 provides DNS-based routing to AWS infrastructure. VPC provides network segregation and greater EC2 control. EKS provides managed Kubernetes. ECS provides managed container orchestration and is Amazon's alternative to Kubernetes.
Q16

What constraint applies when attaching an EBS volume to an EC2 instance, and why is EBS useful?

Answer: Both the volume and the instance must be in the same Availability Zone. EBS is useful for separating your data storage from the server that executes your software.
Q17

What databases does RDS support, and is a VPC necessary for the project?

Answer: RDS supports Aurora, PostgreSQL, MySQL, MariaDB, Oracle Database and SQL Server. A VPC is not necessary for the project — you use the default VPC created by AWS instead, since VPC configuration can be complex.
Q18

Explain the difference between TCP and UDP, including ordering and port numbering.

Answer: TCP is connection-oriented: it establishes an end-to-end connection and ensures packets are delivered in order. UDP is connectionless and best-effort, making no guarantees about ordering or even delivery. UDP has its own set of ports, so TCP port 80 differs from UDP port 80.
Q19

How do ports allow multiple applications to run on one host, and what is the rule about listening?

Answer: Applications "listen" on a particular TCP port, so each application listens on a different port and multiple applications share the host. Only one running application may listen to a given port at a time.
Q20

What is a firewall, and how do home routers and software firewalls differ?

Answer: A firewall is a security system that allows or disallows network traffic according to a set of rules. A home router makes decisions about incoming/outgoing traffic and prevents attackers from accessing your network; a software firewall runs on a host machine and provides rules about traffic allowed to enter that host.
Q21

What three things must you specify when configuring an AWS Security Group, and what is the default behaviour for unmatched traffic?

Answer: You must specify the Protocol (TCP/UDP/ICMP), the Port(s) the rule applies to, and the Source IP address(es) the rule applies to. The rules are a whitelist, so any packet not matching a rule is automatically dropped.
Q22

Why might you add an SSH rule from 0.0.0.0/0, and what is the risk?

Answer: It is useful for development to allow SSH access from any source (0.0.0.0/0). The risk is that it opens port 22 to the entire internet, which is dangerous in production.
Q23

What problem do Elastic IPs solve, and what does an Elastic Load Balancer provide?

Answer: When an EC2 instance restarts, AWS may reassign it a different public IP, making dependent configurations like DNS records hard to maintain. An Elastic IP is a consistent address that the instance always has whenever created. An Elastic Load Balancer distributes traffic across EC2 instances, enabling easy horizontal scaling for production websites.
Q24

List the four applications you should install to deploy a website, and explain nginx's role.

Answer: A web server, an application interface, the web application, and a database. nginx is a fast web server and reverse proxy; it receives and processes HTTP requests but does not interpret application code, so we use proxy_pass to forward requests to the application interface.
Q25

What is WSGI and uWSGI, and what language/software are they designed for?

Answer: WSGI is a specification for the interface between a web server and an application server; uWSGI is software implementing it. The application interface runs multiple application "workers" for concurrency. uWSGI is designed for Python programs and has good support for Django.
Q26

Which RDBMS is recommended and why, and what are the three rough setup steps?

Answer: MySQL is recommended because it is feature-rich and relatively easy to use; PostgreSQL and MariaDB are acceptable alternatives. The steps are: install the DB software; configure users (username & password); configure application code to use the DB by connecting with the username & password.
Q27

Why and how should you separate data from application code on EC2?

Answer: You should always separate data from application code, typically by configuring the DB to save data to a separate volume from the OS and web application. On EC2 you use a separate EBS volume for database storage and configure the RDBMS to store data there (MySQL has documented steps for moving its data directory).
