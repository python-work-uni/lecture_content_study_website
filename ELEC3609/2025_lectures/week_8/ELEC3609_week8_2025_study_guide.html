Linux Fundamentals

Linux is an open-source, UNIX-like operating system whose defining feature is the Linux kernel. It was released in 1991 by Linus Torvalds. The kernel is the core interface between the hardware and the software system processes. A Linux distribution (distro) defines a collection of software that comes pre-packaged as a complete operating system, combining the kernel with:

  • Package managers (e.g. apt-get, pacman)
  • Window managers (e.g. GNOME, i3)
  • Text editors and administration utilities

Common distros include Ubuntu, Debian, CentOS, and Arch Linux. Why Linux matters: it has become the most widely installed general-purpose OS thanks to the proliferation of Android, and it is the most dominant OS for web servers (>90%). That is why this unit deploys onto Linux — it is the platform your software will actually run on.

💡
Why It Matters:: The kernel is common to every Linux system; distributions differ by the software stacked on top. Knowing the difference helps when choosing a server image.
02

Linux Users & Privileges

Every program in Linux executes under the authority of a specific user account. Understanding privileges is critical for secure deployments. The root user (root / superuser) is the most privileged user on a Linux system:

  • User ID (UID) is 0.
  • Root can do anything — modify any file, kill any process, and bind to any network port.
  • Other users can have a wide variety of limited privileges.

Program-specific (unprivileged) users. Programs execute as a particular user. If a program needs special privileges, it may need root — but usually it does not, and so it should run as a different user. The benefit is damage containment: if such a program is compromised, it can only perform actions that its running user could perform. Dedicated service users you will see in practice:

  • Web servers (including nginx and Apache) usually run as the www-data user.
  • MySQL programs (including mysqld) usually run as the mysql user.
  • Linux systems often include a nobody user, used for programs that need almost no special privileges.

Monitoring processes: the command ps aux shows a list of all processes running on the system and the user each is running as.

⚠️
Common Trap:: Running a web server as root is a classic mistake. If that server is exploited, the attacker inherits full system control. Run it as an unprivileged, dedicated user instead.
03

Linux Capabilities

Traditional root vs capabilities. In the classic UNIX/Linux model, privilege is binary:

  • root (UID 0) has all privileges.
  • If a process is compromised while running as root, the attacker gains full control of the system.

Capabilities split root privileges into smaller, fine-grained units, so each process can be assigned only the subset it really needs. Examples include:

  • CAP_NET_BIND_SERVICE — bind a socket to privileged ports (numbers below 1024)
  • CAP_SYS_ADMIN — system administration tasks such as mounting filesystems
  • CAP_DAC_OVERRIDE — bypass file read/write/execute permission checks
  • CAP_NET_RAW — create raw/packet sockets (used for sniffing or spoofing)
  • CAP_CHOWN — arbitrarily change file ownership

Why capabilities improve security:

  • Least privilege principle — grant only what is needed
  • Damage containment — a compromise affects only the granted subset
  • Reduced attack surface — fewer dangerous powers exposed

Real-world example — running nginx:

  • Traditionally: nginx needed root just to bind port 80.
  • With capabilities: run nginx as an unprivileged user but grant only CAP_NET_BIND_SERVICE.
  • If nginx is hacked, the attacker cannot create raw sockets (CAP_NET_RAW), mount filesystems (CAP_SYS_ADMIN), or change file ownership (CAP_CHOWN).
🧠
Memory Hook:: Think of capabilities as "slicing root into small pieces" — you hand out only the slice the program needs.

Secure Shell (SSH) Basics

Secure Shell (SSH) is a secure replacement for the old Telnet protocol. It lets a user access the shell or terminal on a remote machine. Because Linux is the dominant server platform on the internet, SSH is an essential tool for any web master.

ProtocolSecurityPort
Telnet (legacy)Sends commands and passwords in plain text — insecureTCP 23
SSH (modern)Encrypts the tunnel, terminal I/O, and credentialsTCP 22

SSH server:

  • The most common SSH server software is OpenSSH, which originates from the OpenBSD project.
  • It listens for incoming connections on TCP Port 22.
  • It authenticates connecting users using passwords or public/private keys.

SSH client:

  • OpenSSH also provides an SSH client, the client-side software that connects to the server.
  • On Linux, stick with the default OpenSSH.
  • On Windows, PuTTY is often a better option.
💡
Why It Matters:: SSH is how you administer a remote cloud server. If it is misconfigured or left on a weak password, it becomes the front door for attackers.
06

SSH Keys & Key Management

SSH provides both authentication and encryption. Logging in with only a remote user's password is possible, but that is bad — passwords are vulnerable to brute force. Best practice is to use SSH keys. How public-key cryptography works. A key pair (private + public) is generated for authentication, which is achieved by demonstrating possession of the private key without revealing it:

  • Private key — held by you, never shared; only you can sign a request with it.
  • Public key — shared publicly; anyone can verify your signature with it.

Two sets of keys are involved:

  • Server keys — the server has its own key pair, which lets initial connections be encrypted with its public key and lets clients authenticate the server. Only the server possessing the private key can read incoming connections.
  • Client keys — each client has its own key pair, used to authenticate when connecting to the server.

Server host keys:

  • Stored at /etc/ssh/ssh_host_rsa_key (private) and /etc/ssh/ssh_host_rsa_key.pub (public).
  • On first connecting to a new server, you get a warning; accepting it adds an entry to your ~/.ssh/known_hosts file.
  • By keeping track of known server public keys, clients minimise the potential for a MITM (man-in-the-middle) attack — if the host key ever changes unexpectedly, SSH raises a warning.

Client keys:

  • To authenticate a user, the client proves ownership of a private key corresponding to an authorised public key.
  • The server holds, in the user's home directory, /home/myuser/.ssh/authorized_keys, containing the public keys of everyone authorised to connect as that user.
  • The server checks that the connecting client possesses the matching private key; if so, the connection is authorised.

The authentication challenge-response flow (the private key never leaves the client):

→

ssh-agent and agent forwarding:

  • SSH typically reads private keys from ~/.ssh/id_rsa, which is encrypted; every time SSH runs it needs the passphrase.
  • ssh-agent is a program that stores the unencrypted private key in memory, attached to a running process, so you don't retype the passphrase for every connection.
  • SSH processes connect to the agent and ask it to perform signing operations.
  • The ForwardAgent option allows remote SSH clients to access your local ssh-agent (and therefore your unencrypted private key). This is handy when jumping from a bastion host to a private server, but note the risk: it exposes your agent to those remote hosts.
⚠️
Common Trap:: Password-based SSH logins invite brute force; use key-based auth. Also be cautious with ForwardAgent — you are trusting intermediate hosts with access to your signing agent.

Terminal Editors & Package Managers

Terminal text editors. Desktop editors like Atom or Notepad++ are graphical and cannot run on a remote server via SSH, so you need a command-line editor — typically to edit configuration files on the remote server.

  • Nano — very simple, often the default on many Linux versions; familiar interface using arrow keys. Exit with Ctrl+X; write with Ctrl+O.
  • Vim — very flexible, fully featured, but can be challenging to learn. Enter insert mode with i, leave a mode with esc, and use : to access commands — :q to quit, :wq to write and quit.

Package managers. Ubuntu's package manager is the Advanced Packaging Tool (APT). Installing software via the package manager is easiest because it can automatically update software for you (primary command: apt-get install <package>). You may need to install software manually if you can't use the package manager:

  • There is no package for the software you want.
  • The packaged software is out of date.
  • You want to install into a different location.
  • The software must be compiled with different options than the package manager provides.
💡
Why It Matters:: Prefer the package manager — it handles dependencies and updates. Compile manually only when the packaged version cannot meet your needs.

Networking & Elastic IPs

All the software you run involves responding to network requests, so you must understand networking concepts and their operation — in particular TCP/UDP ports (OSI Layer 4), firewalls, load balancers, and public IPs (OSI Layer 3). The OSI Model is a way to conceptualise network systems, with each layer being an abstraction of the previous one. You should be quite familiar with it to understand how technologies interact. For web infrastructure the key layers are:

  • Layer 3 (Network) — logical addressing (IP addresses) and routing.
  • Layer 4 (Transport) — end-to-end communication and port multiplexing (TCP/UDP).

Public IPs on EC2. When you start an EC2 instance, AWS assigns it a public IP address. If you restart the instance, it can be reassigned a different IP, which makes updating dependent configuration — such as DNS records — very difficult. Elastic IPs. To keep a consistent IP between restarts, you can assign the instance an Elastic IP (EIP) — a static IPv4 address allocated to your AWS account. Once assigned, the instance always has this IP whenever it is created, across stops, reboots, and restarts. This keeps DNS A-records, external firewall whitelists, and front-end configuration stable.

⚠️
Common Trap:: Relying on a default EC2 public IP for a production site guarantees a broken DNS record the first time the instance restarts. Use an Elastic IP.

Ports: TCP vs UDP

Most web software communicates via the Transmission Control Protocol (TCP). TCP establishes an end-to-end connection and ensures packets are delivered in the order they were sent. Applications "listen" on a particular TCP port. This lets multiple applications run on the same host, each listening on a different port. Any application can choose any port, but standard numbers exist for particular application types. Only one running application may listen to a port at a time. The User Datagram Protocol (UDP) is a connectionless protocol — "best-effort", making no guarantees that packets arrive in order, or arrive at all. UDP has its own separate set of ports: TCP Port 80 is different from UDP Port 80.

FeatureTCPUDP
ConnectionConnection-oriented (requires a 3-way handshake)Connectionless
DeliveryGuaranteed, in-order, with retransmissions and flow controlBest-effort; may be lost, delayed, or reordered
OverheadHigherMinimal latency and overhead
Typical usesHTTP (80), HTTPS (443), SSH (22), MySQL (3306), PostgreSQL (5432)DNS (53), video streaming, VoIP, online gaming
🧠
Memory Hook:: TCP = "reliable and ordered, costs more"; UDP = "fast and forgetful, guarantees nothing."

Firewalls & Security Groups

A firewall is a security system that allows or disallows network traffic according to a set of rules. Firewalls come in many shapes and sizes:

  • Your home router — makes decisions about incoming/outgoing traffic and prevents attackers from reaching your network.
  • Software firewalls — run on a host machine and define what traffic may enter the host.

AWS Security Groups (SGs) are sets of firewall rules applied to EC2 instances. When first configuring an EC2 instance you can either create a new security group or add the instance to an existing one. To configure a rule you must specify:

  • Protocol — TCP / UDP / ICMP
  • Port(s) — the TCP/UDP port(s) the rule applies to
  • Source — which source IP address(es) the rule applies to (a CIDR block), e.g. 0.0.0.0/0 for universal public access or 203.0.113.5/32 for one specific IP

Key behaviour: the rules are a whitelist — any packet not matching a rule is automatically dropped (disallowed). There are no "deny" rules; the default is deny. Security Groups are stateful, meaning replies to allowed traffic are automatically permitted. For development, it may be useful to add a rule for SSH access from any source (0.0.0.0/0) — convenient, but risky in production. A common port and Security Group reference:

ServicePortProtocolRecommended source
SSH22TCPAdmin IP (X.X.X.X/32) or any for dev
HTTP80TCPPublic (0.0.0.0/0)
HTTPS443TCPPublic (0.0.0.0/0)
MySQL DB3306TCPOnly the EC2 Security Group ID (internal)
⚠️
Common Trap:: Opening SSH to 0.0.0.0/0 exposes the login service to the entire internet. Restrict it to your admin IP wherever possible.

Load Balancing & the Web Stack

Elastic Load Balancing (ELB) provides a load balancing service for EC2 instances. It is a useful tool for production websites because it allows easy horizontal scaling — adding more instances behind a single entry point. For the project you should learn how to configure ELB for your deployment. Web servers. A web server receives incoming HTTP requests, processes them, and usually returns an HTTP response. There are many types of web server software, including Apache, Nginx, and IIS (details covered in the Week 3 lecture). Recommended: nginx (pronounced "engine-X") is a fast web server that can also act as a reverse proxy. Due to its widespread use and ease of configuration, it is highly recommended for the project.

  • Nginx can receive and process an HTTP request, but it does not interpret web application code.
  • Instead, we ask nginx to proxy_pass HTTP requests to the application interface.

Application interfaces. A web application interface provides a simple interface between a web server and the application server, running multiple application "workers" so the application can process requests concurrently.

  • WSGI (Web Server Gateway Interface) is the specification for such an interface.
  • uWSGI is the software that implements WSGI; it is designed for Python programs and has good support for Django.

Databases & Server Applications

To deploy a website properly, configure several applications on your server. In particular, you should install:

  • A web server
  • An application interface
  • The web application
  • A database

Databases. Most web applications require persistent storage of data, so you will most likely need a relational database management system (RDBMS). MySQL is recommended because it is feature-rich and relatively easy to use; PostgreSQL and MariaDB are acceptable alternatives. Regardless of the RDBMS, the rough setup steps are:

  1. Install the DB software.
  2. Configure users (username & password).
  3. Configure the application code to use the DB — connecting with the username and password.
💡
Why It Matters:: The application is only as good as its connection to persistent, durable data. Configuring the database user correctly is both a functional and security concern.
14

Volume Separation & Data Safety

You should always separate your data from your application code. Typically this involves configuring your DB to save data to a separate volume from where your operating system and web application are installed. If working on EC2, you should utilise a separate EBS volume for database storage. Implementation strategy on EC2:

  1. Attach a dedicated EBS volume to the EC2 instance (e.g. mounted at /mnt/db_volume).
  2. Reconfigure the RDBMS data directory to store database files on that volume — for MySQL, moving /var/lib/mysql to the new volume.

Benefits of data separation:

  • Instance resilience — if the EC2 root OS crashes or is re-imaged, the database volume remains intact and can be re-attached to a fresh server.
  • Scalability — the database volume can be snapshotted, backed up, or expanded independently of the OS disk.
  • Performance — disk I/O is spread across separate storage.
⚠️
Common Trap:: Storing database files on the OS root volume means a server rebuild can destroy your data. Decouple storage from compute.

Worked Scenarios & Calculations

Scenario 1 • Why run nginx

Why run nginx as www-data with a capability?

A traditional nginx had to start as root just to bind port 80. If an attacker exploits nginx, they get root and own the machine. With capabilities, nginx runs as www-data and is granted only CAP_NET_BIND_SERVICE. It can still bind port 80, but an exploit cannot create raw sockets, mount filesystems, or change file ownership. Same function, far smaller blast radius.

Scenario 2 • SSH key authentication

SSH key authentication step by step

You generate a key pair. You place the public key into /home/myuser/.ssh/authorized_keys on the server and keep the private key on your laptop. When you run ssh myuser@server, the server checks authorized_keys, issues a cryptographic challenge, and your client signs it with the private key. The server verifies the signature with the public key and grants access — the private key never crosses the network.

Scenario 3 • Detecting a MITM with known_hosts

Detecting a MITM with known_hosts

The first time you connect, you accept the server's host key and it is saved to ~/.ssh/known_hosts. Later, if an attacker intercepts the connection and impersonates the server IP, their host key will not match the stored one — SSH raises a strict warning and blocks access.

Scenario 4 • Choosing EBS and

Choosing EBS and an Elastic IP for a database server

You launch an EC2 instance and attach an EBS volume for the database — but both must be in the same Availability Zone or the attach fails. Separately, because EC2 reassigns a public IP on restart, you allocate an Elastic IP so the DNS record pointing at your server stays valid across reboots.

Scenario 5 • Assembling the four-tier stack

Assembling the four-tier stack

A request arrives at nginx (Tier 1), which serves static files directly and proxy_passes dynamic requests to uWSGI (Tier 2). uWSGI runs Python worker processes that execute your Django/Flask application (Tier 3), which queries MySQL (Tier 4). The database files live on a separate EBS volume, so rebuilding the OS never destroys the data.

Why is running a web server as root dangerous, and what is the alternative?
Answer:
A flaw such as RCE gives the attacker full OS control under root. Run it as an unprivileged user (e.g. www-data), optionally granting only the needed capability.
Q2
How do Linux capabilities improve security?
Answer:
They split root into fine-grained privileges so a process gets only the subset it needs (e.g. CAP_NET_BIND_SERVICE to bind port 80), enforcing least privilege and containing damage.
Q3
What must be true when attaching an EBS volume to an EC2 instance?
Answer:
Both must be in the same Availability Zone.
Q4
Why use an Elastic IP on a production EC2 server?
Answer:
Default EC2 public IPs change on stop/restart, breaking DNS and firewall config; an Elastic IP is a static IPv4 address that persists.
Q5
How does SSH public-key authentication avoid sending the private key?
Answer:
The server issues a challenge; the client signs it with its local private key; the server verifies with the matching public key in authorized_keys. The private key never leaves the client.
Q6
What is the purpose of ~/.ssh/known_hosts?
Answer:
It stores trusted server public keys so a changed key — signalling a possible MITM — triggers a warning.
Q7
What does ssh-agent and ForwardAgent do?
Answer:
ssh-agent holds the decrypted private key in memory so you don't retype the passphrase; ForwardAgent lets remote hosts use your local agent through the tunnel (with associated exposure risk).
Q8
Compare TCP and UDP with web examples.
Answer:
TCP is connection-oriented, reliable, and ordered (HTTP 80, HTTPS 443, SSH 22, MySQL 3306, PostgreSQL 5432). UDP is connectionless and best-effort (DNS 53, streaming, VoIP, gaming).
Q9
How does an AWS Security Group handle traffic by default?
Answer:
It is a whitelist — unmatched inbound traffic is dropped. Rules specify protocol, port(s), and source CIDR.
Q10
Why does nginx need uWSGI rather than running Python directly?
Answer:
Nginx is an HTTP server/reverse proxy and does not interpret application code; it proxy_passes dynamic requests to uWSGI, which implements WSGI and manages Python workers.
Q11
What are the four installation layers of the project server stack?
Answer:
A web server (nginx), an application interface (uWSGI), the web application, and a database (MySQL).
Q12
What is the benefit of separating the database onto its own EBS volume?
Answer:
Data is decoupled from the OS/app; the volume survives OS crashes or rebuilds and can be snapshotted or scaled independently.
Q13
When must you install software manually instead of via the package manager?
Answer:
When there is no package, the package is out of date, you need a custom install location, or the software must be compiled with different options.
