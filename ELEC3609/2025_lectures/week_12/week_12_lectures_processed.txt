[Short Answer Answering Template (5-Mark Question Strategy)]
Each short answer question explicitly specifies mark values and recommended word/paragraph limits.
To earn full marks on a 5-mark short answer question (e.g., "Describe the key characteristics of a DDoS attack"), 
structure your response into four logical components:

1. Core Definition & Characteristics (1-2 Marks): Define the mechanism precisely.
2. Attack Scenario / Context (1 Mark): Describe a realistic technical scenario where it occurs.
3. Root Causes / Vulnerabilities (1 Mark): Explain what system weaknesses enable the attack.
4. Stakeholder & System Impact (1 Mark): Analyze long-term operational, financial, or security consequences.

2. WEB NETWORKING FUNDAMENTALS & OSI LAYER ARCHITECTURE
--------------------------------------------------------------------------------
Web platforms rely on underlying network protocols to transport data reliably 
between clients and servers.

[OSI Model Focus Layers]
The Open Systems Interconnection (OSI) model conceptualizes network communications 
into 7 layers. In web software platforms, primary attention is centered on Layers 3, 4, and 7:

+---------+-------------------+--------------------------------------------------+
| Layer   | Name              | Core Protocols & Functionality                   |
+---------+-------------------+--------------------------------------------------+
| Layer 7 | Application       | HTTP, HTTPS, SSH, DNS. User-facing data payload. |
| Layer 4 | Transport         | TCP, UDP. End-to-end transport & port addressing.|
| Layer 3 | Network           | IP (IPv4/IPv6), BGP. Host addressing & routing.  |
| Layer 2 | Data Link         | IEEE 802.11 (WiFi), Ethernet. Frame switching.   |
| Layer 1 | Physical          | Copper wires, Coaxial, Fiber optics, Radio.      |
+---------+-------------------+--------------------------------------------------+

[DHCP: Dynamic Host Configuration Protocol]
When a device joins a local network, DHCP automatically configures four critical network parameters:
1. IP Address: Identifies the host uniquely on the local subnet.
2. Subnet Mask: Defines network boundaries and distinguishes local from non-local traffic.
3. Default Gateway: The router host interface that forwards non-local packets outside the subnet.
4. Nameservers (DNS): Specifies the IP address of DNS servers used to resolve hostnames.

Memory Retention Tip: If a client machine cannot reach external web sites, DHCP configuration 
(IP, Gateway, DNS) is the VERY FIRST diagnostic check to perform!

[Core Web Support Protocols]
- DNS (Domain Name System): Hierarchical system translating human-friendly domain names (e.g., `example.com`) to IP addresses. Operating on UDP/53 (and TCP/53 for large transfers).
- SSH (Secure Shell): Secure encrypted protocol providing remote terminal administration and code execution on servers over TCP/22.
- BGP (Border Gateway Protocol): Standardized exterior gateway protocol designed to exchange routing and reachability information between autonomous systems (AS) on the global internet.

[Transport Layer Comparison: TCP vs. UDP]
+----------------------+-----------------------------------+-----------------------------------+
| Metric / Feature     | TCP (Transmission Control Protocol)| UDP (User Datagram Protocol)      |
+----------------------+-----------------------------------+-----------------------------------+
| Layer                | Layer 4 (Transport)               | Layer 4 (Transport)               |
| Connection Type      | Connection-oriented (Handshake)   | Connectionless (No Handshake)     |
| Reliability          | Guaranteed in-order delivery;     | Best effort; packets can drop,    |
|                      | automatic ACKs & retransmissions  | arrive out of order, or duplicate |
| Data Unit            | Segments                          | Datagrams                         |
| Overhead             | Higher (header overhead + state)  | Minimal (low latency header)      |
| Common Port Examples | SSH (TCP/22), HTTP (TCP/80),      | DNS (UDP/53), Streaming,          |
|                      | HTTPS (TCP/443)                   | Voice/VoIP, Gaming                |
| Attack Vulnerability | TCP SYN Flooding (state exhaustion)| UDP Amplification / Reflected DDoS|
+----------------------+-----------------------------------+-----------------------------------+

3. HTTP PROTOCOL, COOKIES & AUTHENTICATION FLOWS
--------------------------------------------------------------------------------
HyperText Transfer Protocol (HTTP) is the foundational application-layer protocol 
of the World Wide Web.

[Common HTTP Methods]
- GET: Requests data from a specified resource. Must be idempotent and safe (no side effects). Body is typically omitted.
- POST: Submits data to be processed to a specified resource, resulting in creation of a new resource or state change. Non-idempotent.
- PUT: Creates a new resource or completely replaces an existing resource at the target URL.
- PATCH: Applies partial modifications to an existing resource.
- DELETE: Removes the specified resource.
- OPTIONS: Returns the HTTP methods supported by the server for the targeted URL (crucial for CORS preflight).
- HEAD: Asks for a response identical to a GET request, but without the response body (used for checking headers/cache validation).

[HTTP Cookies & State Management]
HTTP is natively stateless. Cookies enable servers to maintain session state across requests.
Cookies are managed via two standard HTTP headers:
- Server Response Header: `Set-Cookie: token=4f3e; Secure; HttpOnly; SameSite=Strict`
- Client Request Header: `Cookie: token=4f3e` (Browsers automatically send matching cookies on every subsequent request to that domain).

[5-Step Cookie Authentication Flow]

  Client (Browser)                                    Server
  +--------------+                                +------------+
  | 1. Visit Site| ---- Request (No Cookie) ----> |            |
  | (Unauth)     | <--- Response (Login Form) --- |            |
  |              |                                |            |
  | 2. Submit    | ---- POST /login (user,pass)-> | Verify     |
  |    Credentials|                               | Credentials|
  |              |                                | Generate   |
  |              | <--- Response + Set-Cookie --- | Session/   |
  |              |      (token=xyz123)            | Auth Token |
  |              |                                |            |
  | 3. Visit     | ---- GET /dashboard ----------->| Read       |
  |    Protected |      Cookie: token=xyz123      | Cookie,    |
  |    Page      | <--- 200 OK + User Data ------ | Authenticate|
  +--------------+                                +------------+

4. SCALING WEB ARCHITECTURE & INFRASTRUCTURE PATTERNS
--------------------------------------------------------------------------------
As user traffic grows, web architectures must evolve from monolithic single-server 
setups to distributed, fault-tolerant infrastructure.

[Architectural Evolution Stages]

1. SINGLE SERVER ARCHITECTURE
   - Web server, application server, and database co-located on a single host.
   - Drawbacks: Single point of failure (SPOF); CPU and RAM contention between database queries and app execution; poor scalability.

2. SEPARATE DATABASE SERVER
   - The database engine is moved to a dedicated server hardware instance.
   - Advantages:
     * Eliminates resource contention on the application server.
     * Security Enhancement: The database is removed from the DMZ (Demilitarized Zone / public subnet) and placed in a isolated private subnet.

3. LOAD BALANCED APPLICATION CLUSTER
   - A Load Balancer (LB) sits in front of multiple application servers to distribute incoming traffic.
   - Common LB Software: HAProxy, Nginx, Varnish.
   - Key Advantages: Horizontal scaling, high availability, and zero-downtime failover (if one server fails, the LB routes traffic to healthy nodes).

4. HTTP ACCELERATORS / CACHING REVERSE PROXIES
   - Positioned in front of web servers to cache dynamic or static response payloads in high-speed RAM.
   - Common Accelerators: Varnish, Squid, Nginx.
   - Purpose: Drastically reduces response latency and offloads traffic from app servers for frequently accessed content.

5. HYBRID ENTERPRISE ARCHITECTURE
   - Combines Load Balancers, HTTP Caching Proxies, horizontal App Server Pools, and Database Master-Replica Replication into a unified resilient architecture.

5. WEB DEVELOPMENT PROCESS, REQUIREMENTS & SYSTEM DESIGN
--------------------------------------------------------------------------------
Structured software engineering processes ensure that software systems meet business 
objectives while preventing scope creep and architectural defects.

[Software Requirements Specification (SRS)]
- Definition: A formal, comprehensive contract detailing exactly what a software system MUST do and MUST NOT do.
- Purpose: Serves as the primary communication bridge between non-technical business stakeholders and software engineers.
- Scope Control: Defines explicit boundaries to prevent scope creep and establishes the definition of "Done" for a project.
- Golden Rule: Architectural and design diagrams (UML, wireframes) must NEVER introduce requirements that are omitted from the SRS.

[Requirements Modeling Tools]

1. UML USE CASE DIAGRAMS & EVENT FLOW DOCUMENTATION
   - Models functional requirements by showing system boundaries, actors, and use case interactions.
   - Event Flow Documentation captures detailed specification table fields:
     * Name: Short descriptive identifier.
     * Goal: Core objective achieved by the use case.
     * Actors: Initiating and participating actors.
     * Preconditions: System state requirements prior to execution.
     * Main Flow: Step-by-step nominal execution sequence.
     * Subflows & Alternative Flows: Exception handling, edge cases, and error paths.
     * Priority: Relative importance for MVP (Minimum Viable Product) scheduling.

2. UML SEQUENCE DIAGRAMS
   - Visualizes object and system interactions in strict chronological sequence.
   - Essential for mapping multi-step network communications, API exchanges, and complex component workflows over time.

3. WIREFRAMES & STORYBOARDS
   - Low-fidelity visual structural mockups ("cartoons") of user interfaces.
   - Purpose: Allows stakeholders and developers to evaluate layout, user experience (UX), and navigation flow without getting distracted by colors, fonts, or graphic assets.

6. WEB PROGRAMMING, STATUS CODES & FRONT-END TOOLING
--------------------------------------------------------------------------------
Modern web platforms combine front-end markup, DOM manipulation, asynchronous communications, 
and automated build systems.

[HTML & The DOM (Document Object Model)]
- HTML: Markup language defining document structure and semantically marking content.
- DOM: In-memory tree structure representation of the HTML document created by the browser. 
  JavaScript manipulates the DOM dynamically to modify content, attributes, and styles without requiring server round-trips.

[HTTP Status / Error Codes Category Breakdown]
+----------+-------------------+--------------------+------------------------------------+
| Code Range| Category          | Famous Examples    | Description                        |
+----------+-------------------+--------------------+------------------------------------+
| 1xx      | Informational     | 100 Continue       | Server received request headers.   |
|          |                   | 101 Switching Pro. | Upgrading protocol (e.g. WebSocket)|
| 2xx      | Success           | 200 OK             | Standard successful HTTP response. |
|          |                   | 201 Created        | Resource successfully created.     |
| 3xx      | Redirection       | 301 Moved Perm.    | Permanent redirect (SEO preserved).|
|          |                   | 302 Found (Temp)   | Temporary redirect.                |
|          |                   | 304 Not Modified   | Cache valid; payload omitted.      |
| 4xx      | Client Errors     | 400 Bad Request    | Malformed request payload/syntax.  |
|          |                   | 401 Unauthorized   | Authentication credentials missing.|
|          |                   | 403 Forbidden      | Authenticated but lack permission. |
|          |                   | 404 Not Found      | Target resource does not exist.    |
| 5xx      | Server Errors     | 500 Internal Error | Unhandled app server exception.    |
|          |                   | 502 Bad Gateway    | Invalid response from upstream app.|
|          |                   | 503 Service Unavail| Server overloaded or down for maint|
+----------+-------------------+--------------------+------------------------------------+

[Single Page Applications (SPA) & AJAX]
- SPA: Web applications that load a single HTML document and dynamically update content as the user interacts with the app.
- AJAX (Asynchronous JavaScript and XML): Fundamental web technology enabling client background requests without full page reloads.
- Evolution of AJAX Data Fetching APIs:
  `XMLHttpRequest (XHR) [Clunky]` -> `jQuery $.ajax() [Library]` -> `Fetch API / Axios [Modern Standard]`

[Front-End Task Runners & Build Tools]
- Grunt / Gulp: JavaScript-based task runners running on Node.js/npm (acting as a "Makefile for front-end assets").
- Key Automated Automation Tasks:
  * Asset Minification: Stripping whitespace and comments from HTML, CSS, and JS.
  * Image Optimization: Compressing asset file sizes for faster page load times.
  * Linting: Code formatting and static code quality checks.
  * Bundling & Dependency Linking: Concatenating multi-file source scripts into single deployment bundles.

[End-to-End Lifecycle of a Web Request]
When a user types a URL into a browser address bar and hits Enter:

CLIENT SIDE:
1. Browser parses the URL (protocol, domain, port, resource path).
2. Browser inspects local cache (HTTP headers, 304 revalidation check).
3. OS identifies network interface and routes packet.
4. OS resolves domain name via DNS lookup (Recursive DNS -> Nameservers -> IP).
5. OS establishes Layer 4 TCP 3-way handshake with target server IP (Port 80/443).
6. Browser transmits HTTP GET Request across established TCP socket.

SERVER SIDE:
7. Load Balancers receive TCP stream, terminate TLS/SSL, parse HTTP headers, and route request to an application server node.
8. Application Server executes back-end business logic (e.g. Django view/controller).
9. App Server queries Database / Cache layer to retrieve persistent records.
10. App Server compiles response payload (HTML/JSON) and returns HTTP response via TCP back to Load Balancer to Client.

CLIENT SIDE:
11. Browser parses HTTP response headers and body payload.
12. Browser parses DOM structure, triggers sub-resource downloads (CSS, JS, Images), establishes WebSockets if required, and renders final page layout.

7. CI/CD PIPELINES & DEPLOYMENT STRATEGIES
--------------------------------------------------------------------------------
Continuous Integration and Continuous Deployment (CI/CD) automate software delivery 
from developer check-ins to production infrastructure.

[Full CI/CD Pipeline Stages]
1. Source Commit & Trigger: Code pushed to remote repository branch.
2. Linting & Static Analysis: Verifying syntax, style standards, and structural flaws.
3. Automated Build: Compiling binaries, bundling JavaScript, and preparing artifacts.
4. Test Automation Suite:
   - Unit Tests: Testing isolated functions/classes in memory.
   - Integration Tests: Testing interaction between modules, databases, and APIs.
   - System / Acceptance Tests: End-to-end user path testing in staging environment.
   - Regression Tests: Ensuring new features do not break legacy capabilities.
5. Release Artifact & Deployment: Deploying approved builds to production infrastructure.

[Deployment Strategy Comparison]

1. ROLLING DEPLOYMENT
   - Definition: Slowly updates server instances one by one (or in small batches) behind the load balancer.
   - Advantage: Requires NO extra server infrastructure (1x cost).
   - Disadvantage: During deployment, clients will experience a temporary mix of old (v1) and new (v2) application code across different requests.

2. BLUE-GREEN DEPLOYMENT
   - Definition: Maintains two identical physical environments: "Blue" (Active Live traffic) and "Green" (Idle New release).
   - Process:
     1. New release (v2) is fully deployed and smoke-tested in Green while Blue serves users.
     2. Router / Load Balancer instantly switches 100% of user traffic from Blue to Green.
   - Advantage: Zero downtime, zero version mixing, instant rollback capability (just flip router back to Blue if errors emerge).
   - Disadvantage: Double infrastructure costs during deployment.

[ASCII Diagram: Blue-Green Deployment]

                     +-------------------+
                     | Load Balancer /   |
                     | Router Switch     |
                     +---------+---------+
                               |
                 +-------------+-------------+
                 | (Traffic Switch)          |
                 v                           v
       +-------------------+       +-------------------+
       | BLUE ENVIRONMENT  |       | GREEN ENVIRONMENT |
       | (v1 - ACTIVE)     |       | (v2 - NEW RELEASE)|
       +-------------------+       +-------------------+

Web platforms face persistent malicious threats. Web developers must engineer systems

[Password Storage & Authentication Best Practices]
- Cryptographic Hashing: Passwords must NEVER be stored in plaintext or encrypted reversibly.
- Hashing + Unique Salt: Use robust slow cryptographic hash functions (Bcrypt, Argon2, PBKDF2) salted per-user to neutralize Rainbow Table attacks and fast GPU brute-forcing.
- Outdated Software Risks: Unpatched libraries and frameworks expose platforms to known public CVE exploits. Maintain active dependency auditing and automated security patching.

[Quick-Fire Practice Exam & Self-Assessment]
--------------------------------------------------------------------------------

Q1: True or False? In a 5-mark short answer exam question on web security, providing a 1-sentence definition of the attack is sufficient to score full marks.
    -> ANSWER: FALSE. A full-mark answer requires explaining the definition, a complex attack scenario, root cause vulnerabilities, and stakeholder impact.

Q2: Which protocol is used by DHCP to configure nameservers, and what port does standard DNS run on?
    -> ANSWER: DHCP provides the DNS server IP addresses. Standard DNS operates on UDP/53 (and TCP/53 for large payloads/zone transfers).

Q3: Explain the core architectural reason for moving a database to a separate server off the web application server.
    -> ANSWER: (1) Eliminates CPU/RAM resource contention between database queries and application execution. (2) Enhances security by removing the database from the public DMZ into a private subnet.

Q4: What is the main operational difference between Blue-Green Deployment and Rolling Deployment?
    -> ANSWER: Blue-Green uses two identical environments and switches 100% of traffic instantly (requiring 2x infra), whereas Rolling updates instances incrementally in a single pool (1x infra cost, but temporary version mixing).

Q5: True or False? Browsers automatically include all matching cookies set by a server with every subsequent HTTP request to that server.
    -> ANSWER: TRUE. Browsers automatically append matching domain cookies in the `Cookie:` header.

Q6: What HTTP error code category indicates a missing resource, and what code represents a Bad Gateway server error?
    -> ANSWER: 4xx indicates Client Errors (404 Not Found). 5xx indicates Server Errors (502 Bad Gateway).

Q7: What is the primary purpose of a Software Requirements Specification (SRS)?
    -> ANSWER: The SRS serves as the authoritative communication contract between stakeholders and developers, defining what the system must and must not do to prevent scope creep and establish when the project is finished.

Q8: Describe how anti-CSRF tokens defend against Cross-Site Request Forgery attacks.
    -> ANSWER: CSRF attacks rely on browsers automatically sending session cookies. Anti-CSRF tokens add a unique, unpredictable secret in request payloads/headers that a third-party attacker site cannot read or forge.

Q9: True or False? The final ELEC3609/9609 exam requires writing complete Django Python code blocks on paper.
    -> ANSWER: FALSE. The exam does NOT require writing or testing code. It focuses on high-level web concepts, development processes, and architectural principles.

Q10: Why must passwords be salted in addition to being hashed?
    -> ANSWER: Salting adds a unique random string to each password before hashing, ensuring identical passwords produce different hash outputs. This completely neutralizes pre-computed Rainbow Table attacks.
