Web Fundamentals: OSI, DHCP and Core Protocols

Every web request travels down and back up a stack of network layers, and before any HTTP happens DHCP gives your machine its identity while DNS turns a name into an address.

The OSI model

The OSI model is a way of conceptualising network systems. You need to be familiar with Layers 3, 4 and 7 throughout this course. The layers with the examples used in the unit:

LayerRoleExample
Layer 1 — PhysicalThe physical medium carrying bitsCopper line, COAX, Fibre
Layer 2 — Data LinkLocal link delivery between directly connected devicesIEEE 802.11a/b/g/n (Wi-Fi)
Layer 3 — NetworkAddressing and routing between networksIP
Layer 4 — TransportEnd-to-end delivery of data between applicationsTCP/UDP
Layer 7 — ApplicationThe protocols applications speakHTTPS

DHCP

When you connect to a network, your computer is usually configured with the Dynamic Host Configuration Protocol (DHCP). It provides four things:

  • IP address — identifies you on the local network.
  • Subnet mask — defines what "local" means with regard to your IP address.
  • Default gateway — a host that can route packets to non-local IP addresses.
  • Nameservers — a host that can resolve domain names, i.e. a DNS server.
✅
Exam tip: DHCP configuration is the first thing to check if you cannot reach any web sites — without an address, gateway and nameserver you cannot even start a request.

Other common web protocols

  • DNS — translates a URL to an IP address.
  • SSH — allows web-based server administration and remote code execution.
  • BGP — Border Gateway Protocol: interconnectivity and routing between large networks.
DHCP — Dynamic Host Configuration Protocol: the mechanism that gives a machine its IP address, subnet mask, default gateway and nameserver when it joins a network.

TCP vs UDP, HTTP Methods and Cookies

TCP and UDP are the two transport choices on Layer 4, HTTP is the request/response language on top, and cookies are how stateless HTTP remembers who you are.

TCP vs UDP

Both sit at Network Layer 4, but they make opposite promises.

AspectTCPUDP
GuaranteeGuarantees in-order delivery of data to the layers aboveBest effort — sends "datagrams" instead of TCP's "segments"
ReliabilityHandshake; reliable, ordered streamPackets are not acknowledged or re-transmitted unless done explicitly at the application layer
ConnectionHandshake enforcedNo handshake enforced
PortsNeeded — e.g. SSH on TCP/22Needed — e.g. DNS on UDP/53
Notable attackFamous cyber attack pattern: TCP flooding—

HTTP methods

These are the most commonly used HTTP methods:

  • GET — request data about a specified resource.
  • POST — create a resource.

Many more exist:

  • PUT — create/update a resource.
  • PATCH — partial modification of a resource.
  • DELETE — deletes the specified resource.
  • OPTIONS — returns the supported HTTP methods for this resource.
  • HEAD — equivalent to a GET request without the response body.

Consistency is key: use the method that matches the intended operation.

HTTP cookies

A HTTP cookie is a small piece of data, set by a website, which is stored in the user's browser. Browsers automatically include all the cookies set by a server with every HTTP request sent to that server. Two headers control cookies:

Cookie: username=abc123; authToken=4f3e
Set-Cookie: username=abc123
Set-Cookie: authToken=4f3e

Cookies are often used for tracking users and authentication. A typical login flow:

  1. User visits the website for the first time → no cookie.
  2. User submits the login form to the server with username + password → still no cookie.
  3. Server generates an authentication token (auth-tok) → server responds with Set-Cookie: token=[auth-tok].
  4. User visits the website again → client sends Cookie: token=[auth-tok].
  5. Server recognises the auth-tok and knows the request came from that user.
🧠
Memory hook: Request carries Cookie; the Response sets Set-Cookie. The browser then attaches that cookie automatically to every future request to that server — which is exactly why session cookies are valuable to attackers.
⚠️
Common trap: Because browsers send cookies automatically, any site that can make your browser issue a request can piggyback on your session — the root of CSRF (see the security section).
🤔
Pause & predict: Why does HTTP need cookies at all? What is missing from HTTP itself that cookies supply?

HTTP Status Codes

Status codes are grouped by their first digit, so knowing the five classes lets you infer the meaning of any code you meet.

Code classCategoryExamples
1xxInformational100: Continue; 101: Switching Protocols
2xxSuccess200: OK — the standard response
3xxRedirection301: Moved Permanently; 302: Found / Moved Temporarily (similar to 303 & 307); 304: Not Modified
4xxClient404: Not Found
5xxServer502: Bad gateway
🧠
Memory hook: 1xx = "here's info", 2xx = "it worked", 3xx = "look elsewhere", 4xx = "you messed up", 5xx = "the server messed up".
✅
Exam tip: 502 (Bad gateway) is a server-side error — a gateway or proxy received an invalid response from the upstream server. Do not confuse it with a 4xx client error.
🤔

Scaling Web Architecture

Start with one server, then split responsibilities one at a time — database, then traffic, then caching — so each layer can scale and fail independently.

Recap: single server architecture

Everything (web/application logic and the database) runs on one machine. This is simple but creates resource contention and puts the database on the same exposed host.

Separate DB server

Separate the database from the application server to eliminate resource contention. This also increases security by removing the database from the DMZ, or public internet.

Load balancer

Load balancers (LB) can be added to a server environment to improve performance and reliability by distributing the workload across multiple servers. If one of the load-balanced servers fails, the other servers handle the incoming traffic until the failed server becomes healthy again. Typical implementations use HAProxy, Nginx and Varnish.

HTTP accelerator

An HTTP accelerator, or caching HTTP reverse proxy, reduces the time it takes to serve content to a user through a variety of techniques. Typically the response from a web or application server is cached for a period of time in memory. Software capable of HTTP acceleration includes Varnish, Squid and Nginx.

Combinations

It is possible to load balance the caching servers in addition to the application servers, and to use database replication in a single environment. The purpose of combining these techniques is to reap the benefits of each without introducing too many issues or complexity.

single server→separate DB server→load balancer→HTTP accelerator→combined architecture
💡
Why it matters: Each addition solves one specific problem — contention (separate DB), reliability and performance (load balancer), latency (HTTP accelerator). Combining them multiplies the benefit, but every extra layer adds complexity, so you add them only when the problem justifies it.
🤔

The Web Development Process: Use Cases, Sequence Diagrams, Wireframes and the SRS

Before writing code you model what the system must do — who uses it, in what order, what it looks like, and what "finished" means.

UML use case diagrams

A UML use case diagram shows the system's actors and their goals. A worked example in the unit is a use case model of a restaurant business.

Use case documentation — flow of events

Create a big table that lists the use cases (the Monopoly example on Canvas). Describe each use case using these fields:

FieldMeaning
NameGive the use case a short name.
GoalThe main goal the use case is trying to achieve.
ActorsActors which initiate a use case and/or are involved in one.
PreconditionsConditions that must be met before the use case can start.
Main flowA full description of the use case.
SubflowsActions or use cases on which the use case depends.
Alternative FlowsAlternative action flows, e.g. from error scenarios.
PriorityHow important the use case is to the system, or the MVP.

Sequence diagrams

Sequence diagrams describe how objects interact with each other and in what order. They are very useful for communicating how several systems interact, or for providing detail around how various actors interact with system components in a multi-step process. An example shows a computer asking a server for emails.

Wireframes

Wireframing lets designers gain a visual "feel" for the site without focusing on graphical detail. The idea is to create a "cartoon" version of the website that enables a preliminary website experience. Wireframes are usually just a series of images, but can sometimes include clicking and linkage between images in the form of a storyboard. Example: a profile-page wireframe.

Software Requirements Specification (SRS)

A Software Requirements Specification details exactly what the system does and does not do. In essence it is a communication tool between project stakeholders and software designers. It is a very important document that lets you say the project is "finished" and mitigates scope creep. It forms the primary specification document and should capture all information regarding the project. Crucially, the diagrams should not introduce new information that is not contained within the SRS.

💡
Why it matters: The SRS is the definition of done. Without it, every new idea becomes an argument about whether the work is finished — that endless expansion is scope creep.
⚠️
Common trap: Diagrams and the SRS must agree. If a diagram shows behaviour the SRS never states, the specification is inconsistent and unverifiable.
🤔

Web Programming I: HTML, the DOM, SPAs and AJAX

HTML describes the page, the DOM is its live in-memory tree, and AJAX lets JavaScript change that tree without reloading the whole page.

HTML

HyperText Markup Language (HTML) is a markup language used for describing web pages. An HTML custom element consists of capabilities such as:

  • Changing HTML content.
  • Updating values of an attribute.
  • Dynamic HTML content (i.e. Date()).
  • Writing directly to the HTML output stream.

DOM

The Document Object Model (DOM) is the browser's live, tree-structured representation of the page, which JavaScript reads and modifies.

Single Page Application (SPA)

A Single Page Application loads once and updates its content dynamically rather than requesting a whole new page from the server for every interaction.

AJAX

Asynchronous JavaScript and XML (AJAX) allows the page to be updated with external data without a full refresh. AJAX is a fundamental aspect of the modern web. The technology evolved:

  • Traditionally we used XHR — clunky.
  • JavaScript libraries like jQuery improved the situation.
  • Native browser APIs such as Fetch are also an option where supported.
ℹ️
Note: Despite the name, AJAX is not tied to XML — modern AJAX commonly exchanges JSON, but the concept (asynchronous background requests) is unchanged.
🤔

Web Programming II: Build Tools, the Request Lifecycle and Web Stacks

Behind a fast site sits automation (task runners) and a repeatable lifecycle that carries a request from URL to rendered page through load balancers and application servers.

Grunt — a JavaScript task runner

  • Grunt is a JavaScript task runner, similar to a Makefile but for HTML front ends.
  • It is a Node.js application, installed via npm.
  • It automates boring, repetitive tasks:
  • Minification of images, CSS, JS and HTML.
  • Dependency linking.
  • Linting (error/style checking).
  • Testing.
  • Gulp is another popular JS task runner.

Web request overview

Client (before the request):

  1. Browser: parse URL.
  2. Browser: check cache.
  3. OS: identify network.
  4. OS: resolve using DNS.
  5. OS: establish TCP connection to the web server.
  6. Browser: submit HTTP request to the web server.

Server:

  1. Load balancers establish the TCP connection and receive the HTTP request.
  2. LB software parses the HTTP header, then routes requests to an application server.
  3. The app server executes back-end website logic, probably connecting to a database.
  4. The app server generates a response and returns it via the TCP connection.

Client (after the response):

  1. Browser: parse response.
  2. Browser: fetch additional resources — assets (CSS, JS, images), establish websocket connection(s), load browser plugins.
  3. Render page.

Web stacks — LAMP and LEMP

The classic web stacks bundle an OS, web server, database and language runtime:

  • LAMP = Linux, Apache, MySQL, PHP.
  • LEMP = Linux, Nginx (the "E"), MySQL, PHP.
URL→cache check→DNS→TCP connect→HTTP request→load balancer→app server→database→response→assets→render
🧠
Memory hook: A task runner is a Makefile for the front end — it does the repetitive chores (minify, lint, test) so you do not.
✅

Databases and Data Modelling

Data modelling turns fuzzy requirements into a precise, normalised entity-relationship diagram that the database schema is built from.

Data modelling is the process of defining and analysing the data requirements of an information system. The process involves three steps:

  1. Identifying the detailed system requirements.
  2. Normalising the entities.
  3. Writing the data model.

Use UML to develop a formalised entity-relationship diagram (ERD) using Crow's foot notation.

Entity-Relationship Diagram (ERD) — A diagram showing the entities in a system, their attributes, and the relationships between them; built in UML using Crow's foot notation.
Normalisation — The process of organising data to reduce redundancy and dependency, so each fact is stored once and the schema stays consistent.
💡
Why it matters: Get the model right and the database enforces your rules for you. Get it wrong and you fight duplicated, inconsistent data forever.
🤔
Pause & predict: In the three-step process, why does normalisation come before writing the data model rather than after?

CI/CD, Testing and Deployment

Continuous integration automatically checks every change, and the deployment strategy decides how a verified change reaches users without downtime.

What continuous integration actually does

  • Linting and static analysis.
  • Building.
  • Testing.
  • Publishing, releasing and deploying.

Testing types

  • Unit testing — test individual units of code in isolation.
  • Integration testing — test that units work together.
  • Acceptance testing — test that the system meets the agreed requirements.
  • Regression testing — test that previously working behaviour has not broken.
  • System testing — test the complete, integrated system as a whole.

Types of deployment

StrategyMechanismTrade-off
Rolling deploymentProgressively deploy/release the new version until the entire pool has been updatedWill serve a mix of old/new code and pages during the rollout
Blue-green deploymentDo a hard switch over of all traffic to new infrastructure/codeClean cut-over, but requires two environments

Version control

You should be familiar with Git and its most common features — push, commit and revert.

🧠
Memory hook: Rolling = replace servers a few at a time (mixed versions briefly). Blue-green = flip the switch all at once (no mix).
💡
Why it matters: CI catches problems automatically on every change, so defects are found early and cheaply rather than in production.
🤔

Web Security: The Vulnerability Checklist

For every vulnerability you must be able to state three things: what it steals, how it attacks, and how to prevent it.

You should understand these vulnerabilities regarding (a) what they steal, (b) how they attack, (c) how to prevent.

VulnerabilityWhat it stealsHow it attacksHow to prevent
SQL injection (SQLi)Database contents — credentials, personal dataInjects SQL through unsanitised input so the query runs attacker commandsParameterised queries/prepared statements, input validation, least-privilege DB accounts
Cross-site scripting (XSS)Session cookies/tokens; can hijack accountsInjects malicious JavaScript into pages other users view, so it runs in their browserOutput encoding/escaping, input validation, Content Security Policy
Cross-site request forgery (CSRF)Your ability to act as a logged-in userTricks your browser into sending an authenticated request to a site where you are logged inAnti-CSRF tokens, SameSite cookies, re-authentication for sensitive actions
Remote code execution (RCE)Full control of the serverExploits a flaw that lets the attacker run arbitrary code or commandsPatching, input validation, sandboxing, least privilege
Local/Remote File Inclusion (L/RFI)Files and data; can escalate to RCEManipulates a file-path parameter so the app includes an attacker-controlled fileValidate/whitelist file paths, disable remote file inclusion
Distributed Denial of Service (DDoS)Availability — not dataFloods a service from many distributed hosts so real users cannot reach itTraffic filtering/scrubbing, rate limiting, CDN/anycast, load balancing, autoscaling
Broken authenticationAccounts and credentialsWeak passwords, credential stuffing, session hijacking, poor session managementStrong password hashing, multi-factor authentication, secure session handling, rate limiting
⚠️
Common trap: These are not isolated. An L/RFI can lead to RCE, and an XSS can defeat CSRF defences by reading a token. Think in chains, not single bugs.

Memory hook: Ask the same three questions every time — steal, attack, prevent — and you can answer any vulnerability question.

Security Practices and Exam Preparation Strategy

The last pieces are operational — store passwords correctly, patch outdated software, mitigate DDoS — then turn the whole course into a revision plan.

Security miscellaneous

  • You should know how to store passwords and securely perform authentication. Never store passwords in plaintext; use a slow, salted password-hashing algorithm (for example bcrypt) and manage sessions/tokens securely.
  • You should understand the risks of running outdated software — known, publicly documented vulnerabilities remain unpatched, so old versions are an open door.
  • You should be familiar with DDoS attacks and mitigations.

Glossary

Every term you need to speak this week's language.

OSI model
A layered way of conceptualising network systems; this course focuses on Layers 3 (network), 4 (transport) and 7 (application).
DHCP
Dynamic Host Configuration Protocol: assigns a machine its IP address, subnet mask, default gateway and nameservers when it joins a network.
DNS
Domain Name System: translates a URL/domain name into an IP address.
SSH
Secure Shell: allows web-based server administration and remote code execution, typically over TCP port 22.
BGP
Border Gateway Protocol: provides interconnectivity and routing between large networks.
TCP
Transmission Control Protocol: a Layer 4 protocol guaranteeing in-order delivery using a handshake; e.g. SSH on TCP/22.
UDP
User Datagram Protocol: a best-effort Layer 4 protocol that sends datagrams with no handshake and no acknowledgement; e.g. DNS on UDP/53.
HTTP cookie
A small piece of data set by a website and stored in the browser, automatically sent with every request to that server.
HTTP status code
A three-digit response code whose first digit signals the class: 1xx informational, 2xx success, 3xx redirection, 4xx client, 5xx server.
Load balancer
Software or hardware that distributes workload across multiple servers to improve performance and reliability; e.g. HAProxy, Nginx, Varnish.
HTTP accelerator
A caching HTTP reverse proxy that stores server responses in memory to reduce the time taken to serve content; e.g. Varnish, Squid, Nginx.
Use case
A description of an actor's goal when interacting with a system; documented with name, goal, actors, preconditions, main flow, subflows, alternative flows and priority.
Software Requirements Specification (SRS)
The primary specification document stating exactly what the system does and does not do; the definition of "finished" that mitigates scope creep.
DOM
Document Object Model: the browser's live, tree-structured representation of a page that JavaScript reads and modifies.
AJAX
Asynchronous JavaScript and XML: updates a page with external data without a full refresh; implemented via XHR, jQuery or Fetch.
Entity-Relationship Diagram (ERD)
A UML diagram of entities, attributes and relationships, drawn with Crow's foot notation.
CI/CD
Continuous Integration / Continuous Delivery: automating linting, building, testing and deployment on every change.
SQL injection (SQLi)
Injecting SQL through unsanitised input to steal or alter database contents; prevented with parameterised queries and least privilege.
Cross-site scripting (XSS)
Injecting malicious JavaScript into pages others view, stealing session tokens; prevented with output encoding and CSP.
Cross-site request forgery (CSRF)
Making a logged-in user's browser send an unwanted authenticated request; prevented with anti-CSRF tokens and SameSite cookies.
Remote code execution (RCE)
Exploiting a flaw to run arbitrary code on a server; prevented by patching, validation and sandboxing.
Local/Remote File Inclusion (L/RFI)
Manipulating a file-path parameter so the app includes an attacker-controlled file; prevented by whitelisting paths.
Distributed Denial of Service (DDoS)
Flooding a service from many distributed hosts to destroy availability; mitigated with scrubbing, rate limiting and CDNs.
bcrypt
A slow, salted password-hashing algorithm used to store passwords so a database leak does not expose plaintext credentials.

Q2

What are the short-answer and essay formats, and what is expected regarding coding and Django?

Answer: Short-answer questions generally give a recommended number of words/paragraphs and each specifies its mark value. The example (5 marks) asks you to describe the key characteristics of a DDoS attack and prompts you to consider a complex attack scenario, what can lead to the attack, and how it impacts stakeholders including long-term consequences — each prompt is mark-bearing, so answer each explicitly. The final two questions are longer-form essays that present two scenarios with several sub-questions. You will not be asked to write or test code, but you should be familiar with the overall front-end and back-end development process, and you may be asked about Django as a framework and its features — ORM, User module and templating — with an emphasis on concepts over implementation detail.
Q3

What does DHCP provide a machine, and what is it the first thing to check for?

Answer: DHCP provides an IP address (identifying you on the local network), a subnet mask (defining what "local" means), a default gateway (a host that routes packets to non-local IPs) and nameservers (a DNS server to resolve domain names). It is the first thing to check if you cannot reach any web sites.
Q4

Compare TCP and UDP on guarantees, acknowledgement and ports.

Answer: Both are Network Layer 4 protocols. TCP guarantees in-order delivery to the application layers above, uses a handshake, and is associated with the TCP flooding attack. UDP is best effort, sends datagrams rather than segments, does not acknowledge or re-transmit packets unless the application layer does so, and enforces no handshake. Both need port designations — e.g. SSH on TCP/22 and DNS on UDP/53.
Q5

List the HTTP methods and what each does, then explain the two cookie headers.

Answer: GET requests data about a specified resource; POST creates a resource; PUT creates/updates a resource; PATCH partially modifies a resource; DELETE deletes the specified resource; OPTIONS returns the supported methods for the resource; HEAD is a GET without the response body. For cookies, the request header Cookie carries stored cookies to the server (e.g. Cookie: username=abc123; authToken=4f3e) and the response header Set-Cookie stores them (e.g. Set-Cookie: username=abc123). Consistency is key.
Q6

Walk through the cookie-based login flow.

Answer: (1) The user visits the site for the first time — no cookie. (2) They submit the login form with username and password — still no cookie. (3) The server generates an authentication token and responds with Set-Cookie: token=[auth-tok]. (4) On the next visit the client sends Cookie: token=[auth-tok]. (5) The server recognises the token and knows the request came from that user.
Q7

Give the five HTTP status-code classes with an example of each.

Answer: 1xx Informational (100 Continue, 101 Switching Protocols); 2xx Success (200 OK, the standard response); 3xx Redirection (301 Moved Permanently, 302 Found/Moved Temporarily, 304 Not Modified); 4xx Client (404 Not Found); 5xx Server (502 Bad gateway).
Q8

Explain the three scaling additions, what problem each solves, and why they are combined.

Answer: A separate DB server removes the database from the application server to eliminate resource contention and improves security by taking the database out of the DMZ/public internet. A load balancer distributes workload across multiple servers for better performance and reliability, with surviving servers handling traffic when one fails (HAProxy, Nginx, Varnish). An HTTP accelerator is a caching reverse proxy that stores responses in memory to reduce serving time (Varnish, Squid, Nginx). Combining them — load-balancing caching servers as well as application servers, and using database replication — lets you reap the benefits of each without introducing too many issues or complexity.
Q9

What fields document a use case, and what is an SRS for?

Answer: A use case is documented with Name, Goal, Actors, Preconditions, Main flow, Subflows, Alternative Flows and Priority, usually in a big table of use cases. A Software Requirements Specification details exactly what the system does and does not do; it is a communication tool between stakeholders and designers, the primary specification document, and it lets you declare the project "finished" while mitigating scope creep. Diagrams must not introduce information not in the SRS.
Q10

What are sequence diagrams and wireframes used for?

Answer: Sequence diagrams describe how objects interact with each other and in what order; they communicate how several systems interact or detail how actors interact with components in a multi-step process. Wireframes give designers a visual "feel" for the site without graphical detail — a "cartoon" version enabling a preliminary experience, usually a series of images but sometimes a clickable storyboard.
Q11

What does AJAX do, and how has the technology evolved?

Answer: AJAX (Asynchronous JavaScript and XML) allows the page to be updated with external data without a full refresh and is fundamental to the modern web. Traditionally XHR was used but was clunky; JavaScript libraries like jQuery improved things; native browser APIs such as Fetch are an option where supported.
Q12

What does continuous integration do, and name the testing types and deployment strategies.

Answer: CI performs linting and static analysis, building, testing, and publishing/releasing/deploying. Testing types are unit, integration, acceptance, regression and system testing. Deployment strategies are rolling deployment (progressively update the pool, briefly serving mixed old/new code) and blue-green deployment (a hard switch of all traffic to new infrastructure/code). You should also know Git push, commit and revert.
Q13

What are the three steps of data modelling and how is the model expressed?

Answer: Data modelling is the process of defining and analysing the data requirements of an information system. The steps are: identify the detailed system requirements, normalise the entities, and write the data model. The model is expressed using UML to develop a formalised entity-relationship diagram (ERD) in Crow's foot notation.
Q14

For each of SQLi, XSS, CSRF, RCE, L/RFI, DDoS and authentication, state what it steals, how it attacks and how to prevent it — and what should you know about password storage, outdated software and DDoS mitigation?

Answer: SQLi steals database contents by injecting SQL through unsanitised input; prevent with parameterised queries, validation and least privilege. XSS steals session cookies/tokens by injecting JavaScript into pages others view; prevent with output encoding and CSP. CSRF steals your ability to act as a logged-in user by making your browser send an authenticated request; prevent with anti-CSRF tokens and SameSite cookies. RCE steals full server control by exploiting a flaw to run arbitrary code; prevent with patching, validation and sandboxing. L/RFI steals files/data (and can escalate to RCE) by manipulating file-path parameters; prevent by whitelisting paths. DDoS steals availability by flooding from many hosts; mitigate with scrubbing, rate limiting, CDNs and autoscaling. Broken authentication steals accounts via weak passwords, credential stuffing and session hijacking; prevent with strong hashing, MFA and secure session handling. You should also know how to store passwords (never plaintext — slow salted hashing) and perform authentication securely, understand that outdated software leaves publicly documented vulnerabilities unpatched, and know DDoS mitigations.
