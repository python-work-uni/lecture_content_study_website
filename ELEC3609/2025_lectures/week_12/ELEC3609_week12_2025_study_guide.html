Exam Structure & Time Plan

The final exam is comprised of 22 questions split into 3 sections, and questions are worth varying amounts of marks, so allocate enough time to complete each section. There are 10 minutes of reading time. There are two separate exams — ELEC3609 (Paper 20.A) and ELEC9609 (Paper 20.B) — so make sure you complete the correct one.

Exam Instructions & Rules

  • Duration — 2 hours and 10 minutes (130 minutes) total, including 10 minutes of reading time.
  • Reading time — You can start writing whenever you are ready, but you are strongly encouraged to use the time to plan and structure your responses.
  • Format — Paper-based. Attempt all questions and follow the instructions for each question carefully.
  • Answer sheet — Keep it clean and neat, and clearly indicate the question number and section number for every answer.

Coding Scope

  • You will not be asked to write code during the exam.
  • You will not be asked to test code during the exam.
  • You should be familiar with the overall web development process, both front-end and back-end.
  • You may be asked about Django as a framework or the features it provides (ORM, User module, templating). This is about the concepts, not specific implementation details.
✅
Exam Tip:: Know the ideas behind ORM, authentication and session management, and MVC/MVT templating. You will never be asked to type Python on paper.

Short & Essay Answer Strategy

Short-answer questions generally give a recommended number of words or paragraphs, and every question specifies the number of marks.

The 5-Mark "Rule of 4"

For a question such as "Describe the key characteristics of a DDoS attack" (5 marks), structure your answer into four logical components:

  1. Core definition and characteristics — define the mechanism precisely (1-2 marks).
  2. Attack scenario / context — describe a realistic complex scenario where it might be exploited (1 mark).
  3. Root causes / vulnerabilities — explain what system weaknesses lead to the attack (1 mark).
  4. Stakeholder and system impact — analyse long-term operational, financial, or security consequences (1 mark).

Essay Section

  • The final two questions require longer-form answers.
  • You are presented with two scenarios and asked several sub-questions related to them (e.g., scaling a web system, resolving a security breach, or designing a CI/CD pipeline).
  • Answers must address every sub-question thoroughly, using clear engineering terminology and structured reasoning.
🧠
Memory Hook:: For a 5-mark answer, use Definition → Scenario → Cause → Impact (the "Rule of 4").

The OSI model is a way of conceptualising network systems as layers. Throughout this course you need to be familiar with Layers 3, 4, and 7.

LayerNameCore Protocols & Functionality

Layer 4TransportTCP, UDP — end-to-end transport and port addressing
Layer 3NetworkIP (IPv4/IPv6), BGP — host addressing and routing
Layer 2Data LinkIEEE 802.11 (WiFi), Ethernet — frame switching
Layer 1PhysicalCopper line, COAX, fibre, radio
💡
Why It Matters:: Most exam questions live at Layer 4 (TCP/UDP) and Layer 7 (HTTP), but you must be able to place them correctly and name the layer.
05

DHCP & Core Protocols

When you connect to a network, your computer is usually configured automatically by DHCP (Dynamic Host Configuration Protocol), which supplies four things:

  1. IP address — identifies you on the local network.
  2. Subnet mask — defines what "local" means with regard to your IP address.
  3. Default gateway — a host that can route packets to non-local IP addresses.
  4. Nameservers — a host used to resolve domain names, i.e., a DNS server.

Other common web protocols:

  • DNS (Domain Name System) — translates a URL/domain name to an IP address (UDP/53, and TCP/53 for large transfers).
  • SSH (Secure Shell) — allows web-based server administration and remote code execution (TCP/22).
  • BGP (Border Gateway Protocol) — handles interconnectivity and routing between networks.
⚠️
Common Trap:: If you cannot reach any websites, the very first thing to check is your DHCP configuration (IP, subnet mask, gateway, and DNS).
🧠
Memory Hook:: DHCP configures I-S-G-N — IP address, Subnet mask, Gateway, Nameservers.

TCP vs UDP

FeatureTCPUDP
LayerLayer 4 (Transport)Layer 4 (Transport)
ConnectionConnection-oriented (handshake)Connectionless (no handshake)
ReliabilityGuarantees in-order delivery; ACKs and retransmissionBest effort; packets can drop, reorder, or duplicate
Data unitSegmentsDatagrams

PortsSSH TCP/22, HTTP TCP/80, HTTPS TCP/443DNS UDP/53

  • TCP guarantees in-order delivery of data for the layers above it and requires a handshake.
  • UDP sends datagrams with no acknowledgement or retransmission, unless this is performed explicitly at the application layer.
🧠
Memory Hook:: TCP is registered mail (tracked, signed for, in order); UDP is a postcard (fast, dropped in the box, no guarantee).
07

HTTP Methods & Cookies

Common HTTP Methods

  • GET — request data about a specified resource.
  • POST — create a resource.
  • PUT — create or completely update a resource.
  • PATCH — partial modification of a resource.
  • DELETE — delete the specified resource.
  • OPTIONS — return the HTTP methods supported for that resource.
  • HEAD — equivalent to a GET request without the response body.

Consistency is key: use the same method semantics across your whole API.

Cookies & State

HTTP is natively stateless, so cookies let a server maintain state. An HTTP cookie is a small piece of data, set by a website, that is stored in the user's browser. Browsers automatically include all cookies set by a server with every HTTP request sent to that server.

DirectionHeader
RequestCookie: username=abc123; authToken=4f3e
ResponseSet-Cookie: username=abc123

A Typical Login Flow

  1. User visits the website for the first time — no cookie.
  2. User submits the login form with username and password — still no cookie.
  3. Server generates an authentication token (auth-tok) and responds with Set-Cookie: token=[auth-tok].
  4. On the next visit, the client sends Cookie: token=[auth-tok].
  5. The server recognises the token and knows the request came from that user.
💡
Why It Matters:: Cookies are how stateless HTTP remembers who you are — which is exactly why they are a favourite target for attackers (XSS, CSRF).
08

Scaling Web Architecture

As user traffic grows, architecture evolves from a single server into distributed, fault-tolerant infrastructure.

  1. Single server — web server, application server, and database on one host. Simple, but a single point of failure with CPU/RAM contention between database queries and app execution.
  2. Separate database server — separates the database to eliminate resource contention, and increases security by removing the database from the DMZ/public internet into a private subnet.
  3. Load-balanced application cluster — a load balancer (LB) distributes the workload across multiple servers; if one fails, the others handle incoming traffic until it becomes healthy again. Typical implementations: HAProxy, Nginx, Varnish.
  4. HTTP accelerator / caching reverse proxy — caches the response from a web or application server in memory for a period of time to reduce how long it takes to serve content. Examples: Varnish, Squid, Nginx.
  5. Hybrid architecture — load balance the caching servers in addition to the application servers, and use database replication in a single environment, reaping the benefits of each technique without too much complexity.
Reference
Clients --> Load Balancer --> HTTP Accelerators --> App Servers --> DB Master
                                                                     |
                                                                     +--Replicate--> DB Replica (reads)
💡
Why It Matters:: Each stage trades extra complexity for resilience and scale. You only add the next stage when you actually need it.

Requirements & UML Modelling

Software Requirements Specification (SRS)

An SRS documents exactly what the system does and does not do. In essence it is a communication tool between project stakeholders and software designers, it allows you to say the project is "finished", and it mitigates scope creep. It forms the primary specification document and should capture all information about the project.

⚠️
Golden Rule:: Diagrams should not introduce new information that is not already contained within the SRS.

Use Case Documentation

A use case model shows system boundaries, actors, and interactions. Describe each use case in a big table using fields such as:

FieldPurpose
NameA short name for the use case
GoalThe main goal the use case is trying to achieve
ActorsActors who initiate and/or are involved in the use case
PreconditionsConditions that must be met before the use case can start
Main flowA full description of the use case
SubflowsActions or use cases on which the use case depends
Alternative flowsAlternative action flows, e.g., from error scenarios
PriorityHow important the use case is to the system or MVP

Other Modelling Diagrams

  • Sequence diagrams — describe how objects interact with each other and in what order; very useful for showing how several systems interact or how actors interact with components in a multi-step process.
  • Wireframes — allow designers to gain a visual "feel" for the site without focusing on graphical detail; essentially a "cartoon" version of the website. They are usually a series of images but can include clicking and linkage in the form of a storyboard.
✅
Exam Tip:: If a diagram adds a requirement not in the SRS, that is a defect. The SRS is the single source of truth.

HTML, DOM & Status Codes

  • HTML (HyperText Markup Language) — a markup language used for describing web pages.
  • DOM (Document Object Model) — the browser's tree representation of the page. JavaScript manipulates the DOM dynamically to change HTML content, update attribute values, generate dynamic content (e.g., Date()), or write directly to the HTML output stream.

HTTP Status / Error Codes

RangeCategoryExamples
1xxInformational100 Continue, 101 Switching Protocols
2xxSuccess200 OK — the standard response
3xxRedirection301 Moved Permanently, 302 Found / Moved Temporarily, 304 Not Modified
4xxClient404 Not Found
5xxServer502 Bad Gateway
💡
Why It Matters:: The first digit tells you who is responsible and what to do next — redirect (3xx), fix the request (4xx), or fix the server (5xx).
11

SPA, AJAX & Build Tools

  • Single Page Application (SPA) — a web application that loads a single HTML document and dynamically updates content as the user interacts with it.
  • AJAX (Asynchronous JavaScript and XML) — allows the page to be updated with external data without a full refresh, and is a fundamental aspect of the modern web.
  • The tooling for AJAX has evolved: raw XHR (clunky) → jQuery (a library that improved the situation) → native Fetch API (where supported).
  • Grunt — a JavaScript task runner, similar to a Makefile but for HTML front ends. It is a Node.js application installed via npm, and it automates boring, repetitive tasks:
    • Minification of images, CSS, JS, and HTML
    • Dependency linking
    • Linting (error and style checking)
    • Testing
  • Gulp is another popular JavaScript task runner.

The Web Request, End to End

  1. Browser parses the URL, then checks the cache.
  2. OS identifies the network, resolves DNS, and establishes a TCP connection to the web server.
  3. Browser submits the HTTP request to the web server.
  4. Load balancers establish the TCP connection, receive the request, parse the HTTP header, and route it to an application server.
  5. The app server executes back-end logic (probably connecting to a database) and generates a response, returning it via the TCP connection.
  6. Browser parses the response, fetches additional resources (CSS, JS, images), establishes websockets if required, loads browser plugins, and renders the page.

CI/CD & Deployment Recap

Continuous Integration (CI) automates the path from a code commit to a deployable artifact: linting and static analysis, building, testing, then publishing, releasing, and deploying.

  • Unit testing — tests individual functions/classes in isolation.
  • Integration testing — tests how modules, databases, and APIs work together.
  • System / acceptance testing — tests end-to-end user paths.
  • Regression testing — ensures new features do not break existing capabilities.

Deployment Types

  • Rolling deployment — progressively deploy/release the new version until the entire pool has been updated; it will serve a mix of old and new code/pages.
  • Blue-green deployment — do a hard switch over of all traffic to new infrastructure/code.

Version Control

  • You should be familiar with Git and its most common features: push, commit, and revert.
🧠
Memory Hook:: CI = build, test, publish. CD = release, deploy, monitor.

Web Security & Passwords

You should understand each vulnerability in terms of (a) what it steals, (b) how it attacks, and (c) how to prevent it.

VulnerabilitySteals / TargetsPrevention
SQLiDatabase contents, user credentialsParameterised queries / ORM, input validation
XSSSession cookies, auth tokens, DOM sessionHTML escaping, Content Security Policy, HttpOnly cookies
CSRFUser actions, unauthorized state changesAnti-CSRF tokens, SameSite cookies
RCEServer filesystem, full host compromiseNever pass user input to shell exec calls
L/RFILocal server files, remote malwareWhitelist file paths; avoid dynamic path imports
DDoSAvailability, network bandwidthRate limiting, CDN filtering, IP scrubbing
AuthenticationUser accounts and sessionsSecure hashing and salting, secure session handling

Passwords & Outdated Software

  • Passwords must never be stored in plaintext or reversibly encrypted.
  • Hash them with a strong, slow, salted algorithm (Bcrypt, Argon2, PBKDF2). A unique salt per user means identical passwords produce different hashes, neutralising rainbow-table attacks and fast GPU brute forcing.
  • Running outdated software exposes you to known public exploits — audit dependencies and patch automatically.
  • You should also understand the risks of DDoS attacks and their mitigations.
⚠️
Common Trap:: A salted hash protects the stored password; it does nothing if your query is vulnerable to SQL injection.

Worked Scenarios & Calculations

Scenario 1 • Scoring a 5-Mark Short Answer

Scoring a 5-Mark Short Answer

Question: "Describe the key characteristics of a DDoS attack" (5 marks). A full-mark answer covers all four parts: (1) definition — overwhelming a service with traffic from many distributed sources to exhaust availability; (2) scenario — a botnet floods a retail site during a sale so genuine customers cannot check out; (3) cause — no rate limiting or traffic filtering, so the infrastructure absorbs the flood; (4) impact — lost revenue, reputational damage, and long-term customer distrust.

Scenario 2 • Tracing a Web Request

Tracing a Web Request

Reference
Client: parse URL --> check cache --> identify network --> resolve DNS
        --> TCP connection --> HTTP request
Server: load balancer receives --> routes to app server --> app logic + DB
        --> response returned
Client: parse response --> fetch assets (CSS/JS/images) --> render page
Scenario 3 • Diagnosing a Status Code

Diagnosing a Status Code

A browser shows stale content → the server likely returned 304 Not Modified, telling the client to reuse its cache. An API call fails with 502 Bad Gateway → an upstream server returned an invalid response (a 5xx server error). A missing page returns 404 Not Found (4xx client error). A moved page returns 301 Moved Permanently (3xx redirection).

Scenario 4 • Scaling a Growing Site

Scaling a Growing Site

A startup begins with a single server running the web app and database. As load grows, it moves the database to its own server (removing resource contention and pulling the DB out of the DMZ). Next it adds a load balancer in front of several app servers, then an HTTP accelerator to cache hot responses, and finally database replication so reads spread across replicas while writes go to the master.

Scenario 5 • Blue-Green vs Rolling in Practice

Blue-Green vs Rolling in Practice

A payments platform cannot tolerate users seeing two different versions, so it uses blue-green: deploy v2 to the idle environment, smoke-test it, then flip all traffic at once and keep the old environment ready for an instant rollback. A content site with backward-compatible changes uses rolling to save infrastructure cost, accepting a short window where some requests hit v1 and others v2.

Potential Exam Focus & Practice

Progress: 0 / 13 Mastered
Q1
Describe the exam structure and how you should allocate time.
Answer:
22 questions in 3 sections: MCQ (20 marks, 20 min), Short Answer (55 marks, 70 min), Essay (25 marks, 30 min); 100 marks total in 2 hours, plus 10 minutes of reading time. Allocate time in proportion to marks.
Q2
True or false: the final exam requires writing complete Django Python code blocks on paper.
Answer:
False. The exam does not require writing or testing code; it focuses on high-level web concepts, development processes, and architectural principles, including Django concepts such as ORM and templating.
Q3
How should a 5-mark short-answer question be structured?
Answer:
Four parts — core definition/characteristics, a realistic attack or usage scenario, root causes/vulnerabilities, and stakeholder/system impact (Definition → Scenario → Cause → Impact).
Q4
Which OSI layers matter in this course, and what lives at each?
Answer:
Layer 3 (IP/BGP — addressing and routing), Layer 4 (TCP/UDP — transport and ports), and Layer 7 (HTTP/HTTPS/SSH/DNS — application data).
Q5
What four things does DHCP configure, and what should you check first if a client cannot reach websites?
Answer:
IP address, subnet mask, default gateway, and nameservers (DNS). DHCP configuration is the very first diagnostic check.
Q6
Compare TCP and UDP.
Answer:
TCP is connection-oriented with a handshake, guarantees in-order delivery, uses segments and ACKs, and runs common services on ports 22/80/443. UDP is connectionless, best-effort, uses datagrams with no acknowledgement, and runs DNS on port 53.
Q7
List the common HTTP methods and what each does.
Answer:
GET (read), POST (create), PUT (create/update), PATCH (partial modify), DELETE (remove), OPTIONS (list supported methods), HEAD (GET without a body).
Q8
True or false: browsers automatically include all matching cookies with every subsequent request to that server.
Answer:
True. Browsers automatically append matching domain cookies in the Cookie: header, which is how sessions are maintained over stateless HTTP.
Q9
Explain the core architectural reason for moving a database onto a separate server.
Answer:
It eliminates CPU/RAM resource contention between database queries and application execution, and improves security by removing the database from the public DMZ into a private subnet.
Q10
What is the primary purpose of a Software Requirements Specification (SRS)?
Answer:
It is the authoritative communication contract between stakeholders and developers, defining what the system must and must not do, preventing scope creep, and establishing when the project is "finished".
Q11
How do anti-CSRF tokens defend against CSRF?
Answer:
CSRF relies on browsers automatically sending session cookies. An anti-CSRF token adds a unique, unpredictable secret in the request payload/header that a third-party attacker site cannot read or forge.
Q12
Why must passwords be salted as well as hashed?
Answer:
A unique salt per password ensures identical passwords produce different hashes, neutralising pre-computed rainbow-table attacks; combined with a slow algorithm (Bcrypt/Argon2/PBKDF2) it also resists fast brute forcing.
Q13
What is the main operational difference between blue-green and rolling deployment?
Answer:
Blue-green uses two identical environments and switches 100% of traffic instantly (2x infrastructure), giving zero version mixing and instant rollback; rolling updates instances incrementally in a single pool (1x infrastructure) but temporarily serves mixed versions.
