Continuous Integration and Development: Move Fast and Break Nothing

Continuous Integration (CI) is the engineering discipline of merging every developer's work into a shared mainline several times a day, then automatically linting, building, testing, publishing and deploying it. This guide explains the "Integration Hell" problem CI was invented to solve, the goals and trade-offs of a CI system, the three kinds of conflict, and the full pipeline from code style checks to post-deployment telemetry.

Read this first: CI is not a tool you install — it is a habit of integrating small changes constantly, backed by an automated pipeline that gives you fast, trustworthy feedback. Every concept this week (conflicts, stale branches, linting, building, testing, deployment) exists to serve one goal: keep the mainline working so you spend your time building features, not untangling merges.

The Problem: Integration Hell

Long ago teams built features in isolation for months, then tried to merge everything at once — and the merge usually broke the build.

Before Continuous Integration existed, teams of developers would each work on their own features until it was time to integrate them into a coherent product. Only then, in the Integration Phase, would the changes from tens or hundreds of developers be merged into a common codebase. Because each developer had been working against an old, private copy of the code, that merge frequently failed to compile due to conflicts.

This state of paralysis has a name.

Integration Hell — A state where new changes cannot be integrated into the mainline codebase quickly or effectively. Teams effectively spend more time checking in code than writing it.
💡
Why it matters: Integration Hell is the disease; Continuous Integration is the cure. If you understand the pain of a late mega-merge, every CI practice later in this guide will feel obviously necessary rather than bureaucratic.

Why Integration Hell Happens

The lecture names two root causes, each with a matching remedy:

CauseWhy it hurtsRemedy
Changes have deviated too much from masterYour branch no longer resembles the mainline, so merging is a huge, error-prone jobRebase often
The change itself is too large and touches too many filesA single integration event becomes enormous and hard to reason aboutScope changes correctly; prefer small changes over big changes

The emotional cost is real too — teams would sometimes emerge victorious from integration, and other times the project would fail, "causing much weeping and gnashing of teeth."

🤔
Pause & predict: Two developers each spend six weeks on separate branches and then merge on the same day. Which of the two root causes above is dominating their problem, and what single habit would have prevented it?
✅
Exam tip: When asked "what problem does CI solve?", do not just say "merge conflicts." Name Integration Hell explicitly, give both root causes, and give the matching remedy (rebase often; prefer small changes).

What Continuous Integration Is

CI is the practice of merging all developers' working copies into a shared mainline codebase several times a day.

Continuous Integration (CI) is the practice of merging all developers' working copies to a shared mainline codebase several times a day. The word "continuous" is the key: integration stops being a phase at the end of the project and becomes a small, constant activity.

Continuous Integration — The practice of merging all developers' working copies to a shared mainline codebase several times a day.

The mental model

Think of the mainline (the shared branch, usually master) as a river that must always be healthy. Every developer is a small tributary that joins the river many times a day, so each joining is small enough to verify quickly. Compare that with the old model, where dozens of tributaries all tried to join at once at the very end:

Old: Integration Phase

  • Developers work alone for a long time
  • One giant merge at the end
  • Build fails; conflicts everywhere
  • Time is lost untangling, not building
  • High risk the project fails outright

CI: Continuous Integration

  • Developers merge several times a day
  • Many tiny merges, each easy to check
  • Failures are caught immediately
  • Time is spent on new features
  • Confidence that master always works
🧠
Memory hook: "Several times a day, small changes all the way." If your integration happens once a month, it is not continuous — it is a phase.

Goals of Continuous Integration

CI exists to prevent Integration Hell while giving every change a fast, trustworthy, reproducible verdict.

The lecture lists seven goals. Together they explain why an organisation bothers to build CI at all.

  1. Avoid Integration Hell — a state in which developers spend more time checking code into the repository than writing the code itself.
  2. Provide an isolated, reproducible test environment — so a test that passes for one developer passes for everyone, every time.
  3. Provide an isolated, reproducible build environment — so the build does not depend on whatever happens to be installed on someone's laptop.
  4. Increase deployment confidence — you trust that what you ship will work, because it has already been verified.
  5. Enforce coding style and code quality — standards are checked automatically, not argued about in review.
  6. Test code in multiple environments — catch issues that only appear on a different OS, runtime or browser.
  7. Streamline development workflows and increase productivity — remove manual, repetitive, error-prone steps.
💡
Why it matters: Notice that only goal 1 is about conflicts. The rest are about confidence and reproducibility. A CI system that only merges but never tests or builds in a clean environment has missed most of the point.

Considerations: the four trade-offs

A CI setup is a design decision, and four properties are always in tension:

ConsiderationThe question it answers
SpeedHow fast does a developer get feedback after pushing?
ReproducibilityDoes the same input always produce the same result?
ReliabilityDoes the pipeline pass/fail consistently, without flaky results?
ClarityCan a developer understand why a job failed and how to fix it?
🧠
Memory hook: S-R-R-C — Speed, Reproducibility, Reliability, Clarity. If a CI system is slow or flaky, developers stop trusting it and start ignoring it.

Conflicts: The Three Failure Modes

"Conflict" is an umbrella term for every way integration can fail — and there are three distinct kinds.

By encouraging small, incremental changes, adopting CI aims to minimise the cost of resolving conflicts. Crucially, the lecture broadens the word "conflict": there are different ways an application can fail during or after integration, and all of them count as conflicts.

Conflict typeWhat has happenedHow it shows up
Merge conflictDevelopers modified the same file concurrentlyGit cannot combine the edits automatically
Functional conflictDevelopers modified files concurrently such that the resulting system does not compile/buildThe build breaks
Logical conflictDevelopers modified files concurrently such that the system does not execute successfullyThe build succeeds, but the program misbehaves at runtime
⚠️
Common trap: A merge conflict is the easy one — it is loud and obvious. Functional and logical conflicts are more dangerous because each developer's change was individually valid; only the combination is broken. Logical conflicts in particular can slip past a build and only appear at runtime.

Can we avoid conflicts altogether?

The best way to minimise the cost of resolving conflicts is to avoid conflicts altogether — but the lecture is honest that this is difficult.

  • Ideally, components of an application would be independent, with very few dependencies between them.
  • Practically, it makes sense to write reusable modules shared between components — which creates coupling.
  • Even with well-isolated components, some process must build all the separate modules into a single application. That process is called integration.
  • Naturally, the more developers committing to a codebase, the higher the risk of conflicts.
🤔
Pause & predict: If two developers edit different files but their combined code makes a function return the wrong value, which conflict type is this — and would a compiler or a linter catch it?

Stale Branches and the Cost of Drift

The longer a branch stays checked out, the more it drifts, and the more expensive it becomes to rejoin the mainline.

There is a general expectation that HEAD (usually the master branch) is always in a functional state. As a result, conflicts are expected to be resolved by the developer who is last to land their changes — the person whose merge actually breaks something owns the fix.

The central risk is branch staleness:

  • The longer a branch of code remains checked out, the greater the risk of multiple integration conflicts and failures when it is reintegrated into the mainline.
  • When developers submit code, they must first update (merge or rebase) their code to reflect changes made in the repository since they took their copy.
  • The more changes the repository has accumulated, the more work developers must do before submitting their own changes.

What goes wrong when branches go stale

  1. Rebasing your changes onto master is not fun — it is tedious and error-prone.
  2. Test results may no longer be valid after the change has been merged or rebased, because the code being tested is no longer the code that was tested.
  3. Eventually the repository may differ so much from the developers' baselines that the time to integrate exceeds the time it took to make the original changes.
  4. In the worst case, developers must discard their changes and completely redo the work, because the original purpose of the change may now be invalid or require a completely different approach.
⚠️
Common trap: Do not confuse staleness with laziness. A branch can be stale simply because the mainline moved fast. The remedy is mechanical: rebase often and keep branches short-lived.

Benefits of Small Incremental Changes

Small change sets make bugs cheap to find, cheap to revert, and cheap to reason about.

This section is the payoff of everything above. When you make incremental changes:

  • Integration bugs are detected early and are easy to track down because the change sets are small. This saves both time and money over the lifespan of a project.
  • Failures are cheap to undo. When unit tests fail or a bug emerges, if developers need to revert the codebase to a bug-free state without debugging, only a small number of changes are lost — precisely because integration happens frequently.
💡
Why it matters: The value of a small change is not just "less to merge." It is that a small diff has a small search space. When something breaks, you know it broke in one of the last few small commits, not somewhere across six weeks of work.
🧠
Memory hook: Small diffs = small blame radius. The commit that broke it is almost always the commit you just pushed.

What CI Actually Does: The Pipeline

A CI job is a fixed sequence: lint, build, test, then publish/release/deploy.

A CI system is not magic — it runs a defined sequence of stages on every change. The lecture enumerates them:

Linting & static analysis→Building→Testing→Publishing→Releasing & Deploying

Testing itself expands into four ordered layers:

Unit testing→Integration testing→Acceptance testing→Regression testing
StagePurpose in one line
Linting and static analysisCatch errors, style violations and risky constructs without running the code
BuildingTurn source into a runnable/optimised artifact (compilation plus much more)
TestingVerify behaviour from the unit level up to the end-to-end user level
Publishing, releasing, deployingExpose artifacts and deliver the new version to users
ℹ️
Note: Regression testing is not strictly "fourth in line." It is a category of test added whenever a bug is fixed, and those tests then run as part of the suite on every future change.

Linting and Static Analysis

Linting and static analysis both inspect code without running it — linting is the fast, always-trustworthy subset.

Both tools analyse source code without executing it, but they differ in scope, speed and trustworthiness.

Linting — The process of running a program that analyses code for potential errors; it can also enforce code style guides.
Static analysis — Also called static code analysis, a method of program debugging done by examining the code without executing it. It provides an understanding of code structure and helps ensure the code adheres to industry standards.

History and relationship

Lint was the name originally given to a particular program that flagged suspicious and non-portable constructs (likely to be bugs) in C language source code. Semantically, linting and static analysis are very similar tools. Generally, however, linting is a subset of static analysis, consisting only of rules that are fast and accurate.

Linting vs static analysis at a glance

PropertyLintingStatic Analysis
False positivesZero false positivesSome tolerance for false positives
Auto-fixViolations can often be automatically fixedViolations cannot usually be auto-fixed
ScopePerformed on a file-by-file basisGenerally analyses the entire code base
SpeedFast, rapid feedbackSlower, but comprehensive

Which rules belong to which?

Linting rulesStatic analysis rules
Coding styleCyclomatic complexity
Deprecated classes/functionsType inference
Inefficient language constructsNpath complexity
Naming conventionsUnused classes/functions
Spelling mistakes

🧠
Memory hook: Linting is the spell-checker — instant, per-file, usually auto-correctable. Static analysis is the editor's full manuscript review — slower, whole-project, but catches structural problems like complexity and type errors.
🤔

Building: More Than Compilation

In CI, "building" means producing a deployable artifact — compilation is only one of many steps.

Traditionally, building refers to compilation: the translation of source code into object code. However, dynamic languages (PHP, Python, Ruby) do not require compilation, so "build" must mean something broader in a CI context.

Building backend code

For backend code, building usually involves more than just compilation:

  • Optimising the autoloader (if applicable) or symbol map
  • Pre-populating caches
  • Pre-rendering templates
  • Vendoring dependencies

Building frontend code

Building frontend code is a different process:

  • Bundling CSS/JavaScript assets
  • Minifying images (lossy vs lossless compression)
  • Minifying CSS/JavaScript assets (obfuscation, whitespace)
  • Transpiling JavaScript (source-to-source compilation)
  • Vendoring dependencies
ℹ️
Note: "Vendoring dependencies" appears in both lists — it means copying third-party libraries into your repository so the build is self-contained and reproducible rather than depending on an external package source that might change.
✅
Exam tip: If asked why dynamic languages still need a build step, say: they skip compilation, but they still need caches warmed, templates pre-rendered, dependencies vendored and (for frontend) assets bundled and minified.

Testing: The Four Layers

Tests run from the smallest unit upward, trading speed for realism at each step.

CI runs multiple kinds of tests, each answering a different question and running at a different cost.

Unit testing

Verifies individual pieces of code in isolation.

  • Language-specific tooling: Golang go test; Java JUnit; Python Nosetests/Pytest; PHP PHPUnit; Ruby RSpec.
  • Basic criteria:
  • Fast to execute
  • One-to-one mapping with source code
  • Zero or minimal dependencies (other code, filesystem, network, etc.)
  • White box testing — the tester knows the internal implementation
  • Can be executed in different environments to help future-proof your application

Integration testing

Ensures that different components of your application interact in the expected manner.

  • Should be executed after unit tests
  • Should focus on testing the API rather than implementation details
  • Black box testing — the tester does not rely on internal knowledge

Acceptance testing

Focuses on functionality from a user perspective.

  • Tests the application end-to-end
  • Very slow (relatively), but very important
  • Includes cross-browser testing

Regression testing

Used to prevent bugs from reoccurring.

  • When fixing a bug, consider adding a regression test
  • Regression tests often cover bizarre edge cases

Comparison

Test typeScopePerspectiveSpeed
UnitSingle unit, isolatedWhite boxFastest
IntegrationComponent interactionsBlack boxModerate
AcceptanceEnd-to-end, user-facingUser / black boxVery slow
RegressionPreviously fixed bugsMixedVaries (run always)
💡
Why it matters: The order is deliberate. Fast, cheap unit tests fail first so you get quick feedback; slow, realistic acceptance tests run last because they are expensive. This is the test pyramid idea in practice.
🧠
Memory hook: Unit = one box, white. Integration = between boxes, black. Acceptance = whole product, user's eyes. Regression = the ghost of bugs past.
🤔

Publishing and Continuous Deployment

Publishing exposes build artifacts to the deployment process; Continuous Deployment triggers deployment automatically.

At the completion of a CI job you typically produce one or more artifacts. What those artifacts are depends on the programming language, the tooling, and the deployment process.

Examples of artifacts

  • Archive (tar, zip)
  • Binary
  • Mobile application (.apk)
  • Package (deb, rpm)

Publishing is the process that exposes artifacts from CI to the deployment process — it is the hand-off between "we built and tested something" and "we are going to ship it."

Automatic deployment

If you are feeling brave, you can trigger deployments automatically at the completion of your CI job. This is referred to as Continuous Deployment.

⚠️
Common trap: Publishing ≠ deploying. Publishing makes an artifact available; deployment actually delivers it to users. You can publish on every commit but still deploy manually.
ℹ️
Note: Continuous Deployment means every passing change goes live automatically — no human gate. This is distinct from Continuous Delivery, where deployment is automatic-ready but triggered by a human decision.

Deployment: Definition and Strategies

Deployment delivers the latest version to users; the strategy you choose decides how risky that moment is.

Deployment is the process by which the latest version of an application is delivered to the users.

Examples of deployment:

  • Submitting an APK to the Google Play Store
  • Updating code on a fleet of production servers
  • Pushing files to an S3 bucket

The deployment questions to answer

  • How often to deploy?
  • Use existing infrastructure or new?
  • Automated or manual?
  • Monitoring
  • Rolling back

Types of deployment

StrategyHow it worksKey consequence
Rolling deploymentProgressively deploy/release the new version until the entire pool has been updatedWill serve a mix of old and new assets during the rollout
Blue-green deploymentSpin up an entirely new set of infrastructure with the new code, then do a hard switch-over of all traffic to the new infrastructure/codeInstant cut-over; old environment remains as a fallback

Rolling deployment

  • Update servers a few at a time
  • No big-bang switch
  • Users may hit old and new versions
  • Easy to pause or halt mid-rollout

Blue-green deployment

  • Stand up a whole new environment
  • Switch all traffic at once
  • Users hit exactly one version
  • Requires double infrastructure (temporarily)
✅
Exam tip: The distinguishing phrase for rolling is "mix of old and new assets"; for blue-green it is "hard switch over of all traffic." Use those exact ideas in your answer.

Post-Deployment Verification

Shipping is not the finish line — you must verify that the change works in the hands of real users.

Now that our changes are in the hands of users, how do we verify that everything is working as expected? As covered in an earlier week (Week 6), this is the time to look at:

  • Testing — continue validating behaviour in the live environment
  • Logging — record what the system does so failures can be reconstructed
  • Real-time Telemetry — stream live metrics about health and performance
💡
Why it matters: Tests passing in CI proves the code works in a controlled environment. Post-deployment verification proves it works in production, with real traffic, real data and real users — where the consequences of failure actually matter.

The complete lifecycle, end to end

Write small change→Commit often→CI lints→CI builds→CI tests→Publish artifact→Deploy (rolling/blue-green)→Post-deploy monitoring

Glossary

Every term you need to speak this week's language.

Continuous Integration
The practice of merging all developers' working copies to a shared mainline codebase several times a day.
Integration Hell
A state where new changes cannot be integrated into the mainline codebase quickly or effectively, usually from large or long-lived changes.
Integration Phase
The old practice of merging all developers' work into a common codebase in one late, large event.
Mainline
The shared, canonical codebase (typically the master branch) that all developers merge into.
HEAD
The tip of the currently checked-out branch, generally master, which is expected to always be in a functional state.
Rebase
Replaying your commits on top of the latest mainline so your branch reflects upstream changes; the standard remedy for drift.
Merge conflict
A conflict where developers have modified the same file concurrently.
Functional conflict
A conflict where concurrent modifications mean the resulting system does not compile or build.
Logical conflict
A conflict where concurrent modifications mean the system does not execute successfully, even though it builds.
Stale branch
A branch left checked out for a long time that has drifted from the mainline, raising integration risk.
Linting
Running a program that analyses code for potential errors, per file, with zero false positives and often auto-fixable results; also enforces style guides.
Static analysis
Debugging by examining code without executing it; whole-codebase, slower, comprehensive, tolerating some false positives.
Cyclomatic complexity
A static-analysis metric counting the number of independent paths through code.
Npath complexity
A static-analysis metric measuring the number of acyclic execution paths through a function.
Type inference
Static analysis that determines the types of expressions without explicit annotations.
Build
In CI, the process of producing a deployable artifact — compilation plus caching, template pre-rendering, vendoring, bundling and minification.
Vendoring dependencies
Copying third-party libraries into the repository so builds are self-contained and reproducible.
Transpiling
Source-to-source compilation, such as converting modern JavaScript into a form older browsers can run.
Unit testing
Fast, white-box testing of individual code units with zero or minimal dependencies and one-to-one mapping to source.
Integration testing
Black-box testing that components interact in the expected manner, focused on the API rather than implementation.
Acceptance testing
Slow, end-to-end testing of functionality from a user perspective, including cross-browser testing.
Regression testing
Tests added when a bug is fixed to prevent it reoccurring; often cover bizarre edge cases.
Artifact
An output of a CI job, such as a tar/zip archive, binary, apk or deb/rpm package, that is exposed to deployment.
Publishing
The process that exposes artifacts from CI to the deployment process.
Continuous Deployment
Automatically triggering a deployment at the completion of a passing CI job.
Deployment
The process by which the latest version of an application is delivered to users.
Rolling deployment
Progressively deploying the new version until the entire pool is updated, serving a mix of old and new assets.
Blue-green deployment
Spinning up entirely new infrastructure with the new code and hard-switching all traffic to it.
Telemetry

Practice Questions

Q1

Define Continuous Integration and state the frequency the lecture specifies.

Answer: CI is the practice of merging all developers' working copies to a shared mainline codebase. The lecture specifies that this happens several times a day.
Q2

What is Integration Hell, and what are the two root causes with their remedies?

Answer: Integration Hell is a state where new changes cannot be integrated into the mainline codebase quickly or effectively. The two causes are (1) changes have deviated too much from master — remedy: rebase often; and (2) the change is too large and touches too many files — remedy: scope changes correctly and prefer small changes over big changes.
Q3

List the seven goals of Continuous Integration.

Answer: (1) Avoid Integration Hell; (2) provide an isolated, reproducible test environment; (3) provide an isolated, reproducible build environment; (4) increase deployment confidence; (5) enforce coding style and code quality; (6) test code in multiple environments; (7) streamline development workflows and increase productivity.
Q4

What are the four considerations for a CI system?

Answer: Speed, Reproducibility, Reliability and Clarity.
Q5

Distinguish merge, functional and logical conflicts.

Answer: A merge conflict occurs when developers modify the same file concurrently and Git cannot combine the edits. A functional conflict occurs when concurrent modifications mean the resulting system does not compile or build. A logical conflict occurs when concurrent modifications mean the system does not execute successfully, even though it may build.
Q6

Why are stale branches risky? Give at least three consequences.

Answer: The longer a branch stays checked out, the more it drifts from the mainline. Consequences: rebasing becomes painful; test results may no longer be valid after merge/rebase; the time to integrate may exceed the time taken to make the original changes; and in the worst case developers must discard their changes and completely redo the work because the original purpose is now invalid.
Q7

What is the difference between linting and static analysis?

Answer: Both inspect code without executing it, but linting is a subset of static analysis consisting only of rules that are fast and accurate. Linting has zero false positives, is performed file-by-file, gives rapid feedback and violations can often be auto-fixed. Static analysis tolerates some false positives, generally analyses the entire codebase, is slower but comprehensive, and violations cannot usually be auto-fixed.
Q8

Classify these rules as linting or static analysis: coding style, cyclomatic complexity, unused variables, type inference, unreachable code, Npath complexity.

Answer: Linting: coding style, unused variables, unreachable code. Static analysis: cyclomatic complexity, type inference, Npath complexity.
Q9

Dynamic languages like PHP, Python and Ruby do not require compilation. What does "building" mean for them in CI?

Answer: For backend code it means more than compilation: optimising the autoloader or symbol map, pre-populating caches, pre-rendering templates, and vendoring dependencies. For frontend code it means bundling CSS/JavaScript assets, minifying images (lossy vs lossless), minifying CSS/JavaScript assets (obfuscation, whitespace), transpiling JavaScript (source-to-source compilation), and vendoring dependencies.
Q10

Name the four testing layers in CI and give one distinguishing property of each.

Answer: Unit testing — fast, white-box, one-to-one mapping with source, zero or minimal dependencies. Integration testing — black box, verifies components interact as expected, focuses on the API, runs after unit tests. Acceptance testing — end-to-end from a user perspective, cross-browser, very slow but very important. Regression testing — prevents bugs reoccurring, added when fixing a bug, often covers bizarre edge cases.
Q11

What is an artifact, and what does publishing do?

Answer: An artifact is an output produced at the completion of a CI job — for example a tar/zip archive, a binary, an apk mobile application, or a deb/rpm package. Publishing is the process that exposes artifacts from CI to the deployment process.
Q12

What is Continuous Deployment, and how does it differ from publishing?

Answer: Continuous Deployment is automatically triggering a deployment at the completion of a CI job (if you are feeling brave). Publishing only exposes the artifact to the deployment process; it does not itself deliver the version to users.
Q13

Define deployment and give three examples from the lecture.

Answer: Deployment is the process by which the latest version of an application is delivered to users. Examples: submitting an APK to the Google Play Store, updating code on a fleet of production servers, and pushing files to an S3 bucket.
Q14

Compare rolling and blue-green deployment.

Answer: Rolling deployment progressively deploys/releases the new version until the entire pool has been updated, so during the rollout it serves a mix of old and new assets. Blue-green deployment spins up an entirely new set of infrastructure with the new code and does a hard switch-over of all traffic to the new infrastructure/code.
Q15

After deployment, how do you verify everything is working as expected?

Answer: By using testing, logging and real-time telemetry — the post-deployment practices introduced in Week 6.
