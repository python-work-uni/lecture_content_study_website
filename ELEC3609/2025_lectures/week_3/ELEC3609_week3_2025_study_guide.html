Lecture overview

This lecture is about how real web systems are put together and how they grow. It starts with the classic LAMP and LEMP stacks and the three-tier web architecture, then compares the major web server engines (IIS, Apache, Nginx) and the languages and frameworks used to build the application tier — with a close look at Django's Model-View-Template pattern. It then surveys data storage, from disk and object stores to relational and NoSQL databases, and finishes with production best practices: decoupling, statelessness, redundancy, and a step-by-step roadmap for scaling a web architecture.

Classic Web Stacks: LAMP & LEMP

LAMP and LEMP stacks are the most ubiquitous stacks used for developing and deploying web applications. Because of their modular nature, the components can easily be swapped out.

StackComponents
LAMPLinux, Apache, MySQL, PHP
LEMPLinux, Nginx, MySQL, PHP

Both share Linux, MySQL and PHP; the difference is the web server — Apache in LAMP, Nginx in LEMP (the "E" stands for "engine-x", the pronunciation of Nginx).

The lecture also references the paper Principled Design of the Modern Web Architecture (2002), which lists the goals modern web architecture is designed to achieve:

  • Scalability of component interactions
  • Generality of interfaces
  • Independent deployment of components
  • Intermediary components to reduce interaction latency
  • Enforce security
  • Encapsulate legacy systems
💡

Why It Matters:

Because the stack is modular, you can swap one component without rebuilding everything — for example, replacing Apache with Nginx, or MySQL with Postgres. This is why the same architecture appears under many different acronyms.

Three-Tier Architecture & Server Roles

A refresher on the three-layer architecture:

Web Server

  • Takes HTTP(S) traffic only.
  • Uses HTTP on port 80, or HTTPS on port 443 if encrypted.

Application Server

  • Possibly running on HTTP (port 80) or HTTPS (port 443) if encrypted.
  • Or on any designated TCP ports.

Web Server vs Application Server. The key distinction: a web server exclusively handles HTTP requests, whereas an application server serves business logic to application programs through any number of protocols, possibly including HTTP.

Web ServerApplication Server
HandlesHTTP(S) requests onlyBusiness logic for applications
ProtocolsHTTP / HTTPSAny number of protocols, possibly including HTTP
Ports80 (HTTP), 443 (HTTPS)80/443 or any designated TCP ports
💡

Why It Matters:

Mixing up these roles leads to confused designs. The web server faces the public internet and speaks HTTP; the app server runs your logic and may speak other protocols to databases and services.

Single-Server MVP & Its Limits

The lecture builds an example website to set up a development web server and develop a sample site. Two practical rules:

  • Always develop on a similar system to what you intend to deploy on — for this course, that means Linux.
  • Vagrant is software that creates and configures virtual development environments, so your development environment can match production.

MVP: Everything on One Server

An MVP (Minimum Viable Product) can be built by running everything on a single server.

ProsCons
Simple for debugging; usually the first iterationNot production ready — real configuration is very different across multiple layers and compute nodes
Good for demo or technical validation purposesArchitecturally things are not decoupled, which is tough for troubleshooting
Not ready for horizontal scaling
⚠️

Common Trap:

A single-server MVP can feel finished because the demo works, but it has no separation of concerns and no path to scale. Treat it as a prototype, not a product.
04

Scaling the App Tier: DNS & LBs

Case Study 1: Moving the App Server

In a single-server MVP, your web server talks to the application server over localhost:8080. If the application server is moved to another server, what are your options?

Option A — Use the IP address, e.g. 10.100.0.2:8080.

  • Problem: if the server dies and a new server comes up with a new IP address, the old IP is hardcoded in a configuration file. The web server now points at nothing.

Option B — Use DNS (an A record).

  • Create an A record so application.mysite.com.au points to 10.100.0.2.
  • The web server configuration file now says application.mysite.com.au instead of an IP.
  • If the application server dies and the new one is assigned a new IP by the DHCP server (e.g. 10.100.0.4), you simply change the DNS record — which can be done automatically with scripts — to the new IP.
  • The web server needs no configuration changes.

Case Study 2: The App Server Gets Slammed

Everything is fine until the application server is overloaded. Two options to improve performance:

  • Option 1: a bigger instance with more CPUs (or a more powerful CPU) and more memory — scale up.
  • Option 2: more instances — scale out.

With Option 2 you now have two app servers (10.100.0.2 and 10.100.0.4) but only one representative DNS record (application.mysite.com.au). The answer is an internal load balancer: application.mysite.com.au points to the load balancer, which then routes traffic to one of the servers.

🧠

Memory Hook:

"DNS fixes the moving target; the load balancer fixes the crowded one." DNS handles a server changing address; a load balancer handles many servers sharing the work.

Web Server Engines: IIS, Apache, Nginx

ServerReleasedKey traits
IIS1996Microsoft's web server. Long history of security vulnerabilities — avoid if possible. Use it for ASP/ASP.NET (still consider Apache) or Windows-specific features such as AD-integration.
Apache1995Open source, developed by the Apache Software Foundation. Dynamically loadable module system. Can scale but can be tricky to set up. Typically spawns threads to handle requests (mpm_prefork), though other options exist.
Nginx2004Designed from the beginning to scale easily; adoption grew quickly. Spawns worker processes. Memory and CPU usage are typically relatively consistent, even under load.

Once you have an Ubuntu Server environment, a LEMP stack can be set up accordingly.

💡

Why It Matters:

The architectural difference matters at scale — Apache's thread/process-per-request model grows heavier with load, while Nginx's worker-process model stays relatively consistent. That is why Nginx became dominant for high-traffic sites.

Languages & Frameworks: HTML to Python

HTML

HyperText Markup Language (HTML) is the standard markup language used to create web pages. The World Wide Web Consortium (W3C) develops HTML standards.

ASP and ASP.NET

  • Active Server Pages (ASP) was released in 1996 and is now known as Classic ASP or ASP Classic. It was Microsoft's first server-side script engine for dynamically generated web pages.
  • ASP.NET (released 2002) supersedes ASP. It uses a Common Language Runtime (CLR) to allow most .NET languages to be supported.

Python

  • Use a framework rather than writing everything from scratch.
  • Python plans its language evolution using PEPs (Python Enhancement Proposals), so you know what to expect in the next few years.
  • Common frameworks: Flask and Django.
  • These typically come with a built-in development server (a lightweight web server) for development use.
  • For production, they are set up with Apache and Nginx using the WSGI (Web Server Gateway Interface) specification. WSGI is the standard bridge that lets a web server hand HTTP requests to a Python application.

PHP

  • Use a framework. Without proper planning, PHP will become a mess (e.g. spaghetti code).
  • Common frameworks: Codeigniter and CakePHP.
  • PHP can be set up with either Apache or Nginx.
🧠

Memory Hook:

"Python uses PEPs and WSGI; PHP risks spaghetti." Frameworks and standards are what keep web code maintainable.

Django's Model-View-Template

Django organises an application into three parts:

  • Models — represent how data is organised in the database.
  • Views — what you see when you visit a site.
  • Controllers — control the flow of information.

Django's actual pattern is called Model-View-Template (MVT), and it maps onto the classic MVC idea as follows:

  • Model — similar to MVC's Model, it handles the data and logic part and maintains a connection with the database.
  • View — works differently from the View layer of MVC. In Django, the view accepts requests and sends out responses.
  • Template — the presentation layer, commonly coded in HTML or DTL (Django Template Language).
Django componentRole
ModelData and logic; maintains the database connection
ViewAccepts requests and sends responses (the logic layer)
TemplatePresentation layer in HTML or DTL
⚠️

Common Trap:

Django's naming is misleading. Django's View is really the controller (it handles requests), and Django's Template is really the view (the presentation). Do not assume the names map one-to-one to classic MVC.

Data Storage Media & Cloud Storage

Storage Media

Storage comes in many forms:

  • Hardware form factor — magnetic (spinning) drive versus Solid State Drive (flash) HDD.
  • SAN storage — interconnected with Ethernet (iSCSI) or Fibre Channel.
  • Network Attached Storage (NAS).
  • In-memory storage.
  • Object store — AWS S3, Google Cloud Storage.
  • Block store — disks.
  • File store — NFS, Samba, CephFS, HDFS (Hadoop).

Disks

  • Hold static files (HTML, images, CSS).
  • SSD versus spinning drives.
  • Leverage OS RAM caching to serve frequently used files faster.

Cloud Storage

Cloud storage is a model of data storage in which data is stored in logical pools, the physical storage spans multiple servers (and often locations), and the physical environment is typically owned and managed by a third party. Offerings include Azure Storage, Google Cloud Storage and Amazon S3.

Amazon S3 (Simple Storage Service) is a cost-effective, simple-to-use service used to store and retrieve any amount of data, at any time, from anywhere on the web.

ℹ️

Background:

Object stores like S3 are not databases — they store whole files (images, videos, backups) rather than rows and tables. Cloud storage also improves durability because data is spread across many servers and locations.

Relational Databases & SQL

What a Relational Database Is

A relational database maintains and enforces relationships between data. It organises data into one or more tables of columns and rows:

  • Typically each table represents an entity, such as a customer or product.
  • Rows represent instances of that entity.
  • Columns represent values attributed to that instance, such as address or price.

A schema change often results in system downtime and planned maintenance — the structure is rigid by design.

SQL Standards

  • There has been an ANSI/ISO SQL standard since 1986.
  • Most SQL is not completely portable among RDBMS products; this typically affects only more advanced features — for example, Teradata does not support pivots.
  • Transact-SQL (TSQL) is typically more feature rich.

Major Relational Databases

  • MySQL / MariaDB — the most popular and commonly used. Lots of third-party tools and libraries. Does not implement the full SQL standard: for example 'foo' || 'bar' means 'foo' OR 'bar', whereas the standard defines || as string concatenation. Concurrency can be an issue.
  • Postgres — follows ANSI/ISO SQL standards. Complete support for reliable transactions — Atomicity, Consistency, Isolation, Durability (ACID). Great spatial extension. Replication can be tricky.
  • Microsoft SQL Server (MSSQL) — good for the MS stack. Integrates easily into the BI/DW stack (SSIS, SSAS, SSRS). Generally cheaper than Oracle and Teradata, but consider and plan license costs, even in the cloud. Requires DBAs.
💡

Why It Matters:

SQL databases give you strong guarantees (ACID) and enforced relationships, which is exactly what financial and inventory data need — at the cost of rigidity and more careful scaling.

NoSQL Databases in Depth

NoSQL / NewSQL databases are non-relational: they store data more like loose pages, and do not store data in the same relational manner. Their characteristics:

  • New data structures
  • More flexible schemas, or no schemas
  • Better scalability
  • Eventually consistent rather than strictly consistent

The lecture surveys five examples:

Redis — key/value based

  • Written in C — blazing fast.
  • Protocol is Telnet-like and binary safe.
  • Disk-backed in-memory database, master-slave replication, automatic failover.
  • Stores simple values or data structures by keys.
  • Supports INCR and similar operations, bit and bitfield operations, sets, lists, hashes and sorted sets.
  • Values can be set to expire (as in a cache).
  • Pub/Sub lets you implement messaging.

Cassandra — column based

  • Written in Java.
  • Main point: store huge datasets in "almost" SQL.
  • Protocol: CQL3 and Thrift.
  • CQL3 is very similar to SQL, but with limitations that come from scalability — most notably no JOINs and no aggregate functions.
  • Querying by key, or key range (secondary indices are also available).
  • Data can have expiration (set on INSERT).
  • Map/reduce is possible with Apache Hadoop.

MongoDB — document based

  • Written in C++.
  • Main point: JSON document store.
  • Master/slave replication (auto failover with replica sets).
  • Sharding built in.
  • Queries are JavaScript expressions.
  • Geospatial queries and indexing.
  • Multiple storage engines with different performance characteristics.
  • Journaling.
  • Text search integrated.
  • Deployment would require some heavy lifting if you want HA — e.g. voting systems using ZooKeeper.

ElasticSearch — document based

  • Written in Java.
  • Main point: advanced search — stores JSON documents.
  • Protocol: JSON over HTTP (plugins: Thrift, memcached).
  • Parent and child documents with versioning and time outs.
  • Very versatile and sophisticated querying, scriptable.
  • Write consistency: one, quorum or all. Asynchronous replication.
  • Sorting by score or geo distance.
  • Fuzzy searches (approximate date, etc.).
  • Use cases: dynamic web search with auto-suggest; the ELK stack for log analysis.
  • ELK = ElasticSearch, Logstash, Kibana.
DatabaseModelWritten inStandout feature
RedisKey/valueCIn-memory speed, expiry, Pub/Sub
CassandraColumnJavaHuge datasets via CQL3, no JOINs
MongoDBDocumentC++JSON store, built-in sharding
ElasticSearchDocument/searchJavaFull-text and fuzzy search; ELK
🧠

Memory Hook:

"Redis caches, Cassandra scales, Mongo documents, Elastic searches." One phrase per database.

Production Best Practices: Decoupling

Decoupling means giving different components dedicated resources:

  • Web servers
  • App servers
  • Database

The benefits:

  • It is good to have a well-understood scope of work for each component.
  • Reduced blast radius — a failure in one component does not take down everything.
  • Easier troubleshooting and incident response.
  • Smaller but more components — moving towards a microservices architecture.
💡

Why It Matters:

Decoupling is the difference between one server where every problem is everyone's problem, and a system where you can isolate, diagnose and recover each part independently.
12

Scalability & Statelessness

Statelessness is the foundation of all scalability. Stateful applications won't scale.

  • Components of the same layer should not share anything between them.
  • The lecture points to the 12 Factor App principles as a reference.
  • Scale out vs scale up:
  • Scale-out — horizontal scaling; the model supercomputing has been using. Load balancing is IMPORTANT.
  • Scale-up — bigger, bigger and bigger. Often not realistic due to the physical laws and economics.
  • Scalability does not apply only to compute and memory, but also to I/O:
  • IOPS (I/O operations per second)
  • Bandwidth
  • Latency
⚠️

Common Trap:

Teams often assume scalability is only about CPU and RAM. Disk I/O — IOPS, bandwidth and latency — is frequently the real bottleneck.
💡

Why It Matters:

If a server stores per-user session state locally, requests must return to that exact server. Making components stateless lets any server handle any request, which is what makes horizontal scaling possible.

Redundancy & Reliability Terms

Redundancy is about removing all SPOFs (single points of failure):

  • Master/Slave configurations
  • Replications

The lecture asks you to guess AWS S3's durability (it is famously extremely high — the secondary source cites 99.999999999%, or eleven 9s).

Four terms are distinguished:

  • Durability — is the data stored securely in the event of failures?
  • Availability — system uptime; the percentage of time the system is able to serve requests. (For reference, 99.99% availability is about 52.6 minutes of downtime per year.)
  • Reliability — similar to availability, but a system can be available yet not functioning correctly.
  • Resilience — the ability of the system to recover in the event of failures; self-healing.

Some software defects relate to performance — they cannot be replicated when the load is low. Think about avalanche or cascading effects, where one failure triggers others. Extended reading: Chaos Monkey.

TermQuestion it answers
DurabilityIs the data safe from loss or corruption?
AvailabilityWhat percentage of time can it serve requests?
ReliabilityDoes it work correctly while available?
ResilienceCan it recover and self-heal after failure?
🧠

Memory Hook:

"D-A-R-R" = Durability, Availability, Reliability, Resilience — four different promises, often confused.

Scaling Roadmap: Step by Step

Web architectures evolve incrementally from a simple MVP to a multi-tiered, resilient system. The lecture walks through these stages:

Stage 1 — Single Server Architecture. Everything (web server, app server, database) runs on one machine. Good for prototypes; not production ready.

Stage 2 — Separate DB Server. Separate the database from the application server to eliminate resource contention, and increase security by removing the database from the DMZ or public internet.

Stage 3 — Load Balancer. Add a load balancer to improve performance and reliability by distributing the workload across multiple servers. If one load-balanced server fails, the others handle incoming traffic until it becomes healthy again. Typical implementations: HAProxy, Nginx, Varnish.

Stage 4 — HTTP Accelerator. An HTTP accelerator (caching HTTP reverse proxy) reduces the time to serve content through a variety of techniques. Typically the response from a web or application server is cached for a period of time in memory. Examples: Varnish, Squid, Nginx.

Stage 5 — Master-Slave Database Replication. One way to improve a database that performs many reads compared to writes (such as a CMS) is master-slave replication. It requires a master and one or more slave nodes; all updates are sent to the master, and reads can be distributed across all nodes.

Stage 6 — Combinations. It is possible to load balance the caching servers in addition to the application servers, and to use database replication in a single environment. The purpose of combining these techniques is to reap the benefits of each without introducing too many issues or complexity.

💡

Why It Matters:

You do not jump straight to a complex architecture. You add one layer at a time as a real bottleneck appears, which keeps the system as simple as it can be for the load it must handle.

Worked Examples & Scenarios

Example 1

The Hardcoded-IP Failure

A single-server MVP has the web server configured to call the app server at localhost:8080.

  1. The app server is moved to a new machine at 10.100.0.2:8080, so the config is updated to that IP.
  2. The machine dies; DHCP assigns the replacement 10.100.0.4.
  3. The hardcoded 10.100.0.2 now points at nothing — the site breaks.
  4. The fix: create an A record so application.mysite.com.au points to the app server, and have the web server use the name.
  5. Next time the IP changes, update the DNS record (automatically with a script) and leave the web server untouched.
Example 2

From One App Server to a Pool

  1. Stage 1: web, app and database all on one server — fine for a demo.
  2. Stage 2: move the database to its own server to remove resource contention and take it out of the DMZ.
  3. Stage 3: the app server is overloaded, so add a second app server — now there are two IPs behind one name.
  4. Add a load balancer: application.mysite.com.au points at the LB, which routes to either app server and routes around a failed one.
  5. Stage 4: add an HTTP accelerator (e.g. Varnish) so cached responses are served from memory.
  6. Stage 5: add master-slave replication so reads spread across slaves while writes go to the master.
Example 3

Choosing a Database for a CMS

A content-management system performs far more reads than writes.

  • A relational database is a natural fit because content has clear relationships (articles, authors, categories) and a well-defined schema.
  • Because reads dominate, master-slave replication lets many slaves serve reads while the master handles writes.
  • If the system also needs fast lookups of cached fragments, Redis can hold short-lived values with expiry.
  • If it needs powerful search with auto-suggest, ElasticSearch (part of the ELK stack) is the specialised tool.
Example 4

Reading the NoSQL Table

Compare two document stores from the lecture:

  • MongoDB is written in C++ and stores JSON documents, with master/slave replication and built-in sharding; queries are JavaScript expressions.
  • ElasticSearch is written in Java and specialises in advanced search over JSON documents, with JSON-over-HTTP access, fuzzy search and async replication.
  • Both are "document based", but MongoDB is a general-purpose data store while ElasticSearch is built for search.
Example 5

The Four Reliability Promises

For a photo-sharing service, distinguish the terms:

  • Durability — if a disk fails, are the uploaded photos still safe? (Cloud object storage spreads copies across servers and locations.)
  • Availability — what percentage of the time can users load the site? (e.g. 99.99% ≈ 52.6 minutes downtime per year.)
  • Reliability — when the site is up, does it actually work correctly, or does it return errors?
  • Resilience — after a failure, can the system recover and self-heal without human intervention?
