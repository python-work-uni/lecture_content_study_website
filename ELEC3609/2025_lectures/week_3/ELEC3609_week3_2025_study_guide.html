Web Servers, Stacks and Scaling the Modern Web Architecture

How a web application is assembled from a web server, an application server and a database, how each layer is chosen from real products (Apache, Nginx, Django, MySQL, Redis, S3), and how the whole thing is scaled, decoupled and made redundant for production.

Read this first: Every web system is the same three jobs split apart — take HTTP traffic, run business logic, store data. Once you see the request travelling from the client, through a web server, into an application server, and out to a data store, every product name in this guide is just a choice about which box does which job and how those boxes survive failure.

From Single Server to the LAMP/LEMP Stack

A web application is only ever three jobs — serve HTTP, run logic, store data — and the stack you pick is how you assemble those jobs.

Every web application, no matter how large, performs the same three functions. A web server accepts HTTP(S) traffic from clients. An application server runs the business logic that decides what the client should receive. A data store keeps the persistent state. The entire discipline of web architecture is deciding whether those three run together or apart, and what software fills each slot.

What is a stack?

A stack is a named, pre-packaged combination of these layers. Because the layers are modular, individual components can easily be swapped out without rewriting the rest.

The two most ubiquitous stacks used for developing and deploying web applications are LAMP and LEMP:

Principled Design of the Modern Web Architecture

A 2002 paper (Fielding & Taylor, "Principled Design of the Modern Web Architecture") laid out the goals that still drive how we structure web systems today.

The modern web architecture was not designed by accident. Its goals were stated explicitly, and they explain many of the rules you will meet later in this guide:

  • Modern web architecture — a coherent style rather than a pile of ad-hoc technologies.
  • Scalability of component interactions — the system must grow by adding components, not by making one component infinitely large.
  • Generality of interfaces — components talk through a small, uniform interface so they can be replaced independently.
  • Independent deployment of components — each part can be updated without redeploying everything.
  • Intermediary components to reduce interaction latency — caches and proxies can sit between client and server to speed things up.
  • Enforce security — security is a design goal, not an afterthought.
  • Encapsulate legacy systems — old systems are wrapped behind the general interface rather than rewritten.
ℹ️
Note: This is the origin of the principles behind REST-style architecture. The recurring themes — general interfaces, independent deployment, intermediaries — reappear as decoupling, load balancing and HTTP acceleration later.
🤔
Pause & predict: Before reading on, predict: if "generality of interfaces" is a design goal, would a system that requires every component to know the exact internal details of every other component be well-designed?

Three-Layer Architecture: Web Server vs Application Server

Separating the HTTP-facing layer from the logic layer is the first and most important structural decision.

The classic three-layer architecture divides responsibilities:

  • Web server — takes HTTP(S) traffic only. Listens on HTTP (port 80) or HTTPS (port 443) when encrypted. It does not run business logic; it serves static content and forwards dynamic requests onward.
  • Application server — runs the business logic. It may also communicate over HTTP (80) or HTTPS (443), or over any designated TCP ports.
  • Database — stores the persistent data (covered later).

Application server vs web server — the precise distinction

This distinction is examinable and easy to get wrong:

Web server — Exclusively handles HTTP requests. Serves static assets and forwards dynamic requests. |
Application server — Serves business logic to application programs through any number of protocols, possibly including HTTP but not limited to it. |
🧠
Memory hook: Web server = HTTP only. Application server = business logic over any protocol.

Developing on the deployment target

A crucial workflow rule: always develop on a similar system to what you intend to deploy on. For this course that means Linux, because that is where the production environment lives. Developing on Windows and deploying to Linux invites configuration surprises.

Vagrant is software that creates and configures virtual development environments — it lets you spin up a Linux environment locally that mirrors the target deployment.

✅
Exam tip: If asked "why use Vagrant?", the answer is reproducibility: a disposable, configurable Linux VM that matches production, so the "works on my machine" problem disappears.
🤔
Pause & predict: A web server listens on port 80, but an application server can use any TCP port. What does that tell you about how tightly the two are coupled?

MVP: Single Server Architecture and Its Case Studies

The minimal viable product puts everything on one machine — perfect for a first iteration, fatal for production.

The MVP (Minimal Viable Product) architecture runs everything — web server, application server and database — on a single server. A new ASP.NET Core project is the typical example of this starting point.

Pros and cons

ProsCons
Simple for debugging; usually the first iterationNot production ready — real configuration differs when layers span multiple compute nodes
Good for demos or technical validationArchitecturally not decoupled; tough for troubleshooting
Not ready for horizontal scaling

Case study 1 — moving the application server

In the single-server MVP, the web server talks to the application server over localhost:8080. If you move the application server to another machine, what are the options?

  • Hardcode the IP address — e.g. 10.100.0.2:8080.
  • Problem: if that server dies and a replacement gets a new IP from DHCP, the configuration breaks because the address is hardcoded in a configuration file.
  • Use DNS with an A record — point application.mysite.com.au at 10.100.0.2, and put the hostname (not the IP) in the web server configuration.
  • Now if the application server dies and the replacement is assigned 10.100.0.4, you simply change the DNS record (automatable with scripts) to the new IP.
  • The web server needs no configuration changes at all.
💡
Why it matters: Using a DNS A record turns a brittle hardcoded address into a level of indirection. The web server depends on a name that stays constant while the address behind it can change freely.

Case study 2 — the application server gets slammed

The application server is now overloaded. Two options:

  1. Vertical scale-up: a bigger instance with more CPUs (or a more powerful CPU) and more memory.
  2. Horizontal scale-out: run more instances.

With option 2 you now have two application servers (10.100.0.2 and 10.100.0.4) but only one DNS record (application.mysite.com.au). The solution is an internal load balancer: point the DNS record at the load balancer, and let it route traffic to one of the application servers.

⚠️
Common trap: A single DNS A record cannot point to two servers meaningfully for load distribution. The DNS record points to the load balancer, and the load balancer owns the fan-out.
🤔
Pause & predict: You have two identical application servers and one DNS name. Why is DNS alone the wrong tool for distributing load, and what component belongs in between?

Web Servers: IIS, Apache and Nginx

Three web servers dominate the market, each with a distinct history, concurrency model and best-fit scenario.

A web server is the software that terminates HTTP(S) traffic. The choice affects performance under load, ease of configuration and security posture.

IIS (Internet Information Services)

  • Microsoft's web server, released 1996.
  • Has a long history of security vulnerabilities and should be avoided if possible.
  • Use it when running an ASP or ASP.NET application (though Apache remains a valid alternative) or to use Windows-specific features such as AD (Active Directory) integration.

Apache HTTP Server

  • Open source, now developed by the Apache Software Foundation.
  • Released 1995 — very commonly used.
  • Dynamically loadable module system: features can be added without recompiling.
  • Can scale, but can be tricky to set up.
  • Typically spawns threads to handle requests (mpm_prefork); other processing models exist.

Nginx

  • Released 2004, designed from the beginning to scale easily.
  • Adoption has grown quickly.
  • Spawns worker processes.
  • Memory and CPU usage are typically relatively consistent, even under load — a key advantage over thread-per-request designs.
  • Configured with a sample configuration file (declarative config).
ServerReleasedModelNotes
IIS1996Windows serviceAvoid if possible; ASP.NET/AD use cases
Apache1995Threads (mpm_prefork)Flexible modules; tricky to set up
Nginx2004Worker processesBuilt to scale; stable resource use

Once you have an Ubuntu Server environment, a LEMP stack can be set up accordingly.

🧠
Memory hook: IIS = Insecure history + Microsoft. Apache = All-purpose but tricky. Nginx = New and nimble, consistent under load.
✅
Exam tip: The Nginx advantage to quote is predictable resource usage under load because of the worker-process model, versus Apache's thread spawning.

Languages and Frameworks: HTML, ASP.NET, Python and PHP

Server-side languages generate dynamic pages — and you should almost always use a framework rather than raw code.

HTML — the presentation markup

HyperText Markup Language (HTML) is the standard markup language used to create web pages. The World Wide Web Consortium (W3C) develops the HTML standards. HTML describes structure and content; it is not a programming language and runs in the browser.

ASP and ASP.NET — Microsoft's server-side engines

  • Active Server Pages (ASP) was released in 1996, now known as Classic ASP or ASP Classic. It was Microsoft's first server-side script engine for dynamically generated web pages.
  • ASP.NET (released 2002) supersedes ASP.
  • ASP.NET uses a Common Language Runtime (CLR) so that most .NET languages are supported — a single runtime hosting many languages.

Python

  • Use a framework.
  • Python plans its language evolution through PEPs (Python Enhancement Proposals) — so you know what you get in the next few years. This long-term planning is a reason to trust it for production.
  • Two frameworks: Flask (lightweight) and Django (full-featured).
  • Python frameworks typically come with a built-in development server (a lightweight web server) for local work.
  • In production they are set up with Apache or Nginx using the WSGI (Web Server Gateway Interface) specification.
WSGI — Web Server Gateway Interface — the standard specification that lets a Python application run behind a general-purpose web server such as Apache or Nginx. |

PHP

  • Use a framework.
  • Without proper planning PHP code becomes a mess — spaghetti code.
  • Frameworks include CodeIgniter and CakePHP.
  • Can be set up with either Apache or Nginx.
💡
Why it matters: The built-in development server is convenient but not production-grade. Real deployments front the framework with Apache or Nginx via WSGI (Python) so the battle-tested web server handles connections and static assets.
🤔

Django: Model-View-Template (MVT)

Django follows an MVC-like pattern but renames the layers — and the meaning of "View" changes.

Django is the full-featured Python web framework. It is described first in MVC terms and then in its own terms.

The MVC framing

  • Models — represent how data is organized in the database.
  • Views — what you see when you visit a site.
  • Controllers — control the flow of information.

The Django (MVT) framing

Django is best understood as Model-View-Template:

  • Model — similar to MVC's Model: handles the data and logic part and maintains a connection with the database.
  • View — works differently from the View-layer of MVC. In Django, the view accepts the requests and sends out the responses (i.e. it contains the request-handling logic, much like MVC's controller).
  • Template — the presentation layer, commonly coded in HTML or DTL (Django Template Language).
⚠️
Common trap: In Django the View is not the presentation layer — the Template is. The Django View behaves like the controller in classic MVC. Do not carry the MVC naming straight across.
🧠
Memory hook: Django MVT: Model = data, View = logic/request handling, Template = presentation.
🤔

Data Storage: Media and Storage Types

Storage is chosen along two axes — the physical medium and the access model (block, file, object, in-memory).

Storage media (hardware)

  • Hardware form factor: magnetic (spinning) drive vs. Solid State Drive (SSD, flash).
  • SAN storage: drives interconnected with Ethernet (iSCSI) or Fibre Channel.
  • Network Attached Storage (NAS).
  • In-memory storage.

Storage access models

  • Object store — e.g. AWS S3, Google Cloud Storage.
  • Block store — raw disks.
  • File store — NFS, Samba, CephFS, HDFS (Hadoop).

Disk

  • Used for static files (HTML, images, CSS).
  • SSD vs spinning disk is a performance/cost trade-off.
  • Leverage OS RAM caching to serve hot files quickly.
🧠
Memory hook: Object = whole blobs via API (S3). Block = raw disks. File = a filesystem you mount (NFS/Samba). In-memory = fastest, volatile.
✅
Exam tip: Static files belong on disk (with OS RAM caching), not in a database. A database is for structured, related data.
🤔
Pause & predict: You need to store millions of user-uploaded images. Would you put them in a relational database, a block store, or an object store? Justify using the access model.

Relational Databases and the SQL Standard

Relational databases enforce relationships between structured tables — at the cost of rigid schemas.

A relational database (RDBMS):

  • Maintains and enforces relationships between data.
  • Organizes data into one or more tables of columns and rows.
  • Each table typically represents an entity (such as a customer or product).
  • Rows represent instances of that entity.
  • Columns represent values attributed to that instance (such as address or price).
  • A schema change often results in system downtime and planned maintenance — this rigidity is the price of enforced structure.

SQL — who needs a standard?

  • There has been an ANSI/ISO SQL standard since 1986.
  • Most SQL is not completely portable among RDBMS.
  • Portability issues typically affect only more advanced features — e.g. Teradata doesn't support pivots.
  • Transact-SQL (TSQL) is typically more feature rich.

The major relational databases

MySQL standard quirk: 'foo' || 'bar' means 'foo' OR 'bar' in MySQL, whereas the SQL standard defines || as string concatenation.

Postgres provides complete support for reliable transactions — Atomicity, Consistency, Isolation, Durability (ACID).

⚠️
Common trap: "SQL is portable" is false in general. Core statements usually transfer, but advanced features differ — and MySQL's || operator is a classic counter-example.
🧠

NoSQL Databases: Redis, Cassandra, MongoDB, Elasticsearch

Non-relational databases trade strict consistency and joins for flexible schemas, scalability and specialised data models.

What "New SQL or No SQL" means

  • Non-relational databases store data more like loose pages, not in the same relational manner.
  • New data structures.
  • More flexible schemas, or no schemas.
  • Better scalability.
  • Eventually consistent rather than strictly consistent.

Redis — key/value based

  • Written in C — blazing fast.
  • Protocol: Telnet-like, binary safe.
  • Disk-backed in-memory database, master-slave replication, automatic failover.
  • Simple values or data structures by keys.
  • Supports INCR & co, bit and bitfield operations, sets, lists, hashes and sorted sets.
  • Values can be set to expire (as in a cache).
  • Pub/Sub lets you implement messaging.

Cassandra — column based

  • Written in Java.
  • Main point: store huge datasets in "almost" SQL.
  • Protocol: CQL3 & Thrift.
  • CQL3 is very similar to SQL but with limitations that come from scalability — most notably no JOINs, no aggregate functions.
  • Querying by key, or key range (secondary indices also available).
  • Data can have expiration (set on INSERT).
  • Map/reduce possible with Apache Hadoop.

MongoDB — document based

  • Written in C++.
  • Main point: JSON document store.
  • Master/slave replication (auto failover with replica sets).
  • Sharding built-in.
  • Queries are JavaScript expressions.
  • Geospatial queries and indexing.
  • Multiple storage engines with different performance characteristics.
  • Journaling.
  • Text search integrated.
  • Deployment requires heavy-lifting for HA (high availability) — e.g. voting systems using ZooKeeper.

Elasticsearch — document based

  • Written in Java.
  • Main point: advanced search — stores JSON documents.
  • Protocol: JSON over HTTP (plugins: Thrift, memcached).
  • Parent and children documents with versioning & time-outs.
  • Very versatile and sophisticated querying, scriptable.
  • Write consistency: one, quorum or all. Asynchronous replication.
  • Sorting by score, geo distance.
  • Fuzzy searches (approximate date, etc.).
  • Use cases: dynamic web search with auto-suggest; ELK stack for log analysis.
  • ELK = Elasticsearch, Logstash, Kibana.

RedisKey/valueCIn-memory speed, caching, Pub/Sub

MongoDBDocumentC++JSON documents, sharding built-in

Memory hook: Redis = fast cache, Cassandra = columns at scale, MongoDB = JSON docs, Elasticsearch = search.

Cloud Storage and Amazon S3

Cloud storage hides the physical disks behind a third-party-managed, multi-server, often multi-location pool.

Cloud storage is a model of data storage in which:

  • data is stored in logical pools,
  • the physical storage spans multiple servers (and often locations),
  • the physical environment is typically owned and managed by a third party.

Many offerings exist on the market: Azure Storage, Google Cloud Storage, Amazon S3.

Amazon S3

Amazon Simple Storage Service (S3) is a cost-effective, simple-to-use service that can be used to store and retrieve any amount of data, at any time, from anywhere on the web. It is the canonical example of an object store.

ℹ️
Note: S3's design is why "durability" (see the redundancy section) can be discussed as a near-guarantee: data is replicated across many devices and locations by the provider.
🤔

Production Best Practices: Decoupling, Scalability and Redundancy

Three principles separate a demo from a production system: decouple components, keep them stateless, and remove every single point of failure.

Decoupling

Give different components dedicated resources:

  • Web servers
  • App servers
  • Database

Benefits:

  • A well-understood scope of work per component.
  • Reduced blast radius — a failure affects less.
  • Easier troubleshooting and incident response.
  • Downside: smaller but more components, moving towards a microservices architecture.

Scalability

  • Statelessness is the foundation of all scalability. Stateful applications won't scale.
  • Components of the same layer should not share anything in between them.
  • These principles are captured in the 12 Factor App (https://12factor.net/).
  • Scale out vs. scale up:
  • Scale-out (horizontal scaling): the model supercomputing has been using; load balancing is IMPORTANT.
  • Scale-up (vertical scaling): "bigger, bigger and bigger" — often not realistic due to physical laws and economics.
  • Scalability applies not only to compute and memory but also to IO:
  • IOPS (IO operations per second)
  • Bandwidth
  • Latency
💡
Why it matters: A stateful application ties a user's session to one server, so you cannot freely add servers or route requests anywhere. Removing state from the application tier is what makes horizontal scaling and load balancing possible.

Redundancy

  • Remove all SPOFs (single points of failure).
  • Use Master/Slave and Replication.
  • Durability vs. Availability vs. Reliability vs. Resilience:
PropertyQuestion it answers
DurabilityIs the data stored securely in the event of failures?
AvailabilitySystem uptime — the percentage of time able to serve requests.
ReliabilitySimilar to availability, but a system can be available yet not functioning correctly.
ResilienceThe ability of the system to recover in the event of failures — self-healing.
  • Some software defects are performance-related and cannot be replicated when the load is low.
  • Think about avalanche or cascading effects — one failure triggering others.
  • Extended reading: Chaos Monkey.
⚠️
Common trap: Availability is not the same as reliability. A server returning HTTP 500 errors on every request is available (it responds) but not reliable (it is not functioning correctly).
🧠
Memory hook: D-A-R-R: Durability = data survives, Availability = up, Reliability = correct, Resilience = recovers.
🤔
Pause & predict: Your database is replicated and never loses data, but during an outage it serves no requests. Which property is strong and which is weak?

Scaling Web Architecture: Load Balancers, Caches and Replication

Production scale is built by incrementally separating components: database, then load balancer, then cache, then database replication — and then combining them.

Recap: single server architecture

Everything on one host — the MVP baseline from earlier. Each step below removes a constraint or a single point of failure.

Step 1 — Separate DB server

Separate the database from the application server to:

  • Eliminate resource contention (the database and app no longer compete for the same CPU, memory and IO).
  • Increase security by removing the database from the DMZ or public internet.

Step 2 — Load balancer

A load balancer (LB) is added to a server environment to improve performance and reliability by distributing the workload across multiple servers. If one load-balanced server fails, the others handle incoming traffic until the failed server becomes healthy again.

  • Typical implementations: HAProxy, Nginx, Varnish.

Step 3 — HTTP accelerator

An HTTP accelerator, or caching HTTP reverse proxy, reduces the time to serve content using a variety of techniques. Typically the response from a web or application server is cached in memory for a period of time.

  • Examples: Varnish, Squid, Nginx.

Step 4 — Master-slave database replication

For a database that performs many reads compared to writes (such as a CMS), use master-slave replication:

  • Requires a master and one or more slave nodes.
  • All updates (writes) are sent to the master.
  • Reads can be distributed across all nodes.

Step 5 — Combinations

It is possible to load balance the caching servers in addition to the application servers, and to use database replication in a single environment. The purpose of combining these techniques is to reap the benefits of each without introducing too many issues or complexity.

Single server→Separate DB server→Load balancer→HTTP accelerator→Master-slave replication→Combined environment
💡
Why it matters: Each step is a targeted fix: separate DB removes contention, LB removes a compute SPOF, cache cuts latency, replication removes a database SPOF and spreads read load. Production architecture is the accumulation of these independent improvements.
✅
Exam tip: Be able to draw the progression from single-server MVP to a combined environment, labelling each new component and stating the specific problem it solves.
🤔
Pause & predict: Master-slave replication suits read-heavy workloads. What happens to write throughput as you add more slaves, and why doesn't replication help there?

Key Takeaways

If you remember nothing else, remember this.

1

Every web application is three jobs — serve HTTP, run business logic, store data — and architecture is how you separate them.

2

LAMP = Linux/Apache/MySQL/PHP; LEMP swaps Apache for Nginx; modular components can be swapped freely.

3

A web server handles HTTP exclusively; an application server serves business logic over any number of protocols.

4

The modern web architecture's stated goals include scalability, general interfaces, independent deployment, latency-reducing intermediaries, security and legacy encapsulation.

5

The single-server MVP is easy to debug and good for demos, but is not decoupled and not ready for horizontal scaling.

6

A DNS A record decouples the web server from a changing application-server IP; a load balancer is needed once there are multiple application servers.

7

IIS (1996) has a poor security history; Apache (1995) is modular but tricky; Nginx (2004) uses worker processes and stays consistent under load.

8

Use a framework in every server-side language; Python deploys behind Apache/Nginx via WSGI, and Django follows Model-View-Template where the View handles requests and the Template is the presentation layer.

9

Storage comes in object (S3), block (disks), file (NFS/Samba/CephFS/HDFS) and in-memory forms; static files live on disk with OS RAM caching.

10

Relational databases enforce relationships and rigid schemas; Postgres fully supports ACID, MySQL deviates from the SQL standard, and MSSQL suits the MS/BI stack.

11

NoSQL trades strict consistency for flexible schemas and scale: Redis (K/V cache), Cassandra (columns, no JOINs), MongoDB (JSON docs), Elasticsearch (advanced search, ELK).

12

Decoupling reduces blast radius; statelessness is the foundation of scalability; scale-out beats scale-up; redundancy removes SPOFs.

13

Distinguish durability (data survives), availability (uptime), reliability (correct functioning) and resilience (self-healing recovery).

14

Scale production incrementally: separate DB server, load balancer, HTTP accelerator, master-slave replication, then combine.

Glossary

Every term you need to speak this week's language.

Web server
Software that exclusively handles HTTP requests, listening on port 80 (HTTP) or 443 (HTTPS) and serving static content or forwarding dynamic requests.
Application server
A server that serves business logic to application programs through any number of protocols, possibly including HTTP.
Three-layer architecture
The separation of a web system into a web server layer, an application server layer and a database layer.
LAMP
A ubiquitous web stack: Linux, Apache, MySQL, PHP.
LEMP
The LAMP stack with Nginx replacing Apache (the "E" stands for Engine-x).
MVP
Minimal Viable Product — running everything on a single server; simple to debug but not production ready or horizontally scalable.
DNS A record
A DNS record mapping a hostname (e.g. application.mysite.com.au) to an IP address, letting infrastructure change IPs without reconfiguring clients.
Load balancer
A component that distributes workload across multiple servers, improving performance and reliability and allowing failed servers to be bypassed.
IIS
Microsoft's Internet Information Services web server, released 1996; historically vulnerable and best avoided unless using ASP.NET or Windows-specific features like AD integration.
Apache
Open-source Apache HTTP Server (1995) with a dynamically loadable module system; scalable but tricky to configure.
Nginx
Web server released 2004, built to scale; spawns worker processes and keeps memory/CPU usage consistent under load.
WSGI
Web Server Gateway Interface — the specification for running Python web frameworks behind Apache or Nginx.
Django
A full-featured Python web framework using the Model-View-Template pattern.
MVT
Model-View-Template: Django's pattern where Model handles data, View handles requests/responses, and Template is the presentation layer.
Vagrant
Software that creates and configures reproducible virtual development environments.
Relational database
A database that enforces relationships and organizes data into tables of rows (instances) and columns (attributes); schema changes often cause downtime.
SQL
The standard query language for relational databases, standardized by ANSI/ISO since 1986, though implementations are not fully portable.
ACID
Atomicity, Consistency, Isolation, Durability — the four transaction guarantees fully supported by Postgres.
NoSQL
Non-relational databases that use flexible or absent schemas, offer better scalability and are eventually consistent rather than strictly consistent.
Redis
A key/value, disk-backed in-memory database written in C, supporting expiry, data structures and Pub/Sub messaging.
Cassandra
A column-based database written in Java that stores huge datasets in "almost SQL" (CQL3) with no JOINs or aggregate functions.
MongoDB
A C++ document database storing JSON documents, with built-in sharding, replica sets and JavaScript queries.
Elasticsearch
A Java document database and search engine using JSON over HTTP, supporting fuzzy search and the ELK stack.
Object store
A storage model that keeps whole objects accessible by key/API, such as Amazon S3 or Google Cloud Storage.
Cloud storage
A model where data lives in logical pools spanning multiple servers and locations, owned and managed by a third party.
Statelessness
The property that servers hold no per-user state between requests; described as the foundation of all scalability.
Scale-out
Horizontal scaling by adding more servers, requiring load balancing.
Scale-up
Vertical scaling by making one machine bigger; often unrealistic due to physical laws and economics.
IOPS
Input/output operations per second — a measure of storage performance that scalability must account for alongside bandwidth and latency.
SPOF
Single Point of Failure — any component whose failure takes down the system; redundancy aims to remove all of them.
Durability

Q1

In one sentence, what three jobs does every web application perform?

Answer: It accepts HTTP(S) traffic (web server), runs business logic (application server), and stores persistent data (database).
Q2

What exactly distinguishes a web server from an application server?

Answer: A web server exclusively handles HTTP requests, whereas an application server serves business logic to application programs through any number of protocols, possibly including HTTP.
Q3

List the four components of LAMP and state how LEMP differs.

Answer: Linux, Apache, MySQL, PHP. LEMP replaces Apache with Nginx; the other three components stay the same.
Q4

Give two pros and two cons of the single-server MVP architecture.

Answer: Pros: simple for debugging and usually the first iteration; good for demos or technical validation. Cons: not production ready (real configuration differs across multiple compute nodes); architecturally not decoupled and tough to troubleshoot; not ready for horizontal scaling.
Q5

In Case Study 1, why is a DNS A record better than hardcoding an IP address for the application server?

Answer: Hardcoding an IP breaks when a failed server is replaced by one with a new DHCP address. With an A record the web server references a stable hostname, so when the IP changes you only update the DNS record (automatable) and the web server needs no configuration changes.
Q6

In Case Study 2, the application server is overloaded and you add a second instance. What component must now sit in front of them, and why not just use DNS?

Answer: An internal load balancer. A single DNS record cannot meaningfully distribute load across two servers; instead the DNS record points to the load balancer, which routes traffic to one of the application servers.
Q7

Compare IIS, Apache and Nginx on release year and concurrency model.

Answer: IIS: 1996, Microsoft service with a poor security history. Apache: 1995, spawns threads (mpm_prefork), dynamically loadable modules. Nginx: 2004, spawns worker processes, with memory and CPU usage consistent even under load.
Q8

What is WSGI and where does it fit in a Python deployment?

Answer: The Web Server Gateway Interface — the specification that lets Python frameworks (Flask, Django) run behind general-purpose web servers such as Apache or Nginx.
Q9

Explain Django's MVT and how the View differs from MVC's View.

Answer: Model handles data/logic and the database connection; View accepts requests and sends responses; Template is the presentation layer (HTML or DTL). Django's View behaves like MVC's controller, while MVC's View (presentation) corresponds to Django's Template.
Q10

Name the three storage access models with one example each, plus the in-memory option.

Answer: Object store (AWS S3, Google Cloud Storage); block store (raw disks); file store (NFS, Samba, CephFS, HDFS). In-memory storage is the fourth, fastest but volatile option.
Q11

Why does a relational database schema change often cause downtime?

Answer: Because relational databases enforce relationships and a fixed structure; altering the schema requires planned maintenance, during which the system is often unavailable.
Q12

What does ACID stand for, and which database in the lecture fully supports it?

Answer: Atomicity, Consistency, Isolation, Durability. Postgres provides complete support for reliable ACID transactions.
Q13

Give a concrete example of MySQL deviating from the ANSI SQL standard.

Answer: In MySQL, 'foo' || 'bar' means 'foo' OR 'bar', whereas the standard defines || as string concatenation.
Q14

Match each NoSQL database to its data model: Redis, Cassandra, MongoDB, Elasticsearch.

Answer: Redis — key/value; Cassandra — column based; MongoDB — document based (JSON); Elasticsearch — document based with advanced search.
Q15

What limitations does Cassandra's CQL3 have compared with SQL, and why?

Answer: No JOINs and no aggregate functions; these limitations come from its design for scalability across distributed nodes.
Q16

Define durability, availability, reliability and resilience.

Answer: Durability: data stored securely in the event of failures. Availability: system uptime, the percentage of time able to serve requests. Reliability: whether the system functions correctly (it can be available but not reliable). Resilience: the ability to recover from failures — self-healing.
Q17

State the foundation of all scalability and the two scaling directions.

Answer: Statelessness is the foundation of all scalability — stateful applications won't scale. Scale-out (horizontal, add servers, needs load balancing) versus scale-up (vertical, bigger machines, limited by physical laws and economics).
Q18

What problem does separating the database onto its own server solve?

Answer: It eliminates resource contention between the database and application server and increases security by removing the database from the DMZ or public internet.
Q19

How does master-slave database replication work and what workload does it suit?

Answer: A master plus one or more slaves: all updates go to the master, and reads are distributed across all nodes. It suits read-heavy workloads such as a CMS.
Q20

What is an HTTP accelerator and name three examples.

Answer: A caching HTTP reverse proxy that caches web/application server responses in memory for a period of time to reduce serving time. Examples: Varnish, Squid, Nginx.
