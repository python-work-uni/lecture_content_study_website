Case study - 1
– In a single server MVP setup, your web server talks to the 
application server over this - localhost:8080
– If the application server is moved to another server, what would you 
do? What are the options?
– IP address e.g. 10.100.0.2:8080
• Issue: what if the server is dead, and a new server comes with a new IP 
address? Oh… this IP address is HARDCODED in one of the 
configuration files.
– DNS (A record)
– A record : application.mysite.com.au is pointing to 10.100.0.2
– Instead, now the web server configuration file says 
application.mysite.com.au
– What if the application servers is dead? And the new one is assigned with a 
new IP address (by DHCP server) 10.100.0.4
– Simple. Change the DNS record (can be achieved automatically with 
scripts) to the new IP
– Application.mysite.com.au = 10.100.0.4
– Web server does not need any configuration changes

–
Everything is fine. However, now the application 
server gets slammed.
–
What would you do to improve its performance?
– Option 1: Bigger instance with more CPUs (or a

– Option 2: More instances
• OK. Now problem comes. You have two 
application servers. 10.100.0.2 and 
10.100.0.4
• And you only have one representative DNS 
record for application server: 
application.mysite.com.au
• What would you do?
• Internal load balancer now kicks in.
• Application.mysite.com.au points to the 
load balancer and it would then route traffic 
to one of the web servers.

Relational Databases
– Maintains and enforces relationships between data.
– Organizes data into one or more tables of columns and rows.
– Typically, each table represents an entity, such as a customer or 
product.
– Rows represent instances of that entity.
– Columns represent values attributed to that instance (such as address 
or price).
– Schema change often results in system downtime and planned 
maintenance

SQL – who needs a standard?
– There has been an ANSI / ISO SQL standard since 1986.
– Most SQL is not completely portable among RDBMS.
– Typically, only effects more advanced features e.g. Teradata 
doesn’t support pivots.
– Transact-SQL (TSQL) is typically more feature rich.

Redis– K/V Based
– Written in: C - blazing fast.
– Protocol: Telnet-like, binary safe.
– Disk-backed in-memory database, master-slave replication, 
automatic failover.
– Simple values or data structures by keys.
– Supports INCR & co, bit and bitfield operations, sets, lists, 
hashes and sorted sets.
– Values can be set to expire (as in a cache),
– Pub/Sub lets you implement messaging.

--- Slide 41 ---
The University of Sydney
Page 41
Cassandra – Column Based
– Written in: Java.
– Main point: Store huge datasets in ”almost” SQL.
– Protocol: CQL3 & Thrift.
– CQL3 is very similar to SQL, but with some limitations that 
come from the scalability (most notably: no JOINs, no 
aggregate functions).
– Querying by key, or key range (secondary indices are also 
available).
– Data can have expiration (set on INSERT).
– Map/reduce possible with Apache Hadoop.

--- Slide 42 ---
The University of Sydney
Page 42
MongoDB – Document Based
– Written in C++.
– Main point: JSON document store.
– Master/slave replication (auto failover with replica sets).
– Sharding built-in.
– Queries are JavaScript expressions.
– Geospatial queries and indexing.
– Multiple storage engines with different performance 
characteristics.
– Journaling.
– Text search integrated.
– Deployment would require some heavy-lifting if you want HA. 
E.g. voting systems using ZooKeeper

--- Slide 43 ---
The University of Sydney

ElasticSearch – Document Based
– Written in: Java.
– Main point: Advanced Search - stores JSON documents.
– Protocol: JSON over HTTP (Plugins: Thrift, memcached).
– Parent and children documents with versioning & time outs.
– Very versatile and sophisticated querying, scriptable.
– Write consistency: one, quorum or all. Asynchronous 
replication.
– Sorting by score, geo distance.
– Fuzzy searches (approximate date, etc).
– Use cases: dynamic web search with auto-suggest; ELK stack for 
log analysis
– ELK = ElasticSearch, LogStach, Kibana

Scalability
– Statelessness: this is the foundation of all scalability. Stateful 
applications won’t scale.
– Components of the same layer should not share anything in between 
them
– Refer to these principles: 12 Factor App https://12factor.net/ 
– Scale out vs. scale up
– Scale-out: horizontal scaling; The model supercomputing has been 
using; load balancing is IMPORTANT
– Scale-up: bigger, bigger and bigger. Often not realistic due to the 
physical laws and economics
– Scalability does not apply to only compute and memory, but 
also IO
– IOPS (IO per second)
– Bandwidth
– Latency

Redundancy
– Remove all SPOFs (single point of failure)
– Master/Slave; Replications
– Take a guess on AWS S3’s durability
– Durability vs. Availability vs Reliability vs Resilence
– Durability: is the data stored securely in the event of failures?
– Availability: refers to system uptime. Percentage of time able to serve 
requests.
– Reliability: similar to availability. System can be available but not 
functioning correctly
– Resilency: ability for the system to recover in the event of failures. Self-
healing.
– Some software defects are in relation to performance (cannot be 
replicated when the load is low)
– Think about Avalanche or cascading effects.
– Extended reading: Chaos Monkey

Load Balancer
– Load balancers (LB) can be added to a server environment to 
improve performance and reliability by distributing the 
workload across multiple servers. If one of the servers that is 
load balanced fails, the other servers will handle the incoming 
traffic until the failed server becomes healthy again.
– Typical implementations use HAProxy, Nginx, and Varnish.

HTTP Accelerator
– A HTTP accelerator, or caching HTTP reverse proxy, can be used

– Examples of software capable of HTTP acceleration: Varnish, 
Squid, Nginx.

Master-Slave Database Replication
One way to improve performance of a database system that 
performs many reads compared to writes, such as a CMS, is to 
use master-slave database replication. Master-slave replication 
requires a master and one or more slave nodes. In this setup, all 
updates are sent to the master node and reads can be distributed 
across all nodes.
