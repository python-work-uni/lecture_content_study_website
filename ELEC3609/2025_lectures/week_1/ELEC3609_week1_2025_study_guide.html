03

The Internet vs the World Wide Web

These two terms are often used interchangeably, but the lecture draws a sharp distinction.

The Internet is a big network of networks — a medium that allows computers to talk to each other.

The World Wide Web (WWW, or "the Web") is a way of accessing information over the medium of the Internet.

The key idea: the Web is just one of many information-transfer mechanisms on the Internet. Other examples given in the lecture are:

  • Email
  • Instant Messaging
  • File Transfer
  • Media Streaming
  • Usenet
🧠

Memory Hook:

The Internet is the road network; the Web is just one type of vehicle (a web browser) driving on it. Email, streaming and file transfer are other vehicles on the same roads.
💡

Why It Matters:

Saying "the Internet is down" when only one website fails, or "I use the Internet" when you mean "I use the Web", confuses infrastructure with application. Engineers must keep the layers separate in their thinking.
04

Websites, URLs & URIs

A website is a collection of web pages on the World Wide Web. A single web page can be identified by a Uniform Resource Locator (URL), also known as a Uniform Resource Identifier (URI).

The standard structure of a URL is:

URL structureprotocol://domain.tld/path/file.ext

Examples from the lecture:

  • https://google.com — a normal web address using the HTTPS protocol
  • mailto:huaming.chen@sydney.edu.au — an email address scheme
  • ftp://ftp.google.com — a file transfer address

Websites are generally made up of HTML, JavaScript and CSS, and can contain multiple pages and hyperlinks.

URL vs URI. A URI is the broad term for any name or address that identifies a resource; a URL is the specific kind of URI that also says where the resource is and how to reach it (protocol + domain + path). Rule of thumb: all URLs are URIs, but not all URIs are URLs. The lecture also poses the open question: how about Web 3.0, which was coined in 2014?

💡

Why It Matters:

You will read and write URLs constantly in this unit — in Django routes, in REST API calls, and in deployment configuration. Knowing the pieces makes debugging far easier.
⚠️

Common Trap:

mailto: and ftp:// are valid URIs but they are not ordinary web (HTTP) URLs. Not every URI points at a web page.
05

What Is Software?

The lecture defines software as a collection of computer programs, consisting of:

  • Compiled code or modules
  • Configuration
  • APIs
  • Services provided by other web or local services
  • Operating systems
  • Hardware drivers
  • Firmware or embedded programs
💡

Why It Matters:

Software is not just the code you write. Your web application depends on configuration files, third-party APIs, other services, the operating system, drivers and firmware. A bug anywhere in that stack can break your site.

The Three Pillars of a Platform

An internet software platform stitches together three foundational areas. This "stitching" idea is the purpose of the unit.

PillarWhat it covers
InternetFundamentals of how web applications or services work: networking, interaction and protocols, cyber security.
SoftwareHow software is designed, built, packaged and deployed: coding, packaging, ways of coding and packaging, and human factors.
PlatformsCloud and DevOps: cloud technologies, Infrastructure as Code, SaaS models, DevOps and DevSecOps.

The lecture also notes that the idea of a "platform" has changed over time — what platforms looked like in the past is very different from how they look now (from traditional hardware to modern cloud platforms).

🧠

Memory Hook:

I-S-P = Internet, Software, Platforms. Every topic in ELEC3609 belongs to one of these three buckets.
07

The Platform Life Cycle

The life cycle of an internet software platform alternates continuously between two phases:

Development

  • Plan, Design — decide what to build and how.
  • Build & Test — write the code and check it works.
  • Package — bundle it up so it can be released.

Operations

  • Release & Configure — put it into the live environment and set it up.
  • Monitor — watch how it behaves in the real world.
  • React & Respond — fix problems, adjust and improve.

The cycle then repeats: what you learn while operating feeds back into planning and design.

Life cycle flowPlan & Design → Build & Test → Package → Release & Configure → Monitor → React & Respond
💡

Why It Matters:

This is the loop you will follow for your own group project and later for your career. It also shows why "done" is never really final — operations continuously feed new development.

Data Pipelines & Industry at Scale

A Data Pipeline Example

The lecture uses a data pipeline as an example of how platforms evolve and integrate. Its stages are:

Data pipelineData ingestion → Data processing → Data analytics → Data visualisation
  • Data ingestion — sensor data is taken in, either real-time, near real-time, or in batches.
  • Data processing — Extract, Transform and Load (ETL) is applied.
  • Data analytics — the data is analysed.
  • Data visualisation — the outcome is visualised to provide insights.

Industry Case: Qantas

The lecture cites Qantas running a cloud team of just 12 engineers. The drivers were "Automation, Automation and Automation" and "everything as code". Reported results:

  • 250+ applications
  • 5000+ Blue/Green deployments every month
  • Over 2.7 million instances launched
  • Use of Site Reliability Engineering (SRE) and the Internet of Things (IoT)

Blue/Green deployment is a technique for releasing software with two identical environments: one serves live traffic while the other receives the new version, and traffic is switched over once the new version is verified. Site Reliability Engineering applies software engineering practices to operations and infrastructure problems.

ℹ️

Background:

The point of the case study is scale through automation. A tiny team can operate a huge estate only if manual steps are replaced by code.

Group Project & Assessment

The Project

Over the semester you implement a web development project. You form groups in the first tutorial (maximum 5 people), then follow these steps:

  1. Propose an idea.
  2. Identify requirements and use cases.
  3. Design wireframes for the user interface.
  4. Schedule the development and present a project plan.
  5. Design system architecture.
  6. CODE CODE CODE!
  7. Deploy the system to the cloud.
  8. Present your final site.

Publish your project to the cloud and show working tests:

Glossary

Internet

A big network of networks; the medium that lets computers talk to each other.

World Wide Web (WWW)

A way of accessing information over the medium of the Internet; just one of many Internet services.

Website

A collection of web pages on the World Wide Web.

URL (Uniform Resource Locator)

The address that identifies a single web page, in the form protocol://domain.tld/path/file.ext.

URI (Uniform Resource Identifier)

The broader term for any name or address identifying a resource; every URL is a URI.

Protocol

The scheme part of a URL (e.g. https, mailto, ftp) that says how to access the resource.

Domain

The human-readable name portion of a URL, such as google.com.

TLD (Top-Level Domain)

The final part of a domain name, such as .com or .au.

HTML

HyperText Markup Language; one of the languages websites are generally made from.

CSS

Cascading Style Sheets; one of the languages websites are generally made from.

JavaScript

The scripting language used to make websites interactive; one of the languages websites are made from.

Hyperlink

A link between pages or resources, allowing websites to contain multiple connected pages.

Software

A collection of computer programs, including compiled code, configuration, APIs, services, operating systems, drivers and firmware.

API

An interface through which software or services can be used by other software.

Firmware

Embedded program code that runs on hardware.

Platform

The environment on which software runs; modern platforms centre on cloud and DevOps.

Internet Software Platform

A system that stitches together Internet fundamentals, software engineering, and cloud/DevOps platforms.

Infrastructure as Code (IaC)

Managing infrastructure through code rather than manual setup.

SaaS

Software as a Service; a cloud delivery model listed under the Platforms pillar.

DevOps

Practices that combine development and operations to deliver software continuously.

DevSecOps

DevOps with security integrated throughout.

Data pipeline

A flow that ingests, processes, analyses and visualises data.

Data ingestion

Taking data in, in real time, near real time, or batches.

ETL (Extract, Transform and Load)

The processing step of a data pipeline.

Data visualisation

Presenting analysed data so it provides insights.

Blue/Green deployment

Releasing with two identical environments so traffic can be switched with zero downtime.

Site Reliability Engineering (SRE)

Applying software engineering practices to operations and infrastructure.

Internet of Things (IoT)

Networks of connected devices, cited in the Qantas case study.

Software-defined everything

The trend of controlling systems through software.

Internet of everything

The trend of connecting people, processes, data and things.

Learning outcome (LO)

A stated capability students must achieve by the end of the unit.

Django

The Python web framework used as the baseline programming tool in this course.

AWS Academy

The portal giving students access to cloud computational resources.

REST API

A web API called over HTTP; the project must perform AJAX requests to one.

AJAX

A technique for making asynchronous requests from a web page to a server.

Wireframe

A sketch of a user interface used during design.

Use case

A description of how an actor achieves a goal in a system.

System architecture

The overall structure of the system's components and how they interact.

Supervised exam

The final assessment held during the exam period, worth 30%.

Census date

The University deadline by which commencing students must complete the Academic Honesty Education Module.

Academic integrity

Behaving honestly, ethically and responsibly in all elements of study.

Worked Examples & Scenarios

Example 1

Is It the Internet or the Web?

A student cannot load a single website but their email app is still receiving messages. What is really happening?

  • Email is a separate Internet service (its own information-transfer mechanism), so it can keep working when one web server is down.
  • The Internet — the underlying medium — is still up; only the Web (one service on it) is affected.
  • The correct statement is "that website is down", not "the Internet is down".
Example 2

The Qantas Scale Story in Numbers

Qantas runs a cloud team of 12 engineers managing 250+ applications, with 5000+ Blue/Green deployments every month and over 2.7 million instances launched.

  • 5000+ deployments per month is roughly 160+ per day, which is only possible because "everything is code" and the process is automated.
  • Blue/Green deployment is what makes this safe: a new version is verified in one environment before traffic is switched.
  • The lesson: automation, not headcount, is what produces scale.
Example 3

Tracing the Platform Life Cycle

A team wants to fix a slow login page.

  1. Plan & Design — decide the caching approach.
  2. Build & Test — write and test the change.
  3. Package — bundle the new version.
  4. Release & Configure — deploy it behind a switch (e.g. Blue/Green).
  5. Monitor — watch response times in production.
  6. React & Respond — if it is still slow, fix and start the loop again.
Example 4

Reading the Assessment Table

Add the weights to confirm the unit totals 100%: System & Database Design 15% + System Implementation & Testing 35% + System Deployment & Security 12% + Weekly Individual Tasks 8% + Supervised Exam 30% = 100%.

  • The single biggest item is implementation and testing at 35%.
  • The exam alone (30%) is worth nearly as much as the whole group implementation.
  • Weekly tasks (8%) are small but spread across weeks 2–4 and 6–10, so consistent effort matters.
Example 5

A URL and a URI

Compare the three lecture examples:

  • https://google.com — a URL and a URI; it uses the HTTPS protocol and points to a web resource.
  • mailto:huaming.chen@sydney.edu.au — a URI but not a web URL; it names an email destination.
  • ftp://ftp.google.com — a URI using the FTP scheme, not the Web's HTTP scheme. This is why the rule is: all URLs are URIs, but not all URIs are URLs.
