Software Packages: Configuration
– While it is good practice to release software that is secure-by-
default, many software packages come with insecure 
configuration. 
– It is critical to review all configuration options prior 
deployment.
– Question to ask:
– What configuration options are available?
– Are the default values for these options secure?
– Are there any features enabled that you’re not using?
– Can you disable these features?

--- Slide 14 ---
The University of Sydney
Page 14
Software Packages: Configuration
– Identify all the configuration options
– Be sure to read the documentation and view example configurations.
– Search the Internet for example configurations
– Generally configurations are readily available online. Don’t blindly 
trust these. Evaluate the configuration.
– Identify all features and components
– Usually prepackaged software is general purpose. This means while it 
has the functionality required for your application, it may also offer 
other features.
– Disable unwanted features
– Reduce complexity and surface area for possible attacks.

Software Packages: Database
– It is usually the responsibility of the deployer to configure the 
database required by pre-packaged software. 
– Care must be taken while doing this.
– Questions to ask:
– Does the package need to have its own database or can/will it share?
– What DB permissions are required?
– If the application is vulnerable, will DB compromise lead to system 
compromise?

--- Slide 17 ---
The University of Sydney
Page 17
Software Packages: Database
– Identify database requirements
– Does the software create a single database for all of its tables? Or does 
it create multiple databases?
– Evaluate database permissions
– It is best practice to give the minimum set of permissions to an 
application. A good approach is to start by giving the minimal set of 
access and extending when necessary.
– Evaluate the scope of DB compromise
– If a malicious user discovers an SQL injection in our application, they 
may be able to run arbitrary commands on our database. Important to 
update database as well.

Deployment of Software Packages
– Software packages can come with a web/HTTP interface.
– We don’t want this interface directly exposed to the Internet, 
we want our own layer that we have control over in between.
– A reverse proxy (Nginx, Apache) or load balancer can enable 
us finer control over which requests can reach the application.
– Especially important if the application exposes an admin or 
control interface without authentication.

--- Slide 19 ---
The University of Sydney
Page 19
Reverse Proxy
– Intercepting incoming web requests with a reverse proxy (RP) can 
provide many advantages:
– Scaling
– We can increase the number of concurrent connections by using the 
RP as a load balancer. We can run many instances of the application 
and scale horizontally. Database is still a bottleneck to share state.
– Request Authentication
– If our application is an internal service, we can perform basic 
authentication to keep anonymous web users from accessing it.
– Malicious user can’t access the application if blocked by RP.
– Web Application Firewall (WAF)
– A WAF can inspect incoming requests and reject them if they appear 
to be attack vectors

HTTP Basic Authentication
– HTTP Basic Authentication requires HTTP requests to include 
a username and password to be considered authorised.
– If the HTTP requests arrives without a valid username and 
password, a 401 Unauthorized response is served.

--- Slide 21 ---
The University of Sydney
Page 21
HTTP Basic Authentication - Mechanics
– Server Side:
– 1.Server responds to initial request with a 401 Unauthorized 
HTTP response, containing a HTTP header:
 
WWW-Authenticate: Basic realm=“User Visible Realm”
– Client Side:
– 1.Prompts user for username/password
– 2.Combines username and password with a single colon:
 
“Aladdin:OpenSesame”
– 3.Encodes string in RFC2045-MIME variant of base64.
– 4.Sets HTTP request Authorization header to base64-encoded 
credentials:
 
Authorization: Basic QWxhZGRpbjpPcGVuU2VzYW1l

Web Application Firewall
– A Web Application Firewall (WAF) applies rules and/or filters 
to incoming HTTP requests. A WAF will try to identify HTTP 
requests that appear to contain exploitation code and reject 
them.
– All requests should go through the WAF, so it usually sits at 
the edge/web layer in front of your application.
– A WAF is only as good as the rules it evaluates. Keep the 
rule/filter sets up to date.

Docker: Containers
– Instead of running virtual machines, Docker allows us to run 
containers.
– A Docker container can be thought of as a minimalistic Linux 
host.
– We can install any application that we like into the container, 
and the container itself can be (almost) any distribution of 
Linux.
– A Docker container is created based off a Docker image. An 
image file describes the base operating system, and any 
modifications that need to be made, such as dependencies.

Docker: Volumes
– Docker containers are good for running applications, but they 
are not good for storing data. Containers do not maintain state. 
Typically, we mount volumes into Docker containers to allow 
for persistence.
– If we were creating a Docker container for a database, such as 
MySQL, the data directory for the application should be stored 
in an attached volume.
– The mounted volume is a folder on the host machine and exists 
outside the container. We can now destroy the container 
without losing any data.

--- Slide 29 ---
The University of Sydney
Page 29
Docker: Networking
– Docker containers can be linked to each other and have 
nominated ports forwarded form the host OS to the container.
– If we have a web application, such as Wordpress, we can have 
one container for the application and a separate container for 
the MySQL database.
– By linking the containers, the Wordpress application can talk 
to the MySQL container directly. No other containers or 
system are allowed to communicate with the database unless 
specified directly via Docker.
– This segmentation significantly improves security and ease of 
deployment.

Prometheus
– Prometheus is an open-source system for storing and graphing 
highly dimensional data and metrics.
– Efficiently stores metrics in a custom format and scales 
through functional sharding and federation. Data is scraped 
from monitored services over HTTP, rather than the 
applications publishing metrics to Prometheus.
– Developed at SoundCloud originally, now a member of the 
Cloud Native Computing Foundation.

Custom Tracking/Analytics
– You may find that user tracking systems readily available on 
the market are too heavy (performance) or do not meet your 
needs. In situations like these, you may need to build out the 
beginnings of a data warehouse solution.
– Database schemas are generally optimised for user 
performance, not for analytics. Calculating a user’s balance by 
summing their deposits is relatively straight forward. 
Calculating the balance for all users is less-bounded.
– Transforming the database into a format that is better 
optimised for queries, or importing the data into another 
service, are the most common ways of dealing with this.

--- Slide 52 ---
The University of Sydney
Page 52
ETL
– When building a custom tracking system, a common approach 
is to use the Extract, Transform, Load (ETL) process:
– Extract: Extract the data from various sources
– User clicks from JavaScript, web access logs, database changes
– Transform: Transform the data into a consistent format or 
structure.
– Load: Load the transformed data into a final application.

MapReduce
– If we need to perform very computationally intensive analytics 
tasks across a large data set, a useful technique can be 
MapReduce.
– The approach is to perform the data analytics in a distributed 
sense, splitting over two different steps.
 
- Map: Performs filtering and sorting.
 
- Reduce: Consolidates data into a summary format.
