Standing on the Shoulders of Giants: Pre-packaged Software, Docker Deployment and Monitoring

This week is about not building everything yourself. You learn how to evaluate and safely deploy pre-packaged web software (WordPress, MediaWiki, vBulletin), how to harden its application code, configuration and database, how to put a reverse proxy and firewall in front of it, how to package and ship it with Docker containers, and how to monitor and analyse the running system with tools like Prometheus, Grafana, ELK, Nagios, Sentry and Google Analytics.

Read this first: Every pre-packaged application is really just three things — application code, configuration and a database — that you must deploy, secure and watch. Your job as a platform engineer is to wrap that bundle in layers of control: a reverse proxy/WAF at the edge, containers for reproducible deployment, and a monitoring stack that tells you what is happening. Hold this "layers around a bundle" picture in mind and every tool this week slots into place.

Pre-packaged Software: Deploying from the Shoulders of Giants

Pre-packaged software lets you get a real product online in hours instead of months, but you inherit its code, its dependencies and its security baggage.

What pre-packaged software is

Pre-packaged (off-the-shelf) web software is an existing, ready-to-run application that you install rather than build. It is the fastest way to get something up and running. The lecture's canonical examples:

PackageWhat it is
WordPressContent Management System (CMS)
vBulletinInternet forum software
MediaWikiOpen-source wiki platform
PhabricatorProject management tool

The three components every package has

Just like any other website, these packages consist of:

  • Application code — the program itself.
  • Configuration files — settings that shape behaviour.
  • Database — where state and content live.

The package supplies the application code for you, but it is up to the deployer to configure the application and the infrastructure. That division of responsibility is the theme of the whole week. Supporting services such as Memcached (a caching layer) are often part of the deployment picture too.

💡
Why it matters: The vendor hands you code and wishes you luck. Configuration, database, hosting and security are your problem. Most real-world breaches of these systems come from the parts the vendor did not do for you.

The security you inherit

Adopting a package means inheriting not just the main application code but all of its dependencies. The dependency surface includes:

  • Dependency management (the tools that pull in packages).
  • Libraries & frameworks.
  • Plugins / extensions.
  • Container images.
  • System packages.

The resulting risk categories are:

  • Supply chain attacks — malicious code injected upstream.
  • Outdated dependencies — known bugs left unpatched.
  • Plugin/extension ecosystem — third-party add-ons of varying quality.
  • Trust in Docker Hub images — pre-built images you did not build yourself.
🧠
Memory hook: You are not just adopting an app; you are adopting its entire family tree of dependencies.

Application Code: Deciding Whether to Trust It

Blindly running other people's code is dangerous, especially when that code is old and complex — so investigate before you commit.

It can be dangerous to blindly run other people's code, especially when it is old and complex. Before adopting a package, ask:

  • What is it written in?
  • Is the code-base mature?
  • How active is development on the project?
  • Does the software have a history of security vulnerabilities?

Five investigation techniques

  1. Identify other users. If large companies have adopted the software, it is likely they reviewed it before deciding. Their diligence is weak evidence in your favour.
  2. Identify potential support avenues. Determine if support is available through the software supplier. Do they provide direct support? How much does it cost?
  3. Check the frequency of commits. If the software is open-source, look at the activity of its code repository. The more frequent and recent the commits, the more active the development.
  4. Scan for vulnerabilities. Depending on the language and tooling, run a static source-code vulnerability scanner.
  5. Search for known vulnerabilities. Check sites that disclose existing vulnerabilities, such as cvedetails.com.

Tools that automate dependency and vulnerability checks

npm audit                  # Node.js dependency vulnerability audit
pip-audit                  # Python dependency vulnerability audit
OWASP Dependency-Check     # OWASP project: detects vulnerable dependencies
Snyk Vulnerability DB      # security.snyk.io vulnerability database
✅
Exam tip: Know the purpose of each tool, not just its name: npm audit and pip-audit audit dependencies in Node and Python projects; OWASP Dependency-Check is language-agnostic; Snyk is a vulnerability database/service.

Configuration: Secure-by-Default Is a Myth

While secure-by-default releases are good practice, many packages ship with insecure configuration — you must review every option before deployment.

While it is good practice to release software that is secure-by-default, many software packages come with insecure configuration. It is critical to review all configuration options prior to deployment. Questions to ask:

  • What configuration options are available?
  • Are the default values for these options secure?
  • Are there any features enabled that you're not using?
  • Can you disable these features?

Four configuration-review actions

  1. Identify all the configuration options. Read the documentation and view example configurations.
  2. Search the Internet for example configurations. Configurations are generally readily available online — but don't blindly trust them. Evaluate the configuration before using it.
  3. Identify all features and components. Pre-packaged software is usually general purpose: it has the functionality you need, but it also offers many features you do not.
  4. Disable unwanted features. This reduces complexity and the surface area for possible attacks.
⚠️
Common trap: Copying a config from a blog or Stack Overflow without reading it. A working config is not the same as a secure config.

Database: Requirements, Permissions and Blast Radius

The deployer configures the database, so the deployer owns database security — grant the minimum permissions and limit the damage a compromise can do.

It is usually the responsibility of the deployer to configure the database required by pre-packaged software, and care must be taken while doing this. Questions to ask:

  • Does the package need its own database, or can/will it share?
  • What DB permissions are required?
  • If the application is vulnerable, will DB compromise lead to system compromise?

Three database-review actions

  • Identify database requirements. Does the software create a single database for all of its tables, or multiple databases?
  • Evaluate database permissions. It is best practice to give an application the minimum set of permissions. A good approach is to start with the minimal access and extend only when necessary.
  • Evaluate the scope of DB compromise. If a malicious user finds an SQL injection in the application, they may be able to run arbitrary commands on the database. It is therefore important to update the database itself, not just the app.
💡
Why it matters: The database is where the valuable data lives. Least-privilege permissions ensure that an application compromise does not automatically become a full database or system compromise.

Deployment: Putting a Layer of Control in Front

Pre-packaged software often ships its own web interface, and you never want that interface exposed raw to the Internet — insert a layer you control.

Software packages can come with a web/HTTP interface. We don't want that interface directly exposed to the Internet; we want our own layer that we control in between. A reverse proxy (Nginx, Apache) or a load balancer gives us finer control over which requests can reach the application.

This is especially important if the application exposes an admin or control interface without authentication — an unauthenticated admin panel is an open door.

Reverse proxy — A server that sits in front of your application, receives incoming web requests on its behalf, and forwards only the requests you allow to the backend application.

Reverse Proxy: Scaling, Auth and the WAF

Intercepting requests with a reverse proxy gives you load balancing, request authentication and a place to run a Web Application Firewall — three controls from one layer.

Intercepting incoming web requests with a reverse proxy (RP) provides several advantages:

1. Scaling

Use the RP as a load balancer to increase the number of concurrent connections. Run many instances of the application and scale horizontally. Caveat: the database is still a bottleneck for shared state.

2. Request Authentication

If the application is an internal service, perform basic authentication at the proxy to keep anonymous web users out. A malicious user can't access the application if the RP blocks them first.

3. Web Application Firewall (WAF)

A WAF can inspect incoming requests and reject those that appear to be attack vectors.

HTTP Basic Authentication

HTTP Basic Authentication requires HTTP requests to include a username and password to be considered authorised. If a request arrives without valid credentials, the server returns a 401 Unauthorized response.

HTTP Basic Authentication — mechanics

Server side:

  1. The server responds to the initial request with a 401 Unauthorized HTTP response containing the header:
WWW-Authenticate: Basic realm="User Visible Realm"

Client side:

  1. Prompts the user for username/password.
  2. Combines username and password with a single colon: "Aladdin:OpenSesame".
  3. Encodes that string in the RFC2045-MIME variant of base64.
  4. Sets the HTTP request Authorization header to the base64-encoded credentials:
Authorization: Basic QWxhZGRpbjpPcGVuU2VzYW1l
⚠️
Common trap: Base64 is encoding, not encryption. Credentials travel merely obfuscated, so Basic Auth must run over HTTPS.

Web Application Firewall in detail

A WAF applies rules and/or filters to incoming HTTP requests. It tries to identify requests that appear to contain exploitation code and rejects them. All requests should go through the WAF, so it usually sits at the edge/web layer in front of the application.

A WAF is only as good as the rules it evaluates — keep the rule/filter sets up to date.

🧠
Memory hook: The reverse proxy is the bouncer, Basic Auth is the ID check, and the WAF is the metal detector.

Docker and Linux Containers vs Virtual Machines

Containers give you isolation without a full guest operating system, and Docker automates packaging and deploying applications inside them.

VMs vs Linux containers

  • A hypervisor enables the execution of virtual machines inside a host operating system.
  • Linux containers remove the need to install a guest operating system, allowing multiple isolated Linux systems to run on a single host operating system.

The payoff is less overhead per isolated environment, because containers share the host kernel.

What Docker is

Docker is an open-source project to automate the deployment of applications inside Linux containers. It allows easy deployment of packaged applications, including any necessary dependencies. Multiple services/containers can be combined using the tool Docker Compose.

Docker containers

Instead of running virtual machines, Docker allows us to run containers. A Docker container can be thought of as a minimalistic Linux host. You can install any application you like into the container, and the container itself can be (almost) any distribution of Linux.

A Docker container is created based off a Docker image. An image file describes the base operating system and any modifications that need to be made, such as dependencies.

Virtual machine

  • Runs under a hypervisor inside the host OS.
  • Requires a full guest operating system.
  • Heavier: each VM carries its own OS.

Linux container

  • No guest OS needed.
  • Multiple isolated Linux systems on one host.
  • Lighter, shares the host kernel.

Docker Images, Volumes and Networking

Images are the recipe, containers are the running dish, volumes keep the data alive, and container networks decide who can talk to whom.

Docker image example

A sample Docker image that specifies the following:

  • use Ubuntu 18.04 (Xenial) as the base image.
  • executes make in /app (mounted filesystem).
  • copy all files from the /app directory.
  • invoke Python with the entry point of our application.
FROM ubuntu:18.04
RUN make /app
COPY . /app
CMD python /app/app.py

Volumes: where state lives

Docker containers are good for running applications but not good for storing data — containers do not maintain state. Typically we mount volumes into Docker containers to allow persistence.

For example, if creating a Docker container for a database such as MySQL, the data directory for the application should be stored in an attached volume. The mounted volume is a folder on the host machine and exists outside the container. We can then destroy the container without losing data.

Networking: containers talking to containers

Docker containers can be linked to each other and have nominated ports forwarded from the host OS to the container. Example: a WordPress web application can run in one container and the MySQL database in a separate container.

By linking the containers, the WordPress application can talk to the MySQL container directly. No other containers or systems are allowed to communicate with the database unless specified directly via Docker. This segmentation significantly improves security and ease of deployment.

💡
Why it matters: Stateless containers + external volumes = you can rebuild or replace a container freely while your data survives. Linking containers = a database that only its own app can reach.
🧠
Memory hook: Containers are cattle, volumes are the barn.

Docker Hub and Cloud Container Orchestration

Reuse pre-built images from Docker Hub instead of rebuilding, then manage large container fleets with orchestration platforms like AWS ECS or Google Kubernetes Engine.

Docker Hub

Why re-create the wheel? We don't need to build our own Docker containers — we can stand on the shoulders of the giants who have come before us. The Docker project runs a service called Docker Hub, which contains pre-built Docker images. These can be used as a starting point for building services. Many large software companies and projects release Docker Hub images for their software.

Security is a factor to consider here — a pre-built image is still someone else's code (recall the supply-chain and "trust in Docker Hub images" risks).

Container orchestration

When running containers in production, it is common to have container fleets of 10s–1000s. How do we manage these?

  • Google Kubernetes Engine (GKE) — Google's open-source cluster management system for deploying and managing containerised applications on Google Cloud. Kubernetes can also be used outside Google Cloud.
  • AWS Elastic Container Service (ECS) — for deploying Linux containers within the AWS ecosystem.
ℹ️
Note: Docker packages and runs containers on a single host; orchestration platforms coordinate thousands of containers across many hosts.

Monitoring: What to Watch and the Core Tools

A large-scale site must be monitored on every facet, and the toolchain splits cleanly into metrics, graphing, logging, infrastructure and errors.

When running a large-scale website, it is essential to monitor everything. Facets to consider:

FacetQuestion it answers
User InteractionWho clicks on what?
User AnalyticsWhat local time do users usually come online?
HTTP Error RateWhat pages are throwing 500s and impacting users?
Infrastructure MetricsHow is our infrastructure performing? Can we handle 2x load? 10x?

The monitoring toolbox

There are many tools and techniques for monitoring website metrics at the system and application level:

  • Prometheus — metrics.
  • Grafana — graphing above metrics + dashboards.
  • Elasticsearch, Logstash, Kibana (ELK) — logging.
  • Nagios — infrastructure monitoring.
  • Sentry — error detection.

Prometheus

Prometheus is an open-source system for storing and graphing highly dimensional data and metrics. It efficiently stores metrics in a custom format and scales through functional sharding and federation. Data is scraped from monitored services over HTTP, rather than applications publishing metrics to Prometheus. Developed at SoundCloud originally, it is now a member of the Cloud Native Computing Foundation.

Grafana

Grafana allows us to visualise, query and alert on key metrics, regardless of where they are stored. Grafana can have multiple backend metrics systems.

Logging, Infrastructure Monitoring and Error Detection

ELK centralises logs, Nagios watches infrastructure, and Sentry aggregates errors — together they cover the "what happened" half of operations.

Logging with the ELK stack

Once a website reaches a certain size, manually looking at logs on each host is not feasible given the number of services to monitor. The ELK stack (Elasticsearch, Logstash, Kibana) is a commonly used industry pattern for ingesting and querying large volumes of logs (application, web access/error, etc.) in a centralised location.

Kibana is an open-source data visualisation plugin for Elasticsearch. It offers a simple interface for querying Elasticsearch (the service that stores the logs).

Nagios: infrastructure monitoring

Nagios is an open-source "industry standard" for monitoring infrastructure. Many custom metrics can be configured to monitor:

  • Network transfer rates.
  • Server performance.
  • Application metrics.

Nagios has integrations that let it send email, integrate with chat programs, and trigger alerts if metrics are exceeded.

Sentry: error detection

Sentry collects errors from your website, both front-end and back-end, and consolidates and aggregates them into a single feed of events. It allows real-time monitoring of errors experienced while using the website and is a critical piece of infrastructure for large-scale websites.

Tracking and Analytics: Google Analytics and KISSmetrics

Product analytics tells you who your users are and how they behave, so you can prioritise what to build and support.

Google Analytics

Google Analytics (GA) is a tool for tracking and reporting on website traffic. It is a JavaScript library that can be included on any web page. It is essential for determining:

  • Who has visited your website.
  • What browser they are using.
  • What page they came from.

It is a great tool for identifying your audience and prioritising browser/feature support.

KISSmetrics

KISSmetrics is a customer intelligence platform that performs a subset of the features of Google Analytics but provides much deeper insights. It enables an administrator or marketing manager to gain detailed visibility regarding user interaction across devices. It offers a much wider variety of tools and analytics than Google Analytics, however it costs substantially more.

Google Analytics

  • JavaScript library added to any page.
  • Tracks traffic, browser, referrer.
  • Broad audience identification.
  • Free/cheap, general purpose.

KISSmetrics

  • Customer intelligence platform.
  • Deeper cross-device user insights.
  • Wider variety of analytics.
  • Costs substantially more.

Custom Tracking: ETL and MapReduce

When off-the-shelf analytics is too heavy or too shallow, you build a data warehouse using ETL, and scale heavy computation with MapReduce.

Why build custom tracking?

You may find that user tracking systems readily available on the market are too heavy (performance) or do not meet your needs. In those situations you may need to build the beginnings of a data warehouse solution.

The core problem: database schemas are generally optimised for user performance, not for analytics. Calculating a single user's balance by summing their deposits is relatively straightforward. Calculating the balance for all users is less-bounded — it does not scale the same way.

The common fixes: transform the database into a format better optimised for queries, or import the data into another service.

ETL: Extract, Transform, Load

When building a custom tracking system, a common approach is the Extract, Transform, Load (ETL) process:

  1. Extract: Extract the data from various sources — user clicks from JavaScript, web access logs, database changes.
  2. Transform: Transform the data into a consistent format or structure.
  3. Load: Load the transformed data into a final application.

MapReduce

If we need to perform very computationally intensive analytics tasks across a large data set, a useful technique is MapReduce. The approach performs the data analytics in a distributed sense, split over two steps:

  • Map: Performs filtering and sorting.
  • Reduce: Consolidates data into a summary format.
Extract→Transform→Load→Query
💡
Why it matters: Operational databases are tuned to serve one user fast; analytics needs to scan everyone. ETL reshapes data for that purpose, and MapReduce spreads the heavy scan across many machines.

Glossary

Every term you need to speak this week's language.

Pre-packaged software
Ready-made web applications such as WordPress, vBulletin, MediaWiki and Phabricator that you deploy rather than build; they supply application code only, not configuration or database.
Supply chain attack
An attack that compromises software through its upstream dependencies, libraries, plugins or images rather than the main application.
Dependency auditing tools
Tools such as npm audit (Node), pip-audit (Python) and OWASP Dependency-Check that detect known vulnerabilities in a project's dependencies.
Least privilege
The practice of granting an application the minimum set of database permissions needed, extending only when necessary.
Reverse proxy
A server (e.g. Nginx, Apache) that intercepts incoming web requests and forwards only permitted ones to the backend application; can also load balance.
HTTP Basic Authentication
An authentication scheme requiring a username and password in the request; failures return 401 Unauthorized with a WWW-Authenticate header.
Web Application Firewall (WAF)
A filter at the edge/web layer that inspects incoming HTTP requests and rejects those that look like exploitation attempts.
Linux container
An isolated Linux environment that shares the host kernel and needs no guest operating system, unlike a VM under a hypervisor.
Docker
An open-source project that automates deploying applications inside Linux containers, including dependencies; Docker Compose combines multiple services.
Docker image
A file describing a base operating system plus any modifications (such as dependencies) from which containers are created.
Docker container
A minimalistic Linux host created from an image; containers do not maintain state.
Volume
A folder on the host machine mounted into a container so data persists outside the container's lifecycle.
Docker Hub
Docker's service hosting pre-built images that can seed new services; trust in these images is a security consideration.
Elastic Container Service (ECS)
AWS's service for deploying Linux containers within the AWS ecosystem.
Kubernetes / GKE
An open-source cluster management system (Google Kubernetes Engine on Google Cloud) for deploying and managing containerised applications.
Prometheus
An open-source system for storing and graphing highly dimensional metrics, scraping data from services over HTTP.
Grafana
A tool to visualise, query and alert on metrics from multiple backend systems via dashboards.
ELK stack
Elasticsearch, Logstash and Kibana — an industry pattern for centrally ingesting and querying large volumes of logs.
Nagios
An open-source industry-standard infrastructure monitoring tool with email/chat alerting.
Sentry
A tool that collects and aggregates front-end and back-end errors into a single real-time event feed.
Google Analytics
A JavaScript library for tracking and reporting website traffic, browser and referrer data.
KISSmetrics
A customer intelligence platform offering deeper cross-device user insights than Google Analytics at higher cost.
ETL
Extract, Transform, Load — the process of pulling data from sources, reshaping it, and loading it into an analytics store.
MapReduce
A distributed analytics technique where Map filters and sorts and Reduce consolidates into a summary.

Q1

What are the three components of any pre-packaged web application, which one does the package provide, and what security risks do you inherit by adopting it?

Answer: Application code, configuration files and a database. The package provides the application code; the deployer must configure the application and infrastructure (including the database). Inherited risks include supply chain attacks, outdated dependencies, the plugin/extension ecosystem and trust in Docker Hub images (also inherited libraries, container images and system packages).
Q2

You are evaluating an open-source package before adopting it. Name four investigation techniques, and name tools that audit its dependencies.

Answer: Techniques: identify other users (large adopters likely reviewed it); identify support avenues (availability and cost of supplier support); check commit frequency (more frequent/recent commits = more active development); scan for vulnerabilities with a static source scanner; search known vulnerabilities (e.g. cvedetails.com). Dependency tools: npm audit (Node), pip-audit (Python), OWASP Dependency-Check (language-agnostic), Snyk Vulnerability DB.
Q3

Why is it risky to trust a default configuration, and what four questions should you ask when reviewing configuration?

Answer: Many packages ship with insecure configuration despite secure-by-default being good practice. Ask: what configuration options are available; are the defaults secure; are there features enabled you aren't using; can you disable those features. Disabling unused features reduces complexity and attack surface.
Q4

Explain the principle of least privilege for database permissions and why it matters if the application is vulnerable.

Answer: Give the application the minimum permissions it needs, starting minimal and extending only when required. If an attacker finds an SQL injection, least privilege limits what they can do — without it, an application compromise could become a database or even system compromise. The database itself should also be kept updated.
Q5

What is the purpose of placing a reverse proxy in front of a pre-packaged application, and why is it especially important for admin interfaces?

Answer: A reverse proxy (or load balancer) is a layer you control between the Internet and the application, giving finer control over which requests reach it, plus scaling, request authentication and WAF capability. It is especially important if the application exposes an admin or control interface without authentication, which would otherwise be openly reachable.
Q6

Describe the full mechanics of HTTP Basic Authentication on both sides, and explain why HTTPS is required.

Answer: The server returns 401 Unauthorized with header WWW-Authenticate: Basic realm="User Visible Realm". The client prompts for username/password, joins them with a colon (Aladdin:OpenSesame), base64-encodes the string using the RFC2045-MIME variant, and sends Authorization: Basic QWxhZGRpbjpPcGVuU2VzYW1l. Requests without valid credentials get a 401. HTTPS is required because base64 is encoding, not encryption, so credentials are otherwise only obfuscated.
Q7

How does a Linux container differ from a virtual machine, and what does Docker add on top?

Answer: A VM runs under a hypervisor and requires a full guest operating system. A Linux container needs no guest OS and shares the host kernel, so multiple isolated Linux systems run on one host. Docker automates deploying applications (and their dependencies) inside Linux containers; Docker Compose combines multiple services.
Q8

Interpret this Dockerfile line by line: FROM ubuntu:18.04, RUN make /app, COPY . /app, CMD python /app/app.py.

Answer: FROM ubuntu:18.04 sets Ubuntu 18.04 as the base image; RUN make /app executes make in the mounted /app filesystem during the build; COPY . /app copies all files into /app; CMD python /app/app.py sets the command that starts the application by invoking Python on the entry point.
Q9

Why are volumes needed with Docker, and what happens if you run a database container without one?

Answer: Containers do not maintain state, so data stored inside a container is lost when it is destroyed. A volume is a host-machine folder mounted into the container so data persists; running a database like MySQL without an attached volume risks losing its data directory.
Q10

In a WordPress + MySQL container setup, how does container linking improve security?

Answer: The two containers are linked so the WordPress application can talk directly to the MySQL container, while no other container or system can communicate with the database unless explicitly allowed via Docker. This segmentation improves both security and ease of deployment.
Q11

What is Docker Hub, what security consideration comes with it, and what problem do AWS ECS and Google Kubernetes Engine solve?

Answer: Docker Hub is Docker's service hosting pre-built images that serve as starting points for building services (so you don't rebuild the wheel); the security consideration is trust, since you are running someone else's image (supply-chain risk). ECS and GKE/Kubernetes orchestrate production container fleets of 10s–1000s; GKE is an open-source cluster management system also usable outside Google Cloud.
Q12

Match each monitoring tool to its job (Prometheus, Grafana, ELK, Nagios, Sentry), and explain how Prometheus collects and scales.

Answer: Prometheus = metrics, storing/graphing highly dimensional data; Grafana = visualising, querying and alerting on metrics/dashboards across multiple backends; ELK (Elasticsearch, Logstash, Kibana) = centralised log ingestion and querying; Nagios = infrastructure monitoring with alerts; Sentry = front-end and back-end error detection/aggregation. Prometheus scrapes data from monitored services over HTTP rather than receiving pushes, stores metrics in a custom format, and scales via functional sharding and federation.
Q13

Compare Google Analytics and KISSmetrics, and state when you would build custom tracking instead.

Answer: Google Analytics is a JavaScript library included on any page for tracking/reporting traffic, browser and referrer — useful for audience identification and prioritising browser support. KISSmetrics is a customer intelligence platform performing a subset of GA's features but with much deeper cross-device user insights and a wider variety of analytics, at substantially higher cost. Build custom tracking when off-the-shelf systems are too heavy (performance) or don't meet your needs; database schemas are optimised for user performance, not analytics, so computing metrics for all users is far less bounded.
Q14

Describe the ETL process and the MapReduce technique.

Answer: ETL — Extract data from various sources (user clicks from JavaScript, web access logs, database changes); Transform it into a consistent format or structure; Load the transformed data into a final application. MapReduce is a distributed technique for very computationally intensive analytics over large data sets: Map performs filtering and sorting, and Reduce consolidates the data into a summary format.
