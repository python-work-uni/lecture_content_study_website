Front-end Development: Building for the Browser

The front-end is everything the user actually sees and touches. This week covers how to design a good user experience, how browsers differ, and the three core technologies — HTML (structure), CSS (presentation) and JavaScript (behaviour) — plus the DOM that binds them, single page applications, AJAX, and the build tools that glue modern web projects together.

Read this first: Think of a web page as three separate jobs done by three separate languages. HTML says what the content is, CSS says what it looks like, and JavaScript says what it does. The browser is the runtime that renders all three, and every browser does it slightly differently. Hold that separation-of-concerns picture in your head and the whole lecture becomes one story about structure, style, behaviour, and compatibility.
~20 min read13 teaching sections14 practice questions24 key terms

By the end you will be able to

  • Explain what the front-end is and where it sits relative to the backend.
  • Distinguish UX from UI, and describe the roles of wireframe, mockup and prototype.
  • Explain why browsers differ and how to test and constrain cross-browser compatibility.
  • Write the skeleton of a valid HTML5 document and use key elements, tags and attributes correctly.
  • Describe the DOM and manipulate it from JavaScript.
  • Write CSS rules with element, class and ID selectors and use media queries for responsive design.
  • Explain what JavaScript is, its historical weaknesses, and how TypeScript and JQuery relate to it.
  • Describe single page applications and AJAX, weighing their pros and cons.
  • Identify what Bower, Grunt and Webpack each do in a front-end toolchain.

The Front-end and the Interface

The front-end is the presentation layer — the interface between the user and everything the backend does.

The front-end is the presentation layer of a web application. It sits between the user and the backend, where the backend handles data access, computation and business logic. Everything that runs inside the browser and that a user can see or interact with is front-end software. Because the front-end is the interface, its quality is measured by the experience it creates. A homely aphorism captures the stakes: "Mobile is a magnifying glass for your usability problems." Design flaws that are forgivable on a big desktop screen become glaring on a small phone, so testing on constrained devices exposes problems you would otherwise miss.

Building good user interfaces is engineering, not art

A common misconception is that good UI is a matter of artistic talent. It is not.

  • Building effective user interfaces is not art.
  • Effective interfaces are sensible, consistent and structured.
  • If you can develop software, you can build an effective user interface — provided you dedicate the time.
💡
Why it matters: Framing UI as structured engineering rather than innate artistry means interface quality is something you can systematically learn, plan and test — not a mysterious gift.

What makes a good user experience

  • Users shouldn't need instructions.
  • Common tasks should take simple steps.
  • Every click matters.
  • Ultimately: make the user happy.

Design is how it works, not how it looks

Steve Jobs framed the whole discipline: > "Most people make the mistake of thinking design is what it looks like. People think it's this veneer — that the designers are handed this box and told, 'Make it look good!' That's not what we think design is. It's not just what it looks like and feels like. Design is how it works."

Classic examples used to make this point are familiar apps like Google Inbox, Medium and Slack (good, thoughtful interfaces), contrasted with LingsCars (a notoriously chaotic page). The everyday proof that bad design is everywhere is the door: a door whose handle says "pull" while its shape says "push" fails at how it works even if it looks fine.

🤔
Pause & predict: Think of an app you use daily. Identify one place where it makes you read instructions or take an extra step. Was that a visual problem or a behaviour problem?
🧠
Memory hook: Design is not veneer — it is how it works.

UX vs UI, and Design Deliverables

UX and UI are distinct specialisms, and each produces a distinct artefact — wireframe, mockup and prototype.

People casually say "UI/UX" as one thing, but they are different roles, different skills and different deliverables.

The three design artefacts

These artefacts form a progression from abstract structure to interactive behaviour, and each answers a different question.

Wireframe

  • Shows the information that will be displayed.
  • An outline of the structure and layout of components.
  • A blueprint for each page that will be implemented.

Mockup

  • Key information: the visual appearance of the page.
  • Should be more detailed than a wireframe.

The prototype then adds behaviour on top:

  • Key information: how the page works.
  • Can be low or high fidelity; the focus is on how it behaves.
  • Users should be able to use and interact with it.
Wireframe→Mockup→Prototype

(Structure → Appearance → Behaviour)

✅
Exam tip: If a question asks which artefact is interactive, the answer is always the prototype. If it asks which is a blueprint/outline, it is the wireframe.

Design practice and resources

Two design practices matter for the web:

  • Responsive design — layouts that adapt across devices.
  • Inclusive design — design that does not exclude people on the basis of disability, religion, gender identity, race, language, sexual orientation, ethnicity, pronunciation, or age.

Useful reference resources for patterns and inspiration include:

  • UI Patterns — https://ui-patterns.com/patterns
  • Hike — https://hike.one/
  • UX Library — https://www.uxlibrary.org/explore/ui-design/ui-patterns-and-inspiration

Web Components

A web component is a reusable blob of HTML, CSS and JS that behaves like a custom HTML element.

A web component is a set of custom HTML elements plus the technologies that facilitate their development. Put simply, components are components on the Web — any reusable blob of HTML, CSS and JS.

Web components are valued because they give you four properties:

Reactivity

The component responds and updates when its underlying data changes.

Encapsulation

The component's internals are kept self-contained and isolated from the rest of the page.

Modularity

Functionality is split into distinct, well-bounded pieces.

Reusability

The same component can be dropped into many pages and projects.

💡
Why it matters: Encapsulation plus reusability is what lets large front-end codebases stay maintainable — you build a component once, trust it behaves predictably, and reuse it everywhere.

The Browser Landscape and Compatibility

Not all browsers are created equal — you must test deliberately and choose what you support strategically.

The browser is the runtime for front-end code, and no two browsers render identically. This is a core practical constraint of front-end work.

Everything varies

  • Each browser is different.
  • Each version of a browser is different.
  • Each version is different on each operating system.
  • Screen resolutions differ.
  • Mobile devices add further variation.

Because of this, you must consider interoperability between browsers, browser versions and operating systems whenever you write web applications.

ℹ️
Note: Can I Use? (caniuse.com) is the standard quick reference for checking browser support for a given feature and its known limitations.

Cross-compatibility testing

  • If your application must run on a certain browser, you must test it on that browser. Never assume it will work.
  • Test different browsers on your own local machine.
  • Test different operating systems by emulating them with virtual machines — but beware: virtualisation can introduce bugs itself.
  • Professional tools and services exist for cross-compatibility testing, often letting you test on real hardware and devices (for example, a Windows Phone).
⚠️
Common trap: Testing in a VM is not the same as testing on real hardware. Virtualisation can create bugs (or hide them), so real-device testing is more trustworthy when it matters.

You don't need to support ALL browsers

  • You don't need to — and probably shouldn't — support every browser, version and operating system.
  • At the start of your project, decide what you will and won't support.
  • Base that decision on your intended customer base: know your intended audience.
✅
Exam tip: "Support everything" is the wrong answer. The right approach is a deliberate, documented support decision grounded in your audience.

HTML Foundations: Versions and Document Structure

HTML is an evolving specification that gives a document its structure, and every document starts with a DOCTYPE.

HTML (HyperText Markup Language) is a constantly evolving specification. Browsers implement subsets of the specifications, which is why the same document can behave differently across browsers.

Version timeline

YearMilestone
1997HTML 3.2
1999HTML 4.01
2007HTML5 draft published
2014HTML5 published as a W3C Recommendation

Features introduced with HTML5 include the <audio> and <video> elements, and new input types such as data, time and color.

The DOCTYPE tag

The DOCTYPE is not an HTML tag — it is an instruction to the browser telling it which version of HTML the page uses.

  • It must be the very first line in your document.
  • The HTML5 DOCTYPE declaration is:
<!DOCTYPE html>
  • This HTML5 declaration will masquerade as HTML4 for older browsers.
  • The HTML4 DOCTYPE is more complex:
<!DOCTYPE HTML PUBLIC "-//W3C//DTD HTML 4.01//EN" "http://www.w3.org/TR/html4/strict.dtd">
🧠
Memory hook: DOCTYPE is an instruction, not a tag — and it goes first, always.

A minimal HTML5 document

A simple HTML5 document implements structure (HTML), presentation (CSS) and behaviour (JavaScript) together. The mandatory outer skeleton is:

<!DOCTYPE html>
<html lang="en">
  <head>
    <title>My Page</title>
    <link rel="stylesheet" href="styles.css">
  </head>
  <body>
    <h1>Hello</h1>
    <p>This is a page.</p>
    <script src="app.js"></script>
  </body>
</html>

Element overview

The basic building-block elements include:

ElementRole
<html>Encapsulates the entire document
<head>Metadata, separate from rendered content
<title>Document title (mandatory in <head>)
<body>The rendered content
<h1>Top-level heading
<p>Paragraph

HTML Tags, Head, Body and Attributes

Each tag has a role, the head and body split metadata from content, and attributes configure elements.

The HTML tag

  • Encapsulates the entire HTML document.
  • Can specify the language used in the document (for example <html lang="en">).

The HEAD tag

  • Contains meta information separate from the content.
  • Its elements are not rendered in the view.
  • CSS files are generally imported here.
  • JavaScript imported here delays rendering of the page until the scripts are loaded. JS can instead be imported in the body to speed up page loading.
  • The <title> tag is mandatory in this section.
💡
Why it matters: Script loading blocks rendering. Putting scripts at the end of the body lets the page paint first, so users see content sooner.

The BODY tag

  • Contains the HTML elements to be rendered to the view.
  • If you place <script> tags in this section, convention is to put them just before the closing </body> tag.
  • Body is a mandatory tag for an HTML document.
  • Never skip the end tag.
  • Empty elements have no closing tag — for example <br>.

Attributes

Two firm rules:

  • Always use lowercase attributes.
  • Always quote attribute values.

Either single or double quotes are accepted, but quoting is required. Elements commonly given attributes include <a>, <img> and <p>:

<a href="https://www.sydney.edu.au/">Visit USYD</a>
<img src="img_girl.jpg">
<p style="color:red;" title="I'm a tooltip">This is a red paragraph.</p>
⚠️
Common trap: Forgetting the closing tag (or mismatching quotes around an attribute) are the two most common beginner HTML errors. Empty elements like <br> are the deliberate exception.

The DOM: The Document Object Model

The DOM treats an HTML document as a tree of objects that JavaScript can read and change.

The Document Object Model (DOM) treats an HTML document as a tree-like structure of objects. Each element, attribute and piece of text is a node in that tree.

Manipulating the DOM from JavaScript forms the majority of JavaScript usage in the browser. This is the mechanism that makes pages dynamic.

Finding elements

JavaScript locates elements in the tree using built-in methods, including:

  • By ID: getElementById
  • By tag name: getElementsByTagName
  • By class name: getElementsByClassName
  • and others beyond these.

What you can do once you have an element

  • Change HTML content.
  • Update the value of an attribute.
  • Create dynamic HTML content — for example inserting the current Date().
  • Write directly to the HTML output stream.
  • and much more.
💡
Why it matters: Every dynamic behaviour on a modern web page — a countdown, a live search box, a cart that updates without reloading — is ultimately JavaScript modifying DOM nodes.

Reasoning about event order

A classic DOM question asks what a script logs when elements are connected and disconnected. The observable answer depends on the order in which nodes are added to and removed from the tree: when a custom element is inserted it typically logs 'connected', and when it is removed it logs 'disconnected'. Reading the sequence of DOM insertions and removals is what determines the output.

🤔

CSS: Cascading Style Sheets

CSS describes presentation and cleanly separates "what's in a document" from "what it looks like".

Cascading Style Sheets (CSS) describes the presentation of an HTML document. It enables a separation of concerns between two questions:

  • What's in a document? → HTML
  • What does a document look like? → CSS

Like HTML, CSS has different versions and varying support across browsers. CSS can be difficult to get right but is 100% worth it.

CSS syntax

selector { property: value; }
PartMeaning
SelectorPoints to the HTML element the style applies to
PropertyThe attribute that should be modified
ValueWhat the value should be updated to
{ }The declaration block; may contain multiple property–value pairs

Selectors

Element selector — selects by tag name. This selects the body element, applies a background colour and sets a font:

body {
  background-color: #f0f0f0;
  font-family: Arial, sans-serif;
}

Class selector — selects any element carrying that class. Here any element with the dog class gets bold, blue text:

.dog {
  font-weight: bold;
  color: blue;
}
  • A class may be applied to multiple elements.
  • An element may have multiple classes.

ID selector — selects only one element. The first element with the dog-name id becomes underlined with red text:

#dog-name {
  text-decoration: underline;
  color: red;
}
  • An id is used to select only one element.
  • An element may have only one id.
🧠
Memory hook: #id is unique like a passport number; .class is a shared label like a team jersey.

Media queries and responsive design

Media queries let you customise how a document displays across devices by applying conditions to CSS rules.

  • CSS is applied if the @media query returns true.
  • They are great for creating responsive pages.
@media (max-width: 600px) {
  body { font-size: 14px; }
}
🤔
Pause & predict: You need to style three separate elements the same way, but they must remain individually identifiable for JavaScript. Which selector type — element, class or id — is the right tool?

CSS Frameworks

The best CSS is written by someone else — use a framework, but choose it deliberately.

The lecture's conclusion about hand-written CSS is blunt: the best CSS is written by someone else. Use a framework.

Popular frameworks

  • Bootstrap
  • Foundation
  • Materialize

Choosing a framework

Choose carefully — switching between frameworks can be laborious and time-consuming. When evaluating a framework, consider four factors:

Aesthetics

Does the default look and feel suit your product?

Grid system

Does its layout grid fit how you want to arrange pages?

Community support

Is there an active community for help, plugins and longevity?

Cross-browser compatibility

Does it behave consistently across the browsers you support?

✅
Exam tip: Switching frameworks is the expensive choice, so the decision belongs early — the same "decide up front" principle as choosing which browsers to support.

JavaScript: Language, Issues and TypeScript

JavaScript makes pages dynamic by manipulating the DOM, evolved from a famously awkward language into a solid one.

JavaScript is a high-level, dynamic, untyped, interpreted programming language. It lets pages become dynamic by manipulating the HTML DOM with code. Alongside HTML and CSS it forms the fundamental core of today's modern web. Learning to appreciate JavaScript will improve your applications and make you more employable.

Historical issues

Early versions of JavaScript were hard to develop in, for concrete reasons:

  • Weird equality / automatic conversion. Loose equality and implicit coercion caused surprises.
  • The behaviour of this. Its value was notoriously context-dependent.
  • Lack of a type system.
  • Weak static analysis support and poor tooling.
  • Lack of a module system.

JavaScript is constantly evolving, and the language has improved significantly in more recent versions. The verdict: JavaScript isn't perfect, but it's here to stay.

TypeScript

TypeScript is an open-source language that implements a superset of JavaScript while adding optional static types.

  • Developed and maintained by Microsoft.
  • Designed for the development of large web applications.
  • Transpiled back to JavaScript (so browsers can run it).
  • It adds support for:
  • types
  • modules / namespaces
  • classes

JavaScript

  • High-level, dynamic, untyped, interpreted.
  • Runs directly in the browser.
  • Weak static analysis and poor historical tooling.
  • No native type system or classic module system in early versions.

TypeScript

  • Superset of JavaScript with optional static types.
  • Written in TypeScript, transpiled to JavaScript.
  • Microsoft-maintained; aimed at large apps.
  • Adds types, modules/namespaces and classes.
🤔
Pause & predict: TypeScript adds types, but browsers don't understand TypeScript. What must happen to your source before a browser can run it?

JQuery, Single Page Applications and AJAX

SPAs and AJAX let JavaScript update the page without a hard refresh — powerful, but with real trade-offs.

JQuery

JQuery is described as the "Swiss army knife" of the web:

  • Commonly used on web pages.
  • Highly supported with an active community.
  • Likely to have everything you need to interact with the DOM.
  • Great for cross-platform support.

It is becoming less popular because modern frameworks supersede JQuery's functionality, and browsers now implement native versions of much of what the library provided.

Single Page Applications (SPAs)

A single page application loads a single HTML document and uses JavaScript to update the user's view without a hard refresh. SPAs move a lot of work to the client side (browser) and typically create a smoother, more fluid user experience, enabling significantly more powerful web applications.

Pros:

  • Provide a faster interface.
  • Encourage separation of concerns.
  • Are reusable.
  • Allow for "serverless" browser applications.
  • Simpler binding of data to views.
  • Easy to serve from a CDN, decreasing user load time.
  • Removes load from backend servers.

Cons:

  • Typically require more work.
  • Typically require more experienced developers due to complexity.
  • New frontier — frameworks are rapidly evolving.
  • Pushes workload into the browser, which is bad for low-spec/mobile devices.

AJAX

AJAX stands for Asynchronous JavaScript and XML. It allows the page to be updated with external data without a full refresh. AJAX is a fundamental aspect of the modern web.

Ways to do it, in historical order of convenience:

  • Traditionally XHR (XMLHttpRequest) — clunky and cumbersome.
  • JavaScript libraries like JQuery improved the situation.
  • Native browser APIs such as Fetch where supported.

Popular JavaScript frameworks

  • Angular (Google)
  • React (Facebook)
  • Ember
  • Backbone.js
⚠️
Common trap: SPAs are not free wins. The same client-side power that makes them smooth also burdens low-spec and mobile devices, and demands more experienced developers.
🤔
Pause & predict: A team wants a snappy app with minimal server load, but their users are mostly on cheap phones. Which SPA "con" should worry them most?

Development Tools

Bower, Grunt and Webpack automate dependency management, repetitive tasks and bundling.

Real front-end projects rely on build tooling. Three tools represent the classic trio.

Bower — a package manager for the web

  • Imagine pip, but for frontend HTML, JS and CSS libraries.
  • A Node.js application, installed via npm.
  • Can fetch packages and their dependencies.
  • Makes it much easier to update packages.
  • You document your dependencies in a bower.json file.

Grunt — a JavaScript task runner

  • Similar to a Makefile, but for HTML frontends.
  • Also a Node.js application, installed via npm.
  • Automates boring, repetitive tasks:
  • minification of images, CSS, JS and HTML
  • dependency linking
  • linting (error/style checking)
  • testing
  • Gulp is another popular JS task runner.

Webpack — a JavaScript module bundler

  • Generates static assets containing only the dependencies needed.

Bower

  • Package manager.
  • Fetches libraries and their dependencies.
  • Config in bower.json.
  • Mental model: pip for the front-end.

Grunt

  • Task runner.
  • Automates minification, dependency linking, linting, testing.
  • Mental model: Makefile for front-ends.

Bower

Dependency / package management for front-end libraries.

Grunt

Task automation for repetitive build steps.

Webpack

Module bundling into static assets with only what's needed.

Putting It Together: The Modern Front-end Stack

One request from a browser flows through HTML, CSS, JavaScript and the DOM — and quality comes from deliberate design, testing and tooling.

To consolidate: a browser requests a document. The HTML defines the structure, the CSS defines the presentation, and the JavaScript defines behaviour by manipulating the DOM. Web components package HTML, CSS and JS into reusable, encapsulated units. SPAs lean heavily on JavaScript to update views without reloads, using AJAX / Fetch to pull in data. Frameworks (CSS and JS) and build tools (Bower, Grunt, Webpack) make this manageable at scale.

The through-line is deliberation: decide which browsers you support, choose your frameworks early, test on the real target platforms, and design interfaces that are sensible, consistent and structured.

HTML (structure)→CSS (presentation)→JavaScript (behaviour)→DOM (live page)
💡
Why it matters: Separation of concerns is the organising idea of the entire week. Each layer has one job, which is what keeps complex front-ends comprehensible and testable.
✅
Exam tip: If asked to explain "separation of concerns" in the front-end, name the three languages and the job each owns, then say the DOM is the boundary where JavaScript reaches into the document.

Key Takeaways

If you remember nothing else, remember this.

1

The front-end is the presentation layer: the interface between the user and the backend, running in the browser.

2

Good UI is sensible, consistent and structured engineering — not artistic talent — and good UX means users need no instructions and every click counts.

3

UX and UI are distinct: UX charts the user journey and information architecture, UI governs colour, typography and visual aesthetic.

4

Wireframe = structure/blueprint; mockup = visual appearance; prototype = how it works (interactive, low or high fidelity).

5

Browsers, browser versions, operating systems, resolutions and devices all differ, so test deliberately and choose which browsers to support up front based on your audience.

6

HTML5 is the current spec; the DOCTYPE is an instruction (not a tag), must be first line, and <html>, <head>, <title> and <body> form the mandatory skeleton.

7

Attributes must be lowercase and quoted; the head holds non-rendered metadata and CSS; scripts in the body should sit just before the closing </body> tag to avoid blocking render.

8

The DOM is a tree of objects; manipulating it from JavaScript is the majority of browser JavaScript, using methods like getElementById and getElementsByTagName.

9

CSS separates "what's in a document" from "what it looks like"; the syntax is selector { property: value; } with element, class (.), and id (#) selectors.

10

Media queries apply CSS conditionally to build responsive pages; frameworks like Bootstrap, Foundation and Materialize are usually better than hand-rolled CSS, but switching frameworks is costly.

11

13

Bower manages front-end packages (bower.json), Grunt automates repetitive tasks (minify, lint, test), and Webpack bundles modules into static assets.

Practice Questions

Look away from the page first — retrieval is what builds memory.

Answer, reveal, then tick “Mastered”. Your progress is saved.
Q1

What is the front-end, and how does it relate to the backend?

Answer: The front-end is the presentation layer of a web application. It is the interface between the user and the backend, where the backend handles data access and computation. The front-end is the software that executes in the browser.
Q2

Explain the difference in responsibilities between a UX designer and a UI designer.

Answer: A UX (interaction) designer charts the user pathway, plans information architecture, and is expert in wireframes, prototypes and research. A UI (visual) designer chooses colour and typography, plans the visual aesthetic, and is expert in mockups, graphics and layouts. UX shapes the journey; UI paints the scenery.
Q3

What are the three design artefacts, and what question does each answer?

Answer: A wireframe shows the information to be displayed and outlines structure/layout — a blueprint for each page. A mockup shows the visual appearance and is more detailed than a wireframe. A prototype shows how the page works and is interactive (low or high fidelity).
Q4

Why must a front-end developer care about browser differences, and how should testing and support decisions be approached?

Answer: Browsers, browser versions, operating systems, screen resolutions and devices all differ, so interoperability must be considered. Test each required browser on that browser (never assume), test OSes via virtual machines (noting virtualisation can itself introduce bugs), and use professional tools/services that test on real hardware and devices. You need not — and probably shouldn't — support everything; decide up front what you will and won't support based on your intended audience.
Q5

Write the DOCTYPE for an HTML5 page and state two rules about it.

Answer: <!DOCTYPE html>. It is not an HTML tag — it is an instruction to the browser about which HTML version the page uses. It must be the very first line of the document, and the HTML5 form will masquerade as HTML4 for older browsers.
Q6

Compare the <head> and <body> tags, state where CSS and JS should go, and give two rules for attributes.

Answer: <head> contains meta information separate from content, is not rendered in the view, and is where CSS is generally imported; <title> is mandatory there. Importing JS in the head delays rendering until scripts load, so JS is often imported in the body instead. <body> contains the rendered elements and is mandatory; convention places script tags just before the closing </body> tag. For attributes: always use lowercase names and always quote values (e.g. <a href="https://www.sydney.edu.au/">Visit USYD</a>).
Q7

What is the DOM, and how does JavaScript use it?

Answer: The Document Object Model treats an HTML document as a tree-like structure of objects. JavaScript manipulates the DOM — the majority of browser JavaScript usage — to change HTML content, update attribute values, create dynamic content (e.g. Date()), and write to the HTML output stream. Elements are found by id (getElementById), tag name (getElementsByTagName) or class name (getElementsByClassName).
Q8

Explain the separation of concerns CSS provides, give the CSS rule syntax, and distinguish element, class and id selectors.

Answer: CSS separates "what's in a document" (HTML) from "what a document looks like" (CSS). The syntax is selector { property: value; }, where the selector points to the element, the property is the attribute to modify, the value is the new setting, and the { } declaration block can hold multiple property–value pairs. Element selectors target a tag (e.g. body). Class selectors (.dog) can apply to multiple elements, and an element can have multiple classes. ID selectors (#dog-name) select only one element, and an element may have only one id.
Q9

What are media queries, and name three popular CSS frameworks plus four factors for choosing one.

Answer: Media queries apply conditions to CSS rules so the CSS is applied only if the @media query returns true, allowing a document to adapt across devices — the key tool for responsive pages, e.g. @media (max-width: 600px) { ... }. Popular frameworks: Bootstrap, Foundation and Materialize. Factors: aesthetics, grid system, community support, and cross-browser compatibility. Choose carefully because switching frameworks later is laborious and time-consuming.
Q10

Summarise JavaScript's definition and its historical development problems.

Answer: JavaScript is a high-level, dynamic, untyped, interpreted programming language that makes pages dynamic by manipulating the DOM. Historical problems: weird equality/automatic conversion, confusing behaviour of this, lack of a type system, weak static analysis and poor tooling, and lack of a module system. It has improved significantly in recent versions.
Q11

What is TypeScript and how does it relate to JavaScript?

Answer: TypeScript is an open-source language implementing a superset of JavaScript while adding optional static types. It is developed and maintained by Microsoft for large web applications and is transpiled back to JavaScript. It adds support for types, modules/namespaces and classes.
Q12

Define a single page application and give two pros and two cons.

Answer: An SPA loads a single HTML document and uses JavaScript to update the user's view without a hard refresh, moving work to the client side. Pros: faster interface, separation of concerns, reusable, serverless browser apps, simpler data-to-view binding, easy CDN serving, reduced backend load. Cons: more work, needs more experienced developers, rapidly evolving frameworks, and heavy client-side workload bad for low-spec/mobile devices.
Q13

What is AJAX, and what technologies have been used to implement it?

Answer: AJAX (Asynchronous JavaScript and XML) allows a page to be updated with external data without a full refresh and is fundamental to the modern web. It was traditionally done with XHR (XMLHttpRequest), which is clunky; libraries like JQuery improved it; and native browser APIs such as Fetch are an option where supported.
Q14

What does each of Bower, Grunt and Webpack do?

Answer: Bower is a package manager for front-end HTML, JS and CSS libraries (a Node.js app installed via npm, with dependencies documented in bower.json). Grunt is a JavaScript task runner that automates minification, dependency linking, linting and testing (Gulp is an alternative). Webpack is a JavaScript module bundler that generates static assets containing only the dependencies needed.
