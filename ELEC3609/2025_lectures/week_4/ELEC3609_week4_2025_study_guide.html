It explains what makes a good user experience, how designers plan a page using wireframes, mockups and prototypes, how to cope with many different browsers and devices, and the three core web technologies — HTML, CSS and JavaScript. Front-End, UX & UI Roles

The front-end is the presentation layer of a web application. It runs in the client's browser and acts as the interface between the user and the back-end (data access, computations and business logic). Everything you can see and click on a website is front-end code. A memorable line from the lecture captures why this layer matters:

💡
Why It Matters:: "Mobile is a magnifying glass for your usability problems." A cramped phone screen exposes every clumsy layout, tiny button and confusing step that a large desktop monitor might hide. Design for the worst case and the best case looks after itself.

Good UX Is Engineering, Not Art

Building effective user interfaces is not art. Effective interfaces are sensible, consistent and structured. The lecture's encouraging point is that if you can develop software, you can build an effective user interface — provided you dedicate the time to it. The golden rules of good user experience:

  • Users shouldn't need instructions — the interface should explain itself.
  • Simple steps for common tasks — keep frequent actions short and direct.
  • Every click matters — each unnecessary click is friction that loses users.
  • Make the user happy — predictable, responsive interactions reduce frustration.

Steve Jobs framed the same idea: "Design is not just what it looks like and feels like. Design is how it works."

UX vs UI — Two Different Jobs

RoleFocusTypical Deliverables
UX designer (interaction design)How it works: charts the user pathway, plans information architectureWireframes, prototypes, user research
UI designer (visual design)How it looks: chooses colour and typography, plans visual aestheticMockups, graphics, layouts
Technical artistBridges the gap between visual artwork and front-end code/performanceMixed visual and technical work
🧠
Memory Hook:: UX = eXperience (behaviour and flow) · UI = Interface (visual style). Both are needed, but they are different skills.
⚠️
Common Trap:: Do not treat UX and UI as the same role. A beautiful screen (UI) can still be frustrating to use (bad UX). The lecture shows both: LingsCars is an example of how not to design, while Google Inbox, Medium and Slack are held up as good design. The phrase "It's not you. Bad doors are everywhere" is a reminder that confusing design is the designer's fault, not the user's.
02

Webpage Design Deliverables

Before writing code, designers move through three increasing levels of detail: wireframe, mockup and prototype. Each answers a different question. Wireframe

  • Shows the information that will be displayed.
  • An outline of the structure and layout of components.
  • A blueprint for each page that will be implemented.
  • Deliberately low fidelity — boxes and placement, not visual styling.

Mockup

  • Key information: the visual appearance of the page.
  • Should be more detailed than a wireframe (colours, typography, images).

Prototype

  • Key information: how the page works.
  • Can be low or high fidelity; the focus is on behaviour.
  • Users should be able to use and interact with it.
StagePrimary QuestionFidelity
Wireframe"Where do components go?"Low (structure only)
Mockup"What will it look like?"High (static visual)
Prototype"How does the user interact?"Low or high (interactive)
✅
Exam Tip:: If a question asks which deliverable to build first, the answer is the wireframe — structure always comes before appearance and behaviour.
🧠
Memory Hook:: W-M-P = Wireframe (where), Mockup (what it looks like), Prototype (how it works).
03

Browser Fragmentation

Not all browsers are created equal. Each browser is different, and so is each version of a browser. Each version is also different on each operating system, and you must add different screen resolutions and mobile devices to the picture. The practical consequence: when writing web applications you must consider interoperability between browsers, browser versions and operating systems. Sources of variation to keep in mind:

  • Different browser engines and feature support.
  • Older vs newer versions of the same browser.
  • Different operating systems (Windows, macOS, Linux, iOS, Android).
  • Different screen resolutions and devices, especially mobile.

caniuse.com provides a quick reference on browser compatibility for features and limitations. It is the standard first stop when you need to know whether a CSS or JavaScript feature is safe to use.

💡
Why It Matters:: Browsers implement only subsets of the official specifications. A feature that exists in one browser may be missing or behave differently in another, so "it works on my machine" is never enough.
04

Cross-Browser Compatibility Testing

If your application must run on a certain browser, you must test it on that browser — never assume it will work. Testing approaches:

  1. Local machine — test different browsers by installing them on your own computer.
  2. Virtual machines — test different operating systems by emulating them inside a VM.
  • Note: virtualisation can introduce bugs itself, so results may not perfectly match real hardware.
  1. Professional tools and services — many commercial services test cross-compatibility on real hardware and devices (for example, a Windows Phone device), which is more reliable than emulation.

You Don't Need to Support ALL Browsers

This is a key strategic point:

  • You don't need to (and probably shouldn't) support all browsers, versions and operating systems.
  • At the start of your project, decide what you will and won't support.
  • Base that decision on your intended customer base — know your intended audience.
⚠️
Common Trap:: Trying to support everything is a recipe for endless testing and bug-fixing. Make the support decision deliberately and early, then test only what you promised to support.

Responsive & Inclusive Design

Two design practices shape modern front-end work.

Responsive Design

Responsive design makes a layout adapt to different screen sizes and devices (desktop, tablet, phone). It is implemented in CSS with media queries and flexible layouts so one page works everywhere.

Inclusive Design

Inclusive design is design that does not exclude people on the basis of:

  • Disability
  • Religion
  • Gender identity
  • Race
  • Language
  • Sexual orientation
  • Ethnicity
  • Pronunciation
  • Age

The goal is software that everyone can use, regardless of who they are. Design resources mentioned in the lecture:

  • https://ui-patterns.com/patterns
  • https://hike.one/
  • https://www.uxlibrary.org/explore/ui-design/ui-patterns-and-inspiration
💡
Why It Matters:: Responsive design handles where the page is viewed; inclusive design handles who is viewing it. Good front-end work accounts for both.

Web Components & Their Pillars

A Web Component is a set of custom HTML elements plus the technologies that facilitate their development. Think of it as any reusable blob of HTML, CSS and JavaScript that you can drop into a page like a normal tag. Web components give you four pillars of benefit:

PillarMeaning
ReactivityThe component updates itself automatically when its data or attributes change.
EncapsulationStyles and markup are kept internally, so they don't leak out and clash with the rest of the page.
ModularityA complex piece of UI is packaged as one self-contained unit.
ReusabilityThe same custom element can be used again and again across pages or projects.
🧠
Memory Hook:: R-E-M-R = Reactivity, Encapsulation, Modularity, Reusability. Or remember "REMRe" — a reusable component reacts and hides its internals.
💡
Why It Matters:: Components let teams build a page out of tested, independent building blocks instead of one giant file, which makes large front-ends easier to maintain.

HTML Versions & DOCTYPE

HTML is a constantly evolving specification. The lecture gives a short timeline:

YearMilestone
1997HTML 3.2
1999HTML 4.01
2007HTML5 draft published
2014HTML5 published as a W3C Recommendation

Browsers implement subsets of the HTML specification. HTML5, for example, introduced elements such as <audio> and <video>, and new input types including data, time and color.

The DOCTYPE Declaration

The DOCTYPE is an instruction to the browser about which version of HTML the page uses. Important points:

  • It is not an HTML tag.
  • It must be the very first line in the document.
  • The HTML5 DOCTYPE is simple and short:
Reference
<!DOCTYPE html>
  • This HTML5 declaration will masquerade as HTML4 for older browsers, so it is safe to use.
  • HTML 4 DOCTYPEs are more complex, for example:
Reference
<!DOCTYPE HTML PUBLIC "-//W3C//DTD HTML 4.01//EN" "http://www.w3.org/TR/html4/strict.dtd">
✅
Exam Tip:: If asked why the HTML5 DOCTYPE is so short, the answer is that it is deliberately simple and backwards-compatible — modern browsers treat it as HTML5 while older ones still render the page.
08

HTML Document Structure

A minimal HTML5 document implements CSS and JavaScript alongside markup. The core structural elements are <html>, <head>, <title> and <body>, and content is marked up with elements such as <h1> and <p>. <html> tag

  • Encapsulates the entire HTML document.
  • Can specify the language used in the document (for example lang="en").

<head> tag

  • Contains meta information that is separate from the content.
  • Its elements are not rendered in the view.
  • CSS files are generally imported here.
  • JavaScript imported here delays rendering of the page until the scripts are loaded. JS can instead be imported in the body to speed up page loading.
  • The <title> tag is mandatory in this section.

<body> tag

  • Contains the HTML elements to be rendered to the view.
  • If you place script tags in the body, convention is to place them just before the closing body tag.
  • The body is a mandatory tag for an HTML document.
  • Never skip the end tag.
  • Some elements are empty elements (no closing tag), for example <br>.
💡
Why It Matters:: Where you put your <script> changes page speed. Scripts in the <head> block rendering; scripts at the end of the <body> let the visible page paint first.
⚠️
Common Trap:: Forgetting to close a tag (or closing the wrong element) creates malformed DOM trees. HTML is forgiving, but silent mistakes cause layout bugs that are hard to trace.

HTML Attributes & the DOM

Attributes Best Practices

  • Always use lowercase attributes.
  • Always quote attribute values.
  • Single or double quotes are both acceptable, but be consistent.

Examples from the lecture:

Reference
<a href="https://www.sydney.edu.au/">Visit USYD</a>
<img src="img_girl.jpg">
<p style="color:red;" title="I'm a tooltip">This is a red paragraph.</p>

The Document Object Model (DOM)

The DOM (Document Object Model) treats an HTML document as a tree-like structure of objects. Manipulating this tree from JavaScript forms the majority of JavaScript usage in the browser. Finding elements — common DOM selection methods:

  • By ID: getElementById
  • By tag name: getElementsByTagName
  • By class name: getElementsByClassName

What you can do with the DOM (custom element behaviour):

  • Change HTML content.
  • Update the values of attributes.
  • Produce dynamic HTML content (for example inserting the current Date()).
  • Write directly to the HTML output stream.

Custom Element Lifecycle Callbacks

Custom HTML elements hook into browser DOM events through lifecycle callbacks:

  • connectedCallback() — invoked when the element is attached to the document DOM (logged as 'connected').
  • disconnectedCallback() — invoked when the element is detached/removed from the DOM (logged as 'disconnected').
🧠
Memory Hook:: Think connect = appear, disconnect = disappear. The callback fires exactly when the element enters or leaves the page.
✅
Exam Tip:: A favourite lecture quiz asks what gets logged when an element is added and then removed — the answer is 'connected' then 'disconnected'.

CSS Syntax & Selectors

Cascading Style Sheets (CSS) describes the presentation of an HTML document. It enables a separation of concerns between what's in a document (HTML) and what a document looks like (CSS). Like HTML, CSS has different versions and varying support across browsers. It can be difficult to get right, but it is 100% worth it.

CSS Syntax

The general form of a rule is: CSS Rule Syntax: selector { property: value; }

  • Selector — points to the HTML element the style should apply to.
  • Property — the attribute that should be modified.
  • Value — what the value should be updated to.
  • { } Declaration block — can contain multiple property-value pairs.

The Three Core Selectors

SelectorSyntaxScope
Elementbody { ... }All elements of that HTML tag.
Class.dog { ... }All elements carrying that class; reusable across many elements.
ID#dog-name { ... }One unique element only.
  • A class may be applied to multiple elements, and an element may have multiple classes.
  • An id selects only one element, and an element may have only one id.

Example effects from the lecture:

  • The element selector styles body with a background colour and font.
  • The .dog class gives elements bold, blue font.
  • The #dog-name id underlines the element and turns its font red.
⚠️
Common Trap:: Reusing the same id on several elements is invalid, even if browsers appear to cope. Use a class when you need to style more than one element.
11

Media Queries & CSS Frameworks

Media Queries

Media queries allow us to customise how a document displays on a range of devices by applying conditions to CSS rules. The CSS applies only if the @media query returns true. This is the core mechanism behind responsive pages. For example, a rule inside @media (min-width: 768px) applies only on wider (desktop-scale) screens, while the base rule applies on narrow (mobile) screens.

💡
Why It Matters:: One HTML page plus media queries can serve phones, tablets and desktops, instead of maintaining separate mobile and desktop sites.

CSS Frameworks

The lecture's memorable claim is: "The best CSS is written by someone else." Use a framework. Popular frameworks:

  • Bootstrap
  • Foundation
  • Materialize

Choose carefully — switching between frameworks can be laborious and time-consuming. Criteria when choosing a framework:

  • Aesthetics
  • Grid system
  • Community support
  • Cross-browser compatibility
🧠
Memory Hook:: A-G-C-C = Aesthetics, Grid, Community, Cross-browser compatibility.

JavaScript & TypeScript

JavaScript

JavaScript is a high-level, dynamic, un-typed, interpreted programming language. It allows pages to become dynamic by manipulating the HTML DOM with code. Alongside HTML and CSS it forms a fundamental core of today's modern web, and learning to appreciate it will improve your applications and make you more employable. Historical JavaScript issues (early versions were hard to develop in):

  • Weird equality and automatic type conversion.
  • Confusing behaviour of this.
  • Lack of a type system.
  • Weak static analysis support and poor tooling.
  • Lack of a module system.

JavaScript is constantly evolving and has improved significantly in recent versions. The lecture's verdict: "JavaScript isn't perfect but it's here to stay."

TypeScript

TypeScript is an open-source programming language that implements a superset of JavaScript while adding optional static types.

  • Developed and maintained by Microsoft.
  • Designed for the development of large web applications.
  • It is transpiled back to JavaScript so browsers can run it.
  • Adds support for types, modules/namespaces and classes.

jQuery

jQuery is described as the "Swiss army knife" of the web.

  • Commonly used on web pages.
  • Highly supported with an active community.
  • Likely to have everything you need to interact with the DOM.
  • Great for cross-platform support.

It is becoming less popular because modern frameworks have superseded jQuery's functionality, and browsers now implement native versions of much of the library.

💡
Why It Matters:: TypeScript adds safety for big codebases; jQuery made the DOM easy before browsers caught up. Knowing both explains why today's frameworks look the way they do.

SPAs, AJAX & JS Frameworks

Single Page Applications (SPAs)

A Single Page Application loads a single HTML document and uses JavaScript to update the user's view without a hard refresh. SPAs move a lot of work to the client-side (browser) and typically create a smoother, more fluid user experience, allowing significantly more powerful web applications.

SPA ProsSPA Cons
Provide a faster interfaceTypically require more work
Encourage separation of concernsRequire more experienced developers (complexity)
ReusableNew frontier — frameworks evolve rapidly
Allow for "serverless" browser applicationsPush workload into the browser, bad for low-spec/mobile devices
Simpler binding of data to views—
Easy to serve from a CDN, decreasing load time—
Removes load from backend servers—

AJAX

AJAX stands for Asynchronous JavaScript and XML. It allows a page to be updated with external data without a full refresh, and it is a fundamental aspect of the modern web. The evolution of AJAX tooling:

  • XHR (XMLHttpRequest) — the traditional approach, but clunky and cumbersome.
  • JavaScript libraries like jQuery — improved the situation.
  • Native browser APIs such as Fetch — a modern option where supported.

Popular JavaScript Frameworks

  • Angular (Google)
  • React (Facebook)
  • Ember
  • Backbone.js
⚠️
Common Trap:: Do not confuse AJAX with SPAs. AJAX is the technique for fetching data in the background; an SPA is an architecture that uses such techniques, among others, to avoid full page reloads.

Front-End Tooling & Bundlers

As front-ends grew, a toolchain grew around them to manage dependencies and automate repetitive work. The lecture covers three tools; all are Node.js applications installed via npm.

Bower — Package Manager for the Web

  • Think of it as pip but for frontend HTML, JS and CSS libraries.
  • A Node.js application — installed via npm.
  • Can fetch packages and their dependencies.
  • Much easier to update packages.
  • Document your dependencies in a bower.json file.

Grunt — JavaScript Task Runner

  • Similar to a Makefile but for HTML frontends.
  • Also a Node.js application — installed via npm.
  • Automates boring, repetitive tasks:
    • Minification of images, CSS, JS and HTML.
    • Dependency linking.
    • Linting (error/style checking).
    • Testing.
  • Gulp is another popular JS task runner.

Webpack — Module Bundler

  • A JavaScript module bundler.
  • Generates static assets with only the dependencies needed.

Full toolchain flow:

Reference
Write code  -->  Bower (fetch libraries)  -->  Grunt/Gulp (minify, lint, test)  -->  Webpack (bundle)  -->  Deploy
💡
Why It Matters:: These tools turn many human-readable source files into a small, optimised set of static assets, which is what actually gets served to users. Understanding them explains modern build pipelines.
🧠
Memory Hook:: B-G-W = Bower gets libraries, Grunt runs tasks, Webpack bundles the result.

Worked Scenarios & Calculations

Scenario 1 • Choosing a browser support matrix

Choosing a browser support matrix

A startup is building a booking site for Australian university students.

  1. Identify the intended audience — mostly students on modern phones.
  2. Check real usage data on caniuse.com and analytics to find which browsers that audience actually uses.
  3. Declare support for the current versions of the major mobile browsers and the latest two desktop browsers.
  4. Test only those combinations, using local installs for desktop and a professional device-cloud service for phones. Result: a small, defensible support list instead of an impossible "all browsers" promise.
Scenario 2 • Where to place a script tag

Where to place a script tag

A page feels slow because nothing appears until JavaScript loads.

  • Before: <script> is in the <head>, so the browser downloads and runs it before painting the body — rendering is delayed.
  • After: the script is moved to just before </body>, so the visible content parses and paints first, then the script runs. Lesson: script placement directly affects perceived load time.
Scenario 3 • Styling the same element two ways

Styling the same element two ways

You want a name shown in red and underlined.

  • If only one element ever needs this style, use an ID selector: #dog-name { color: red; text-decoration: underline; }.
  • If many elements should share it, use a class: .dog { color: blue; font-weight: bold; }, then add class="dog" wherever you need it. This shows why classes are reusable while IDs are unique.
Scenario 4 • A component that

A component that announces its lifecycle

A custom element logs its own lifecycle.

  • When the element is added to the page, connectedCallback() runs and logs 'connected'.
  • When the element is removed, disconnectedCallback() runs and logs 'disconnected'. By the end of the sequence both messages appear, in that order.
Scenario 5 • From source files

From source files to a shipped bundle

A team finishes editing separate HTML, CSS and JS files.

  1. Bower fetches the framework and library dependencies listed in bower.json.
  2. Grunt (or Gulp) minifies images, CSS, JS and HTML, links dependencies, lints the code and runs tests.
  3. Webpack bundles everything into static assets containing only the dependencies actually needed.
  4. The small bundle is served to users, load time drops, and the backend is freed from extra work when a CDN serves it.

What is the DOCTYPE and what are its rules?
Answer:
It is an instruction to the browser about the HTML version, not an HTML tag, and it must be the very first line. <!DOCTYPE html> is the HTML5 form and safely masquerades as HTML4 for older browsers.
Q7
Why does script placement affect page load?
Answer:
JavaScript in the <head> delays rendering until scripts load; placing scripts at the end of the body lets the page render sooner.
Q8
What is the DOM and why is it important?
Answer:
The Document Object Model is a tree-like structure of objects representing the HTML document; manipulating it with JavaScript is the majority of browser-side JavaScript usage.
Q9
Name three ways to find elements in the DOM.
Answer:
getElementById (by id), getElementsByTagName (by tag) and getElementsByClassName (by class).
Q10
What is the difference between a class selector and an ID selector?
Answer:
A class can be applied to many elements and an element can have multiple classes; an ID selects exactly one element and an element may have only one ID.
Q11
How do media queries enable responsive design?
Answer:
They apply CSS conditions based on device/viewport characteristics, so a single page adapts its layout across screen sizes; the rules apply only when the @media query returns true.
Q12
What is TypeScript and how does it relate to JavaScript?
Answer:
TypeScript is Microsoft's open-source superset of JavaScript that adds optional static types, modules/namespaces and classes; it is transpiled back to JavaScript for browsers, and is aimed at large web applications.
Q13
What are the trade-offs of Single Page Applications?
Answer:
Pros include a fast, fluid interface, separation of concerns, reusability, simpler data binding, CDN-friendly serving and less backend load; cons include more work, more experienced developers, rapidly evolving frameworks and heavy client-side workload that hurts low-spec or mobile devices.
Q14
What is AJAX and how has its implementation evolved?
Answer:
AJAX (Asynchronous JavaScript and XML) updates a page with external data without a full refresh; it evolved from clunky XHR, to jQuery's simplified wrappers, to modern native APIs such as Fetch.
Q15
What does each front-end build tool do?
Answer:
Bower manages front-end packages and records them in bower.json; Grunt (or Gulp) is a task runner automating minification, dependency linking, linting and testing; Webpack is a module bundler that produces static assets with only the needed dependencies.
