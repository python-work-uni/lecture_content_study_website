Identify Network Landscape
When you connect to a network, usually your computer is configured 
with the Dynamic Host Configuration Protocol (DHCP).
This provides your computer with:
– IP Address: Identifies your computer on the local network.
– Subnet Mask: Defines what “local” means with regards to your IP 
address.
– Default Gateway: A host that can route packets to non-local IP 
addresses.
– Nameservers: A host which can be used to resolves domain names. 
A DNS server.
First thing to check if you cannot reach any web sites

Resolve IP to DNS
We can’t establish a connection with ‘cusp.sydney.edu.au’. Instead, we 
need an IP address.
The operating system can resolve a domain name to an IP address for 
us. The resolution process is roughly:
 
1.Check OS local DNS entries (e.g. /etc/hosts/ )
 
2.Identify nameservers (a.k.a DNS server)
– Usually provided by DHCP
– Specified in /etc/resolv.conf
 
3.Submit a UDP request to a nameserver on port 53.
 
4.Name servers keep recursively asking their parent name server 
until one knows the IP.
 
5.The IP is returned according to a matching A-record for the 
domain.
– Check out DNS record types for more information.

Recap - Establish TCP Connection 
Once we have an IP address, we must open a TCP connection.
The Transmission Control Protocol (TCP) lives on layer 4 of the OSI Model. It 
is not responsible for addressing or segregation like the layers below it, but is 
instead responsible for delivery of packets.
TCP guarantees in-order delivery of data for the application layers above it.
TCP Segments are assigned to particular ‘ports’, which define what application 
they are intended for.
Depending on which protocol we use, a standard TCP port is chosen by 
default:
–
HTTP: Port 80
–
HTTPS: Port 443
(Web servers can run on non-standard ports, these are just conventions)

--- Slide 16 ---
The University of Sydney
Page 16
Recap - Aside: User Datagram Packet
The User Datagram Protocol (UDP) also lives on layer 4 with TCP, 
however it does not guarantee delivery at all.
UDP is a ‘best effort’ protocol, which sends ‘datagrams’ instead of 
TCP’s ‘segments’.
With UDP, packet deliveries are not acknowledged, and packets are not 
re-transmitted (unless performed explicitly at the application layer).
UDP also operates on a particular “port”, though a TCP and UDP 
port are considered different.
DNS operates on UDP port 53 and it does not use TCP.

HTTP Structure
– A HTTP request or responses consists of:
– Header: Contain meta-data such as cookie and connection information.
– Body: Contains the data to be sent with the transmission (optional).
– There are several types of web requests:
– GET: A simple request header only 
– POST: A request containing data in the body, e.g. form data, file 
upload, etc.
– HEAD: The same as GET, except server omits the body in the response 
(only sends header)
– PUT: Replace a target resource on the server 
– DELETE: Delete a target resource on the server
– OPTIONS: Ask the server which request types are allowed against a 
particular resource

Internet-facing web servers
– An internet-facing web server can directly receive HTTP requests 
from clients. Usually, the first recipient of the HTTP request is not 
the service that provides the response.
– Instead, it is often:
– A load balancer (LB) routes requests to appropriate servers for processing.
• Load balancers allow a ‘pool’ of servers to handle incoming requests 
by forwarding a request to an available resource.
– DDoS mitigation services (e.g. web application firewall) often serve as the 
first-layer for handling requests on large websites.
     Their purpose is to simply ensure that incoming requests aren’t part of a 
cyber attack.
• Legitimate packets are forwarded (often to the regular LB)
• Attack packets are dropped
– E.g. CloudFlare
– Content Delivery Network (CDN)
– Secured HTTP = HTTPS by using TLS protocols (SSL is obsolete)

Slave/Master Databases
When handling lots of web requests, we must read and write to 
the database frequently.
To spread the load on the database, we separate read and 
write operations to slave and master DBs respectively:
Master/Primary: The master database accepts reads and write 
operations. Since it is difficult to have multiple write locations, there is 
usually only one master database.
Slaves/Replicas: Any updates to the master database are quickly 
replicated to all slave databases.
– Slaves can be used for read operations only.
– Since data is not modified on slaves, there can be many replicated 
slaves, improving parallelizability of DB reads.

--- Slide 26 ---
The University of Sydney
Page 26
Slave Drift
– Any changes applied to the master DB will also be replicated to the 
slave database. 
– However, this does not occur instantaneously and there is a small, but 
significant, time delay between a write to the master DB and the 
propagation of the change to all slave DBs.
– This is called slave-drift or replication delay and must be managed 
appropriately by your application.
– DB reads that lead to important decisions, such as payments, should 
usually be made against the master to prevent race conditions or 
side-effects by reading potentially stale data.
– There are replication configurations that avoid this problem but 
come with other trade-offs, such as delayed writes and/or reduced 
fault tolerance.

Client Rendering
The HTTP status codes instruct the client on how to handle the response.

the browser to immediately follow the URL specified in the Location field in 
the response header.
A 200 (OK) response is usually accompanied by a resource in the response 
body, which is rendered by the browser.

Parse HTML into DOM
– If a HTTP response contains HTML, the browser parses this HTML 
to build something called the Document Object Model (DOM).
– The DOM forms the browser’s internal representation of the web 
page.
– The relationships between various HTML elements (such as <div> 
or <img>) tags are defined and can be manipulated via the DOM.
– It is common for JavaScript libraries, such as jQuery, to manipulate 
the DOM so as to modify the layout of web pages.
– Browser plugins often interact with browsers at this level

DOM Resources
While the Hyper Text Markup Language (HTML) specifies how components 
of the web page are structured, there are usually many other resources that 
define how the page behaves.
For example:
–
CSS: Cascading Style Sheets (CSS) are used to specify positional and 
appearance attributes of DOM elements. CSS can be specified inside 
HTML <style> tags, or in external files that are included by means of 
<link> HTML tags in the <head> section.
 
 
<link rel="stylesheet" href="/styles/cusp_style.css" type="text/css" />
–
JS: JavaScript (JS) can be used in the browser to perform arbitrary 
computation, often including live manipulation of DOM elements. JS can 
be specified inside HTML <script> tags directly, or included from an 
external file using the „src‟ attribute.
 
<script type="text/javascript" src="/scripts/util/Util.js"> </script>

Step Two: Determine Use Cases
Attempts to convert your problem statements into use cases. Use 
cases are made up of actions which are performed by actors.
Action: A simple, distinct, and easily defined action that can be 
performed by an actor.
Actor: A role within the system, not an individual.
1.Identify flow of events
2.Extract distinct actions
3.Group associated actions into a high-level use case
4.Expand use cases into extensions

Use Case Documentation – Flow of Events
Create a big table that lists the use cases (see Monopoly example on Canvas).
Describe each use case using fields such as:
Name: Give the use case a short name.
Goal: The main goal that the use case is trying to achieve.
Actors: Actors which initiate a use case and/or are involved in a use case.
Preconditions: A list of conditions that must be met before the use case can 
start.
Main flow: A full description of the use case.
Subflows: A list of actions or use cases on which the use case depends.
Alternative Flows: Any alternative action flows, e.g. ones that might come 
from error scenarios.
Priority: An indication of how important the use case is to the functioning of 
the system, or the MVP.

Software Requirements Specification
– A Software Requirements Specification (SRS) document 
details exactly what the system does and does not do.
– In essence, the SRS is a communication tool between project 
stakeholders and software designers.
– It is a very important document that allows you to say the 
project is ‘finished’, and mitigates scope creep. This forms the 
primary specification document and should capture all 
information regarding the project.
– Any diagrams should not introduce new information that is not 
contained within the SRS. Diagrams should provide additional 
context/clarification only.
