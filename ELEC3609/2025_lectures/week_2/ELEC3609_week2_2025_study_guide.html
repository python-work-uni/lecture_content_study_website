Web Fundamentals and Project Management: From URL to SRS

This week traces the complete journey of a web request — from the moment a user types a URL, through DNS, TCP and HTTP, into load balancers, application servers and databases, and back to the browser as a rendered page. It then shifts to the human side of building software: requirements analysis and design using use cases, sequence/state diagrams, wireframes, the Software Requirements Specification, and task-management tools.

Read this first: Every website you use is the same two-part story. On the technical side, a URL becomes an IP address (DNS), then a reliable connection (TCP), then a structured message (HTTP) that a fleet of servers answers. On the human side, none of that gets built correctly until someone writes down what the system must do (use cases and an SRS) and who is doing which task (task management). Master both halves and you can explain, design and deliver an internet software platform end to end.
~20 min read14 teaching sections14 practice questions24 key terms

By the end you will be able to

  • Trace every step that happens between entering a URL and seeing a rendered page, naming which actor (browser, OS, DNS, load balancer, app server, database) performs each step.
  • Break a URL into its scheme, subdomain, domain, gTLD, ccTLD and path, and explain what each part means.
  • Explain how DHCP, caching and recursive DNS resolution work, including the role of the A-record and UDP port 53.
  • Compare TCP and UDP across delivery guarantees, handshaking, ports and example protocols.
  • Describe the structure of an HTTP request/response and distinguish GET, POST, HEAD, PUT, DELETE and OPTIONS.
  • Explain three-tier server architecture (load balancer, app server, database) and why master/slave replication creates slave drift.
  • Interpret HTTP status-code classes and describe how the browser parses HTML into the DOM and renders it.
  • Convert problem statements into use cases, document them, and structure a Software Requirements Specification.
  • Choose appropriate project-management and task-management tools for a collaborative software project.

The End-to-End Journey of a Web Request

One URL entry sets off a precise, layered pipeline that converts a human-readable address into pixels on screen — and every stage has a clear owner.

When Bob types a URL into the browser, a well-defined sequence unfolds across two halves: the client asks for something, the server produces it, and the client turns the answer into a page.

Client side — making the request

  1. Browser: parse the URL into its components (scheme, domain, path).
  2. Browser: check the cache for a stored copy of the resource.
  3. OS: identify the network you are connected to.
  4. OS: resolve the domain using DNS to get an IP address.
  5. OS: establish a TCP connection to the web server.
  6. Browser: submit the HTTP request over that connection.

Server side — producing the response

  1. Load balancer (LB) accepts the TCP connection and receives the HTTP request.
  2. LB software parses the HTTP header, then routes and forwards the request to an application (app) server.
  3. App server executes the back-end website logic, probably connecting to one or more databases.
  4. App server renders a response and returns it via the TCP connection.

Client side — handling the response

  1. Browser: parse the response (headers and body).
  2. Browser: fetch additional resources — assets such as CSS, JavaScript and images; establish web-socket connections; load browser plugins.
  3. Browser: render the page to the graphical content you see.
Parse URL→Check cache→Resolve DNS→Open TCP→Send HTTP request→LB routes→App server logic→DB access→HTTP response→Fetch assets→Render page
💡
Why it matters: Almost every later topic is just one box in this diagram expanded. If you can narrate this pipeline from memory, you can place any new concept (TLS, CDNs, caching, load balancing) in the right spot.
🤔

Parsing a URL

A URL is a structured address, and each segment tells a different layer of the system where to go and what to fetch.

A URL follows the general shape protocol://domain.tld/path/file.ext. Take the concrete example:

https://cusp.sydney.edu.au/students/view-unit-page/uos_id/101257

Reading it left to right:

subdomaincuspthe specific service within the domain
domainsydneythe registered organisation name
gTLDedugeneric top-level domain

Another example is https://www.sydney.edu.au/units/ELEC3609, where the path /units/ELEC3609 points at a specific unit page.

Cache, DHCP and DNS Resolution

Before any connection is opened, the browser checks what it already has, the OS learns how to reach the network, and DNS translates a name into an IP.

Browser cache

There are many caching layers on the internet; one is the browser cache. It stores copies of assets so they do not need re-downloading:

  • JavaScript files
  • CSS files
  • Images
  • Fonts

Identifying the network landscape

When you connect to a network, your computer is usually configured by the Dynamic Host Configuration Protocol (DHCP), which supplies four things:

Provided by DHCPPurpose
IP AddressIdentifies your computer on the local network
Subnet MaskDefines what "local" means relative to your IP
Default GatewayA host that routes packets to non-local IP addresses
NameserversA host (DNS server) used to resolve domain names
✅
Exam tip: The first thing to check if you cannot reach any website is your DHCP-supplied network configuration (IP, gateway, nameservers).

Resolving a domain name to an IP (DNS)

We cannot connect to cusp.sydney.edu.au directly — we need an IP address. The OS resolves it roughly like this:

  1. Check OS local DNS entries (e.g. /etc/hosts).
  2. Identify nameservers (a.k.a. DNS server) — usually provided by DHCP and specified in /etc/resolv.conf.
  3. Submit a UDP request to a nameserver on port 53.
  4. Nameservers keep recursively asking their parent name server until one knows the IP.
  5. The IP is returned according to a matching A-record for the domain.
⚠️
Common trap: DNS itself uses UDP (port 53), not TCP. It is the one connection step that does not need TCP's reliability guarantees.

The OSI Model and TCP vs UDP

Networks are built in layers, and the two transport protocols at layer 4 trade reliability against speed in fundamentally different ways.

The OSI model

The OSI model is a way to conceptualise network systems in which each layer is an abstraction from the layer below it. A few reference points:

  • Layer 1: physical media — copper line, COAX, fibre, etc.
  • Layer 2: data link — IEEE 802.11a/b/g/n (Wi-Fi).
  • Layer 4: transport — TCP/UDP.
  • Layer 7: application — HTTPS.

TCP vs UDP

Both live on layer 4 (the network/transport layer) but behave very differently:

AspectTCPUDP
GuaranteeIn-order delivery for layers above"Best effort" — no guarantee at all
Unit of dataSegmentsDatagrams
HandshakeYesNo handshake enforced
Acknowledgement / retransmissionBuilt inNone (unless done explicitly at the application layer)
PortsNeeded, e.g. SSH on TCP/22Needed, e.g. DNS on UDP/53
Notable attackTCP flooding—
💡
Why it matters: Choosing TCP or UDP is a design decision. If losing a packet silently would break your application, use TCP; if you value low latency and can tolerate loss (or handle it yourself), UDP is the fit.
🧠
Memory hook: TCP = Trustworthy, Connected, Port-ordered. UDP = Unreliable, Datagram, Prompt.
🤔
Pause & predict: DNS needs an answer quickly and can simply retry, while a file download must arrive intact. Which protocol suits each?

Establishing TCP Connections and Ports

Once an IP address is known, a TCP connection is opened — and ports decide which application on that host the traffic belongs to.

The Transmission Control Protocol (TCP) lives on layer 4 of the OSI model. It is not responsible for addressing or segregation like the layers below it; it is responsible for delivery of packets. Specifically, TCP guarantees in-order delivery of data for the application layers above it.

TCP segments are assigned to particular ports, which define what application they are intended for. Depending on the protocol, a standard port is chosen by default:

ProtocolDefault port
HTTP80
HTTPS443

Web servers can run on non-standard ports — these are just conventions.

UDP in contrast

The User Datagram Protocol (UDP) also lives on layer 4, alongside TCP, but it does not guarantee delivery at all:

  • It is a "best effort" protocol that sends datagrams instead of TCP's segments.
  • Packet deliveries are not acknowledged and packets are not re-transmitted (unless performed explicitly at the application layer).
  • UDP also operates on a port, but a TCP port and a UDP port are considered different.
  • DNS operates on UDP port 53 and does not use TCP.
ℹ️
Note: "In-order delivery" means if you send segments 1, 2, 3, the receiving application sees them as 1, 2, 3 — even if the network delivered 2 before 1. TCP reorders and retransmits to hide that.

HTTP Structure and Request Methods

HTTP is a simple, text-based message format: metadata in a header, optional data in a body, and a verb that says what to do.

Both an HTTP request and an HTTP response consist of two parts:

  • Header: contains meta-data such as cookie and connection information.
  • Body: contains the data to be sent with the transmission (optional).

Request methods

There are several types of web request:

MethodWhat it does
GETA simple request, header only
POSTA request containing data in the body (e.g. form data, file upload)
HEADSame as GET, except the server omits the body in the response (only sends the header)
PUTReplace a target resource on the server
DELETEDelete a target resource on the server
OPTIONSAsk the server which request types are allowed against a particular resource

With an open TCP connection to the web server, the browser just needs to send it an HTTP request through that connection.

🧠
Memory hook: The safe, read-only method is GET; anything that changes server state (POST/PUT/DELETE) deserves extra care because it is not idempotent in the same way.
🤔
Pause & predict: A browser wants to check whether a cached file is still current without downloading it again. Which method should it use, and what will the response body contain?

Server-Side Architecture: Load Balancers, App Servers and Frameworks

The first machine to receive a request is rarely the one that answers it — traffic is filtered, balanced, then processed by application code.

Typical three-layer architecture

Using AWS IaaS services as the example, a typical architecture has three layers, with end-to-end encryption in transit:

  • Elastic Load Balancing (ELB) — the load balancer.
  • Elastic Cloud Compute (EC2) — the web/app servers.
  • Relational Database Services (RDS) — the database layer.

The load balancer provides:

  • Load balancing — route traffic based on performance and health status.
  • Content-based routing — route traffic based on contents.
  • SSL offloading — terminate HTTPS at the LB.
  • Port forwarding — e.g. HTTP to HTTPS.

Internet-facing web servers

An internet-facing web server can directly receive HTTP requests from clients. Usually the first recipient is not the service that provides the response. Instead it is often:

  • A load balancer (LB) that routes requests to appropriate servers. LBs let a "pool" of servers handle incoming requests by forwarding each request to an available resource.
  • DDoS mitigation services (e.g. a web application firewall) that act as the first layer on large websites, ensuring incoming requests are not part of a cyber attack. Legitimate packets are forwarded (often to the regular LB); attack packets are dropped. Example: CloudFlare.
  • Content Delivery Network (CDN) — caches content close to users.
  • HTTPS, secured using TLS protocols (SSL is obsolete).

Application servers

App servers do the actual processing of HTTP requests. They contain:

  • Back-end website code
  • Business logic
  • Database interface methods
  • Caching layers

Typical forms:

  • Virtual machines (IaaS): EC2, GCE
  • Containers: docker
  • Serverless: Lambda, Google Cloud Function

This is where the majority of the work lies in a typical web architecture.

Web frameworks

Since there are many standard web-server functions, developers work within a web framework rather than re-inventing the wheel. A few language/framework pairings (and notable companies using the language):

LanguageFrameworksCompany example
PythonFlask, DjangoInstagram
PHPCodeigniter, CakePHPFacebook

✅
Exam tip: If asked "which layer does most of the work?", the answer is the application server — it holds the business logic, the framework and the database interfaces.

Databases: SQL, NoSQL and Master/Slave Replication

Persistent data lives in databases, and scaling reads is done by copying a single master to many read-only slaves — at the cost of a small replication delay.

App servers typically read information from databases. There are many types, split into two main families:

FamilyNatureExamples
SQL (relational)Maintain and enforce relationships between dataMySQL, PostgreSQL, SQLite, Microsoft SQL Server
NoSQL (non-relational)Store data more like loose pages, often with no schemasMongoDB, Redis, DynamoDB, Cloud Data Store

Databases can reside on the same host as the app server, or separately (recommended).

Master/slave (primary/replica) databases

When handling lots of web requests we read and write to the database frequently. To spread the load, read and write operations are separated:

  • Master/Primary: accepts both read and write operations. Since it is difficult to have multiple write locations, there is usually only one master.
  • Slaves/Replicas: any updates to the master are quickly replicated to all slaves. Slaves can be used for read operations only. Because data is not modified on slaves, there can be many replicated slaves, improving parallelisability of DB reads.

Slave drift (replication delay)

Changes applied to the master are replicated to slaves, but not instantaneously — there is a small yet significant time delay between a write to the master and its propagation to all slaves. This is called slave drift or replication delay, and it must be managed by your application.

  • DB reads that lead to important decisions, such as payments, should usually be made against the master to prevent race conditions or side-effects from reading stale data.
  • There are replication configurations that avoid this problem, but they come with trade-offs such as delayed writes and/or reduced fault tolerance.
⚠️
Common trap: Reading from a slave immediately after writing to the master can return stale data. Never route correctness-critical reads through a replica.
🤔
Pause & predict: A user updates their password, then immediately logs in again. Should the login check read from the master or a slave? Why?

Generating and Returning HTTP Responses

After the business logic runs, the app server fills a template with data and packages the result as a header plus a body.

Once the application server has performed all the business logic to decide how it will respond, it must generate the response. Typically this involves insertion of data into a template, which forms the HTTP response.

  • Variables in the application code are inserted between {{ and }}.
  • Code can also be specified between {% and %}.
<h1>Welcome, {{ username }}</h1>
{% if is_admin %}<a href="/admin">Admin</a>{% endif %}

Just like a request, an HTTP response contains two sections:

  • Header: meta-data such as the HTTP status code, content type and length.
  • Body: typically the HTML, or contents of a requested resource (optional).
ℹ️
Note: {{ ... }} is for values (data), {% ... %} is for logic (loops, conditionals). This templating pattern is common across web frameworks.

Parsing the Response: Status Codes, the DOM and Rendering

The status code tells the browser what to do next, and the HTML is turned into a manipulable object tree that the rendering engine paints to screen.

HTTP status codes

The response can specify a status code indicating the outcome:

Code classCategoryExamples
1xxInformational100: Continue; 101: Switching Protocols
2xxSuccess200: OK — the standard response
3xxRedirection301: Moved Permanently; 302: Found/Moved Temporarily (similar to 303 & 307); 304: Not Modified
4xxClient error404: Not found
5xxServer error502: Bad gateway

Status codes instruct the client on how to handle the response:

  • A 302 causes the browser to immediately follow the URL specified in the Location field of the response header.
  • A 200 (OK) is usually accompanied by a resource in the response body, which the browser renders.

Parsing HTML into the DOM

If the response contains HTML, the browser parses it to build the Document Object Model (DOM) — the browser's internal representation of the web page. The relationships between HTML elements (such as <div> or <img>) are defined and can be manipulated through the DOM. It is common for JavaScript libraries such as jQuery to manipulate the DOM to modify page layout, and browser plugins often interact at this level.

DOM resources

HTML specifies structure, but other resources define behaviour:

  • CSS: Cascading Style Sheets specify positional and appearance attributes of DOM elements. They can be inside <style> tags or in external files linked from the <head>:
<link rel="stylesheet" href="/styles/cusp_style.css" type="text/css" />
  • JS: JavaScript performs arbitrary computation in the browser, often including live manipulation of DOM elements. It can be inline in <script> tags or included via the src attribute:
<script type="text/javascript" src="/scripts/util/Util.js"> </script>

The browser must perform many subsequent HTTP (or other) requests to collect these resources — which may live on the same server or on different servers.

Browser plugins and rendering engines

Plugins can interfere with and/or modify the response — for example, AdBlock prevents ads from showing.

The rendering engine (web browser engine) actually renders the page into the graphical content you see; it is responsible for the look and feel of a browser. It decides things like how check-boxes appear. Examples:

EngineBrowser
BlinkGoogle Chrome
EdgeHTMLMicrosoft Edge
WebKitApple Safari
GeckoMozilla Firefox
🧠
Memory hook: 2xx = good, 3xx = go elsewhere, 4xx = you messed up, 5xx = the server messed up.
🤔

Project Management Tools and Use Cases

Good software starts by writing down the problem, then converting that problem into use cases built from actors and actions.

Tools of the trade

Written tools should enable collaboration and produce professional-looking documents:

  • Google Docs — easy collaboration, supports versioning.
  • Latex — looks professional (with the right template), easy to use with version-control systems (e.g. git), great for formatting and consistency.
  • Microsoft Word — feature rich, but difficult to manage version control and difficult to collaborate.

Graphical tools should make sensible, accurate diagrams easy:

  • LucidChart — multiple editors, integrates with Google Docs.
  • Adobe Illustrator — super flexible, but not as easy for a beginner.
  • Balsamiq — wireframing only.
  • Diagrams.net (previously Draw.io) and Microsoft Visio.

Management tools manage workflow and development processes:

  • GitHub, Jira (integrates well with software development life cycles), Phabricator, Asana (lightweight web-based tool), Microsoft Project (traditionally used by big projects and organisations).

Step one: identify problems

Ask what core issues you are trying to solve. Identify reasons someone would want to use your website, and what problem it solves. Create a series of problem statements, e.g.:

  • "Buyers have no way of expressing how much they want to pay for an item."
  • "Sellers have difficulty determining the price to sell at."
  • "Non-technical people have no way of getting a website built."

Step two: determine use cases

Convert problem statements into use cases, which are made up of actions performed by actors:

  • Action: a simple, distinct, easily defined action that can be performed by an actor.
  • Actor: a role within the system — not an individual.

The process:

  1. Identify the flow of events.
  2. Extract distinct actions.
  3. Group associated actions into a high-level use case.
  4. Expand use cases into extensions.

Use case models are drawn using UML (Unified Modelling Language) — for example, a use case diagram of a restaurant business.

💡
Why it matters: An actor is a role, not a person. "Customer" is an actor; "Bob" is not. Getting this right keeps your use case model reusable and testable.
🤔
Pause & predict: For a marketplace site, is "log in" a high-level use case or an action? How would you decide?

Documenting Requirements: Use Case Fields, Diagrams and the SRS

Requirements are captured in a standard set of fields, illustrated with diagrams, and bound together in the SRS — the document that defines when the project is finished.

Use case documentation — flow of events

Create a big table listing the use cases, and describe each using these fields:

  • Name: a short name for the use case.
  • Goal: the main goal the use case is trying to achieve.
  • Actors: actors who initiate and/or are involved in the use case.
  • Preconditions: conditions that must be met before the use case can start.
  • Main flow: a full description of the use case.
  • Subflows: actions or use cases the use case depends on.
  • Alternative Flows: other action flows, e.g. from error scenarios.
  • Priority: how important the use case is to the system's functioning, or the MVP.

Sequence diagrams

Sequence diagrams describe how objects interact with each other and in what order. They are very useful for communicating how several systems interact, or for detailing how actors interact with components in a multi-step process.

State diagrams

State diagrams (a.k.a. state machine diagrams) describe the various states of system components. They are essential for communicating how abstract concepts such as tickets or user accounts progress through the system. Both the states themselves and the state transitions (which constrain how objects may move between states) are defined.

Wireframes

Wireframing lets designers gain a visual "feel" for the site without focusing on graphical detail. The idea is a "cartoon" version of the website that enables a preliminary experience. Wireframes are usually just a series of images, but can sometimes include clicking and linkage between images in the form of a storyboard.

Software Requirements Specification (SRS)

An SRS details exactly what the system does and does not do. In essence it is a communication tool between project stakeholders and software designers. It is very important because it lets you declare the project "finished" and mitigates scope creep. It is the primary specification document and should capture all project information. Diagrams should not introduce new information not contained in the SRS — they only add context and clarification.

The SRS has three main parts:

1. Introduction — enough for a business executive to understand the project, including all important considerations, without too much depth:

  • Purpose
  • Definitions
  • System Overview
  • References

2. Overall Description — discusses the project at a high level but still examines how it is used, how it works, scope, dependencies/requirements and constraints:

  • Product Perspective, System Interfaces, User Interfaces
  • Hardware/software/communication interfaces, Memory constraints
  • Design Constraints, Operations, Site adaption requirements
  • Product functionality, User characteristics
  • Constraints, assumptions and dependencies

3. Specific Requirements — the nitty-gritty, highly granular requirements where it should be easy to tell whether the system satisfies them:

  • External interface requirements
  • Functional requirements
  • Performance requirements
  • Logical database requirements
  • Software system attributes: Reliability, Availability, Security, Maintainability, Portability
⚠️
Common trap: Adding new facts only inside a diagram (e.g. a new field on a sequence diagram) breaks the rule that the SRS is the single source of truth. Put the information in the text, then illustrate it.
🤔
Pause & predict: A stakeholder asks to add a feature late in the project. Which SRS property protects the team's scope, and which field of a use case would you update first?

Task Management Software

A website is built from many tasks, so teams use dedicated software to track who does what without stepping on each other's toes.

Building a website is hard, with lots and lots of tasks to complete. Task-management software answers the question: how do we make sure everyone knows what they are doing, and that we are not stepping on each other's toes?

GitHub (used in this course)

The course primarily uses GitHub as its task-management software. Features:

  • Most popular source control (software configuration management) tool.
  • Integrated with task management — tickets / issues / defects.
  • Code review / scan; security & compliance.
  • Platform deployment.

Phabricator

Some companies use Phabricator to manage most of their engineering workflow. The most-used components are:

  • Maniphest: ticketing and task management.
  • Diffusion: repository hosting.
  • Differential: reviewing code.

JIRA

  • Bug/issue tracking and tasks.
  • Service tickets and timesheets.
  • Extendible through a marketplace/ecosystem.

Asana

  • Tasks visualised and categorised as tiles.
  • Similar tool: Trello.

Microsoft Project

  • Gantt chart views.
  • Integration with Microsoft Office.
  • Similar tool: SmartSheets.
🧠
Memory hook: Phabricator's three D/M names map to duties — Maniphest = manage tasks, Diffusion = host code, Differential = review code.

Key Takeaways

If you remember nothing else, remember this.

1

Entering a URL triggers a fixed pipeline: parse URL → check cache → identify network → resolve DNS → open TCP → send HTTP request → LB routes → app server logic → database → response → fetch assets → render.

2

A URL decomposes into protocol (scheme), subdomain, domain, gTLD, ccTLD and path; each identifies a different part of the target.

3

DHCP configures a host with its IP address, subnet mask, default gateway and nameservers; checking it is the first step when no site loads.

4

DNS resolves a name to an IP by checking local entries, finding nameservers from DHCP/resolv.conf, querying UDP port 53, and recursing to parents until an A-record is returned.

5

The OSI model stacks abstractions (layer 1 physical, layer 2 data link, layer 4 transport, layer 7 application); TCP and UDP both sit at layer 4.

6

TCP guarantees in-order delivery, uses segments and handshakes, and defaults to ports 80 (HTTP) and 443 (HTTPS); UDP is best-effort, uses datagrams, and carries DNS on port 53.

7

HTTP messages have a header (metadata) and optional body; GET, POST, HEAD, PUT, DELETE and OPTIONS express the intended operation.

8

Real architectures front app servers with load balancers, DDoS mitigation and CDNs, and secure traffic with TLS (SSL is obsolete).

9

App servers hold the business logic and frameworks; databases come as SQL (relational) or NoSQL, with a single master handling writes and many read-only slaves handling reads.

10

Master/slave replication introduces slave drift, so correctness-critical reads (e.g. payments) must go to the master.

11

HTTP status classes are 1xx informational, 2xx success, 3xx redirection, 4xx client error and 5xx server error; the browser parses HTML into the DOM and a rendering engine paints it.

12

Requirements work moves from problem statements to use cases (actors and actions), documented in standard fields, illustrated with sequence/state/wireframe diagrams, and bound in an SRS that defines scope and mitigates scope creep.

13

Task-management tools (GitHub, Phabricator, JIRA, Asana, Microsoft Project) keep a multi-person project coordinated.

Glossary

Every term you need to speak this week's language.

URL
A structured address identifying a resource on the web, made of a protocol, domain and path.
DNS
The Domain Name System translates human-readable domain names into IP addresses via recursive lookups and A-records.
DHCP
Dynamic Host Configuration Protocol; assigns a host its IP address, subnet mask, default gateway and nameservers.
TCP
Transmission Control Protocol at OSI layer 4; guarantees in-order delivery, uses segments, handshakes and ports.
UDP
User Datagram Protocol at OSI layer 4; a best-effort protocol sending datagrams with no acknowledgement or retransmission.
Port
A number identifying which application a TCP/UDP segment or datagram is intended for (e.g. HTTP 80, HTTPS 443, DNS 53).
HTTP
Hyper Text Transfer Protocol; the request/response protocol consisting of a header and an optional body.
GET
An HTTP method that is a simple, header-only request for a resource.
POST
An HTTP method carrying data in the body, such as form data or a file upload.
Load balancer
A service that receives requests and forwards them to an available server in a pool, routing by health, performance or content.
DOM
Document Object Model; the browser's internal tree representation of an HTML page, manipulable by JavaScript.
CSS
Cascading Style Sheets; specify positional and appearance attributes of DOM elements.
JavaScript
A language that performs arbitrary computation in the browser, often manipulating the DOM live.
SQL
Relational database family that maintains and enforces relationships between data (MySQL, PostgreSQL, SQLite, SQL Server).
NoSQL
Non-relational database family storing data like loose pages, often schema-less (MongoDB, Redis, DynamoDB).
Master database
The single primary database that accepts both reads and writes.
Slave/replica database
A read-only copy of the master, many of which can exist to parallelise reads.
Slave drift
The replication delay between a write to the master and its propagation to slaves.
Use case

Q1

List, in order, the six client-side steps the browser and OS perform before the HTTP request is sent to the server.

Answer: 1. Browser parses the URL. 2. Browser checks the cache. 3. OS identifies the network. 4. OS resolves the domain using DNS. 5. OS establishes a TCP connection to the web server. 6. Browser submits the HTTP request to the web server.
Q2

For the URL https://cusp.sydney.edu.au/students/view-unit-page/uos_id/101257, identify the protocol, subdomain, domain, gTLD, ccTLD and path.

Answer: Protocol: https (HTTPS). Subdomain: cusp. Domain: sydney. gTLD: edu. ccTLD: au. Path: /students/view-unit-page/uos_id/101257.
Q3

What four things does DHCP provide, and why is checking it the first diagnostic step when no websites load?

Answer: IP address (identifies the computer on the local network), subnet mask (defines what "local" means), default gateway (routes packets to non-local IPs) and nameservers (DNS servers for name resolution). If any of these are wrong, no name can be resolved or routed, so no site will load — making it the first thing to check.
Q4

Describe the DNS resolution process and state which protocol and port the query uses.

Answer: The OS (1) checks local DNS entries such as /etc/hosts, (2) identifies nameservers usually supplied by DHCP and listed in /etc/resolv.conf, (3) submits a UDP request to a nameserver on port 53, (4) the nameservers recursively ask their parent servers until one knows the IP, and (5) the IP is returned via a matching A-record. The query uses UDP port 53.
Q5

Compare TCP and UDP on delivery guarantee, data unit, handshake, and give one example protocol/port for each.

Answer: TCP guarantees in-order delivery, sends segments, enforces a handshake, and e.g. SSH runs on TCP/22 (HTTP on 80, HTTPS on 443). UDP is best effort with no guarantee, sends datagrams, enforces no handshake, does not acknowledge or retransmit, and e.g. DNS runs on UDP/53.
Q6

Name the two parts of an HTTP message and explain the difference between GET, HEAD and POST.

Answer: Every HTTP request/response has a header (meta-data such as cookies and connection info) and an optional body. GET is a simple header-only request; HEAD is the same as GET except the server omits the body in the response (headers only); POST sends data in the body, such as form data or a file upload.
Q7

Explain the roles of the load balancer, DDoS mitigation and CDN in an internet-facing architecture.

Answer: The load balancer routes requests across a pool of servers based on health/performance or content, and can perform SSL offloading and HTTP→HTTPS port forwarding. DDoS mitigation (e.g. a web application firewall such as CloudFlare) is the first layer, dropping attack packets and forwarding legitimate ones. A CDN caches content closer to users.
Q8

What are the three typical forms of an application server, and what does an app server contain?

Answer: Forms: virtual machines (IaaS, e.g. EC2, GCE), containers (docker) and serverless (Lambda, Google Cloud Function). An app server contains back-end website code, business logic, database interface methods and caching layers, and is where the majority of the work lies.
Q9

Distinguish SQL from NoSQL databases with examples, then explain the master/slave model.

Answer: SQL databases are relational and maintain/enforce relationships between data (MySQL, PostgreSQL, SQLite, Microsoft SQL Server). NoSQL databases are non-relational, storing data like loose pages often without schemas (MongoDB, Redis, DynamoDB). In the master/slave model there is usually one master that accepts reads and writes; updates replicate to many read-only slaves, which parallelise reads.
Q10

What is slave drift and how should an application handle it?

Answer: Slave drift (replication delay) is the small but significant time lag between a write to the master and its propagation to all slaves. Reads leading to important decisions, such as payments, should be made against the master to avoid race conditions or side effects from stale data. Alternative replication configurations avoid it but trade off delayed writes and/or reduced fault tolerance.
Q11

Give the meaning of the 1xx–5xx HTTP status classes and the specific meaning of 200, 301, 302, 304, 404 and 502.

Answer: 1xx informational, 2xx success, 3xx redirection, 4xx client error, 5xx server error. 200 OK is the standard success response; 301 Moved Permanently; 302 Found/Moved Temporarily (browser immediately follows the Location header); 304 Not Modified; 404 Not Found; 502 Bad Gateway.
Q12

What is the DOM and how do CSS and JavaScript relate to it?

Answer: The DOM (Document Object Model) is the browser's internal tree representation of an HTML page, defining relationships between elements such as <div> and <img>, manipulable by JavaScript. CSS specifies positional and appearance attributes of DOM elements (via <style> tags or linked external files); JavaScript performs arbitrary computation, often manipulating the DOM live (via inline <script> or src).
Q13

Convert a problem statement into use cases: define actor and action and list the four-step process.

Answer: An action is a simple, distinct, easily defined operation performed by an actor; an actor is a role within the system, not an individual. Process: (1) identify the flow of events, (2) extract distinct actions, (3) group associated actions into a high-level use case, (4) expand use cases into extensions.
Q14

What is an SRS, why does it matter, and what are its three main parts?

Answer: A Software Requirements Specification details exactly what the system does and does not do; it is a communication tool between stakeholders and designers, lets you declare the project finished, and mitigates scope creep. Its three parts are the Introduction (purpose, definitions, system overview, references), the Overall Description (product perspective, interfaces, constraints, user characteristics, etc.) and the Specific Requirements (external interface, functional, performance, logical database requirements, and software system attributes: reliability, availability, security, maintainability, portability).
