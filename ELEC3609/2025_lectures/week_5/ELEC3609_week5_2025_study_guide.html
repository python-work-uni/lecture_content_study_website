Client–Server Communication and Backend Web Development

This week covers how a browser and a server actually talk to each other — the data formats (XML, JSON), the protocol (HTTP), and the headers that carry requests, cookies, content types and identity — then moves to the backend: how to model data, how the TIL app's entities and relationships are drawn, how MVC and MTV split responsibilities, and the toolchain (Git, Python, pip, virtual environments, IDEs) you will use all semester.

Read this first: Almost every modern app is a conversation between a client (the browser) and a server (the program holding the data). One side must format the data, the other must understand the format, and both must agree on a protocol and a set of headers to carry it. Keep that single picture in mind: format → protocol → headers for communication, then model → view → controller for the code that serves it.

  • Contrast MVC and MTV and say which layer handles data, requests and presentation.
  • Set up a Python project with Git, pip and an isolated virtual environment, and explain why each exists.

The Problem of Client–Server Communication

Two machines that do not share memory must agree on what to send and how to send it before anything works.

A client is the program that asks for something (typically a web browser). A server is the program that holds resources and answers. Because they are separate processes — often on separate machines — they cannot share variables or function calls directly. They need two agreements:

  • A format for the data (how a book, a user, or a post is written down).
  • A way to transmit and receive that data reliably over a network.

This is the whole foundation of the web: without a shared format and transport, the server's data is meaningless noise to the client.

General Client–Server Communication Mechanisms

MechanismWhat it isTypical use
SocketsA raw bidirectional connection between two endpointsLow-level network programming
Remote procedure calls (RPC)Calling a function that runs on another machine as if it were localDistributed systems, APIs

ℹ️
Note: You do not have to implement sockets, RPC or pipes in this course — you need to recognise them as the underlying mechanisms that higher-level formats and protocols are built on.

MIME Types: Labelling the Format

MIME (Multipurpose Internet Mail Extensions) type is the standard label that determines the file format and the format's contents. The catalogue of these labels is maintained by IANA. A MIME type is written as type/subtype, for example:

  • text/html — an HTML web page
  • image/png — a PNG image
  • application/json — JSON data
  • text/css — a CSS stylesheet
💡
Why it matters: When a browser receives bytes, the MIME type is how it decides whether to render them as a page, show an image, or hand them to JavaScript. Get the type wrong and the client interprets the data incorrectly.

XML — A Language for Describing Languages

XML defines the rules for encoding documents and lets you define the schemas that other tag-based languages obey.

XML (Extensible Markup Language) defines a set of rules for encoding documents. Crucially, it is a language for describing the rules of other languages: XML lets you define schema|schemas for tag-based languages. A schema is effectively a contract for communication between client and server — both sides agree on the structure before exchanging data.

XML is:

  • a markup language, not a programming language (it has no logic or loops);
  • human-readable (you can read it in a text editor);
  • machine-readable (programs can parse it deterministically);
  • designed to be self-descriptive (tags carry their own meaning);
  • designed to carry and transport data, not to display it (presentation is someone else's job).

XML Terminology

  • Markup: the elements that define the structure of the document. Usually enclosed by < and > or by & and ;.
  • Content: all the information between markup.
  • Tag: a type of markup that begins with < and ends with >. There are three flavours:
  • start tag: <section>
  • end tag: </section>
  • empty-element tag: <img src="dog.jpg"/>
  • Attribute: markup on a start tag or empty-element tag that defines key–value pairs about that element, e.g. <img src="dog.jpg" alt="woof"/> has the attributes src="dog.jpg" and alt="woof".
🧠
Memory hook: Three tag flavours = start, end, empty. An empty-element tag closes itself with />, so it needs no separate end tag.

A Complete XML Example

<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE book SYSTEM "book.dtd">
<book language="en" author="Huaming Chen">
  <title>Internet Software Platforms</title>
  <chapter>
    <heading>Client Server Communication</heading>
    <paragraph>HTTP is a request-response protocol.</paragraph>
  </chapter>
</book>

Document Types: DOCTYPE and DTD

To define which fields are allowed in an XML document, and in what structure, you provide a document type declaration (DOCTYPE). The DOCTYPE identifies a document type definition (DTD), which defines the fields and their structure.

For the XML book example, the DTD is:

<!ELEMENT book (title , chapter+)>
<!ELEMENT chapter (heading , paragraph*)>
<!ELEMENT heading (#PCDATA)>
<!ELEMENT paragraph (#PCDATA)>
<!ATTLIST book
  language CDATA #REQUIRED
  author   CDATA #REQUIRED
>

Read this like a grammar: a book contains exactly one title followed by one or more chapters (+ means one-or-more). Each chapter contains one heading then zero or more paragraphs (* means zero-or-more). #PCDATA means parsed character data (plain text). The ATTLIST declares that book requires both a language and an author attribute (#REQUIRED).

✅
Exam tip: Be able to explain the symbols: + = one or more, * = zero or more, #PCDATA = text content, #REQUIRED = the attribute must be present.

JSON — Lightweight Data Representation

JSON borrows JavaScript's object syntax to give the web a compact, language-independent way to represent data.

JSON (JavaScript Object Notation) is an open-standard format for representing data online. As the name suggests, it is based on how objects are represented in JavaScript. It is language-independent and supported by most programming languages, which is why it became the web's default data interchange format.

JSON is typically used for:

  • API requests/responses — the body of most modern web APIs;
  • Serialization — turning in-memory objects into text that can be stored or sent;
  • Configuration files — settings for tools and apps.

A JSON Example

{
  "id": 42,
  "username": "abc123",
  "public": true,
  "postDate": "2025-09-01",
  "tags": ["http", "cookies"]
}

XML

  • Tag-based markup with start/end tags
  • Can define and validate structure with a DTD/schema
  • More verbose; good for documents and strict contracts
  • Self-descriptive and human-readable

JSON

  • Key–value pairs with {} objects and [] arrays
  • Lighter and faster to parse; native to JavaScript
  • The default for API request/response bodies
  • Also human-readable but far less verbose
💡
Why it matters: Both carry data and neither displays it. Choose XML when you need a formal, validated schema (a strict contract); choose JSON for lightweight API data where speed and simplicity matter.

HTTP — The Request-Response Protocol

HTTP is the language of the web: a client makes a request, and the server responds — usually with a web page.

HTTP (Hypertext Transfer Protocol) is designed to allow communication between an HTTP client and an HTTP server. HTTP works as a request-response protocol: a client makes a request, and the server responds, generally with a web page. This is important — HTTP is stateless, so each request stands alone unless something (like a cookie) carries state forward.

An HTTP Request

A client sends an HTTP request to the server. An example request to www.elec3609.com/index.html:

GET /index.html HTTP/1.1
Host: www.elec3609.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)
Accept: text/html
Cookie: username=abc123; authToken=4f3e

Anatomy: the request line names the method (GET), the path (/index.html) and the protocol version (HTTP/1.1). Each following line is a header in Name: value form, ending with a blank line.

An HTTP Response

The server sends a response, which the browser then renders into a web page:

HTTP/1.1 200 OK
Content-Type: text/html; charset=UTF-8
Set-Cookie: authToken=4f3e

<html>
  <body><h1>Welcome to ELEC3609</h1></body>
</html>

Anatomy: the status line gives the protocol version, a status code (200 = OK) and a reason phrase, followed by headers and then the body (the resource itself).

🧠
Memory hook: A request is "please give me this"; a response is "here it is, and here is what it is." The response's Content-Type tells the browser how to interpret the body.

HTTP Methods — What a Request Wants to Do

The method (verb) on the request line tells the server what operation the client wants to perform on a resource.

These are the most commonly used HTTP methods:

  • GET: used to request data about a specified resource. (Read-only; safe to repeat.)
  • POST: used to create a resource.

Many more exist:

MethodPurpose
PUTCreate/update a resource
PATCHPartial modification of a resource
DELETEDeletes the specified resource
OPTIONSReturns the supported HTTP methods for this resource
HEADEquivalent to a GET request without the response body
⚠️
Common trap: POST creates, while PUT creates or replaces a resource, and PATCH only partially modifies it. Do not treat them as interchangeable — "Consistency is key": use methods the way their meaning intends so clients and servers stay predictable.
🤔
Pause & predict: A client needs to change only a user's email address on a large profile resource. Which method is the best fit, and why is PUT the wrong instinct?

Cookies — Carrying State Across Stateless Requests

A cookie is a small piece of data a website stores in the browser, and the browser automatically sends it back on every request to that server.

An HTTP cookie is a small piece of data, set by a website, which is stored in the user's browser. Browsers automatically include all the cookies set by a server with every HTTP request sent to that server. This is what lets a stateless protocol remember who you are.

There are two HTTP headers that control cookies on the web:

  • Requests: the Cookie header sends stored cookies to the server.
  Cookie: username=abc123; authToken=4f3e
  • Responses: the Set-Cookie header tells the browser to store a cookie.
  Set-Cookie: username=abc123
  Set-Cookie: authToken=4f3e

A Typical Login Flow

  1. User visits the website for the first time — no cookie exists yet.
  2. User submits the login form to the server with a username and password — still no cookie.
  3. The server generates an authentication token (auth-tok) and responds with Set-Cookie: token=[auth-tok].
  4. On the next visit, the client automatically sends Cookie: token=[auth-tok].
  5. The server recognises the token and knows the request came from that user.

Cookies are often used for tracking users and authentication. Because cookies are security-sensitive, they support important protective attributes: HttpOnly, Secure and SameSite.

  • HttpOnly — the cookie is not readable by JavaScript, reducing theft via cross-site scripting.
  • Secure — the cookie is only sent over HTTPS.
  • SameSite — restricts the cookie from being sent on cross-site requests, mitigating CSRF.
💡
Why it matters: HTTP is stateless, but real apps need to remember you between requests. Cookies are the bridge — and because they are powerful, the HttpOnly/Secure/SameSite attributes are what keep them safe.

HTTP Headers That Describe the Exchange

Three headers tell the two sides what format is acceptable, where the user came from, and what software is asking.

Content Type — Negotiating the Format

A request uses the Accept header to indicate to the server which data types it will accept in the response. A client can define multiple data types that it supports, e.g. Accept: text/html, application/json.

The response defines the Content-Type header, which determines what type of data is contained in the body of the response. This is an indication to the browser as to how it should interpret the response.

Accept (request)

  • Sent by the client
  • Lists the MIME types the client can handle
  • May list several, separated by commas

Content-Type (response)

  • Sent by the server
  • Declares the actual format of the response body
  • Tells the browser how to interpret the bytes

Referer — Where the User Came From

The Referer header is sent with requests made by a browser. It indicates to the server the previous page the user was on. Example:

  • I go to www.google.com and search for "elec3609".
  • I click the link to the www.elec3609.com website.
  • The browser's request to www.elec3609.com includes a Referer header containing the previous address: https://www.google.com/.

User-Agent — What Software Is Asking

The User-Agent header tells the server what type of software the client is using. It typically includes:

  • Browser
  • Rendering engine
  • Operating system
ℹ️
Note: The spelling "Referer" is a historical misspelling that stuck in the HTTP standard — expect the single-r spelling in headers. Servers use it for analytics and, sometimes, for security checks on where traffic originates.

Data Modelling — From Requirements to Structure

Data modelling turns fuzzy requirements into a precise, analysable structure that a database can store.

Data modelling is the process of defining and analysing the data requirements of an information system. It happens before you write application code, because getting the structure wrong is expensive to fix later. The process involves:

  1. Identify the detailed system requirements.
  2. Normalise the entities.
  3. Write the data model.

We use UML to develop a formalised entity-relationship diagram (ERD), drawn using Crow's foot notation (so called because the "many" end of a relationship looks like a bird's foot).

Example Website: TIL

We model a social "Today I Learned" platform called TIL.

TIL Rough Requirements

  • A user can sign up with a username and password.
  • Users can make posts, consisting of:
  • Subject
  • Content
  • Post date
  • Posts can be:
  • public (visible to all users) or private (visible only to the creator);
  • associated with zero, one or more tags.
  • Tags are free-form text labels that are dynamically created when first used.
✅
Exam tip: Notice how "posts can be public or private" becomes a single boolean field, while "zero, one or more tags" becomes a many-to-many relationship. Reading requirements carefully tells you which structures you need.

ERD, Models, Keys and Relationships

An ERD becomes real as tables: each entity is a table, each table has an id primary key, and relationships are expressed with foreign keys.

Models

A model describes the fields which hold information about a particular entity. Each attribute of a model has a designated type, such as:

  • String
  • Numeric
  • Boolean
  • Date/Time

An entity is represented by a single table in a database. Each table should have an id field, which uniquely identifies each row, as the primary key. Each of the entities in an ERD can be considered a model.

Foreign Keys — Expressing "One-to-Many"

Models rarely exist in isolation — they have relationships with other models. A relationship to another model is expressed through a foreign key (FK). Foreign keys specify a one-to-many relationship.

TIL example: A Post can be associated with one User. Posts therefore contain a foreign key to their associated User.

🧠
Memory hook: "One-to-many" = a mother may have many children, but a child has only one mother. The "one" side is the parent; the "many" side carries the foreign key pointing back to the parent.

Many-to-Many Relationships

To achieve a many-to-many relationship, we typically use an intermediate table (a join table) to express the relationship.

TIL example: A Post can be associated with many Tags, and a Tag can be applied to many Posts. So neither table can hold a single foreign key — a third, intermediate table links each Post to each Tag.

🧠
Memory hook: "Many-to-many" = an Author can write several Books, and a Book can be written by several Authors. You cannot store that with one FK on either side — you need a link table.

Putting the TIL ERD Together

Entity (table)Key fieldsRelationships
Userid, username, passwordone-to-many → Posts
Postid, subject, content, post_date, is_public, user_id (FK)many-to-one → User; many-to-many → Tag
Tagid, name (free-form)many-to-many → Post
PostTag (intermediate)post_id (FK), tag_id (FK)resolves Post ↔ Tag many-to-many
💡
Why it matters: The ERD is the contract for your database. Primary keys guarantee every row is uniquely identifiable; foreign keys and intermediate tables encode how records relate, so the application can join them correctly.

MVC and MTV — Structuring the Application

MVC splits code into Model, View and Controller; the MTV variant renames the roles so the framework (Django) maps cleanly onto them.

Model-View-Controller (MVC)

A common way to structure the code of a web application is the model-view-controller (MVC) architecture. In this pattern, code functionality is separated into three responsibilities:

  • Model: handles the data.
  • View: renders data into views (usually HTML).
  • Controller: interprets requests and encapsulates business logic.

The benefit is separation of concerns: the data, the presentation and the request-handling logic can change independently.

Model-View-Template (MTV)

The framework used in this course (Django) uses Model-View-Template (MTV), which is the same idea with different names:

  • Model: similar to MVC — handles the data and logic part, and maintains a connection with the database.
  • View: works differently from the View layer of MVC. Here the view accepts the requests and sends out the response (i.e. it behaves like MVC's controller).
  • Template: the presentation layer. It is commonly coded in HTML or DTL (Django Template Language).

MVC

  • Model → data
  • View → renders data (HTML)
  • Controller → interprets requests + business logic

MTV (Django)

  • Model → data + database connection
  • View → accepts requests, sends response
  • Template → presentation (HTML/DTL)
⚠️
Common trap: The names are misleading across the two patterns. MVC's View renders output; MTV's View handles requests, and MTV's Template does the rendering. Map by responsibility, not by name.

Development Environment — Version Control with Git

A version control system tracks every change so you never again name a file "final_v2_copy_SUBMITTED".

A version control system (VCS) helps keep track of changes to a file or files. Without one, you end up with chaos like:

Report_draft.doc
Report_draft_final.doc
Report_draft_finalv2.doc
Report_draft_final - Copy.doc
Report_fixed.doc
Report_SUBMITTED.doc

A VCS eliminates that by giving you many other benefits:

  • Improved ability to collaborate;
  • Compare changes made to a file over time;
  • Revert to a previous version of a file.

Common Version Control Software

  • Git: the industry-standard tool, and what this course uses. Git integration is supported by GitHub and BitBucket, two leading online repository hosting providers.
  • SVN (Apache Subversion): an older VCS that is fading in popularity.
  • Hg (Mercurial): an alternative VCS written in Python.
✅
Exam tip: Practise Git! It is used extensively in this course and in your career — the sooner you master it, the easier your life will be.

Python, Package Managers and Virtual Environments

Python is the prescribed backend language; pip installs its packages, and virtual environments keep each project's dependencies isolated.

Python

Python is the prescribed backend language for this course. It is an interpreted high-level programming language (interpreted = run line-by-line by an interpreter, not compiled ahead of time; high-level = abstracts away machine details).

Package Managers

A package manager is a piece of software for managing dependencies — libraries or extensions which add functionality or features to a language. Common package managers:

LanguagePackage manager
Pythonpip
NodeNPM
PHPComposer
RubyRubyGems

pip is the standard Python package manager. It lets us easily install Python packages onto our system:

pip install django

This will fetch and install the Django package and its dependencies.

The Problem: Conflicting Dependencies

Python only allows us to install one version of a package at a time. So how do we handle conflicting project dependencies?

  • Awesome Website requirements: simplejson == 3.16, django == 3.1
  • Better Website requirements: simplejson <= 3.17, django >= 3.2

It is not possible to find a set of requirements that satisfies the desired versions across both projects with a single global install. Symbolic links are a hacky non-answer.

The Solution: Virtual Environments

To solve this, we use Python Virtual Environments. Virtual environments allow us to have multiple, isolated installations of Python. Each virtual environment can have its own Python dependencies without conflicting with each other.

Key rules:

  • A virtual environment must be activated before it can be used.
  • Do not commit your virtual environment into your repository.

Virtual Environments in Python 3

The venv module was shipped since Python 3.3, meaning support for virtual environments is built-in. Each venv has its own site-packages and Python executable, isolated from the system install. To create one, run:

python3 -m venv myenvname
🧠
Memory hook: A virtual environment is a sandbox per project: its own Python, its own packages, no fights with other projects. Create it, activate it, and never commit it.

Integrated Development Environments

An IDE is a text editor plus the tools that make coding faster and less error-prone, all in one window.

An Integrated Development Environment (IDE) makes writing code easier by combining a text editor with additional features:

  • Debugger
  • Syntax highlighting
  • Version control
  • Refactoring
  • Search

Some commonly used IDEs:

  • Visual Studio Code
  • PyCharm
  • Eclipse
ℹ️
Note: You can write Python in a plain editor, but an IDE bundles debugging, version-control integration and refactoring into one place — which pays off quickly on a multi-week project like TIL.

Practice Questions

Look away from the page first — retrieval is what builds memory.

Answer, reveal, then tick “Mastered”. Your progress is saved.
Q1

Why do a client and a server need a shared schema before they can exchange data?

Answer: Because they are separate processes that do not share memory, so the bytes one sends are meaningless unless both sides agree on the format and structure. A schema acts as a contract that defines which fields exist and how they are organised, so the receiver can correctly parse what the sender encoded.
Q2

Name the three tag flavours in XML and give an example of each.

Answer: Start tag <section>, end tag </section>, and empty-element tag <img src="dog.jpg"/>. The empty-element tag closes itself with /> and needs no separate end tag.
Q3

In the book DTD, what do chapter+, paragraph*, #PCDATA and #REQUIRED mean?

Answer: chapter+ means one or more chapters; paragraph* means zero or more paragraphs; #PCDATA means the element contains parsed character data (plain text); #REQUIRED means the attribute must be present on the element.
Q4

What is the difference between XML and JSON, and when would you prefer each?

Answer: XML is a tag-based markup language that can define and validate structure via a DTD/schema, making it good for documents and strict contracts; it is more verbose. JSON is a lighter, language-independent key–value format that is native to JavaScript and is the default for API request/response bodies, serialization and config. Prefer XML when you need formal schema validation; prefer JSON for lightweight API data.
Q5

Describe the structure of an HTTP request and an HTTP response.

Answer: A request begins with a request line — method, path and protocol version (e.g. GET /index.html HTTP/1.1) — followed by headers and a blank line. A response begins with a status line — version, status code and reason phrase (e.g. HTTP/1.1 200 OK) — followed by headers and then the body (the resource, often HTML).
Q6

What does each of GET, POST, PUT, PATCH, DELETE, OPTIONS and HEAD do?

Answer: GET requests data about a resource; POST creates a resource; PUT creates or updates a resource; PATCH partially modifies a resource; DELETE deletes a resource; OPTIONS returns the supported methods for the resource; HEAD is equivalent to GET but without the response body.
Q7

Why are cookies necessary even though HTTP is stateless, and which headers set and return them?

Answer: HTTP treats each request independently, so without extra state a server could not recognise a returning user. A cookie is stored in the browser and automatically sent with every request to that server, carrying identity forward. The server sets cookies with the Set-Cookie response header, and the client returns them with the Cookie request header.
Q8

Walk through the five steps of a typical cookie-based login flow.

Answer: (1) User visits with no cookie. (2) User submits username and password — still no cookie. (3) Server generates an authentication token and replies Set-Cookie: token=[auth-tok]. (4) On the next visit the client sends Cookie: token=[auth-tok]. (5) The server recognises the token and knows the request came from that user.
Q9

Explain the difference between the Accept and Content-Type headers.

Answer: Accept is a request header in which the client lists the MIME types it is willing to receive, possibly several. Content-Type is a response header in which the server declares the actual format of the response body, telling the browser how to interpret the bytes.
Q10

What do the Referer and User-Agent headers tell a server?

Answer: Referer indicates the previous page the user was on (for example https://www.google.com/ after clicking a search result). User-Agent tells the server what software the client is using, typically the browser, rendering engine and operating system.
Q11

What are the three steps of data modelling, and how is the result expressed?

Answer: (1) Identify the detailed system requirements, (2) normalise the entities, (3) write the data model. The result is expressed as a formalised entity-relationship diagram (ERD) drawn with UML using Crow's foot notation.
Q12

In the TIL app, how is a Post's relationship to a User modelled, and how is a Post's relationship to Tags modelled?

Answer: A Post relates to one User, which is a one-to-many relationship: the Post table holds a foreign key (user_id) pointing to the User's primary key. A Post can have many Tags and a Tag can apply to many Posts, which is many-to-many: it is implemented with an intermediate table holding foreign keys to both Post and Tag.
Q13

What is the difference between MVC and Django's MTV, and what is the trap?

Answer: MVC splits code into Model (data), View (renders data as HTML) and Controller (interprets requests and holds business logic). In MTV, Model handles data and the database connection, View accepts requests and sends responses, and Template is the presentation layer written in HTML or DTL. The trap is mapping by name: MTV's View behaves like MVC's Controller, and MTV's Template does the rendering that MVC's View does — map by responsibility, not by name.
Q14

What problem do Python virtual environments solve, and what are the two key rules?

Answer: Python allows only one version of a package at a time, so projects with conflicting version requirements cannot share a single global install. Virtual environments give each project an isolated Python with its own dependencies. The rules are: activate the environment before using it, and never commit it into your repository.
