Introduction
The quality of a web application is critical.
This lecture will not cover why testing is important or the value 
of testing. Almost every course you have taken will have covered 
this already.
This lecture will instead focus on fundamental testing concepts, 
like verifying the correctness of a web application and systems in 
general.
Applying a combination of these techniques for your assignment 
will assist in ensuring that your application has been deployed 
successfully and meets the requirements.

Test 101
Each test takes time to write, maintain and execute. As such, we 
should make sure each test provides value.
A good way to think about testing is that we have a budget for 
time spent on tests. Focus your time where it will provide the 
most value first.
Breadth vs depth vs critical functionality. E.g. Users can’t do 
much unless they can log-in to the website.

Unit Testing
Unit, or functional, testing is the process of verifying 
functionality and components independently of the whole system.
The aim is to test the smallest testable piece of code that can be 
isolated, ideally a single function/method/subroutine.
One approach is to mock out other dependencies.
Example: testing the validate email function.

System Testing
System testing is the process of verifying the bahaviour and 
functionality of the entire system, including:
- Security
- Performance
- Reliability
- External interfaces
Also commonly referred to as end-to-end testing.

Acceptance Testing
Acceptance testing is the process of verifying that desired 
acceptance criteria are met from the user’s perspective and that 
the system satisfies the business requirements.
Each use-case should be covered by one or more acceptance tests.
While this is a more objective view of a system, it can still be 
automated.

Black-box/White-box Testing
Black-box testing:
- No programming/software/implementation knowledge.
- Tests based only on specification or design.
- Usually used for System and Acceptance testing.
- An external tester is ideal as they won’t have any bias based 
on knowledge of the implementation.
White-box testing:
- Utilize knowledge of the implementation to design tests cases 
to cover key paths.
- Usually used for Unit and Integration testing.
- Written by the developer to verify their code.

Regression Testing
Regression testing is the process of verifying that incremental changes 
have not broken existing functionality.
It makes sense to run the full suites of tests after any code, 
infrastructure or configuration change. These tests can almost 
immediately identify issues and help narrow down any problems.
This helps to highlight possible errors and/or backwards incompatible 
changes when run preemptively during development.
A comprehensive suite can take minutes, need to determine where the 
best place to run these. A common approach is after any manual or unit 
tests are run as another check and again before commit/push.

Brute-forcing all input combinations?
Can we just brute force all possible inputs and test them all?
•
Yes, sometimes. But it’s not a great idea and almost never worth the 
time.
Most systems are complex enough that the sheer number of 
combinations of inputs means you’ll be running tests for a long period 
of time when attempting them all.
•
Consider a phone:
o Does it make sense to attempt to call every single phone number to verify 
call functionality? Is that a good use of time if it took weeks?
•
There will still be gaps:
o Concurrency
o Order of inputs or timing of requests
o Random seeds/input
o Hardware failure

Fuzzing
Automated tools that can generate invalid and non-standard 
inputs and test the behavior of a system
The idea with fuzzing is to define the valid inputs and have the 
fuzzer generate input that is semi-valid to test boundary 
conditions.
They can highlight:
• Unhandled edge cases
• Non-performant code
• Possible crashes (memory leaks) and security concerns

Performance and Load Testing
Determines how well a system performs under known workloads. 
By adjusting the stress factor, we can simulate high load and 
identify bottlenecks in our system. 
Volume testing is a way to test functionality under load. 
Stress testing is a way to test reliability under load. 
Load testing is a way to test performance under load.
Important to ensure that simulated workload is realistic. 
We want the site to handle 10,000 concurrent users during peak 
so we’ll test how it performs with: 1000, 5000, 10,000, 15,000 
simulated users.

Robustness/Destructive Testing
Destructive testing intentionally causes failures in components of 
the system to test how the system performs. 
Designed to answer the following: 
• Will our system recover if it fails? 
• Will we lose data? 
• How long will it take to recover? 
• Do we have backups? 
• Do they work? 
• Who knows how to fix?

--- Slide 22 ---

Netflix Simian Army
Netflix desires high uptime and availability and they have 
developed a suite of automated tools to test how well their 
production systems handle particular failure/abnormal scenarios:
• Chaos Monkey: Randomly disables production instances. 
• Latency Monkey: Introduces artificial delay in the client-
server communication layer. 
• Conformity Monkey: Detects abnormal instances that don’t 
adhere to best practices and terminates them. 
• Doctor Monkey: Detects instances that are unhealthy and 
routes traffic away from them. This allows for time to 
investigate without sacrificing system stability. 
• Chaos Gorilla: Big Chaos Monkey. Simulates outage of an 
entire availability zone.

--- Slide 31 ---
The University of Sydney

How to design good test cases?
– Prefer quality of tests over quantity. 
– Diversity is key. 
– Aim to cover as many unique tests cases as possible. 
– Cover the basic test cases before looking for the more esoteric 
edge cases. 
– Always consider what could happen if someone was 
intentionally malicious. 
– Don’t forget about possible bugs in libraries. Would your code 
handle it?

Equivalence Partitioning
When making tests cases, it is important to identify clusters of 
inputs that are functionally equivalent or treated similarly by the 
code. 
In the previous example, all odd numbers were treated equally by 
the function, as were all even. When generating tests, there is 
reduced value in multiple odd number tests as we are not 
covering new failure cases. In this case we are partitioning inputs 
based on even-ness. 
Boundary cases are a common cause for issues as we’ll see in the 
next example. Does oddEven handle 0 correctly?

Guideline Based Testing
A lot of code is vulnerable to common logic flaws made by 
programmers. Buffer overflows in common programs/libraries 
are a great example. 
Focus more on issues that are likely to slip by a developer and 
draw their attention to it. 
Did you consider Unicode when handling strings? 
Did you free that memory you allocated? 
Static analysis tools can help automate this technique.

Code Coverage
It is good to estimate which parts of your code are covered by 
tests.
Code coverage tools can highlight, line-by-line, which parts of 
code are executed by tests. However, just because code has 100% 
coverage, does not mean that it is bug-free - just that there is at 
least one test that executes this statement.
Would we be satisfied with only one test for any of our example 
methods covered in previous slides?
Code coverage is only an indicator (not a direct measure) of 
quality.

--- Slide 42 ---
The University of Sydney
Page 42
Code Coverage
Function Coverage: how many of the functions defined have 
been called? 
Statement Coverage: how many of the statements have been 
executed? 
Branch Coverage: how many of the branches of control flow 
structures have been executed? if/elif/else, while, for, switch
Condition Coverage: how many of the boolean conditions 
within branches evaluated to both true and false? 
Line Coverage: raw metric of how many lines have been tested.
