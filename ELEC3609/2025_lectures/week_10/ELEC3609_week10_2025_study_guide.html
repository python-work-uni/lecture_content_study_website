Quality and Testing: From Unit Tests to Defensive Design

A practical tour of how to verify that a web application actually works — the four levels of testing, black-box vs white-box reasoning, regression and non-functional testing, fuzzing, linting, how to design test cases with equivalence partitioning, code coverage metrics, and how defensive programming prevents whole classes of bugs.

Read this first: Testing is not about running every possible input; it is about spending a fixed budget of effort to buy the most confidence. Everything in this guide follows from two ideas — test the smallest unit that can fail in isolation, then test the interactions between units — and from choosing which tests give the most value for the time they cost.

Foundations: Why We Test and How to Spend the Effort

Testing is an investment of a limited budget, so spend it where it buys the most confidence — critical functionality and breadth first, depth second.

The quality of a web application is critical, but the interesting question is not whether testing matters — almost every course covers that — it is how to verify correctness of a web application and of software systems in general. Applying a combination of the techniques in this guide is what lets you confidently say an application has been deployed successfully and meets its requirements.

Test 101: tests cost time

Every test you write must be written, then maintained, then executed — again and again. Each of those steps costs time. The practical consequence is that you should only keep tests that provide value.

💡
Why it matters: Think of testing as having a budget of time. You cannot test everything, so focus your time where it returns the most value first.

When deciding where to spend that budget, weigh three competing pulls:

  • Breadth — cover many features lightly.
  • Depth — cover one feature exhaustively.
  • Critical functionality — cover the paths everything else depends on.

A concrete example of critical functionality: users cannot do much of anything unless they can log in. So login deserves attention before an obscure settings toggle does.

🤔
Pause & predict: If you had only one hour to test a signup-and-login website, would you spend it trying every password length, or making sure the login flow works end-to-end for a normal user? Justify your choice in terms of the budget idea.

The Four Levels of Testing

Testing is organised into levels that zoom out from a single function to the whole business need, and each level answers a different question.

Unit (functional) testing

Unit testing is the process of verifying functionality and components independently of the whole system. The aim is to test the smallest testable piece of code that can be isolated — ideally a single function, method or subroutine. To isolate it, you often mock out other dependencies. Example: testing a validate_email function on its own.

Integration testing

Integration testing is the process of verifying the interactions and communication between software components. Here a component is usually defined as a module or class. Stubs and drivers are commonly used to stand in for the pieces that are not yet available or that you want to control.

System testing

System testing verifies the behaviour and functionality of the entire system, including:

  • Security
  • Performance
  • Reliability
  • External interfaces

It is commonly referred to as end-to-end testing.

Acceptance testing

Acceptance testing verifies that the desired acceptance criteria are met from the user's perspective and that the system satisfies the business requirements. Each use-case should be covered by one or more acceptance tests. Although it takes a more objective, user-facing view, acceptance testing can still be automated.

Memory hook: Zoom out in four steps — one function (unit) → functions talking (integration) → whole system (system) → does the user accept it (acceptance).

Black-box vs White-box Testing

Black-box testing ignores the implementation and tests against the specification; white-box testing uses knowledge of the code to target key paths.

Black-box testing

  • No programming, software or implementation knowledge is required.
  • Tests are based only on the specification or design.
  • Usually used for System and Acceptance testing.
  • An external tester is ideal here, because they carry no bias from knowing how the code works.

White-box testing

  • Uses knowledge of the implementation to design test cases that cover key paths through the code.
  • Usually used for Unit and Integration testing.
  • Written by the developer to verify their own code.

Black-box

  • Driven by the spec, not the code
  • No implementation knowledge
  • External tester is ideal (no bias)
  • Used for System & Acceptance testing

White-box

  • Driven by knowledge of the code
  • Targets key control-flow paths
  • Written by the developer
  • Used for Unit & Integration testing
💡
Why it matters: Because a black-box tester does not know the implementation, they are more likely to exercise the unexpected input that a developer unconsciously assumed away — exactly the inputs that break systems.

Regression Testing

Regression testing proves that new changes have not quietly broken behaviour that used to work.

Regression testing is the process of verifying that incremental changes have not broken existing functionality. It makes sense to run the full suite of tests after any code, infrastructure or configuration change. These tests can almost immediately identify issues and help narrow down where a problem was introduced. Run preemptively during development, they highlight possible errors and backwards-incompatible changes.

A comprehensive suite can take minutes to run, so you must decide where the best place to run it is. A common approach is:

  • after any manual or unit tests, as an additional check, and
  • again before commit/push.
✅
Exam tip: Regression testing is defined by its purpose (catching breakage from change), not by a level. It can be run at any level and is triggered by change events, not by a phase of development.

Why Not Brute-Force Every Input? And Fuzzing

Testing every possible input is combinatorially impossible, so we sample intelligently — and let fuzzers generate the hostile inputs we would never think of.

The brute-force question

Can we just test all possible inputs? Yes, sometimes — but it is not a great idea and is almost never worth the time. Most systems are complex enough that the sheer number of input combinations means you would be running tests for a very long period to attempt them all.

Consider a phone: does it make sense to call every single phone number to verify call functionality? Even if you spent weeks, you would still have gaps, because brute force does not cover:

  • Concurrency — simultaneous operations interfering with each other.
  • Order of inputs / timing of requests — the same inputs in a different sequence behave differently.
  • Random seeds / random input — non-determinism.
  • Hardware failure — the environment breaking underneath the software.

Fuzzing

Fuzzing uses automated tools that generate invalid and non-standard inputs and test the behaviour of a system. The idea is to define the valid inputs, then have the fuzzer generate semi-valid input that pushes against boundary conditions.

Fuzzers can highlight:

  • Unhandled edge cases
  • Non-performant code
  • Possible crashes (including memory leaks) and security concerns
⚠️
Common trap: Passing your normal test suite tells you nothing about malformed, oversized or adversarial input. Fuzzing exists precisely because developers test the inputs they expect, not the inputs an attacker or a corrupted client will send.

Non-Functional Testing: Performance, Load, Stress and Volume

Non-functional testing measures how the system behaves under load rather than whether a feature is correct.

Performance and load testing determines how well a system performs under known workloads. By adjusting the stress factor, you simulate high load and identify bottlenecks in the system.

Three closely related variants differ in what they probe under load:

  • Volume testing — tests functionality under load.
  • Stress testing — tests reliability under load.
  • Load testing — tests performance under load.

It is important that the simulated workload is realistic. Example: if the site must handle 10,000 concurrent users at peak, you test how it performs with 1,000 → 5,000 → 10,000 → 15,000 simulated users, so you can see where it degrades and whether it holds at and beyond the target.

🧠
Memory hook: Volume = does it still work? Stress = does it stay up? Load = is it fast enough?

Security, Usability and Robustness Testing

Beyond speed and correctness, you must test whether the system is safe, understandable, and able to survive failure.

Security testing

Required to ensure that our system is secure. A useful checklist is the top 10 vulnerability list (the well-known catalogue of the most common web security flaws).

Usability testing

Designed to test whether a website is intuitive and discoverable by users. Common techniques:

  • Hallway testing — grabbing random people to try it.
  • Expert review — a specialist evaluates the interface.
  • A/B testing — showing two variants and comparing which performs better.

Robustness / destructive testing

Destructive testing intentionally causes failures in components of the system to test how the system performs overall. It is designed to answer hard operational questions:

  • Will our system recover if it fails?
  • Will we lose data?
  • How long will it take to recover?
  • Do we have backups?
  • Do they work?
  • Who knows how to fix it?
💡
Why it matters: A system that has never failed has never been tested under failure. Destructive testing is how you discover whether recovery, backups and incident response actually work before a real outage forces the question.

The Netflix Simian Army (Chaos Engineering)

Netflix keeps high availability by deliberately breaking production with automated tools — the industrial version of destructive testing.

Netflix desires high uptime and availability, so it developed a suite of automated tools that test how well its production systems handle particular failure and abnormal scenarios:

  • Chaos Monkey — randomly disables production instances.
  • Latency Monkey — introduces artificial delay in the client-server communication layer.
  • Conformity Monkey — detects abnormal instances that do not adhere to best practices and terminates them.
  • Doctor Monkey — detects unhealthy instances and routes traffic away from them, allowing time to investigate without sacrificing system stability.
  • Chaos Gorilla — a "big Chaos Monkey" that simulates the outage of an entire availability zone.
🧠
Memory hook: Monkey = small, targeted chaos; Gorilla = zone-sized chaos. Conformity cleans up misconfigured instances; Doctor heals unhealthy ones.

Manual vs Automated Testing, and Choosing an Approach

There is no single correct testing strategy — cover your acceptance criteria and pick the mix that fits your framework, program and users.

Manual testing

Manual testing is directly performed by a human operator, whether the developer or a dedicated QA agent. Examples:

  • Exploratory testing — investigating without a scripted plan.
  • Visual regression testing — a human eyeballing whether the UI still looks right.

Automated testing

Automated tests are comprised of many different tools driven by a computer. Examples:

  • End-to-end (E2E) tests
  • Unit tests
  • Integration tests
  • Performance tests

Which approach? The Test Pyramid

The Test Pyramid is a great way of conceptualising where the majority of your tests should go. It minimises the time spent on tests for the most value and leads to issues being caught earlier in development. Its opposite is the Ice Cream Anti-Pattern — top-heavy with slow, brittle tests. An alternative framing is the 3D Testability Polygon.

The guiding principles matter more than the diagram:

  • It is more important to cover your acceptance criteria than to adhere rigorously to a testing strategy. Find an approach that works for your framework, the nature of your program, and the requirements of your users.
  • Consider the cost/value of each test you write.
  • Consider the cost of issues × likelihood for each test case you don't write.
Expected test value
value = (cost of failure × probability of failure) − cost of writing and maintaining the test

Linting

Linters are cheap automated checks that catch programmatic and stylistic errors before they ever reach a test.

Linters are tools which run over your program and identify programmatic and stylistic errors. Typical findings:

  • Unused imports
  • Unreachable code
  • Variable, class or function names that do not conform to style guidelines
✅
Exam tip: Linting is not testing — it does not check whether your logic is correct. It catches a category of low-level mistakes cheaply, freeing your test budget for behaviour that actually matters.

Designing Test Cases and Equivalence Partitioning

Good test cases come from partitioning inputs into groups the code treats the same, then probing the boundaries between them.

How to design good test cases

  • Prefer quality of tests over quantity.
  • Diversity is key — aim to cover as many unique test cases as possible.
  • Cover the basic test cases before chasing more esoteric edge cases.
  • Always consider what could happen if someone were intentionally malicious.
  • Do not forget about possible bugs in libraries — would your code handle it if a dependency misbehaves?

Equivalence partitioning

When making test cases, identify clusters of inputs that are functionally equivalent — that is, treated similarly by the code. In the odd/even example, all odd numbers are treated equally, as are all even numbers. Writing many odd-number tests therefore adds little value, because they do not cover new failure cases. You are partitioning inputs based on even-ness.

Boundary cases are a common cause of issues. In the odd/even example, the sharp question is: does oddEven handle 0 correctly? Zero sits on the boundary between the two partitions and is a classic place for bugs.

💡
Why it matters: One representative per equivalence class gives you the same coverage as hundreds of inputs from that class, at a fraction of the cost — and the boundaries between classes are where the real bugs hide.
🤔
Pause & predict: For a function that validates an age field accepting 0–120, name the equivalence classes and the specific boundary values you would test.

Worked Examples: oddEven, Palindromes and the Signup Form

Three concrete functions show how to turn the partitioning method into a real, diverse list of test cases.

Example 1: odd/even

def oddEven(num):
    # Number is divisible by 2 so is even
    if num % 2 == 0:
        return "Even"
    # Number must be odd
    return "Odd"

Does it work? How would we know? By designing test cases across partitions and edge types:

  • Odd numbers: 1, 3, 5
  • Even numbers: 0, 2, 4, 6
  • Negative numbers: -1, -2, -3
  • Large numbers: max int
  • Invalid data types: string, boolean, float
  • None / Null / Undefined
⚠️
Common trap: In the lecture's own list, the "odd" group was written as 1, 2, 3 — but 2 is even. That is exactly the kind of slip that a careful test case would catch. Always sanity-check that each value really belongs to the partition you put it in.

Example 2: palindromes

Consider isPalindrome(word), which takes a word and returns whether it is a palindrome. Motivating cases include "madam", "12321", and "Madam, in Eden, I'm Adam".

We should consider:

  • Even-length words
  • Odd-length words
  • Empty string: ""
  • Invalid data types: number, object, boolean, …
  • None / Null / Undefined
  • Unicode multi-byte characters
  • Right-to-left languages and/or multi-byte characters

Example 3: user signup form

For a signup form, consider:

  • Empty strings: first/last name, email, date of birth
  • Missing parameters from the request
  • Long string fields: names and email
  • Unicode string fields: names and email
  • Invalid dates: 3000, -1700, 40/15
  • Numeric characters in first/last name
  • Emails that should match some format
🧠
Memory hook: For any string input, run the U.N.E.M. checklist — Unicode, Null/None, Empty string, Malformed/oversized.

Code Coverage

Coverage tells you which lines your tests touched — but it is an indicator of quality, never a guarantee of it.

It is good to estimate which parts of your code are covered by tests. Code coverage tools can highlight, line by line, which parts of the code are executed by tests. However, just because code has 100% coverage does not mean it is bug-free — it only means there is at least one test that executes this statement. Would you be satisfied with only one test for any of the example methods above? Coverage is only an indicator (not a direct measure) of quality.

The main coverage metrics:

  • Function coverage — how many of the functions defined have been called?
  • Statement coverage — how many of the statements have been executed?
  • Branch coverage — how many branches of control-flow structures have been executed? (if/elif/else, while, for, switch)
  • Condition coverage — how many of the boolean conditions within branches evaluated to both true and false?
  • Line coverage — the raw metric of how many lines have been tested.
Coverage vs correctness
100% coverage ≠ 0 bugs — it means every line ran at least once, not that every line was checked for every input.

Defensive Programming and Design Patterns

Instead of only detecting bugs after the fact, design code so that entire classes of bugs cannot occur.

Defensive programming

Hand in hand with verifying the quality of a web application, you can eliminate entire classes of bugs through good code design. Defensive programming comes at the cost of more complicated code, but it ensures your application can deliver on its availability and security requirements.

Consider two programs that open a file and display its output. The defensive version anticipates that the file may be missing, unreadable or malformed and handles that explicitly. The guiding rule: always take advantage of language constructs (in-built design patterns) rather than hand-rolling fragile logic.

Design patterns

Design patterns exist for a reason. They represent consensus from seasoned developers that these patterns will solve common problems. Reusing them means you inherit battle-tested solutions instead of rediscovering the same failure modes.

ℹ️
Note: Testing and defensive design are complementary, not alternatives. Tests detect bugs; defensive design prevents whole categories of them, reducing how much of your testing budget those categories consume.
🤔

Q1

What is the difference between unit testing and integration testing in terms of what each verifies?

Answer: Unit testing verifies the functionality of the smallest isolatable piece of code (ideally a single function/method) independently of the whole system, often by mocking dependencies. Integration testing verifies the interactions and communication between software components such as modules or classes, commonly using stubs and drivers.
Q2

Which testing level is also called end-to-end testing, and what does it cover?

Answer: System testing. It verifies the behaviour and functionality of the entire system, including security, performance, reliability and external interfaces.
Q3

What does acceptance testing check, and how many acceptance tests does each use-case need?

Answer: It verifies that desired acceptance criteria are met from the user's perspective and that the system satisfies business requirements. Each use-case should be covered by one or more acceptance tests. It can still be automated.
Q4

Distinguish black-box from white-box testing, including which levels each usually serves.

Answer: Black-box testing requires no implementation knowledge and designs tests only from the specification or design; it is usually used for System and Acceptance testing, where an external tester is ideal because they have no implementation bias. White-box testing uses knowledge of the implementation to design tests covering key paths; it is usually used for Unit and Integration testing and is written by the developer.
Q5

What is regression testing, and when should the full suite be run?

Answer: Regression testing verifies that incremental changes have not broken existing functionality. It makes sense to run the full suite after any code, infrastructure or configuration change — commonly after manual or unit tests as an extra check and again before commit/push — to catch issues and backwards-incompatible changes early.
Q6

Give two reasons brute-forcing all input combinations is a bad idea, and list two categories of gaps it still leaves.

Answer: It is not a good use of time because complex systems have a combinatorially huge number of input combinations, so exhaustive testing takes far too long and is almost never worth it. It still misses concurrency, order/timing of inputs, random seeds/input, and hardware failure.
Q7

What is fuzzing and what three kinds of problems can it reveal?

Answer: Fuzzing uses automated tools to generate invalid and non-standard (semi-valid) inputs, testing behaviour at boundary conditions after the valid inputs are defined. It can highlight unhandled edge cases, non-performant code, and possible crashes (including memory leaks) and security concerns.
Q8

How do volume, stress and load testing differ?

Answer: Volume testing tests functionality under load, stress testing tests reliability under load, and load testing tests performance under load. All simulate workloads, ideally realistic ones, while adjusting the stress factor to find bottlenecks.
Q9

Describe three Netflix Simian Army tools and the failure each injects.

Answer: Chaos Monkey randomly disables production instances. Latency Monkey introduces artificial delay in the client-server communication layer. Conformity Monkey detects abnormal instances that do not follow best practices and terminates them. Doctor Monkey detects unhealthy instances and routes traffic away. Chaos Gorilla simulates the outage of an entire availability zone.
Q10

What is destructive (robustness) testing, and name three questions it answers.

Answer: It intentionally causes failures in components to test how the system performs. It answers questions such as: will the system recover if it fails, will we lose data, how long will recovery take, do we have backups, do the backups work, and who knows how to fix it.
Q11

What is equivalence partitioning and why does it reduce test count without losing value?

Answer: It identifies clusters of inputs that are functionally equivalent, i.e. treated the same by the code (for example all odd numbers). One representative test per cluster covers the same failure cases as many tests from that cluster, so writing multiple tests within one partition adds little value — while boundary cases between partitions remain important.
Q12

What are the five code coverage metrics, and what does 100% coverage actually guarantee?

Answer: Function coverage (functions called), statement coverage (statements executed), branch coverage (control-flow branches executed), condition coverage (boolean conditions evaluated both true and false), and line coverage (raw lines tested). 100% coverage only guarantees that at least one test executes each statement — it does not mean the code is bug-free; coverage is an indicator, not a direct measure, of quality.
Q13

What is defensive programming, what does it cost, and what does it protect?

Answer: It is designing code so that entire classes of bugs are eliminated through good code design, for example by always using in-built language constructs and design patterns. It costs more complicated code but ensures the application can deliver on availability and security requirements.
Q14

Why is the Ice Cream Anti-Pattern considered bad, and what does the Test Pyramid recommend instead?

Answer: The Ice Cream Anti-Pattern is a top-heavy suite dominated by slow, brittle end-to-end tests. The Test Pyramid recommends the majority of tests be small and fast at the base (unit tests), with progressively fewer integration and end-to-end tests above, minimising time spent for the most value and catching issues earlier.
